# Single-host Docker, converged with Ansible

One Linux machine running both billet roles, provisioned by the `junioryono.billet.host` role instead of by hand. Docker is the backend because its only prerequisite is Docker; Firecracker needs `/dev/kvm`, a guest kernel you build, a Ceph cluster and two bridges before a job can run.

If you would rather do it by hand once to see the moving parts, [docs/getting-started/index.md](../../../../../docs/getting-started/index.md) is the same deployment without Ansible. Read it first if anything below is surprising — it explains the GitHub-side steps in more detail, and they are the ones people get wrong.

## What was actually walked

This example is the end of a walk on a throwaway Ubuntu 24.04 host, not a sketch. What the walk proved, and what it did not:

- **Proven here.** A block generated by `billet init --emit ansible` is accepted by this role unchanged, and a fresh host converges 143 tasks from it. A second converge runs 43 tasks and changes one — starting the service — so everything the role installs is idempotent. A missing App key is refused at input validation rather than inside the upgrade transaction, and a transaction that fails partway rolls the host back to its previous binary, config, units, ledger and service state.
- **Proven on the CLI path, not re-walked here.** A real workflow reaching a runner and going green. That segment is downstream of Ansible and identical either way — the role installs the same binary and the same config the CLI walk used.
- **Not proven.** Anything on non-Ubuntu, on arm64 bare metal, or with more than one machine.

## Prerequisites

A GitHub **organization** (billet cannot onboard a personal account), a Linux host with Docker and passwordless sudo over SSH, and Ansible on your workstation.

## 1. Create the runner group, in GitHub

Do this first — `billet init` refuses to write a Docker config without one. A container shares the host kernel, so billet runs only *trusted* work on it, and trusted means a pool GitHub restricts rather than a promise billet makes.

**Settings → Actions → Runner groups → New runner group**: name it, grant it the repositories you trust (not "All repositories", and **not an empty list** — a group with selected visibility and nothing selected routes nothing, silently), and tick **Restrict this runner group to selected workflows** with the full workflow path including the ref.

## 2. Mint the App, then generate the block

The order matters, and it is the one thing about this path that is not obvious. `billet init` writes `app_id: 0` because the App does not exist yet, and a zero `app_id` is refused when the config is **loaded** — so the role cannot converge that block at all, not with the services disabled and not under `BILLET_MAINTENANCE`. The App has to exist before the block is generated.

On the target host, or anywhere with a billet binary:

```bash
(set -C; printf '%s\n' 'github: {}' > ~/billet-app.yaml)
billet github-app create --org your-org --config ~/billet-app.yaml
```

`set -C` makes the shell refuse an existing `~/billet-app.yaml` rather than truncate it: after a successful run that file is your only local record of the App id, the installation id and the key path, and the App private key is issued exactly once.

Then generate the block against the App you just made:

```bash
billet init --emit ansible \
  --config ~/billet-app.yaml \
  --org your-org \
  --runner-group billet-trusted \
  --workflow 'your-org/your-repo/.github/workflows/ci.yml@refs/heads/main' \
  > group_vars/linux.yml
```

Add `--max-vcpu`/`--max-memory` if you are generating from a machine other than the target, since the emission otherwise measures whatever it is running on.

## 3. Converge

```bash
ansible-galaxy collection install -r requirements.yml
ansible-playbook -i inventory.yml site.yml \
  -e billet_binary_src=/path/to/billet \
  -e billet_github_private_key_src=/path/to/app-private-key.pem
```

Both `-e` inputs are needed only on the first converge; afterwards the role uses what is installed. The key is required whenever the config names a `github.private_key_path`, whichever services are enabled — `billet check` reads it on every host the role touches.

Point a workflow at the tier's label (`billet status` lists them) and dispatch it on a branch the runner group allows.

## When it does not work

**The converge fails inside the upgrade transaction and rolls back.** The message names the failing step; the ledger, binary, units and config are restored. The usual cause is `billet check` refusing the config — a zero `app_id`, or a key that is not where `github.private_key_path` says.

**The converge fails at "Prove committed services are stably active".** The services were installed and started but did not stay up. `journalctl -u billet-server` on the host says why; a 401 from GitHub means the App key and the installation do not match.

**The job queues forever.** That is billet's characteristic failure — the runner-group and workflow-allowlist checks in [docs/getting-started/index.md](../../../../../docs/getting-started/index.md) are the list to work through.
