# A Firecracker host, converged with Ansible

One bare-metal machine running billet with real kernel isolation: every job gets its own microVM, and the cache is an RBD image in a Ceph cluster on that machine's NVMe.

**Read the prerequisites before anything else.** They are most of the work, billet cannot do them for you, and none of them is a default you can accept.

## What this needs that Docker did not

| | |
|---|---|
| **`/dev/kvm`** | Bare metal, or a machine with nested virtualisation. Firecracker is a VMM; there is no software fallback. |
| **A guest kernel** | An uncompressed kernel *you* build and place at `node.firecracker.kernel_image`. Neither this role nor `billet images pull` creates it. `docs/reference/reference-hardware.md` records how the measured host builds one. |
| **A Ceph cluster** | Two pools, and a non-`admin` identity for billet. The role can bootstrap a single-host cluster, but only when you name every disk it may consume — that path is destructive by definition and is never inferred. |
| **Two bridges** | `billet0` for trusted guests, `billet1` for untrusted. The role creates both from `billet_networks`, whose defaults already match what `billet init` generates. |
| **Guest images** | A published generation from `billet images pull`, not a container image. |

If that list is longer than you want, [the Docker example](../single-host-docker/README.md) is the same deployment with none of it, and [`docs/getting-started/index.md`](../../../../../docs/getting-started/index.md) walks it by hand. Start there and come back.

## What has been proven, and what has not

**This example is not walked end to end.** The Docker example is, and says so; this one cannot be, because the maintainers' CI has no `/dev/kvm` and no Ceph cluster. Being specific about the difference:

- **Proven.** A block generated by `billet init --emit ansible --provider firecracker` is accepted by this role: it converges past every input assertion — including the one that checks the provisioning flags against `node.provider` — and runs to the point where it needs the Ceph cluster. That seam is gated in CI, because the Docker emission once produced a block the role refused and nothing noticed.
- **Not proven, though it might read that way.** The gate runs in check mode, and check mode skips the Firecracker download, unpack and install. It would stay green if those were broken. What it covers is whether the block is *accepted*, not whether Firecracker is installed correctly.
- **Not proven either.** Anything from the Ceph cluster onward: pool creation, a guest booting, a job running in a microVM, the cache being mapped. Those are exercised by the maintainers on the reference hardware, not by this example.

Treat the steps below as the shape of the deployment rather than a walkthrough that has been rehearsed for you.

## 1. Prepare the host

Get `/dev/kvm` present, build the guest kernel, and decide the Ceph question. `billet check` reports which of these is missing once a config exists, and is the fastest way to find out where you are.

## 2. Create the runner group, mint the App, generate the block

Identical to [the Docker example's steps 1 and 2](../single-host-docker/README.md) — with one difference that matters. Firecracker can run **untrusted** work, because a microVM isolates the guest kernel. Give `--runner-group` and `--workflow` and you get `trust: trusted` tiers bound to that policy; omit them and you get `trust: untrusted` tiers that attach to the second bridge.

The generated config says which you got, in the comment above `untrusted_bridge`. That comment answers "can I drop this bridge?", so read it rather than assuming.

## 3. Converge

```bash
ansible-galaxy collection install -r requirements.yml
ansible-playbook -i inventory.yml site.yml \
  -e billet_binary_src=/path/to/billet \
  -e billet_github_private_key_src=/path/to/app-private-key.pem
```

Or set `billet_version: v0.3.26` in `group_vars` and let the host fetch a pinned release itself — see the collection README on which of the two to use, because it is a decision about egress rather than convenience.

A dry run (`--check`) is worth doing first. It does not download Firecracker or touch Ceph, and it will tell you about a config the role refuses before anything is changed.

## When it does not work

**`billet check` names a missing prerequisite.** That is the intended way to find them; work through its list.

**The converge stops at a Ceph task.** The cluster is not reachable from this host, or the pools do not exist. `billet_ceph_bootstrap` creates a single-host cluster, and needs `billet_ceph_mon_ip` and `billet_ceph_devices`.

**A guest never boots.** The kernel at `node.firecracker.kernel_image` is the usual cause — a pulled generation boots its own recorded kernel, so that path is the fallback for a hand-built one.

**A job queues forever.** The runner-group and workflow-allowlist checks in [docs/getting-started/index.md](../../../../../docs/getting-started/index.md) apply here unchanged.
