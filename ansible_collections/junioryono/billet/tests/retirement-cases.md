# Contract notes

The missing-binary-source refusal precedes retirement routing in real and check modes. `Inspect persisted billet installation inputs` runs after preparation and server-policy derivation, followed by the separate binary-source assertion; the existing binary, supplied source, release pin or channel satisfies that one rule. Config-shape, key-presence and all other ordinary input refusals stay behind routing. The retired server-only boundary case plants `/usr/bin/billet`, so it passes this assertion even with `billet_config: {}`.

In check mode only, preparation publishes `billet_exclusion_candidate_unstaged` when its answerer is empty, the claim is `none`, the platform stages Linux candidates, and staging predicts a binary change or has a resolved release still unfetched. Retirement combines that fact with check mode, an empty incapable answerer and no legacy claim, reports `unverified-check-mode`, and admits the ordinary preview without claiming a classifier answer. A real run stages and classifies with the candidate; that classification may choose different work, which the reason states. A managed or recorded answerer, a legacy claim, an unknown version or an attempted-but-unanswered classifier never obtains this exception merely because a candidate source is supplied.

The complete-classifier floor is `v0.11.0`; `v0.10.1` remains an incapable maintenance-release control. An incapable or absent retirement answerer holds, under either value of `billet_enable_server` and with or without `--requested`, except for the explicitly unverified check-mode candidate preview above. The reason names `billet_retire_capability_floor` (`v0.11.0`): this collection needs billet at or above that floor on the host; upgrade the managed binary or converge with an older collection. Requested retirement is also refused by name. Other incapable or absent check-mode cases report the hold and succeed without ordinary work. Local configuration, a clean identity locator, absent retirement artefacts and one stopped or absent service unit cannot prove that no controller or shared reservation exists: a controller may run by hand, under another supervisor, or as a surviving child of a stopped `KillMode=process` unit. The caller therefore reads none of those as compatibility evidence and keeps no three-path artefact screen.

A legacy claim keeps its own rule: a verified capable executable classifies read-only; `ordinary` enters ordinary convergence, `recovery` runs the existing recovery alone and ends at the fresh-converge boundary, and every other route holds. Without a capable executable it holds. Preparation leaves the answerer empty for a legacy claim in a real converge, but check-mode preparation may publish a non-empty dry-run answerer. `retirement.yml` resets a legacy claim's retirement answerer to empty and selects it only after the managed executable passes verification. A pre-guard managed binary with no candidate, or a host with no billet and no candidate, also leaves preparation's answerer empty; the last case is refused by the binary-source validation before routing through real `main.yml`. An install or binary change stages a candidate, but candidate-first preparation alone selects it as answerer. A managed binary that already answers the guard remains the answerer even after staging a newer candidate, so a below-floor managed answerer still holds in that case. The floor concerns the selected executable's observed version, never the desired installation pin; recognised development builds attempt strict classification.

The Go classifier's recovery reason says to retry classification, while the caller boundary requires a fresh converge: this implementation ends the invocation and lets the next preparation/classification do that retry. The older `dry-run-request`, `dry-run-adopt` and `dry-run-unknown-ledger` filenames describe dispatch, not route; the command's route wins. No command behaviour was changed.

# Design constraints found in 5c.d1

The deployment's node hosts must have preparation facts before this collection. The shipped fleet playbook prepares the current control-plane play before its later Linux/macOS plays, so it cannot itself provide those facts for ordinary compute hosts at this point. This implementation follows the explicit no-answerer-is-failure rule and names the prerequisite; it does not prepare or silently omit those nodes. An earlier preparation play covering those nodes is needed. The survivor must additionally converge in the same play as the retiring host: preparation only in an earlier play is refused because retained hostvars cannot distinguish a healthy survivor from one that failed there, and this caller adds no revalidation protocol. The outside-this-play refusal (`ansible_play_hosts_all` excludes the survivor) names that limitation and the same-play remedy; the separate no-longer-active-in-this-play refusal (present in `ansible_play_hosts_all`, absent from `ansible_play_hosts`) names failure, unreachability, or an intentional end of that host and requires resolving the cause before converging both controllers together. The shipped `playbooks/fleet.yml` targets all `control_plane` hosts in one play, so both controllers converge together when both belong to that group and are included by the host limit; Linux and macOS nodes follow in separate plays.

A collection containing a macOS node cannot satisfy the specified endpoint command: `cmd/billet/nodemigrate.go` explicitly refuses darwin, including `--dry-run`. The collector makes the prescribed call under the host's own platform/escalation and reports its refusal. Supporting that deployment needs a producer capability change, outside this caller pass. `release inspect` has no `--environment-file` flag; it reads the loaded unit's environment internally, and the collector forwards that inspected file name to `rollout status`.

A fresh transition id cannot be compared to a caller-known id before reserve: Go mints it inside the reservation and accepts no caller id. The parser validates its grammar, the role saves it, and the request/completion and cleanup must agree. When classification observed an existing row, the reservation's id is compared to that row before collection. No classifier journal is fabricated for a new request.

# Cancellation contract and limits

The sequence is `ANSWERER server retire --reserve --json --run HOLDER --retiring-host HERE --survivor-host RECORDED --installed-sha256 DIGEST --config /etc/billet/billet.yaml [--environment-file FILE]`, require `adopted` and bind run/retiring/survivor/transition to this holder and the classifier's row, then `ANSWERER server retire --abandon-reservation --json --run HOLDER --retiring-host HERE --config /etc/billet/billet.yaml [--environment-file FILE]`, require `abandoned` and the same transition id, then open the ordinary boundary. The digest is from the installed file; the survivor is never read from desired inventory. Neither mutation takes stdin. Both calls ignore unreachable only to let `retire-answer.yml` reject it as an ordinary failure; classifier calls now use the same conversion. `billet_retirement_cancel_step` names preparation, adoption or abandonment in the final refusal; the three cancellation raw/stat results are reset by their tasks before use. A validated fresh `reserved` answer enters cancellation's own nested abandonment rescue, using the request path's preserve-failure, abandon, parse, bind and combined-failure shape. Cleanup is bound to that fresh answer's transition, and the command enforces `row.Run == --run`; it never opens ordinary work. An unconfirmed cleanup names the outstanding retiring host, recorded survivor, current run and fresh transition. A mismatched `adopted` answer triggers no cleanup because this caller has not confirmed its observed binding.

The design's preparation/takeover wording is broader than the implementation: `converge-guard prepare` never takes another holder's guard, even without a marker. It returns the existing held-guard recovery diagnostic before retirement dispatch. An explicit `hold --recover-from` is the command that reaches the marker-without-journal refusal and names abandonment under the old run. This pass preserves and tests the earlier preparation refusal; it does not promise that rerunning under a new holder will cancel an unrecovered old guard. The design's earlier recovery sentence also says to reclassify in the same invocation, but its later explicit fresh-converge boundary governs, as already implemented.

R6's unprepared-survivor case remains at the continuation entry: a new request with an initially unprepared survivor is rejected by R2/R16 before reservation or collection, so making that the starting state of a successful new-request handoff would contradict the preconditions. The added R6 case covers the missing new-request path without weakening them. The harness shares a namespace and simulates the command's effects; real host/service behavior remains the Go producers' and rehearsals' responsibility. No new-request collection eligibility, retained-node support, earlier-play revalidation or macOS endpoint support was added. All local validation for this pass was deliberate reading; no build, test, lint, formatter, Ansible run or gate was executed.
