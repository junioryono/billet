# billet Ansible collection

**If this is your first billet deployment, start with [examples/single-host-docker](examples/single-host-docker/README.md).** It is one machine running both roles with Docker, written from a walk on a throwaway host, and it covers the GitHub-side steps that have to happen before a converge can succeed. The rest of this document is the role's reference — every variable, and the upgrade transaction in detail.

`junioryono.billet.host` turns an already installed Linux machine into a billet control plane and Firecracker compute host. It installs the billet binary supplied by the operator, creates the service identity and systemd units, installs Firecracker and Ceph client tooling, loads the RBD kernel client now and after every boot, creates isolated DHCP/NAT guest bridges, renders `billet.yaml`, checks the Ceph pools, configures a periodic Ceph health check, and renders and enables the deployment backup timer (`billet-backup.timer`, daily, the same unit the package ships) on every host whose control plane may run, fenced on the ledger mount the way the server unit is; `billet_backup_timer: false` installs it disabled, and a systemd drop-in on that unit is refused like one on either service, because the fence is rendered into the unit itself. The guest policy admits the configured image-verification callback only on the trusted bridge, so `billet images verify` works without exposing arbitrary host ports. It drains the node before changing any live guest-network input and restarts it after a selected Firecracker binary changes. An installed `billet_service_user` or `billet_service_group` change is refused from freshly reloaded systemd policy before account or state ownership mutation because moving the ledger and credentials is an explicit offline migration. Check mode never reloads the live manager and refuses pending Billet unit policy it cannot inspect safely. A binary upgrade is transactional: the role inspects the controller's candidate digest, copies that binary and every generated candidate artifact into one unique recovery journal, rechecks the journaled digest, preserves the installed configuration, units and binary, records prior identity, exact supported systemd enablement and active-service state in a durable manifest, and publishes its transaction pointer `active/recovery` inside the converge guard the role holds (a managed binary that predates the guard, with no candidate, claims `/var/lib/billet/upgrades/active` with the pre-R no-replace hard link instead). Before any of that, and before every other task, the role prepares the exclusion: it requires a holder (`billet_converge_guard_holder`, from `BILLET_CONVERGE_GUARD_HOLDER` or `-e`) and calls `billet converge-guard prepare` twice under the transaction lock: the first call acquires the guard or validates this holder's (refusing another holder's naming the way out), the staging then copies the candidate into an exclusively allocated recovery directory under the guard, and the second call declares the intent (the staged candidate, judged at the capability floor and for a downgrade and re-bound into the record; no change; or the recovery of this converge's interrupted transaction) before `settle` closes the acquiring invocation's window. A refusal between the acquisition and the settlement releases the guard this run acquired and nothing else; otherwise the operator releases with the holder they exported. It reloads systemd again and refuses redirected configuration or unit inputs, any effective systemd service drop-in, and masked, linked, alias, or transient enablement before mutation because those overlays, symlink topologies, and in-memory definitions cannot be replaced and reconstructed safely from the journal; fold intentional service changes into the role-managed unit before upgrading. It then proves only the configured Firecracker images this node can run, resolving an omitted node name from the TLS certificate before applying node-pinned tier policy, preferring to boot-verify an already imported generation that records the required guest contract before it fetches another compatible signed replacement, drains the node, stops the server, removes the installed executable so operator commands cannot race the migration, establishes and durably flushes the maintenance fence, preserves and commits the stopped-ledger snapshot, and installs and validates the journaled candidate as the only ledger writer. After candidate units are loaded, the transaction rechecks effective drop-ins immediately before validation and readiness probing. Candidate units run explicit quiescent probes: the server opens and validates the fenced ledger without polling GitHub or dispatching work, while the node initializes its provider without registration or workload polling. Each candidate process notifies systemd only after that initialization completes; ordinary no-binary convergence preserves each installed unit's `Type=notify` or `Type=exec` readiness protocol so updating the collection cannot impose notification on an unchanged legacy binary or restart an already upgraded service merely to remove it. The role proves both candidates remain stable before it installs steady-state units with no maintenance bypass, persists desired enablement, flushes every mutated host filesystem, and records the durable commit. The shared finalizer then opens administration, replaces probes with full services in server-then-node order, proves their stability, and removes the active pointer only after success. The role accepts only distinct dedicated state directories below `/var/lib/billet`, derives recovery paths and ownership from the validated manifest, and refuses symlinks before it changes ownership or restores privileged files. If Ansible or the host is interrupted while the active pointer exists, the next converge inspects it before account, package, Firecracker, networking, Ceph, or other desired-state work and then asks for a fresh converge. An uncommitted transaction first proves both services terminal with zero main/control PIDs and conclusively empty or absent cgroups, validates the completed snapshot before removing current ledger entries, disables candidate units and removes their persistent and runtime enablement links before restoring or removing the previous unit files, restores the exact prior configuration, units, binary, enablement and ledger, durably records the rollback, then opens administration and returns only the previously active services; a failed first installation therefore cannot leave dangling links that enable a later installation. A legacy uncommitted journal that already records a transient service is left fenced for manual recovery, while a legacy journal with a durable commit can still finish because finalization never restores its previous definition. A transaction whose upgrade or rollback commit record already exists retries only finalization and retains the pointer until full services are stable; it never restores old state after operator writes may have been admitted. A compatible verified generation remains published because another upgraded host may already depend on that fleet-wide fact; unused immutable generations are left for retention. If process or recovery evidence is inconclusive, restoration stops before modifying the ledger and leaves the active pointer and recovery directory for manual inspection. It never creates a GitHub App, invents capacity, chooses disks, or starts billet until the supplied configuration passes `billet check`. An existing GitHub App private key is never replaced implicitly: a matching source is accepted idempotently, while a different source is refused so credential rotation remains an explicit operator action. Setting either service enable flag to false stops and disables a service previously installed by the role. Setting `billet_alert_email` back to empty or disabling Ceph stops and removes the Ceph health timer and removes `/etc/msmtprc` only when this role created it, including configurations created before the ownership sidecar existed.

The role can bootstrap a new single-host Ceph cluster only when `billet_ceph_bootstrap` is explicitly true and `billet_ceph_devices` names every device to consume. That path is destructive by definition and is never inferred from available disks.

There are two ways to give the role a binary, and which you pick is a decision about egress rather than convenience.

**`billet_version`** names a release the target fetches for itself — `billet_version: v0.3.26`. The archive is verified against that release's own `checksums.txt` before it is unpacked, which proves the download is complete and uncorrupted and says nothing about whether the release host is honest; unlike the Firecracker hashes this collection pins, a hash for a release that ships after the collection cannot be pinned here. It must name one release: `latest` is refused, because a moving target makes a converge non-deterministic and drives a real drain and restart on a day nobody chose. `billet_release_url_base` points that at an internal mirror.

**`billet_binary_src`** hands over a binary you already have, over the SSH connection Ansible is already using. Nothing on the host reaches the network, which is what an egress-filtered or air-gapped node needs, and it is also how you try a build against an inventory that pins a version — set both and the supplied binary wins, and the role says so rather than ignoring the version quietly.

Set `billet_binary_src` to the Linux binary the role should install. A repository can pin the collection and binary to one release by downloading it into a controller-side staging directory, then passing the verified file directly to the role:

```bash
billet_stage=$(mktemp -d)
curl -fsSL https://raw.githubusercontent.com/junioryono/billet/v0.3.0/scripts/install.sh | BILLET_VERSION=v0.3.0 BILLET_OS=linux BILLET_ARCH=amd64 BILLET_INSTALL_DIR="$billet_stage" sh
ansible-playbook site.yml -e "billet_binary_src=$billet_stage/billet"
```

A Billet contributor can instead build the binary from the same checkout as the collection. Keeping the binary input explicit makes the requested version auditable; the role owns the safe drain, image-compatibility, migration, recovery, and restart sequence when that input changes. An unchanged candidate and compatible recorded generation are metadata-only checks, so an ordinary second converge neither downloads the guest again nor reports a binary change.

The destructive host acceptance harness kills the Ansible controller at every claim, executable, snapshot, migration, quiescent-probe, durable-decision, full-service, fence-removal and pointer-removal boundary. It requires a maintenance-window host already running Billet plus two valid binaries with different hashes; it checks exact binary/config/unit hashes, owners, modes, active and enabled service state, full rather than probe service processes, ledger validation, fence cleanup, manager-environment cleanup and final idempotence after every recovery. It never reads the GitHub App private key. Point it at an inventory that supplies the ordinary role variables:

```bash
BILLET_ACCEPT_DESTRUCTIVE_HOST_UPGRADE_TEST=1 ansible_collections/junioryono/billet/tests/host-upgrade-live.sh inventory.yml host-a /tmp/billet-candidate-a /tmp/billet-candidate-b
```

See `roles/host/defaults/main.yml` for the complete input surface.

`junioryono.billet.ssh_access` is what every host converged from CI needs before anything else: the keys a converge connects with (`billet_ssh_authorized_keys`, a list of `{key, state}` for the account Ansible connects as, discovered with `id -un` when the inventory leaves it to SSH configuration), an operator's break-glass key beside them (`billet_ssh_breakglass_key`), sshd hardened with password and keyboard-interactive authentication off (`billet_ssh_harden`, `billet_ssh_permit_root_login`), the hostname set from the inventory and unattended security upgrades on Debian-family hosts. Its one rule cannot be gated: it refuses to write the hardening on a host its own converge would leave with no way in. A key is exactly a type, its material and an optional comment on one line, and its identity is the material, because that is what the module installs and removes by (it ignores the type and the comment and replaces the options of a key it already holds): a comment where a key should be, a line carrying options, a value spanning lines, one material with two states or under two types, two present entries for one material, the break-glass key doubling as a converge key (one private key is not two), and keys installed for `root` under any policy but `yes` or `prohibit-password` are each refused before anything is written; a key that needs options is not this role's to install. The drop-in is validated as part of the whole configuration sshd reads (`/usr/sbin/sshd -t` with the file in place), put back or removed when sshd refuses it, and sshd is restarted only after that validation, because a fragment that parses alone can still make the configuration unsatisfiable. With nothing configured it does nothing, which is what lets the collection's fleet playbook run it on every host in its `control_plane` and `linux` groups.host` in your own play. Revoke a key with `state: absent` while the key is still written out, because the module removes by material; delete the entry once that has converged everywhere. `tests/ssh-access-check.sh` drives each refusal and the install against a fake `sshd` without root.

`junioryono.billet.fleet` is the playbook a consumer runs: `- import_playbook: junioryono.billet.fleet` is the whole of its `site.yml`, and its own plays go after that line. Three plays in upgrade order: `control_plane` (`ssh_access`, `host`, `cloudflared_connector`), `linux` (`ssh_access`, `host`, `warp_connector`, `cloudflared_connector`, and `development_host` when `billet_development_enabled` is true) and `macos` (`development_host` when enabled). Every role skips cleanly on absent inputs, so an inventory that names no keys, no tokens and no development switch converges exactly the host role. The inventory declares all three groups, empty ones allowed (`macos: {hosts: {}}`), as `billet init hybrid` and the examples write them, because a targeted group the inventory never declares fails the run under `ANSIBLE_HOST_PATTERN_MISMATCH=error` after the earlier plays have converged; the guard is tagged `always` so a run under `--tags` cannot skip it. No play sets `become`: the roles escalate per task, and `development_host` runs Homebrew as the login user it reads from the facts. Each play's first task is the host role's converge guard, so a converge driven from a runner billet manages is refused before `ssh_access` changes anything; `tests/fleet-playbook-check.sh` pins the shape and proves that ordering.

`junioryono.billet.development_host` is a separate, reusable developer-machine layer for Debian-family systemd hosts and macOS. It installs current Caddy and Terraform from their publishers' repositories, installs mkcert, stages and validates a caller-defined certificate/key pair before installation, and keeps a caller-supplied Caddyfile running across reboots through systemd or launchd. The role has no application or domain defaults: a repository supplies its SANs, proxy configuration and environment, while Billet owns package verification, CA trust, private-key permissions and service lifecycle. Disabling the proxy unloads and removes the prior systemd or launchd definition.

The role defaults to a localhost-only certificate and an empty proxy routing table. Set `billet_development_tls_sans` and `billet_development_proxy_config_src` for a real project. On macOS, Homebrew must already be installed; every formula and the launchd service are then converged by the role. See `roles/development_host/defaults/main.yml` for the complete input surface.

Run the playbook with `--check --diff` before converging a new or existing machine. The role still runs read-only identity, package and version probes in check mode, while deferring generated certificate validation until the files exist, so a first dry run can describe the installation without failing on tools it has not installed yet. When systemd reports a pending daemon-reload for a billet unit, the dry run compares the facts it reads from the loaded state (`User`, `Group`, `Type`, the loaded `ExecStart` records) with the unit file on disk and continues with a report when they agree; it refuses when they differ or cannot be compared (a drop-in anywhere the manager searches, an alias on disk or in memory, an `ExecStart` outside the plain grammar the role writes), because on systemd 255 the flag is set for every unit by any `systemctl enable` on the host until the next reload. A real converge ends with the reload its own enables left pending.

```yaml
- name: Configure development machines
  hosts: development
  gather_facts: true
  roles:
    - role: junioryono.billet.development_host
      billet_development_tls_sans:
        - "*.dev.example.test"
        - dev.example.test
        - localhost
        - 127.0.0.1
        - "::1"
      billet_development_proxy_config_src: "{{ playbook_dir }}/Caddyfile"
      billet_development_proxy_environment:
        DEVELOPMENT_CERT_FILE: "{{ billet_development_tls_cert_path }}"
        DEVELOPMENT_KEY_FILE: "{{ billet_development_tls_key_path }}"
```

Add a new Linux or macOS machine to that inventory group and rerun the playbook; package installation, local trust, certificate renewal on SAN changes, configuration validation and boot persistence all converge through the same role.
