# ADR-007: A Billet-owned CodeBuild provider, and why it does not use CodeBuild's own runner integration

**Status:** accepted, Aug 2026. Supersedes the EC2-Mac-plus-Tart direction for Billet's primary AWS macOS experience; Tart remains the answer for owned Apple hardware and for jobs that cannot accept the 36-hour ceiling below.
**Decision:** an **ordinary `NO_SOURCE` CodeBuild project, started with `StartBuild` after Billet has already acquired and escrowed a scale-set job**, running GitHub's own Actions runner from Billet's own single-use JIT configuration. Reserved-capacity `MAC_ARM` fleets are how Billet reaches AWS-managed Apple silicon.
**Rejected:** CodeBuild's native GitHub Actions runner integration, a plaintext JIT environment variable, Secrets Manager for the JIT handoff, tag-scoped build ownership, untrusted work on any *reserved* CodeBuild fleet or macOS. **Admitted:** untrusted work on an *on-demand* container fleet with a verified isolated network, after measuring that on-demand destroys its machine between builds — under two documented exposures that make it weaker than the `ec2` untrusted path.

This ADR exists because the original request for this backend was filed as context rather than a spec, and because researching the API before writing any code contradicted four of its premises. Everything under "What the API permits" is from AWS's own reference. Everything under "What has to be measured" is behaviour the documentation does not settle, and billet's house rule — *a rule about someone else's API is pinned to measured behaviour, not to reasoning* — says those must be run rather than reasoned about.

## The requirement

The same one ADR-002 states for EC2, with one addition. A tier listing `providers: [firecracker, codebuild]` must be placeable on either, so one stable `runs-on` label survives the bare-metal host going away — and a tier listing `providers: [tart, codebuild]` must let a macOS label survive without anybody allocating an EC2 Mac Dedicated Host, operating a macOS host, installing Tart, or building an 81 GB macOS guest image. AWS holds the Apple hardware agreement for a managed fleet, which is the thing an operator cannot buy their way out of otherwise.

What has to run is a **GitHub Actions job**, which on Linux means Docker inside it.

## What the API permits

### CodeBuild's Actions-runner integration is webhook-only, and Billet does not use it

A CodeBuild "Runner project" requires a `WORKFLOW_JOB_QUEUED` webhook and a `runs-on: codebuild-<project>-${{ github.run_id }}-${{ github.run_attempt }}` label. CodeBuild owns job detection, fetches the runner registration token itself during `DOWNLOAD_SOURCE`, and overrides the project's buildspec while doing it. **There is no API-invoked form of that feature.** The original request named this as the branch to "record and replan", and the replan is short, because the feature was never needed: Billet already knows how to start GitHub's runner from a JIT configuration it minted itself — that is what the `ec2` backend does inside an instance and what the `tart` backend does inside a guest. So this provider starts an ordinary project and does the same thing inside a build.

The consequence worth stating is what Billet keeps by not using it: the scale-set listener, the capacity ledger, ordered provider fallback, node policy, custody, and the stable-label contract. A workflow that says `runs-on: linux-x64` keeps saying that. Nothing in a repository names a CodeBuild project or a Billet release, which is the whole point.

A Billet-owned project must therefore **not** carry a competing `WORKFLOW_JOB_QUEUED` webhook. Two schedulers acquiring the same job is not a race Billet can win, and the failure looks like duplicate runners rather than like a configuration mistake.

### `StartBuild.idempotencyToken` is valid for five minutes

AWS documents the window. That is materially weaker than EC2's `ClientToken`, whose behaviour Billet's live smoke test measured: relaunching the same lease with a different disk size is refused with `IdempotentParameterMismatch` long after the fact. Here, past five minutes, an identical retry starts a **second build** — two runners for one job, both registered with GitHub, one free to pick up unrelated work.

So the token is necessary and not sufficient, and the launch path does what `provider.Find`'s own doc comment already prescribes for exactly this case: after an ambiguous failure it **asks** rather than retrying. The token still earns its place — it makes a *fast* retry safe, which covers the transport-level retry inside one call — but nothing in the design may depend on it holding for the life of a lease.

### Builds cannot be tagged

CodeBuild tags exist on projects and report groups. There is no build tag, and `StartBuild` has no field that becomes one. The `ec2` backend scopes destruction by `sh.billet.owner` **on the instance**, and `List` feeds a loop that terminates — so a boundary two installations could both satisfy is a way for one to destroy the other's live jobs. That boundary has to be rebuilt from what is available:

- a **dedicated project per deployment-and-node**, tagged with the deployment identity, which is the coarse boundary;
- the **owner and lease-name markers as environment-variable overrides**, read back through `BatchGetBuilds`' `environment.environmentVariables`, which is the per-build boundary.

Neither marker is a secret, so both may be plaintext and CloudTrail-visible. What matters is that `List` and `Find` verify both before reporting a build as Billet's, and that an owner-marked build whose lease-name marker names no lease **fails the whole inventory** rather than being omitted from it — the `ec2` rule, for the `ec2` reason: this list frees capacity, so a silently dropped row is capacity handed back for compute that is still running.

### There is no way to list only active builds, and history is kept for a year

`ListBuildsForProject` returns build ids newest-first, 100 per page, with no status filter — and it *errors* if `sortOrder` is passed when the project has more than 100 builds, so the default ordering is the only one usable at scale. `BatchGetBuilds` takes at most 100 ids. Build history is retained for a year.

So `List` and `Find` are a bounded page-walk plus a `BatchGetBuilds` per page, and what bounds them is **CodeBuild's own enforced timeout**: a build that started longer ago than `timeoutInMinutes + queuedTimeoutInMinutes + slack` cannot still be running, because CodeBuild ends it. The window is therefore a consequence of the operator's declared build ceiling rather than a number Billet picked, which matters — an operator whose jobs finish in an hour gets a cheap inventory, and one who declares the full 36 hours pays for the walk. Billet still adds no timeout of its own; it reads the one the operator declared.

The cost has to be measured against real history rather than projected, and recorded in `docs/aws-acceptance.md`. If it binds, the mitigation is the operator declaring a tighter ceiling, which is their decision to make.

### Two external ceilings, not one

- **A build timeout of 5–2160 minutes.** The original request names the 36-hour maximum, and it is real: every CodeBuild-backed Actions job has an unavoidable 36-hour cap that Billet cannot lift. **CodeBuild never satisfies billet's unlimited-duration guarantee**, and nothing in Billet's documentation or output may imply that it does.
- **A queued timeout of 5–480 minutes**, which the original request does not mention. A build that waits longer than that for capacity **fails**. On a fleet at capacity with `QUEUE` overflow, that is a second way a job dies for a reason outside Billet, and an operator has to see it before enabling a tier.
- **A queue of at most 30 builds for the whole account**, measured 2026-09-02 rather than read: past thirty queued builds `StartBuild` is refused with `AccountLimitExceededException: Cannot have more than 30 builds in queue for the account`, and Service Quotas lists no such quota to raise. It is a third external ceiling, account-wide across every project, and it bounds what a deployment may safely escrow against CodeBuild: a burst beyond roughly *concurrency quota + 30* is refused at launch, which billet reports as a conclusive failure and GitHub requeues up to three times before failing the job.

Both are reported as provider capabilities by `billet check` (and deliberately not by `billet status`; see the Consequences below for why), and `node.codebuild.accept_external_build_ceiling` has **no default** — its absence is the refusal, the same shape as `node.firecracker.untrusted_bridge` and `node.ec2.untrusted_security_group_ids`. A ceiling an operator did not acknowledge is a ceiling they find out about from a failed 36-hour build.

### Reserved capacity is not a per-job isolation boundary, and every macOS fleet is reserved capacity

AWS's own words. On-demand fleets: *"The machines are destroyed when the build finishes."* Reserved fleets: *"These machines remain idle, ready to process builds"*, they may be shared across projects, and — explicitly — *"data cached on fleet instances, including source files, Docker layers, and cached directories specified in the buildspec, can be accessible to other projects within the same account. This is by design."* On-demand does not support macOS at all.

That settles the original request's "verify the isolation boundary and network defaults for untrusted work" in the strict direction for reserved capacity. **Untrusted work is refused on every reserved CodeBuild fleet**, and `Accepts(TrustUntrusted)` names that documented sharing rather than a network setting, because no security group fixes a machine that later runs somebody else's build. `TrustUnknown` stays refused for the separate reason it always is: untrusted is a classification Billet made, unknown means it could not classify the job at all, so there is no basis for choosing anything. macOS is reserved-only, so it can never take untrusted work.

### On-demand Linux is a per-job machine, and untrusted work is admitted there under a narrower door

The reserved refusal above rests on a machine that survives between builds. On-demand is a different mechanism, and the question was whether it destroys its machine rather than quoting AWS's sentence that it does. **Measured 2026-09-02** (`docs/aws-acceptance.md`): 31 on-demand `LINUX_CONTAINER` builds across serial and concurrent waves reported **31 distinct host boot-ids**, every host freshly booted (uptime 3–5 minutes), and **no marker of any kind survived from one build to the next** — not the container filesystem, not `$HOME`, not the host root disk a privileged build mounted read-write, not a Docker image or volume. Two back-to-back waves of 14 shared zero hosts. The one thing that persisted was the opt-in `cache: type: LOCAL`, which billet's project never sets. So an on-demand Linux build is a per-job boundary the way an `ec2` instance is, and the machine is no longer the objection — the network is, exactly as it is for `ec2`.

So untrusted work is admitted on an **on-demand container tier with a declared isolated network**, and only there. `node.codebuild.untrusted_vpc_id`/`untrusted_subnets`/`untrusted_security_group_ids` name the network, their absence is the refusal (the `node.ec2.untrusted_security_group_ids` shape), and `Accepts` and the launch path share one function (`untrustedNetwork`) so a network configured but not enforced is impossible. Because StartBuild has no VPC override, the network lives on the **project** and the launch **verifies** — via `BatchGetProjects` — that the project's `vpcConfig` is exactly the declared network before it starts a fork's build, failing closed if it cannot. A `fleet_arn` refuses it (a `fleetOverride` discards the project VPC and reserved capacity is shared) and a non-container `environment_type` refuses it (reserved-only).

**Two exposures make this strictly weaker than the `ec2` untrusted path, and both are unavoidable properties of CodeBuild rather than choices Billet can undo.** They are why untrusted CodeBuild is a documented, opt-in capability rather than a default, and why untrusted work must run on a **dedicated** CodeBuild node and project, never one shared with trusted tiers:

1. **A VPC-connected on-demand build's service role is reachable from inside the build** (CodeBuild injects it at `169.254.170.2`, confirmed in the measurement), and a VPC build's service role *must* hold `ec2:CreateNetworkInterface`/`DeleteNetworkInterface` plus unscopable `ec2:Describe*`. On `ec2`, an untrusted instance gets **no** instance profile and therefore zero AWS credentials; here a fork can read a service role that necessarily carries EC2 network permissions. The terraform module scopes the mutating ENI actions to the untrusted subnet and security group, but `Describe*` cannot be resource-scoped, so a fork can enumerate account network topology. This is the reason a reserved fleet uses a *separate* `fleet_service_role` whose credentials never enter the build — an option on-demand does not have.
2. **The JIT parameter path is read with that same service role**, so a fork could read any registration under the untrusted node's `jit_parameter_path` whose exact lease name it can guess. Lease names are unguessable and single-use, and every registration under an untrusted node's path belongs to another equally-untrusted fork — but only if untrusted work does not share a node (and therefore a project, role and path) with trusted tiers. Billet does not yet *enforce* that separation; it is an operator requirement stated here and in `docs/codebuild.md`, and a config guard refusing a trusted tier on an untrusted CodeBuild node is worthwhile follow-up.

What is proven: on-demand Linux is a per-job machine. What still needs a human before this is enabled in anger: a live fork pull-request acceptance on an on-demand tier reaching only its security group (it depends on the terraform network below and a full deployment), and a decision on whether the two exposures above are acceptable for a given account. macOS can never take untrusted work.

### Everything else that shapes the design

- **Default concurrency is 1** per environment and compute type, adjustable per quota; a Mac ARM fleet defaults to 1 concurrently running instance; an account gets 10 fleets per region. A default account cannot run two concurrent builds of one shape, which an operator has to know before a tier advertises capacity. Reading the quota belongs to the general cloud preflight, and `billet check` does not report it until that lands; the ceilings it does report are its own.
- **macOS is `MAC_ARM`**, two machine types: Apple M2 with 24 GB and 8 vCPU, and Apple M2 with 32 GB and 12 vCPU. Medium is offered in us-east-1, us-east-2, us-west-2, ap-southeast-2 and eu-central-1; Large in the first four. Reserved capacity carries an initial per-instance charge and bills for as long as the fleet is provisioned, so a macOS fleet is a standing cost rather than a per-job one.
- **A reserved fleet takes exactly one subnet in one availability zone** and needs a NAT gateway.
- **A `fleetOverride` on `StartBuild` makes CodeBuild ignore the project's VPC configuration.** The fleet's own network governs, so a network reviewed on the project proves nothing about a build that named a fleet.
- **Lambda compute types are refused.** `BUILD_LAMBDA_*` cannot run Docker, which is the same reason ADR-002 disqualified Lambda outright. A compute type that cannot run a real Actions job is not a cheaper option; it is a tier that fails on its first `docker build`.

## What had to be measured, and what it turned out to be

Recorded here so the list is not rebuilt from memory, and because two of these could have invalidated decisions above. **All but one have now been measured against real CodeBuild in `810711872940`/us-west-2 on 2026-08-31; the observations are in `docs/aws-acceptance.md`.** Several contradicted what this document had assumed, and each one changed code.

1. **MEASURED — the secret channel holds.** `BatchGetBuilds` reports a `PARAMETER_STORE` variable's *name*, never its value, and the staged value appeared nowhere in the response or the build log. One detail that decides how the buildspec may be written: CloudWatch logs each command's **source text**, not its expansion, so a buildspec that echoed the variable *would* leak it. Billet's never names it.
2. **MEASURED — A RESERVED INSTANCE IS NOT SCRUBBED BETWEEN BUILDS.** Asked directly on a real `MAC_ARM` fleet: build one wrote `$HOME/billet-scrub-marker`, and a separate build on the same fleet read it back intact as the same user (`cbuser`, `/Users/cbuser`). So the refusal of untrusted work on this backend is confirmed rather than merely prudent — no network setting fixes a machine whose filesystem the next job inherits. It does NOT settle the separate question of an **on-demand** fleet destroying its machine; that remains its own measurement.
3. **MEASURED — the token behaves as documented.** Two identical `StartBuild` calls with one token returned the *same* build id; a changed parameter under that token was refused `InvalidInputException: Request parameter mismatch for idempotency token`. The five-minute validity was not waited out and does not need to be: what it means for Billet is that an ambiguous `StartBuild` must not be retried **at all**, because the window is wall-clock and Billet does not bound its own HTTP client's timeout. `client.callCreating` is that rule.
4. **MEASURED — `StopBuild` against a terminal build SUCCEEDS**, returning the build's terminal status rather than an error. Against an id the project never issued it returns `ResourceNotFoundException`, which Billet treats as neither an error nor proof.
5. **MEASURED, AND THE ANSWER WAS THE OPPOSITE OF THE ASSUMPTION.** A build CodeBuild timed out reports `buildStatus: FAILED`; the timeout appears only as `phases[BUILD].phaseStatus: TIMED_OUT` with `contexts[0].statusCode: BUILD_TIMED_OUT`. `TIMED_OUT` *is* a documented build status, so Billet asks about both — but the first implementation read `buildStatus` alone, which is a predicate that could never fire for the case it exists for, and every build the service's own ceiling ended would have been filed as somebody's failing test.
6. **MEASURED — `aws/codebuild/macos-arm-base:14` ships Xcode 26.2 (build 17C52), git 2.52.0 and `bsdtar` 3.5.3, on arm64, and does NOT ship the Actions runner** (no `~/actions-runner`, no `Runner.Listener` on PATH). The runner's absence is what the generated buildspec already assumed, and is why `internal/runnerrelease/pinned.txt` carries the `osx-arm64` checksum. `bsdtar` rather than GNU tar is the detail to remember before reaching for a GNU-only flag.
7. **MEASURED — the inventory walk against 1,054 builds inside the window costs 22 requests and 6.5 seconds, with no throttling** (2026-09-02, `docs/aws-acceptance.md`): two requests per hundred builds in the window, about 0.3s each, and nothing for history outside it. The window, not the year of history, is what a sweep pays for. Generating that history found a THIRD external ceiling the design had not named — the account queues at most 30 builds across every project — recorded above.
8. **MEASURED THE HARD WAY — a standard SSM parameter caps its value at 4096 characters and a JIT runner configuration exceeds it**, so every launch died at staging until `putJITConfig` began asking for `Intelligent-Tiering`. Nothing caught it because every test stages a short placeholder.
9. **MEASURED THE HARD WAY — a CodeBuild container runs as root and GitHub's runner refuses to start there**, printing `Must not run interactively with sudo` and exiting zero, after which CodeBuild reports the build SUCCEEDED. The buildspec now exports `RUNNER_ALLOW_RUNASROOT=1` in the phase that execs the runner.

Two more were asked because a review round claimed something the design depended on:

10. **A project-scoped IAM grant authorizes `StopBuild` and `BatchGetBuilds`.** A role holding exactly the five actions on one project ARN succeeded at all five and was correctly refused on a project the policy does not name; IAM's own simulator additionally refuses a `build/...`-scoped statement against a build ARN, so that is not a resource type these actions accept. A review had argued the reverse, which would have meant every teardown and inventory failing after the first launch.
11. **Reserved Parameter Store namespaces are case-insensitive**, stated in AWS's own refusal text. Billet's path check was case-sensitive, so `/AWS/billet` loaded and then failed on every registration.
12. **MEASURED for the control plane's sweep (2026-09-02): a `GetParametersByPath` cursor is positional, so deleting while paging skips entries** — three parameters at `MaxResults 1`, delete the one page one returned, and page two with the old token returns the *third*, never the second. The sweep collects the whole listing before it deletes anything. Two more from the same session: a listing `WithDecryption=false` returns each SecureString as KMS ciphertext (`AQICAHi…`, ~250 bytes) and not the plaintext, so a controller that never asks for decryption never holds a registration; and `GetParametersByPath` is authorised against the *path* ARN, not its children — the simulator says so, and a real role holding the children-only grant is refused the listing with the path named as the resource — which is why the controller's grant names both. **One more from the same role, and it is the one to remember:** with no `kms:*` action anywhere in its policy, the role still received **plaintext** when it asked `WithDecryption=true`, because the account's `aws/ssm` key authorises any principal reaching it through Parameter Store. The absence of a KMS grant is therefore not what keeps a registration out of the controller; billet's request stating no decryption, and the response type having no `Value` field, are — and a customer-managed key is what makes the grant decisive again, **also measured**: under a fresh key the same role's decrypting listing was refused `kms:Decrypt`, its delete still succeeded, and a page mixing one customer-key parameter with one default-key parameter failed whole rather than leaking the default one.

## Consequences

- **A RESERVED FLEET IS A 24-HOUR COMMITMENT, NOT AN HOURLY ONE, AND DELETING IT DOES NOT STOP THE BILLING.** Measured: `DeleteFleet` succeeds, moves the fleet to `PENDING_DELETION`, and answers *"Fleets are deleted after all instances have run for 24 hours. Fleets are available to build projects while they are pending deletion."* At the `arm.m2.medium` rate from AWS's own pricing API — $0.02 per minute — that is **$28.80 minimum** for a macOS fleet, whatever it is used for. The measurement above cost exactly that, for two builds lasting under a minute each. This is the most expensive thing an operator can get wrong about this backend, it applies to every reserved fleet rather than only the macOS ones, and it is why `billet check` reports a fleet's configured capacity: a fleet is standing cost, and the only decision that avoids it is not creating one. Two refinements measured on 2026-09-02: the hold is on INSTANCES that ran, so a fleet AWS never found capacity for (`status.context: INSUFFICIENT_CAPACITY`, which `billet check` now warns on) is deleted at once; and a fresh fleet is `ACTIVE` in about twenty seconds while its first build then queues for as long as the Mac takes to provision — 206 seconds in a region with capacity, and until the queued ceiling fails the build in one without, for as long as the shortage lasts — during which GitHub cancels and requeues the job on its own pickup deadline and billet correctly stops and restarts builds to match.
- **A codebuild node is an orchestrator, so `node.max_vcpu` and `node.max_memory` are required rather than detected**, exactly as for `ec2`. `ProviderKind.RunsOnHost` returns false, and the allowlist form of that function is why a third remote backend is treated as remote by default rather than by remembering.
- **A codebuild node declares its purchasable shapes, and placement charges the shape rather than the tier request.** This reuses the mechanism `ec2` already has — the node registers ordered `type`/`vcpu`/`memory`/`price_usd_per_hour` entries, placement picks the first that fits, and every fallback is authorised atomically against the node and deployment ceilings before the request reaches AWS. That is also the answer to the original request's "define how reserved-fleet capacity maps to Billet's vCPU/memory accounting": it maps the way EC2 shapes already do, and no new accounting concept is introduced. Do not declare a shape you are unwilling to buy.
- **One Billet node per project-and-fleet, adjudicated by the control plane.** "Two Billet nodes must not each advertise the same shared fleet capacity" is a claim about two *different machines'* config files, which no config validation can see: the registration names the fleet, the ledger records it, and a registration naming a fleet another node already holds is refused. `nodeapi.MinVersion` does not move, because no codebuild node can exist below the version that introduces the provider.

  **THE CLAIM ENDS ONLY AT A PROVEN DECOMMISSION, and getting that wrong twice is worth recording because both wrong answers read as obviously right.** The first version scoped the holder query to `live = 1`: liveness says nothing about remote compute — `ForgetEveryNode` marks every host not-live whenever a control plane *starts*, and a node that merely disconnected is not-live while its builds keep running — so a differently named node could take the fleet across an ordinary restart and advertise its whole capacity on top of live work. The second scoped it to `decommissioned_at = ''`, which let a **forced** exclusion release it; `--force` exists precisely for the host nothing could ask and records `decommission_proven = 0` so every later drain keeps saying so. Both were the same mistake: deriving permission from what is *broken* rather than from what is *proved*. What releases a claim now is `decommission_proven = 1`, which is the drain's compute barrier, and the refusal names `billet drain --wait` before `billet nodes decommission`. The ordinary replacement needs none of it, because it reuses the node **name**, which the query excludes.
- **The macOS licence cap does not apply to a managed fleet, and this is the one place that needed a real decision rather than a reuse.** `NodePolicy.MacOSLimit()` returns `config.DefaultMacOSVMLimit` — two, Apple's standard per-host allowance — for a host nothing was declared about, which is right for an Apple machine somebody owns and wrong for a fleet AWS operates under its own agreement. Left alone it would silently cap a five-instance macOS fleet at two concurrent builds and blame Apple in the diagnostic. So the *default* is keyed on whether the registered provider runs work on the host, and the diagnostic names Apple only when it does. The configured cap still applies when an operator sets one; what changes is what silence means.
- **`terraform destroy` REFUSES UNDER A RUNNING BUILD, AND IT IS THE MODULE THAT REFUSES, because AWS does not.** The module's README had said AWS refuses to delete a project with builds in progress; measured on 2026-09-02, `DeleteProject` succeeds while a build is in its `BUILD` phase, the build runs on to completion and `BatchGetBuilds` keeps answering for it — so a destroy would have removed the node role, the build role and the log group under a live job and reported a clean apply, and the Terraform requirement was unmet by a sentence nobody had checked. `terraform_data.active_build_guard` now depends on everything a build needs and runs `scripts/refuse-active-builds.sh` as a destroy-time provisioner, which walks the project's builds through the operator's `aws` CLI and refuses while any is not terminal, treating a CLI error, an unknown id, an unknown status or an unfinished walk as a refusal too. Proved against the real module: refused with everything intact under a running build, succeeded after `StopBuild`. Three decisions in it are not obvious. The guard's `triggers_replace` is the project name, the region, and the module's other build-facing identities (`name`, the parameter path, the log group) — a `terraform_data`'s `input` updates in place and only `triggers_replace` replaces, so with the project in `input` alone a rename would have replaced the PROJECT while merely updating the guard, and the provisioner would never have run; a review caught that. What that orders is stated rather than overclaimed: Terraform destroys the old guard before it destroys or replaces what the guard depends on, and promises nothing about in-place updates on the same apply, so a rename under a live build is caught by the guard rather than prevented by it, and reconfiguring what a build depends on is `billet drain --wait`'s job. The escape (`BILLET_SKIP_ACTIVE_BUILD_GUARD=1`) is an ENVIRONMENT VARIABLE, because a destroy-time provisioner sees the values in state rather than on the command line, so a `-var` at destroy time would not reach it; its window is CodeBuild's service ceilings rather than the module's timeouts because those are sound for an adopted project too. The script pins `TZ=UTC`, because the CLI renders `startTime` in the machine's local zone and a lexical comparison against a UTC cutoff was seven hours wrong on the laptop that measured it and would have been right on a UTC server. And it never calls `StopBuild`: the drain is `billet drain --wait`'s, and a destroy that cannot proceed says so.
- **A drain, an upgrade, a release rollout and a Terraform apply all leave active builds running.** The only routes to `StopBuild` are ordinary completed-job cleanup, an authoritative GitHub cancellation or terminal outcome, and `billet force-destroy` — which already refuses unless admission is sealed by an operator and whose target set is fixed when the request is taken. `Destroy` polls the exact build to a terminal state before returning `TeardownStopped`; API ambiguity keeps the capacity charged, which is the `ec2` rule for an unconfirmed teardown applied to a service whose stop is even less synchronous.
- **A restart re-adopts.** The build keeps running, the lease stays charged, and the node's inventory recovers it by exact deployment, project and lease identity. GitHub does not requeue a job whose runner vanished mid-execution, so tearing one down on restart would be a deliberate job failure.
- **A LIVE BUILD BEATS A TERMINAL ONE IN A TARGETED LOOKUP, and `Find` did not do that.** Custody reads a terminal answer from `Find` as *causal proof* and settles the lease on it. `List` refuses two live builds carrying one lease marker precisely because billet cannot tell which one the runner is inside — but `Find` returned the newest match, so a lease whose newest build was terminal while an older one was still executing had its capacity handed straight back. Every match is examined now: the single live one wins whatever the order, two live ones are refused exactly as `List` refuses them, and the newest terminal one is returned only when nothing for that lease is running.
- **A STAGED CREDENTIAL IS REAPED BY THE CALLER THAT HOLDS THE PROOF, through `provider.StagedCredentialReaper`.** A CodeBuild build cannot be handed a secret — `StartBuild` has no field for one — so the registration lives in Parameter Store and *outlives the build*, which means destroying the compute does not remove it. Two things were wrong. The cleanup had **no production caller at all** while its own doc comment claimed the node's tending sweep invoked it, so every lease that settled without a `Destroy` — the ordinary case here, since the runner exits and the build ends on its own — left its parameter behind. And it tried to derive its own authorisation: it deleted when no build could be found, which is indistinguishable from a build that has not yet appeared, so an ambiguous launch's parameter could be deleted out from under the very build the launch path deliberately keeps it for. The optional interface exists so the *caller* supplies the proof, and billet calls it only from custody settlement, which by construction runs after something has proved the compute is gone.

  **THE ONE THAT ESCAPES ALL THREE IS SWEPT BY THE CONTROL PLANE, ON THE LEDGER'S AUTHORITY, AND NOTHING ON A NODE COULD HAVE DONE IT.** Three places remove a staged registration and each holds a proof: a conclusive launch refusal (no build exists), a confirmed teardown (the build is terminal), and custody settlement including the confirmed non-custody launch exit (the compute is proved gone). A node process that dies between staging a parameter and reaching any of them leaks exactly one — the live acceptance measured three, left by a killed node. A sweep on the node was rejected and stays rejected, and the reason is worth keeping: from the provider alone, "I see no build for this lease" is indistinguishable from "the build has not appeared yet", which is precisely the case an ambiguous launch deliberately keeps the parameter for. The only sound authorisation is the *ledger's* — the lease is terminal, and has been for longer than any build could still be running — and only the control plane holds it. So a codebuild node now REPORTS its parameter path and region at registration (wire 18, recorded beside the fleet; reported rather than refused, because the field decides where a sweep looks and every deletion is authorised per lease), and the control plane sweeps every path the fleet has ever registered on the reaper's tick — decommissioned hosts included, since a dead node's path is exactly the one nobody is left to clean. The rule per name is closed: a name that is not `billet-<lease>` is kept and counted foreign; a lease the ledger has never heard of is kept, counted, and named in the log (a ledger restored from an older backup, or a foreign writer, and a build may be running under it); an open lease is kept; a terminal lease closed less than the **service** maximum window ago (36h build + 8h queued + the hour of slack — the largest window any node could declare, so no node fact is needed) is kept; and only a lease closed longer ago than that, whose parameter is ALSO older than the window by AWS's own `LastModifiedDate`, loses it — the second proof because `finished_at` carries the clock of whichever billet closed the lease, and a clock a window slow would otherwise release a registration its build was still waiting to read. A ledger that cannot answer stops the pass with nothing further removed. The controller never holds a registration: it lists with `GetParametersByPath` and `WithDecryption=false`, decodes a type with no `Value` field, and its grant is `GetParametersByPath` plus `DeleteParameter` on the path and its children — no `GetParameter`, no `PutParameter`, no KMS, no CodeBuild action — rendered by the same generator as the other two roles, attached by the module's `controller_role_name`, and printed by `billet init iam --controller-sweep`. The listing is taken whole before any delete, because the real cursor is positional and deleting while paging measurably skips the next entry (finding 12 above). Each pass is recorded per path so `billet status` can report what was removed and which hosts registered without a path and are therefore unswept. What is left open: a node that re-registers under a new path stops its old path being swept, which the status record names.
- **A 5xx IS NOT A REFUSAL, and calling it one was a way to strand a build.** `Launch` deletes the staged registration on a *conclusive* failure, because a single-use credential left in Parameter Store is one nobody finds until it matters. The first version asked only "does this error carry a code" — and an AWS 500 carries one, so a server error that had **committed** the build and lost its response was read as proof nothing started. The build then starts, resolves nothing, registers nothing, and every signal Billet has says the launch merely failed. Only a 4xx is the service answering no; the retry policy already treated a 5xx as ambiguous, and the two must not disagree about the same response.
- **The log group is pinned on every launch, so the build role's grant is true by construction.** That role's policy is scoped to a group ARN. With no `logsConfigOverride` the *project's* own configuration decided where the build wrote — which agrees with Billet's derived default for a project Billet created, and does not for an adopted or edited one carrying a custom group. The result was a role that could not write its own logs. `config.CodeBuildConfig.LogGroupName` is the single derivation both the launch path and the IAM renderer read, for the same reason `CheckCodeBuild` is exported: two derivations of one value is one derivation that is wrong.
- **On rollouts: there is no new notion of "converged" to invent.** A codebuild node is a host Billet installs onto, so the rollout coordinator's observation-based convergence applies to it unchanged. The *builds* are not Billet installations — nothing is installed onto them and nothing upgrades them — and the non-destructive drain already covers them.
- **The JIT registration travels through SSM Parameter Store SecureString**, one parameter per build under a per-deployment path, referenced by a `PARAMETER_STORE`-typed environment-variable override named `ACTIONS_RUNNER_INPUT_JITCONFIG`. So the value never reaches argv, never reaches a buildspec command, and only the parameter *name* reaches CloudTrail. Chosen over Secrets Manager because `DeleteSecret` imposes a seven-day recovery window unless forced while `DeleteParameter` is immediate, and because a per-build secret is billed monthly where a standard parameter is not. It is written before `StartBuild` and deleted only once consumption is established; a parameter Billet cannot prove it wrote is never deleted.

  The trade this accepts is the one ADR-002 already states for EC2 user data, and for the same reason: the registration is readable by the job, because one build holds exactly one job and is single-use. What it must not become is a channel to anything else, which is why the build's service role is a **different principal** from the node role and gets its own least-privilege rendering.
- **Billet generates the buildspec and sends it as `buildspecOverride`**, for the reason ADR-002 gives about not shipping a Packer template: the contract between Billet and its runner is a few lines of shell, and a project-owned buildspec is a second place for them to disagree. Terraform creates the project with a minimal placeholder so `CreateProject` validates. The command is not a secret; the JIT config is never in it. And because it is generated, it is **executed in a test** rather than pattern-matched — the `ec2` boot-script lesson, where a quoted heredoc inside `$( )` produced a script that failed to parse on a later line and an instance that started, registered nothing, and reported success.
- **Billet pins all three Actions runner tarballs a CodeBuild tier can need.** `linux-x64`, `osx-arm64` for a `MAC_ARM` build and `linux-arm64` for an `ARM_CONTAINER` one all live in `internal/runnerrelease/pinned.txt` — the same one file, because *two pins is one pin that is wrong* — with line 1 unchanged so `scripts/build-guest-image.sh`'s `awk "NR==1{print \$2}"` keeps working.
- **Billet signs its own CodeBuild requests**, reusing `internal/awssig`, for ADR-002's measured reason: an SDK dependency is ~12 MB and 15 modules carried by every node in the fleet, including the bare-metal hosts these backends exist to fall back *from*. CodeBuild speaks AWS JSON 1.1 rather than the EC2 query protocol, so the signer gets **its own vectors** generated by `aws-sdk-go-v2` signing an identical JSON request — the EC2 vectors are query-protocol and prove nothing about a signed JSON body with an `X-Amz-Target` header.
- **`billet check` makes the ceilings visible before work is admitted**: the 36-hour build ceiling, the 8-hour queued ceiling, the macOS reserved-capacity requirement, the supported regions and shapes, the fleet's configured capacity and cost, and the account's concurrency quota for the configured shape. An unacknowledged ceiling and an unwatched quota are the two ways this backend disappoints somebody quietly.

  **The ceilings are `check`'s to report and not `status`'s, and that is a decision rather than an omission.** They are node configuration, and `billet status` runs against the control plane's ledger — on a multi-host deployment the control plane's own config file may carry no `node:` block at all, or one for a different backend than the codebuild node actually registered. A line printed there would speak for whichever config happened to be beside the ledger, which is worse than the check that speaks for the machine the builds are launched from. Putting them on the wire so `status` could report them truthfully is a protocol field for a diagnostic, and the node wire's rule applies: a field that decides nothing about capacity, fencing, identity, custody or destruction is not worth a version bump.

  **What `status` does now report for this backend is the money**, which it can answer from the ledger because a node registers its priced shapes: `alloc.RemoteCostNodes` covers every provider `RunsOnHost` excludes. It was scoped to `ec2`, so a deployment whose cloud capacity was codebuild printed no cost line at all — and the absence of a cost line is indistinguishable from a fleet that costs nothing.
