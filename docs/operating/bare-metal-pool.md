# A pool of rented bare metal

A control plane with `server.pool` in its config orders Firecracker hosts from rented bare metal, keeps a floor of them per architecture, and orders more when a Firecracker tier is short of hosts. [ADR-030](../reference/decisions/adr-030-rented-bare-metal-pool.md) is the design and [the bare-metal hosts record](../reference/records/bare-metal-hosts.md) what it was measured on; the [configuration reference](../reference/configuration.md) has every field.

## What is built, and what is not yet

- **Built:** ordering. The controller keeps each architecture's floor, never past the maximum, and orders one more host for a Firecracker tier whose fresh capacity report says it is short of hosts (it has work the allocator could not buy for, and every reason was a host: none that can place its shape, or none with room; a seal, a tier's cap, a share or the deployment ceiling never count, and a share or ceiling with no room for one more of the tier's shape is named beside full hosts or none, so a spent budget never reads as a shortage; nor does a tier draining or one whose count of waiting work is unknown), while no placed host is still on its way. It orders nothing on an architecture while any order there is unknown, being ordered or uncertain, because that order may hold a host already. It passes over a choice its source refused (no stock, a quota, a refusal an operator acts on) for `refusal_backoff`. A report older than five minutes, or in error, is not read as demand, and the floor is kept regardless. Its sources are AWS bare-metal instances (`aws-metal`) and phoenixNAP Bare Metal Cloud (`phoenixnap`).
- **Built: the join.** A host joins with `billet join --pool-order <order>` and its order's single-use token, as its node `pool-<order>`. On AWS it is admitted with no person when its source vouches for it: the instance is running, the enrollment came from its private address, the identity document it sends verifies under AWS's certificate and names it, and its console names only its key. A placed host counts as on its way until a node joins from it, so demand grows the pool one host at a time while one is on its way.
- **When the source cannot tell**, or on phoenixNAP, which has no channel to its hosts, the request waits in `billet nodes pending` with its order beside it, for you to compare the fingerprint with the host's console and approve it with `billet nodes approve`, as any node's.
- **When the source contradicts the host** (another key on its console, a document naming another instance), or another key already holds the host's name, its order is held: nothing is admitted from it and its token is not spent, and the host is told to wait, so it keeps asking. `billet pool` lists every held order with why. An order whose tokens all lapsed with nothing joined is held the same way. A held order still counts against the maximum and no longer counts as on its way. Its requests are recorded in `billet nodes pending` with the order beside them, without spending its token. Look at the host's console: deny a request whose key the console does not name, approve the one it does (`billet nodes approve`) if you are sure it is the host, release the hold with `billet pool unhold <order>` so its next ask is judged again, or release the host.
- **An address or a launch time that does not match** is not a contradiction: a NAT or a proxy in front of the enrollment listener explains the first, and the request waits for a person instead of holding the order. A listener behind `server.tls_router` is not asked to see a host's address at all.
- **Built: release on a person's word.** `billet pool release --reason TEXT <order>` releases a placed host, only on proof it holds nothing (ADR-030):
  - **A host a node joined from** leaves placement at once, and stays out across its node's restarts. The order is sealed once the ledger proves the host runs nothing, then the node's certificates are revoked and the source is asked to take the host back. The proof is that the host holds no lease, nothing in quarantine and nothing in custody, and its node was decommissioned on the compute barrier's proof. Two things the node says after that decommission contradict the release for good: an inventory of its current registration showing anything running, and the node arriving to register, even if its registration is refused. A later empty inventory does not undo it, and neither does a control-plane restart; only a fresh decommission on proof does. The decommission itself is left as you recorded it, so `billet drain` and a CodeBuild fleet's claim read it as they always have. The proof is read again every time the source is asked to take the host back, so a contradiction after the seal stops the release: `billet pool` lists the order as sealed, the pool's log says the release is contradicted, and a person looks at the host, takes it back in the source's console and closes the order with `billet pool close`.
  - **The procedure for a joined host**, until a node can drain alone:
    1. `billet pool release --reason TEXT <order>` takes it out of placement.
    2. `billet drain --wait` seals the whole deployment, so nothing new starts on any host until step 5, and waits until every host, this one included, answers twice across five minutes that it runs nothing.
    3. Stop the node on the pool host (`systemctl stop billet-node`). A decommission refuses a node still talking to the control plane.
    4. `billet nodes decommission pool-<order>` must say the exclusion was proved. If it says unproven, or refuses, the host is not proved idle; do not `--force` it for a release, because a forced decommission is never proof.
    5. `billet resume` reopens the deployment.
    6. The pool's next step seals the order. With no pool running (no `server.pool`, or a control plane stopped), `billet pool release <order>` with no `--reason` seals it, and `billet pool close` closes it once you have taken the host back in the source's console.

    A node that registers again after step 4 clears its decommission, so the procedure starts again from step 2.

    **A host whose node can never prove itself again** (it died, or lost the credential it authenticates with, which `billet ca issue` will not reissue for a `pool-` name) cannot be decommissioned on proof. Settle anything it still holds (`billet leases`, `billet leases release --force`, `billet force-destroy`), take the host back in the source's console, and close the order with `billet pool close --force --reason TEXT <order>`. Its node's certificates are revoked and the order records that a person closed it without proof.
  - **A node's inventory alone is never the proof.** It is stamped when it arrives, not when the node listed it, and a launch still running is in none. A node that drains alone, answering only once its launches settle, is owed; until it exists, releasing a joined host takes a deployment-wide `billet drain --wait`.
  - **A host a certificate was issued for under its order's name without the order knowing** (by `billet ca issue`, which v0.31.0 still accepted a `pool-` name from) is released as a joined host: the release links the order to that name, so its node's certificates are revoked at the seal. A decommission taken before that release does not count, because the order did not yet know its node; follow the procedure below from step 2 after the release. The same holds for a host joined before you upgraded to the billet that added release: decommission it again after the upgrade.
  - **A host admitted but whose node never registered** was never placeable, so it is sealed as soon as nothing holds it: at the pool's next step, or by `billet pool release <order>` with no `--reason`.
  - **A host nothing joined from** is sealed at once, on the ledger's word that nothing was ever admitted for it, and its tokens are retired.
  - Either way, the order is closed only on the source's own answer that the host is gone. `billet pool` shows a host still draining, and why it was released.
  - **phoenixNAP never says gone of a server it took back.** So on phoenixNAP, wherever the source is no longer configured or now orders somewhere else, and for a sealed host taken back by hand, a person closes the sealed or released order with `billet pool close --reason TEXT <order>`, after checking the source's console. The order's reason records that a person closed it.
  - **A `pool-` name is the pool's.** `billet ca issue` and `billet join` refuse one without its order, and a node registering under a sealed order's name is not placeable.
- **Not yet:** the pool does not shrink itself; a person releases a host. The pool's IAM, including the console read the join needs on AWS, is owed.

## An order's life

Every order is a row in the ledger, written before its source is asked, so `billet pool` always shows what was ordered:

- **ordering**: the row is committed and the source has been, or is being, asked.
- **placed**: the source named the host.
- **refused**: the source refused, or the order failed before anything reached the source; the reason is on the order.
- **sealed**: a release is proved and the node's certificates are revoked: nothing joins from the order or is placed on its host again, and the source is asked to take the host back.
- **released**: the source took the host back. It still counts against the maximum until the source says it is gone.
- **gone**: the source said, in its own answer for that host, that it is gone. Not-found and elapsed time are never that answer.
- **uncertain**: the answer was lost, the source lists no host for the order, and a resend could place a second one. On AWS, whose launches carry the order as an idempotency token, the pool sends a lost order again for ten minutes from its first attempt before it calls it uncertain; phoenixNAP takes no such token, so a lost answer there is uncertain at once. A resend the source refuses makes the order uncertain too: the refusal says nothing about the first attempt, which may have placed a host.

An order records where its source orders (an AWS account, region, subnet and zone; a phoenixNAP account). If the config or the credentials change so the source orders somewhere else, or the source is no longer configured or no longer declares the order's shape, an order still being ordered is not read back or sent again; it becomes uncertain, because reading it back anywhere else could miss the host it placed. Look where it was placed, then close it.

An uncertain order holds its place against the maximum and stops all ordering on its architecture, because it may hold a host. Its SCOPE column in `billet pool` says where it was placed; look for it there, in the source's own console: an EC2 instance tagged `sh.billet.pool-order=<order>`, or a phoenixNAP server named `billet-<order>`. The pool reads an uncertain order back where it was placed at every step, never sending it again, and an order its source now lists there is placed, so its host joins as any other; one placed somewhere its source no longer orders is not read there, and if there is one, it is real and can be released by hand; if there is none, close the order:

```bash
billet pool abandon --reason "no instance tagged with the order in us-west-2" p1a2b3c4d5e6
```

## What a host runs on its first boot

The `boot_prelude` script, then `billet join --server <join_server> --ca-fingerprint <the deployment's> --token <the order's> --node-name pool-<order> --pool-order <order> --provider firecracker`. The join dials the enrollment listener (`bootstrap_addr`, else the router's `enroll_addr`, else `server.bootstrap_listen`; a pool needs one, and the address the host dials may be neither a wildcard nor loopback). It writes `billet-pool-join order=<order> fingerprint=<its key's>` to `/dev/console`, on a line of its own, before every attempt and sends the instance identity document it reads over IMDSv2, when it has one. The source reads only a line that is that line and nothing else, and the join's own output spells that line's start without its hyphens, so nothing the join prints can stand for it. It runs once, so it asks again, with the same key, whenever an answer does not arrive (the authority, or an enrollment whose answer was cut off, which may have been its admission), and stops on a refusal, a denial, a TLS answer (a certificate that does not verify, a listener that wants a client certificate, which a `join_server` naming the node wire rather than the bootstrap listener meets) or its certificate. The prelude installs billet and what a Firecracker node needs (the host role's packages, the kernel and guest image), or is nearly empty on an image that already has them. It runs as a script of its own under `bash -euo pipefail`, so a command that fails, an unset variable or a failed stage of a pipeline stops the boot before the join, and whatever it sets or traces does not reach the join. Its output reaches the same console unguarded, so it must never print a line of the form above: printing what a network answered, verbatim, is how a forged one would get there. The whole payload carries a join token, so it is a credential: it reaches the source's API and nothing else, and it must fit EC2's 16384 bytes of user data.

## Credentials

- **AWS:** the control plane's own role, through the usual credential chain. It needs to launch, describe and terminate instances tagged `sh.billet.pool-owner=<deployment>` and read their console; the policy `billet init iam` renders does not cover pool hosts yet.
- **phoenixNAP:** an API client's id and secret, in the environment variables `phoenixnap.client_id_env` and `client_secret_env` name, never in the config. A new account may hold one server, and an API client may be refused orders until the account is cleared to order; the order is then refused with the API's own message.
