# ADR-002: Which AWS service runs a job, and why billet signs its own requests

**Status:** accepted, Aug 2026
**Decision:** **EC2, one instance per job**, launched with `RunInstances` directly, signed by billet's own SigV4 implementation.
**Rejected:** Fargate, Lambda, CodeBuild, EKS, AWS Batch, an Auto Scaling Group, and the AWS SDK.

## The requirement

A tier that lists `providers: [firecracker, ec2]` must be placeable on either, so that losing the bare-metal host does not take the `runs-on` label down with it. That is the whole point of the cloud backend — it is an **availability** mechanism, not a performance one, and a job that fails over runs with a cold cache by design.

The two backends do not share an image namespace or necessarily a runner entrypoint: Firecracker boots a Ceph generation such as `ubuntu-2404-x64@verified`, while EC2 boots a region-scoped AMI id. A multi-provider tier therefore carries one `launch` entry per accepted provider, each with that backend's image and optional command; the control plane selects the entry only after placement chooses a node and sends the node one concrete launch shape. Single-provider tiers retain the shorter top-level `image` and `command` fields.

What it has to run is a **GitHub Actions job**, and that is a stronger requirement than "a container": real workflows use service containers, `docker build`, and `docker compose`. Whatever runs a job has to be able to run Docker inside it.

## The options

| Option | Verdict |
|---|---|
| **EC2, instance per job** | **Chosen.** A whole machine, any AMI, Docker works natively, and the instance is a real isolation boundary — which is what lets this backend accept fork pull-request work that the container backend must refuse. |
| Fargate (ECS or EKS) | **Disqualified.** AWS's own docs: *"Features such as privileged containers or access are currently unavailable on Fargate. This will affect uses cases such as running Docker in Docker."* Requested since 2019 ([containers-roadmap#1000](https://github.com/aws/containers-roadmap/issues/1000), [#95](https://github.com/aws/containers-roadmap/issues/95)) and still open. It also cannot attach a block device — only EFS, a network filesystem, which is exactly what the caching plane exists to remove. |
| Lambda | **Disqualified.** A 15-minute ceiling against GitHub's 6-hour job default, and no Docker. |
| CodeBuild | **Disqualified, and interesting.** It has a native Actions-runner mode, so it genuinely could run the jobs — but it replaces billet rather than serving it. Placement, the capacity ledger and the caching plane are the product; handing them to AWS leaves nothing. |
| EKS / Kubernetes | **Disqualified by an earlier decision.** That is actions-runner-controller, and billet exists because ARC does not track individual jobs and Kubernetes absorbs the scheduling billet wants to own. See `docs/upstream-references.md`. |
| AWS Batch, or an Auto Scaling Group | **Wrong layer.** Both maintain a *count*. billet places a *specific lease on a specific host* and needs the instance id back synchronously, which is also why ADR-001 rejected an ASG for the control plane. |

**Firecracker is not available on EC2 outside `.metal` instances**, so on AWS the instance itself is the isolation boundary rather than a microVM inside it. That is why `provider.ProviderEC2`'s own documentation says so, and why this backend may accept `TrustUntrusted` at all.

## Why billet signs its own requests

The obvious move is `aws-sdk-go-v2`. It was measured rather than assumed:

| | Size | Modules |
|---|---|---|
| A program that only constructs an EC2 client and calls `RunInstances` once | **13.2 MB** | 15 |
| The whole of billet, before this backend | **21.8 MB** | 4 direct |

Adding roughly 12 MB and 15 modules would be carried by **every node in the fleet**, including the bare-metal hosts this backend exists to fall back *from*, and billet's stated identity is a single static binary. The `docker` backend already refused the Docker SDK for the same reason against a far smaller library.

Only four API actions are needed — `RunInstances`, `TerminateInstances`, `DescribeInstances`, `DescribeImages` — and the EC2 query API is form-encoded HTTP.

**What makes the trade safe is that the signer is pinned to AWS's own output, not to a reading of the specification.** `internal/provider/ec2/sign_test.go` carries vectors generated by `aws-sdk-go-v2` signing an identical request, with and without a session token, and the snippet that regenerates them. billet matches byte for byte. This is the house rule about third-party APIs — *pin it to what their code does* — applied to a signature.

Generating those vectors immediately paid: AWS's signer also signs `Content-Length`, and deliberately **excludes** headers something else writes later (`User-Agent`, `X-Amzn-Trace-Id`, `Expect`, `Transfer-Encoding`). Reasoning from the specification would have produced a signer that works until Go's transport adds a header, and then fails as a bare 403.

### What this does NOT give you, stated plainly

- **Only two credential sources**: environment variables, then this instance's IAM role over IMDSv2. Shared-config profiles, SSO and assume-role are not read — project them into the environment.
- **No AWS SDK middleware**: no adaptive retry, no client-side rate limiter, no request metrics. billet retries throttles and 5xx three times with backoff and gives up.
- **Four actions.** Anything else needs writing.

## Consequences

- **`node.max_vcpu` and `node.max_memory` are required for an ec2 node.** It is an orchestrator, not a machine: detection would report whatever small instance holds the process. They are hard resource budgets: the node registers its ordered shapes, placement charges the first fitting shape, and a fallback shape is authorised atomically against both the node and deployment ceilings before its request reaches AWS. Provider order makes home fill first. Each shape also declares `price_usd_per_hour`; `billet check` reports that node's conservative compute-only peak from those rates and the tighter of the node and deployment resource ceilings, while `billet status` reports the tighter of the shared deployment ceiling and the sum of every registered EC2 node's ceiling. Registration, rather than current liveness, defines that fleet report because a disconnected orchestrator may still have billable instances and can reconnect. The rate is operator-audited metadata, not a runtime gate: refusing a queued job because a copied price went stale would turn cost reporting into an unattended CI outage, while querying the separate Pricing API would make admission depend on another service. The shapes are the enforceable cost policy—do not declare a shape you are unwilling to buy—and an AWS Budgets alarm is the account-wide backstop. The estimate excludes EBS, NAT, transfer and every other account charge. Spot remains a separate reliability choice.
- **Spot defaults off.** GitHub does not requeue a job whose runner vanished mid-execution, so a reclaim is a failed build rather than a retry, and defaulting to spot would make the failover path the unreliable one. Enabling it requires `interruption_queue_url`, an SQS queue targeted by an EventBridge rule for `EC2 Spot Instance Interruption Warning`; the node role needs `sqs:ReceiveMessage` and `sqs:DeleteMessage` on that queue. billet long-polls it, durably records `ec2 spot interruption: <action>` on the lease before asking EC2 to terminate, keeps the capacity charged until termination is confirmed, and acknowledges the SQS message only after that handoff. A duplicate is harmless. This does not save the job—the warning is best effort and two minutes cannot migrate an Actions job—but it returns capacity promptly and leaves a reason in history instead of waiting for lease expiry. Spot remains explicit after this machinery because a cheaper build that can be reclaimed is still the wrong default for an availability backend. A live FIS experiment has exercised the EventBridge/SQS path and confirmed the durable failure reason, termination custody, capacity return and failed GitHub job; the measurements are in `docs/aws-acceptance.md`. (#41)
- **A node is a serial launch queue.** The node runtime executes one command at a time, so an ec2 node representing 64 concurrent jobs issues 64 `RunInstances` calls in sequence. The command timeout is 10 minutes, which is ample at normal latencies and tightens under throttling. The mitigation available today is to run several ec2 nodes, each a separately registered node with its own budget.
- **A successful `Destroy` does not mean the machine has stopped**, unlike every other backend. This was an open hazard and is now closed (#46): `Destroy` reports whether the compute is CONFIRMED gone or merely asked to go, and an unconfirmed teardown keeps the capacity charged to its host. A targeted lookup includes EC2's retained `terminated` record as causal proof while fleet inventory excludes that historical noise; if the record is unavailable, an absence must remain uninterrupted through the full remote-consistency window. The measurement below is what the design now assumes rather than what it violates. **Measured across four runs**: `Destroy` returned in **~410–600 ms** every time, and for a further **11 seconds to 1 minute 43 seconds** the provider went on reporting the instance as running. Two cautions on that number, both of which a reviewer had to force. It measures `Instance.Running`, which is true for every EC2 state except `stopped` and `terminated` — `shutting-down` included, deliberately, since a backend that cannot tell must not report live work as finished — so it bounds *how long billet believes compute may still be executing*, not how long a workload actually ran; the guest command in the test is `/bin/true`. And the variance is the point: this is not a constant anyone can build a timeout around, which is a further argument against "wait for it to stop" and for confirming quiescence out of band. That belief window is exactly what the listener used to act on, since it treated a successful `Destroy` as proof the compute is gone; it no longer does. `TerminateInstances` returns when the request is accepted, and the listener used to treat a successful destroy as its proof that compute is gone before releasing the lease. Destroy is reached on paths where the guest is still working — a drain, a custody teardown, an operator killing a job — so another job could start while the old one was still finishing a deploy or a migration. Waiting was never the answer, because a node executes one command at a time and teardown would stall every launch behind it. The answer taken was the one this entry predicted: keep the capacity charged while something confirms quiescence out of band, which is what custody already did for compute billet cannot account for — so the fix routed an unconfirmed teardown into it rather than building anything new.
- **Every EBS device leaves with an explicit `DeleteOnTermination`. On a NON-ROOT device an image's explicit `false` is honoured; the root is always `true`.** billet states the flag for every EBS device it launches, so no default governs. (Non-root instance-store and suppressed mappings carry no such flag and are left alone. A root that is not established as EBS-backed is refused at the image lookup, before anything is launched — every root parameter billet sends is EBS-shaped. An image that omits `rootDeviceType` is settled from its own block device mapping rather than guessed at: a root device carrying an `<ebs>` child is an EBS root, said by EC2 in a different sentence of the same reply. Only an image that proves it by neither route is refused. The population is narrow: AWS lists the instance types that can boot an instance-store root at all — C1, C3, D2, I2, M1, M2, M3, R3, X1, [every one previous-generation](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/RootDeviceStorage.html) — so the question arises only for a deployment pinning one of those nine families *and* supplying such an image. Measured across 26,052 Amazon-owned AMIs in `us-west-2` (a later, unfiltered scan the same month — the 26,044 above were selected *by* an EBS filter and so could not have contained a counterexample): all report `rootDeviceType`, all report `ebs`, and all describe the root in their own mapping with an `<ebs>` child. So the corroborating signal was never missing in that population — though nothing in that population omitted the type, so the fallback itself was never exercised there. `DescribeImages` omits deprecated and disabled images by default, making this a statement about what the call returned rather than about everything published. #54.)

  **This is the one behaviour in the backend that has been measured against real EC2**, because eight rounds of review could not settle it by reading and two reviewers reached opposite conclusions about whether billet was leaking a disk per job. In a live account: `RegisterImage` was given a mapping omitting the flag on both the root and a non-root device, and `DescribeImages` returned **`true`** on both — so an image registered without the flag shows `true`, not the `false` that [the mapping-concepts page](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/block-device-mapping-concepts.html) reads as the "attached volume" default. That is stated as the observable: it cannot distinguish normalisation at write from materialisation at read, and it reaches only the one registration path measured — `CreateImage`, `ImportImage`, `CopyImage` and older images are unobserved, so absent is unreached rather than impossible, and the code still handles it. Consistent with that, **zero** of 9,775 non-root EBS mappings across 26,044 Amazon-owned EBS-backed AMIs in `us-west-2` (measured Aug 2026) omit it — bounding prevalence for the most curated population there is, and only weakly for operator-built or imported images. A launch sending only `DeviceName` + `Ebs.DeleteOnTermination` for AMI-declared devices was accepted, **preserved each device's snapshot and size**, and landed both flags as sent; the device launched with `false` outlived the terminated instance and remained billable. The design did not change as a result — billet's choice for a silent mapping matched what the measured `RegisterImage` path produced — but it no longer depends on any of it staying true, and the other creation paths remain unobserved.

  Where a **non-root** mapping said keep, billet says keep and warns: that is the operator talking about their own AMI, and overriding it would irreversibly destroy whatever the job wrote to that volume, against a leak that is tagged, warned about, and deletable at any time. When one arm is reversible and the other is not, take the reversible one.

  **The root is the exception, and always leaves as `true`.** It is the one device billet already owns — it is the disk the runner boots, it lives for exactly one job, and when a tier asks for a size it is the one billet resizes; AWS permits only size, type and this flag to be modified on a root volume. An image whose root says keep would abandon a full boot disk on every job billet launches from it; since nothing measured produced that flag by omission, somebody likely meant it — but for a machine that outlives its work rather than for a one-job runner. billet overrides it and **says so**, which is what keeps the asymmetry honest. Two channels: one about the image's **intent** — filled silently where the image left a gap, contradicted out loud — and one about the **response's evidence**, where a flag billet cannot read (absent, or not one of `xs:boolean`'s four tokens) gets a line for being outside everything measured rather than for anything the image meant. billet states delete for those and proceeds; refusing would turn a field AWS marks optional into a failed CI job. (#53)

- **`billet ami build` builds the AMI**, driving EC2 itself rather than shipping a Packer template: the contract between billet and an image is six lines of shell, and a separate build tool is a second place for them to disagree. It costs one API action (`CreateImage`) on top of the four this backend already speaks. Provisioning reports success by stopping the instance — a script that fails never reaches its `poweroff`, so the builder stays running with its console log rather than being snapshotted half-finished. The image is minimal: runner, Docker, git, tar, ICU. `actions/setup-*` downloads toolchains at runtime and works; a workflow assuming one is preinstalled fails loudly. (#42)
- **Cold-start timing is measured at the job boundary without a warm pool.** Immediately before each `RunInstances` attempt billet writes that attempt's Unix epoch into user data; doing it after the AMI lookup and anew for every fallback shape keeps local setup and earlier synchronous capacity refusals out of the successful instance's number. The image records a second epoch after Docker is ready and immediately before it starts the runner. GitHub's supported `ACTIONS_RUNNER_HOOK_JOB_STARTED` hook records the third after the runner accepts a job and before any job step, then prints launch-to-job, launch-to-runner and runner-to-job milliseconds in one line. Missing, malformed or reversed timestamps exit zero without output: the observer is never allowed to fail the workflow. Three real cold jobs reached the first step in 47.609 seconds, 52.188 seconds and 58.662 seconds; they spent 37.936–43.220 seconds reaching runner readiness and 9.673–15.442 seconds from readiness to work. That is acceptable for fallback capacity and does not justify live, billable, unleased instances with unresolved trust and teardown semantics, so `warm_pool` remains refused. The acceptance record is in `docs/aws-acceptance.md`.
- **`DescribeInstances` is eventually consistent, and `List` is how billet finds its own compute.** **Measured**: an instance took **1.3 to 3.4 seconds** to appear in `List` after `Launch` returned its id — and on one run a single check right after launch did not see it at all. `Recover` enumerates live compute through `List`, so an instance invisible in the seconds after launch is one a reconciliation pass can conclude does not exist. Related to #48, which is about trusting `InvalidInstanceID.NotFound` on the destroy side; this is the same consistency model on the launch side.

- **Some of this has now run against a real AWS account, and the rest has not.** Every ordinary test drives a fake EC2 API. What has been exercised live, by `TestLiveSmoke` in `internal/provider/ec2` (opt-in, one instance, destroyed inline):

  - the hand-rolled **SigV4 signer**, accepted by real EC2 rather than only matching the SDK's bytes;
  - the **`RunInstances` request shape** billet builds, which launches;
  - **`List`**, including the owner tag filter and recovering a lease id from an instance name;
  - **`Destroy`**, including that a second one is safe;
  - the **`ClientToken` idempotency** — the test relaunches the same lease with a different disk size and AWS refuses it with `IdempotentParameterMismatch`, so a retried launch cannot quietly buy a second machine for one job (AWS documents this behaviour; it does not state how long a token is remembered, and neither does this);
  - and the block-device behaviour recorded above.

  A separate end-to-end acceptance then ran three real GitHub Actions jobs through the control plane, node and EC2 guest. JIT registration, checkout, a Docker build, a service container, runtime Go installation, successful completion and eventual instance disappearance all passed. A fourth job was interrupted through FIS and exercised the EventBridge/SQS reclaim path. The same unchanged workflow also completed on preferred local Firecracker capacity and then on EC2 after that contribution was withdrawn. EBS/S3 cache behavior remains unmeasured. See `docs/aws-acceptance.md`.
