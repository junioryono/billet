# Configuration

`billet.yaml` has ten top-level blocks. `billet server` reads `server`, `github`, `targets`, `tiers`, `nodes`, `sites`, `backup`, `images` and `release`; `billet node` reads `node` and `tiers` (and `server`, on a loopback node, to learn which deployment it joins). One machine running both roles reads one file. The annotated [`billet.example.yaml`](https://github.com/junioryono/billet/blob/main/billet.example.yaml) describes the measured Firecracker deployment; `billet init` writes a runnable file for any backend, and both are parsed by the test suite so they cannot drift from the schema.

Byte sizes are written as `32GiB`, `512MiB` and parsed exactly; durations as Go strings (`30m`, `6h`).

## `server`

| Key | Required | Meaning |
|---|---|---|
| `listen` | yes | the address nodes dial. A loopback address serves plain HTTP with no certificates; anything else requires mTLS |
| `bootstrap_listen` | no | a second address serving only `/v1/ca` and `/v1/enroll`, for a machine that has no certificate yet. Absent means no network enrollment (`billet ca issue` is the way in). Refused against a loopback `listen` |
| `node_tls_hosts` | when `listen` is a wildcard | every name and address a node will dial, including the one it dials `bootstrap_listen` by; both listeners present one certificate |
| `state_dir` | one of `state_dir` or `identity_dir`+`state` | shorthand for `identity_dir: <dir>` plus `state: {backend: sqlite}`; must be local storage |
| `identity_dir` | with `state` | the deployment identity, the node-wire CA and its rotation state, the process lock and the maintenance fence |
| `state.backend` | with `identity_dir` | `sqlite` or `postgres` |
| `state.postgres.dsn_env` | for `postgres` | the name of the environment variable holding the DSN, never the DSN |
| `controllers` | no | `single` (default) or `active-passive`; refused on SQLite |
| `identity.backend` | no | `file` (default) or `aws-ssm` |
| `identity.aws_ssm` | for `aws-ssm` | `region`, `prefix` (isolates one deployment in an account), `kms_key_id` |
| `max_vcpu`, `max_memory` | yes, positive | the deployment ceiling across every tier |
| `placement` | no | `pack` (default) or `spread` |
| `admission_order` | no | `fair` (default) or `fill`; which waiting tier takes the room a finished job leaves |
| `drain_timeout` | no | when billet starts reporting a drain as long; never a deadline |
| `job_detail_retention` | no | how long the ledger keeps a finished job's per-sample series, destinations and guest report (default `72h`, at least `1h`); past it they are deleted and `billet jobs show` says the job's detail was retired. The usage summary is kept |
| `metrics.listen` | with `metrics` | the control plane's Prometheus endpoint (`/metrics`); absent block, no endpoint. A literal loopback address (`127.0.0.1` or `[::1]`, not `localhost`) unless `metrics.allow_remote`; may not share a socket with any other listener in the file, however it is spelled. See [Metrics](../operating/metrics.md) |
| `metrics.allow_remote` | no | admits a non-loopback `metrics.listen`; the endpoint has no authentication |
| `metrics.pprof` | no | also serves Go's profiler under `/debug/pprof/`; refused on any `listen` that is not a literal loopback address, `allow_remote` or not, because a profile carries memory |
| `flight_recorder` | no | `true` keeps the last two minutes of the controller's execution trace in memory and writes them under `identity_dir/flight-recorder` when a heartbeat pass overruns or the claim is lost; off by default. See [Metrics](../operating/metrics.md#the-flight-recorder) |

## `github`

The first GitHub **target**: the owner whose runners this deployment serves, and the App credential for it. It is the target named `default`; `targets` below adds more.

| Key | Required | Meaning |
|---|---|---|
| `org` | one of the two | an organization; matched exactly, so padding is refused |
| `repository` | one of the two | one repository as `owner/name`, owned by a personal account or an organization; the target is that repository and nothing else the owner has |
| `app_id` | yes | written by `billet github-app create` |
| `client_id` | no | when set, the scale-set client signs with it; `billet check` reports which issuer it tested |
| `installation_id` | yes | creating an App does not install it |
| `private_key_path` | yes | the key GitHub issued once |
| `max_vcpu`, `max_memory` | no | this target's share: the most its tiers may hold at once between them, inside `server.max_vcpu`/`max_memory`; see [A target's share](#a-targets-share) |

A repository target is **untrusted-only**: a repository has no runner groups, so nothing on GitHub's side can restrict a pool there, and `trust: trusted`, `runner_group` and `workflows` are refused on a tier under one. Its repository becomes the cache scope of each of its tiers, which therefore publish from its default branch by default. Its App holds `administration: write` on that repository, the only permission GitHub offers for registering a repository's runners ([ADR-011](decisions/adr-011-targets-and-repository-scope.md)).

## `targets`

Further targets, each an organization or a repository with its own App, served by the same control plane, fleet, CA and identity. `targets` requires the `github` block, which is always the first target and always the one named `default`; a `targets` entry named `default` is refused as a second spelling of it. Two targets may not name one `private_key_path`.

| Key | Required | Meaning |
|---|---|---|
| `name` | yes | the target's name, in the tier-label grammar, unique; what `tiers[].target`, `github-app create --target`, the archive and the host role refer to it by |
| `org` or `repository`, `app_id`, `client_id`, `installation_id`, `private_key_path`, `max_vcpu`, `max_memory` | as for `github` | the target and its credential; with a file-backed identity every target needs its own `private_key_path`, with a store-backed one none may set it |

The target's GitHub path (`owner` or `owner/name`) is its identity on the wire and in the ledger; the name is a label for the operator.

### A target's share

Every target's tiers buy from the one deployment ceiling, so a burst of one target's CI can take every host another target's jobs need. `max_vcpu` and `max_memory` on a target's block cap what that target's tiers hold at once between them, charged the way the deployment ceiling is (a remote backend at the shape it buys). A zero or absent dimension is bounded by the deployment ceiling alone. Capping one target leaves the rest for the others: with `server.max_vcpu: 120` and `max_vcpu: 80` on a repository target, that repository's jobs never hold more than 80, so the other target always has at least 40. A tier held back by its own target's share also stops holding its place in `server.admission_order` against other targets' tiers, because room they free could never reach it. A share is refused when it is above the deployment ceiling, below one of its tiers' shapes, or below what its tiers' `reserved` floors hold between them.

## `node`

| Key | Required | Meaning |
|---|---|---|
| `name` | on loopback | otherwise the certificate's name; defaults to the hostname |
| `server_addr` | yes | the control plane's node wire |
| `bootstrap_addr` | no | used once at `--enroll`; falls back to `server_addr` |
| `provider` | yes | `docker`, `firecracker`, `tart`, `ec2`, `codebuild`; `simulated` is billet's own test-only backend and is refused anywhere in a configuration |
| `site` | no | one of the control plane's `sites`; required with `ebs_s3`; refused on `codebuild` |
| `max_vcpu`, `max_memory` | for `ec2` and `codebuild` | what this host contributes; detected on a host backend when unset |
| `tls.cert`, `tls.key`, `tls.ca` | for a non-loopback `server_addr` | from `billet ca issue` or enrollment; refused against a loopback server |
| `lock_dir`, `allow_unlocked_deployment` | no | the host-wide deployment lock; a shared directory must be setgid; failing to place the lock is an error unless opted out |
| `state_dir` | yes | generation pointers, image cache, the node's identity |
| `max_custody` | no | a bound on compute billet is holding without a completion; empty means none, and a job killed by it is archived failed |
| `drain_timeout` | no | when the node starts reporting a drain as long |
| `metrics.listen`, `metrics.allow_remote`, `metrics.pprof` | no | the node's Prometheus endpoint, under the same rules as the server's |
| `stop` | no | what a SIGTERM does while the node holds compute: `drain` (the default) waits for it; `handoff` (Firecracker nodes only) leaves it running for the next node process to adopt, for a host restarted to be upgraded or converged. A host leaving for good is drained or decommissioned, since nothing comes back to adopt what a handoff leaves |
| `cache.listen` | for interception and EC2 caches | one literal non-loopback address; `tls_cert`/`tls_key` required for EC2 and refused on the Firecracker bridge |
| `registry_mirrors` | no | `docker.io`, `ghcr.io`, `quay.io` origins |
| `monitoring` | no | measure each job from the host; absent means off; firecracker, docker and tart only, and `perf` and `guest` firecracker only (see below) |
| `power` | no | lower the CPU's ceiling while the node is idle and restore it before a launch; absent means off; firecracker and docker on Linux only (see below) |

### `node.monitoring` (optional; firecracker, docker and tart only)

`interval` (a Go duration, default `1s`, from `250ms` to `30s`; the upper bound keeps the package energy counter from wrapping unseen between readings), `rapl` (read `/sys/class/powercap/intel-rapl:0/energy_uj`, the package zone only, and share it among jobs by CPU time), `idle_package_watts` (the host's measured idle package power; requires `rapl`; with it the energy above the baseline is shared by CPU time and the baseline by reserved vCPUs, and without it the whole package is shared by CPU time and recorded as `rapl-unsplit`). On firecracker it also asks the jailer to enable the memory and io controllers for each microVM, but only for a controller `billet check` reports present, because the jailer refuses a launch whose key names a file the kernel does not provide. A firecracker node with `monitoring` therefore refuses to start, and `billet check` fails, unless the host proves both: each listed in the cgroup-v2 root's `cgroup.controllers`, and `io.weight` present in a cgroup that has io enabled (the kernel's weight-based io policy, `CONFIG_BLK_CGROUP_IOCOST`). The refusal names each controller that is missing or whose state could not be read, and how to enable both for the jailer's parent cgroup (`<root>/<firecracker binary name>`): on a host whose root lists them, `echo '+memory +io' > /sys/fs/cgroup/cgroup.subtree_control` enables them for the cgroups directly below the root, the jailer's parent among them, and on a hierarchy with no cgroup below the root yet, creating the jailer's parent after that gives the check one to read. An `io.weight` counts only as a regular file in a domain cgroup that is still there. Without `monitoring` the same host is only reported, as before. On docker, a job's network is its container's own `eth0`, read from the host through `/proc/<container init pid>/net/dev` without entering the container, and only while that pid is still the container's; traffic on any other network the container is connected to is not counted, and a container in the host's network, another container's or none has its network recorded as unmeasured. A group the host could not read is recorded as unmeasured, never as zero. Energy is also recorded as unmeasured on a host with more than one package (package 0 alone cannot be shared by CPU time counted on every socket), for an interval whose jobs ran longer than the host was busy, and for a job the sampler missed three intervals of. A job a node adopts goes on being measured, and its usage is reported as its compute goes, as a launched job's is: one the same process held already keeps its series unbroken; one a handover left keeps what the process that handed it over measured (kept under the node's `state_dir`, in `usage/`), with the time between the two processes marked `handover`; and one a crashed process left is measured from its adoption. A job whose compute ends while no node process runs, or before the adopting process has found its counters, reports no usage. Neither counts hardware counters, gets package energy or has its traffic totalled by destination, since what happened before the adopting process looked was counted by nobody there; everything the job's cgroup counts over its whole life is measured as ever. A job's disk written is what its cgroup's `io.stat` counts plus what its memory cgroup still holds dirty (`memory.stat` `file_dirty`): a guest's writes, `O_DIRECT` inside the guest included, reach the host's page cache and are counted by `io.stat` only when the host writes them back, about 30 s later, so a job whose VM stopped sooner had its last writes counted by no cgroup (measured 2026-10-09, #457). The two files are read with `io.stat` on both sides of `memory.stat`, and read again when writeback moved bytes in between. When writeback moved them on all three passes, the sample keeps the first `io.stat` plus `memory.stat`, a lower bound short only by what writeback submitted between those two reads, a fraction of a millisecond apart, and the next sample that reads them still restores the total. A window that starts or ends on such a sample can be off by that much, the same order as the writeback batch every written figure is already exact to; only a written counter that rose on every pass counts, and one that fell is not measured. Writeback for a VM with gigabytes dirty kept `io.stat` moving through every pass on 3 samples in 120 (the reference node, 2026-10-16), and dropping those samples instead had left two seconds of a job's series unseen. The written figure never falls between samples, so it can include data a job wrote and discarded before the host wrote it back, and it is exact only to within one writeback batch, because the kernel clears a page's dirty flag a moment before it submits the page. Without `memory.stat` the written figure is not measured rather than a lower bound.

`flows` (firecracker only) totals each job's traffic by destination from the host's connection tracker, so the numbers are the host's and a job cannot forge them. The node learns the guest's address from the DHCP lease its bridge's dnsmasq granted it (under `/var/lib/billet-dnsmasq/<bridge>/`, the host role's layout), accepting only a lease granted after the job started, since a later job reuses a tap's MAC. A flow is the job's when its original source is that address and the tracker stamped its start between the DHCP grant and the start of the job's destroy, which keeps out entries the address's previous holder left behind (an established TCP entry lives five days) and the next holder's. Before the result is taken, the node proves its listener has read every destruction up to that moment by creating and deleting a sentinel entry on loopback. It needs `net.netfilter.nf_conntrack_acct=1` and `net.netfilter.nf_conntrack_timestamp=1`. A node asked for flows turns either on when it reads 0 and logs that it did, because a setting persisted under `/etc/sysctl.d` is applied at boot only if the connection tracker is loaded by then (on the reference node it was not, and the node refused to start after the reboot of 2026-10-14). It refuses to start, saying so, when the tracker is not loaded at all or a switch cannot be read or set. Each job keeps its 256 largest destinations, with the rest under one total, and is marked incomplete rather than short when the listener was not reading at any point in its time, it opened more than 65,536 flows, a flow carried no start time, its traffic joined an entry the previous holder left, its address changed, or the end could not be proved read. Attribution is by source address, which the host's guest network does not yet stop a root guest forging, so the totals are for people to read and no decision is made from them. When the job's compute is destroyed the node logs its totals and reports them with the rest of its usage, beside the tap's own totals for the job (less 14 bytes a packet for the Ethernet header), and the control plane keeps them, at most 257 rows a job, for `billet jobs show` to print: a large difference between the tap and the destinations is traffic no destination accounts for, such as a flow missed or traffic conntrack never tracks, though the two are read a moment apart, so it is a comparison of counters rather than an exact measure of what was missed. A job whose flows were not totalled is recorded as not measured, never as a job that sent nothing, and so is one with no usage report to carry them (the sampler never measured it, or the report did not reach the control plane). Reporting destinations needs wire 27; against an older control plane the node reports the rest of the usage without them.

`perf` (firecracker only; default off) counts each microVM's vCPU threads with the CPU's hardware counters through `perf_event_open`: one group of six events per `fc_vcpu` thread (cycles, instructions, cache references, cache misses, branch misses and frontend stall cycles), opened on the thread on whichever CPU it runs, with guest mode and kernel mode both counted, since a vCPU thread spends most of its time executing the guest (the `perf` command excludes guest mode unless an event is written `cycles:HG`). Counts are scaled by the group's enabled and running times when the kernel multiplexed it. A thread is counted from when the sampler first sees it: one that appears later is picked up at the next sample, and one that exits keeps its last reading. An event the CPU does not have, or one that could not be counted on every vCPU thread for the whole time (a group the kernel never scheduled, a thread that could not be opened), is recorded as unmeasured rather than as a lower total; a failure costs the measurement, never the job. A node refuses to start with `perf` on a platform without `perf_event_open`, and on a host where the group never counts: at startup it opens the group on a thread of its own pinned to each CPU it may run on in turn, keeps that thread busy until the group counts or has been enabled, which for a thread means running, for ten of the kernel's rotation intervals (`perf_event_mux_interval_ms`, the longest of any PMU, and at least 15 ms) without counting, and refuses unless the group counted on every one (a thread given too little time to tell within about two seconds is refused as unknown, never blamed on a held counter, and a group that never counted is refused naming a held counter or other groups as the reason, since the node cannot tell which), because the kernel schedules a group whole or not at all and a counter can be held on some CPUs only. The reference host has six core counters and the NMI watchdog (`nmi_watchdog` 1) holds one of them, so there the group of six is never scheduled (measured 2026-10-09: `perf stat` with the six as one group on a live `fc_vcpu` thread counted none of them, and five of them as a group counted all the time) and the node refuses, naming the watchdog; `sysctl kernel.nmi_watchdog=0` frees the counter. Reporting counters needs wire 26; against an older control plane the node reports the rest of the usage without them.

`guest` (firecracker only; default off; refused without `node.cache`) asks each guest to start billet's in-VM agent, by the optional metadata key `guest-monitor` (an optional key, so the guest contract does not change and an image older than the agent starts nothing). A guest image that carries it starts `billet guest monitor` as root when the key says `1` and the job has a cache session, handing it the endpoint and bearer as its environment and sending its log to the guest's journal; names a job-completed hook for the runner that asks the monitor for its final batch before GitHub records the job (it prints nothing, waits at most 4 s and always exits 0); and, once the runner has exited, sends the monitor SIGTERM, waits at most 3 s and kills it if it is still there. Nothing the monitor does changes the job's result. The node serves the agent two routes on the guest cache service, authenticated by the guest's own cache bearer: `GET /v1/guest/limits` (the agent's hello, answered with the schemas, interval and largest body the node takes) and `POST /v1/guest/reports`. With `guest` off both answer 404. The job is root in its VM and can send anything the agent would, so what arrives is the guest's own, unverified view: the node keeps it for an operator to read, labelled as the guest's, and decides nothing from it. The lease a batch belongs to is the one the bearer's session was made for, never anything in the request. The node holds every limit whatever the guest sends: a body of at most 64 KiB, read only after the cheaper checks; per job, a bucket of one batch every five seconds with a burst of four (429 with `Retry-After`) and 2 MiB of accepted batches (413); per node, at most eight batches decoded at once (429); and a strict decode, so a batch that is not exactly what the agent's encoder writes is refused (400). Refusals are counted and never logged, because what they would log is the guest's. The batches are kept in memory with the job's cache session and lost if the node process restarts, which the record then says. When the job's compute is destroyed, while the lease is still held, the node merges them, halves their resolution until they fit 256 KiB, and sends them with what it counted (whether the agent said hello, batches accepted and refused, bytes refused, whether the last batch arrived, whether the node restarted, and when on its own clock the first and last batch arrived), bounded at two seconds and never failing the destroy. A guest that never contacted the node still gets a record, with no hello and nothing accepted; a job with no record at all ran on a node with `guest` off or against a control plane older than wire 29, which takes none. `billet jobs show` prints the record, in its text, `--json` and `--html` renderings, labelled as the guest's ([the CLI reference](cli.md)).

On tart there is no cgroup: each VM runs in its own Virtualization.framework process, which billet finds as the one such process holding the VM's `disk.img` open, and measures by that process's own accounting (`proc_pid_rusage`). CPU is the process's user and system time, memory its physical footprint and lifetime peak, disk the bytes it moved to and from storage, and energy macOS's own estimate for the process, recorded with the source `process` and no idle share, since the machine's idle draw is not in it. The OOM count, network, pressure and the guest/VMM thread split are recorded as unmeasured, because macOS keeps none of them for one process. `rapl` and `idle_package_watts` are refused on tart. Reporting the `oom` group and `process` energy needs wire 25; against an older control plane the node reports energy unmeasured, and memory unmeasured whole.

The per-sample series a node reports with each job records the wall time of its first sample on the host's clock and marks every interval the sampler did not see, with why: `missed_tick` (it took no sample for two intervals or more), `failed_read` (a read of a group it had read before failed; that tick keeps no sample, since it would hold the group's last value at a time it was not read), `late_first_read` (every interval before a group was first read, which held that group at zero), `slow_read` (a read of the job took a whole interval), `counter_fell` (a counter fell, and the interval after it, which holds the catch-up), `final_energy` (the last interval of a job whose energy is shared from the package, since the final sample takes no package reading), `sampler_stuck` (a final sample taken while the sampler did not answer), `handover` (the time between the node process that handed a job over and the one that adopted it) and `several` (one interval with more than one cause, as when a long series is halved). Each sample holds the time its read ended, not the time the tick began. `billet jobs show` places a job's steps on that clock, leaves a marked interval uncovered, and lists every one with how long it lasted and why. The clock and the marks need wire 28 and the causes wire 30; against a control plane at 28 or 29 the node sends the marks without their causes (read back as `unspecified`), and against an older one the series without the clock or the marks, and no step is given usage. With `metrics`, the node counts each marked interval by cause (`billet_node_usage_gaps_total`), times each tick of the sampler (`billet_node_usage_tick_seconds`) and counts the disk reads it recorded as a lower bound ([Metrics](../operating/metrics.md)), and its log says each job's unseen time by cause beside the report.

### `node.power` (optional; firecracker and docker on Linux only)

`idle_after` (a Go duration, default `60s`, at least `10s`, so the ceiling does not move between the jobs of one burst), `disable_boost` (write `0` to `/sys/devices/system/cpu/cpufreq/boost` while idle), and `idle_max_freq_khz` (the `scaling_max_freq` written to every cpufreq policy while idle, in kHz as sysfs spells it; a policy whose ceiling is already at or below it is left alone). At least one of the two must be set, since a block that changes nothing is refused. The node is idle when it has recovered what an earlier node process left (so a restarted node whose registration keeps failing never caps the guests it has not adopted yet) and holds nothing: no instance running, none launching and none in custody. The node looks every 5 s; once it has been idle for `idle_after`, and only when every policy's `scaling_max_freq` is at its full (the top of its `scaling_available_frequencies`, with its `scaling_boost_frequencies` while boost is on, or `cpuinfo_max_freq` where there is no table), it records what it is about to change (every policy's `scaling_max_freq`, and with `disable_boost` the global switch and each policy's own `boost`) in `<node.state_dir>/power-baseline.json`, durably, before the first write, then writes the cap and reads every value back, for up to 1 s, since Linux applies a `scaling_max_freq` store through a scheduled policy update rather than at once. A cap that fails part way is followed at once by a restore attempt; if that fails too, the host may stay partly capped, the record is kept, and the node retries every 5 s. A ceiling below its full is not capped from, because `scaling_max_freq` reads the least of every limit on the policy (a firmware `_PPC` limit among them) while a write sets only the user's, so writing the lower value back would keep that limit after it lifts; such a node is left alone until every ceiling is at its full again, which also means a host whose operator lowered `scaling_max_freq` by hand is never capped. Every launch asks for the full ceiling back after its hold on the lease is placed and before the provider is asked to start the guest, waiting at most 2 s; a restore that fails or overruns does not stop the launch, which may then start capped (a capped host runs a job slower, not wrong), and is logged as an error and is retried on every tick until it holds. A restore writes the global boost switch first, then each policy's own (skipping a switch already at its value, since the kernel refuses a policy's switch while the global one is off), then every policy's ceiling, reads each back, and removes the record only once all of them read as recorded. Every restore is such an attempt, retried while the node runs, and the node also makes one when something it did not launch makes it busy, when its stop begins (and caps nothing after that, through the whole of a drain), when it stops (trying for at most 30 s; a stop that cannot restore leaves the cap and its record for the next node process, and says so), and at its start whenever it finds the record, whatever `node.power` says by then: it tries before it reads its certificate or takes its deployment lock, so a start refused for any reason has still tried (an upgrade probe never touches cpufreq). A restore that fails there is logged; a node that goes on to run retries it every 5 s, and one whose start is refused leaves the cap and its record for the next attempt. A record it cannot read, one naming no policy, or one followed by anything else is never taken for no record, so nothing is written from it and nothing is capped over it. At its start, a node with `node.power` refuses to run on anything but Linux, on a host with no cpufreq policy, with `idle_max_freq_khz` that is not one of every policy's `scaling_available_frequencies` (a driver that lists none, such as `intel_pstate`, is refused rather than trusted to take the value as written) or is below a policy's `scaling_min_freq`, and with `disable_boost` on a host without the global `boost` file (billet writes no other switch, such as `intel_pstate/no_turbo`). One process on a host runs the policy: a node with `node.power` holds an exclusive lock on `/sys/devices/system/cpu/cpufreq` itself (a `flock` on the directory, which the kernel drops with its holder) for its whole life, a second node with `node.power` on the same host is refused at its start, and nothing is ever written without that lock, so a start's restore of an earlier cap takes it too and leaves the record for later while another process holds it. A cap is the host's, so it slows any guest on the host, another node's included, while this node is idle: run `node.power` only where this node is the host's one workload. With `disable_boost` a cap is also taken only while boost is on, globally and on every policy that has its own switch, since boost already off is another cap or an operator's setting. A cap whose record is removed or damaged while it is in force is restored from what the node holds, and the loss is logged. The node runs as root, and `billet-node.service` leaves `ProtectKernelTunables` off, which is what leaves `/sys` writable under `ProtectSystem=strict`. The reference host (an AMD EPYC 7763 under `acpi-cpufreq` and `schedutil`, read on 2026-10-23) lists `2450000 2000000 1500000` and has the global switch, so `idle_max_freq_khz: 1500000` with `disable_boost: true` is admitted there. Each cap and restore is logged and counted (`billet_node_power_changes_total`), and the latest launch restore's latency is `billet_node_power_last_launch_restore_seconds`, measured from the launch asking to every value read back.

### `node.firecracker` (required for firecracker, refused otherwise)

`binary_path`, `jailer_path`, `kernel_image` (required; the fallback for a generation that recorded no kernel), `kernel_dir`, `chroot_base`, `jail_uid_min`, `jail_uid_count`, `bridge` (required), `untrusted_bridge` (absent means untrusted work is refused), `image_verify_port`, `cpu_placement`.

`cpu_placement` pins each microVM's vCPUs to host cpus through its cgroup's `cpuset.cpus`, and is absent by default, which lets every guest run on every cpu. `compact` gives a guest whole cores, both SMT siblings, in the lowest last-level-cache group (an EPYC CCD) with room for it, so busy guests share as few groups as possible. `spread` gives it one thread per core, in the group with the most free cores. `packed` gives it one thread per core from the lowest group with a free core onward, so guests share no cores and fill as few groups as they can. Each cpu is claimed for one guest at a time, like its uid and tap, and recorded in its jail, so a restarted node keeps what each running guest holds. A guest the placement cannot fit runs on every cpu, with a warning, rather than being refused. The node refuses to start when the host's cpus cannot be read or its cgroup hierarchy has no `cpuset` controller.

### `node.ceph` (required for firecracker, refused otherwise)

`conf_path`, `user` (defaults to `billet`; `admin` is refused), `keyring_path`, `image_pool` (required), `cache_pool` (required).

### `node.tart` (optional)

`untrusted_isolation` (`softnet`; absent means untrusted work is refused, and naming it makes `billet check` fatal until softnet is setuid root), `untrusted_dns`.

### `node.ec2` (required for ec2)

`region` (required), `endpoint` (https, loopback excepted), `subnet_id` (required), `security_group_ids`, `untrusted_security_group_ids` (absent means untrusted work is refused), `assign_public_ip`, `instance_profile` (optional, and empty is the right answer unless a job needs one), `instance_types` (ordered; each `type`, `vcpu`, `memory`, `price_usd_per_hour`), `spot`, `interruption_queue_url` (required with `spot`; its basename must equal the node's name, and its host must be one `region`'s own partition serves — `sqs.<region>.amazonaws.com` and its legacy and VPC-endpoint forms in the commercial and GovCloud partitions, the `.amazonaws.com.cn` versions of all three in China, and never a mixture, because billet signs the request for `region` and sends it to that host. The host must also be a hostname in its own right — every label ASCII, alphanumeric at both ends, 63 characters at most and 253 for the whole name — on port 443 or no port at all, since the host and its port are what the node dials).

### `node.codebuild` (required for codebuild, refused otherwise)

`region` (required), `endpoint`, `project` (required; billet's alone), `fleet_arn` (reserved capacity; the only route to macOS; untrusted work is refused with it set), `environment_type` (`LINUX_CONTAINER`, `ARM_CONTAINER`, `LINUX_GPU_CONTAINER`, `LINUX_EC2`, `ARM_EC2`, `MAC_ARM`), `compute_types` (ordered; each declares what it holds and costs), `accept_external_build_ceiling` (no default; absent is a refusal, because the 36-hour and 8-hour ceilings are CodeBuild's), `build_timeout_minutes`, `queued_timeout_minutes`, `jit_parameter_path` (required; an IAM boundary), `jit_kms_key_id`, `log_group`, `privileged_mode`, `untrusted_vpc_id`, `untrusted_subnets`, `untrusted_security_group_ids` (all three or fork work is refused; refused beside `fleet_arn`).

### `node.ebs_s3` (for an EC2 site's cache)

`region`, `availability_zone` (must match the subnet's), `bucket`, `prefix`, `kms_key_id`. It exists only to back `node.cache`: without that listener nothing reads it, so `billet check` refuses the pairing rather than letting every job run cold on the instance's root volume.

## `tiers`

| Key | Meaning |
|---|---|
| `label` | the tier's identity inside the deployment (its leases, escrow and history), unique across the file; also the `runs-on` value and the scale set's name unless `runs_on` names another |
| `target` | which target's scale set this is; defaults to the only target and is required when there are several |
| `runs_on` | the scale set's name on its target and the `runs-on` value workflows use; defaults to `label`. Unique within a target, so tiers on different targets can each answer to the same name (`billet-2vcpu-ubuntu-2404` on every organization) while their labels stay distinct. With `sizes` it expands as the label does. Changing it moves the tier to a new scale set; the old one is reported as undeclared and removed with `billet teardown --tier <old> --runner-group <group> --target <target>`. Runners already registered in the old set are not moved: an idle one can take a job still aimed at the old name until it is retired, so change it when that name is no longer in use, as with a `runner_group` change |
| `trust` | `untrusted` (default) or `trusted`; trusted requires `runner_group` and `workflows`, and is refused under a repository target |
| `runner_group` | a non-default group GitHub restricts; empty means GitHub's default group; `&`, `#`, `;`, `%` and `+` are refused because the client does not escape them |
| `workflows` | the exact allowlist the group must carry, with refs |
| `provider` or `providers` | one backend, or an ordered preference list; never both |
| `launch.<provider>` | per-backend `image` and `command` for a multi-provider tier |
| `guest_os` | `linux` (default), `macos`, `windows` |
| `node`, `site` | pins; a single-backend macOS tier pins a node |
| `vcpu`, `memory` | the request; or `sizes` with `memory_per_vcpu` to expand a template into several tiers |
| `disk` | usable root capacity on Firecracker and EC2; ignored by Docker |
| `shm`, `buildkit_cache_mount_limit` | the shared-memory size and the per-mount BuildKit ceiling |
| `image` | a Firecracker image `name@generation` or `name@verified` (a bare name is refused), an AMI id, a container image, or a tart OCI reference; never one beginning with `-`, which a backend's command line would read as an option |
| `command` | the guest command; `command-missing` is a conclusive launch failure |
| `cache` | the tier's caches and how they publish; see [`tiers[].cache`](#tierscache). Every cache the tier can have is on without it |
| `cache_scope` | the static repository (`owner`, `repository`) a tier's caches are scoped to, and for a trusted Actions cache the `workflow_ref` its runner group admits; a repository target supplies it |
| `intercept` | the deprecated spelling of `cache.actions.enabled`; refused beside `cache.actions` |
| `max_concurrent`, `reserved` | a ceiling and a floor; a macOS tier's ceiling defaults to what its hosts permit between them |
| `warm_pool` | refused when non-zero; no backend implements it |

### `tiers[].cache`

Everything here is optional; [Build caches](../operating/build-caches.md) explains each cache. A cache on by default that the tier cannot have (the Actions, Git, Bazel and Go caches need a Linux Firecracker tier) is off; one a tier turns on explicitly is refused where it cannot run.

| Key | Default | Meaning |
|---|---|---|
| `publish` | `default-branch` for an untrusted tier with a repository scope, otherwise `trusted-only` | `trusted-only`: a trusted pool publishes what it writes and an untrusted one nothing. `default-branch`: only a job GitHub proves ran on the default branch under a writing event publishes; needs a repository scope and the App's `actions: read`. `off`: nothing publishes |
| `docker.enabled`, `docker.max_size` | `true`, `100GiB` | the guest's Docker image store and its ceiling |
| `sticky_disks.enabled`, `sticky_disks.max_size` | `true`, `100GiB` | `actions/stickydisk` volumes; a larger request is clamped |
| `actions.enabled`, `actions.max_archive` | on where the scope already holds, `10GiB` | the transparent Actions cache; an untrusted tier needs `default-branch`, a trusted `trusted-only` one a `cache_scope.workflow_ref` in its `workflows` |
| `git.enabled`, `git.max_size` | `true` on Linux Firecracker, `50GiB` | the Git mirror for `github.com` fetches; a repository above the ceiling is not mirrored |
| `bazel.enabled`, `bazel.max_size` | `true` on Linux Firecracker where the tier can publish it (trusted under `trusted-only`, or `default-branch`), `50GiB` | Bazel's HTTP cache and the Remote Execution API for Bazel and Buck2 |
| `go.enabled`, `go.max_size` | `true` on Linux Firecracker where the tier can publish it, as for Bazel, `20GiB` | the Go build cache through `GOCACHEPROG` |
| `go.test_results` | `false` | also cache `go test` results; off, the guest sets `GOFLAGS=-count=1` |
| `npm.enabled` | `false`, the one cache off unless named | the node serves `registry.npmjs.org` to the tier's guests from a store of its own, answering only anonymous reads and splicing everything else to the registry ([ADR-020](decisions/adr-020-npm-registry-interception.md)); Linux Firecracker only. It has no `max_size`: the store is the node's, shared by every tier on it |

A `max_size` is at most `100GiB`, and a baseline larger than a tier's ceiling is not cloned: the job starts cold. A tier an older node would exceed is placed only on a node at protocol 23 or later: every `default-branch` tier (an older node would read the pool's wider pre-#226 keys), a trusted pool publishing `off` or `default-branch`, the Docker store or sticky disks turned off or held smaller, and an Actions archive held below `10GiB`.

## `nodes`

Per-host policy, not a roster: `name`, `provider` (decides only whether an unpinned tier could land here), `guest_os` allowlist, `macos_vm_limit` (defaults to Apple's two on a host that runs work; a cloud fleet gets no default cap). `macos_vm_limit > 0` beside an allowlist excluding macOS is refused.

## `sites`

`name` (matched exactly) and `store` (`ceph` or `ebs-s3`). A node's provider must be one the site's store serves; a tier that names a site may not list `codebuild`.

## `backup`

`s3.bucket`, `s3.region` (required even with an endpoint), `s3.prefix` (default `billet-backups`), `s3.endpoint` (path-style, for RGW, MinIO or R2), `s3.kms_key_id` (empty means SSE-S3). billet never deletes from the bucket.

## `images`

`source` (empty means billet's own published images), `signing_identity` and `signing_issuer` (both required for a non-default source), and `accept`.

`accept` names the components of GitHub's runner image whose licenses this deployment accepts: `android-sdk`, `codeql`, `firefox`, `google-chrome` and `microsoft-edge`. A name that is not one of the five, or a name written twice, is refused. Empty is the default, and nothing is ever accepted on the operator's behalf. Written in the control plane's file, it is accepted for every node: the control plane sends it to each node when the node registers, the node records it as `image-acceptance.json` in `node.state_dir`, and a node installs what either its own `accept` or its control plane's names. A node takes up a change at its next registration, which restarting `billet server` causes on every node; a node whose control plane is older than this release uses its own list alone. A node whose control plane runs on another machine refuses to pull, verify or promote an image until it has registered once, since until then it cannot tell what its deployment accepts. The component names travel between the control plane and the nodes, so accept a component a newer billet adds only once every node runs that billet; an older node refuses its image commands, naming it, until it is upgraded. `billet init` writes it empty on a Firecracker host, with each name and a link to its license above it, and `billet check` reports what each tier's image left out that is not accepted ([Components the image leaves out](../operating/guest-images.md#components-the-image-leaves-out), which also lists the vendor hosts a firewalled node must reach).

The five components' licenses forbid billet redistributing them, so billet's published guest image is to leave them out (#584). A pull of an image that leaves components out installs each accepted one into it before importing it. The install runs in a completion microVM on the node, booted from the newest verified generation of the image whose kernel is on the node, with the new image attached as its second disk. Without one, the pull first imports the image as published as a completion root, a snapshot no tier can boot and no command treats as a generation, boots that, and removes it afterwards whatever the completion came to. GitHub's own installer and tests run for each component, inside the guest. The image is imported only if every accepted component installed and its filesystem then checked clean. Otherwise nothing is imported and every tier keeps the generation it has. Each generation records what its image left out and the version installed of each accepted component. `billet images refresh` pulls the image again while its newest generation lacks a component the deployment accepts or carries one it no longer accepts, so accepting a component later completes the next generation, and `billet images verify` and `promote` refuse to mark a generation that lacks one. billet's build leaves them out of every image it publishes, and proves before publishing that each completes, by completing a copy of the image with each one on the builder. An image built before that carries all five and declares none, so a pull of it installs nothing.

## `release`

`channel` (`stable` or `candidate`) or `version` (an exact tag or a 40-hex commit; `latest` and `main` are refused; setting both is an error), `automatic` (on unless written `false`; the one switch for the control plane starting rollouts, the hosts' scheduled updaters acting on them, and the daily guest-image refresh), `maintenance_window.start`/`end` (HH:MM UTC; bounds when an automatic rollout may begin and never stops one), `signing_identity` and `signing_issuer` (both or neither; honoured by `rollout start`, `host-upgrade` and the automatic starter alike).

## Rules that are not visible in the schema

- Tiers and `nodes` are read at startup and snapshotted; changing them restarts the control plane. Nodes register dynamically.
- A path, pool, region or endpoint is trimmed; an identity (`sites[].name`, `tiers[].site`, `node.site`, `github.org`, `github.repository`, `targets[].name`, `tiers[].target`, `tiers[].runner_group`) is refused with padding, because a trimmed identity names a different deployment on another machine.
- `node.ceph` is refused on every backend but firecracker; `node.cache` is refused on docker; `node.ceph` and `node.ebs_s3` are refused on codebuild.
- The mirror of those — a store with no `node.cache` to serve it — is a `billet check` verdict rather than a load refusal, because `billet decommission` and `billet init iam` both read a store block on a config that has lost its listener. `node.ebs_s3` without a listener FAILS the check; `node.ceph` without one is reported, since `image_pool` still boots every guest and `cache_pool` is a required field.
- `billet init` writes a whole file and refuses to replace one it cannot prove is its own output (it writes `<path>.new` instead; `--force` overrides); `billet github-app create --config` edits five scalars under `github:` (or, with `--target NAME`, under the named `targets:` entry, created when absent) in place and preserves everything else.
- `--config` is never defaulted to the working directory; `billet check -h` prints the per-user default, and the packaged services use `/etc/billet/billet.yaml` (Linux) or `/usr/local/etc/billet/billet.yaml` (macOS).
