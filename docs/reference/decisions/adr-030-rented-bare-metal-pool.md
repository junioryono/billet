# ADR-030: A pool of rented bare metal

Accepted, 2026-11-05, except where a section says what it still owes. Issue #553.

## Context

A Firecracker node starts a job in seconds and serves every cache, and it needs KVM, so it needs bare metal. Per-job EC2 is the fallback when nothing else has room, and it is slower to start (47.6 to 58.7 s to the first step). An operator who wants capacity past the machines it owns can rent bare metal from two kinds of source:

- **A dedicated-server provider.** phoenixNAP's Bare Metal Cloud is the first one billet speaks to: it orders by API, and bills by the hour or by a reservation of one, twelve, twenty-four or thirty-six months.
- **AWS bare-metal instances**, billed by the second. Four launches on 2026-11-05 reached their first script 21 to 47 s after the call.

What was measured of both, with dates, is in the [bare-metal hosts record](../records/bare-metal-hosts.md). This record decides how billet orders, admits, grows, shrinks and polices such a pool.

## Decision

### Host sources behind one contract

A new package, `internal/hostsource`, holds the contract a source implements, beside `internal/provider` and below the scheduler: a source imports neither `server`, `node`, `nodeplane` nor `cmd`, and writes no ledger, a provider never imports a source, and no ledger writer imports one, so a source is never called inside a transaction; depguard holds all four (`hostsource`, `provider`, `ledgerwriters`). A source may use a provider's client, as the AWS source uses the `ec2` provider's. A source answers:

- **Order** a host of a named shape in a named location, carrying the payload its first boot runs and the pool's order identifier, which the source records on the host (an EC2 `ClientToken` and tag, a phoenixNAP hostname). It answers with the source's identifier for the host, with `ErrNoStock` or `ErrQuota`, which the scaler reports and never waits on, or with `ErrRefused`, a refusal an operator acts on (phoenixNAP's 403 to an API client that may not order, measured). `ErrNotSent` says the order failed before anything reached the source (a local refusal, or a quota or stock read the order needed), so no host can exist for it. Any other error is could-not-tell.
- **Find** the host an order placed, by that identifier, so an order whose answer was lost is read back rather than placed again.
- **Describe** a host: provisioning, running, failed or releasing, as the source reports it. An unread or unknown state is could-not-tell, which is the zero value, never provisioning.
- **Gone**, the answer that frees a host's row, in three values with could-not-tell as the zero. It says gone only on the source's own affirmative terminal answer for that exact host, read after a release (EC2's `terminated`, which `DescribeInstances` keeps showing for a while), never on not-found or on elapsed time: AWS documents that a not-found can coexist with a running instance. A source that has no terminal answer, as phoenixNAP has none measured yet, never says gone, and its host leaves the ledger by an operator's word.
- **Release** a host, only with a proof (below).
- **Terms**: lead time, billing granularity and minimum term, per shape, which decide whether a source covers the floor or bursts, and for how long after its first attempt an order is idempotent, which decides whether a lost answer may be ordered again. A shape that is preemptible is refused.

The AWS source, `internal/hostsource/awsmetal`, launches, describes and terminates through the same EC2 client the `ec2` provider uses, with its retry ladder, its error codes, its `ClientToken` idempotency and its redaction, so there is one EC2 client as there is one signer. Today the source reaches it through a pool-host surface the `ec2` provider exports; moving the client below both, with the one transport-error rule the phoenixNAP source now copies, is owed with the pool. The phoenixNAP source, `internal/hostsource/phoenixnap`, uses the BMC API with a client-credentials token. Each source's credentials are redacting types read from the environment or the identity store, never from argv, and never logged.

### Shape

About 4 GiB of memory per vCPU, so a 2 vCPU job can have 8 GiB, and local NVMe for guest disks and the read caches. On AWS that rules out `c7i.metal-24xl` and `c7g.metal`, which have 2 GiB per vCPU and no instance store. Of the types that fit, `m7gd.metal` (arm64, 64 vCPU) and `z1d.metal` (x86, 48 vCPU, which AWS rates at a sustained 4.0 GHz) were launched; `m6id.metal`, `m8gd.metal-24xl` and `m8id.metal-48xl` fit on paper and are owed a launch. Which x86 type a pool names is owed the in-guest single-thread measurement under full load that #553 asks for: on the host, a `z1d.metal` thread lost 48% of its speed with every other cpu busy, and that run did not separate its causes. On phoenixNAP the `s1`, `s2` and `d` types carry NVMe; the 6-core E-2276G and the 8-core E-2388G (64 GiB each, 12 and 16 threads) both fit the ratio, and the E-2388G is preferred for its threads.

### Storage

A pool must shrink to its floor without losing a cache generation, so a generation's only copy is never on an elastic host.

- **On AWS metal**, Firecracker uses the `ebs-s3` store: the Actions, Go and Bazel caches as the objects [ADR-024](adr-024-caches-off-firecracker.md) keeps in S3, and a sticky disk or image store as a volume the node attaches to its own instance and hands its guest as a block device. The instance's NVMe holds guest disks and read caches only. This changes a site rule: today a Firecracker node needs `node.ceph` (`internal/config/ceph.go`), and the config change that accepts `node.ebs_s3` for a Firecracker node on AWS metal is owed with the probe that proves the path, since no billet node attaches a store volume to itself today.
- **On phoenixNAP**, the site's store is an always-on tier the pool never shrinks: a Ceph cluster on three hosts on a monthly reservation, with the elastic hosts as Ceph clients. Its replication and failure-domain layout are owed a measurement on real servers, and until then a phoenixNAP pool runs with its caches off.
- **Failure domains.** An EBS volume lives in one availability zone, so an AWS pool host is ordered in the zone of the site whose volumes it attaches, and a site spread across zones is a site per zone. A phoenixNAP pool orders in its storage tier's location.

### Orders that survive a lost answer

The scaler's orders are ledger rows, one per order, which become the host's once the source names it. An order's row, with its identifier, is committed before the source is called, and the call carries that identifier as the source's idempotency key or marker. A restarted or uncertain scaler reads the order back with Find before it does anything else. When Find cannot say (a source error) the order is held as could-not-tell and not placed again. Find listing no host lets the scaler order once more, under the same identifier and with the same shape, image and location, only inside the window the source's Terms give for its deduplication, counted from the first attempt the order's row records: EC2 keeps a `ClientToken`'s record for a bounded time, and billet's window for it is ten minutes. Past the window, and on a source with none, phoenixNAP among them, an order whose answer was lost waits for a person, because an order still in flight can land after a list that did not show it, and a deduplication record that has lapsed dedups nothing. It is still read back where it was placed, never sent again, and a host listed there is the order's: the order is placed and its host joins.

### Growing and shrinking

The control plane runs the scaler, because it holds the demand, in a package of its own (`internal/pool`) assembled through `internal/app`.

- **A floor, then bursts.** Each architecture keeps a floor of ready hosts that the operator configures, from sources whose lead time is long and whose term is cheap; bursts come from sources that answer in minutes and bill by the hour or less. A floor sized from measured usage is a recommendation billet can make once the job statistics of #535 exist; it is not computed here.
- **A tier pinned to one node is no pool's demand**: no host the pool orders is that node, so growing for it would order hosts its work can never run on.
- **Growth starts ahead of demand,** from the queue wait the listener records (#525), purchases the allocator refused, and, once #524 lands, predicted runtimes, which the scaler takes through a seam rather than waiting for.
- **Shrink only by drain, and release only on proof.** A timer may propose a drain, near the end of a billed hour for a source that bills by the hour; it never releases a host. The proof is ledger facts, read and sealed in one transaction so no lease can be placed between the check and the release: the host is sealed against placement, and it holds no lease, no quarantine and no custody, and its node's last inventory reported no compute. The seal is one way: the transaction moves the host to `releasing`, which nothing moves back, and a resume or a placement contends for the same row and is refused once a release has sealed it, so a proof never outlives its seal. The node's own drained ending is not on the wire today, so it is not part of the proof; if it is added, it joins it.
- **A host that never joined** (its first boot failed, or its node never enrolled) has no drain to prove. It is released on a different proof: its order is sealed against enrollment and its join token revoked in one transaction, and the ledger records that no enrollment was ever admitted for it, so it never held anything a job could have used.
- **A host that dies holding work** stays charged and in quarantine, with its leases and custody, until the existing force paths (`billet leases release --force`, `billet force-destroy`) settle it on an operator's word, never on a timer.
- **No spot or preemptible capacity for pool hosts.** A spot host can be taken with two minutes' warning, which ends every job running on it, and GitHub does not requeue a job whose runner vanished, so each would need a rerun by hand. Per-job EC2 may still use spot, where an interruption costs one job's rerun rather than a host's worth.
- **Each source's limits are inputs, not surprises**: AWS's running-instance vCPU quota through `awsquota`, phoenixNAP's server quota and stock through its own API (one server on a new account, measured), each read before an order.

### Joining without a person

Enrollment today is a key fingerprint a person compares. A pool host is admitted without one only when the plane can read that fingerprint from the host through a channel the source authenticates for that exact host; a token and an address are not enough, because both can be copied or reassigned.

- **On AWS**, the host generates its node key on first boot and writes the key's fingerprint to its serial console, as one line (`billet-pool-join order=<order> fingerprint=<fingerprint>`, `joinconsole.Line`) before every attempt to enroll, because the plane reads the newest 64 KiB of the console; only a whole line is read, one that is that line and nothing else from the newline before it to the newline after it (never the edge of the bytes read, which can begin or end part way through a line), so a line the console cut short says nothing, and neither does the same text quoted inside other boot output (an error, a status a network answer wrote), which reaches the same console. The host writes its line on a line of its own, and everything its join prints, and the answer it ends with, is written with the line's start spelled without its hyphens and every carriage return as `\r`; nothing the authority's unverified answer wrote is quoted at all. The plane reads the console of the exact instance the order launched (`GetConsoleOutput` with `Latest`), which only that instance can write and only the account can read, and admits an enrollment only when its key's fingerprint is the only one there for the order, the instance identity document the host sends (read over IMDSv2 before every attempt until one is read) verifies under AWS's certificate for the region and names that instance, account, launch (`pendingTime` is the instance's `LaunchTime`) and private address, the instance is running, and the enrollment's source address is that instance's private address. Behind a router the listener does not see the host's address, and the document, which no one but that instance can read, stands for it. The host's launch keeps the `ec2` provider's metadata settings (IMDSv2 required, hop limit 1), and the host's NAT drops guest traffic to the metadata addresses, so no guest can read the host's token, identity document or role.
- **Measured on 2026-11-06** on a t3.micro in us-west-2 (the bare-metal hosts record): the document's base64 `signature` verifies as RSA-SHA256 under the region's RSA certificate and under no other pairing; `pendingTime` was the instance's `LaunchTime` and `privateIp` its private address; a line written to `/dev/console` every 15 s was in `GetConsoleOutput --latest` by the next read, at most 48 s after it was written, the first 70 s after launch. AWS publishes a different RSA certificate for each of 39 regions, and us-west-2's lapses in 2029, so a document none of billet's certificates verifies proves nothing either way.
- **On phoenixNAP**, no source-authenticated channel from the host is known, so a pool host there waits for a person's fingerprint comparison, as a node does today, with its order shown beside it in `billet nodes pending`. Automated admission there is owed a channel.
- **Three answers.** A source vouches only when every check is positive for this key, contradicts only on a positive answer about the host itself (other keys on the console and not this one, a verified document naming another instance, account or address, an instance that is ending), and otherwise cannot tell: a failed read, a console that has not shown the line yet or names two keys, a document it cannot verify, and an address or a launch time that does not match, which a NAT or a proxy in front of the listener, or a launch EC2 recorded differently, would explain without anything being wrong with the host. A reason never quotes an AWS answer, whose prose can name the caller's account and role; a failure is said by its code.
- **The ledger is asked before the source.** An unauthenticated caller reaches no AWS call without a live token of an open order, or the request it already recorded under its spent token: a pool token under another name and a closed order are refused first, an order being ordered, or uncertain, is told to ask again; a lapsed token of an open order holds the order there and then when nothing can join from it any more (no live token, no request waiting), as the pool's step would, so it waits on no pool loop, and its request is then recorded for a person, and otherwise asks again, recording and spending nothing; and a held order is answered pending without asking anything. A key that joined from the order while its request was on its way is answered what it was given. Each order's source is asked at most once every 15 s, whatever key a caller presents, because a host asks every five, the console read is throttled and a caller chooses its key; a request the budget defers is told to ask again, never treated as could-not-tell, so nothing is recorded or spent on a request another ask may be about to contradict. Each ask is bounded to 5 s inside the enrollment listener's 10 s write timeout, and a hold applies only to the order as it stood when it was judged, so a person's release is never undone by a verdict reached before it.
- **The admission is one transaction**: it checks the order is placed, held for no one and joined by no node, spends a live token minted for that order (every send of an order mints one, and a resend under EC2's `ClientToken` returns the host that booted with the first send's, so any of the order's tokens admits it), records the request approved with its certificate, records the certificate's serial for revocation, links the order to its node with the key and serial, and retires the order's other tokens. The node's name is the order's (`alloc.PoolNodeName`), never the request's, and a pool order's token under any other name is refused and not spent; an operator's token under a `pool-` name is refused too, so it cannot claim a host's name before the host asks. The link compares the hold it read, so a hold committed in between links nothing. Sealing or releasing an order moves it out of `placed`, so an admission and a release cannot both succeed. A retried enrollment with the same key finds itself admitted and is handed the first certificate.
- **A contradiction holds the order and spends nothing.** The hold is a column of the order (`join_hold`, migration 76), not a state, because migration 75's states are frozen; it keeps its first reason, is only set on an order a node may still join from, and a held order admits nothing on its source's word or a new request until a person acts. A conflict (the source vouches for a key, and another key already holds the name) holds the order in the transaction that found it. A held order, a contradiction and a conflict are all answered pending, so the host keeps asking while a person looks, and the answer quotes nothing the source said. A held order's request is recorded pending under its order without spending any token (the name still the first key's), so a person always has the key the host presents to compare and approve, even once every token of the order has lapsed. A person acts in one of three ways: approves a request already recorded under the order (`billet nodes approve`), which links the order to its node in the same transaction, as the admission does, and clears the hold; releases the hold (`billet pool unhold`), so the host's next ask is judged again; or releases the host. A held order no longer counts as on its way, so it does not stop growth for demand, and it still counts against the maximum.
- **What the source cannot tell is recorded pending under its order**, spending the token, so a person can approve it and the host's next ask is judged again. An order whose tokens all lapsed with nothing joined and no request waiting is held by the pool's next step, so a host that can never join is not counted on its way forever.
- **Release revokes first.** The certificate recorded on the order is revoked before the source is asked to take the host back: the node's certificates, by serial and by a cutoff for any billet cannot name, are revoked in the transaction that seals the order.
- **Built (2026-11-07): release on a person's word.** `billet pool release` asks for it.
  - **A joined host's** node is taken out of placement at once, and its registration keeps it out while the release stands, or after it is sealed: a registration in flight when the seal commits cannot put back a host the source is about to take.
  - **The seal** is written in the transaction that reads its proof. The host holds no lease, quarantine or custody, and either its node never registered, so it was never placeable, or it was decommissioned on the compute barrier's proof and no inventory of its current registration since reports compute.
  - **An inventory is never the proof.** It is stamped when it arrives, not when the node listed it; a launch still running is in none; and the barrier writes inventories of its own, out of order with the node's sweeps. A proof built from inventories was tried in review and withdrawn (2026-11-07): every fence on its timing left an order in which a host still running a launch read as empty.
  - **What a host draining alone needs** is an acknowledgement the node gives only after its launches settle, fenced by its epoch and its dispatch generation: the compute barrier's per-node ask, without the deployment's seal, with the host's own exclusion from placement in the seal's place. A node's own drained ending, sent as it withdraws, would be a second such proof. Until one exists, a joined host is released after a deployment-wide `billet drain --wait` and `billet nodes decommission`.
  - **An unjoined host** is sealed in the asking's own transaction, on the ledger's word that nothing was ever admitted for the order (no approved request under its name, no certificate ever issued for it), with its tokens retired.
  - **The proof** (`internal/releaseproof`, a leaf, because the ledger may not import a source) is built in the sealing transaction. A seal stands for it after that transaction, so a release asked again after a failure or a restart is the same release.
  - **Counting.** A sealed or released host counts against the maximum until it is gone, and towards neither the floor nor demand.
  - **Gone, or closed by a person.** An order is gone on its source's own terminal answer, asked only where it was placed. A source that never gives one (phoenixNAP), or that is no longer configured or now orders elsewhere, leaves a released order for a person to close with `billet pool close`, which also closes a sealed host a person took back by hand. Its reason says a person closed it.
  - **A pool's names are its orders'.** `billet ca issue` refuses a `pool-` name. A registration under the name a sealed order would have given its node is held out of placement, whether or not a node ever linked.
  - **A refused approval records nothing.** A person's approval records the certificate it issues in the approval's own transaction, so an approval the ledger refuses (a mistyped fingerprint) leaves no certificate that would read as a node admitted.
  - **Still owed:** the per-node clearance above, and automatic shrink, which needs a measure of how long a host has been idle so a host ordered for demand is not released the step after.

The rules of `billet-identity-and-ca` and `billet-security` apply in full: the token is a request to enroll, never an identity, and the certificate a node then holds is what proves it afterwards.

### What a returned host keeps

A phoenixNAP server goes to its next tenant with its disks. The node's key, its guest disks and its read caches live on a volume encrypted with a key the host generates at boot and never writes down, so a released host's disks hold nothing readable once its power goes. billet relies on no source's wiping, so an AWS pool host uses the same encryption, and the two sources keep one layout.

### A host its provider polices

A hosting provider locks a server that scans, mines or sends packets at a high rate, and one job could cost a whole host that way. On a pool host every guest's traffic is NATed through the host with per-tap limits on packet rate, new connections per second and egress bandwidth, outbound SMTP is refused, and the metadata addresses are dropped. These are nftables rules the host role and the Firecracker provider install, one rule set with the per-tier egress policy of #727 rather than a second; their defaults are owed a measurement against a real build's traffic before they ship, so they never throttle a job billet exists to run.

## Consequences

- An operator can rent capacity from two kinds of source behind one contract, and a third source is a package that implements it.
- A pool on phoenixNAP needs a monthly storage tier before its caches turn on, a person at each enrollment until a source-authenticated channel exists, and a raised server quota before it can grow past one host.
- A Firecracker node on AWS metal needs the site rule that requires Ceph relaxed for `ebs-s3`, and a store volume attached to a metal instance and handed to a guest proved, before its caches turn on.
- The metal source shares the `ec2` provider's EC2 client rather than growing its own.
- The ledger grows one table, `pool_orders` (migration 75): an order is its host once the source names one, and its node once one joins from it, so one row carries the whole life, with every move one way. Migration 76 adds what the join needs: the order a join token and an enrollment came in under, and on the order the key admitted from it, its certificate's serial and its hold; it binds a token and a request migration 75's pool left to their order by the note and the name that pool gave them.
- billet carries AWS's RSA certificate for each region's identity documents (`internal/awsidentity/certificates.pem`, read 2026-11-06), and a region's rotation is a refresh of that file.

## What was rejected

- **Spot or preemptible pool hosts,** for the reason above.
- **Ceph across the elastic hosts' own NVMe.** Shrinking to the floor would have to move every placement group off a host before releasing it, which turns a drain of minutes into one of hours and makes a host the source reclaims a data-loss event.
- **A timer that removes idle hosts, or that turns not-found into gone.** Release is on proof, and gone is the source's affirmative answer.
- **Admitting on a token, an identity document or an address.** Each can be copied or reassigned, and none names the key that enrolls.
