# ADR-018: The Git proxy answers as GitHub does

Accepted, 2026-10-21. Supersedes ADR-013's rule that the Git proxy serves only objects a ref reaches.

## Context

The node's Git proxy (`internal/node/gitproxy.go`) serves a guest's `git fetch` of a github.com repository from a bare mirror on the node, after GitHub has authorised the job's own header for that repository. Until this decision it served only objects a current ref of the mirror reaches, under protocol v0, so that an object a deleted branch once reached would never leave the mirror. It refreshed the mirror on the request path, under a per-repository lock that a request waited on without a bound, and every request to GitHub went through one shared HTTP/2 connection.

On 2026-10-21 that design failed a production fleet's CI in two ways.

- **`upload-pack: not our ref`.** actions/checkout fetches a pull request's merge commit by its name. When the pull request moved or was merged before the job ran, GitHub's merge ref no longer named that commit; the mirror still held it, no ref of the mirror reached it, and the mirror's upload-pack refused it. GitHub serves the same fetch. Dozens of jobs failed this way over five days.
- **Checkouts that hung.** One full-history checkout's lazy fetch of about 6,800 files ran for exactly ten minutes, the proxy's fixed transfer limit, and ended with `curl 18 transfer closed with outstanding read data remaining`. Two others ended with `HTTP 408` from GitHub after 85 and 130 seconds. Meanwhile every other checkout of the repository took 48 to 59 seconds instead of 8, and all of them recovered the second the ten-minute transfer was cut.

## What was measured

GitHub's git server, 2026-10-21, git 2.51.0 and hand-built smart-HTTP requests:

- **GitHub serves, by name, under v0 and v2, a commit no ref reaches.** Superseded `refs/pull/N/merge` commits 50 minutes, 2 days, 19 days and 77 days old were all served, and so was a commit that exists only in a fork, fetched through the parent repository's URL. A commit from another fork network was refused. `allow-reachable-sha1-in-want` is what GitHub advertises; `allow-any-sha1-in-want` is what it does.
- **A refusal is `200 OK` and one `ERR upload-pack: not our ref <name>` line, before anything else.**
- **GitHub's `408` is an idle limit on request bodies, not a total one.** A body trickled at one byte a second for 158 seconds was answered; a gap of 10.5 seconds or more between body bytes was answered `408` at about 10.2 seconds. A 14.5 MB body with 290,355 wants was answered.
- **`refs/pull/N/merge` moves only when the pull request's head is pushed,** within seconds of the push; it is not recomputed when the base branch moves. On the affected repository two of forty fifteen-second samples saw any ref change.
- **GitHub sends nothing before its response headers,** then side-band keepalives every five seconds while it counts a pack.
- **GitHub advertises no `packfile-uris`, `bundle-uri`, `object-info` or `ref-in-want`** under v2, and answers a request for one with an empty `200`.

git itself (v2.56.0's source, with experiments on a mirror holding a deleted branch's objects):

- Under v2, upload-pack serves any object present, whatever `uploadpack.allow*SHA1InWant`, `hideRefs` or a namespace say. Under v0 over HTTP it checks reachability for commits only, so a tree or a blob no ref reaches passes.
- In both protocols a `have` line for any present object is acknowledged, and haves seed delta bases: the protocol cannot keep an object a repository holds from a client that names it. git's own documentation says the only protection is not to hold it.
- Sixteen concurrent full fetches cost 34 s of CPU from 43 unconsolidated packs and 3.4 s from one pack with a bitmap.

## Decision

**A job GitHub has just authorised for a repository may be served any object that repository's mirror holds.** A mirror holds only what billet fetched from that repository on github.com, one mirror per trust class and repository, so it holds nothing GitHub would not give the same header: GitHub serves an object no ref reaches by its name, and a `have` can already find out whatever a repository holds. The rule billet had was stricter than GitHub, and the strictness was what failed jobs. Authorisation is unchanged: GitHub's own answer to the job's header, asked for every advertisement, standing for a minute, ended by a later refusal.

**A mirror is one repository's, by the id GitHub gives it, not by its name.** A name passes to another repository once its owner renames or deletes the first, and the first repository's objects, unreachable ones included, are not the second's to give. So each advertisement asks GitHub's REST API, with the job's own header, which repository the name is (`GET /repos/{owner}/{repo}`; the header actions/checkout writes for git is accepted there, measured 2026-10-21, and a header that cannot read the repository is answered 404), with every advertisement, never carried from an earlier grant, because a name answers 200 to every advertisement whichever repository it is. A mirror is stamped with that id when it is made; one stamped with another id, or with none billet can read, is renamed aside before anything of it is served and deleted in the background, and a fetch is served only from a mirror stamped with the id its grant names. A name the API will not tie to an id is GitHub's to answer, and no mirror is made for it. GitHub serves git by name only (`https://github.com/repositories/<id>` is not found over git, 2026-10-21), so a fetch cannot be bound to the id itself. Instead a mirror is marked unverified, on disk and synced before each fetch begins, and the mark is removed only when GitHub names the same repository after the fetch; a fetch that failed, a name that changed hands, or an API that could not say leaves the mark, and a marked mirror is never served, never fetched into, and replaced at the next advertisement, after a restart as before one. A serve that fails after its answer began, by a failing exit or a crash on a signal (only the kill a request's own end sends is excused), marks the mirror broken, a mark no refresh clears; a mark the disk refuses holds the mirror out of service in the process and takes away its repository stamp, which needs no space. A disk that refuses even that is left to the in-process hold: a record written before every serve would cost a sync on every fetch to cover a disk on which no cache works, and after a restart the next failure is caught again. The last checks before an answer commits, and after an advertisement is read, read the mirror's stamp and marks again, because a refresh shares a serving request's hold on the mirror.

What is left is a name that passes from one repository to another and back within the seconds one fetch takes: GitHub names the first repository before and after, and the second one's objects stay in the first one's mirror. Only a fetch bound to the id would close it, and GitHub offers none. It is accepted, because arranging it needs someone who can rename and create the organisation's repositories, with a credential that reads both, and that person can already give the first repository's readers the second; and no accident hands a name away and back inside one fetch. Replaced mirrors are renamed into a `.discarded` directory at the mirrors' root, a name no repository can have, and deleted in the background.

**Nothing that goes wrong in the mirror fails a fetch GitHub would answer.** A want or a shallow boundary the mirror lacks, a negotiation the proxy cannot read, a mirror whose upload-pack refuses or says nothing: each sends the request, whole, to GitHub. The first line of the mirror's answer is read before any byte reaches the client, so a refusal there, or a first line that does not come within a minute, still goes to GitHub, on the request's own context, which the abandoned attempt never ends. A serve that fails after its answer began cannot be taken back: that one fetch fails, the mirror is marked unverified, and the next advertisement replaces it, so every job after it is answered. GitHub's grant is checked again just before the mirror answers, after the request body was read, so a refusal GitHub gave meanwhile stands.

**A refresh belongs to no request.** One refresh runs at a time per mirror, on the proxy's own context, with the header of the job that started it. An advertisement waits for it at most ten seconds and then sends GitHub's own advertisement; the fetch after that is still served from the mirror when the mirror holds what it names. A refresh that began before GitHub answered a request is joined and the refs compared again, so a job is never told a mirror's refs that are older than GitHub's answer to it. A lock file or a temporary pack found when a refresh starts was left by one that was killed, and is removed. Git's own automatic gc and maintenance are off, so no detached process outlives the refresh with the job's header in its environment.

**A refresh fetches only what moved.** The advertisement GitHub gave the job that started the refresh says which refs moved, appeared or went since the mirror was last fetched, so the refresh fetches those by name and removes the ones GitHub dropped, each only while it still names the object the refresh saw. Git offers GitHub, as what the mirror has, the old value of every moved ref and the default branch's tip: a new branch has no old value, and a rebased one shares nothing with its old value past where it left the default branch, so without the default branch the fetch would bring the whole history again. An advertisement asked for before the mirror's last refresh finished (the proxy numbers its questions to GitHub) is fetched whole, to GitHub's refs as they are now, because that refresh may have brought refs GitHub made after the advertisement was answered, and read narrowly each would look dropped. A new mirror, a ref name billet will not put on git's command line, more than 256 refs to change, or a narrow fetch that fails (a ref GitHub dropped after it advertised it refuses a fetch that names it) fetches every ref, pruning, as every refresh did before. Measured on the shared test host on 2026-10-22 with git 2.43 over `file://`, so without the network: moving one ref of a repository with 5,000 pull-request refs took 0.057 s narrow against 0.104 s whole, and with 50,000 refs 0.44 s against 1.05 s; over a network the whole fetch also downloads the ref listing on every refresh, 3.1 MB for 50,000 refs against 58 bytes for the one that moved.

**A mirror is kept in few packs, off the request path.** A fetch keeps what it brought as the pack it came in (`fetch.unpackLimit=1`), never loose objects. After a refresh that worked, while its slot is still held so no fetch runs beside it but with the waiting jobs released, the mirror is maintained when that is due: once a day it is rewritten as one pack with a bitmap and a commit-graph, with what no ref reaches set aside in a cruft pack and nothing removed (`repack --cruft --cruft-expiration=never -d -b`); once a week it is pruned; and otherwise, once it holds eight packs, a geometric roll-up merges the small ones and leaves the large pack and its bitmap as they are. One pass runs on a node at a time, and one that finds another running is left to a later refresh; it needs room on the disk for a second copy of the mirror. A job whose refs moved while its mirror is maintained waits for the pass as it waits for a refresh, within the same ten seconds, and is GitHub's to answer after that; its fetch is still served from the mirror when the mirror holds what it names. Measured on the shared test host on 2026-10-22 with git 2.43, on a bare clone of golang/go (476 MB, 718,000 objects): the daily repack took 17.4 s and 800 MB at its peak, the same with two threads as with sixteen because it reuses the deltas it finds; a geometric roll-up of 21 packs to 2 took 0.35 s and 47 MB, against 2.9 s and 717 MB with a multi-pack-index bitmap, which served a full clone no faster (1.5 s either way, against 8.2 s from the clone as fetched, without a bitmap). Repacking deletes packs under the upload-packs reading them, which git survives: 103 full fetches beside 90 repacks, full and geometric, none failed. So a pass that removes no object takes no exclusive hold on the mirror, only the shared one a refresh takes, which keeps a claim from renaming it aside mid-pass.

**Pruning has the mirror alone.** An upload-pack that found an object before a prune removed it, and reads it after, has already begun its answer, which then fails and marks the mirror broken. So the weekly prune (`repack --cruft --cruft-expiration=<fourteen days ago> -d -b`) waits up to five seconds for the fetches being served to finish and runs with the mirror to itself; from the moment it asks, new requests go to GitHub rather than queueing behind it, and a prune that does not get the mirror is counted busy and left to a later refresh.

**An object no ref reaches may be pruned fourteen days after the first pass that set it aside, not before.** A daily repack or a prune writes what no ref reaches into a cruft pack, which records each object's age; git gives an object leaving an ordinary pack that pack's mtime, a loose object its file's, and keeps the age a cruft pack recorded for one already in it (measured with git 2.43 on 2026-10-22: an object in a 30-day-old pack that had just become unreachable was pruned at once by a 14-day expiry). So before every such pass the mirror's ordinary packs and loose objects, a loose one an older fetch left included, are dated now, and an object is dated by the pass that first finds it unreachable, whatever gap came before; the next weekly prune once that date is fourteen days old removes it, and a mirror whose stamps cannot be read prunes nothing. That is when an object may go, not when it must: maintenance runs only after a refresh, and a mirror is refreshed only when GitHub's refs have moved, so a mirror in use whose refs never change is never pruned, and a prune that fetches being served keep from the mirror waits for a later refresh. A geometric roll-up leaves the cruft pack as it is, and an object in it is still served by id. A fetch of a pruned object goes to GitHub, which goes on serving it as long as it keeps it.

**The proxy reaches GitHub over its own HTTP/1.1 connections.** Over the shared HTTP/2 connection every advertisement and every forwarded fetch on a node shared one connection's flow control, so one large download held back the rest, and a request body that stopped arriving for ten seconds was ended by GitHub with `408`. That is an inference from the symptoms; HTTP/1.1 removes the mechanism whether or not it was the cause. Every request body is read whole before GitHub sees a byte of it, so a guest that sends slowly never meets GitHub's idle limit: in memory up to 64 MiB, on disk up to 512 MiB, and a larger one is refused rather than streamed.

**A git request ends when no byte has moved for three minutes,** and at two hours whatever happens. The fixed ten-minute limit of the other caches cut transfers that were still alive. The end moves the connection's own deadlines, not only the request's context, because a read of a stalled guest's body or a write to it is not woken by a context. The advertisement's whole wait, its lock waits, reading the mirror's refs and the refresh, is one ten-second deadline.

**Every git request ends with one line in the node's log:** where it was answered, why it was not answered from the mirror, its status, its bytes and how long it took. Every refresh logs its outcome and duration.

## What is not decided here

- **Dropping a mirror at once.** An object GitHub has since removed (a sensitive-data removal through GitHub Support) stays in a mirror until a prune that runs at least fourteen days after the first pass that found it unreachable, which needs the mirror's refs to move, or until the mirror is reaped. `billet cache git forget`, to drop a mirror at once, is the next change.
- **Protocol v2 to the guest.** The mirror still speaks v0 to guests; v2 would let the proxy forward GitHub's ref listing unchanged and serve only fetches.

## Rejected

- **Keep the reachability rule and send what it refuses to GitHub.** It is correct, but every full-history checkout's lazy fetch and every superseded merge commit would go to GitHub, and the rule protects nothing GitHub does not already hand out.
- **A checkout action that borrows objects from a mirror disk through alternates,** as several hosted runner services do. It keeps GitHub in every fetch and cannot refuse anything GitHub would serve, but it needs every workflow changed and a disk attached to every guest; billet's proxy needs neither.
- **Waiting for the refresh, however long.** It is what made one slow fetch every job's ten minutes.
