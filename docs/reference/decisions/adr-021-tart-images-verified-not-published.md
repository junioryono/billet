# ADR-021: A Tart tier boots an image billet verified, never one billet published

Accepted, 2026-10-25. Issue #24.

## Context

A Firecracker tier boots an image billet builds, gates, signs and publishes, and `@verified` resolves to the newest generation a node proved to boot (`billet-guest-images`). A Tart tier boots whatever reference it names. The documented tiers name third-party images, a macOS image with Xcode and an arm64 Ubuntu image with the runner and Docker ([Run jobs on a Mac](../../deploying/mac-tart.md)).

For a remote reference, billet does three things:
- `billet images pull` runs `tart pull`.
- The daily refresh pulls an image only when it is absent and never pulls a tag again that has moved (`internal/ops/images/imagesrefresh.go`).
- A launch pins the tag to the digest it resolves to in the local store (`tart fqn`) before it clones.

Nothing boots the image before a job does. Nothing checks that its runner is inside GitHub's thirty days. Nothing records which image a deployment decided to trust.

Three properties of tart 2.37.0, read from its source on 2026-10-25, decide how such a record can be kept:
- **A clone may fetch.** `tart clone` of a remote reference pulls it when its cache entry is missing. `Registry` does not compare the manifest it receives with a digest it asked for. So a clone of `<repository>@sha256:<d>` is not, by itself, a guarantee of those bytes.
- **Moving a tag can delete.** Re-pointing a tag runs the OCI cache's garbage collection. That removes a digest no tag names any more, unless it was pulled by digest.
- **One store per user.** The OCI cache and the VMs live in one store per user (`TART_HOME`), which every deployment running as that user on the Mac shares. When an operation needs room, tart prunes the OCI and IPSW caches by itself, unless `TART_NO_AUTO_PRUNE` is set. It never prunes a local VM by itself.

Billet could publish Tart images of its own, as it does for Firecracker, or verify the images a deployment already uses. The two questions behind that choice are what billet may redistribute and what it costs to build.

**macOS.** The macOS Tahoe 26 software license agreement (read from Apple's published PDF on 2026-10-25) allows, in section 2B(iii), "up to two (2) additional copies or instances of the Apple Software ... within virtual operating system environments on each Apple-branded computer you own or control that is already running the Apple Software", for software development, testing during software development, macOS Server or personal use. Among its restrictions on use it says: "Except as expressly permitted in Section 3, you may not rent, lease, lend, sell, redistribute or sublicense the Apple Software." The Xcode and Apple SDKs Agreement (read the same day) says use of the Apple Software "is authorized only for execution on an Apple-branded product running macOS". It also says the licensee agrees "not to rent, lease, lend, upload to or host on any website or server, sell, redistribute, or sublicense the Apple Software and Apple Services, in whole or in part, or to enable others to do so". A macOS image with Xcode, published as a release asset of this repository, would be billet redistributing both. The reasoning #584 applied to the Android SDK ([ADR-005](adr-005-runner-image-parity.md)) applies here: what an operator may run on their own Mac, billet may not hand them.

**Linux.** Nothing in the licences stops billet publishing an arm64 Linux image, and ADR-022 publishes one for Firecracker. A Tart image is a different artifact, though.
- Tart's Linux VMs boot through EFI. Virtualization.framework also has a direct kernel boot loader, but tart does not use it. So a Tart image needs a partitioned disk, a bootloader, and a kernel with the virtio drivers Virtualization.framework presents. billet's Firecracker guest is a bare ext4 filesystem with a microVM kernel beside it.
- A Tart guest takes its registration over `tart exec`, which needs tart's guest agent in the image.
- A Tart image is published by pushing to an OCI registry in tart's own layout, which `tart push` does only on macOS.

That makes it a second image pipeline, with a Mac in its publish path, for one tier shape that runs only on Apple hardware.

## Decision

**billet publishes no macOS image and no Tart Linux image.** A Tart tier names a third party's registry reference, or a VM the operator built on the Mac itself.
- Whether a third party may distribute an image is between that party and the software's licensors.
- Whether the operator may run it, or host an image of their own on a registry, is their own position under the macOS licence and, for Xcode, the Xcode agreement, whose restriction on hosting is not limited to public servers.
- billet hosts, mirrors and bundles none of it. Its documentation names example images without vouching for their licensing.

**A Tart tier may name `<image>@verified`, and then boots only a copy of what billet booted.**
- **Spelling.** `<image>` is a remote reference or a local VM name. The spelling is the one a Firecracker tier already uses. Validation refuses `@verified` combined with an `@sha256:` digest. A remote reference is normalised the way tart resolves it (registry, repository, and the default tag `latest`) before it is used as a key.
- **Pulling in a store of its own.** A remote reference is pulled in a private tart store, never in the shared one. tart re-points the cache entry it was asked for at whatever manifest the registry returns, without comparing them, and garbage-collects as it does. A pull in the shared store could therefore replace a digest another deployment pins, or evict an entry another deployment's unverified tier uses. So, for a remote reference, `billet images verify` and the refresh:
  - ask the registry for the tag's current digest (the OCI distribution API, anonymously where the registry allows it);
  - pull `<repository>@sha256:<d>` with `TART_HOME` set to a fresh directory under `node.state_dir`;
  - refuse unless the `manifest.json` tart stored for that entry hashes to `<d>` (`tart fqn` alone answers the name it was asked for, whatever the registry served). tart 2.37.0 does not check the disk chunks, configuration or NVRAM it downloads against that manifest, so the digest records what was asked for and the base's own content hash, below, records what was booted. Two Macs that recorded one digest for different bytes are told apart by it;
  - clone it there into the base.

  Nothing in the shared store moves or is evicted, whatever the registry serves. The private store must be on the same filesystem as the shared one, which the verification checks and refuses otherwise, so that the base can be moved in by a rename. Once the base has moved, the private store is deleted, cache and all. So no digest a verification pulled is kept anywhere but in its base.
- **The verified copy is a base VM.** The verification makes the base, a local VM billet owns, from the pulled digest in the private store or from the operator's local VM in the shared one: `billetbase-<deployment>-<image>-<n>`, where `<image>` is a short hash of the image key and `<n>` is the verification's generation number, unique per verification. The remote digest, when there is one, is kept in the record rather than in the name, so verifying the same digest again, or a local VM that changed, makes a new base and never renames over a recorded one. The name is outside the `billet-` prefix that `provider.LeaseOf` reads as a lease, so no node's `List`, orphan sweep or inventory treats it as compute, and the deployment in the name keeps two deployments' bases apart. It enters the shared store in the launch path's ownership order: a staging name, the deployment's marker (of a kind `List` never inventories), the store lock and the rename. A base made in the private store reaches the staging name in the shared store by renaming its VM directory, which on one filesystem moves no bytes. That is sound only for a standalone VM. tart can also clone an image published with a stacked disk into a VM whose directory holds only a writable overlay, while the layers beneath stay in the private store's content store. So a base must hold its own `disk.img` and be neither a stacked VM nor a stacked cached image, and a stacked image is refused. A base also carries no saved suspension state: billet removes a `state.vzvmsave` copied from a suspended local VM before the base is hashed or probed, because `tart run` would otherwise resume it, and the probe would prove a resume rather than the cold boot every job whose clone loses that state makes. Whether the images a deployment names are stacked is measured before this is relied on. Each rename holds tart's own lock on the shared `TART_HOME` directory, the lock tart's clone takes around moving a VM into its store. Under it billet only renames and runs no tart command, since some, `clone` among them, take that lock again and would wait on billet forever. billet's store lock is always taken before tart's. `tart get` must read the base under its staging name, with tart's lock released, before the second rename gives it its own name. tart's automatic pruning reclaims only the OCI and IPSW caches, never a local VM, so the bytes stay on the Mac whatever happens to any cache or tag. Every tart command billet runs in the shared store for `@verified` runs with `TART_NO_AUTO_PRUNE` set: the clone of an operator's local VM into a base, a probe's clone, and every launch's clone of a base. tart reclaims cache space after any clone, so without it these could evict an image another deployment uses. A base removed by hand (`tart delete`, or `tart prune --entries vms`) is gone, and the launch refuses as below.
- **One verification of an image at a time.** A verification holds a lock for that image, in this deployment, for its whole life. Under it, before anything else, it removes what an earlier verification of this deployment left behind: a probe, a base staging clone, and a finished base of this image that no record names (a verification that failed, yielded or died after the base was made). Each base is removed under its own lock.
- **What is probed is the base.** The probe is a clone of the base VM, named `billetprobe-<deployment>-<hash>` for the same reason as the base, and held in custody: the verification takes an exclusive lock on a file of that probe's own and passes it to the probe's `tart run`, as a macOS slot is passed, so the lock stays held exactly as long as that process or its children live. A probe's name is deleted or reused only after its custody lock can be taken, which proves its process has ended, Linux or macOS. Its processes are found as that file's holders. The probe is booted with the network flags of the trust class it is verified for. Through `tart exec` it asks the guest what a job depends on:
  - on both operating systems, the runner answers `--version`;
  - on Linux, Docker with Buildx and Compose answer;
  - on macOS, `xcodebuild -version` answers.

  The probe is destroyed and proved stopped before anything is recorded. Because every launch clones the same base, what a job boots is a copy of what was probed, whatever tart's registry client did or did not check.
- **Records.** A record holds the image key, the base VM, the digest it was pulled as (remote references only), a content hash of the base itself (the sha256 of its disk, configuration and NVRAM, computed when the base is made), the runner version, the time, and the runner's deadline. It lives in a file under `node.state_dir`, written through `durablefile`.
- **How long bases are kept.** The two newest bases of each image are kept, counted by distinct content, so verifying the same bytes again replaces their base rather than pushing the previous image out. Distinct content is judged by the disk and NVRAM and by the configuration with the fields a clone regenerates, the MAC address among them, left out. The record keeps the exact hash for the audit, but a clone of an unchanged VM never counts as new content. That keeps a rollback target. Older ones are deleted when a newer one is recorded, and an unpromote deletes its base. Bases are the whole of what billet keeps for `@verified`, so what it holds on the Mac is two bases per image. A private store a crash left behind is deleted by the next verification of that image, under its verification lock.
- **A base cannot change unnoticed.** A base is an ordinary local VM to tart, and `tart set --disk` or a run of it would change it under billet's record. So the record also holds each base file's identity as the kernel reports it (device, inode, size and change time, the last of which no user can set), taken before the base is hashed and compared again after, so the hash is of the files the identities name. Every clone of a base compares those with the files before the clone and again after it completes, and on any difference discards the clone before it boots and marks the base invalid. Hashing tens of gigabytes on every launch is what this avoids. A base is never run.
- **Launch.** `@verified` resolves to the newest record of that image, and the launch clones its base VM: a local clone, with no network and no fallback. A launch refuses, naming the command that would fix it, when the base is gone or the runner's deadline has passed.
- **A macOS guest holds a slot for exactly as long as its process lives, and a probe yields its slot to a job.** Apple's grant allows two macOS guests per Mac. The control plane counts macOS guests per node only through the leases it places (`macos_vm_limit`), and a probe holds no lease. Nor does the moment billet asks tell whether a guest is about to start: `tart run` is a detached process that outlives billet, and it can wait on tart's own lock before the VM reports running.
  - **Slots, held by the guest's own process.** The store holds one slot file for each macOS guest the node may run, `$TART_HOME/.billet/macos-slot-<n>`: the node's macOS limit (`nodes[].macos_vm_limit`, two unless an operator's licence raises it), as the control plane places against it. `nodes:` is the control plane's policy, which a node's own file need not carry, so the limit reaches the node the way `images.accept` does: in every accepted registration's answer, from the wire version that carries it, written durably under `node.state_dir`. A command that runs beside the node, such as a verification, reads that record. With no record, which is an older control plane or a node that has not registered, a probe refuses, and a launch, which the control plane only sends a registered node, uses Apple's default of two and `billet check` says so. Every billet macOS launch and every macOS probe takes an exclusive lock on a free one, writes its own identity (the VM's name and the time) into the file, and passes that descriptor to the `tart run` process it starts, which inherits it. billet then closes its own copy, as it already does for the run log, so only the guest's process holds the slot. A reader trusts the identity in a slot file only while the slot is locked. The first deployment to create the slots records their number in the store beside them. A deployment whose limit differs refuses to start a macOS guest, and `billet check` says why, so two deployments sharing a store cannot together run more guests than the smaller limit allows. Every macOS launch and probe holds the store's slot lock while it reads the recorded count, checks it against its own limit, counts the guests and takes its slot, so admission sees one count from start to finish. The record is rewritten under the same lock, only while no slot is held and every deployment present on the store names the same limit, which is how an operator raises or lowers it. The slot files keep their names across a change. The kernel keeps the slot held for as long as that process, or anything it spawned, lives, through billet's own death or restart, and releases it when the guest's process ends. So a guest that is still starting holds its slot without billet, and no elapsed time ever releases one. That the descriptor survives `tart run` for the VM's life, and whether softnet, which `tart run` starts for an untrusted guest, inherits it too, are measured on the reference Mac before this is relied on.
  - **Guests no slot accounts for.** A macOS VM another account starts, or a billet from before this change, holds no slot, and upgrading billet does not give an already running guest one. So every macOS start, a job's launch and a probe alike, is admitted only if the slots held, its own included, plus every running macOS VM whose name no held slot records, number no more than the limit. A job's launch that a free slot file would admit but this count refuses asks a probe to yield, if one holds a slot, and otherwise fails as any launch does. A billet from before this change can still have a detached launch starting that no inventory sees, so the protocol holds only once every billet on the store has this change. `billet check` reports a store where it cannot tell. Which VMs run is not taken from `tart list`, which can call a running VM stopped when it cannot open the VM's lock, and omits a directory whose layout it cannot read while its VM keeps running. Admission counts the resource itself: every live Virtualization.framework VM process the account can see is a running guest, whatever tart says and whatever disk path it holds, since `tart set --disk` can replace a running VM's disk file while the VM keeps the old one open. A process counts as Linux only by positive proof that billet itself started it as a Linux guest. It must hold open the disk of a billet-owned Linux lease VM or Linux probe, identified by the device and inode of the disk file billet's own clone produced, recorded when billet launched it, and the deployment's marker must still name that VM Linux. Every other live VM process counts as macOS: an operator's VM of either kind, and a process matched only by a path or by a disk it may have attached as a second disk. `billet check` names the processes it counted that way. Admission is allowed only if the slots held, its own included, plus the macOS guests no held slot records, number no more than the limit, and it refuses when the processes or their open files cannot be read. A refusal names the VMs it counted, and so does `billet check`.
  - **Yielding.** A macOS launch that finds no free slot while a probe holds one writes a yield request beside the slots, naming itself and the time, and waits at most two minutes. It removes its request on every way out, and a probe ignores a request older than that wait. A probe checks for a request every few seconds. When it sees one, it ends its guest. It stops the VM, and it ends the `tart run` process it started and waits for that process to exit, because a guest still starting can be waiting on tart's store lock, where `tart stop` reports it already stopped and deleting its directory ends nothing. The slot counts as released only when an exclusive try of the slot file's lock succeeds. The verification ends as "yielded to a job", and the next refresh or the operator runs it again. So a launch waits about a minute, well inside the node's ten-minute command timeout, and the node's queue is not held behind a whole probe.
  - **A probe whose verifier died** keeps its slot through its guest's process, and its guest keeps running. The next verification of that image removes it under the image's verification lock. A launch that needs its slot and finds the image's verification lock free, which proves no verifier owns the probe, destroys it before it starts its own. It finds the probe's processes as its custody file's holders (`lsof`), ends only the holders it positively identifies as that probe's: a process whose executable is tart's or softnet's and which holds the custody file. Neither tart nor softnet ever opens a file of billet's, so such a process can hold that file only by inheriting it from the probe's own launch. That covers softnet reparented after a crashed `tart run`. Any other opener, a billet process trying the lock or anything else, is left alone, and the launch then waits for the lock or fails as any launch does, and waits until the slot's lock can be taken. It never touches a probe whose verification lock is held; it asks it to yield instead.
  - **A Mac whose macOS slots are always busy** may see a probe yield every time. `billet check` reports an image whose verification keeps yielding beside its runner's deadline. The path that always finishes is to stop the Mac's nodes with `billet local down --node`, which drains each node's own jobs and exits, so no control plane places anything there. That means every deployment's node on a store that several share, since another deployment's jobs would otherwise keep the slots busy. Then run `billet images verify --no-yield`, which refuses while the node runs, and finally `billet local up`. The `--node` flag is added for this, because a plain `local down` on a Mac that also runs the control plane stops both roles and seals the deployment. `billet drain` is not that path either: it seals the whole deployment.
  - **Scope.** The slots cover one store, which is how billet installs a Mac node: one service account and one `TART_HOME`. A VM another account starts on the same Mac is invisible to them, as it already is to `macos_vm_limit`.
  - A Linux probe takes no slot. Its CPU and memory are not reserved, as the Firecracker probe's are not, so a Linux verification may briefly overcommit the Mac.
- **Two questions, answered at different times.** Whether the image boots is decided once, by the verification, and never changes for a base. Whether its runner is inside GitHub's window changes without the image changing.
  - The verification refuses a runner `internal/runnerrelease` proves expired.
  - Once a newer runner release exists, the window has a date. The deadline is stored by runner version, in a file of its own beside the records, so every record of that runner version shares it. Deleting a base, unpromoting it, or verifying another image with the same runner never removes a stored deadline. An answer of "could not tell" never erases one either.
  - The launch compares the stored deadline for its record's runner version with the clock, so it needs neither the network nor a refresh.
  - The daily refresh and `billet check` ask again for every record whatever `release.automatic` says, and report a runner whose window is unknown as unknown.
- **Records under concurrency.** One lock file beside the record serialises the record's reads and commits, and is never held across a probe. A verification takes the record's generation number when it starts, and commits only if no unpromote of that image ran in between. An unpromote is never undone by a probe already in flight. A launch that has resolved its base before an unpromote still completes its clone, under the base's lock.
- **Unpromote is a rollback that holds.** `images unpromote <image>@<base>` removes a record and its base. It also records the withdrawal of the digest it was pulled as, keyed by the normalised image, in a file of its own beside the records that no base retention touches. Under the record lock, every record carrying that digest is removed with its base, so no older base of the same bytes keeps serving. Launch resolution skips any record whose digest is withdrawn, and the refresh never verifies a withdrawn digest again, so a tag that still names it does not bring it back. With no eligible base left, a launch refuses. An operator clears a withdrawal with `images verify` of that digest by hand.

**The refresh verifies new images only for `@verified` references.**
- For a remote `@verified` reference whose tag now names a new digest, the refresh pulls that digest and verifies it, macOS included, under the slot lock.
- A reference no tier names with `@verified` is left exactly as today: pulled only when absent, pinned at each launch.
- A local VM is verified again only when an operator asks, since nothing tells billet it changed.

**An older node is never sent a reference it cannot read.** The tier's image reaches a node as a plain string, and a node from before this change would hand `…@verified` to `tart fqn`. So the control plane sends a `@verified` Tart tier only to a node whose wire version reads it, gated as `billet-add-wire-change` describes. A node with no usable record for a tier's image refuses that tier's launch with the command that would verify one, as a Firecracker node with no verified generation does. A Mac's own image commands read its file too: the daily refresh, and the image step of a host upgrade, which runs before the new binary is installed. So a Tart tier's `@verified` is written into a file only once every host that reads that file runs this change. `billet check` and `billet node config-change` refuse it while any registered node predates it, as `arch` is held back (ADR-022).

## Consequences

- What billet asserts about a Tart image is what it can prove from inside a booted guest: the runner, its window, and the toolchain entry points a job uses. It does not assert parity with GitHub's own macOS or arm64 Linux image. GitHub publishes the template for its arm64 Linux image (ADR-022), but billet has no route that turns it into a Tart image, and none is measured.
- A verified image costs a base VM on the Mac's disk. It holds the image's bytes alone, since its private store is deleted once it has moved. Two bases are kept per image. Because billet's clones of a base run without automatic pruning, a `@verified` launch on a full disk fails rather than evicting cache entries as an unverified launch's clone may. A verification needs room for one more copy of the image while its private store exists. `billet check` reports free space against the newest base's size.
- A macOS launch can wait about a minute for a probe to yield, and a macOS verification can be cut short by a job and run again. A probe cannot start while the node's macOS limit is used up, counting guests that hold no slot.
- Records and bases are per node. Two Macs that name the same image each verify it, as two Firecracker nodes at different sites each verify their own generation.
- A reference without `@verified` keeps working, and `billet check` names every Tart tier that boots an image nobody verified.
- status.md's Tart cells move when a deployment's Tart tiers boot `@verified` images and the conformance workflow's arm64 run passes on one, not when this lands.

## Alternatives rejected

- **Publish a macOS image.** The macOS and Xcode licences forbid billet redistributing either.
- **Publish a Tart Linux image built from billet's arm64 guest.** It needs an EFI disk, a second kernel, tart's guest agent, a registry push from a Mac, and a completion route for what the image leaves out, all for one tier shape. A verified third-party or operator-built image gives the same guarantee, a boot billet observed, at a fraction of the cost. It can be reopened if a deployment needs GitHub's arm64 image contents on a Mac rather than in an arm64 Firecracker microVM (ADR-022).
- **Record the digest and clone the remote reference at each launch.** That is what the first draft of this record said. A clone of a missing cache entry fetches whatever the registry serves, and a tag move can delete the verified digest. Only a local copy keeps what was probed.
- **Require the node stopped for a macOS probe.** The proof of a stop reads systemd and not launchd, it says nothing about the moment after it was taken, and a stopped node can leave guests running. A lock that launches share is an exclusion rather than an observation.
- **Ship tooling that builds a macOS image on the operator's Mac.** It needs the operator's Apple account to download Xcode, takes hours, and would be a second image pipeline billet maintains for Apple's formats. An operator who builds their own VM verifies it by name.
- **Pin a digest in the tier instead of `@verified`.** `<repository>@sha256:…` already works and stays allowed. But a digest an operator copied proves nothing was booted, and a fleet that pins by hand stops taking up runner releases until someone edits every tier. That is the thirty-day outage `@verified` exists to prevent on Firecracker.
