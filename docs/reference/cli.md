# CLI

`billet <command> [flags]`. Every command that reads a deployment's configuration takes `--config <path>` (the exceptions are `version`, `release record`, and the `acceptance` subcommands other than `up`, which work from their workspace); the default is the per-user config path (`billet check -h` prints it), never the working directory, and the `local` commands default to the packaged service config (`/etc/billet/billet.yaml` on Linux, `/usr/local/etc/billet/billet.yaml` on macOS). Most failures exit 1. Where a command uses 2 or 3 as an answer rather than an error, so a monitor can tell a task from an outage, the entry below says so.

## Roles

### `billet server`

Run the control plane: long-poll GitHub for assigned jobs, own the capacity ledger, tell nodes what to launch. Run `billet node` beside it to run jobs on the same machine.

| Flag | Meaning |
|---|---|
| `--dry-run` | connect to GitHub and advertise zero capacity: proves the whole path without accepting a job |
| `--upgrade-probe` | open candidate state without polling, dispatching or accepting work; the host-upgrade transaction's quiescent probe. Proves what it can, prints nothing, and exits zero, which is what `billet host-upgrade` waits for |
| `--upgrade-probe-hold` | with `--upgrade-probe`, print the readiness line and stay up until stopped; the Ansible role's `Type=notify` probe unit passes it, when the candidate lists it, and stops the unit itself |

### `billet node`

Run a compute host that dials a control plane. One per machine, including the machine the server is on.

| Flag | Meaning |
|---|---|
| `--enroll` | ask the control plane to admit this machine, then wait for an operator to approve it |
| `--ca-fingerprint <fp>` | the control plane's CA fingerprint, from `billet ca show` (required with `--enroll`) |
| `--join-token <token>` | a short-lived token from `billet ca token` (required with `--enroll`) |
| `--bootstrap-addr <addr>` | the control plane's enrollment address; overrides `node.bootstrap_addr`, defaults to `node.server_addr` |
| `--upgrade-probe` | initialise the candidate provider without dialing or accepting work; prints nothing and exits zero |
| `--upgrade-probe-hold` | with `--upgrade-probe`, print the readiness line and stay up until stopped; passed only by the Ansible role's probe unit, when the candidate lists it |

## Setup

### `billet init`

Generate a `billet.yaml` that runs. It measures the host, writes a ceiling below what it found, and keeps every generated tier that fits individually under it. A fresh generation lands at `<path>.new` unless it can prove the existing file is its own output; `--force` overwrites.

| Flag | Meaning |
|---|---|
| `--profile local\|local-service` | user-session paths for two terminals, or the paths the shipped services read (default `local`) |
| `--force` | overwrite the existing file even when it cannot be proved to be billet's own output |
| `--provider docker\|firecracker\|tart\|ec2\|codebuild` | this host's backend (default `docker`) |
| `--org` or `--repository` | the target: an organization, or one repository as `owner/name`; exactly one of the two |
| `--runner-group`, `--workflow` (repeatable) | the trusted pool; required for docker, refused with `--repository` (a repository has no runner groups, so docker cannot serve one) |
| `--listen` | the loopback address the server binds and the node dials (default `127.0.0.1:7717`) |
| `--image` | the tier image (default: a runner container for docker, a golden generation for firecracker) |
| `--emit file\|ansible` | write the file, or print the `billet_config` block for an inventory and write nothing |
| `--join ADDR` | write a node-only config for this machine that dials the control plane at `ADDR` (its node-wire `host:port`), carrying the measured ceiling as `node.max_vcpu`/`max_memory` and naming the certificate bundle under the config's `tls/` directory, and print what the control plane's config needs: how far to raise `server.max_vcpu`/`max_memory`, and the `tiers:` and `nodes:` to add. Not with `--emit ansible` |
| `--state-backend sqlite\|postgres`, `--state-dsn-env` | where the ledger lives; the DSN's environment variable is required for postgres |
| `--node-name` | this host's name; required for a macOS tier on tart or codebuild |
| `--guest-os macos\|linux` (repeatable), `--macos-image`, `--linux-image` | tart guest kinds and their images (defaults `ghcr.io/cirruslabs/macos-tahoe-xcode:latest` and `ghcr.io/cirruslabs/ubuntu-runner-arm64:latest`) |
| `--kernel-image`, `--ceph-user`, `--ceph-keyring`, `--cache-listen`, `--cache-guest-endpoint` | firecracker: the fallback kernel, the RADOS identity (never `admin`), its keyring, the guest-facing cache endpoint |
| `--region`, `--subnet`, `--security-group` (repeatable), `--untrusted-security-group` (repeatable), `--instance-type` (repeatable), `--price type=usd` (repeatable), `--max-vcpu`, `--max-memory` | ec2: the region signed into every request, network, shapes (prices are fetched; `--price` overrides), and the required cloud budget |
| `--codebuild-project`, `--codebuild-environment`, `--codebuild-fleet-arn`, `--codebuild-fleet-capacity`, `--compute-type NAME=vcpu,memory,price` (repeatable), `--jit-parameter-path`, `--jit-kms-key-id`, `--codebuild-log-group`, `--privileged`, `--build-timeout-minutes`, `--queued-timeout-minutes`, `--accept-external-build-ceiling` | codebuild: the dedicated project, environment type, reserved fleet and its capacity, ordered purchasable shapes, the parameter path the IAM policy is scoped to, and the acknowledgement of CodeBuild's 36-hour and 8-hour ceilings, which is required and changes nothing about how billet behaves |

### `billet init hybrid`

Generate the hybrid shape as one unit into `--out DIR`: a Terraform root over the billet module, an inventory with both hosts and one tier catalogue with ordered providers, the playbook, the collection pin and a numbered `RUNBOOK.md`. Three renders of one generation, selected by flags: with nothing extra the **plan** render carries a `<terraform output NAME>` placeholder for every fact the apply produces; with `--terraform-output` the **prepare** render fills them from `terraform output -json` and keeps the controller server-only and prepare-only, because the co-located node's certificate bundle does not exist until `billet ca issue` has run and the host role's `billet check` refuses a missing one; with `--commission` the controller gains the EC2 orchestrator and every tier's `launch.ec2.image` becomes `--ami`, which is required there because a commissioned deployment advertising a placeholder image would fail every job that reached the cloud. A file is replaced only when its first line carries billet's marker; an operator's own file gets the fresh generation beside it at `<file>.new`.

| Flag | Meaning |
|---|---|
| `--out` | the directory to write into (required) |
| `--name`, `--region` | the Terraform name prefix and the region (region required) |
| `--org` or `--repository`, `--runner-group`, `--workflow` (repeatable), `--config` | the target (an organization, or one repository), the trusted pool (omit both policy flags for untrusted tiers; refused with `--repository`), and the file `github-app create` wrote the App identity into |
| `--control-plane-private-ip` | the controller's address, declared into the root, `server.listen`, every `server_addr` and `ansible_host` before the apply |
| `--controller-name`, `--local-name` | the two hosts' inventory and certificate names (defaults `<name>-control-plane`, `<name>-fc-1`) |
| `--local-vcpu`, `--local-memory` | what the Firecracker host has (required); its contribution leaves headroom |
| `--max-vcpu`, `--max-memory` | the cloud budget, which is the orchestrator's ceiling (required) |
| `--instance-type` (repeatable), `--price` | `TYPE` (fetched from AWS) or `TYPE=vcpu,memory,usd` (declared, no credentials); `--price` overrides a fetched price |
| `--ssh-ingress-cidr` (repeatable), `--key-name` | IPv4 CIDRs that may SSH to the controller (empty for a route that ends on the controller itself), and the key pair it launches with (empty attaches none; the runbook reaches the fresh image with EC2 Instance Connect) |
| `--local-ansible-user`, `--local-image` | the account Ansible connects to the Firecracker host as (empty leaves it to your SSH configuration), and the guest generation every tier boots there (default the x64 generation billet publishes) |
| `--kernel-image`, `--ceph-user`, `--ceph-keyring`, `--cache-listen`, `--cache-guest-endpoint` | the Firecracker host's inputs, as for `billet init --provider firecracker` |
| `--cache`, `--local-site`, `--cloud-site` | give the cloud half an EBS+S3 site cache: the module creates the bucket and the rule admitting runners to it, the orchestrator gains `node.ebs_s3` and a `node.cache` HTTPS listener, and both hosts declare the place their storage is in (defaults `home` and the region). You supply the listener's TLS pair |
| `--builder` | grant the controller's role what `billet ami build` performs, so the image is built there rather than from a workstation holding your AWS credentials |
| `--terraform-output`, `--commission`, `--ami`, `--force` | the prepare render's facts, the commission render, its AMI (required with `--commission`), and replacing a file that is not billet's own |

### `billet init iam`

Print the IAM policy this config's node role needs, derived from the config: cache adds EBS and S3, spot adds the queue, an instance profile adds `PassRole`. Every ec2 policy also denies `ec2:RunInstances` for a snapshot the deployment does not own, because that grant otherwise reads any snapshot in the account through a block-device mapping.

| Flag | Meaning |
|---|---|
| `--builder` | also grant what `billet ami build` needs |
| `--payload-bucket <bucket>` | with `--builder`, also grant put, get and delete on the objects `billet ami build --payload-bucket` stages there (`billet-payload-*`) and nothing else |
| `--build-role` | print the CodeBuild build service role's policy instead of the node's |
| `--controller-sweep` | print the control plane's grant for sweeping staged registrations under this node's parameter path |
| `--account <id>` | the 12-digit account (codebuild) |
| `--deployment <id>` | scope to this deployment (defaults to the state directory's id) |
| `--account-wide` | scope by tag presence instead of deployment id; only safe for a single deployment per account |
| `--role-arn`, `--kms-key-arn` | the profile's role for `PassRole` scoping; the full key ARN when the configured key is a bare id or alias |

### `billet github-app create`

Create the GitHub App in a browser, install it on the organization or the repository, write the five identity scalars into an existing config in place, and save the private key beside it. Refuses everything it can before touching GitHub, because the key is issued once. For an organization the App asks for metadata read and organization self-hosted runners write; for a repository it asks for metadata read and repository **administration write**, the only permission GitHub offers for the job, and the command says so. The manifest form follows the owner's account type, resolved before the browser opens.

| Flag | Meaning |
|---|---|
| `--org` or `--repository` | the organization, or one repository as `owner/name` (exactly one) |
| `--target` | which target the App serves: `default` writes `github:`, any other name writes the `targets:` entry of that name, creating it when absent (default `default`) |
| `--config` | the `billet.yaml` to write the identity into |
| `--key-path` | where to write the key (default: beside the config, `app-private-key.pem` for the default target and `app-private-key-<name>.pem` otherwise) |
| `--name` | a suggested App name |
| `--no-browser` | print URLs instead of opening a browser |
| `--actions-read` | request `actions: read` (default `true`), which default-branch cache publication needs to prove a job's branch from GitHub's record of its run; `--actions-read=false` leaves it out |
| `--port` | a fixed loopback callback port, for `ssh -L` |

### `billet github-app store-key --from <path> [--target NAME]`

Publish an existing App private key into a store-backed deployment (`server.identity.backend: aws-ssm`), at the `default` target's parameter or at the named target's (`github-app-key-<name>`).

### `billet check`

Validate the config and the state directory, prove every target's App key signs a JWT GitHub accepts and its App is installed with exactly the permissions requested for that target's scope (one `target` line per target when there are several; the worst verdict is the report's), check every trusted tier's runner group (a repository target's tiers say the group is not probed and why), say what this node's guests will get from the site's store, count a Ceph node's kernel RBD mappings by what accounts for each and name any cache volume mapped for more than six hours that no cache session holds (reported, never failing the check; run as root, since the custody records are root's, or it says it could not tell), and report registered nodes, images, backups and cloud cost peaks. Works while the control plane is running. A node carrying `node.ebs_s3` with no `node.cache` listener fails the check: that store backs nothing else, so every job would run on the instance's root volume and publish nothing.

| Flag | Meaning |
|---|---|
| `--authorize` | also dry-run a launch against AWS to prove the ec2 role may `RunInstances` |
| `--maintenance-probe` | the host-upgrade transaction's quiescent probe: cross the maintenance fence, skip every network call |

The report names the host's converge guard when one is held: informational under a day, a `WARNING` naming `billet converge-guard recover --holder H --old-driver-stopped` past it, and a `WARNING` for a hold that never returned from its publication or a record whose time cannot be read. Nothing expires a guard; the warning is the reminder.

On Linux it also says whether needrestart, which unattended upgrades run after every package upgrade, leaves billet's services alone: nothing when needrestart is not installed, the file carrying `$nrconf{override_rc}{qr(^billet-)} = 0;` when one does, a `WARNING` naming `/etc/needrestart/conf.d/90-billet.conf` when none does, and could-not-tell when a configuration file cannot be read. It recognises only that line, so a host kept safe another way still reads as the warning.

On a Linux node it also says whether `node.lock_dir` outlives the node's stop: a `WARNING` when `billet-node.service` still declares it, or a parent of it, as a `RuntimeDirectory`, which systemd removes at every stop of the node under the locks other processes hold there (an image verification's among them); a `WARNING` when it is not `/run/billet/locks`, the one directory the node unit makes writable for its lock and the one spelling `billet local up` accepts, or when that path is a link to somewhere else; a `WARNING` when the directory does not exist, since the node unit will not start without it; nothing when the unit is not installed; and could-not-tell when systemd or the filesystem could not be asked. The node unit this release ships names the directory in `ReadWritePaths` and a tmpfiles.d entry creates it at boot, but a host a rollout upgraded keeps the units it had until the package is installed or the host role converges it.

## Running the services

### `billet local status|up|down|uninstall`

Manage the systemd units (Linux) or launch agents (macOS). `status` reports what the service manager actually has loaded. `up` runs `billet check`, starts the server, then the node, proves each held its process, then enables them; it writes no units on systemd and writes the agents on macOS. `up` exits 2 when the services are up but admission could not be reopened (an operator's seal, or a seal it could not read), so the host is running and takes no work until `billet resume`. `down` seals admission, waits for running work, stops the node, stops the server and disables both. `uninstall` is `down` plus forgetting the services, leaving the data.

| Flag | Applies to | Meaning |
|---|---|---|
| `--dry-run` | up, down, uninstall | report and change nothing |
| `--reason` | down, uninstall | recorded on the seal |
| `--timeout` | down, uninstall | give up waiting after this long (default: wait for as long as the jobs take) |
| `--force` | down, uninstall | stop services running a different billet build |
| `--without-compute-proof` | down | stop once the ledger is quiet, without asking each host what it is running |

### `billet local prepare`

The privileged bootstrap the package's postinstall, `billet local up` and the host role run (Linux, as root): it moves this host onto the global authority exclusion, or repairs its metadata, and publishes the authority's status back to the caller, which refuses whatever a closed (retired) authority forbids. It authorises nothing else. The identity directory is the configuration's server directory when a configuration exists, else the packaged default.

| Flag | Meaning |
|---|---|
| `--account` | the service account the units run as |
| `--group` | the service group (defaults to the account's name) |
| `--wait` | how long to wait for a lock another billet holds (default `1m`) |
| `--json` | print the answer as JSON |

### `billet local backup|restore|recover`

Capture a deployment as one unit, put it back as one unit or not at all, or put it back over itself. [Backup, restore and recover](../operating/backup-restore-recover.md).

| Flag | Applies to | Meaning |
|---|---|---|
| `--out <dir>` | backup | the destination, created and empty |
| `--no-upload` | backup | write the archive and do not copy it to `backup.s3` |
| `--from <dir>` | restore, recover | a backup directory |
| `--from-backup <name\|latest>` | restore, recover | fetch an archive from `backup.s3` |
| `--into <dir>` | restore, recover | where a fetched archive is kept |
| `--deployment <id>` | restore, recover | which deployment's archives to look at |
| `--old-controller-fenced` | restore, recover | assert the controller this backup came from is stopped and disabled everywhere (required) |
| `--external-ledger-attached` | restore | assert a PostgreSQL ledger has been restored and this host's config points at it |
| `--accept-failing-jobs` | recover | proceed even though work is outstanding; every job named fails |
| `--reason`, `--timeout` | recover | recorded on the seal; give up waiting for quiescence |
| `--dry-run` | restore, recover | report what would happen and every refusal, and change nothing |
| `--abandon` | restore, recover | undo an interrupted run, removing only what it created; recover also puts the superseded ledger back |

## Capacity and admission

| Command | Meaning |
|---|---|
| `billet status` | admission, controller and epoch, capacity, tiers (grouped by target when there are several), nodes with protocol versions, cost peaks, unproven hosts, and the host's own converge guard when one is held (`guard held by H for AGE`). Under each tier whose jobs started in the last hour, the p99 of their queue wait, from GitHub's queue time to billet's start (`billet jobs wait` has the rest), with the jobs that have no GitHub queue time on record counted as unknown |
| `billet leases held` | every lease whose compute is not confirmed gone |
| `billet leases quarantined` | capacity held for compute nobody has accounted for |
| `billet leases failures [--since 24h] [--limit 50]` | jobs GitHub did not report as succeeded on leases billet's infrastructure disrupted; billet re-runs nothing |
| `billet jobs show [--json [--window FROM,TO] \| --html] <lease>` | which GitHub job the lease ran (repository, workflow ref, job name, event, GitHub's job id), when GitHub queued it and handed it to the scale set and to a runner (GitHub's clock; `-` where no message carried the time), and how long it waited with the parts `billet jobs wait` splits a wait into (`unknown` where an end of a part is not recorded) and, with `node.monitoring`, what the host measured it do: CPU with the guest and VMM split, peak memory, disk and network bytes, pressure stalls and package energy (on tart, macOS's own estimate for the VM's process), and, with `node.monitoring.perf`, the vCPU threads' hardware counters and what they imply: instructions per cycle, cache misses and branch misses per 1,000 instructions, and the share of cycles the frontend stalled; and, with `node.monitoring.flows`, where its traffic went: the 20 largest destinations by total bytes with a count and total of the rest, the traffic beyond the 256 the node keeps by name, whether the totals are complete or a lower bound, and the tap's own totals beside them as a comparison of two counters read a moment apart. A group the host could not read says `not measured`, and so does an OOM count a host keeps none of, an event the CPU did not count, every ratio that needs one, and destinations that were not totalled. `--json` prints the same record as one object for a program: an empty string is a field the ledger has no value for, `usage` is `null` when no report was recorded, and `usage.measured` answers true or false for every group, so a zero is read only where it was measured ([measurement validation](../operating/measurement-validation.md) reads it) Then the job's steps as GitHub records them, read when the command runs with the App of the target that served the job (it needs `actions: read`, which `billet github-app create` requests by default) and bounded at 20 seconds, 1 MiB a response, 1000 jobs in the run and 1000 steps in the job: each step's name, start and duration, and the CPU, peak memory, disk, network and energy the host's series shows in the step's window. The job is found in its run's job list by its runner's name, because the job id a scale-set message carries is not the one GitHub's REST API takes. Windows are aligned to the second on two clocks, GitHub's for the steps and the host's for its samples, with no correction for skew between them; inside one sample interval a counter's increment is split by time and rounded to the unit, and the peak memory is the highest level sampled inside the step, so a step with no sample inside it has none. A step the series does not fully cover (it began before the first sample, ended after the last, or spans an interval the sampler marked as unseen or across which a counter fell) is printed as partial with how much is covered, never as a smaller total; a step GitHub gives no start or end time is listed without usage; a series recorded without its start on the host's clock (by a node, or for a control plane, older than wire 28) gives no step usage and says so. A GitHub read that fails is printed as the reason and does not fail the command, and a run GitHub has deleted shows no steps, because GitHub keeps a job's record only as long as its run. `--json` prints the record and its usage and reads no steps from GitHub. `--window FROM,TO` (RFC 3339, with `--json` only) adds `window`: the host's series integrated over those instants as a step's window is, with `complete` true only when the series covers the whole of it and every quantity otherwise over `covered_ms`, and beside it `inner` and `outer`, the same over the whole sample intervals inside the window and over it (each `null` when the series has no such samples), between which the window's true figure lies, since splitting an interval by time is a guess about when in it a counter moved, and `gaps`, each interval inside the window the sampler did not see, cut to it, with `from`, `to`, `ms` and `cause` (at most 1000, and `gaps_more` counts the rest), which is what `covered_ms` falls short of `span_ms` by; `usage` is `null`, `gaps` is `null` and `unavailable` says why when there is no report or no series on the host's clock. The record's `usage.series` is the series' own account: its `first` and `last` sample on the host's clock, its `samples`, the `unseen_ms` of every gap and the same `gaps` list (adjacent gaps of one cause joined), or `null` without a series on the host's clock, with `series_unavailable` saying why. A window short of its span by more than its gaps passed the largest total an int64 holds, which leaves an interval uncovered that is no gap. In the text report and on the page a `series` section says the same: when the series ran, how many samples it holds and every interval it did not see, with when, how long and why (the first 20, then a count), or that it saw them all; the page also draws them as a strip above the charts on the charts' axis, at the charts' resolution. `--html` prints the same report as one self-contained, read-only page (`billet jobs show --html <lease> > job.html`; [an example](../_static/examples/jobs-show.html)): the job's identity, a timeline of its steps, CPU, memory, disk and network charts over the host's series with each step's window shaded and the lease's vCPU and memory drawn across the first two, the per-step usage table, the usage report with the hardware counters, and the destinations with the tap's comparison. It reads the steps from GitHub as the text report does and words every verdict, partial window and `not measured` as the text report does; a GitHub read that fails is the steps section's reason and the rest still renders. Choosing a step focuses every chart on its window. The page fetches nothing: its Content-Security-Policy allows no source but inline style and its one script by hash, every string GitHub or a workflow chose is escaped, and the charts are inline SVG. A series of more than 720 sample intervals is drawn as 720 equal windows (a rate as the average over a window the series covers whole, any other a break; memory as the highest level sampled in it) and the page says so, so a page of the largest series the ledger keeps is under 96 KiB, plus about 1 KiB a step and the text GitHub and the workflow chose, which is shown whole. A memory line breaks wherever the series cannot tell (an interval the sampler marked as unseen, or one across which a counter fell, and the catch-up after it), as the rate lines do. A partial step's CPU, disk, network and energy are over the part the series covers, and its peak memory is the highest level sampled anywhere in the step, in the text report and on the page alike. With `node.monitoring.guest`, each of the three renderings ends with what the job's own VM reported through billet's in-VM agent, under the heading "Reported by the job's own VM. The job runs as root there and can change any of it; billet does not act on it." wherever the guest's numbers appear, and every string the guest wrote (process, step, suite and test names) printed quoted and escaped. First its verdict: no report recorded (the node had guest monitoring off or is older than wire 29; `--json` has a `guest` of `null`), the guest never contacted the node (an image older than the agent, or an agent that did not start), the agent introduced itself and the node accepted none of its batches, the node accepted batches and could not keep them, a report that does not decode, and, with a report, node restarted (the batches held before the restart were lost), partial (the node has no record of accepting the agent's last batch, which a refused last batch and a restart both leave, or it accepted it and not every batch it accepted is in the report, since the node may drop what it cannot assemble and the merge may refuse a batch) or complete; none of the first five is ever shown as zeros. Then what the node counted of the channel (the batches it accepted and refused, the bytes it dropped, whether it saw the agent's hello and last batch, and when the first and last batch arrived on its clock) and, with a report: the report's account of the agent's batches and its resolution; the skew, one-sided, as the time from the guest's last sample stamp to the node's receipt of the last batch, which bounds how far the guest's clock lags the node's (a negative one proves it ahead); the guest's used memory, page cache and lowest available memory beside the host's peak level, and on the page a chart of the first two over the host's level on the host's axis, placed by the guest's own clock; the cross-checks where both sides measured the same thing, the guest's busy CPU since boot against the host's vCPU thread time and its eth0 bytes against the tap, each shown with the difference and judged by neither; the agent's own CPU and an upper bound on the bytes its batches added to the tap (the node counts the batches it accepted, not their bytes); the guest's step marks matched by name, in order, to GitHub's steps, whose numbers and names are the authority, each with the mark's offset from GitHub's start and named by GitHub's number and its name as the agent cut it to 64 bytes, GitHub's whole name being the Steps section's; the busiest five processes of each step by the step the process sample ended in (the last group open-ended when marks past the report's bound were left out, and the section saying no group holds one step's alone when a batch that could have carried a mark may be missing: as a loss where the counts prove one, a number between its first and last that no merged batch carries or a batch the node accepted and the report does not hold, and as uncertain for an attempt the node refused, which the agent's retry may have delivered), the rest summed and the CPU of processes that exited between samples apart; and the JUnit results the agent found, which a report cannot tell when the node has no record of accepting the agent's last batch, or accepted it and the report cannot show it holds it. `--json`'s `guest` carries the verdict, the node's counts under `channel` and the decoded report under `report`. A guest report the ledger can keep adds under 3 MiB to the page: about 2.4 MiB when every section is at its bound, every name is made of the character that grows most when quoted and escaped and every number is at its widest, and about 500 KiB when its text does not compress |
| `billet jobs wait [--tier T] [--since D] [--json]` | how long jobs waited for a runner, from what the ledger recorded: for the jobs that started in the last `--since` (default 24h), per tier and charged shape, the count, mean, p50, p75, p90, p99 and p99.99 (nearest rank) and the longest, named by its lease so a number leads to `billet jobs show`. The wait runs from GitHub's queue time to billet's record of the start, and is split into parts that, for each job, add up to its wait (each part is summarised over the jobs whose two ends of it were recorded, so the parts' percentiles need not add up): **at github**, queued to GitHub handing the job to this scale set (GitHub's clock alone); **for room**, that hand-over to billet buying the lease the job ran on (both clocks; negative when the room was bought first, an idle runner or a purchase on the offer); **to start**, the purchase to the start (billet's clock alone: the launch, the runner's registration and any time it stood idle). GitHub's times are GitHub's clock and the start is billet's, so a wait is only as exact as the two agree; a negative one is printed as it is and counted, never as zero. A job with no GitHub queue time on record (assigned before the ledger kept one; or offered with none, before the control plane last started, or past the 50,000 offers a tier keeps, or whose start's write failed: GitHub sends no queue time on the start, so the control plane keeps the one an offer or an assignment carries in memory for the start) is counted as unknown and kept out of every percentile, and so is a part either of whose ends is missing. Jobs still queued have no start: each tier's count and its oldest come from its listener's last report. A `--tier` the configuration does not name is refused. `--json` prints the same as one object, every duration in seconds, a part no job could be measured for as `null` and a shape the ledger did not record as a `vcpu` of `null`; a window larger than one report reads (200,000 jobs) is marked partial, and the jobs left out are its oldest |

Retirement's completion document and completed ledger row are historical facts bound to the deployment, participants, transition, reservation and `DoneAt`. `--complete-row` and `--acknowledge-row` verify their caller's authorization, and `--complete-row` verifies every binding on the branch that advances a row while answering `already` on a row already `done` under the same transition id; neither re-verifies each field on every branch, and neither certifies the retiring host's health now. Fresh local proof remains necessary for publication and settlement. The three ordinary admission modes above are mutually exclusive with one another and with retirement mutation/classification; their successful answers say `state: nothing`. See [controller retirement](../operating/upgrades.md#when-a-controller-retires) for preparation, check-mode limits, the endpoint prerequisite and the invocation boundaries, and [retained environment files](../operating/upgrades.md#retained-node-environment-files) for the supported `EnvironmentFile` grammar.

The upgrade root's trust boundary is proved before any of these takes the lock, through descriptors and never by pathname: every directory on the way to `/var/lib/billet` (or `/usr/local/var/lib/billet` on a Mac) is reached by a walk from the filesystem root, one component relative to the descriptor of the one above it, and must be owned by root or by the account running the command and writable by nobody else unless the sticky bit is set; the parent must be owned by that account; the root a directory owned by it and not writable by group or others; `active` 0700 and owned by it; `transaction.lock` a regular file; none of them a symlink; the root is opened relative to the parent's descriptor and the lock relative to the root's, each `O_NOFOLLOW`, and once the lock is held the root's name must still hold the directory the lock was taken inside, so a name replaced between the check and the use is not the thing used. Every name a mutator then touches under the root is resolved relative to that root descriptor, and the guard directory a release, a recovery or a takeover acts on is validated (0700, owned) before its record is believed.

## Sharing the uplink

### `billet uplink shape [--interface NAME] [--reflectors A,B,...] [--max-up MBIT] [--max-down MBIT] [--gateway ADDR|none]`

Keep this host's own traffic, its guests' included, from filling the queue of the internet line it shares with the rest of its site. It runs until stopped, as root, on Linux: CAKE on the interface (the default route's unless `--interface` names one) in both directions, each starting at 25 Mbit/s when nothing has been learned, never at the interface's speed. Twice a second it pings the reflectors (by default 1.1.1.1, 8.8.8.8 and 9.9.9.9, three operators, a delay counting only when most of them see it) and reads what the interface moved. A direction is cut only while it is busy with this host's own traffic, on either of two signs that the line is full. When 3 of the last 6 rounds came back more than 15 ms above each reflector's idle baseline, it is cut to below what it was moving, more deeply the higher the delay. When probes went unanswered in at least 2 of the last 6 rounds, from most of the reflectors between them, and in this round too, it is cut to three quarters of what it was moving: a gateway that drops rather than queues shows a full line as loss, and barely as latency. An unanswered probe is a loss and never a delay, so a round most reflectors missed has no delay, and a cut taken in it logs `delay=unmeasured`. While a direction runs at its rate, a round measures a delay under 15 ms and the last 6 rounds show no dropping line, its rate rises: 4% a step back up to nine tenths of what it was moving at its last cut, where the line was last found full, and from there 2% at most every ten seconds; near that line, and before any cut has found one, only while it moves nine tenths of its rate, so a rate the line itself stops short of climbs no further. What a direction moved is taken as its line only when it was moving at least half its rate and at least a twentieth of what the other direction moved, so an upload carrying a download's acknowledgements, about 2 to 3% of it, is cut with the download and keeps the line it found. On a line whose upstream is under a twentieth of its downstream (1000/35 cable plans) a full upload looks the same while the download is busy, so its line is found while the download is quiet and kept from then on, and until then it climbs back as one with no line found. A round with no measured delay never raises a rate, a round that counted no reflector neither cuts nor raises, and a reflector silent for ten seconds stops counting until it answers again (when none answers for that long the journal says it cannot tell, and says so again when they return). Nothing about the line's speed has to be configured: a gateway that drops rather than queues is found by overrunning it until the loss rule sees it, and the slow climb near where it was found keeps that to a few seconds now and then rather than at every climb. `--max-up` and `--max-down` set an optional ceiling in Mbit/s that a direction never rises past (0, the default, is the interface's speed; anything else must be at least 10). It also asks the default route's gateway each round, and follows it when the route moves (`--gateway` names another IPv4 address, which is not followed, `--gateway none` asks none, one it cannot look up is logged and left out, and one that is also a reflector is asked only as a reflector): the gateway's own rise more than 15 ms above its baseline, confirmed by another high reading at most four rounds (two seconds) before it, one quiet reply between them or not, though two in a row end the stall, so a lone spike cuts nothing, counts as the reflectors' delay does, cutting a busy direction, each pair with no reply read between covering at most one earlier round too, the nearest that counted a reflector, its first reading's included, so a gateway answering one probe in three still cuts and two pings alone never do, while any high reading holds a rate and keeps a queue from reading as gone and a quiet reading clears a stall unless a high one stands just before it, the deeper of its confirmed rise (the lesser of its two readings) and the reflectors' delay setting the cut, but only in a round that counted a reflector, and judged against its own delay at the cut, on two readings too, as a cut is judged by the reflectors' loss only when its line was dropping; its unanswered probes are never loss, because a gateway answers ICMP only when it has the time, though while it stalls a round it gave no reading in is not clear, until it has been silent ten seconds and stops counting. A rate near the interface's speed is not taken as a full line: the shaper cannot tell a line as fast as the interface from a slower one, and a slower one that drops shows as the reflectors' loss. Every rate it sets, where each direction last found the line full, and the rates in force again every minute and as it stops, are kept in `/var/lib/billet-uplink/learned` (the unit's `StateDirectory`, not the `/run/billet-uplink/` its record of the interface lives in), and the next run, after a restart, an upgrade or a reboot, starts each direction there as it was, however long it was down, but no higher than nine tenths of the line found, and a record written before the line was kept, by a shaper that started each run at its ceiling and recorded that before measuring anything, counts as nothing learned (the journal says `resuming the rates an earlier run learned`); rates learned on another interface are not used (within one boot the kernel's index for it decides; across a reboot, which renumbers interfaces, its name, and its hardware address as it was at the last record where both boots' are known; and when either boot's identity cannot be read, the name and the index both), the file is installed so a power cut leaves the last whole record, and a rate learned above a ceiling since lowered starts at that ceiling; with nothing usable a direction starts at 25 Mbit/s. Each change sets both directions from the shaper's own state, so a rate set by hand with `tc qdisc change` lasts only until its next cut or rise in either direction; a lasting limit is `--max-up` and `--max-down`. Stopping it removes the shaping, and the journal says so (`removed the shaping this run installed, as it stopped`). So does the installed billet being replaced by an upgrade, after which it exits with an error so the unit starts it again on the new binary; it checks for that once a minute, so the upgrade paths do not wait for it: `billet host-upgrade` restarts a running, enabled `billet-uplink.service` onto the binary it leaves, after a commit and after a rollback, and the host role's transaction stops it and starts it again. A restart of the shaper that fails is reported and never fails or rolls back the upgrade. The host role runs it as `billet-uplink.service`; [the shared-uplink record](records/shared-uplink.md) has the measurements behind it.

### `billet uplink check [--interface NAME]`

Say whether this host can be shaped, changing nothing but loading the `sch_cake` and `ifb` modules: the kernel has CAKE and IFB, and the interface carries no traffic policy of somebody else's. Only qdiscs the kernel assigned (handle `0:`) may be replaced; CAKE, an ingress qdisc and an `ifb-` device count as billet's only when the record a run of the shaper keeps under `/run/billet-uplink/` names the interface, and a `clsact` qdisc never does. The shaper refuses anything else rather than replace it. The host role enables `billet-uplink.service` only where this passes.

### `billet uplink clear [--interface NAME]`

Remove what the record under `/run/billet-uplink/` says a `billet uplink shape` installed, and only that. The record names the interface by its kernel index as well as its name, so the shaping is found on an interface renamed since, a device that has taken the old name is left alone, and an interface that is gone leaves only its IFB device to remove. With no record it removes nothing, because nothing else proves what is on an interface is billet's, and it inspects the interface (the default route's unless `--interface` names one) before saying there is nothing to clear: CAKE, an ingress qdisc or the shaper's `ifb-` device there, or an interface it could not inspect, exits non-zero saying it cannot tell whose they are, with the commands that remove them by hand. A record that exists and cannot be read is an error too, never "no record". It refuses while a shaper runs, and exits non-zero when a removal failed. The unit runs it as `ExecStopPost`, so a crash is cleared too; after an ordinary stop the shaper has already removed its own shaping and its record, so this finds no record and an interface carrying nothing of billet's.
