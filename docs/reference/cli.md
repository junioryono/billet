# CLI

`billet <command> [flags]`. Every command that reads a deployment's configuration takes `--config <path>` (the exceptions are `version`, `release record`, and the `acceptance` subcommands other than `up`, which work from their workspace); the default is the per-user config path (`billet check -h` prints it), never the working directory, and the `local` commands default to the packaged service config (`/etc/billet/billet.yaml` on Linux, `/usr/local/etc/billet/billet.yaml` on macOS). Most failures exit 1. Where a command uses 2 or 3 as an answer rather than an error, so a monitor can tell a task from an outage, the entry below says so.

## Roles

### `billet server`

Run the control plane: long-poll GitHub for assigned jobs, own the capacity ledger, tell nodes what to launch. Run `billet node` beside it to run jobs on the same machine.

| Flag | Meaning |
|---|---|
| `--dry-run` | connect to GitHub and advertise zero capacity: proves the whole path without accepting a job |
| `--upgrade-probe` | open candidate state without polling, dispatching or accepting work; the host-upgrade transaction's quiescent probe. Proves what it can, prints nothing, and exits zero, which is what `billet host-upgrade` waits for |
| `--upgrade-probe-hold` | with `--upgrade-probe`, print the readiness line and stay up until stopped; the Ansible role's `Type=notify` probe unit passes it, when the candidate lists it, and stops the unit itself |

### `billet node`

Run a compute host that dials a control plane. One per machine, including the machine the server is on.

| Flag | Meaning |
|---|---|
| `--enroll` | ask the control plane to admit this machine, then wait for an operator to approve it |
| `--ca-fingerprint <fp>` | the control plane's CA fingerprint, from `billet ca show` (required with `--enroll`) |
| `--join-token <token>` | a short-lived token from `billet ca token` (required with `--enroll`) |
| `--bootstrap-addr <addr>` | the control plane's enrollment address; overrides `node.bootstrap_addr`, defaults to `node.server_addr` |
| `--upgrade-probe` | initialise the candidate provider without dialing or accepting work; prints nothing and exits zero |
| `--upgrade-probe-hold` | with `--upgrade-probe`, print the readiness line and stay up until stopped; passed only by the Ansible role's probe unit, when the candidate lists it |

## Setup

### `billet init`

Generate a `billet.yaml` that runs. It measures the host, writes a ceiling below what it found, and keeps every generated tier that fits individually under it. A fresh generation lands at `<path>.new` unless it can prove the existing file is its own output; `--force` overwrites.

| Flag | Meaning |
|---|---|
| `--profile local\|local-service` | user-session paths for two terminals, or the paths the shipped services read (default `local`) |
| `--force` | overwrite the existing file even when it cannot be proved to be billet's own output |
| `--provider docker\|firecracker\|tart\|ec2\|codebuild` | this host's backend (default `docker`) |
| `--org` or `--repository` | the target: an organization, or one repository as `owner/name`; exactly one of the two |
| `--runner-group`, `--workflow` (repeatable) | the trusted pool; required for docker, refused with `--repository` (a repository has no runner groups, so docker cannot serve one) |
| `--listen` | the loopback address the server binds and the node dials (default `127.0.0.1:7717`) |
| `--image` | the tier image (default: a runner container for docker, a golden generation for firecracker) |
| `--emit file\|ansible` | write the file, or print the `billet_config` block for an inventory and write nothing |
| `--join ADDR` | write a node-only config for this machine that dials the control plane at `ADDR` (its node-wire `host:port`), carrying the measured ceiling as `node.max_vcpu`/`max_memory` and naming the certificate bundle under the config's `tls/` directory, and print what the control plane's config needs: how far to raise `server.max_vcpu`/`max_memory`, and the `tiers:` and `nodes:` to add. Run by `billet join`, which passes `--join-deployment` from the authority it verified, it prints that half as one `billet join accept <token>` command instead. Not with `--emit ansible` |
| `--state-backend sqlite\|postgres`, `--state-dsn-env` | where the ledger lives; the DSN's environment variable is required for postgres |
| `--node-name` | this host's name; required for a macOS tier on tart or codebuild, and accepted with `--join` on any backend, because a joining node enrolls by it before any certificate names it |
| `--join-deployment` | with `--join`: the deployment the node enrolls with, which binds the printed `billet join accept` token to it; `billet join` sets it from the authority it verified |
| `--guest-os macos\|linux` (repeatable), `--macos-image`, `--linux-image` | tart guest kinds and their images (defaults `ghcr.io/cirruslabs/macos-tahoe-xcode:latest` and `ghcr.io/cirruslabs/ubuntu-runner-arm64:latest`) |
| `--kernel-image`, `--ceph-user`, `--ceph-keyring`, `--cache-listen`, `--cache-guest-endpoint` | firecracker: the fallback kernel, the RADOS identity (never `admin`), its keyring, the guest-facing cache endpoint |
| `--site`, `--ebs-s3-region`, `--ebs-s3-availability-zone`, `--ebs-s3-bucket`, `--ebs-s3-prefix`, `--ebs-s3-kms-key-id` | firecracker, with `--join`: the site this host is at, and on AWS metal the site's ebs-s3 store, whose volumes the node attaches to its own instance (ADR-030); the store needs `--site` and the cache listener, and its prefix defaults to `billet-cache` |
| `--region`, `--subnet`, `--security-group` (repeatable), `--untrusted-security-group` (repeatable), `--instance-type` (repeatable), `--price type=usd` (repeatable), `--max-vcpu`, `--max-memory` | ec2: the region signed into every request, network, shapes (prices are fetched; `--price` overrides), and the required cloud budget |
| `--codebuild-project`, `--codebuild-environment`, `--codebuild-fleet-arn`, `--codebuild-fleet-capacity`, `--compute-type NAME=vcpu,memory,price` (repeatable), `--jit-parameter-path`, `--jit-kms-key-id`, `--codebuild-log-group`, `--privileged`, `--build-timeout-minutes`, `--queued-timeout-minutes`, `--accept-external-build-ceiling` | codebuild: the dedicated project, environment type, reserved fleet and its capacity, ordered purchasable shapes, the parameter path the IAM policy is scoped to, and the acknowledgement of CodeBuild's 36-hour and 8-hour ceilings, which is required and changes nothing about how billet behaves |

### `billet init hybrid`

Generate the hybrid shape as one unit into `--out DIR`: a Terraform root over the billet module, an inventory with both hosts and one tier catalogue with ordered providers, the playbook, the collection pin and a numbered `RUNBOOK.md`. Three renders of one generation, selected by flags: with nothing extra the **plan** render carries a `<terraform output NAME>` placeholder for every fact the apply produces; with `--terraform-output` the **prepare** render fills them from `terraform output -json` and keeps the controller server-only and prepare-only, because the co-located node's certificate bundle does not exist until `billet ca issue` has run and the host role's `billet check` refuses a missing one; with `--commission` the controller gains the EC2 orchestrator and every tier's `launch.ec2.image` becomes `--ami`, which is required there because a commissioned deployment advertising a placeholder image would fail every job that reached the cloud. A file is replaced only when its first line carries billet's marker; an operator's own file gets the fresh generation beside it at `<file>.new`.

The renders are bound to one root by a **generation fingerprint**. The plan render mints it, the root declares it as the `generation` output, and the runbook's every render command carries it as `--generation`. A prepare or commission render refuses outputs whose `generation` names another root, even when their `name` and `region` match. The first render into a directory records the fingerprint in `--out/GENERATION`, one line, outside the marker rule, and never replaces it; a render with no `--generation` reads it from there, so a re-run of the plan render and `--force` keep it, a `--generation` that disagrees with it is refused, and a prepare or commission render that finds neither is refused. A directory whose root has no record (rendered before the fingerprint, or by a render that died before recording it) is never given a fresh one: pass the root's own `generation` value as `--generation` to adopt it. Renders into one `--out` take an advisory lock on it, and a second is refused while the first runs. The render also compares the root's `account_id` output with the account its own AWS credentials are in (STS `GetCallerIdentity`). A different account is refused; when no credentials resolve, or STS cannot answer, it prints that the account was not verified and goes on, bound by the generation. A root rendered before the fingerprint has neither output, and its outputs are refused with the way through, which is a merge: render the plan again into a scratch `--out` with the same flags, copy its `generation` and `account_id` output blocks into your root and nothing else, check that `terraform plan` adds only those two outputs, apply, save `terraform output -json` again and pass `--generation` with the value you copied. Re-rendering in place is not the same thing. Which of two things a render does is decided by the root's first line, not by whether you edited it: a root that still begins with billet's marker is replaced whole (a newer billet's render also moves the module's release pin), and one whose marker you removed gets the fresh render beside it at `main.tf.new`, where an apply never reads it. That rule holds for every render after the merge too, so remove the marker from a root you want billet to stop replacing.

| Flag | Meaning |
|---|---|
| `--out` | the directory to write into (required) |
| `--name`, `--region` | the Terraform name prefix and the region (region required) |
| `--org` or `--repository`, `--runner-group`, `--workflow` (repeatable), `--config` | the target (an organization, or one repository), the trusted pool (omit both policy flags for untrusted tiers; refused with `--repository`), and the file `github-app create` wrote the App identity into |
| `--control-plane-private-ip` | the controller's address, declared into the root, `server.listen`, every `server_addr` and `ansible_host` before the apply |
| `--controller-name`, `--local-name` | the two hosts' inventory and certificate names (defaults `<name>-control-plane`, `<name>-fc-1`) |
| `--local-vcpu`, `--local-memory` | what the Firecracker host has (required); its contribution leaves headroom |
| `--max-vcpu`, `--max-memory` | the cloud budget, which is the orchestrator's ceiling (required) |
| `--instance-type` (repeatable), `--price` | `TYPE` (fetched from AWS) or `TYPE=vcpu,memory,usd` (declared, no credentials); `--price` overrides a fetched price |
| `--ssh-ingress-cidr` (repeatable), `--key-name` | IPv4 CIDRs that may SSH to the controller (empty for a route that ends on the controller itself), and the key pair it launches with (empty attaches none; the runbook reaches the fresh image with EC2 Instance Connect) |
| `--local-ansible-user`, `--local-image` | the account Ansible connects to the Firecracker host as (empty leaves it to your SSH configuration), and the guest generation every tier boots there (default the x64 generation billet publishes) |
| `--kernel-image`, `--ceph-user`, `--ceph-keyring`, `--cache-listen`, `--cache-guest-endpoint` | the Firecracker host's inputs, as for `billet init --provider firecracker` |
| `--cache`, `--local-site`, `--cloud-site` | give the cloud half an EBS+S3 site cache: the module creates the bucket and the rule admitting runners to it, the orchestrator gains `node.ebs_s3` and a `node.cache` HTTPS listener, and both hosts declare the place their storage is in (defaults `home` and the region). You supply the listener's TLS pair |
| `--builder` | grant the controller's role what `billet ami build` performs, so the image is built there rather than from a workstation holding your AWS credentials |
| `--terraform-output`, `--commission`, `--ami`, `--force` | the prepare render's facts, the commission render, its AMI (required with `--commission`), and replacing a file that is not billet's own |
| `--generation` | the fingerprint the plan render minted and the root declares (four groups of four lowercase hex digits); default read from `--out`'s `terraform/main.tf`, or minted by a plan render |

### `billet init iam`

Print the IAM policy this config's node role needs, derived from the config: cache adds EBS and S3, spot adds the queue, an instance profile adds `PassRole`. Every ec2 policy also denies `ec2:RunInstances` for a snapshot the deployment does not own, because that grant otherwise reads any snapshot in the account through a block-device mapping. The launch grant allows an instance and its volumes only when the launch tags them with this deployment's owner, and only into the config's `subnet_id` and its trusted and untrusted security groups, so the role cannot launch elsewhere in the account or launch compute billet cannot see.

| Flag | Meaning |
|---|---|
| `--builder` | also grant what `billet ami build` needs |
| `--builder-subnet <id>`, `--builder-security-group <id>` | with `--builder`, also let launches use the subnet and the group `billet ami build` is told to launch with, when they are not the config's |
| `--payload-bucket <bucket>` | with `--builder`, also grant put, get and delete on the objects `billet ami build --payload-bucket` stages there (`billet-payload-*`) and nothing else |
| `--build-role` | print the CodeBuild build service role's policy instead of the node's |
| `--controller-sweep` | print the control plane's grant for sweeping staged registrations under this node's parameter path |
| `--pool` | print the control plane's grant over `server.pool.aws_metal`'s hosts instead, from a config with no `node:` block: describe instances, launch only into the pool's subnet, groups and images with the instance and its volumes tagged with nothing but `Name`, `sh.billet.pool-owner=<deployment>` and `sh.billet.pool-order`, and terminate and read the console of only an instance carrying that pool owner; `--role-arn` names the role inside `aws_metal.instance_profile`, and `--kms-key-arn`, repeated for each, a customer-managed key the hosts' volumes are encrypted under (each image's, or the account's EBS default), used and granted only through EC2 in the pool's region; AWS's own `aws/ebs` key needs none |
| `--account <id>` | the 12-digit account (codebuild) |
| `--deployment <id>` | scope to this deployment (defaults to the state directory's id) |
| `--account-wide` | scope by tag presence instead of deployment id; only safe for a single deployment per account |
| `--role-arn`, `--kms-key-arn` | the profile's role for `PassRole` scoping; the full key ARN when the configured key is a bare id or alias |

### `billet migrate workflows [--path DIR] [--repo OWNER/NAME] [--map LABEL=TIER]... [--rightsize FILE] [--public] [--write] [--open-pr]`

Point a repository's workflows at this deployment's tiers. It reads `.github/workflows/*.yml` and `*.yaml` in a local checkout (`--path`, default the current directory) and rewrites each `runs-on` that names a GitHub-hosted label to the tier that matches it. It edits the value's bytes and nothing else, never re-serializing the YAML, so comments, quoting and formatting survive; a value whose bytes are not the label where the parser says it is (an escape, a block scalar) is left alone and said. With neither `--write` nor `--open-pr` nothing is written: the diff, which `git apply` takes, goes to stdout and the report of every `runs-on` to stderr.

| Flag | Meaning |
|---|---|
| `--path` | the checkout to read |
| `--repo` | the repository as owner/name; without it, it is read from the checkout's `origin` remote. Only tiers of a target serving it are chosen from, and a repository no target serves is refused |
| `--map` | use this tier, named by its label, for this label, in place of the choice; may be repeated, and is how a larger runner's or a self-hosted runner's own name is mapped. A tier the repository's targets do not have is refused |
| `--rightsize` | also apply the recommendations in this file, the output of `billet jobs rightsize --json`. A job moves only when the name GitHub shows for it is the report's (a name that is an expression is never one), it has no matrix, it is on the tier the report judged, and both tiers are one each of this configuration's for the repository and of one family as `billet jobs rightsize` judges it now (every setting but the name, size and capacity the same, and no less disk, shared memory or BuildKit cache), with a known and equal architecture, the recommended one allowing the workflow, and both tiers still the shape the report records them at (a report that records none is refused too), so a report written before a tier changed is judged by the tier as it is; what is written is the configuration's name for it, matched without regard to ASCII case alone. Anything else stays and is said, and a move whose memory rests on the job's own VM's report says so. A file of another schema is refused |
| `--public` | choose for the larger shape GitHub gives a public repository |
| `--write` | edit the files in place, each whole or not at all, keeping its mode; every file and both workflow directories are read again first, and nothing is written if one changed since it was read |
| `--open-pr` | edit them on a new branch `billet/migrate-workflows-<time>`, commit, push that branch alone to `origin` by its full ref (no tags, no submodules) and open a pull request once git reports the branch sent, with your own `git` and `gh`, into the repository, onto the branch the checkout was on, from the branch on the owner of the URL the operator's tooling pushes origin to, after its rewrite rules (origin's configured push URL, else its URL, when that is a path on this machine), with the report as its body on stdin. Refused before anything changes for a dirty checkout (untracked files included, whatever `status.showUntrackedFiles` says), a detached HEAD, a changed workflow git does not track, an origin that names no repository, pushes to more than one, or pushes to another repository of the same owner (a pull request's head names its repository by owner alone), or no `gh`; and before writing, when origin pushes to another repository or through another URL on the new branch, which it names by repository and never by URL. A failure after that says where it stopped and leaves what was done. Billet's App has no contents permission and this command does not ask for one ([ADR-011](decisions/adr-011-targets-and-repository-scope.md)) |

**How a tier is chosen.** From the label: its OS, its architecture, its version (`-latest` means any), and the shape GitHub gives a job on it, as its reference gave them on 2026-11-03: 2 vCPU and 8 GB on standard Linux in a private repository and 4 and 16 in a public one, 1 and 5 on `ubuntu-slim`, 3 and 7 on macOS, 4 and 14 on `macos-*-intel`, 12 and 30 on `macos-*-large` and 5 and 14 on `macos-*-xlarge`, the last two documented rather than measured. The smallest tier serving the repository whose OS, architecture and version are the label's and whose vCPUs and memory hold that shape is chosen; a trusted tier must list the workflow. From the tier: its `arch`; failing that arm64 for a macOS guest or tart alone; failing that the word every image it can boot names (`x64`, `amd64`, `x86_64`, `arm64`, `aarch64`), and its version from an image's `ubuntu-2404` or `macos-15`, or the macOS name in it. A tier none of that settles has an unknown architecture and is never chosen by guessing: the report says to name `arch` on it or pass `--map`.

`.github` and `.github/workflows` must be directories, not links, and each edited file is read back before it is offered: it must be the same workflow with exactly the edited values changed to exactly the labels meant, or nothing in it is changed. A label that would read back as something else bare, such as a tier named `null`, is written double-quoted. **What is reported and left alone:** an expression; a `matrix` value (`runs-on` reading one lists each hosted label in it and what it would become, since a leg's label also picks what its steps expect); a runner group; a list of several labels; a label passed to a reusable workflow as an input (the called workflow's own `runs-on` is rewritten in its own file, and the caller has none); a YAML anchor or alias, on the `runs-on` or on the job, and a job that takes its keys from another mapping with `<<`, which other jobs may share; a Windows label, `xcode-*`, and `macos-13` and older, which ran on Intel and are retired; a name this does not know; and a label no tier fits, with what was passed over. One already on a tier is listed as such.

### `billet github-app create`

Create the GitHub App in a browser, install it on the organization or the repository, write the five identity scalars into an existing config in place, and save the private key beside it. Refuses everything it can before touching GitHub, because the key is issued once. For an organization the App asks for metadata read and organization self-hosted runners write; for a repository it asks for metadata read and repository **administration write**, the only permission GitHub offers for the job, and the command says so. The manifest form follows the owner's account type, resolved before the browser opens.

| Flag | Meaning |
|---|---|
| `--org` or `--repository` | the organization, or one repository as `owner/name` (exactly one) |
| `--target` | which target the App serves: `default` writes `github:`, any other name writes the `targets:` entry of that name, creating it when absent (default `default`) |
| `--config` | the `billet.yaml` to write the identity into |
| `--key-path` | where to write the key (default: beside the config, `app-private-key.pem` for the default target and `app-private-key-<name>.pem` otherwise) |
| `--name` | a suggested App name |
| `--no-browser` | print URLs instead of opening a browser |
| `--actions-read` | request `actions: read` (default `true`), which default-branch cache publication needs to prove a job's branch from GitHub's record of its run; `--actions-read=false` leaves it out |
| `--actions-write` | request `actions: write`, which a tier with `retry.disrupted` needs to re-run a job billet disrupted. It includes read, and GitHub's grant also covers dispatching workflows and deleting logs, artifacts and caches, none of which billet does |
| `--port` | a fixed loopback callback port, for `ssh -L` |

### `billet broker serve --config broker.yaml`

Hold App keys for deployments that hold none, and mint their installation tokens over mutual TLS, for what each deployment's registration names and nothing else. [ADR-025](decisions/adr-025-installation-tokens-from-a-broker.md) says why, and [Configuration](configuration.md#the-token-brokers-file) states the file.

### `billet broker client-key [--config PATH] [--show] [--new-deployment]`

On a control-plane host configured with `server.token_broker`: make the key this host proves its deployment with, at `client_key_path`, and print the deployment, the key's fingerprint and the stanza to register at the broker. It refuses to replace a key that exists, because the broker knows it by fingerprint; `--show` prints an existing key's. An active-passive pair runs it on each host and registers both.

### `billet github-app store-key --from <path> [--target NAME]`

Publish an existing App private key into a store-backed deployment (`server.identity.backend: aws-ssm`), at the `default` target's parameter or at the named target's (`github-app-key-<name>`).

### `billet check`

Validate the config and the state directory, prove every target's App key signs a JWT GitHub accepts and its App is installed with exactly the permissions requested for that target's scope (one `target` line per target when there are several; the worst verdict is the report's), check every trusted tier's runner group (a repository target's tiers say the group is not probed and why), say what this node's guests will get from the site's store, count a Ceph node's kernel RBD mappings by what accounts for each and name any cache volume mapped for more than six hours that no cache session holds (reported, never failing the check; run as root, since the custody records are root's, or it says it could not tell), and report registered nodes, images, backups and cloud cost peaks. Works while the control plane is running. A node carrying `node.ebs_s3` with no `node.cache` listener fails the check: that store backs nothing else, so every job would run on the instance's root volume and publish nothing.

| Flag | Meaning |
|---|---|
| `--authorize` | also dry-run a launch against AWS to prove the ec2 role may `RunInstances` |
| `--maintenance-probe` | the host-upgrade transaction's quiescent probe: cross the maintenance fence, skip every network call |

The report names the host's converge guard when one is held: informational under a day, a `WARNING` naming `billet converge-guard recover --holder H --old-driver-stopped` past it, and a `WARNING` for a hold that never returned from its publication or a record whose time cannot be read. Nothing expires a guard; the warning is the reminder.

On a control plane with live hosts registered it also marks a tier `UNPLACEABLE` when no live host can place its shape: none runs one of its providers, admits its guest OS, has a macOS slot for a macOS tier, or is large enough for the shape it would charge. Such a tier advertises and is assigned work all the same, and its jobs wait until a host that fits registers. Advisory; the check does not fail on it.

On a Firecracker node, a `mirrors` section says what its guests pull through. For each of `docker.io`, `ghcr.io` and `quay.io` it says the mirror answers, trusting their authority (`node.registry_mirrors_ca`, or the one the host role installed) as a guest would, or `NOT ANSWERING` and why, which costs guests the saving and no job; a maintenance run says it probed nothing. With no mirror configured it says `NO DOCKER HUB MIRROR at site <site>` and what limit that leaves the site under. Both are advisory. The check fails only on an authority it cannot hand a guest: a file it cannot read, or one holding anything but CA certificates.

After the tiers, an `npm` line says which tiers enable the npm cache ([ADR-020](decisions/adr-020-npm-registry-interception.md)), which a node serves only when it has `node.cache`, or `NO NPM CACHE` when none does: the cache is on for every firecracker Linux tier unless it writes `cache.npm.enabled: false`, and without it every job fetches the registry itself, so a stall on the way fails each job that meets it. It reads the configuration and probes nothing; a file with no tiers, a fleet node's, prints no `npm` line. Advisory; the check does not fail on it.

On Linux it also says whether needrestart, which unattended upgrades run after every package upgrade, leaves billet's services alone: nothing when needrestart is not installed, the file carrying `$nrconf{override_rc}{qr(^billet-)} = 0;` when one does, a `WARNING` naming `/etc/needrestart/conf.d/90-billet.conf` when none does, and could-not-tell when a configuration file cannot be read. It recognises only that line, so a host kept safe another way still reads as the warning.

A release build also says, on a `manifest` line, which release manifest produced it, the way a rollout reads the host: the manifest's digest when the host's record proves this binary's bytes; that nothing records one (a package install, a binary supplied by hand), so a rollout reads the version alone and `billet status` shows `NAMED NO MANIFEST` until `install.sh`, the host role or a rollout's upgrade records it; that the record names other bytes, when something replaced billet without recording it; or that it could not tell. It decides nothing.

On a Firecracker node it also reports, for each image the tiers boot, the generation they boot and the versions of the left-out components it was completed with, what its image left out that `images.accept` does not accept, what it lacks that `images.accept` accepts and what will complete it (the refresh timer, a pull by hand when `release.automatic` is false, moving a pin, or verifying a newer generation that already matches and speaks this billet's guest contract), a tier naming a generation that does not exist, and, unless `--maintenance-probe` is set, whether the channel's image is one this billet can import or needs a newer billet. All of it is reported, never failing the check ([Components the image leaves out](../operating/guest-images.md#components-the-image-leaves-out)).

On a Linux node it also says whether `node.lock_dir` outlives the node's stop: a `WARNING` when `billet-node.service` still declares it, or a parent of it, as a `RuntimeDirectory`, which systemd removes at every stop of the node under the locks other processes hold there (an image verification's among them); a `WARNING` when it is not `/run/billet/locks`, the one directory the node unit makes writable for its lock and the one spelling `billet local up` accepts, or when that path is a link to somewhere else; a `WARNING` when the directory does not exist, since the node unit will not start without it; nothing when the unit is not installed; and could-not-tell when systemd or the filesystem could not be asked. The node unit this release ships names the directory in `ReadWritePaths` and a tmpfiles.d entry creates it at boot, but a host a rollout upgraded keeps the units it had until the package is installed or the host role converges it.

## Running the services

### `billet local status|up|down|uninstall`

Manage the systemd units (Linux) or launch agents (macOS). `status` reports what the service manager actually has loaded. `up` runs `billet check`, starts the server, then the node, proves each held its process, then enables them; it writes no units on systemd and writes the agents on macOS. `up` exits 2 when the services are up but admission could not be reopened (an operator's seal, or a seal it could not read), so the host is running and takes no work until `billet resume`. `down` seals admission, waits for running work, stops the node, stops the server and disables both. `uninstall` is `down` plus forgetting the services, leaving the data.

| Flag | Applies to | Meaning |
|---|---|---|
| `--dry-run` | up, down, uninstall | report and change nothing |

### `billet local prepare`

The privileged bootstrap the package's postinstall, `billet local up` and the host role run (Linux, as root): it moves this host onto the global authority exclusion, or repairs its metadata, and publishes the authority's status back to the caller, which refuses whatever a closed (retired) authority forbids. | Flag | Meaning |
|---|---|
| `--account` | the service account the units run as |
| `--group` | the service group (defaults to the account's name) |
| `--wait` | how long to wait for a lock another billet holds (default `1m`) |

### `billet local unit-paths`

Say which host paths the command a shipped systemd unit runs needs, and how (Linux): `billet local unit-paths [--json] <unit>` for `billet-images-refresh.service`, `billet-node.service`, `billet-server.service` or `billet-backup.service`, the units whose sandbox is `ProtectSystem=strict`. Each path is `read` (a file it opens), `write` (a directory it creates entries in), `private` (a directory in the unit's own `PrivateTmp`, whose writes never reach the host's) or `lock` (a lock it takes), with what the command does there; a lock named for a deployment identity the host has not minted yet is said to be unknown. Every path is built by the functions the command itself calls, so it is the list a drop-in that narrows or widens a unit's sandbox has to keep permitting. With `--exercise` it performs each access the way the command does, creating what the command would create (a missing directory, a deployment identity where the command would mint one, its lock files), and exits non-zero naming every path it could not reach: run as a unit's `ExecStart` in place of its command, it proves that unit's real sandbox permits what the command does, which is what `scripts/test-unit-sandboxes.sh` does with the packaged units on real systemd. An exercise runs as the unit's own account and refuses root for a unit that runs as its service account (`sudo -u billet billet local unit-paths --exercise billet-server.service`), since what it creates beside the ledger would otherwise be root's. A marker never writes over anything: it is created exclusively, never through a link, and its name begins `billet-unit-paths-`. A directory configured through a `..` is refused as could-not-tell, since after a link it names one directory to the kernel and another to a path joined from it, and its command may write either.

| Flag | Meaning |
|---|---|
| `--json` | print the paths as JSON |
| `--exercise` | perform each access instead of reporting it |
| `--marker` | with `--exercise`, leave a file of this name (beginning `billet-unit-paths-`) in each writable directory, so whoever is outside the unit's sandbox can see where the write landed |
| `--units` | print the units billet declares, in the order a fresh host runs them (the server, the node, then the timers' units), and nothing else |

### `billet local backup|restore|recover`

On a PostgreSQL ledger the ledger travels as `pg_dump`'s copy, and restore and recover put it back with `pg_restore`: the PostgreSQL client must be installed at the server's major version or newer, and its absence is refused before anything is written. ## Sharing the uplink

### `billet uplink shape [--interface NAME] [--reflectors A,B,...] [--max-up MBIT] [--max-down MBIT] [--gateway ADDR|none]`

Keep this host's own traffic, its guests' included, from filling the queue of the internet line it shares with the rest of its site. It runs until stopped, as root, on Linux: CAKE on the interface (the default route's unless `--interface` names one) in both directions, each starting at 25 Mbit/s when nothing has been learned, never at the interface's speed. Twice a second it pings the reflectors (by default 1.1.1.1, 8.8.8.8 and 9.9.9.9, three operators, a delay counting only when most of them see it) and reads what the interface moved. A direction is cut only while it is busy with this host's own traffic, on either of two signs that the line is full. When 3 of the last 6 rounds came back more than 15 ms above each reflector's idle baseline, it is cut to below what it was moving, more deeply the higher the delay. When probes went unanswered in at least 2 of the last 6 rounds, from most of the reflectors between them, and in this round too, it is cut to three quarters of what it was moving: a gateway that drops rather than queues shows a full line as loss, and barely as latency. Unless the reflectors confirm a queue by themselves (their delay over 15 ms in 3 of the last 6 rounds, this one included), a loss, a gateway stall or a rise not yet confirmed is blamed on a direction only while it moves at least a tenth of its rate, or of the line it found when that is lower, so a direction carrying a trickle is not cut for a loss somebody else caused (#592: the reference node's two such cuts moved about 3% of their line). A line that drops rather than queues and stands under a tenth of the rate, because it shrank, because LAN traffic raised the rate before any line was found, or because the traffic overruns it in bursts too short to reach a tenth over two seconds, is then cut for only once the rate comes down; a line that queues is still cut for on its delay. An unanswered probe is a loss and never a delay, so a round most reflectors missed has no delay, and a cut taken in it logs `delay=unmeasured`. While a direction runs at its rate, a round measures a delay under 15 ms and the last 6 rounds show no dropping line, its rate rises: 4% a step back up to nine tenths of what it was moving at its last cut, where the line was last found full, and from there 2% at most every ten seconds; near that line, and before any cut has found one, only while it moves nine tenths of its rate, so a rate the line itself stops short of climbs no further. What a direction moved is taken as its line only when it was moving at least half its rate and at least a twentieth of what the other direction moved, so an upload carrying a download's acknowledgements, about 2 to 3% of it, is cut with the download and keeps the line it found. On a line whose upstream is under a twentieth of its downstream (1000/35 cable plans) a full upload looks the same while the download is busy, so its line is found while the download is quiet and kept from then on, and until then it climbs back as one with no line found. A round with no measured delay never raises a rate, a round that counted no reflector neither cuts nor raises, and a reflector silent for ten seconds stops counting until it answers again (when none answers for that long the journal says it cannot tell, and says so again when they return). Nothing about the line's speed has to be configured: a gateway that drops rather than queues is found by overrunning it until the loss rule sees it, and the slow climb near where it was found keeps that to a few seconds now and then rather than at every climb. `--max-up` and `--max-down` set an optional ceiling in Mbit/s that a direction never rises past (0, the default, is the interface's speed; anything else must be at least 10). It also asks the default route's gateway each round, and follows it when the route moves (`--gateway` names another IPv4 address, which is not followed, `--gateway none` asks none, one it cannot look up is logged and left out, and one that is also a reflector is asked only as a reflector): the gateway's own rise more than 15 ms above its baseline, confirmed by another high reading at most four rounds (two seconds) before it, one quiet reply between them or not, though two in a row end the stall, so a lone spike cuts nothing, counts as the reflectors' delay does, cutting a busy direction, each pair with no reply read between covering at most one earlier round too, the nearest that counted a reflector, its first reading's included, so a gateway answering one probe in three still cuts and two pings alone never do, while any high reading holds a rate and keeps a queue from reading as gone and a quiet reading clears a stall unless a high one stands just before it, the deeper of its confirmed rise (the lesser of its two readings) and the reflectors' delay setting the cut, but only in a round that counted a reflector, and judged against its own delay at the cut, on two readings too, as a cut is judged by the reflectors' loss only when its line was dropping; its unanswered probes are never loss, because a gateway answers ICMP only when it has the time, though while it stalls a round it gave no reading in is not clear, until it has been silent ten seconds and stops counting. A rate near the interface's speed is not taken as a full line: the shaper cannot tell a line as fast as the interface from a slower one, and a slower one that drops shows as the reflectors' loss. Every rate it sets, where each direction last found the line full, and the rates in force again every minute and as it stops, are kept in `/var/lib/billet-uplink/learned` (the unit's `StateDirectory`, not the `/run/billet-uplink/` its record of the interface lives in), and the next run, after a restart, an upgrade or a reboot, starts each direction there as it was, however long it was down, but no higher than nine tenths of the line found, and a record written before the line was kept, by a shaper that started each run at its ceiling and recorded that before measuring anything, counts as nothing learned (the journal says `resuming the rates an earlier run learned`); rates learned on another interface are not used (within one boot the kernel's index for it decides; across a reboot, which renumbers interfaces, its name, and its hardware address as it was at the last record where both boots' are known; and when either boot's identity cannot be read, the name and the index both), the file is installed so a power cut leaves the last whole record, and a rate learned above a ceiling since lowered starts at that ceiling; with nothing usable a direction starts at 25 Mbit/s. Each change sets both directions from the shaper's own state, so a rate set by hand with `tc qdisc change` lasts only until its next cut or rise in either direction; a lasting limit is `--max-up` and `--max-down`. Every five minutes it also logs `the line since the last report`: the rate CAKE holds and the line found in each direction (`up_mbit`, `down_limit_mbit` and so on), the most and the mean each direction moved (`down_peak_mbit`, `down_mean_mbit`), how many rounds measured a delay over 15 ms, lost a probe, saw the gateway stall or measured nothing (`delayed_rounds`, `lossy_rounds`, `gateway_stalled_rounds`, `blind_rounds`), the cuts taken, and the reflectors' median and 95th-percentile delay, so a day with no cut still says where the line was held and whether it showed a queue. Stopping it removes the shaping, and the journal says so (`removed the shaping this run installed, as it stopped`). So does the installed billet being replaced by an upgrade, after which it exits with an error so the unit starts it again on the new binary; it checks for that once a minute, so the upgrade paths do not wait for it: `billet host-upgrade` restarts a running, enabled `billet-uplink.service` onto the binary it leaves, after a commit and after a rollback, and the host role's transaction stops it and starts it again. A restart of the shaper that fails is reported and never fails or rolls back the upgrade. The host role runs it as `billet-uplink.service`; [the shared-uplink record](records/shared-uplink.md) has the measurements behind it.

### `billet uplink check [--interface NAME]`

Say whether this host can be shaped, changing nothing but loading the `sch_cake` and `ifb` modules: the kernel has CAKE and IFB, and the interface carries no traffic policy of somebody else's. Only qdiscs the kernel assigned (handle `0:`) may be replaced; CAKE, an ingress qdisc and an `ifb-` device count as billet's only when the record a run of the shaper keeps under `/run/billet-uplink/` names the interface, and a `clsact` qdisc never does. The shaper refuses anything else rather than replace it. The host role enables `billet-uplink.service` only where this passes.

### `billet uplink clear [--interface NAME]`

Remove what the record under `/run/billet-uplink/` says a `billet uplink shape` installed, and only that. The record names the interface by its kernel index as well as its name, so the shaping is found on an interface renamed since, a device that has taken the old name is left alone, and an interface that is gone leaves only its IFB device to remove. With no record it removes nothing, because nothing else proves what is on an interface is billet's, and it inspects the interface (the default route's unless `--interface` names one) before saying there is nothing to clear: CAKE, an ingress qdisc or the shaper's `ifb-` device there, or an interface it could not inspect, exits non-zero saying it cannot tell whose they are, with the commands that remove them by hand. A record that exists and cannot be read is an error too, never "no record". It refuses while a shaper runs, and exits non-zero when a removal failed. The unit runs it as `ExecStopPost`, so a crash is cleared too; after an ordinary stop the shaper has already removed its own shaping and its record, so this finds no record and an interface carrying nothing of billet's.

## Acceptance

`billet acceptance` stands an isolated deployment up beside this one against a real account, runs a real job, and destroys exactly what it made. It is never run on a pull request: by hand, or by the `aws-acceptance` workflow, which runs the matrix below weekly and on dispatch from the `acceptance` environment.

| Command | Meaning |
|---|---|
| `billet acceptance up --config <derive-from> --workspace <dir> [--account] [--label-prefix accept] [--region] [--fleet-listen --fleet-bootstrap --boot-prelude]` | derive the isolated deployment from `--config` (read, never written) into a workspace this run owns entirely; `--account` is the AWS account the credential must be in, and `--region` the one `sts:GetCallerIdentity` is asked in (default the config's, or its pool's); a `--workspace` too long for the node's unix socket (103 bytes on macOS, 107 on Linux) is refused here, before anything exists, when the config has a node. A config with a `server.pool` and no node is a pool's run, and needs the three fleet flags: the node wire and the enrollment listener its hosts dial (one address on two ports) and the boot prelude it hands them, which replace the pool's own `join_server`, `bootstrap_addr` and `boot_prelude`; a resume naming other ones is refused |
| `billet acceptance run --workspace <dir> [--jobs 1] [--wait 30m] [--pool-released 0] [--no-teardown]` | run real jobs and wait for that many to reach a terminal outcome; a workspace left sealed, as `--no-teardown` leaves one, is refused before anything starts, naming `billet resume`. A pool's run has no node to start, and `--pool-released` keeps its control plane up that long after the jobs for the pool to release its idle hosts itself, before the seal |

| `billet acceptance matrix teardown-policy --workspace <dir>` | print the IAM policy a run's teardown needs beside the node's own: `s3:DeleteObject` on this deployment's own cache state objects, which `billet decommission` deletes and the node's rendered policy never grants; nothing when the config has no ebs-s3 cache |
| `billet acceptance matrix pool-init-args --config <file>` | print the config's `server.pool.init_args` one flag and its value a line, in `billet init`'s order, less the kernel and Ceph flags a pool prelude sets itself: what the acceptance lane's prelude hands a pool host |
| `billet acceptance matrix pool-host-iam --workspace <dir>` | print the policy a pool's run's hosts need for its deployment: what `billet init iam` prints for a Firecracker node at the site and ebs-s3 store the pool's `init_args` name |

## `billet version [--notices]`

Print the version and the Go version. `--notices` prints instead the licenses of the third-party software the binary contains: every Go module it links, Go's own, and the upstream files it embeds. The release archives carry the same file as `THIRD_PARTY_NOTICES`, and the packages install it as `/usr/share/doc/billet/THIRD_PARTY_NOTICES`. A release names itself by its tag, `v0.9.2`, whichever way the build stamped it; releases through v0.9.1 printed `0.9.1`, and every guard that ordered releases read that as not a release.
