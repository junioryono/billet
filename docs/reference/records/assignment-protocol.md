# What GitHub.com does with an assignment

On 2026-10-21 billet measured, against GitHub.com, the behaviour [ADR-012](../decisions/adr-012-steady-advertisement.md) rests on and GitHub does not document: how long an assignment nobody runs is kept, whether capacity that appears is used at once, what the advertised ceiling counts, whether lowering it takes an assignment back, what a cancellation looks like, whether a new session's statistics restore a backlog, whether one message carries every assignment it counts, and how many message sessions one installation may hold (#140). It is a record of what GitHub answered on that day, not a promise about what it will answer.

## How it was measured

`TestLiveAssignmentProtocol` (`internal/integration/assignmentprotocol_live_test.go`) drives one measurement per run against a throwaway scale set of its own, through billet's own scale-set client: it opens a message session, polls at a scripted capacity, acknowledges every message, dispatches a workflow whose one job sleeps on the scale set's label, and writes every message, failed poll, statistics block and job status, with the time it was received, to a JSON report. It records rather than asserts, and it fails only when the mechanics a finding rests on did not happen. It starts no runner except in U2, which starts one `ghcr.io/actions/actions-runner` container on a single-use registration for the first job assigned.

What the report holds is what billet's client decoded, not the raw payloads, and an error the client retried and recovered from never reaches it: so the findings below are about the fields billet reads and the failures it would see, not about every byte or status code on the wire. Times are from the start of each probe, and an event's time is when the probe received it, not when GitHub acted.

The App was a billet App installed on a free organization that exists only for testing billet; the dispatching repository was private; the probes ran on billet's shared Linux test host, three message sessions at a time except in U7. Each measurement ran once. Afterwards every run the probes dispatched was completed or cancelled (the repository's 54 runs all read `completed`), and all 29 scale sets they created were deleted with `billet teardown --tier <name> --runner-group Default`, each deletion acknowledged by GitHub.

## What GitHub did

| | Question | Measured 2026-10-21 |
|---|---|---|
| U4 | How long is an assignment nobody runs kept? | One job, capacity 1, no runner, for 90 minutes. The probe received the job's assignment 7 s after it started (about 5 s after the dispatch returned), its **cancellation 5 minutes later** (`JobCompleted`, result `canceled`), and a new assignment of the same run under a new job id 1–2 s after that. That happened twice. The **third assignment was not cancelled in the 80 minutes left** of the probe. GitHub's REST API reported the job `queued` throughout, while the message statistics' `TotalAssignedJobs` went 1, 0, 1, 0, 1 with the cycles. |
| U2 | What does the advertised ceiling count? | Capacity 2, five jobs queued, one runner started on the first assignment. **Assigned and running work together never exceeded 2**: with one job running, one more was assigned; when it finished, an unrun job took its place. `TotalAssignedJobs` counted the running job (2 assigned, of which 1 running, at 1m04s), so the two counters are not to be added. The unrun assignments cycled as U4's did, each cancelled about five minutes after it arrived. Two of the four unrun jobs reached a third assignment (at 20m30s and 25m18s) that was still outstanding when the 30-minute window ended; the other two were cancelled twice and not assigned again in the window. |
| U3 | Does lowering the advertisement take an assignment back? | **Not early.** Two jobs assigned at capacity 2, then every poll at capacity 0 for 20 minutes: both cancellations arrived at the ordinary five minutes (5m06s and 5m08s), and **neither job was assigned again** while the advertisement stayed at 0. |
| U4-DROP | The same, with one job | Assigned at capacity 1, the advertisement dropped to 0: its cancellation arrived at 5m07s and the job was **not assigned again** in the remaining 85 minutes. |
| U6a | Is capacity that appears used at once? | One job queued while advertising 0 for five minutes: **assigned 2 s after the advertisement rose to 1.** |
| U6b | Is the last advertisement honoured while a listener is silent? | **Inconclusive.** Phase one's assignment still held the scale set's one slot when phase two's session opened (its statistics said one job assigned), and its cancellation was first seen when polling resumed at 11m03s; when GitHub actually cancelled it is not known, so the queued job may have had nowhere to go whatever the answer. It needs a run on a fresh scale set. |
| C1 | Does a cancellation GitHub makes to reassign look different from an operator's? | **Not in any field billet reads.** Both arrived as `JobCompleted` with result `canceled` and request id 0. After the operator's cancellation GitHub assigned the run's job once more under a new job id and cancelled it in the same message. Whether the raw payload carries a cause billet's client drops was not recorded. |
| C2 | Do a new session's statistics restore an acknowledged backlog? | **Yes.** Two jobs assigned and acknowledged, the session closed and a new one opened: its statistics said `TotalAssignedJobs: 2` (and `TotalBusyRunners: 2`, with no runner registered). |
| C3 | Does one message carry every assignment it counts? | **Yes, here.** Forty jobs queued at capacity 40: one message carried all 40 assignments, and its statistics said 40. |
| U7 | How many message sessions may one installation hold, and what does it say past that? | **Twenty held for an hour with no error billet saw.** Past twenty is unmeasured; see [below](#u7-many-sessions-on-one-installation). |

Every assignment, in every measurement, arrived as `JobAssigned` with `runnerRequestId: 0`, with no `JobAvailable` and no acquisition, as billet has measured since 2026-08-19.

## What billet takes from it

- **An assignment waits while billet buys room for it, within limits.** A job billet has been assigned and has not started is cancelled after about five minutes and assigned again, and in U4 the third assignment, after two such cycles, was kept for at least 80 minutes. So a job queued behind a full fleet is not lost to the protocol, but the churn before that is messages billet must treat as ordinary (`canceled` with no runner), not as failures. ADR-012's open question, how long an assignment is kept once its cycles stop, is answered for at least 80 minutes; what follows a third assignment over a longer wait is not measured.
- **Lowering an advertisement does not take back a fresh assignment; it only stops new ones.** In U3 and U4-DROP the assignments were cancelled at GitHub's own five minutes and nothing was assigned again while the advertisement stayed at 0: which is why the seal lowers the advertisement and the drain counts assigned work separately (#140). What happens to an assignment already in its long-kept third cycle when the advertisement falls is not measured.
- **The ceiling is the scale set's total, running work included,** as `steadyAdvertisement` assumes: advertising what is committed while draining is the right number, and `TotalAssignedJobs` less the runners covering it is the count of work waiting.
- **No field billet reads tells a cancellation's cause,** so billet attributes a `canceled` completion by its own records, never by the message.
- **A restart's view of the queue is right:** a new session's statistics carry the acknowledged backlog, which is what `reportOrphanedBacklog` and the first reconciliation rely on.

## U7: many sessions on one installation

From 09:29 to 10:29 UTC on 2026-10-21, with every other user of the installation kept off it, one App installation held **20 message sessions open at once**, each on a scale set of its own, each long-polling at capacity 0 for the hour: 72 polls a session, about 50 seconds a poll, and **no error surfaced to billet from any open, poll or close**. billet's client retries a throttled or failed request before it reports one, so a 429 or a server error it recovered from would not show here; what this says is that twenty sessions for an hour worked for billet that day, not that GitHub never pushed back. More than twenty, and longer, are unmeasured.

The installation's REST budget was not recorded: the probe asked billet's scale-set client for the rate-limit headers it last saw each minute, and the client exposes none of the message API's, so every sample came back empty. The session limit is what this measured, not the REST budget a deployment's other calls spend.
