# Host rehearsals

Four operations were, until 2026-09-04, proved only against fakes: the host upgrade transaction (`cmd/billet/hostupgrade.go` stops a service, replaces a binary and migrates a ledger, and every test of it supplied a fake host and asserted the order), `billet local recover` over a deployment a real control plane had served, a CA rotation across nodes that renew, and a PostgreSQL promotion under a real partition. This records the harness that now drives each of them on packaged hosts under real systemd, what its first run found, and what has and has not run.

## The harness

`scripts/rehearsal-lib.sh` starts privileged `ubuntu:24.04` containers with systemd as PID 1, the shape `scripts/test-systemd-lifecycle.sh` already trusts, installs a `.deb` into each, issues node certificates as the service account, and asserts on unit state, journals and files. Five drivers, each a `make` target and a job of `.github/workflows/rehearsals.yml` (weekly, and on dispatch; never on `pull_request`, because every one starts a real control plane with a real App's key):

| Target | What it drives | Package |
|---|---|---|
| `make rollout-rehearsal` | two hosts on release FROM moved to release TO by `billet rollout start` alone, the controller through `billet-upgrade.timer` (on a FROM before v0.6.0, the operator's `host-upgrade`), the node through the coordinator's dispatch; then a downgrade candidate that cannot open the migrated ledger proved to roll back with the hosts still on TO | the two published releases |
| `make recover-rehearsal` | a served deployment backed up, moved on, stopped with `local down`, recovered as root; the recovered plane starts sealed with an operator's seal, the node re-registers, `billet resume` lifts the seal, nothing root put back stays owned by anyone but `billet` (the superseded ledger excepted) | the tree's own (`make dist`) |
| `make ca-rotation-rehearsal` | two nodes on twenty-minute leaves (`billet ca issue --lifetime`), `ca rotate`, the control plane restarted to present the overlap, both nodes proved renewed onto the new authority, `ca retire`, both re-registering with the old authority gone | the tree's own |
| `make promotion-rehearsal` | an active-passive pair on one PostgreSQL ledger with short server keepalives, the leader cut off with `docker network disconnect`, the standby's promotion timed, the node re-registering, the old leader proved to stop and return as a standby when the partition heals | the tree's own |
| `make retirement-rehearsal` | an active-passive PostgreSQL pair with a node on A and a separate node; both endpoints moved to B before a retained-node retirement assembled from real inspections, followed by file, unit, receipt, registration, row, journal and read-only re-entry assertions | the tree's own |

Three rules the harness holds, each written down because a review found the rehearsal passing without it: a registration is proved by the controller journal's `node registered node=<name>` line after a clock mark taken before the boundary, never by the name appearing in `billet status`, which prints every node the ledger knows whether or not one has connected; a negative assertion captures the producer's exit status and greps a here-string, because `cmd | grep -q` under `pipefail` and `|| true` both turn "could not tell" into the absence asserted; and a teardown that fails fails the run, since a green rehearsal that left a scale set behind hides the one thing an operator has to act on.

Every rehearsal needs a config whose `github:` block names a working App and the key it points at (`BILLET_REHEARSAL_APP_CONFIG`, `BILLET_REHEARSAL_APP_KEY`) and skips without them; the workflow uses the dedicated acceptance App described in [AWS acceptance](aws-acceptance.md). The architecture is the docker daemon's, not `uname -m`'s, so the harness runs on a Mac's Docker Desktop as well as on `ubuntu-latest`.

## What the first run found

**2026-09-04 (UTC), `make rollout-rehearsal` with FROM=v0.5.0 and TO=v0.6.0, on arm64 under Docker Desktop.** Both packaged hosts came up under real systemd on v0.5.0, the controller claimed its ledger and created the scale set, and the node registered over the real mTLS wire at once. The rollout's first command then refused:

```
billet: imagesource: the manifest's signature does not satisfy this source's policy
  (identity ^https://github\.com/junioryono/billet/\.github/workflows/release\.yml@refs/(heads/release/v[0-9]+\.[0-9]+|tags/v[0-9]+\.[0-9]+\.[0-9]+)$ ...):
  expected SAN value to match regex ..., got "https://github.com/junioryono/billet/.github/workflows/release.yml@refs/heads/main"
```

Every release manifest billet has published is signed as `release.yml@refs/heads/main`, because the cut button runs on `main` and calls the release workflow, and a Fulcio certificate names the requesting workflow under the ref of the run that requested it. The policy in every binary through v0.6.0 accepted only a release-branch or tag ref, on the belief that the workflow runs against the tag. So no shipped billet could verify any release: `billet rollout start`, the automatic starter that v0.6.0 introduced and `billet host-upgrade --version` all stop at that line. The teardown removed the scale set and the run exited non-zero, which is the harness doing what it is for. The fix is the pattern naming the two refs the workflow can run under and a test pinning the measured SAN; it ships as v0.6.1, and a fleet on v0.5.0 or v0.6.0 is moved by the package or the Ansible role once, which install from the release's checksums rather than its manifest.

The finding cost one release cut and had never been visible to a test, because every fixture signs its manifests with whatever identity the test names. It is the kind of defect the rehearsal exists for.

## What the second rollout runs found

**2026-09-05 (UTC), `make rollout-rehearsal` with FROM=v0.8.0 and TO=v0.9.0, twice, on arm64 under Docker Desktop.** The first attempt was killed at 06:13Z by the development machine's memory guard rather than by anything it found, during the controller's own upgrade; its cleanup could not remove the scale set it had created, `rehearse-20260905054234-2vcpu`, which was removed by hand with `billet teardown`. That scale set is the one thing a killed rehearsal leaves outside the machine.

**The second attempt found two defects in `billet host-upgrade`, both present in every release from v0.6.0 to v0.9.0, and the second means no controller with a local ledger had ever been able to self-upgrade.** Both hosts came up on v0.8.0, the node registered at protocol 20, `billet rollout start --version v0.9.0` recorded the rollout, and the controller's root timer began the transaction at 06:17:35Z: `stopped` at 06:17:36, then `fenced`, `snapshotted`, `installed`, `migrated` and into the probe at 06:17:42. It never left it. `runCandidate` ran the candidate with `CombinedOutput`, which waits for the child to exit, while the candidate's `--upgrade-probe` reported ready and then waited at `ctx.Done()` to be stopped by a service manager that had not started it; `billet-upgrade.service` is `Type=oneshot` with `NotifyAccess=none`, so the child had no notify socket and nothing was ever going to stop it. A goroutine dump taken with SIGQUIT at 06:34:44Z, seventeen minutes in, showed the probe's main goroutine at the wait and nothing else, and the control plane was stopped for the whole of it. Killing the probe exposed the second defect: the rollback restored the v0.8.0 binary and recorded `rolled_back`, then failed at clearing the maintenance fence, `fences this ledger for "host upgrade", not "host upgrade rolled back"`, cordoned the host and never restarted its services; the timer's next tick refused on the fenced ledger. The commit path clears the fence with `"host upgrade committed"` against the same rule, so a committed upgrade would have cordoned at the same place, before starting its services. The fake host in `internal/hostupgrade`'s tests ignored the reason argument, which is how both shipped through fourteen ordering tests.

**Fixed in the release after v0.9.0.** The two probe protocols are disjoint by construction, and the candidate says which it speaks. A probe exits zero and prints nothing once it has proved what it can, unless it is passed `--upgrade-probe-hold`, in which case it prints the readiness line and holds until stopped; only the Ansible role's `Type=notify` probe unit passes that flag, because that unit stops the probe itself, and the role passes it only after asking the staged candidate's `-h` whether it lists the flag, so a deliberate downgrade to an older release renders the older shape. The tell is the flag and not the environment: a version of the fix read `NOTIFY_SOCKET`, and a node's detached updater inherits its unit's socket, so a node-dispatched upgrade would have held exactly as before. `runCandidate` asks the same question of the candidate it is about to run: one that lists the flag is judged by its exit status alone, and a readiness line from it is a broken protocol and a refusal; one that does not is a release through v0.9.0, whose line means "stop me" and is the only proof it offers, so one that exits without saying it has proved nothing whatever its status. Such a release answers the stop by exiting zero, through its lifecycle context, so its exit status is its verdict there too, and a death by signal is a refusal whoever sent the signal: a probe that had to be killed has not proved it can stop. Every candidate is sent SIGKILL before it is reaped, because its output closing proves nothing about it being gone: the shipped probes keep their descriptors until they exit, so one whose output has closed is a zombie whose status the kill cannot change, while one that closed its output and kept running is killed and refused, which is the conservative reading. The deadline is the probe's own and not `exec.CommandContext`'s, whose kill runs beside its `Wait` and on a kernel without pidfd is a signal to a number the `Wait` may just have freed (Go's `os` package documents the race); every signal goes through the process handle before the one `Wait`, in the probe and in the usage question alike. A candidate whose exit never arrives after that is one the kernel is holding, and the transaction cordons the host with its journal in place rather than restoring a ledger the candidate may still have open (`ErrUnsafeToRestore`); so does anything still holding the candidate's output once the candidate has gone, or the output of its usage question, because an open pipe proves a descendant is alive and cannot prove it never opened the ledger, and that verdict outranks anything the candidate said or how it exited; a pipe that could not be read to its end is a could-not-tell and cordons the same way. The usage question is bounded on both sides: `billet host-upgrade` gives the candidate's output a grace to close, and the role wraps it in `timeout` and fails the converge on a non-zero exit before any service is stopped. The candidate is never reaped before the last signal it might be sent has gone, so its pid is anchored by the zombie on every platform and a stop cannot reach a process that reused the number; nothing is signalled by process-group number. Anything that still holds the candidate's output when the candidate has gone is found by that output staying open and fails the probe rather than being hunted, which is the limit of what a pipe can tell: a process that closed the output before detaching is not seen. The parent owns that output pipe and reads it to its end before writing any verdict, so a refusal keeps its words; a silent candidate fails at three minutes. The readiness line is matched whole and anchored. The fence is written and cleared under one reason; the harness starts the timer's unit with `--no-block` and prints the upgrade journal when the controller never arrives. `internal/hostupgrade/fence_test.go` lets the real ledger judge the reason, and reverting either clear turns it red. Because the FROM binary is the one that runs the transaction, a controller with a LOCAL ledger on v0.6.0 through v0.9.0 cannot reach the fixed release by rollout: its parent would pass the probe and then cordon at commit on its own fence bug, so it has to be moved once more by the Ansible role or the package (not `install.sh`, which installs to `/usr/local/bin` while the packaged units run `/usr/bin/billet`), and rollouts work from there. A controller on PostgreSQL fences nothing and clears nothing, so its older parent can take the fixed release by rollout; a node-only host has no fence either, but the claim that it could take the fix by rollout applied to launchd only. The systemd launch was not reached by these rehearsals and was refused in production on 2026-09-06, as recorded below.

## What the third rollout run found

**2026-09-05 (UTC), `rehearsals.yml` dispatched with FROM=v0.8.0 and TO=v0.9.1, on a GitHub-hosted amd64 runner (run 33967609724), the first run of the harness off the development machine.** This is the run the previous section predicted: v0.9.1 carries the two fixes, v0.8.0 does not, and the FROM host is the one that runs the transaction. Both packaged hosts came up on v0.8.0 at 13:02:00Z, the node registered at 13:02:58, `billet rollout start --version v0.9.1` recorded the rollout at 13:03:04, and the controller's root timer began the transaction at 13:03:05: `stopped` at 13:03:05, then `imaged`, `fenced`, `snapshotted`, `installed`, `migrated` and `probed` all inside 13:03:10. **The probe passed in under a second**, because the v0.9.1 candidate, passed no hold flag by the v0.8.0 parent, proved what it could and exited zero, which is what `CombinedOutput` was waiting for; the deadlock the previous run sat in for seventeen minutes is gone from the pair. The journal then recorded `upgrade committed from=0.8.0 to=v0.9.1`, and the v0.8.0 parent failed at the next line, exactly as predicted: `the upgrade committed but the ledger is still fenced, so nothing can write to it: state: /var/lib/billet/server/billet.maintenance fences this ledger for "host upgrade", not "host upgrade committed"; billet will not clear somebody else's fence`. `billet-upgrade.service` exited 1, the services stayed stopped, and the harness failed the run at 13:03:15 with `billet-server.service is not active on the controller after its upgrade`. The v0.9.1 binary is installed on that host and its journal says committed; what it needs is an operator, to clear the fence by hand (`billet local` has no command for a fence of this reason) and start the services, because the binary that should have cleared it was the old one. The previous section's one manual move to a fixed release exists so that a fleet never reaches this state. So the claim stands proved from both sides: a local-ledger controller on v0.6.0 through v0.9.0 passes the probe against a fixed candidate and cordons at commit, and the one manual move to a fixed release is not optional. The first green rollout run needs FROM at or above v0.9.1, which means the release after it.

**The same run passed the other three rehearsals on amd64, the first time any of them ran off arm64.** Recover in 559 seconds (13:03:15Z to 13:12:34Z), the served deployment backed up, stopped, recovered as root, restarted sealed and its node re-served; CA rotation in 941 seconds (13:12:34Z to 13:28:15Z), both nodes' installed certificates carrying the new issuer after a renewal wait of 796 seconds against twenty-minute leaves, the retire dropping the old pair and a fresh bundle vouching for the server; promotion in 178 seconds (13:28:15Z to 13:31:13Z), the standby claiming 20 seconds after the partition on keepalives idle 10, interval 5, count 3, and the node re-registered 60 seconds after the partition. Against the arm64 runs of 2026-09-04, promotion and CA rotation were within 10 and 34 seconds (188 and 907 there), while recover took 171 seconds longer (388 there); this run does not say where those seconds went, and what it proves is that all three pass on amd64, not that the architecture is without effect.

## What the first node dispatch found

**2026-09-06 (UTC), the reference deployment's first unattended node dispatch, reported in [#98](https://github.com/junioryono/billet/issues/98).** The v0.9.2 control plane recorded rollout `c7b50db155166e05` to v0.9.2 at 09:01:22Z, settled itself at 09:01:51 and dispatched its v0.8.0 systemd node at 09:02:21. The updater refused `open the upgrade transaction lock: open /var/lib/billet/upgrades/transaction.lock: read-only file system`, and kept refusing on retries every five and a half minutes. The node kept serving and was moved manually with `billet host-upgrade` as root outside its service. This is a production report, not a successful rollout rehearsal.

The child inherited `billet-node.service`'s `ProtectSystem=strict` mount namespace, which makes the upgrade root, `/usr/bin/billet`, the units and the config read-only. A detached session also remains in the service's cgroup, where `KillMode=mixed` kills it when the updater stops the node. The fix starts `systemd-run --no-block` with a transient root oneshot named `billet-host-upgrade-<rollout>-g<generation>`, outside both boundaries, and carries acceptance or refusal over a Unix socket in the node's writable state directory. Launchd keeps its measured `setsid` launch and uses that same socket.

**The starting node must already carry the fix.** Every systemd node on a release through v0.9.2 needs one manual `billet host-upgrade --version <tag> --manifest-sha256 <digest>` as root outside the service, or one role converge with `billet_version` pinned, onto the release carrying the fix. FROM=v0.9.2 and TO=a fixed release still dispatches with v0.9.2 and cannot prove unattended node convergence. The unchanged rollout rehearsal needs a published FROM carrying this fix and a later TO to prove both hosts move and the downgrade rolls back. That run remains pending; process tests of the transient launcher and socket do not prove systemd's real host transaction.

**A focused launch-boundary probe passed on 2026-09-06 at 17:42Z, Ubuntu 24.04 arm64 with systemd 255.4-1ubuntu8.17.** A throwaway program calling this tree's `ExecUpgrader` ran in a root parent unit with `ProtectSystem=strict`, `PrivateTmp=true`, `KillMode=mixed` and only its state directory writable. Its transient updater received a fixture ledger variable through `--setenv=NAME`, answered over the Unix socket, stopped the parent with `systemctl stop`, and wrote a proof file outside the parent's writable paths after the stop returned. The parent recorded the acceptance, both units exited successfully, no acknowledgement socket remained, and the container was removed. This measures environment forwarding, socket reachability across the mount namespaces, and survival of the parent's stop; the program did not run the actual `host-upgrade` transaction or install a release, so the full rollout rehearsal above remains pending.

## What the first recover runs found

**2026-09-04 (UTC), `make recover-rehearsal` three times on this Mac, each stopped by something it exposed, none yet reaching the recovery itself.** The first run died in the harness before a host was up: `aliases[@]: unbound variable`, an empty array expanded under `set -u` on the Mac's `/bin/bash` 3.2, and it exited 0, because on that shell a `set -u` abort reaches the EXIT trap with `$?` of 0 (bash 5.2 and 5.3 report 1; measured with a probe). The harness now initialises a sentinel to 0 before its traps, sets it to 1 as the script's last statement, and fails any run that reaches the trap with status 0 without it. The second run got both hosts up and was refused by `billet local up`: the acceptance App had been given `actions: write` so the acceptance lane could dispatch a workflow, and `billet check` refuses an App whose installation holds a permission billet never requested; the dispatch is a second App's job now and the acceptance App is back to the two permissions the manifest flow asked for. The third run commissioned the deployment, registered the node, took the backup and moved the ledger on, then `local down` was refused: `the ledger is fenced for host maintenance`. The journal explains it: a minute after boot the control plane logged `started a rollout, because the stable channel advanced` from `0.0.0-SNAPSHOT-…` to `v0.6.0`, because a snapshot build reports a release the channel is not on and the deployment said nothing about `release:`, so it was on automatic updates; the packaged root `billet-upgrade.timer` then began the host transaction, fenced the ledger and started replacing `/usr/bin/billet`, which is also why the teardown's `billet teardown` found the binary unrunnable and left the scale set behind (removed by hand with `billet teardown --tier … --runner-group default`). The recover, CA rotation and promotion rehearsals now write `release: {automatic: false}`, since the thing they rehearse is not a rollout, and `billet acceptance up` writes it into every derived config for the same reason: an acceptance deployment proves the tree it was built from, never the channel. The rollout rehearsal keeps the default, because the default is what it rehearses.

**The fourth run passed, 2026-09-04 05:31 to 05:37 UTC, on arm64 under Docker Desktop, package `0.0.0-SNAPSHOT-6fa05f3`.** Both packaged hosts up under real systemd; the deployment commissioned by `billet local up` with the acceptance App, the node registered over the real wire within a second of starting; `billet local backup` took the archive; the ledger moved on; `billet local down` asked the node what it was running (an empty answer twice, the compute barrier's proof) and the harness proved `billet-server.service` stopped afterwards (inactive or failed is the assertion; the transcript said inactive); `billet local recover --old-controller-fenced` as root planned and then replaced the ledger, keeping the one that was there as `billet.db.superseded-2026-09-04T05-32-12Z-2c512640` (asserted non-empty), and left the deployment sealed by an operator's seal; `billet local up` started it and the harness proved the service active and `billet status` reporting the deployment sealed by a seal that survives a restart, as the restore rehearsal said it must; the node that had trusted the old ledger registered with the recovered one at once (the server journal's registration line after a clock mark); `billet resume` lifted the seal and `status` no longer reported it. The harness's ownership scan found no entry in the state directory owned by anyone but `billet` once names matching `billet.db.superseded-*` are excluded, which is the whole of that assertion. The transcript also showed the service disabled by `local down` and the backup and upgrade timers enabled and armed by `local up`; those two are observed output, not assertions. 388 seconds from the first container to the PASSED line, and the teardown removed the run's scale set. What this proves that the in-process suite could not: the recovery runs as root over a directory a real service account owns, on a ledger a real control plane served, and the plane that comes back is the sealed one the design says it must be.

## What the CA rotation runs found

**2026-09-04 (UTC), `make ca-rotation-rehearsal` four times on this Mac, arm64, on the tree's own package.** The first run got all the way to the retire: a controller and two nodes up under real systemd, twenty-minute leaves issued with `billet ca issue --lifetime 20m`, both nodes registered, `billet ca rotate` minted the new authority (the transcript showed its subject carrying `billet-replaces:` and the old fingerprint; the harness asserts only that the subject changed), the control plane restarted to present the overlap, and both nodes renewed onto the new authority 765 seconds after the rotation, each renewal proved by the issuer and the changed serial of the certificate installed on that node (the transcript's journal lines put both on the same sweep, which is observed, not asserted). Then `billet ca retire` ran without `--force`, printed the confirmation an operator is meant to read ("This rotation started 0s ago", which is fourteen minutes rounded to the hour) and exited 0 having retired nothing, and the harness's assertion that `ca-previous.crt` was gone failed the run. The harness had just proved both renewals from each node's installed certificate, which is the check `--force` asserts, so it passes the flag now. The second run passed its own assertions: both nodes' installed certificates carried the new issuer and a new serial 808 seconds after issue and 787 after the rotation (a twenty-minute leaf renews when a third of its life remains, at 800; the harness polls every five seconds), `ca retire --force` ran, `ca-previous.crt` was not found afterwards by a check that could not tell absence from a failed `docker exec`, the control plane restarted and both nodes re-registered with it, a bundle issued afterwards verified the server's certificate while the original node certificate verified only against the bundle it came with, and the teardown removed the scale set; 905 seconds. A review pointed out that an orphaned `ca-previous.key` is ignored by `LoadServing` and would refuse the next rotation, and that the second run could not say whether the key was gone. The third run asserted both files of the previous pair absent, by the same "fail if present" shape, and passed the same way in 928 seconds. The fourth run is the one the proof rests on: it proved each file of the previous pair absent positively with `test ! -e`, its renewals came 809 seconds after issue and 788 after the rotation, the control plane restarted trusting only the new authority and both nodes re-registered with it, the fresh bundle verified the server and the original certificate did not, the teardown removed the scale set, and it took 907 seconds end to end. Measured, too: `ca retire`'s age rounds to the hour, so a rotation younger than thirty minutes reads as "0s ago".

## What the promotion runs found

**2026-09-04 (UTC), `make promotion-rehearsal` six times on this Mac, arm64, on the tree's own package.** Runs one and two failed at the same line and for a reason the transcript did not name: the identity archive taken on controller A could not be extracted on controller B because B, which had never run `ca issue`, had no `/var/lib/billet/server` to extract into (the harness creates it as the service account now, 0700, before the extraction). Every run through the fourth also printed `local: can only be used in a function` against a here-document's line, once per controller: a backtick pair around the words `local down` in a YAML comment inside an unquoted here-document, where a backtick pair is a command substitution, so bash ran `local down` at the top level of the script and substituted nothing; the comment is plain words now. Run three was refused by `billet local up` on both controllers: the harness had supplied the DSN through a systemd drop-in, and `local up` refuses a billet unit with an effective drop-in, as the host transaction does and as the PostgreSQL deployment guide says the host role avoids by rendering a whole unit; the harness renders a whole unit from the packaged one now. Run four's harness waited for A's journal to say `claimed this deployment's controller`, which a `controllers: active-passive` server never says: the first controller logs `standing by` and then `promoted to this deployment's controller` a moment later, because the election path is one path. Run five passed, 201 seconds end to end, and a review of its harness found that its post-heal wait read the whole journal, which A's startup `standing by` line satisfies, so run six repeated it with every post-partition and post-heal journal wait reading the journal since a clock mark taken before its boundary and the claim holder asserted before the partition; it passed in 188 seconds with the same numbers, and those are the ones recorded: A promoted (the harness's first poll found it) and B stood by naming A as the holder; the node registered with A; A was cut off with `docker network disconnect`; with PostgreSQL's `tcp_keepalives_idle=10`, `tcp_keepalives_interval=5` and `tcp_keepalives_count=3` on the server, B was promoted 21 seconds after the partition (the harness polls every five seconds; the keepalive arithmetic says 25) and `billet status` on B named B; the node re-registered with B 62 seconds after the partition; the partition healed, and within ten seconds of the heal A had logged that it was no longer the controller, systemd's restart counter had advanced, and A was standing by for B, with `billet status` on A naming B and B still active (the harness asserts those three in sequence, the first and third from the journal since the heal and the restart from systemd's `NRestarts` counter, and records only the total; the transcript's polls answered at five, five and zero seconds). The teardown removed the scale set. That is the measurement ADR-009 recorded as missing: a dead leader is detected by the database's keepalives, and nothing else in billet has a timer in that path.

## The retained-node retirement

**2026-09-19 (UTC), `make retirement-rehearsal` twice on GitHub-hosted amd64 runners, on the tree's own package, dispatched as `only=retirement`. The first run (35411568410) found a production defect and stopped there, which is the rehearsal working; the second (35413076992) passed in 257 seconds with the fix.** An attempt before both, on this Mac at 00:51:20Z, skipped for want of `BILLET_REHEARSAL_APP_CONFIG` and `BILLET_REHEARSAL_APP_KEY` and measured nothing at all.

The sequence, from the transcript. 01:11:47Z prerequisites and the hosts; 01:13:40Z one identity and one authority on both controllers; 01:13:41Z A started and claimed, B stood by naming A at epoch 1; 01:14:10Z both nodes registered and proved dialling A's address with their installed configurations bound. Leadership handed over at 01:14:11Z: A's server stopped, B promoted at 01:14:17Z at epoch 2, A restarted and logged `standing by for this deployment's controller holder="rehearsal-controller-b (pid 3725)" epoch=2` at 01:14:21Z. The guards prepared, validated and settled on all three hosts. Both node endpoints migrated to B at 01:14:22Z; A's retained node re-registered with B at 01:14:25Z and the separate node at 01:14:34Z, each with a confirmed live incarnation and a written receipt. The reservation was taken at 01:14:41Z against the installed digest, the three real inspections were collected inside it, and the retained-node request went in at 01:14:43Z.

**At 01:16:00Z the command refused, and it was right to.** `outcome: "unknown"`, `reason: "service-operation-effects"`, `state: "intent"`, `why: operation-reactivation: billet-server.service ActiveState="failed" Job=""`. A's journal says what it observed: `Stopping billet-server.service`, then `billet: controller claim: state: waiting for the controller claim: context canceled`, then `Main process exited, code=exited, status=1/FAILURE` and `Failed with result 'exit-code'`.

**The defect is that a standby control plane exits 1 when it is stopped.** `becomeController` blocks in `state.AwaitController`, which returns its context's cancellation when the process is asked to stop; `runServer` returned that error, so the process exited non-zero and systemd recorded the unit as failed. `lifeops.AdmitQuietActivation` requires a stopped server to be `active` or `inactive`, and `failed` is neither, so a retained-node retirement of a standby could not get past its own stop — and no fake had ever produced the state, because only a real service manager records how a process ended. `Restart=on-failure` is why it survived this long: an operator stopping a standby by hand saw it come back and stand by again, and the exit status was invisible until something read the unit's state afterwards. `stoppedBeforeTheClaim` now answers for the claim: a cancellation arriving while this process's own context is done, on a host a successor has not fenced, is the ordinary stop it is, and the error it stands down on is logged rather than dropped, because the claim releases its exclusion through `errors.Join` and a second fault can be attached to it. What makes a clean exit right there and wrong below it is not that nothing has happened — a cancellation inside `ClaimController` lands after the exclusion was taken and can land during the promotion migration — but that the claim's own restore gives the exclusion and the standby latch back, so the deployment is left as the host found it. An adversarial review of the fix found the same defect unfixed for every other error `runServer` can return between the claim and `plane.Run`, including `server.Run`'s whole startup section, whose errors never reach `onlyCancellation`; that is #137 and was found by reading rather than by a run.

**The rerun with the fix passed: 257 seconds end to end, on `0.0.0-SNAPSHOT-dae19cb`, amd64, GitHub-hosted (run 35413076992).** Its shape to the request matched the first run's; what is new is everything after it. The request went in at 01:42:45Z and answered `outcome: "retired"` at 01:44:24Z, 99 seconds later, having taken the whole transition in one call rather than through the survivor-completion path: `stop` at `intent`, `archive` at `stopped`, `rewrite` at `archived`, `restart` at `config-rewritten`, `done` at `node-restarted`, with `row: "done"` completed by the retiring host itself, `receipt: "written"`, `marker: "cleared"` and `settled: true`, the completion bound to the reservation taken at 01:42:44.380172097Z and done at 01:44:19.999106207Z.

What the postconditions then observed on the retiring host: `billet-server.service`, `billet-backup.timer` and `billet-upgrade.timer` each inactive and disabled; the identity directory absent from `/var/lib/billet` and its archive holding a deployment id equal to the survivor's; the installed configuration byte-for-byte the serverless rendering; the retained node registered with the survivor on the first poll, **running on a new systemd invocation** (`34ddbc4de7a2413a9cd3c62830d05775` → `d3ea26eea5204ab7a2bd4db894c64dd9`) with its configuration unchanged since that start, its receipt naming the new installed digest and the survivor's address, and its incarnation confirmed live through the survivor; and the same for the separate node. `rollout status` read through the survivor reported the row `done` for that transition. The read-only re-entry answered `route: "continue"` with `route_why: "this host has a readable journal, so this converge continues the retained-node retirement it records"`, `installed_roles: "node"`, `row_fact: "done-mine"`, identity and authority `unreadable` — which is what an archived identity looks like from the host that no longer holds it — and the controller units stayed inactive and disabled. The teardown deleted the scale set and left no container, network or storage behind.

That is what had never been measured: the command's judgement of a whole retained document whose digests are real bytes, and the transition it then runs against a real service manager. What it still does not measure is a retirement that promotes the survivor (this one retires a host that is already a standby), an interrupted transition's recovery, loaded job custody, or an identity store — the authority is copied between controllers as the promotion rehearsal copies it.

Two further observations from the first run. The teardown's `--abandon-reservation` was refused with `an abandonment is not the way on: a retirement journal exists at intent`, which is the command declining to abandon a transition already begun; the rehearsal's cleanup treats that as the answer rather than an error, and the scale set was deleted regardless (`deleted scale set name=rehearse-retire-20260919011147-2vcpu group=default id=86`). No container, network or scale set survived. The snapshot storage did: `rm -rf` on the host cannot remove the `docker` and `containerd` directories a privileged container's root wrote, so every rehearsal that starts a node has been leaving a temporary directory behind. The teardown empties it as root in a throwaway container of the image the hosts already pulled, and only a directory that survives both attempts is reported.

The driver uses the promotion rehearsal's PostgreSQL ledger and packaged systemd hosts, adds a node section and a Docker daemon to A, and starts both nodes against A's literal address. After their registrations are proved, it hands leadership to B and returns A as a running standby, migrates both node endpoints with `billet node migrate-endpoint`, confirms their incarnations through B and writes their receipts. Guards are prepared and settled before endpoint mutation. The retirement reserves before collecting `release inspect`, `rollout status` and the nodes' endpoint dry runs, with every envelope dated by A's clock; A appears in both `self` and `nodes`, its desired-node digest names the full pre-transition configuration, and `desired` carries that configuration minus `server`, `github`, `targets` and `backup`. No committed report fixture supplies a digest. The request omits `--server-only`; a pending row takes the survivor completion, local acknowledgement and continuation path. The final assertions require A's server and timers inactive and disabled, its identity archived, the exact serverless bytes installed, both nodes live on B with matching receipts and A's node on a NEW systemd invocation with `config_changed_since_start == false` — the restart itself, since a retirement that installed the serverless bytes, refreshed the receipt and left the old process running would satisfy every other equality — the row done and the journal settled, then a settled classification from `server retire --dry-run --json` with A still inactive and disabled. The first run reached the request and stopped there; the second observed all of it.

Two details in the command implementations constrain the ordering. `becomeController` waits for the ledger claim before `serveNodeWire` opens a listener, so a node cannot register directly with B while B is still the standby: the leadership handoff must precede the endpoint move. `node migrate-endpoint` judges the desired rendering but does not install it, so the driver previews the move, installs the rendering and then invokes the migration, as the role does. The driver uses B's observed literal address, present in its certificate's hosts, so no DNS failover assertion substitutes for the address proof. It retires A as a running standby; it does not measure retirement promoting B. The read-only re-entry is the requested classifier proof, not a complete second Ansible converge or an attempted systemd resurrection. The authority is copied between controllers as in the promotion rehearsal; identity-store synchronization, interrupted retirement recovery and loaded job custody are outside this scenario.

A real run needs `BILLET_REHEARSAL_APP_CONFIG` pointing to a billet configuration whose `github:` block names a working App, `BILLET_REHEARSAL_APP_KEY` pointing to its private-key file, Docker serving linux/amd64 or linux/arm64 with privileged systemd containers, `jq`, and exactly one matching package in `dist/`. `make retirement-rehearsal` builds the tree's package through its `dist` prerequisite; the direct script consumes an existing package and downloads no published billet release. EXIT cleanup runs after every started attempt, INT and TERM exit through it, and failure to tear down the scale set makes the run fail. The dispatch choice is `retirement` in `rehearsals.yml`.

## What the harness does not prove

- The hosts are containers on one machine, not two machines: power, network and disk failure domains are shared, and the promotion's partition is a network disconnect rather than a lost link.
- The promotion rehearsal copies the CA directory between controllers by hand; `billet ca sync` needs an identity store the rehearsal does not have.
- No `--abandon` of an interrupted recovery is staged: nothing in `deployarchive` stops a publication mid-way deterministically.
- The rollout's failing candidate is a downgrade, because a rehearsal that runs on the day a release is cut has exactly two releases to work with.
