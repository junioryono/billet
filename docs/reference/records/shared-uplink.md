# The shared uplink

What a morning of failing fetches from the reference deployment's guests turned out to be, measured on 2026-09-11, and what billet changed because of it. The deployment is one EC2 control plane (`billet-control-01`) and one bare-metal Firecracker node (`ubuntu-01`) at a residential site, with billet's own CI running on that node's guests since PR #111.

## What failed

Between 08:30 and 09:00 UTC every CI job that reached the internet beyond GitHub failed, each with a different message: apt's `Connection failed [IP: 185.125.190.83 80]` against `archive.ubuntu.com`, then over HTTPS `Could not wait for server fd - select (11: Resource temporarily unavailable) [IP: 185.125.190.82 443]` (apt's own 30-second bound expiring on a stalled connection), a `TLS handshake timeout` from Docker Hub, and `read: connection reset by peer` from `proxy.golang.org`. A probe run from a guest at 08:19 UTC had been clean. The operator reported the same "clogging" from a laptop at the same site.

## What was measured

**The mirror outage, from three unrelated networks.** From the laptop (a residential fiber connection), from the control plane (AWS us-west-2) and from a fleet guest, every one of the nine IPv4 addresses `archive.ubuntu.com` resolves to refused TCP port 80 for hours (`curl --max-time 6` returned no connection to any of them), while `deb.debian.org` and `example.com` answered on port 80 at once. Over 443 seven of the nine answered, two of them slowly (1.5 to 3.2 seconds to a first byte from the AWS side), and `185.125.190.82` and `.83` answered on neither port. The laptop's `curl http://archive.ubuntu.com/` succeeded only because it has native IPv6 and the AAAA answers were healthy; a guest has no IPv6 route and the control plane no IPv6 address, so both saw a mirror with no working address. A status aggregator recorded Canonical incidents for `archive.ubuntu.com` and `security.ubuntu.com` (and `lists.ubuntu.com` and Landscape) through the same hours. Nothing at the site caused this, and nothing at the site could have fixed it.

**Where a guest's traffic goes.** From a guest, `https://www.cloudflare.com/cdn-cgi/trace` reported `warp=off` and the site's public IPv4 address, `ifconfig.me` the same address, and `ping -M do -s 1472 1.1.1.1` succeeded, so the guest's egress is plain NAT through the node onto the site's residential gateway with a 1500-byte path MTU; the node's WARP connector carries only the Zero Trust ranges (its device profile is in Include mode) and none of the guest's traffic. Idle, the path was clean: 7 ms to `1.1.1.1`, DNS answers in 8 to 13 ms serially and a burst of 300 concurrent lookups through the bridge's dnsmasq at p95 6 ms with no failure, five TLS handshakes each to Docker Hub, `proxy.golang.org`, GitHub and the GitHub container CDN all under 0.2 seconds, 100 parallel HTTPS requests all answered under 0.7 seconds, and zero retransmits or SYN retries in the guest's TCP counters. One of five HTTPS attempts against `archive.ubuntu.com` stalled the full 15 seconds, on the Canonical address that answered nothing.

**What the two hosts at the site share.** The node and the laptop sit on one LAN behind one residential gateway (a fiber gateway at 1 Gbps, no WAN drops or errors in its counters, 25 days up), and every guest's connection is one entry in that gateway's NAT table beside the laptop's. That class of gateway is documented by its users to cap its NAT table at 8192 sessions on older firmware and 32767 on newer, and to drop new connections as it approaches the cap, which reads at a laptop as pages that stall while existing connections keep working. The session count is on the gateway's diagnostics page behind its access code, which this session did not have; whether the fleet reached the cap during the failing hour is therefore not measured, only consistent with every symptom the guests and the laptop showed during a full CI run and with none of them while the fleet was idle. The laptop's `networkQuality` measured idle latency of 15 ms and loaded latency of 103 ms (responsiveness "Medium") at a quiet moment.

**Two things the bridge's own configuration did.** The node's nftables input chain accepts only DHCP, DNS and the cache endpoint from a guest and drops everything else, so `ping 172.31.1.1` from a guest proves nothing about the gateway: a probe that treats that as reachability fails on a healthy host. And the bridge's dnsmasq ran with its defaults, 150 cached names and 150 concurrent forwarded queries, sized for a home router rather than for a fleet of guests asking for the same few hundred names thousands of times an hour.

## What changed

- The guest image carries `apparmor` and `python3-apt`, which every CI job on the fleet had been installing from the archive, and its apt source names two HTTPS mirrors (`archive.ubuntu.com`, then `mirrors.edge.kernel.org`) with a 30-second bound and three retries per fetch; CI's two install steps skip apt when the package is already present and name the same two mirrors when they cannot. A job on the fleet no longer depends on one mirror for anything. Measured on a guest the same day: a deb822 source whose first URI is black-holed moves each fetch to the second URI after the timeout (`apt-get update` still reports the dead mirror, and exits non-zero under `APT::Update::Error-Mode=any`), and a package install then completes from the second mirror in 2 seconds; whether a connection that stalls after connecting fails over the same way was not measured.
- The host role sizes the bridge's resolver for a compute host (`billet_guest_dns_cache_size: 10000`, `billet_guest_dns_forward_max: 1000`), so the fleet's repeated lookups are answered on the node and are not sessions on the uplink.

## What was not done, and what the operator can still do

- The gateway's session count was not read (its access code is printed on the device). If it approaches its cap during a full CI run, the fixes are on the operator's side: a firmware that raises the cap, or the node behind a router of its own whose connection table is sized for it, with the gateway in passthrough (which does not by itself stop the gateway tracking every session).
- Fewer connections per job is the durable answer at a shared site: `node.registry_mirrors` (billet's site-local pull-through caches for Docker Hub, GHCR and Quay) were not configured on this deployment, and billet has no Go module or apt cache of its own.
- The laptop's WARP client was ruled out as its own cause: its tunnel rekeys every two minutes as designed, its route-change log holds only the machine's own link-local churn, and its DNS proxy adds 10 to 80 ms per uncached lookup over the router's resolver, which is the cost of Gateway resolution and not a fault.
