# Control-plane queries

Named SQL statements, one file per domain, compiled by sqlc into `internal/state/ledgerdb`. The generated code is committed; `sqlc.yaml` at the repo root is the configuration and `make sqlc` regenerates.

**ALL LEDGER SQL LIVES HERE, including `internal/alloc`'s and `internal/rollout`'s.** One directory rather than one per owning package, because every guard below is written once against this directory and then covers every domain: the prepare-against-the-migrated-schema check, the read/write classification, the ASCII rule and the wildcard ban. Per-package query sets would have needed all four again each time, and the prepare check is the only thing in the tree that catches an `ON CONFLICT` whose unique index a migration removed.

**The generated package is imported by the three packages that open a transaction and by nobody else**, and a depguard rule enforces it. `internal/alloc` and `internal/rollout` import it for its parameter and row TYPES; the handle itself comes from `state.ReadQueries` / `state.WriteQueries`, so there is one implementation of the read-only refusal and one place listing every query in exactly one of the two halves. Everything above them reaches the ledger through `internal/state`'s or `internal/alloc`'s own methods.

## The rules, and why each exists

**Every parameter is `@named`, never a bare `?`.** Named parameters become named struct fields, so a column reordered inside a statement cannot silently swap two arguments of the same type at the call site.

**Query files are ASCII only, and this one is not a style preference.** sqlc rewrites `@name` into a numbered placeholder by slicing the statement at a byte offset, and a multi-byte character anywhere earlier in the file shifts every offset after it. Measured on v1.31.1: a single em dash in a comment turned `force_destroy` into `roy` and `VALUES` into `VALU`, and the failure arrives as `extraneous input 'roy'` from an ANTLR parser, naming neither the file nor the character. It needs both halves — with positional `?` the same em dash generates cleanly — so the rule is not "avoid em dashes near parameters", it is that these files are ASCII. `TestQueryFilesAreASCIIOnly` names the file, line and rune. Write prose here in plain ASCII and put the paragraph that needs a dash in a Go comment beside the adapter.

**Never `SELECT *`, `RETURNING *`, or `alias.*`.** sqlc resolves a star against the schema at code-generation time, so the projection is implicit in the source and silently re-resolves whenever a migration changes the table: a column added and every starred query quietly gains a field, with nothing in the `.sql` diff to review. Explicit column lists are also what make an ordinary `ALTER TABLE ADD COLUMN` change no generated byte at all. `TestNoQueryUsesAWildcardProjection` enforces it; `-- wildcard-ok: <reason>` on the line or the line above is the escape hatch, and the reason is mandatory.

**A migration is an input to code generation.** sqlc reads `internal/state/pgmigrations` directly rather than a flattened schema, so adding a migration can change generated code. `sqlc diff` in CI is what says so. Regenerate and commit in the same change.

It reads the *PostgreSQL* timeline because generation runs once, with that engine — a `$N` constant executes on both engines and a `?N` constant does not. That is not a claim that PostgreSQL is privileged: the two timelines are proved statement-by-statement to be the same schema, so a catalogue derived from either types the same Go. What it does mean is that `sqlc diff` now checks this set against one catalogue rather than two, and the SQLite side is covered by `TestEveryGeneratedQueryPreparesAgainstTheMigratedSchema` instead — a stronger question than the catalogue answers, because SQLite's prepare also resolves an `ON CONFLICT` arbiter.

**Operation names are logical, not dialect-specific.** `ListScaleSets`, not `SelectScaleSetsBySqliteOrg`. There is one query set for both engines, so a name that described a dialect would be describing the wrong thing.

**And a statement has to be portable, which is a real constraint on what may be written here.** `max(a, b)` is a two-argument scalar on SQLite and an aggregate on PostgreSQL, so `UpsertPendingCompletion`'s three sticky bits read `CASE WHEN a > b THEN a ELSE b END` instead — the portable form, and one that does not quietly depend on those columns being constrained to 0 and 1. `GREATEST` is the opposite trap: PostgreSQL has it and SQLite does not. When a statement will not generate, the answer is the portable spelling, never a second query set.

**Aggregates need a `CAST`, and so does a bare parameter in a `CASE`.** sqlc types a bare `MAX(x)` — and a bare `COALESCE(MAX(x), 0)` — as `interface{}`; `CAST(COALESCE(MAX(x), 0) AS BIGINT)` types as `int64`. The same is true of a parameter sqlc cannot resolve against a column, which is what `CASE WHEN @x = '' THEN col ELSE @x END` is: measured, all three write-once-or-keep parameters of `AdvanceRolloutNode` came out `interface{}` until each occurrence was wrapped in a `CAST`. An `interface{}` at that seam takes whatever the caller passes, so an `int` where a string was meant compiles and fails at run time.

**The cast is spelled `BIGINT`, never `INTEGER`, and a parameterised `LIMIT` is cast too.** `INTEGER` is `int4` on PostgreSQL, so the same statement that types as `int64` on SQLite types as **`int32`** there — and a bare `LIMIT @max_rows` types as `int32` on PostgreSQL for the same reason, which is why the three of them read `LIMIT CAST(@max_rows AS BIGINT)`. That matters because one query set is compiled for both engines: a query whose Go type depends on which engine generated it would make the shared adapter a lie. Measured on v1.31.1 — with `BIGINT` throughout, the two engines emit byte-identical Go apart from the placeholders. SQLite has no `BIGINT` type of its own; it is INTEGER affinity, and `CAST(x AS BIGINT)` is `int64` there too, so nothing about the SQLite side changed. See `docs/reference/decisions/adr-008-state-backends.md`.

**Existence is read from the error, never from the value.** A `:one` returns a zero-value struct alongside `sql.ErrNoRows`, so a caller that tested the struct would report generation 0 as a real row.

## Adding a query

1. Put it in the domain file, with a comment saying what invariant it carries.
2. `make sqlc`.
3. List the new method in `ReadOps` or `WriteOps` in `internal/state/queryset.go` — exactly one of them. `TestEveryGeneratedQueryIsClaimedByExactlyOneHalf` fails if you skip it, and `TestReadOpsHoldsExactlyTheQueriesThatOnlyRead` fails if you put a mutation in `ReadOps`.
4. Write the adapter method in the package that owns the operation, preserving the diagnostic the caller already depends on.

## The raw-SQL allowlist

Twenty-two call sites in `internal/state` execute SQL that is not a generated query, and they are the only ones anywhere in billet. Nine of them are the PostgreSQL backend's: the same questions the SQLite backend asks in the spelling the other engine uses — the durability readback, the bookkeeping table's columns and existence, the catalogue scan, the write lock — plus three the file backend gets for free, identifying which ledger a connection is on, taking the controller claim, and letting the migration's statements wait for their locks. **The rule is mechanical**: the `rawsql` analyzer in `tools/lint` reports every call that executes SQL from Go, in every non-test, non-generated file in the module, and each of these sites carries a `//billet:ignore rawsql // <why>` at the line. A bare directive is itself reported, and an unused one is too — so "0 violations" means "0 sites nobody wrote a reason for".

**This table is the specification, and `TestTheAllowlistTableNamesEveryRawStatement` keeps the two the same.** One row per site. The Call column is **derived from the source by that test**, not typed: the enclosing function, the method, a readable rendering of the statement argument, and `#` plus twelve hex characters of a sha256 over that argument's EXACT source bytes. The two halves do different jobs — the rendering is for a person reading this table and is deliberately lossy (it drops a wrapped line's indentation and shows a Go backtick as a single quote, because a Markdown cell cannot hold one), while the DIGEST is what makes the row an identity. Four versions came before and each was the same mistake in a smaller form: a hand-typed label that no edit to the code could invalidate, and then a rendering asked to serve as an identity while being lossy about the first line only, then about all whitespace, then about a raw string's own indentation and its backticks. Separating legibility from identity is what ends it, and a digest the test cannot take reads `#unreadable`, which no row can carry — so that fails closed rather than defaulting quietly.

**WHAT THE DIGEST CANNOT SEE IS AN ARGUMENT THAT IS AN IDENTIFIER, AND THAT IS FIVE OF THE THIRTEEN ROWS** — `PeekLedger`'s `q`, `migrate`'s `stmt` and `bootstrapSchemaMigrations`, and both of `readOnlyDBTX`'s forwarded `query` parameters. It covers the argument's source, so it sees `q` become `r` and not what either holds, and `bootstrapSchemaMigrations` is a package constant whose entire value could be rewritten under an unchanged key. That is left open deliberately: resolving it needs the type checker or data-flow analysis, this table is documentation rather than a production guard, and every one of those five is a statement whose text is assembled or supplied at run time — which is exactly what the Why column exists to explain and what no derived key could capture. To add or change a row, run the test and paste the identity it prints.

**The comparison walks the whole module, not this package.** The analyzer accepts a reasoned directive anywhere, so an exemption added in `internal/alloc` would be allowed by the gate and invisible to this table. The test fails on one, because there is no row that could describe it.
