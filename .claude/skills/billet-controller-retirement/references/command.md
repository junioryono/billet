# The `billet server retire` command

Part of the `billet-controller-retirement` skill. Each rule is stated in full, with the measurement or incident behind it. Moved here from `billet-releases-and-upgrades`.

**A retirement marks its guard, and a marked guard is released by nobody.** The record's two further members are `transition` (`{"kind": "retirement", "id": <32 hex>}`, the transition id minted at the reservation) and `taken_over_from` (the list of every previous holder, appended at each takeover, never overwritten), both read strictly in Go (`guardRecordMembers`, `guardRecordTypes`, `checkGuardRecord`: a marker of another kind, without an id or with a stray member, or an empty chain, makes the whole record unreadable, so no reader takes an old shape for an absent or a matching marker) and in the Python twin (`guard_fallback.py`'s `OPTIONAL_MEMBERS` kinds `transition` and `holders`, held by `guard_fallback_check.py`). `release`, `release --cleanup` and `recover --holder` refuse a guard carrying the marker (`errGuardTransition`) and ALSO a host whose retirement journal is `done` and not `settled` (the tail clears the marker and then writes settled, so a crash between leaves an unsettled journal without a marker); a journal that cannot be judged refuses too. A takeover (`hold --recover-from`) HOLDS THE MARKER TO ITS JOURNAL (`admitRetirementTakeover`): the journal must exist, be the old holder's by owner or chain (`Journal.Validate` with the guard's `TakenOverFrom`), and name the marker's transition, else the record is kept and the refusal names both ids; a marker beside no journal is an abandoned reservation, refused naming `billet server retire --abandon-reservation`; a guard with NO marker is taken over across exactly the tail's crash window (a `done` journal not yet settled, since the tail clears the marker and then writes `settled`) and the takeover RESTORES the marker from the journal's provenance, while no marker beside a settled journal or a journal at any other phase refuses; every takeover keeps the marker and appends the old holder, and a marker beside a pointer is held to the same rule. The `prepare` answer, its `--dry-run` and `status --json` report both members; the fixtures `guard-status/retirement-marker.json` and `guard-prepare/dry-run-guard-marker.json` are the producers'. THE JOURNAL AND THE TABLE live in `internal/retirement`: `Journal` (schema 1, root-owned 0600 under the 0700 `retired/` directory, which `EnsureRetiredDir` examines on EVERY admission (this account's, 0700, not a link; a 0600 file in a directory another account can write is one that account can replace by its entry) and whose parent it flushes on every admission too, since the creating invocation may have died before its own flush; read through `regularfile` THROUGH EOF (a stat's size is not the file: a complete document in a prefix with more behind it is malformed, and a file that moved under the read is unreadable) and trusted only when owned by the reading account with no group/other bits; the writer held to the reader's 64 KiB bound before publication, the previous journal kept; `provenance` immutable, `ownership` rebound with the chain appended; `row_done`, `completed_by`, `settled`, `timer_stopped_at`, held to the TAIL'S ORDER by `tailWellFormed` on every read and write (`done_at` with `done` and nowhere else, `row_done` iff `completed_by`, `settled` only over an acknowledged row, so a hand-written "settled" journal cannot take the settled shortcut past the acknowledgement); validated whole by `Validate` against the retiring host, the identity, the row's binding fields and the guard's holder or takeover chain, a settled `done` by provenance alone), the completion document and the survivor's answer (`DecodeCompletion`, `DecodeAnswer`, `Answer.MatchesJournal`, every binding field required), and the phase table (`Decide(variant, phase, Facts)` and `DispatchFor(row, journal)`, whose every cell is written to `tests/fixtures/retirement/vectors.json` by the Go test and compared on every run, so the role's and the loader's readers are held to the Go table; `config-rewritten` with the stage installed on a retained node restarts under either verdict and REFUSES an unobservable one, as `archived` does). EVERY DOCUMENT IS DECODED TYPE-DIRECTED (`strictDecode` → `checkMembers`): encoding/json matches a member case-insensitively, so `"ROW"` beside `"row"` is two values for one field that `DisallowUnknownFields` admits; the walk carries the Go type per frame and refuses a member the struct does not spell exactly, a repeated one, and content after the document. `billet server retire` (`cmd/billet/serverretire.go`, dispatched from `cmdServer` before its flags) is the command the role calls: `--reserve` (PostgreSQL active-passive only, the row through `openStateAdminWith` under the identity exclusion, `retireTransitionID`/`retireNow` the seams), `--abandon-reservation` (association validated whole, marker cleared before the row is deleted, a mismatched marker or one beside no row could-not-tell and KEPT), `--complete-row` (the survivor's helper: `--as-host` equals the document's survivor, identity equals its deployment), `--acknowledge-row` (`Answer.MatchesJournal` against the local `done` journal, then `row_done`/`completed_by`), `--dry-run` (no lock, nothing written, the row through `openStateInspect`, `unreadable` never absence), and `--input -` (the request: `decodeRetireInput` and `bindRetireInput` in `serverretireinput.go` — every envelope bound to its host, this run's round and the reservation's clock, each document decoded type-directed and read through PATHS (`report.get/str/boolean/requireStr/requireBool/requireNull`), where an inspector's `{"unknown": why}` at any step of a path is could-not-tell and never a value; `judgeRetireRequest` in `serverretirerequest.go` decides in the order the refusals are reached and `applyRetireIntent` records marker, stage, journal, row, status; `serverretirehost.go` holds the host's own proofs: `readMountinfo`/`mountOf` (the kernel's octal escapes decoded, the longest mount point wins, the identity directory refused when it is itself a mount), `walkTraverses` (a component walk that expands every symlink where it stands, applies `..` to the directory reached, distinguishes a missing component from one it could not examine, and refuses at 40 links) and `hostInterfaceAddresses`, which the inspector reports as `host.addresses` beside `host.node_effective_name`; the survivor's authority is compared by the DER of the certificate its report carries against `wirecert.SnapshotAuthority`'s, never by a reported fingerprint); every mutating mode requires this converge's guard through `retireGuard` (holder equal to `--run`, no pointer, not `preparing`, no stray temporary) FIRST, then holds the identity exclusion (`withIdentityAccess`, which the ledger factory borrows from the registry) through the identity peek, the open and the row's write, and observes the configuration ONCE under both (`observeRetireConfig`: bytes, digest and document from one read), because the second review found the eligibility decided before the lock, the identity peeked outside the exclusion and a `--survivor-host` no `--as-host` could spell; the reservation and the acknowledgement hold an existing marker to the row or the journal (`requireMarkerAssociation`), the acknowledgement validates the journal through `Journal.Validate` with the guard's chain and the identity at the archive and holds `completed_by` to a participant (equal to the recorded one on `already`), the abandon's retry flushes the guard directory and the root before the row is deleted even when the marker is already absent (a rename's durability the earlier run may have died before), a document past its bound is drained to EOF before the refusal, the dry run reads a SQLite row another account owns AS THAT ACCOUNT through `rollout status --json` (`reexecCapture`, the `retireReexecCapture` seam) and reads an unminted identity as `unreadable`; exit 0/2/3 with `state: nothing` on every answer of the command's own (the survivor's `Answer` keeps its spec'd schema); the journal's `transition_id` has the marker's grammar (`transitionIDPattern`) and its reader re-stats after the read (`journalBetweenStatAndRead` the test hook); the fixtures under `tests/fixtures/server-retire/` are the tests' own (`TestTheServerRetireFixturesAreTheCommandsOwn`), the one PostgreSQL test (`TestServerRetireReservesOnAPostgresPair`) named in CI's `test-postgres` run list, everything after the row exercised on SQLite by writing the row directly.

**The dry run is a CLASSIFIER that answers one word, and the role's caller (`retirement.yml`) branches on nothing else.** `billet server retire --dry-run --json` (`cmd/billet/serverretire.go`) takes no lock, mints nothing, migrates nothing and creates no directory, identity, authority or guard — a read-only SQLite open can still leave the driver's `-wal`/`-shm`, which is why it runs as the identity directory's owner. It answers `route` (`ordinary`, `hold`, `recovery`, `new-request`, `continue`, `cancel`, `unsupported-variant`) plus `route_why` for a person; every other member is a diagnostic and an operand. Beside no journal, `--requested` selects `new-request` for an eligible installed controller whether or not it keeps a node; `route_why` names the variant the request will carry. Installed node custody does not bypass pair eligibility: SQLite and single-controller PostgreSQL still hold by name. `unsupported-variant` belongs to a REQUESTED NODE-ONLY HOST: with no server there is no ledger, so its row is unreadable; without the request it is `ordinary`. The role selects the fresh request variant from the classifier's `installed_roles`: `both` selects `retained-node` with a serverless rendering, `server` selects `server-only` with `--server-only` and `desired: null`, and any other or unobserved role refuses before reservation. The rule was paid for over four design reviews: each time the ROLE was given one more report member to combine, another fact only the COMMAND has turned up missing — `billet_enable_server` is requested policy and not an installed role, "no installed configuration" neither proves freshness nor covers a prepared-but-uncommissioned controller, and the guard's abnormal shapes reach the report looking ordinary. The partition is ORDERED and TOTAL and anything unmatched HOLDS; a readable journal selects `continue` INDEPENDENTLY of the ledger, because a settled journal is legitimately checked with no ledger reachable. An OBSERVED GUARD FACT MUST NOT DEPEND ON A FLAG: three exclusions were once gated on `--expected-holder` while only one of them is an expectation, so a run without it answered three different mutating routes over a pointer, a journal and a reservation it had seen in front of it. A MALFORMED published status is deliberately not a hold, since the `done` path repairs it from the journal and holding would make the host that needs the repair the one nothing can route into it; a DANGLING status symlink is unreadable and not absent (`ReadStatus` reads `NoFollow`). `recovery` is the one route that is not about a retirement: an interrupted binary upgrade fences the ledger, so the row reads unreadable and the host would hold forever — the recovery tasks sit behind the ordinary gate and only finalisation removes the fence. It needs the fence to be EXACTLY what refused the read (`state.OnlyCause`, every leaf, so a joined cleanup failure denies it), a transaction whose manifest reads and names THIS host's server directory, and no retirement artefact at all — and it proves NOTHING about whether the recovery will succeed. The recovery's prerequisites (input copies, the ledger volume's mount, the state directories' types) belong to the role's recovery tasks, which refuse by name; a mirror of them in the classifier was tried and two review rounds each found it incomplete in four more ways, because a copy of another component's refusals cannot be complete. `recovery` is permission to run the recovery, and a refused recovery is a failed converge that names its fix.

**The retirement caller requires a capable answerer before routing.** An incapable or absent retirement answerer holds, under either value of `billet_enable_server` and with or without `--requested`, except for the explicitly unverified check-mode candidate preview. The reason names `billet_retire_capability_floor` (`v0.11.0`): this collection needs billet at or above that floor on the host; upgrade the managed binary or converge with an older collection. Requested retirement is also refused by name. Check mode reports the hold and succeeds without ordinary work. When preparation has an empty answerer, no claim and an unstaged Linux candidate, `unverified-check-mode` may preview ordinary work without classification; a real run stages and classifies and can select different work. A supplied candidate beside an incapable managed answerer grants no exception. A new-request preview checks static policy and installed node presence but reserves and collects nothing and proves no real-run survivor preparation. A settled retained preview calls neither entry nor node-config nor closing and opens no retained ordinary work. Local configuration, a clean identity locator, absent retirement artefacts and one stopped or absent service unit cannot prove that no controller or shared reservation exists: a controller may run by hand, under another supervisor, or as a surviving child of a stopped `KillMode=process` unit. The caller therefore reads none of those as compatibility evidence and keeps no three-path artefact screen. A legacy claim keeps its own rule: a verified capable executable classifies read-only; `ordinary` enters ordinary convergence, `recovery` runs the existing recovery alone and ends at the fresh-converge boundary, and every other route holds. Without a capable executable it holds. Preparation leaves the answerer empty for a pre-guard managed binary with no candidate, or a host with no billet and no candidate; the last case also lacks the binary source required by fresh-host validation. Beside a LEGACY claim preparation may still publish an answering executable — check mode does — so `retirement.yml` resets that answerer and verifies a legacy one itself, by its own shape rules, before it classifies; the two stages are separate and the infrastructure skill describes them the same way. An install or binary change stages a candidate, but candidate-first preparation alone selects it as answerer. A managed binary that already answers the guard remains the answerer even after staging a newer candidate, so a below-floor managed answerer still holds in that case. The floor concerns the selected executable's observed version, never the desired installation pin; recognised development builds attempt strict classification. `executable_version.py` remains the version observer; `v0.10.1` is an explicit below-floor maintenance release.

**The fresh retirement request keeps the installed variant.** Before reservation, including check mode, `retirement-request.yml` selects `billet_retirement_requested_variant` from the classifier's observed installed roles and separately refuses either direction of node-presence drift; node removal or installation must converge ordinarily with retirement disabled first. Retained requests require `billet_node_should_run` true, with `billet_enable_node` true and `billet_server_prepare_only` false. Existing binary, server policy, survivor and preparation refusals retain their order. The request reset copies the selection into `billet_retirement_variant` and empties `billet_retirement_serverless_rendering`; after reservation binding, the latter receives B through the one `billet.yaml.j2` serializer over `billet_config | junioryono.billet.serverless_config`. That filter owns the four removed names once and also serves the retained ordinary projection. The command holds B to installed configuration minus those members and refuses remaining inventory drift. Collection requires the retiring host among node hosts exactly for retained-node, preserving its full desired self rendering and digest separately in `billet_retirement_collect_rendering`. Only server-only passes `--server-only`; only retained-node carries B in `desired`. The answer must match the selected variant, and a retired answer pairs server-only with receipt `none` or retained-node with `written` or `current`. Completion binding, abandonment and the tail keep their existing protocol, and every continuation carries `desired: null`. The retained node runs through controller shutdown and configuration replacement, then the command's existing restart phase stops and starts it before done; retention does not promise uninterrupted node uptime.

**Retirement preparation and the endpoint move precede the request.** `billet_retirement_survivor_host` names a distinct inventory controller in the same play, still active in `ansible_play_hosts`, with its own settled, held, pointer-free guard under this driver's holder; earlier-play survivor facts do not suffice. The retiring host's preparation window is closed, and every collected node has its prepared answerer. The survivor report must prove the same PostgreSQL active-passive deployment and authority, without rotation or a retirement of its own. `judgeNodeEndpoint` refuses an address of the retiring controller; loopback reaches the survivor only on the survivor's own host. Converge the retained node's endpoint to the survivor ordinarily with retirement disabled FIRST, so receipt, runtime registration and installed configuration agree before collection. A DNS name or shared address requires `--endpoint-failover-verified`, the operator's assertion it survives removal, carried by `billet_retirement_endpoint_failover_verified`; retirement itself moves no endpoint.

**Entry state separates retirement completion from retained ordinary work.** Fresh requests and incomplete or unsettled continuation end after transition/tail even when their result settles. Server-only completion never opens ordinary work. A binary recovery ends at the fresh-converge boundary; only `ordinary`, confirmed cancellation and an already-settled retained entry's fresh admission open ordinary work. `retirement-settled-entry.yml` calls `--check-settled-entry` before `--check-node-config` binds exact E/rendering and operation bytes; ordinary E removes only `server`, `github`, `targets` and `backup`. Keep `billet_server_retire` while desired input still contains `server`; remove it only with explicitly serverless inventory. Clearing the flag does not undo a journaled transition or authorize recommissioning. Quiet inactive/failed entry requires zero main/control PIDs, no cgroup processes or queued job, persistent enablement and supported loaded/installed agreement; it needs no runtime record and proves neither successful drain nor compute absence. All ordinary work, confirmation, receipt, cleanup and handlers precede `--check-settled-closing`, whose strict current active-node/registration proof is required for success. Settled entry/closing are schema 2 with `enablement_changes`, reported without repair behind proved persistent controller inertness; node-config success remains schema 1. Historical completion is a ledger fact bound to the original proof and `DoneAt`, never current host health: survivor completion and local acknowledgement can succeed after node failure, while strict publication, marker clearing and settlement still require fresh local proof. Closing failure preserves the historical records and any earlier receipt without blessing the pass.

**Retained ordinary operations protect the retired controller, and binary changes use Go.** The operation walker refuses protected lexical, resolved and intermediate path traversal, including missing parents followed by `..`, and recursive operations over protected ancestors. Unknown path or service-effect evidence refuses before dependent mutation; exact node unit replacement cannot introduce unproved execution semantics. The role preserves zero or one installed typed `EnvironmentFile` operand, its optionality and contents, with no mutation grant. Paths must be absolute literal names without whitespace, controls, quotes, globs, specifiers or escapes; present files must pass the bounded regular-file read and restricted `NAME=value` grammar described in `docs/operating/upgrades.md`. The role's binary transaction refuses on a retained host before ordinary mutation. Supported upgrades are the surviving controller's rollout dispatch or an operator's Go `billet host-upgrade`, followed by an unchanged-binary converge; the retired controller timer is not a node upgrade path. The retained pass records the same node lifecycle operations as a node-only pass over the same effective configuration. That recorded-operation parity does not establish the all-host successful-drain guarantee, which belongs to #127. `tests/retirement-cases.md` records every section/count from `ROLE_CASES` and measured CI budgets separately from these evidence limits.

**A locator is not a validation, and discarding one converges over a live reservation.** `observeRetireDryRunConfig` parses UNVALIDATED and validates separately: a configuration whose bytes decode still names its `identity_dir` when an unrelated clause fails (`server.max_vcpu: 0`), so the identity is observed THERE. Discarding it sent the observer to the packaged path, which read clean, and answered `ordinary` over a controller with an intact identity and an outstanding reservation. Only absent or undecodable bytes fall back to `retirement.Root/server` — which is the PACKAGED path and emphatically not `config`'s own default, resolving under the invoking account's config directory; that confusion has now failed a package postinstall and a classifier admission on this branch. A locator that is empty or padded is could-not-tell, never used.

**The transition after intent is one loop over the phase table, and every action is written behind the act it certifies.** `retireTransition` observes the host (where the identity directory is, which recorded digest the installed configuration is, whether the stage is the one intent recorded, and at the phases that read them the backup service, the node's changed-since-start verdict and the node unit), asks `retirement.Decide`, performs exactly that action and observes again, bounded by `retireStepLimit`. The order a healthy host meets: the timers stopped and disabled, `timer_stopped_at` recorded while the journal is still at `intent` (the window a refused backup lands in), the server stopped and disabled, the backup proved finished, the status closed, the journal at `stopped`; the rename and both parents flushed, `archived`; the stage installed with the installed file's own owner and mode (or the configuration removed on a server-only host), `config-rewritten`; the node enabled, the enablement READ BACK as systemd's literal `enabled` (an `enabled-runtime` node passes every running predicate and is gone at the next boot), stopped and started, `node-restarted`; then `done`. A RUNNING BACKUP IS AWAITED AND NEVER KILLED, under a timer and never the record's clock (`retireNow` is a seam a caller pins, and a wait measured against it never ends), and the one failure reconciled is the refusal the retirement itself caused (a start after `timer_stopped_at`, `Result=exit-code`, `ExecMainCode` CLD_EXITED and `ExecMainStatus` 6), cleared with `reset-failed` and re-observed. The lifecycle lock covers the stop-to-archive window and is dropped before the node's restart, which is a drain. A RESUME TAKES THE TRANSITION'S OWN EXCLUSION (`withRetiringIdentityAccess`), because from `stopped` on the status this host published refuses every ordinary writer including this run, and an advance that recognises another run's move or rewrite FLUSHES WHAT THAT RUN OWED before publishing the phase that certifies it (a rename is visible long before its parent's entry is durable). A journal write that fails AFTER its rename answers the phase the journal now HOLDS, with its durability said to be unknown, rather than naming a phase no reader would find. Two comparisons refuse rather than guess: a systemd timestamp in a zone this host cannot resolve is not read as UTC (a positive offset read as UTC moves the instant later, the admitting direction for both callers), and a modification inside the second a process started is could-not-tell, since systemd renders seconds and the filesystem keeps nanoseconds. Uncertainty is never permission to restart: an enablement word this billet does not know, and a registration record from another invocation on a positively ACTIVE node, are `unknown` and refuse rather than draining a running node. A `done` JOURNAL IS ANSWERED BEFORE ANY CONFIGURATION IS READ AND BEFORE ANY LEDGER IS OPENED (`retireDone`, `cmd/billet/serverretiredone.go`), because the host it describes has no identity at its configured path and, when it kept no node, no configuration: the identity comes from the archive the journal recorded and the ledger from its locator. SETTLED is the steady state — nothing taken, nothing opened, the postconditions judged and reported (`archive`, `config`, and the five units in the words the shared table admits; `masked-runtime` admitted for none, a not-found unit quiescent only BESIDE inactive with no process, a failing one named in a `postcondition` refusal). UNSETTLED is a tail another holder left, finished by whoever holds the guard now, which is what makes the window between the marker's clearing and `settled` recoverable; a guard without that retirement's marker is refused. THE COMMAND RESUMES AN INTERRUPTED TRANSITION FROM EVERY PHASE, by one of two paths, and which one is decided by the FILESYSTEM and not by the phase: a `stopped` journal whose move already completed is past the archive whatever its journal says, because the exclusion and the identity the ordinary path would read are inside the directory that has moved. Up to the archive the ordinary path reads both from the installed configuration and takes the transition's own exclusion; past it (`retireResumeArchived`, `cmd/billet/serverretireresume.go`) EVERYTHING COMES FROM THE JOURNAL — the identity from the archive it recorded, the ledger from the locator when the tail asks for it — and the driver runs with NO configuration observation, because there may be none to take (the rewrite installs the staged bytes and holds them to the digest intent recorded). NO LEDGER IS OPENED TO GET THERE and no identity exclusion is taken: the row reached `intent` before the archive did, so nothing must be asked of a database before `done`, and a host past the archive is exactly the one whose database may be out of reach — which the tail already answers as a pending row rather than a failed converge, so requiring a ledger read to resume would make an outage the one thing that leaves a half-transitioned host with no way forward. The authority moved with the directory and every action left touches none of it. What holds either way is ownership: this guard carries the journal's marker, and the journal names this host, this deployment (read at the archive) and this holder or one its takeover chain reached.

**The tail is the local work first and the ledger last, and its order is what makes its crash windows recoverable.** `retireTail` (`cmd/billet/serverretiretail.go`) runs in the same process that reached `done` and does, in this order: the published status (republished when it is absent, malformed or below `done`, since that file is what closes the authority to every ordinary writer); the retained node's endpoint receipt through `refreshReceipt` (the converge that retires a host ends at the retirement and never reaches the ordinary task, and the node's invocation and installed digest both moved under the transition); the completion document, which is emitted on EVERY answer because the role does not decide from the row's word alone; the ledger row; the guard's marker; `settled`. THE ROW GOES THROUGH THE JOURNAL'S LOCATOR (`retireOpenLedgerByLocator`: the backend, the DSN variable's name, the environment file and the archive recorded at `intent`, since the installed configuration has no `server:` and the identity has moved) AND THROUGH `state.OpenPostgresCompletion`, which claims nothing and migrates nothing — an admin open takes the deployment's controller exclusion and migrates the shared schema whenever the survivor happens to be down, which is the one moment a retired host must not become this deployment's control plane; a structural witness holds the file to that one open. ONE CLASSIFIER JUDGES EVERY ERROR the tail's ledger work produces (`retireLedgerProblem`, over the open, the binding and the row's completion alike, because an outage that begins after the connection is established is the same outage), and THE PENDING LIST IS CLOSED: `state.Unreachable`, `ErrSchemaAhead`, `ErrSchemaBehind`, `ErrReleaseBehind`, a DSN variable the locator names that is unset or whose environment file cannot be read, and a DEADLINE — while a ledger bound to another deployment, or a row naming another host, transition or reservation, says the ledger disagrees with this journal and stops for an operator. THE WHOLE ATTEMPT IS BOUNDED (`retireLedgerBound`, two minutes), because the open's thirty-second budget ends when it returns and the binding and the completion would otherwise run with no deadline at all while the guard is held. WHOSE DEADLINE IT WAS decides what an expiry means (`retireDeadlinePending`): the caller's own context ending is the operator stopping the converge and is no pending row, this command's bound is the ledger taking longer than the attempt may, and a deadline NEITHER set is the open's own startup budget — the case an unresponsive connection during the open produces. THE ERROR IS ASKED FIRST in all of it: a context that has expired by the time it is examined proves nothing about an error that arrived before it, so a binding that established another deployment's ledger is still that. A pending row is not a failed converge: the answer is `retired` with `row: pending`, and the survivor's `--complete-row` takes the completion. THE MARKER IS CLEARED ONLY ONCE THE JOURNAL ACKNOWLEDGES THE ROW and fresh local postconditions pass; those postconditions are checked again after marker persistence before `settled` is written, so the one crash remainder is an unsettled journal beside a guard with no marker, which is exactly what the takeover rule reads as an unfinished tail; the marker is cleared from the record READ AGAIN through the guard's descriptor (`classifyGuardDirFrom` then `judgeGuardShape`), never from the shape the run classified before its own intent wrote the marker. The tail's answer takes its `state` from the SAME exit as every other, read when it answers, so a journal that vanished under the run is `unknown` and not the phase the run remembers. Its fixtures are `server-retire/retired-settled.json` and `retired-pending.json`, whose pending case is staged with the locator's variable unset so its diagnostic is the same on every machine.
