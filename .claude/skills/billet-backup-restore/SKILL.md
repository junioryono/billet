# Backup, restore, recover, and durable files

## What this area is

A deployment is four things and they are useless apart: the ledger, the deployment identity, the GitHub App private key and the node-wire authority. `internal/deployarchive` captures them as one archive (`Manifest`, `Schema` 2, digests and sizes per entry; a PostgreSQL ledger is recorded as `ExternalLedger` because copying rows through billet's own connection would produce something that looks like a backup and is not) and puts them back with `PlanRestore`/`PlanRecover`, `Execute`, `Finish` and `Abandon`. `internal/archivestore` is the S3 hop with no delete. `internal/durablefile` is the one ordering for installing a file something remote will name. The rehearsals are `make restore-rehearsal` and `make postgres-restore-rehearsal`, recorded in `docs/reference/records/restore-rehearsal.md`.

## Rules

**The host transaction runs on an external ledger without copying it.** billet still snapshots no PostgreSQL database and `billet local backup` still records such a ledger as external; what changed is that `billet host-upgrade` no longer refuses there. Its journal carries `Ledger: external`, it fences, snapshots and migrates nothing, the candidate is probed through `state.OpenPostgresProbe`, and the migration happens at the candidate's claim; the rollback boundary is the candidate's start and what lies past it is the database's own backup. A `pg_dump` inside the transaction stays rejected for ADR-008's reason.

**All four pieces or none, and nothing is ever overwritten.** A ledger without its identity is a fresh authority that cannot see the compute the old one launched; an identity without the CA cannot issue a certificate; a CA without the App key cannot get a token. So `local backup` captures all four or refuses, and `local restore` installs each piece that is absent, accepts one that is byte-identical, and preserves and refuses one that differs, with no flag that overrides it. The App key is one per target: schema 3 carries `Manifest.Targets` and `github/<name>/app-private-key.pem` for every further target beside the `default` entry, a schema 2 archive reads as the single target `default`, a schema below 3 that names targets is refused, `BackupRequest.Targets` must name every further target the config declares or the backup refuses, and the restore planner refuses a config that does not name every archived target with the same identity, because installing half the credentials is the failure all-or-none exists for. The App key goes through `reserveKeyFile` and `writeKeyAtomically` rather than a second implementation. The authority allowlist is `ca.key`, `ca.crt`, `ca-previous.key`, `ca-previous.crt` and `authority-created` (outside the `ca` directory so its absence is detectable); half of either pair refuses. Authority planning walks the allowlist rather than the archive, or a leftover `ca-previous.crt` on the target is never looked at and the next start reads it as an active rotation. The archive's entry set is closed, so `Open` refuses an entry the planner has no case for.

**Backup, rotate and retire share `wirecert.LockAuthority`.** Rotate mutates five files in sequence; a reader without the lock captures a key from one generation beside a certificate from another, an archive that loads cleanly and verifies nothing. `VACUUM INTO` is the ledger mechanism and its constraints were measured: it cannot run in a transaction, is refused on the reader pool, refuses an existing destination (free no-clobber), creates the file 0644 (corrected), and holds the single writer slot while it runs; it is a consistent snapshot of a live database, so no `-wal` travels.

**Restore's exclusion is three local mechanisms and one human assertion.** The directory lock proves no control plane holds it (and nothing about an operator command, which opens without it); the maintenance fence reaches a handle already open, because `Tx` and `View` consult it on entry; the writer barrier proves a transaction that began before the fence has finished. None reaches another machine, so `--old-controller-fenced` is the operator asserting the old controller is stopped and disabled everywhere; without it two controllers share one identity, one CA and one App credential. Restore and abandon also take `LockAuthority`, directory then authority, matching the backup's order.

**The plan is re-derived inside the exclusion and only that one is acted on.** The planner is lock-free so `--dry-run` can report on a live deployment, and its output is printed for a person; acting on it deleted a ledger because it was empty when somebody looked. The presence of `billet.db` cannot be the refusal (a preflight `billet check` creates one); what proves a directory committed is the identity and the marker, and what proves the ledger replaceable is that every table a deployment writes is empty and the `admission` singleton is exactly the row its migration inserts.

**Publication goes file by file, hashes through a descriptor, and the identity check precedes the close.** Renaming a staged directory into place would leave the restorer holding the old `billet.lock` inode while a server locks the new one. `copyFile` hashes as it copies and publishes with an `os.Link` checked against the descriptor before and the destination after; `f.Stat()` on a closed descriptor reads as "not ours", so closing first leaves the staging copy of a ledger, or a key, behind on every success. Nothing unlinks a pathname it cannot prove it owns: the staging name is `os.CreateTemp`'s and the planner refuses an App-key path that is one of billet's own state files. Containment is `filepath.Rel` plus an `os.SameFile` walk, because a prefix comparison is wrong at `/` and on a case-insensitive filesystem.

**A failed restore leaves the ledger fenced with a journal.** A half-restored directory would start a control plane that mints whatever is missing. Re-running resumes (every install is no-clobber); `--abandon` removes only paths the journal records this run created and can still prove are copies of the archive's. The journal records a path before creating it. A fence a command raised comes down if it published nothing (`WriteMaintenanceFence` reports whether this call created it); past the journal it stays.

**A restore runs as root and hands back what it wrote.** On a packaged host the App key lands in root-owned `/etc/billet`, and systemd's `StateDirectory=` repairs recursively only when the top directory's owner is wrong, which after a restore it is not. `billet local up` repaired only `preflightState`, so a deployment restored perfectly and the control plane could not open one file of it. `lifeops.RepairPaths` takes its set from the plan just executed, plus the `ca` directory (a root-owned 0700 one cannot be traversed) and the two lock files the command created; a failed repair is reported and the command exits 0, because the next thing reached for after "the restore failed" is `--abandon`. The rehearsal found this, not a reading.

**`local recover` puts a deployment back over itself, and every step exists because the previous one cannot promise the next.** It refuses unless the archive is this host's own deployment; seals and waits on `alloc.Quiescence` (a seal stops admission and says nothing about what runs); refuses while anything is outstanding unless `--accept-failing-jobs`, naming each job; requires `--old-controller-fenced`; supersedes the ledger to `billet.db.superseded-<archive time>-<manifest digest>` (never deleted, the only record of the work that failed; RFC 3339 seconds collide for back-to-back backups); and seals again afterwards, because the first seal lived in the ledger just replaced and the archive's admission row is whatever it was, open. The intent guard sits above `planLedger`'s absent-ledger branch or a recover against an uncommissioned host plans as an install. A resume must not re-quiesce, because quiescing opens through `OpenAdmin` and the first attempt's fence refuses it.

**The fence outlives the publication.** `Execute` leaves a recovery fenced (`Result.Unfinished`), the command seals through `state.OpenMaintenance` (the one typed fence crossing), and `deployarchive.Finish` lifts the fence afterwards, under one acquisition of the directory lock, asking `state.PeekAdmission` (no lock, no migration, no fence) whether an operator seal is in place and refusing a journal still at `publishing`. `Finish` proves the seal rather than documenting it; before that the two tests named for the invariant demonstrated it did not hold. `phaseFinished` is written before the fence comes down so a crash on either side leaves something recognisable, and `--abandon` refuses a `finished` journal because undoing a complete sealed recovery removes the restored credentials.

**Order of a supersede: sidecars, sync, ledger.** Moving `billet.db` first and crashing left no ledger at the source, so a re-plan read an ordinary install and put the archive's database beside a `-wal` from a different one, which SQLite replays. A sync between the sidecars and the ledger is what makes the order durable rather than intended; `planLedger` refuses an absent ledger whose sidecars remain. The put-back moves the ledger first, the opposite order, because a resumed run looks for the ledger at the canonical name; the order is pinned by `Result.Restored`.

**An abandon reconciles the whole set by digest, and refuses whatever it cannot vouch for.** `supersedeLedger` records the digest of every file it moves before it moves anything; `putSupersededBack` compares what it finds against those, refuses a canonical file whose digest differs or that is present with nothing recorded, and refuses to lift the fence if it would leave no ledger. Every unresolvable state is an error that leaves the fence and journal standing, because `abandonLocked` reads nil as "ready to start" and a control plane repopulates an empty directory with a fresh ledger. Keys are base names, because a run started at `/srv/billet` and abandoned through a symlink recorded different spellings. Ownership is established before any fence is written, because a restore's abandon meeting a recovery's journal once raised a restore fence over it and neither command could proceed. `strayLedgerSidecars` treats an `Lstat` error as could-not-tell, not absent. The one bounded race: a connection open before the fence that closes afterwards checkpoints the WAL into the file whose digest was recorded; the abandon refuses and names the checkpoint.

**The journal is schema 3 with a closed phase set and an explicit intent.** Schema 1 had neither digests nor intent; schema 2 changed what the digests meant under a number already in use, which is worse than changing the number. `journalSchema` is validated before any of it is read, so a downgrade cannot act on a newer record; `Intent` is validated at every exported mutation, and `Abandon` compares the journal's intent with its own, since `understood` proves a journal names an operation and not this one.

**An archive on the disk it protects is not a backup, and billet owns both ends of one narrow hop.** With `backup.s3` set, `local backup` uploads what it just wrote (never instead), and `local restore --from-backup latest` fetches, verifies and restores on a machine holding only the binary; an `s3://` URL could not replace the config because it carries no region and SigV4 signs one into every request. There is no delete anywhere on the path, not in `internal/archivestore` and not in the generated IAM, so retention is the bucket's, through versioning and a lifecycle rule on noncurrent versions only. Every write is `If-None-Match: *`; the manifest is uploaded last so an interrupted upload is not something a listing offers; the local archive is written and verified first; the credential is env or IMDSv2. `billet check` reports the newest archive's age because a timer that stopped firing looks like one that works. `ErrNoSuchObject` is S3's `NoSuchKey` and nothing else: every 404 used to come back under that name, so a bucket that does not exist reached a restore as "no archive here" on the one day the machine is new and the operator has nothing but the binary — the fix is one line of config and the diagnostic was pointing at their backups (`internal/awss3`, and `billet-providers-aws` for the measurement). The packaged `billet-backup.timer` is enabled by nobody and managed by none of `local up/down/status`. A `--from-backup` retry reuses the copy its first attempt kept when the manifests match.

**A remote record may not name a local file that is not durable yet.** `images pull` installed the paired kernel, synced it, changed its mode after the sync, renamed it, and committed Ceph metadata naming the file without flushing the directory; `fsync(2)` says flushing a file does not flush the entry, so a power loss left a complete published generation whose kernel vanished in recovery. `internal/durablefile.Installer` is the one ordering: metadata change, file sync, atomic rename, containing-directory sync, with the caller's write callback in front so a digest can refuse before anything is renamed. A failure up to the rename leaves nothing; a failed directory sync leaves the file, because the entry may already be durable and the retry re-verifies. The mode is set before the sync because a chmod behind it is metadata nothing committed. `durablefile.MkdirAll` flushes every ancestor even when the directory exists, by the resolved path as well as the name, because `os.MkdirAll` follows symlinked components and a state directory moved to another volume would have its lexical parents flushed and the real entries never committed. The reuse branch re-applies the mode and flushes through one `O_NOFOLLOW` descriptor, never `O_RDWR` (a `0444` kernel refuses it while chmod and fsync succeed read-only), and skips a chmod to the mode the file already has (a read-only mount answers EROFS). `TestAPullDoesNotPublishAGenerationBeforeTheKernelIsDurable` fails each step in turn and asserts `ImportGeneration` was never reached.

**A durable file is not a file nothing else will delete.** A concurrent `images reap` computes the kernels surviving generations need from the generations that exist when it looks, and between `installKernel` and `ImportGeneration` nothing names the new file, so it unlinks it correctly and the pull publishes a generation naming a kernel that is gone. The Ceph publish lock cannot cover that interval (it is cluster-wide with a six-hour stale bound). `cmd/billet/kernellock.go` is an flock on `<kernel dir>/.billet-kernels.lock`, keyed on the directory (two deployments on a host share one; a symlinked directory resolves to one file), waiting rather than refusing, held by the pull from before the install through a successful import and by the reap from before it reads the generation set through the deletion, always outside the publish lock. `--dry-run` takes no lock, because taking one creates a file. The reaper never unlinks the lock file, because unlinking a held lock detaches the path from the inode and the next billet locks a fresh file (proved by mutation: removing the skip alone stays green, removing it and widening the pattern goes red). `nodeKernelDir` is the one answer to where kernels live, because `--kernel-dir` once defaulted to a constant while the launch and the reaper read `node.firecracker.kernel_dir`.

## Measured facts

- The first rehearsal failed at `billet server --upgrade-probe` under the service account with permission denied on the App key.
- `VACUUM INTO`: refused in a transaction, refused on the query-only pool, refuses an existing destination, creates 0644.
- `O_RDWR` on a `0444` kernel: permission denied; chmod and fsync through a read-only descriptor succeed; a no-op chmod on a read-only mount: EROFS.
- A test hook failing every directory sync never reached the reuse branch's own flush, which is how deleting it survived a mutation run.
- Kernel lock mutation: removing the reaper's skip alone leaves the test green; removing it and widening the pattern turns it red.
