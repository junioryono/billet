# Backup and restore

Part of the `billet-backup-restore` skill. Each rule is stated in full, with the measurement or incident behind it.

**The host transaction runs on an external ledger without copying it.** `billet host-upgrade` does not refuse there. Its journal carries `Ledger: external`, it fences, snapshots and migrates nothing, the candidate is probed through `state.OpenPostgresProbe`, and the migration happens at the candidate's claim; the rollback boundary is the candidate's start and what lies past it is the database's own backup. A `pg_dump` inside the transaction stays rejected for ADR-008's reason.

**A PostgreSQL ledger travels as `pg_dump`'s copy of the snapshot billet read it in (archive schema 4, #19).** Schema 4 is written only when a dump is carried, so every other archive stays at 3. `state.ExportPostgresSnapshot` opens a READ ONLY REPEATABLE READ transaction on the inspection pool, reads `pg_export_snapshot()`, the schema, the server's major, the migrations and the binding, and calls back while it holds them. `internal/pgdump` runs `pg_dump --format=custom --schema="<s>" --snapshot=<id>` inside that callback, the schema double-quoted because `--schema` is a pattern: unquoted, `Billet` would dump `billet` and `billet*` every schema it matches. That makes the manifest's migrations exact, and it proves `pg_dump` reached billet's database: importing the snapshot elsewhere fails (measured). The connection reaches the client program as libpq's environment from `state.LibpqEnv`, never argv. pgx-only keys are dropped by name, runtime parameters become `PGOPTIONS -c`, values end at the same six whitespace bytes pgx's `asciiSpace` ends them at (a vertical tab only one parser saw would hide a `service=` from the check), and a keyword the two would act on differently is refused by name before pgx parses: `sslpassword` and `krbspn` (no libpq variable), `service` and `servicefile` (a service file overrides libpq's environment where pgx lets the string override it), and `hostaddr` (pgx ignores it, libpq dials it). The same goes for `PGSERVICE`, `PGSERVICEFILE` and `PGSSLPASSWORD` inherited from the process, and an inherited PG* variable pgx never reads (`PGHOSTADDR`) is dropped from the child's environment rather than passed on. The host and port lists are rendered from pgx's resolved endpoints, primary then fallbacks, deduplicated (sslmode=prefer gives each host a TLS and a plain attempt), never from the text, because the two parsers map a host list's ports differently; an empty host is refused, because libpq reads it as its default socket. User, database and password must agree with pgx's parse. An inherited `PGOPTIONS` is kept ahead of the DSN's runtime parameters when the text names no `options`, as pgx sends it, and an inherited `PGPASSWORD` is redacted like the DSN's. It cannot go through `pgconn.Config`, which keeps no TLS file paths. `deployarchive` runs no subprocess: it is handed `BackupRequest.Dump` and `Target.Postgres`, and only `ops` and `e2e` import `pgdump` (depguard `pgdumpconsumers`). The client's major is checked against the server's (backup) or the dump's (restore) before anything is written, and an absent program is refused naming the package. A backup on a host that cannot run `pg_dump` (`pgdump.ErrClientUnusable`: absent, unrunnable, too old, or a DSN `LibpqEnv` refuses) still writes the identity-only archive (schema 3, the ledger recorded as external), sends it off-site as usual, and then fails naming what to install: refusing outright would leave the packaged timer capturing nothing on the day the client went missing, when the identity half is the only half a replacement host can be rebuilt from. A database that could not be read is not the client's fault and fails before anything is written: an identity-only archive sent off-site would become the newest one, ahead of the last complete archive.

**What the database holds decides a restore, and a database still holding this deployment's ledger is kept.** `planDumpLedger` reads `state.PeekPostgresLedger`, where "could not tell" is a refusal:
- no tables → `Install`;
- a pristine preflight whose migrations are not ahead of the archive's → `ReplaceEmptyLedger`, only with `schema_migrations` present and migrations recorded: empty tables with no billet bookkeeping are somebody's schema, refused;
- bound to this deployment → `KeepLiveLedger` (the host died and the database did not, so its rows are newer, and replacing them is `recover`'s job), but only over a billet ledger: tables with no `schema_migrations` are refused, and so is a ledger whose highest migration is below the archive's, which was restored from something older than this backup and would throw away rows the backup holds;
- bound to nobody but populated → refused unless `--external-ledger-attached`, then kept under the same two conditions;
- bound elsewhere, another schema or no schema → refused.

`pg_restore` puts a dump back into the schema it came from and `--clean` emits `DROP SCHEMA`, which aborts the single transaction when anything else lives there (measured), so the restore filters the schema's own TOC entries out and requires the schema to exist. It is a replacement, not an overlay: `--clean` drops only what the dump holds, so a ledger a later migration widened would keep that migration's tables beside a `schema_migrations` saying it never ran, and the next start would re-run it into an existing table. So `pgdump.Restore` lists the dump's tables in the planned schema, refuses a dump holding none (a manifest whose schema disagrees with its dump would otherwise empty one schema and restore into another), drops every other table of that schema in a transaction of its own (`state.DropTablesOutside`, which checks `current_schema()` first and bounds its lock wait at 30 s), and only then runs `pg_restore --schema=<s>` with the filtered list. The drop is one schema-qualified `DROP TABLE … RESTRICT` over every table at once, never CASCADE: the copies billet keeps are dumps of the schema alone, so a view, foreign key or inheriting table elsewhere that a CASCADE took could never be put back; a dependent anywhere else refuses the whole transaction, and a table in a hierarchy anywhere in the schema, kept names included because pg_restore --clean drops those itself, is refused outright (a partitioned table takes its partitions whatever the drop says; a partition or an inheriting child takes rows out of a parent anywhere). `pg_restore --list` quotes nothing and separates fields with spaces, so the name is read as the one field after the namespace and the owner as the rest (a role billet does not choose may have a space in it); that is unambiguous because no table in a ledger schema may have whitespace in its name, which `ExportPostgresSnapshot` refuses at backup and `DropTablesOutside` at restore, and a schema name with whitespace is refused before `--list` runs. THE WRITER RE-PROVES ITS TARGET: each restore hands `pgdump.Restore` a `state.RestoreInto` (the journaled database, the schema, and the binding it expects: this deployment's for a recovery or a put-back, none for an empty or pristine schema), `DropTablesOutside` checks all three on its own connection inside its transaction, and a data source naming more than one host or port is refused (by `archiveTargetLedger` when the command starts, before anything is sealed or fenced, and again by `pgdump.Restore`), because the drop and pg_restore each connect afresh and could reach different servers; pg_restore cannot re-prove, so it gets one endpoint or nothing. Every caller holds a durable copy of what is there, or proof nothing is, before it calls it. pg_restore sets `lock_timeout` to 0 itself, so a session setting cannot bound its wait. It restores a copy it has just verified by digest, never the archive's path, and reads the migrations and binding back through billet's connection before it lifts anything. `journal.LedgerRestored` lets a resume find its own committed restore on a ledger never bound. `journal.LedgerDatabase` is the database the run writes, journaled before its first write there; every later pass is held to it, the planner compares it before choosing any disposition (a restore resumed after its pg_restore committed would otherwise plan the ledger it finds as one to keep, wherever the connection points), and work recorded without it is could-not-tell. A resume after the restore committed, the recovery's seal (`deployarchive.ProveRestoredLedger`, called before `sealRecoveredDeployment` opens a handle that writes and may migrate) and `Finish` each prove the connection still reaches that database, at the archive's schema and binding, beginning with the archive's migrations, because none of them restores anything and each would otherwise act on whatever the connection reaches by then. `state.PostgresWriterBarrier` holds the writer's advisory lock for an instant before the plan is re-derived, which proves no billet write transaction on any host is mid-commit. A restore's abandon leaves what it put in the database and says so.

**All four pieces or none, and nothing is ever overwritten.** A ledger without its identity is a fresh authority that cannot see the compute the old one launched; an identity without the CA cannot issue a certificate; a CA without the App key cannot get a token. So `local backup` captures all four or refuses, and `local restore` installs each piece that is absent, accepts one that is byte-identical, and preserves and refuses one that differs, with no flag that overrides it. The App key is one per target: schema 3 carries `Manifest.Targets` and `github/<name>/app-private-key.pem` for every further target beside the `default` entry, a schema 2 archive reads as the single target `default`, a schema below 3 that names targets is refused, `BackupRequest.Targets` must name every further target the config declares or the backup refuses, and the restore planner refuses a config that does not name every archived target with the same identity, because installing half the credentials is the failure all-or-none exists for. The App key goes through `reserveKeyFile` and `writeKeyAtomically` rather than a second implementation. The authority allowlist is `ca.key`, `ca.crt`, `ca-previous.key`, `ca-previous.crt` and `authority-created` (outside the `ca` directory so its absence is detectable); half of either pair refuses. Authority planning walks the allowlist rather than the archive, or a leftover `ca-previous.crt` on the target is never looked at and the next start reads it as an active rotation. The archive's entry set is closed, so `Open` refuses an entry the planner has no case for.

**Backup, rotate and retire share `wirecert.LockAuthority`.** Rotate mutates five files in sequence; a reader without the lock captures a key from one generation beside a certificate from another, an archive that loads cleanly and verifies nothing. `VACUUM INTO` is the ledger mechanism and its constraints were measured: it cannot run in a transaction, is refused on the reader pool, refuses an existing destination (free no-clobber), creates the file 0644 (corrected), and holds the single writer slot while it runs; it is a consistent snapshot of a live database, so no `-wal` travels.

**Restore's exclusion is three local mechanisms and one human assertion.** The directory lock proves no control plane holds it (and nothing about an operator command, which opens without it); the maintenance fence reaches a handle already open, because `Tx` and `View` consult it on entry; the writer barrier proves a transaction that began before the fence has finished. None reaches another machine, so `--old-controller-fenced` is the operator asserting the old controller is stopped and disabled everywhere; without it two controllers share one identity, one CA and one App credential. Restore and abandon also take `LockAuthority`, directory then authority, matching the backup's order.

**The plan is re-derived inside the exclusion and only that one is acted on.** The planner is lock-free so `--dry-run` can report on a live deployment, and its output is printed for a person; acting on it deleted a ledger because it was empty when somebody looked. The presence of `billet.db` cannot be the refusal (a preflight `billet check` creates one); what proves a directory committed is the identity and the marker, and what proves the ledger replaceable is that every table a deployment writes is empty and the `admission` singleton is exactly the row its migration inserts.

**Publication goes file by file, hashes through a descriptor, and the identity check precedes the close.** Renaming a staged directory into place would leave the restorer holding the old `billet.lock` inode while a server locks the new one. `copyFile` hashes as it copies and publishes with an `os.Link` checked against the descriptor before and the destination after; `f.Stat()` on a closed descriptor reads as "not ours", so closing first leaves the staging copy of a ledger, or a key, behind on every success. Nothing unlinks a pathname it cannot prove it owns: the staging name is `os.CreateTemp`'s and the planner refuses an App-key path that is one of billet's own state files. Containment is `filepath.Rel` plus an `os.SameFile` walk, because a prefix comparison is wrong at `/` and on a case-insensitive filesystem.

**A failed restore leaves the ledger fenced with a journal.** A half-restored directory would start a control plane that mints whatever is missing. Re-running resumes (every install is no-clobber); `--abandon` removes only paths the journal records this run created and can still prove are copies of the archive's. The journal records a path before creating it. A fence a command raised comes down if it published nothing (`WriteMaintenanceFence` reports whether this call created it); past the journal it stays.

**A restore runs as root and hands back what it wrote.** On a packaged host the App key lands in root-owned `/etc/billet`, and systemd's `StateDirectory=` repairs recursively only when the top directory's owner is wrong, which after a restore it is not. `billet local up` repaired only `preflightState`, so a deployment restored perfectly and the control plane could not open one file of it. `lifeops.RepairPaths` takes its set from the plan just executed, plus the `ca` directory (a root-owned 0700 one cannot be traversed) and the two lock files the command created; a failed repair is reported and the command exits 0, because the next thing reached for after "the restore failed" is `--abandon`. The rehearsal found this, not a reading.
