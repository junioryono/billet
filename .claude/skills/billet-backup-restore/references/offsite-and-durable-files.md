# The off-site hop and durable files

Part of the `billet-backup-restore` skill. Each rule is stated in full, with the measurement or incident behind it.

**An archive on the disk it protects is not a backup, and billet owns both ends of one narrow hop.** With `backup.s3` set, `local backup` uploads what it just wrote (never instead), and `local restore --from-backup latest` fetches, verifies and restores on a machine holding only the binary; an `s3://` URL could not replace the config because it carries no region and SigV4 signs one into every request. There is no delete anywhere on the path, not in `internal/archivestore` and not in the generated IAM, so retention is the bucket's, through versioning and a lifecycle rule on noncurrent versions only. Every write is `If-None-Match: *`; the manifest is uploaded last so an interrupted upload is not something a listing offers; the local archive is written and verified first; the credential is env or IMDSv2. `billet check` reports the newest archive's age because a timer that stopped firing looks like one that works. `ErrNoSuchObject` is S3's `NoSuchKey` and nothing else: every 404 used to come back under that name, so a bucket that does not exist reached a restore as "no archive here" on the one day the machine is new and the operator has nothing but the binary — the fix is one line of config and the diagnostic was pointing at their backups (`internal/awss3`, and `billet-providers-aws` for the measurement). The package enables the packaged `billet-backup.timer` for nobody, and it is outside the service plan `local up`/`down` prove and unwind: `up` enables and arms it as a reported last step, `down` leaves it running, `status` does not report it. The Ansible host role renders and enables it on a role-managed control plane (`billet_backup_timer`). Both copies carry `RequiresMountsFor=` on the state directory, so a failed ledger mount stops the backup as it stops the server, and `EnvironmentFile=-/etc/billet/server.env`, so a PostgreSQL controller's backup has the connection string the server has. A `--from-backup` retry reuses the copy its first attempt kept when the manifests match.

**A remote record may not name a local file that is not durable yet.** `images pull` installed the paired kernel, synced it, changed its mode after the sync, renamed it, and committed Ceph metadata naming the file without flushing the directory; `fsync(2)` says flushing a file does not flush the entry, so a power loss left a complete published generation whose kernel vanished in recovery. `internal/durablefile.Installer` is the one ordering: metadata change, file sync, atomic rename, containing-directory sync, with the caller's write callback in front so a digest can refuse before anything is renamed. A failure up to the rename leaves nothing; a failed directory sync leaves the file, because the entry may already be durable and the retry re-verifies. The mode is set before the sync because a chmod behind it is metadata nothing committed. `durablefile.MkdirAll` flushes every ancestor even when the directory exists, by the resolved path as well as the name, because `os.MkdirAll` follows symlinked components and a state directory moved to another volume would have its lexical parents flushed and the real entries never committed. The reuse branch re-applies the mode and flushes through one `O_NOFOLLOW` descriptor, never `O_RDWR` (a `0444` kernel refuses it while chmod and fsync succeed read-only), and skips a chmod to the mode the file already has (a read-only mount answers EROFS). `TestAPullDoesNotPublishAGenerationBeforeTheKernelIsDurable` fails each step in turn and asserts `ImportGeneration` was never reached.

**A durable file is not a file nothing else will delete.** A concurrent `images reap` computes the kernels surviving generations need from the generations that exist when it looks, and between `installKernel` and `ImportGeneration` nothing names the new file, so it unlinks it correctly and the pull publishes a generation naming a kernel that is gone. The Ceph publish lock cannot cover that interval (it is cluster-wide with a six-hour stale bound). `cmd/billet/kernellock.go` is an flock on `<kernel dir>/.billet-kernels.lock`, keyed on the directory (two deployments on a host share one; a symlinked directory resolves to one file), waiting rather than refusing, held by the pull from before the install through a successful import and by the reap from before it reads the generation set through the deletion, always outside the publish lock. `--dry-run` takes no lock, because taking one creates a file. The reaper never unlinks the lock file, because unlinking a held lock detaches the path from the inode and the next billet locks a fresh file (proved by mutation: removing the skip alone stays green, removing it and widening the pattern goes red). `nodeKernelDir` is the one answer to where kernels live, because `--kernel-dir` once defaulted to a constant while the launch and the reaper read `node.firecracker.kernel_dir`.
