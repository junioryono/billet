# `billet local recover`

Part of the `billet-backup-restore` skill. Each rule is stated in full, with the measurement or incident behind it.

**`local recover` puts a deployment back over itself, and every step exists because the previous one cannot promise the next.** It refuses unless the archive is this host's own deployment; seals and waits on `alloc.Quiescence` (a seal stops admission and says nothing about what runs); refuses while anything is outstanding unless `--accept-failing-jobs`, naming each job; requires `--old-controller-fenced`; supersedes the ledger to `billet.db.superseded-<archive time>-<manifest digest>` (never deleted, the only record of the work that failed; RFC 3339 seconds collide for back-to-back backups); and seals again afterwards, because the first seal lived in the ledger just replaced and the archive's admission row is whatever it was, open. The intent guard sits above `planLedger`'s absent-ledger branch or a recover against an uncommissioned host plans as an install. A resume must not re-quiesce, because quiescing opens through `OpenAdmin` and the first attempt's fence refuses it.

**The fence outlives the publication.** `Execute` leaves a recovery fenced (`Result.Unfinished`), the command seals through `state.OpenMaintenance` (the one typed fence crossing), and `deployarchive.Finish` lifts the fence afterwards, under one acquisition of the directory lock, asking `state.PeekAdmission` (no lock, no migration, no fence) whether an operator seal is in place and refusing a journal still at `publishing`. `Finish` proves the seal rather than documenting it; before that the two tests named for the invariant demonstrated it did not hold. `phaseFinished` is written before the fence comes down so a crash on either side leaves something recognisable, and `--abandon` refuses a `finished` journal because undoing a complete sealed recovery removes the restored credentials.

**Order of a supersede: sidecars, sync, ledger.** Moving `billet.db` first and crashing left no ledger at the source, so a re-plan read an ordinary install and put the archive's database beside a `-wal` from a different one, which SQLite replays. A sync between the sidecars and the ledger is what makes the order durable rather than intended; `planLedger` refuses an absent ledger whose sidecars remain. The put-back moves the ledger first, the opposite order, because a resumed run looks for the ledger at the canonical name; the order is pinned by `Result.Restored`.

**An abandon reconciles the whole set by digest, and refuses whatever it cannot vouch for.** `supersedeLedger` records the digest of every file it moves before it moves anything; `putSupersededBack` compares what it finds against those, refuses a canonical file whose digest differs or that is present with nothing recorded, and refuses to lift the fence if it would leave no ledger. Every unresolvable state is an error that leaves the fence and journal standing, because `abandonLocked` reads nil as "ready to start" and a control plane repopulates an empty directory with a fresh ledger. Keys are base names, because a run started at `/srv/billet` and abandoned through a symlink recorded different spellings. Ownership is established before any fence is written, because a restore's abandon meeting a recovery's journal once raised a restore fence over it and neither command could proceed. `strayLedgerSidecars` treats an `Lstat` error as could-not-tell, not absent. The one bounded race: a connection open before the fence that closes afterwards checkpoints the WAL into the file whose digest was recorded; the abandon refuses and names the checkpoint.

**A PostgreSQL recovery keeps a dump of what it replaces, journaled before the archive's restore runs.** `supersedeDump` takes `pg_dump` of the live ledger behind the recovery's own fence (an `ExportPostgresSnapshot` naming no fence directory). It writes the dump to a private staging name, syncs it, records its digest in `SupersededDigests`, saves the journal, and only then links it no-clobber to `ledger.pgdump.superseded-<archive name>`. The archive's dump is restored after that, in one transaction. The journal also records the database the copy was taken from (`SupersededDatabase`) and the copy's pg_dump major (`SupersededDumpVersion`), and `SupersedePublished` once the copy and its name are synced; only then may the archive's restore run. A recovery replaces the ledger whatever its migrations, because the restore drops what the archive's dump does not name. It refuses another deployment's ledger, a host that is not already this deployment, a ledger bound to no deployment and an archive bound to none: the binding is the one fact that names this deployment's ledger wherever the connection points, so it is what every later pass holds the database to (a same-named database on another server is not bound to this deployment). The copy's migrations (`SupersededMigrations`) are journaled with it. A resume refuses a connection that now reaches another database than the copy's, and a published copy that is gone: past publication the archive's restore may have begun, so a fresh copy could record a ledger part-way replaced as the operator's. `--abandon` proves the copy before anything is restored: a journal that never reached `SupersedePublished` means the database was never touched; past it, a missing copy is refused (only it could say what the database held), and a copy whose digest the journal does not hold is refused. A journal missing the database, the major or the migrations is refused as could-not-tell. Then the database itself must be the copy's, at the archive's schema and bound to this deployment, the writer barrier is taken, the copy is restored through a verified copy with the recorded major, and the read-back must show the journaled database, this deployment's binding and exactly the copy's migrations (the archive's ledger, bound to the same deployment, would pass a binding check alone); any refusal leaves fence and journal standing. The copy is linked to `….abandoned`, the directory synced, and only then unlinked from its recovery name, so a crash leaves it at one name or both. An abandon that stopped after that finds this recovery's digest at the kept name, reads the ledger back once more, and finishes. There is no digest of a database; the journaled dump digest and the single transaction stand in for it. The seal after the restore goes through `app.LedgerRecovery` (`state.OpenPostgresRecovery`, an admin handle that crosses this host's fence and writes), because PostgreSQL's maintenance open is the upgrade probe's and writes nothing. `Finish` reads admission through `PeekPostgresAdmission`.

**The journal is schema 3 with a closed phase set and an explicit intent.** Schema 1 had neither digests nor intent; schema 2 changed what the digests meant under a number already in use, which is worse than changing the number. `journalSchema` is validated before any of it is read, so a downgrade cannot act on a newer record; `Intent` is validated at every exported mutation, and `Abandon` compares the journal's intent with its own, since `understood` proves a journal names an operation and not this one.
