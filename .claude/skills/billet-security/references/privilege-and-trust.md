# Privilege, trust classes and destruction

Part of the `billet-security` skill. Each rule is stated in full, with the measurement or incident behind it.

**The server is unprivileged; the node is a root custodian.** `billet-server.service` runs as `billet` with an empty capability set, `ProtectSystem=strict` and a syscall filter. `billet-node.service` runs as root because Firecracker needs TAP devices, block-device nodes, cgroups, chroots and verified process signalling, and Docker's rootful socket is host root anyway. The isolation boundary is downstream: the jailer drops each VMM to its own uid before Firecracker reads guest-controlled state, and guests never receive the Docker socket. On a Mac the node is a launch agent in the user's session, never root (Virtualization.framework needs the login keychain and tart's store is per-user).

**Trust belongs to a pool, not to the assignment that scaled it up.** GitHub may hand a registered scale-set runner any job in the set, so billet never derives authority from `push` versus `pull_request`. Every tier is `untrusted` unless promoted; a `trusted` tier requires a non-default runner group and an exact `workflows` allowlist, and the plane reads GitHub's `restricted_to_workflows` policy at startup and before every JIT mint, refusing drift. A repository target has no runner groups, so nothing on GitHub's side can restrict a pool there: every tier under one is untrusted, refused at load and again at `server.Run` with `trusted`, `runner_group`, `workflows` or `intercept`, which is also why docker cannot serve a repository target. The operator remains responsible for those workflows not executing untrusted revisions.

**Untrusted work needs a real boundary and a network of its own, and each backend answers differently.** `docker` refuses it outright (shared kernel). `firecracker` refuses until `node.firecracker.untrusted_bridge` names a separate network, because a microVM isolates the kernel and not the bridge, and the ordinary bridge reaches the Ceph cluster and the control plane. `tart` refuses until `node.tart.untrusted_isolation: softnet`, because tart's default NAT reaches the host and lets a guest spoof the bridge. `ec2` admits it only with `node.ec2.untrusted_security_group_ids`. `codebuild` refuses it outright: a reserved fleet's instances survive between builds and share cached data across projects by design, and on-demand builds are strictly weaker than an EC2 instance (the service role is readable from inside the build at `169.254.170.2`, and the same role reads the JIT parameter path, so untrusted forks and trusted tiers must never share a CodeBuild node). `TrustUnknown` is refused as malformed. `Accepts` and the flag builder are one function in tart, because written as two a mechanism admitted and not applied boots untrusted work on the trusted bridge.

**A registration proves who you are; only a command proves what you may do.** A node may mint exactly the registration for a launch it currently holds, remove exactly the runner the ledger attributes to it, and act on exactly the leases it was given. Authentication answers which host; the command table answers what it was given.

**Destruction is scoped by deployment identity.** Every container, instance, jail, VM directory and build carries the identity; `List`, `Find` and every destructive AWS statement filter on it, and a missing or unreadable tag is not ownership. Two billets on one machine share a hostname and must not see each other's compute.

**Never signal a pid you have not proved is still yours.** A pid file holds a number the kernel reuses and a node signals as root. The firecracker backend proves the pid still names its microVM by the `--id <jail id>` pair in `/proc/<pid>/cmdline` (matched as the pair, not the id anywhere in the line), re-checks with the pidfd held immediately before sending SIGKILL (a jailed VMM is its pid namespace's init with no SIGTERM handler, so the kernel drops a SIGTERM from the host; SIGKILL ends it), and treats an unreadable `/proc` entry as "could not tell" rather than "gone". Only "gone" lets teardown continue to unmap disks and remove the jail.

**Giving away a hard link gives away the inode.** The kernel is linked into each jail and the jail tree was then chowned to the VMM's uid, which chowned the host's one kernel to an account every VMM shares; the owner may `chmod` and write it, so one escape rewrites the kernel every later microVM boots without leaving the chroot. Chown the chroot alone; what a jailed process needs is to read. The same rule refuses a key file with more than one link in `lifeops`.

**Privileged operations go through a descriptor, never a pathname.** `os.Chown` follows symlinks and a name checked is not a name changed. Open `O_NOFOLLOW`, verify it is the same regular file the planner saw, `fchmod` before `fchown` (reversed, a chown that succeeds beside a chmod that fails leaves a key owned by the service account with whatever bits it had). `os.Root` does not refuse a symlink inside the root (measured); `unix.Openat` against a real directory descriptor honours the flag. `uid_t` is unsigned 32-bit, so parse ids with `ParseUint(…, 10, 32)`, reject `MaxUint32` and reject 0.

**The IAM grants have no delete where the credential would sit beside what it could destroy.** The backup grant (`internal/archivestore`) and the identity-store grant carry no delete; the CodeBuild controller sweep grant is list-and-delete on the registration path with no `GetParameter` and no KMS, and the missing KMS grant is not the confidentiality boundary under the default key (measured: `WithDecryption=true` returned plaintext with no `kms:*` anywhere), so the boundary is billet's request stating no decryption and a response type with no `Value` field. The build's service role is a different principal from the node role.

**Root-created identity artefacts are handed back to the service account by descriptor, named, never walked.** A privileged `ca show`, `check`, `ca rotate`, `ca sync --force` or restore creates files inside a directory the service account owns; systemd's recursive `StateDirectory=` repair runs only when the TOP directory's owner is wrong, and the installers make it right, so a root-owned `ca/ca.key` or `billet.lock` would stop the next start. `cmd/billet`'s hand-back runs lifeops' `RepairPaths` over the producers' own path helpers (`state.DeploymentIDPath`, `wirecert.CACertPath` and its siblings, `state.LedgerPath`, `state.DirectoryLockPath`): a regular file with more than one link, a file on another filesystem, a symlink or a type other than the one named refuses and changes nothing, so a planted hard link cannot give away the inode it aliases. The two lock files are re-owned whatever their previous owner (`retirement.RepairLocks`, `fchown` on the open descriptor, the inode kept so a holder's flock survives), and never unlinked or recreated.
