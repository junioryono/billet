# Cache bearers, interception and the Git proxy

Part of the `billet-security` skill. Each rule is stated in full, with the measurement or incident behind it.

**A cache bearer lives exactly as long as the compute it belongs to.** Every microVM gets its own 32-byte bearer scoped to its five drive slots; EC2 carries it in user data and sends it back only over HTTPS; it is never a cache key, a log field or a deployment secret. Cleanup marks the session closed before discarding, so a later guest request answers gone. Trust gates publication, not reads: an untrusted job may hydrate from the trusted baseline and its clone is discarded unpublished, so cached bytes are a deployment-and-site trust boundary and a private image pulled by one trusted job is readable by a later job in that boundary. Registry mirrors serve public content without an upstream credential.

**Interception terminates TLS for one host and serves three methods.** `ACTIONS_RESULTS_URL` carries artifact metadata as well as cache traffic, so interception terminates TLS only for that host and handles only three CacheService methods; a mistake there breaks a deploy. It is on by default only where the Actions cache's scope already holds, and an untrusted pool gets it (and the node's CA) only under `cache.publish: default-branch`, where nothing is served before the plane proves the job's ref.

**A cache publishes only what the ref GitHub proves may write, and reads are the pool's (#226, ADR-013).** Under `default-branch` a job's writes publish only for a completion whose `dispatch.CacheAuthority` is proven from GitHub's record of the run (never the launch assignment, never `ACTIONS_RUNTIME_TOKEN`, never `jobWorkflowRef` alone, which a feature branch can point at the default branch by calling a reusable workflow pinned `@main`) and names the session's exact lease, owner and repository; could-not-tell publishes nothing. Proving it needs the App's `actions: read`, which `github-app create` requests by default and which also reads runs, logs and artifacts: disclose it, and `billet check` accepts it as billet's own request rather than an edit. What a default-branch job publishes, every later job of the pool reads, a pull request included, so the namespace is a static repository and an untrusted pool's namespace (`<ns>.scoped/untrusted/…`) is unreachable from a trusted one's and from any guest-chosen key. Per cache, what a publisher can carry to its readers: images it pulled (Docker), whatever it left on a disk (sticky), archives it saved (Actions, scoped per ref as GitHub scopes them), build outputs and action results (Bazel, Go; a CAS blob is verified against its digest, an action result is the publisher's claim). The Git mirror carries only what GitHub gave: every fetch is authorised with the job's own header and a want the mirror may not answer goes to GitHub.

**The Git proxy holds a job's GitHub credentials for exactly one request.** The guest's credential helper hands the node the header checkout wrote; the node sends it only to github.com (a redirect is followed by the node, never relayed with the header), passes it to `git` only through `GIT_CONFIG_*` environment (never argv, where every process on the host reads it, nor a file, nor a log; `gitAuth` redacts itself), and keeps only a sha256 of it with the repository as the key of a one-minute grant. A later refusal from GitHub ends an earlier grant. `TestTheJobsHeaderIsNeverAnArgument` runs the node's git through a recording wrapper.

**No cache bearer is written where a job can read it after the fact.** The Bazel rc names `billet cache credential-helper`, which answers the bearer from the runner's environment and only for the node's own host (a helper that answered every host hands the token to any remote a workflow's bazelrc names); the gitconfig names `billet cache git-credential`, which answers only the node's host too. A host mount point is named by `sessionPathID`, a hash of the bearer, because the mount table and `mount`'s argv are readable by every local process.
