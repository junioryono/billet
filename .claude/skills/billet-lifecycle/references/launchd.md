# launchd: the Mac node

Part of the `billet-lifecycle` skill. Each rule is stated in full, with the measurement or incident behind it.

**On a Mac the node is a launch agent and a root daemon cannot do the job.** Since macOS 15 Virtualization.framework needs an unlocked `login.keychain` (it fails as `SecKeyCreateRandomKey_ios failed`, `Failed to generate keypair`, `Interaction is not allowed with the Security Server`, none naming a keychain); a headless SSH session leaves it locked, so a dedicated node wants automatic login and one first login through Screen Sharing. tart's store is per-user. The agent's PATH is not the shell's (launchd has no Homebrew prefix, so `tart` and `softnet` resolve to nothing), and `ExitTimeOut` is pinned to 88200 because launchd's default is five seconds (not the twenty the man page says) and zero means infinity. `billet local up` installs, starts, proves and enables the agents; run it as the account that will run the node, never under `sudo`.

**What launchd loaded is not what its plist says.** launchd reads a plist once, at bootstrap; `launchctl print` reports the loaded values, so a node can run a stale five-second drain grace while its file is byte-identical to the shipped one. `up` compares the loaded job's program, arguments, timeout and whole environment (a redirected `TART_HOME` makes the inventory describe another machine, which resells live guests). A `bootout` returns in zero seconds with the process still draining, the service in the domain as `state = SIGTERMed` with its pid; billet captures the pid first and waits for both the domain and the process. `launchctl kill TERM` would restart these agents (`KeepAlive{SuccessfulExit:false}`), so launchd's stop is `bootout`, and it comes LAST: `StopAndProve` first asks the process to drain, waits with no bound but the caller's for it to exit, and only then boots out a job with no process. launchd SIGKILLs a job `ExitTimeOut` seconds after the SIGTERM a bootout sends, and macOS 27 clamps an agent's `ExitTimeOut` to 60, so a bootout of a node still draining killed its jobs a minute in (#278); neither request below starts such a timer, a drained node exits 0, and `SuccessfulExit:false` does not restart it. THE ASK IS CHOSEN PER PROCESS BY WHAT THE RUNNING PROCESS SAYS OF ITSELF, never by the binary on disk, which a rollout may have replaced (#281). The node handles `launchd.DrainSignal` (SIGUSR1) as its first level and nothing more (`cli.Lifecycle.DrainOn` in `internal/cli`, installed by `HandleDrainRequests` in `cmdNode` after the upgrade probe returns): a repeat never counts towards the SIGTERM levels and it exits 0 exactly as its first SIGTERM does. Only once the handler is installed does a node on a Mac publish `<log dir>/.drain-<label>` (`PublishDrainReport`: schema 1, label, pid, the kernel start time from `sysctl kern.proc.pid` to the microsecond, `request: "SIGUSR1"` as the capability, release for diagnosis; not `ps -o lstart=`, whose text follows the caller's time zone and locale, which differ between an operator's shell and the agent). A stop whose report proves the service's pid (read no-follow, non-blocking, regular, exact member set, same pid, same start now) sends that pid the request by kill(2) on EVERY poll, re-proving the report immediately before each signal (launchd's `kill` would deliver to whatever it runs at that moment, which after a restart is a process that never said it handles the request), records nothing, and asks a restarted process again in its turn; a process that stops proving it once asked is waited for and asked nothing more. Every other process, a release before the request, one not yet reporting, one whose report is unreadable, malformed, another pid's or an earlier process's, takes the recorded SIGTERM path below UNCHANGED. Measured on macOS 26 (2026-09-30, a CGO_ENABLED=0 Go 1.26 probe): a Go process that has not asked for SIGUSR1 survives it and exits 0 later, because the runtime installs its own handler and drops an unwanted `_SigNotify` signal, so an older node sent the request by mistake does not die, it just never drains and the stop waits forever; that, and a process in the instant before its runtime starts, where the default action does kill, is why the gate exists. Mixing is safe for a node that has the handler: its first SIGTERM after any number of requests is still its first level. THE SIGTERM PATH IS ONCE PER PROCESS, ACROSS CALLS, through `launchctl kill TERM gui/<uid>/<label>` (which addresses the service's current process, never a pid read earlier that another process may have reused), because the node's second SIGTERM escalates its drain: before sending, the stop writes `<log dir>/.stop-<label>` naming the process's incarnation (pid and `ps -o lstart=` start time, the `started` seam), a retry that finds the same incarnation resumes the wait and sends nothing, a different process under the same pid is asked afresh, a record that cannot be written means nothing is sent, and the record is removed once the process is gone. `StopResult.Asked` says a drain was requested even when its end was not proved, so `local down` reports the unit as touched rather than claiming nothing was stopped. A process launchd restarts after one exits (a non-zero exit) is asked in its turn, up to `maxDrainRestarts` (3) per stop, beyond which the service is crashing rather than draining and the stop ends Unknown. A process named right after the ask that is not the one sampled means the service was restarted around the request: which of the two received the SIGTERM cannot be told, so the stop ends Unknown and asks nothing more, naming the record to remove. A `kill` that did not finish (an error, or launchctl ending at -1) may have delivered, so its record stays; only a proved refusal (a positive exit with the process alive) clears it. That ambiguity is the SIGTERM path's alone, and only a process not proved to handle the drain request still meets it. What neither path closes is a restart between the drain's end and the `bootout`: the bootout's SIGTERM is then the new process's first, under launchd's clamped grace. The drift check accepts a loaded `ExitTimeOut` equal to the declared value, or to `min(declared, 60)` only on a release that clamps (`sw_vers -productVersion` 27 or later, the `productVersion` seam; unreadable counts as unclamped), and refuses anything else, such as the five-second default of a stale bootstrap; refusing 60 refused every `local up` after the first on macOS 27. The disabled-override database is durable, keyed by label, outlives the plist and accepts labels that never existed: `uninstall` removes the plist, flushes that removal, then clears the override, because the reverse order leaves a window in which a login starts the node being uninstalled, and leaving it set makes the next install bootstrap a service launchd silently refuses to run. `Bootstrap failed: 5: Input/output error` means already loaded, still draining or disabled alike; diagnose with `print` and `print-disabled`. A parenthesised value (`(never exited)`, `(unlimited)`) is launchd saying there is no value. launchd reports a pid before the program has run a line, and there is no start timestamp and no `sd_notify`, so readiness cannot be proved; `up` says "the same pid survived a settle window" in those words.
