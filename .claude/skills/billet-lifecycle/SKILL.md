# The local service lifecycle

`internal/lifeops` inspects a host and decides what may be done to it; `cmd/billet/local*.go` are the commands that act. Everything here exists because a host can look correct from every angle billet checks and still be running something else.

**Every systemd fact in this file was measured on Ubuntu 24.04 / systemd 255, not read.** Several of them read the other way in the documentation, and each cost a live host to establish. Re-measure before trusting a claim that contradicts one of these, and add what you measure.

## The one that defeats everything built on `systemctl show`

`ExecStart=+/usr/bin/billet server …` runs the command with **full privileges no matter what `User=` says**, and:

```
$ systemctl show unit -p ExecStart --value
{ path=/usr/bin/billet ; argv[]=/usr/bin/billet server … ; ignore_errors=no ; … }
```

is **byte-identical** to the same unit without the `+`. The prefix is not in that answer. `-p ExecStartEx` is:

```
{ path=/usr/bin/billet ; argv[]=… ; flags=privileged ; … }
```

So any authorization decision about *what a unit runs as* must read `ExecStartEx` and require `flags=` to be empty. `ExecStartEx` landed in systemd v246; an absent answer is uncertainty, not "no flags".

**Do not try to read the prefix out of the unit file instead.** That was tried and broken in one round:

```ini
ExecStart=/usr/bin/billet server --config /etc/billet/billet.yaml
ExecStart =
ExecStart = +/usr/bin/billet server --config /etc/billet/billet.yaml
```

systemd accepts whitespace around the key, treats the empty assignment as a **list reset**, runs the third line, and `systemd-analyze verify` says nothing. A reader looking for the literal `ExecStart=` sees only the first line. systemd's own parse cannot disagree with systemd; a hand parser always can.

## Measured systemd behaviour

| Fact | Consequence |
|---|---|
| An absent unit answers `systemctl show` with **exit 0**, `LoadState=not-found`, empty `UnitFileState` | An error from `show` means the manager could not be asked, which is a different fact from "no such unit" and must not be flattened into it. An **empty** `LoadState` is neither — it is a reply billet cannot read. |
| `StateDirectory=` repairs ownership **recursively when the top directory's owner is wrong**, and does **nothing** when the top is already correct | Every run after the first leaves a root-created file under a correctly-owned directory unrepaired. `billet check` opens the ledger as the invoking process, so a root-run preflight leaves `billet.db` and `billet.lock` owned by root and the server cannot write them. |
| An empty `ExecStart=` **resets** the list | A unit's last assignment wins. Counting assignments and refusing more than one diverges from systemd in the safe direction. |
| `Names=` shows an alias only once its **link exists** | An `Alias=` declared in `[Install]` is invisible until something enables the unit. |
| `systemctl disable` follows `[Install] Also=` | Undoing an enable can undo more than the enable did — which was correct in the one case observed, and is not something to rely on blindly. |
| `Conflicts=` on a unit is a **stop** of the named unit when this one starts | A conflict reached through a unit that billet's own unit merely `Wants=` will stop the other service. This is systemd building a transaction, not an adjacency list. |
| A third unit's reverse dependency does not appear on ours until that unit is **loaded** | Reading dependency properties cannot enumerate the transaction. |
| `OnFailureJobMode` is `replace` and `FailureAction`/`SuccessAction`/`StartLimitAction`/`JobTimeoutAction` are `none` on the packaged units | Their harmless value is a **word**, not an empty string, so "refuse if non-empty" refuses every correct host. Same for `DynamicUser=no`. |
| `CapabilityBoundingSet` is the **full set** on the node (it is root) and empty on the server | "Non-empty is suspicious" is wrong for this one. |
| `Type=exec` returns from `start` as soon as `execve` succeeds | Only `Type=notify` makes a successful `systemctl start` mean the process reached `READY=1`. `up`'s central claim is untrue on any other type. |

## Measured launchd behaviour

There are two service managers now: `internal/lifeops` drives systemd, `internal/lifeops/launchd` drives launch agents, and `cmd/billet/local*.go` imposes one ORDER on both. Everything here was measured on macOS 26 by running real agents — `launchd.plist(5)` is wrong about at least one of them — and lives in `internal/lifeops/launchd/reallaunchd_test.go`.

| Fact | Consequence |
|---|---|
| **A loaded job is not its plist.** launchd reads the file ONCE, at bootstrap, and keeps what it read; `launchctl print` reports the LOADED values | Replacing the file changes nothing about the running job. A node can run a stale five-second `ExitTimeOut` while its plist is byte-identical to the shipped one, and comparing the FILE certifies it — after which the next logout SIGKILLs it five seconds into a drain allowed 88200. `up` compares the loaded job's program, arguments, drain grace and WHOLE environment. |
| The **disabled-override database** is durable, keyed by LABEL, and survives both a bootout and removal of the plist. It accepts labels that never existed | This is the launchd sibling of `Names=`, `Also=` and masked-or-linked: an enablement fact invisible from the obvious surface, so it will be assumed absent. A label left disabled with no plist to explain it makes a LATER install bootstrap a service launchd silently refuses to run. `uninstall` removes the plist, FLUSHES that removal, and only then clears the override — the reverse order leaves a window where a login starts the node being uninstalled. |
| `Bootstrap failed: 5: Input/output error` is returned for **already-loaded, still-draining AND disabled** alike | Never interpret it. Diagnose a failed bootstrap by re-reading `print` and `print-disabled`. |
| A plain `bootout` returns in **zero seconds** with the process still draining. The service stays in the domain as `state = SIGTERMed` WITH its pid, and the record disappears only when the process exits | Neither the command's return nor the service's absence is a stop. `SIGTERMed` is the launchd `deactivating` and must never be in a stop-proof allowlist. billet captures the pid first and waits for the service to leave the domain AND that pid to die. |
| `launchctl kill TERM` on a `KeepAlive{SuccessfulExit:false}` agent that exits non-zero **restarts it** | The stop primitive is `bootout`, never `kill` — which is also why the clean-stop rule below (a deliberate stop exits 0) is load-bearing on macOS. |
| launchd's default `ExitTimeOut` is **five seconds**, not the twenty the man page says | Both shipped plists set it explicitly, and a test pins the number by asking launchd about an agent that sets none. |
| `launchctl print` reports **no start timestamp**, and there is no `sd_notify` | Readiness cannot be proved. All that can be established is that the same pid survived a settle window, and `up` says so in those words rather than printing "ready". |
| A parenthesised value — `last exit code = (never exited)`, `(unlimited)` — is launchd saying **there is no value** | Treating it as unparseable made every freshly started agent an error, so billet could not read a single healthy job. |
| launchd reports a **pid before the program has run a line** | Found by a test whose fixture had not installed its TERM trap yet. A pid is not a running process; wait for something the program itself did. |
| macOS has no `/var/lock` and no `/usr/local/var` | The lifecycle lock needs a user-owned path there, and `up` refuses with `sudo mkdir -p` rather than creating root-owned directories it cannot. |

## The rules `up` acts by

**On systemd it finishes a prepared host and writes nothing structural.** No unit files, no service account. Unit provenance is a problem this command cannot settle there — the Ansible role deliberately renders its own units, so "differs from the packaged unit" is the ordinary state of a role-managed host and must never be a refusal. A unit billet did not install is *named*, not replaced.

**On launchd it DOES write the service definition, and a difference IS a refusal.** The two rules look opposed and rest on the same reasoning: what makes a systemd difference ordinary is that something else legitimately renders those units. Nothing else renders a plist — there is no macOS package and no role — so a difference there is either an operator's own edit or a stale billet, and both want a person rather than a silent overwrite. Say which platform you mean before quoting either rule.

The consequence is worth knowing, because it is not obvious from the refusal: after a `billet local down` the label also carries a durable disabled override, so an operator whose plist has one added `PATH` entry gets a refusal about the FILE that does not mention the override at all. Moving their file aside and running `up` again clears both.

**GitHub must be proved, not unrefuted.** `billet check` exits 0 when the probe was skipped (`BILLET_MAINTENANCE=1`) or could not complete, which is right for a diagnostic and is not consent to start a control plane on somebody's organization. Only the explicit *verified* verdict permits starting a server.

**A restart is a drain, and a drain destroys the jobs on the host.** An active service is never touched. `deactivating` is a node draining — starting *through* it is how a converge destroys the work the drain is waiting for — so every `ActiveState` is mapped explicitly and anything unrecognised refuses.

**Start, prove, then enable — except where the manager cannot start a disabled service.** launchd refuses to bootstrap a label carrying a disabled override, so there is no order there in which the proof comes first; `UnitPlan.EnableBeforeStart` declares that, `up` reports it, and what protects the host instead is the unwinding. It is a weaker guarantee and is said in those words rather than being allowed to read like the systemd one. On systemd, never `enable --now`: enabling first commits a unit to every future boot before anything has established it can run. A service that was already running is proved stable immediately before it is enabled, because the plan's sample is minutes old by then — `billet check` talks to GitHub in between.

**Only what this run committed is unwound**, and only the exact state `enabled` shows the links this call wrote. `systemctl enable` is idempotent, so its success says nothing about who performed the transition. Rollback runs on `context.WithoutCancel` with a timeout, because the likeliest way into it is the operator's own interrupt — including the query that decides whether to unwind.

**Privileged operations go through a descriptor, never a pathname.** `os.Chown` follows symlinks and a name checked is not a name changed. Open `O_NOFOLLOW`, verify it is the same file the planner saw and a regular one, then `fchmod` **before** `fchown` — reversed, a chown that succeeds beside a chmod that fails leaves a private key owned by the service account with whatever permissions it had. Refuse a file with more than one link: a hard link is the same inode under another name, and one of these files is an App key.

**`uid_t` is unsigned and 32 bits.** `4294967295` is an ordinary positive `int` on a 64-bit platform and becomes `(uid_t)-1` at the syscall boundary — the "leave this unchanged" sentinel — so parse account ids with `ParseUint(…, 10, 32)` and reject `MaxUint32`. Reject uid/gid 0 too: `User=billet` says which *name* the service runs as, and what that name resolves to is the account database's answer.

## The rules `down` acts by, and the one sentence the whole drain program reduces to

**The seal is not the authority; the barrier is.** Sealing stops new work being *admitted*. It says nothing about what is already running, and it does not take effect at the instant it is run — a listener learns about it on its next poll, and an offer accepted just before that is real work with real compute behind it. So "is it safe to stop this now" is answered by asking what the deployment is still HOLDING (`alloc.Quiescence`), never by the fact that a seal was taken. Anything that waits on the seal instead of the barrier is wrong.

**`down` is a drain that then stops**, in that order: seal → wait → stop node → stop server → disable both. Stopping first would be `systemctl stop` with extra steps, and stopping a node mid-job fails somebody's build — GitHub does not requeue a job whose runner vanished. There is **no default time limit**: a job can run for hours and billet imposes no limit on one, so any default is a guess that ends in killed work.

**Provenance decides who may clear a seal, and it is load-bearing in both directions.** A `local-down` seal is cleared by the next successful `billet local up`; an `operator` seal is not, and `up` reports that it left one alone. Reopening a maintenance seal because a service restarted admits work into somebody's window silently, and their evidence is a job running during it. `down` escalates nothing and overwrites nothing: an operator's seal is left as it is.

**A row billet cannot read is never sealed over.** `AdmissionUnknown` is the fail-closed zero value on purpose. Writing a `local-down` seal onto it turns "I could not tell what this says" into a seal the next `up` CLEARS — opening a deployment on the strength of a row nothing understood. Same for a sealed row whose provenance this build does not issue.

**Only states that PROVE no process remains count as stopped.** `systemctl stop` returns when its job completes, which says nothing about whether the unit came back. Refusing only `active`/`activating` accepted **`deactivating`** — still stopping, process alive — after which the command went on to stop the other unit and report the host down. Allowlist `inactive` and `failed` (nothing is running, which is the question; how it ended is `Result`'s job), treat an empty answer as uncertainty, and treat a state a future systemd adds as not proof.

**A node-only host cannot fence anything, and says so.** There is no ledger there to seal, so nothing on that machine stops the control plane assigning it more work. Stopping the node drains what is on it — `TimeoutStopSec` is 88200s, sized for the maximum drain plus teardown — and the report names `billet drain` against the control plane as what actually fences the deployment. Refusing to run there was proposed and rejected: it makes the command useless on the common fleet shape and pushes operators to plain `systemctl stop`, which has no drain reporting, no disable and no identity check.

**A deliberate stop must exit 0.** Returning `ctx.Err()` from a SIGTERM shutdown made `systemctl stop billet-node` exit 1 and leave the unit `failed`, so `systemctl is-failed` answered yes after every supported drain. That includes the give-up path: compute left running by an escalated drain is re-adopted on the next start, and a non-zero exit would additionally have systemd mark the *service* failed, which is a claim about the service rather than the compute.

**`down` is several systemd jobs, not one**, so a failure part-way through must report where it left the host — what was stopped, what was disabled, and by name any unit that is **stopped but still enabled**, which comes back at the next boot. Read admission at that point rather than asserting it: a resume elsewhere can have cleared the seal while the stops ran, and the seal is the one fact an operator relies on before walking away.

**One lifecycle command at a time**, via a host flock taken immediately before the first mutation — not at the top, or a config the packaged units cannot use gets reported as a failure to create a lock directory. `--dry-run` never needs it. The lock does not reach another machine; the admission generation is what makes a remote change observable.

**THE LEDGER BARRIER IS THE FIRST STAGE, NOT THE ANSWER, and a second one asks the machines.** What the ledger cannot see is compute whose lease has already gone — an in-memory destroy obligation, or a launch whose lease was reclaimed — and neither survives a restart of the process holding it, so "the ledger records nothing outstanding" was never "no job is running on this machine". Both leave an instance carrying the name billet gave it, so the host's own `provider.List` still has it, which is why an inventory query is the instrument and the ledger can never be.

**What makes an answer EVIDENCE is the ordering, not the asking.** `billet drain --wait` writes a durable barrier request (a singleton, scoped to the admission generation) and the CONTROL PLANE observes it — the command is a separate process with no handle to the running plane, and a sealed idle deployment dispatches nothing else at all. The plane waits for `Quiet()` first, because a launch may legitimately be dispatched while a lease is open; then for each host it captures `nodes.dispatch_generation` and `nodes.epoch`, queues a `CommandInventory` behind everything already in that host's serial queue, and records the answer only if BOTH fences are still where they were. A launch dispatched in between makes the recording transaction match nothing. **The bump and the enqueue happen under one hold of `Plane.mu`, bump first** — outside it, a launch could advance the fence, let a barrier read the new value and queue itself ahead, and then append behind it.

**An empty answer is believed only after `computeAbsenceGrace` of CONTINUOUS emptiness, for every backend.** What is stored is a run, not a snapshot: an error, a non-empty list, or either fence moving deletes the row. The host-backend fast path custody has is deliberately not taken here — custody grants a prompt absence only where the launch or inventory was causally observed, and a barrier has no such observation about the class it exists for.

**WRITING A TEST FOR THIS MEANS FIRST GETTING A STRAY TO STAY PUT, AND ON REAL HARDWARE IT WILL NOT.** Measured on the reference host: 45ms after a lease went terminal the node logged `destroying an instance whose lease is gone`, so releasing a lease under a running container races billet's own orphan sweep and the test passes or fails on load. The sweep is correct and it is also the shape of the thing — the window this barrier exists for is the one where the host that WOULD sweep is the host being stopped. So `internal/e2e/computebarrier_test.go` runs a real job to completion, stops the control plane, and only then puts a real container carrying a lease name the ledger never issued. **STOPPING THE CONTROL PLANE IS NOT WHAT MAKES THAT SAFE**: cancelling it does not recall a `CommandSweep` the node has ALREADY been given, and the node runs commands on its own goroutine, so a sweep delivered just before the stop destroys compute placed just after it. The stack sets its reaper tick to an hour instead, so none is ever dispatched. Two more from the same review: `provider.List` reports EXITED containers and `Runner.Instances` reports their lease ids just the same, so a stray has to be asserted `Running` or a command that returns immediately satisfies every assertion below it; and a node's drain has no timeout, so `run`'s stop must be reachable from CLEANUP as well as from the happy path — its node loop is given the operator's `Hurry` channel for the same reason, or a scenario holding compute hangs instead of reporting the assertion that failed. Everything there is real — a real dispatch, the real node wire, a real container runtime — and the one thing steered is the ALLOCATOR's clock, through `alloc.WithClock`; it governs lease TTLs and the quarantine grace too, so the six-minute jump is taken only after the ledger is empty and the server is stopped.

**AND ON THE REAL WIRE IT RUNS BEFORE THE BODY IS DECODED AND BEFORE THE CERTIFICATE IS AUTHORIZED, on the certificate's own common name.** Every refusal ahead of the semantic checks is a permanent one a node does not retry: `decode` is strict, so an unknown field from a node rolled ahead of this control plane is refused before anything is judged, and `authenticated` checks REVOCATION — an operator taking a machine's credentials back, which says nothing whatever about whether that machine is still running compute. So `certificateName` reads the verified chain WITHOUT the revocation check and the authorization decision follows it; the three duplicated lines are the price of keeping "did this host arrive" separate from "may it proceed". A revoked node that keeps arriving can keep its own host unprovable, which is the honest answer rather than a denial of service. **A loopback wire requires no certificate, so there NOTHING can name the host and every run goes** (`InvalidateEveryBarrierRun`), at the very top rather than after the body is read. That one placement closes the rest of the class: the method check, the strict decoder and `maxBody` all refuse before any body exists, all of them permanently, and each is an arrival billet cannot attribute. On loopback the fleet is one machine, so "every host" is that host. **Both forms answer 503 when they fail**, which is why they are ahead of everything instead of tucked into the refusal paths — `decode` writes its own 400 first, so an invalidation attempted after it could only be LOGGED, and a node reads that 400 as permanent and stops retrying, leaving a proof standing on a ledger blip. The registration route is also deliberately NOT method-qualified, because `POST /v1/register` lets ServeMux answer 405 before the handler runs and a certificate holder that reached the path has arrived whatever verb it used. **`InvalidateBarrierRun` reads before it writes**, and that is not tuning: it runs ahead of the revocation check, so a credential an operator has taken back could otherwise reserve SQLite's single writer on every request and starve every scheduling decision in the process.

**THREE RESIDUALS ARE LEFT OPEN DELIBERATELY, and all are stated rather than narrowed into invisibility.** Two hosts sharing one name is the third and it is the pre-existing one: a refused arrival discards the proof once, and the OTHER process — same name, same certificate — can rebuild it by answering the next few barrier rounds. billet cannot tell those two apart, which is what `ErrSuperseded`'s own diagnostic says out loud, and a durable per-name blocker would make one misconfigured registration permanently unprovable until somebody decommissioned the host. A registration that BEGINS and then fails leaves no durable trace — `finishRegistration` clears the in-flight marker — so the incumbent can build a fresh run afterwards while whatever was arriving is unaccounted for. Making that fail closed needs a durable unsettled-registration fence, and the failure mode of one is worse than the gap it closes: a host that fails to register once blocks every later drain until a person intervenes, which is precisely the "safe answer and an unusable one" the compute barrier rejects for membership. In practice a node retries every few seconds and the window shuts. And `billet local down` re-reads the clearance immediately before the first stop, which NARROWS but does not CLOSE the gap between reading and stopping: a registration landing in between is still possible, because that is a read in one process and a stop in another's world. Closing it needs the control plane to refuse registrations for the duration of the stop and hold that refusal until its node wire is closed — a protocol feature, not a tighter loop.

**A REGISTRATION DISCARDS THE HOST'S STORED RUN BEFORE THE REQUEST IS EVEN JUDGED.** `Plane.ArrivingForRegistration` runs first on BOTH paths — `Plane.Register` for the in-process wiring and `handler.register` for every node on the wire, which assembles the sequence itself so it can read the launched leases in between. Putting it on only one is a fix in the path nobody uses, and putting it after `checkRegistration` misses the case that matters most: a PERMANENTLY refused registration — an incompatible protocol range, zero capacity, an undeclared site — is still an authenticated host reporting live compute, and the node does not retry, so a proof left standing there stays standing. Rolling a control plane past an old node's range is exactly that shape. It is deliberately NOT subject to "a refusal changes nothing", which governs the in-memory inventory `beginRegistration` clears: that one comes back only from a successful registration, while a barrier run comes back from the loop asking again. The plane already clears the incumbent's in-memory inventory in `beginRegistration` for the same reason; the durable run needs it too, because the ledger's epoch — which is what fences a run — does not move until `RegisterNode` lands, and `billet drain` reads that ledger from ANOTHER PROCESS where `p.registering` is invisible. In between, a completed run reads as current and the fleet can be reported clear about a host whose new incarnation may hold compute the old one never saw. The dispatch fence beside it (`pending.expectedLedgerEpoch`, plus the `registering` check) is a DIFFERENT guarantee: it stops a superseded process ANSWERING, and cannot invalidate a proof already stored.

**A HOST SAYING IT IS RUNNING SOMETHING BEATS A COMPLETED RUN, and this is the one place the ordinary sweep's telemetry is consulted.** The two coexist by construction: a create the provider accepted but has not yet listed is invisible to the barrier's own samples, so a run completes around it, and then the host's ordinary sweep reports the instance. NO FENCE MOVES — the launch predates the barrier and the registration has not changed — so without this the finished run reads as proof while the host says otherwise, and `billet nodes decommission` records the exclusion as PROVEN. Safe in one direction only, which is why it may BLOCK and could never CLEAR: this is `node_inventory`, stale by construction, and believing it when it says "empty" is the stamped-inventory design rejected when the compute barrier was built. `provenBy` is the single definition both the fleet report and the decommission transaction read, so the two cannot disagree about one host.

**AND THE PROOF IS TWO OBSERVATIONS, NEVER ONE OBSERVATION AND A CLOCK.** The run's proven span is `observed_at − empty_since`, so an empty answer must land at or after the far end of the grace; the current time does not enter the predicate at all. The first version compared `now` against `empty_since + grace` and shipped — elapsed wall-clock authorising a claim about a machine, which is the thing this codebase refuses everywhere else, and it failed exactly where the grace exists to help: a host that answered empty ONCE and then disconnected (a launch the daemon had accepted but not yet listed, and a node that dropped a second later) aged into "proved clear" five minutes on, with the epoch and dispatch fences both still matching because nothing had happened to move them. Silence AFTER a proof is established is still fine, and is a different case.

**`--without-compute-proof` is the named escape, and it prints a DIFFERENT conclusion.** The proof cannot always be obtained: a host that is off, or negotiated a wire below `nodeapi.VersionComputeBarrier`, never answers. `local down` also skips the stage — saying so — when this host's control plane is not running, because that is what would ask. A waived proof must never read like an obtained one.

**A node-only host still cannot prove anything**, for the same reason it cannot seal: the question goes through a control plane on another machine. `billet drain --wait` there covers it.

**`billet nodes decommission` is the membership escape, and it must not launder uncertainty.** "Every registered host" never converges — a node row is durable and a start marks the fleet unreachable rather than removing anything — so a retired machine would block every drain forever. It requires a current proof, or `--force` records the exclusion as **durably unproven**, which `billet status` and every later drain name rather than reporting the fleet clear. It writes `nodes.drained`, reconciling a column the schema has carried since migration 1 that nothing had ever written; re-registration clears it.

## The rules `backup` and `restore` act by

**A deployment is FOUR things and they are useless apart**: the SQLite ledger, the deployment identity, the GitHub App private key, and the node-wire authority. A ledger without its identity is a fresh authority that cannot see the compute the old one launched; an identity without the CA cannot issue a node certificate; a CA without the App key cannot get a token. So `billet local backup` captures all four or captures nothing, and `billet local restore` installs all four or installs nothing — the requirement is worded as a **refusal** for that reason, and neither command has a flag that overrides it.

**The authority unit is larger than "the key and the certificate."** `authority-created` lives OUTSIDE the ca directory deliberately, so that directory going missing is detectable — an archive that captured only `ca/` would restore an authority with no witness, and the next loss would read as day one and mint a replacement. `ca-previous.key` is operationally REQUIRED during a rotation, because it signs the certificate the control plane presents until every node has renewed. An allowlist rather than "copy the ca directory": a crashed `ca rotate` leaves `ca.crt.new` behind, and copying whatever is there puts a half-minted authority into an archive that says it is complete. Half of any pair is a refusal.

**Backup, rotate and retire share one lock.** `wirecert.LockAuthority` — flock on `<state_dir>/ca.lock`, non-blocking. Rotate mutates five files in sequence, so a reader without the lock can come away with a key from one generation beside a certificate from another: an archive that loads cleanly and verifies nothing, discovered on the day it is restored. `Rotate` and `Retire` take it THEMSELVES rather than trusting the CLI, because they are exported entry points. The CA readers on the serving path still do not take it, and they no longer need to: the reader is a control-plane START, and every instant of a rotation is made a state it answers correctly by publication ORDER instead. `ca-previous.crt` says a rotation was STARTED (what to trust) and `ca-previous.key` says it is COMMITTED (what to present with) — Rotate writes the certificate then the key, Retire removes the key then the certificate, and a reader takes them in that same order, so a certificate with no key beside it always means “not committed” and presenting with the CURRENT authority is correct there. The one torn read the current pair's two renames can produce — the new `ca.key` beside the old `ca.crt` — is repaired from `ca-previous.key`, which Rotate syncs before the first rename. A WAITING reader lock was the other candidate and was rejected: `billet local backup` holds this across the whole ledger snapshot, so a control plane that would not start while a backup ran is worse than the diagnostic it fixed.

**`VACUUM INTO` is the ledger mechanism and its constraints were measured.** It cannot run inside a transaction, it is refused on the query-only reader pool, and it REFUSES an existing destination — so it goes through the writer connection outside `DB.Tx`, and no-clobber comes for free. It is a consistent snapshot of a LIVE database, so `billet.db-wal` need not travel. It creates the file **0644** under the usual umask, which is corrected explicitly. And it holds the single writer slot for its duration, which is said out loud rather than discovered.

**The plan is re-derived INSIDE the exclusion, and only that one is acted on.** The planner runs with no lock on purpose — `--dry-run` has to report on a live deployment without touching it — and its output is then printed for a person to read, so minutes pass before anything runs. An operator command holding an `OpenAdmin` handle can commit in that window, and the plan says the ledger is an empty preflight one that may be DELETED. The writer barrier does not help: it proves the writers have finished, which is not a claim about what they wrote. Re-planning under the fence is what makes "this ledger is empty" true at the moment the delete happens rather than at the moment a person read it.

**Restore's exclusion is three local mechanisms and one thing only a person can assert**, and no part is redundant:

1. The **state-directory lock** proves no CONTROL PLANE holds it. It proves nothing about an operator command, which opens through `OpenAdmin` deliberately without it.
2. The **maintenance fence** closes the ledger to every new handle AND to one already open — `Tx` and `View` consult it on entry — which is the only thing that reaches a command already in flight.
3. The **writer barrier** proves a transaction that began BEFORE the fence has finished. The fence is checked when a transaction starts, so a handle that got past it a moment earlier is still free to commit.
4. **`--old-controller-fenced`** is the operator asserting the old controller is stopped and disabled EVERYWHERE. None of the three above reaches another machine, and restoring while the old controller can still start produces two authoritative controllers on one identity, one CA and one App credential with diverging ledgers.

Restore and abandon take **`LockAuthority` as well**, because they write and delete the same five files a rotation mutates and `ca rotate`/`ca retire` hold only that lock. The order is directory then authority, matching the order a backup takes them in. Without it a `ca retire` alongside a restore deletes the ca-previous pair the restore has just published, and the restore reports success while every un-renewed node loses the authority it still trusts.

**Authority planning walks the ALLOWLIST, not the archive's contents**, and that direction is the one that was missed. A target holding a `ca-previous.crt` from an abandoned rotation, restored from an archive that is not rotating, would never have that file looked at: the current authority installs, the restore reports success, and the next control-plane start reads the leftover as an ACTIVE rotation and tries to serve a certificate whose key is not there. An allowlisted file the archive does not carry is preserved and refused, exactly like one whose bytes differ.

**The archive's declared entries are a CLOSED set.** Publication walks a fixed list of items, so an entry a manifest declares and the planner has no case for would pass every integrity check — the file is there, the digest matches — and be silently left behind by a restore reporting success. `Open` refuses an entry schema 1 has no place for.

**Publication never replaces the state directory.** Files go in one at a time, so `<state_dir>/billet.lock` keeps the inode the restore is holding. Staging a directory and renaming it into place would leave the restorer holding the OLD lock while a control plane happily locks the new one — which is the thing that makes the whole lock argument false.

**The fence stays up when a restore fails, and the journal with it.** A half-restored directory holds some of the pieces that make it this deployment and not the others, so a control plane starting on it would mint whatever is missing. Re-running resumes — every install is no-clobber and every decision idempotent, so the plan re-derives — and `--abandon` removes only the paths the journal records this run as having created, and only those it can still prove are copies of what the archive holds. The journal records a path BEFORE creating it: a crash between the two leaves an entry with no file, which an abandon tolerates, where the other order leaves a credential nothing knows about.

**AN ARCHIVE ON THE DISK IT PROTECTS IS NOT A BACKUP, and billet owns BOTH ENDS of one narrow hop rather than either.** The directory stays the contract — the manifest's digests are there so somebody else's tooling can carry it, and leaving `backup:` out is a supported answer — but `backup.s3` makes a backup upload what it just wrote and `--from-backup` restore straight from it. The FETCH is why both ends: on the day this is used the machine is new and holds the binary alone, and upload-only leaves an operator installing another tool mid-outage. An `s3://` URL cannot replace the config, because it carries no region and SigV4 signs one into every request. Five rules hold it up. **There is NO DELETE anywhere on the path** — not in `internal/archivestore`, not in the generated IAM — so the credential on the one host that also holds the App key cannot destroy the copies that exist to survive losing that host; retention is the bucket's, through versioning and a lifecycle rule on NONCURRENT versions only, since expiring current objects would remove backups on a timer. **Every write refuses to replace** (`If-None-Match: *`). **The manifest goes LAST**, and its presence is what makes a prefix an archive, so an interrupted upload is not one anything will offer. **The local archive is written and verified first, always**, and a failed upload says the directory is still complete rather than reporting a backup that failed. And **the credential is env-or-IMDSv2 only**, the fleet's own resolver adapted rather than reimplemented. `billet check` reports the newest archive and its age, because an unwatched backup is no more a backup than an untested one: a timer that stopped firing looks exactly like one that works. The packaged `billet-backup.service`/`.timer` are NOT managed by `billet local up`/`down`/`status` — those own the two services that hold compute and a ledger, and their whole safety content is the order they act in.

**A RESTORE RUNS AS ROOT AND MUST HAND BACK WHAT IT WROTE, and every reason this was missed is worth keeping.** On a packaged host the command has no choice about being root — the App key lands in root-owned `/etc/billet` — so everything it publishes is root-owned inside a state directory the service account owns. `StateDirectory=` does not save it: measured on systemd 255, it repairs recursively only when the TOP directory's owner is wrong, which after a restore it is not. And `billet local up`, which the restore's own output named as the next step, repairs `preflightState` — the five files `billet check` can create — and no part of the authority, so `ca/`, `ca.key`, `ca.crt` and `authority-created` stayed root's however many times it ran. The result was a deployment that restored perfectly and a control plane that could not open one file of it. `RepairPaths` takes the set from the PLAN the restore just executed rather than from a list beside the repair, because a list is what was wrong; the three additions no action publishes are the `ca` DIRECTORY (a root-owned 0700 one cannot be traversed at all, so the authority under it is unreachable however its files are owned) and the two lock files the command created by taking them. A failure to repair is REPORTED and the command still exits 0: the restore is finished and correct by then, and the next thing an operator reaches for after "the restore failed" is `--abandon`, which deletes what that run installed.

**And none of that was found by reading.** `scripts/restore-rehearsal.sh` runs the real `.deb` in a container that has never run billet and does what an operator does; it failed on its first run, at `billet server --upgrade-probe` under the service account, with `permission denied` on the App key. The Go half — `internal/e2e`'s `TestARestoredDeploymentServesTheFleetThatTrustedTheOldOne` — cannot see any of it, because it never leaves the process. When a rule depends on what a service manager or an account database does, the rehearsal is the evidence and the unit test is the reading.

**`billet local recover` PUTS A DEPLOYMENT BACK OVER ITSELF, and every one of its steps is there because of what the previous one cannot promise.** Restore refuses a commissioned deployment — its ledger is a live capacity record — so this is the operation for the ordinary disaster shape, and the design argued it must be separate rather than a flag on restore. It refuses unless the archive is the host's OWN deployment (the identity on disk against the manifest, the same check restore makes, so it can never relabel a host); it SEALS and waits on `alloc.Quiescence`, because a seal stops admission and says nothing about what is running; it refuses while anything is outstanding unless `--accept-failing-jobs`, which names each job by tier, node, phase and run id — and says out loud that compute whose lease has already gone is not in that list. **Three things about it were found by running it rather than by reading.** The intent guard has to sit ABOVE `planLedger`'s absent-ledger branch, or a recover against an uncommissioned host plans as an ordinary install — and the only reason that was caught is that SEALING creates a ledger, so the executor's re-plan refused what the printed plan had allowed. **The deployment must be sealed AGAIN after the ledger is replaced**, because the seal taken beforehand lived IN the ledger that was just replaced, and the archive's admission row is whatever it was when the backup was taken: open. Without it, a recovered control plane takes new work immediately while its nodes hold compute it has never heard of — which is the exact failure the whole operation is arranged around. It is an OPERATOR's seal, so `billet local up` does not clear it. And **an abandon must put the superseded ledger BACK**: the ordinary abandon removes what the run created, which includes the ledger it installed, leaving the operator's own under a name nothing looks at in a directory whose fence is about to come down — a deployment with no capacity record at all, produced by the command whose job is undoing damage. The superseded name is derived from the ARCHIVE's timestamp rather than the clock, so a resumed run recomputes it and recognises the rename it already did.

**AND FIVE MORE THINGS AN ADVERSARIAL REVIEW OF THAT COMMAND FOUND, every one of them an ordering rather than a missing check.** They are listed together because the shape repeats: each is a moment where a guarantee was true on either side of a gap and not inside it. **The fence must outlive the publication.** Clearing it and then sealing left an interval in which a control plane could start on the ledger the archive brought back — whose admission row is open — so `Execute` now leaves a recovery FENCED (`Result.Unfinished`), the command seals through `state.OpenMaintenance` (the one typed fence crossing; `OpenAdmin` honours the fence, and the lock `OpenMaintenance` takes is one `Execute` has released by then), and `deployarchive.Finish` takes the fence down afterwards. A seal that fails now leaves the directory fenced, which is the safe direction. **The sidecars move BEFORE the ledger.** A supersede that moved `billet.db` first and crashed left no ledger at the source, so the re-plan read it as an ordinary INSTALL and put the archive's database down beside a `-wal` belonging to a different one — SQLite replays that. Moving the ledger LAST means every interrupted state still has one where the re-plan will find it. **An abandon moves the ledger set as ONE thing**: deciding each file separately let the superseded `-wal` be renamed beside a ledger the abandon had correctly KEPT, which is the same corruption from the other end. **A resume must not re-quiesce**, because quiescing opens the ledger through `OpenAdmin` and the first attempt's fence refuses it — the documented resume was unreachable until the command learned to recognise its own journal and fence. **And an archive's NAME needs the manifest digest**, not just `CreatedAt`: RFC 3339 seconds collide for two backups taken back to back, and the no-clobber write then refuses the second one's upload.

**The presence of `billet.db` cannot be what refuses a restore.** A preflight `billet check` creates the ledger and its schema on a host nobody has commissioned, which is the documented way to prepare one. What proves a directory is committed is the deployment IDENTITY and the authority marker; what proves the ledger beside them is the preflight's is that every table a deployment writes to is empty.

**`admission` is a singleton its migration INSERTS, so a row count cannot tell it from a decision.** Counting to one exempted a sealed row, an advanced generation, and a provenance and reason a person wrote — so a host somebody had drained read as an untouched preflight ledger a restore may delete. What is checked is the exact row the migration writes.

**A fence a command RAISED comes down if that command published nothing.** A restore fences the ledger before the barrier and the locked re-plan, and every one of those can refuse while leaving the deployment exactly as it was — so leaving the fence up takes a healthy control plane offline over an operation that changed nothing. `WriteMaintenanceFence` reports whether THIS call created the fence, because a caller may only clear one it raised; a fence that predated it belongs to whatever established it. Past the journal the fence stays regardless, which is the state it exists for. And the fence is written all-or-nothing: a partial write leaves a file that closes the ledger and that no caller can recognise as its own to clear.

**Containment is not a string comparison, and it broke twice in one direction.** `strings.HasPrefix(key, dir+separator)` is wrong at the filesystem ROOT — a state directory of "/" builds the prefix "//", which nothing matches, so every path on the machine reads as outside it. And on a case-insensitive filesystem, which is the macOS default, `…/STATE/key.pem` and `…/state` name one directory and two strings; `EvalSymlinks` preserves the caller's spelling of ordinary components, so canonicalising does not reconcile them. billet asks `filepath.Rel` AND walks the key's existing ancestors comparing `os.SameFile`. The two overlap at the root, which is why mutating either alone leaves the test passing and mutating both fails it — redundancy that is measured and said out loud rather than assumed.

**Nothing here unlinks a pathname it cannot prove it owns.** The journal used a predictable `<journal>.new` and cleared it before each write; `github.private_key_path` is an operator's string and nothing stops it naming that file. The staging name is now `os.CreateTemp`'s, which cannot collide, and the planner separately refuses an App-key path that is one of billet's own state files. The single exception is `copyFile` discarding a destination it created with `O_EXCL` moments earlier — the one removal that is provably safe.

**A file verified by PATHNAME is not the file later opened by that pathname.** `Open` digests the ledger, then publication reopens the same name; on media somebody can change, the bytes installed are not the bytes checked. So `copyFile` hashes as it copies — and staging is not enough on its own, which the first version got wrong: the bytes are hashed through a DESCRIPTOR and published by a PATHNAME, and anything able to write that directory can rename the temporary away and leave its own file at the name `os.Link` then publishes. The descriptor is checked against the name before the link and against the destination after it, exactly as `writeKeyAtomically` does one credential over.

**And the identity check comes BEFORE the close.** `f.Stat()` on a closed descriptor fails, which a guard reads as "not ours" — so closing first leaves the staging file behind on every SUCCESSFUL install. That is a second copy of a restored ledger, and one credential over it is a second copy of an App key. The same mistake is already recorded against `writeKeyAtomically`; it was made again here anyway.

**Three vacuous assertions in this area, all found by mutation and all worth knowing.** Tampering with an archive entry by APPENDING a byte tests the size check, not the digest — the same-length case is the one that names it. SQLite deletes `billet.db-wal` and `-shm` when the last connection closes, so sidecars staged before either `PeekLedger` or the writer barrier are gone by the time the executor acts: a test about removing them has to stage them from inside the publication. And two backups of an unchanged deployment are byte-identical unless the clock moves, so a test needing two DISTINCT archives that does not move it is testing one archive twice.

## When a check cannot be built, observe instead

Four rounds went into modelling what starting a unit would do to the other one, and the model was wrong every time, because the closure is systemd's to compute through units billet has never heard of.

**The answer was to stop predicting and start observing.** Sample both units before starting either, sample again after, and refuse if the one you did not start moved. That closes the whole class — `Conflicts` at any depth, a `Requires` that pulls in a control plane — without modelling anything. The same shape catches `[Install] Also=` by comparing enablement before and after.

Sample **both** of billet's units, not only the ones the run planned: a node-only host does not plan the server at all, and that is exactly the case where a transitive `Requires=` starting it matters, because the GitHub proof was skipped on the grounds that no control plane was going to start.

This generalises: when a property depends on something outside billet's model, compare the world before and after rather than enumerating the ways it could change.

## Testing this package

`internal/lifeops` fakes the runner, the account database, the no-follow open and the repair root. Rules learned the hard way here, on top of `billet-testing`:

- **The systemctl fake must answer only the properties it was asked for.** One that returns its whole prepared reply makes deleting a property from the production query invisible: the code stops asking, the fixture keeps answering, every test passes.
- **`os.SameFile` type-asserts the concrete `FileInfo` the `os` package returns.** Wrapping it to adjust one field makes that comparison answer "different file" for every input — and it is the comparison several tests are about. To vary a link count, make a **real hard link**.
- **`syscall.Stat_t` field widths differ by platform and architecture** — `Nlink` is `uint64` on linux/amd64, `uint32` on linux/arm64, `uint16` on darwin, and `Dev` is signed on darwin. billet cross-builds all three, so build a fixture's stat through a converting helper rather than a literal.
- **A fixture that stages a refusal must stage it where systemd reads it.** `OnFailureJobMode` belongs in `[Unit]`; putting it in `[Service]` produces a test that proves nothing, silently.
- Start every unit fixture from a *healthy* one and break exactly one thing, so what the test names is the only difference from a host that works — and keep a test that a healthy host is **not** refused, or a converger that refused everything would pass the whole suite.

## Verifying on a real host

A throwaway Ubuntu EC2 instance is the only way to check several of these, and the checks that matter most are:

1. **The packaged unit still passes.** Every refusal class added here could reject a correct deployment; this is the regression that costs an operator their fleet.
2. **Each refusal staged on a real unit**, not a fixture — the `+` prefix and the whitespace-reset form in particular, because a fixture cannot show you that systemd's ordinary answer is unchanged.
3. **A clean room**: purge, remove `/etc/billet` and `/var/lib/billet`, delete the account, reinstall, and walk the guided path with no flags. That is what an operator does, and it is the only way to catch a default that only works because your host already had the file.
