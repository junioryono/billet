# Builders, user data and the AMI build

Part of the `billet-shell-gates` skill. Each rule is stated in full, with the measurement or incident behind it.

**A probe on the development Mac is not evidence about the builder.** Four mechanisms in one piece of work each reported success: a suppressed `apt-get update` made a probe report "0 lines" from a file it never fetched; an `ldd` jail copied the very library it tested for; a fake chroot prefixed only `argv[1]`; and this Mac's `grep` is ugrep, which reads UTF-16 transparently where GNU grep cannot, so a broken decoder looked correct. Run the probe in `ubuntu:24.04` or read the bytes with the builder's own tools, and prefer an assertion about bytes or emitted argv over a pipeline that happened to work somewhere. A Mac also answers for tools a Linux image may lack: `/usr/bin/swift` exists there, so a verifier test whose runner PATH reached the host's directories passed a case that left swift off the image; the probe's runner PATH is its fake bin alone.

**EC2 user data is 16384 bytes, so the AMI build travels in S3 and user data is a bootstrap.** billet gzips what it sends (cloud-init decompresses it), and once that was a provisioning script carrying the toolcache installers, it outgrew the cap. GitHub's template, the runner that drives it and billet's layer are hundreds of kilobytes, so `billet ami build` stages one tarball in the payload bucket and the user data fetches it by a presigned URL, checks its sha256 before tar reads a byte, unpacks it from `/`, and starts the build unit. The bootstrap runs without `set -x`: the URL is a credential, and a trace writes it to the console and into cloud-init's log inside the image. `packUserData` is still the gate for what user data carries, the job launch's registration included.

**The AMI build is the template runner on the builder itself, and it resumes across the template's reboot (ADR-022).** `scripts/ami/build-ami.sh` runs `run-runner-images.sh` with `scripts/ami/ami-target.sh` as the target driver: the builder is the image, so `exec` runs a step here under `env -i`, `copy-in` and `copy-out` are `cp -R`, and `reboot` records the step the build resumes at, enables the unit for the next boot and reboots. The record holds the build's nonce, its phase (`started`, `rebooting`, `resumed`) and the boot it was written in: the next boot continues only from `rebooting` written in another boot, and any other start with a record is an unplanned restart that fails at `resume` without running the template again. A failure prints a nonce-bound `verdict=fail` block naming the part that failed (`step=`) and, inside the template, the step's number, which billet names from its own plan; it never powers off. Success disables and removes the unit, the inputs and cloud-init's copies of the user data, empties the machine id, prints `verdict=ok` with the components it installed for a dwell, and only then powers off. Each of these is executed by `scripts/ami_build_test.go`, with the machine's paths under `BILLET_AMI_ROOT`.

**A unit cloud-init starts and a later boot resumes is wanted by `cloud-init.target`, never `multi-user.target`.** The build unit runs after `cloud-final.service`, and `cloud-final.service` is ordered after `multi-user.target`, so the same unit enabled under `multi-user.target` is an ordering cycle; systemd breaks it by deleting the unit's start job, and the boot after the template's reboot ran nothing (`multi-user.target: Job billet-ami-build.service/start deleted to break ordering cycle`, measured on real x64 and arm64 builders, 2026-10-25). Under `cloud-init.target`, which cloud-init's generator enables every boot and which is ordered after `cloud-final.service`, both builders resumed at the step their reboot named.

**Vendored scripts are pinned to LF.** `.gitattributes` marks `scripts/kernel/check-config.sh` `text eol=lf`, because the release gate refuses a copy that does not hash to the pin, and a line-ending conversion on checkout changes every byte.
