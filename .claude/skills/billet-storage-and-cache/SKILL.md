# Sites, stores and caches

## What this area is

A site is a place where compute and its storage share a fast network (`sites[]`, `store: ceph | ebs-s3`). A node reports its site at registration, a tier may pin one, and the control plane refuses a node whose provider cannot use the site's store. `internal/store` is the contract every cache implementation satisfies: immutable named generations, copy-on-write clones held under active leases, a writer lease for publication and a fenced pointer advanced by compare-and-swap. `internal/store/ceph` drives RBD through the `rbd` command for firecracker sites; `internal/store/ebss3` uses EBS snapshots and an S3 pointer for EC2 sites. On the node, `internal/node/actions_cache.go`, `actions_proxy.go` and `actions_volume.go` intercept `actions/cache` traffic for Linux firecracker tiers. `actions/stickydisk`, `setup-docker-builder`, `stop-docker-builder` and `build-push-action` are the published actions. `docs/reference/decisions/adr-003-ceph-rbd.md` records the cluster and its measurements; `docs/operating/actions-cache.md` is the operator page.

## Rules

**Storage is a property of the site, not of the compute backend.** `node.ceph` is a sibling of `node.firecracker`, because two hosts in one place map the same pools, and that sharing is the whole reason Ceph replaced ZFS (a ZFS clone exists only on the machine that took it, verified by mapping a clone from a second kernel client). It is required for firecracker and refused for every other backend. `node.ceph.user` defaults to `billet` and `admin` is refused, because `admin` is what `rbd` picks for itself when nothing names an identity and an admin key can delete a pool.

**A cache writer lease is not a capacity lease.** A `WriterLease` lasts across quiesce, filesystem verification and the fenced pointer CAS; a capacity lease stays charged until compute is proved gone. Reusing one lifetime for the other strands machine capacity behind a cache commit or lets an expired compute holder publish. Publication is guarded by three things at once: the expected generation, a live writer lease, and a monotone `FencingToken` whose zero value authorises nothing. A generation record is written before the current pointer, so an interrupted commit leaves the prior pointer or a complete new one. A `Candidate` needs a `Filesystem` with type, UUID and a proven-clean flag; non-empty alone proves neither.

**A writer lease that will not publish is released, and a release is exact.** `Store.ReleaseWriter` gives a lease back on every failure between acquisition and the pointer advance, on both backends. It removes only a record matching the lease's identity, expiry and fence, moves no fence and no pointer, and is a silent no-op for anything else, because a consumed, superseded or foreign lease already leaves the key free and a release runs on a failure path where a second error buries the first. Before it existed a failed publication held the key for the lease's remaining fifteen minutes and the next writer polled S3 every 100ms with nothing in the log; the wait is now a doubling back-off from 500ms to 30s, never longer than the holder's remaining lease, announced once per lease through `store.WriterHeldError`, which unwraps to `ErrConflict`. An Actions receipt is the one place a lease outlives the frame that took it: a fresh lease counts only once the receipt is durable, and whether the old lease is live is the store's question, so it is released unconditionally before re-acquiring.

**Ceph is driven through the `rbd` command, and every naming rule is pinned to what rbd does.** The Go binding is cgo over librados, which would end the single static binary; every call is a process, so the store is for operations measured in tens per job, never per block. A pool beginning with `-` is refused because billet builds positional `pool/image` specs and `rbd info -weirdpool/x` answers `unrecognised option`, not because of `-p`; identity rules written from a false premise were removed, keeping only the `client.` prefix, which measurably authenticates as `client.client.billet`. Ceph creates pools named `a/b`, `a@b` and `a b`, so "is this legal" is never the question; "does billet address it correctly" is.

**Clone v2 is a requirement, and two settings decide it.** On clone v1 a snapshot must be protected before it is cloned and a protected snapshot with a live clone can be neither unprotected nor removed, so a generation any running job holds would be undeletable. `billet check` refuses such a cluster. `require-min-compat-client` is the floor and `rbd_default_clone_format` overrides it, cluster-wide or per pool, and measured, the destination pool's value governs a clone; billet reads both for both pools and names the cause with the command that removes it (`ceph config rm client …` does not remove a pool-level override). The release rule is "not one of the releases older than mimic", because that set can never grow, and `unknown` (Ceph's enum zero, which the setter refuses) counts as older. Replication is reported and not judged.

**A real build on RBD costs 2%, and the fio number that said otherwise measured a machine doing nothing but IO.** `go build` cold 1.02x, fsync-per-file 2.36x, a cold read of 40,000 small files 4.07x (IOPS-bound, the opposite of what the synthetic table predicted, and the cache-hydrate path). Clone, map and mount is about 350ms for a 10GiB image; sequential reads reach 4.5GB/s at depth. Readahead and stride alignment moved nothing.

**The ebs-s3 store's first real publication was refused twice by things every fake accepted.** EC2's `CreateSnapshot` takes no `ClientToken` (`UnknownParameter`), so the token travels as the `sh.billet.snapshot-token` tag and idempotency is billet's: an attempt looks for a snapshot carrying its token before creating one and again after a failed call. The token names the operation (key plus volume), never the attempt, so a restarted attempt finds what a previous one made; a refusal AWS parsed is never retried; an ambiguous answer is reconciled against eventually consistent `DescribeSnapshots` for about a minute; a snapshot in error state counts as the token spent; two snapshots carrying one token are refused. And `ec2:CreateVolume` from a snapshot authorises the snapshot as well, so `BilletCacheCloneSource` grants it on the snapshot ARN conditioned on the owner tag. The hot path never deletes; `Delete` exists only for `billet decommission`'s purge. State objects are namespaced by deployment and site, and pre-release objects without an owner are ignored rather than migrated. And a 404 on a state read is an empty cache only when S3 says `NoSuchKey`: every 404 used to be, so a bucket that did not exist read exactly like a cold cache, every job fetched cold, the cache path fails open by design and `billet check`'s bucket probe reported that the bucket answered. `internal/awss3` holds that rule and the measurement behind it (`billet-providers-aws`).

**The Actions cache is a DNS remap of one origin, serving three methods.** `cache.actions` (or its deprecated spelling `intercept: true`) on a Linux firecracker tier with a static `cache_scope` and a `node.cache` listener; it is on by default only where its scope already holds (`Tier.actionsByDefault`), and explicitly enabled on docker, EC2, macOS or a mixed-provider tier it is refused. Only `CreateCacheEntry`, `FinalizeCacheEntryUpload` and `GetCacheEntryDownloadURL` on the CacheService are served locally; everything else, all of `ArtifactService` included, is spliced upstream with the runtime authorization untouched, because `ACTIONS_RESULTS_URL` carries artifact metadata and is in the release path. The origin is `results-receiver.actions.githubusercontent.com`; a blanket proxy variable would funnel the runner's whole traffic through one relay. The interception CA is minted per node (`wirecert.LoadOrCreateCA` under `actions-interception`) and propagated through the runner's job hook into job and action containers; an untrusted pool gets it only under `publish: default-branch`, where every call first asks the plane for the job's authority (`GET /v1/nodes/{node}/leases/{lease}/cache-authority`), splices while unproven, keys archives under `<ns>.scoped/untrusted/<owner>/<repo>/<arch>/actions/<sha(ref)>/<sha(version)>/<key>`, restores own ref then base then default, and creates only under its own ref where `WriteOwnRef` holds (`actionsKeysFor`). Limits: `actionsArchiveLimit` 10GiB, `actionsVolumeSize` 22GiB, `actionsArchiveCount` 32, `actionsRequestLimit` 64KiB. BuildKit `type=gha` from a container-driver builder works with NO workflow change: the guest image installs a `docker` shim at `/usr/local/bin/docker` (`internal/guestassets/docker-shim.sh`) that rewrites `ACTIONS_RESULTS_URL` for build invocations only (`build`, `buildx`, `bake`, `compose build`), because the buildx client points BuildKit wherever that variable says in its own process and the runner sets it per step where GITHUB_ENV loses; and the plaintext adapter that does the TLS to the node binds the guest's DOCKER GATEWAY rather than loopback, the one address both the guest and every container on its bridge can dial, so no `network=host` is needed. The node mints blob URLs naming a loopback or private address and nothing else; the adapter refuses any other bind, link-local and unspecified by name (Python counts those as private, Go does not). Only build invocations are rewritten because the results origin also carries artifacts and logs the adapter does not serve. A workflow may still name it with `url_v2=${{ env.BILLET_ACTIONS_CACHE_URL }}`. Inside a `container:` job the same shim fronts the image's own client: on an interception tier the runner runs billet's container hook (`internal/guestassets/container-hook.js`, a wrapper that bind-mounts `/opt/billet/bin/docker` read-only into the job container and delegates every command to GitHub's reference docker hook, vendored and pinned by `container-hook.pin`), and the job hook prepends `/opt/billet/bin` to `GITHUB_PATH`. The shim is installed twice on the host and detects a sibling shim by the marker on its line 2, never by path, because two copies comparing paths exec each other forever; it is never mounted over an image's own client. Tiers without interception keep the runner's built-in docker path. The adapter is identified by `X-Billet-Cache-Client: billet-loopback`, which is a routing hint and not a credential. The protocol is reverse-engineered from the official TypeScript client (GitHub has never published the `.proto` files), so every failure is a miss or a warning, never a failed job, and it fails open by two routes.

**A store and a listener are halves of one thing, and `billet check` is where the mirror is caught.** `node.cache` is what a guest talks to; without it the node builds no store, hands out no `BILLET_CACHE_ENDPOINT`, and every job runs cold with nothing published — measured 2026-09-04 on a lane whose config had `node.ebs_s3`, an `ebs-s3` site and pinned tiers and no listener (`/dev/root 77G` for `/var/lib/docker`, `cache: COLD`, an empty bucket, `purged 0 snapshot(s), 0 volume(s), 0 state object(s)`), while check printed that the bucket answered. Config validates only the other direction, so `judgeNodeCache` (`cmd/billet/cachecheck.go`) reports the mirror: `node.ebs_s3` with no listener FAILS the check, because that block backs nothing else; `node.ceph` with no listener is reported and not refused, because `image_pool` still boots every guest, `cache_pool` is required, and `billet init --provider firecracker` writes exactly that. It is a check verdict rather than a load refusal because `billet decommission` purges what the cache left behind and `billet init iam` renders its grants, and both read a store block on a config whose listener has gone.

**A discard is storage, not compute, and never runs on the node's command path (#223).** A teardown that proves the compute gone only closes the cache session (`CacheService.Close`, durable before it returns) and signals `ClosedSessions`. The volumes are discarded by the cache service's own loop in `cmd/billet/main.go`, which runs `RetryClosed` on that signal and every five minutes. `Recover` likewise only closes the sessions of compute the inventory proves absent (`ReconcileInventory`), and a failure there is a warning, never a reason to refuse work. Measured 2026-09-25: every `rbd rm` of a finished job's clone failed for an hour (`exit status 16`, image still open, or no answer). Run in line on the node's serial command queue, each failure delayed the next launch until launches took four to five minutes. Made fatal in `Recover`, it kept the fleet's only Linux host from taking work for thirty-five minutes.

**The kill switch is central, per cache, and consulted before every local operation.** `billet cache enable|disable --org|--repository [--kind docker|sticky|actions|git|bazel|go|all]` writes `cache_blocks(kind, …)` (migration 54; `'*'` is every cache, and a block an older binary wrote was carried as `actions`); nodes read it over `GET /v1/nodes/{node}/cache-policy?kind=` (`CachePolicy.CacheAllowed`), where could-not-tell is refusal. A content-addressed cache asks again every `casPolicyAge` (30s) while in use, and every publication asks again immediately before `PublishCAS`. A session that names no repository is nothing a block can name, so `sessionKindAllowed` allows it rather than ask the ledger, which refuses a repository-less lookup.

**What the cache did for a job is recorded as an observation, from a closed vocabulary, first observation kept.** `alloc.ImageCache` (`warm` with the generation, `cold`, `unavailable`, `unused`) is what the guest's Docker image-store clone answered, observed in `attachDockerStore`; `alloc.ActionsCache` (`served`, `spliced`, `disabled`, `unavailable`, `off`, `unused`) is what interception did for the FIRST CacheService call, recorded where the disposition is FINAL: `actionsResponse` records only what it decides itself (the kill switch, a client billet does not serve), and `actionsProxy.respond` records `served` once the handler answered, `spliced` when a failed handler is retried through GitHub, and `unavailable` when a reservation-bound call failed and could not go upstream; blob legs and artifact traffic observe nothing. The `CacheService` keeps the observation on the durable session (`cacheObserved`, with a `Reported` flag) beside the lease id and epoch the runner scoped the session with at launch, tells its `CacheObserver` (the `node.Runner`, which prefers the lease it holds for the instance in `running`, `launching` or `custody` because that epoch is current, and otherwise uses the session's) with a 2-second bound, marks a CacheService call in flight from dispatch to recorded outcome (the first one durably, `ActionsPending`, so a crash inside it leaves the half unknown after a restart rather than settled as unused) so settlement never writes `unused` over it, records the outcome under a detached bounded context because the guest's request may already be cancelled, never writes a record for a session cleanup has finished (`persistSession` refuses), and settles a session it loaded from disk (`recovered`) with its unobserved halves left unknown rather than `unused`, because a process that did not witness the guest's whole life cannot say what it never asked for (`off` still follows from the scope), and `settleObservation` fills in `unused`/`off` and resends anything unreported when the session ends. The runner calls `SettleObservation` in `destroy` BEFORE it forgets the request, because `Cleanup` runs after that mapping is gone. The ledger writes it onto the lease (fenced) and the history row (unfenced) in one transaction (`alloc.RecordCacheObservation`), the statements keep the first value, and the archive carries it; an empty token means nothing was observed and is never rendered as a miss.

**The conformance workflow is consumer-owned and pinned.** A workflow-restricted runner group cannot authorise a job defined by a cross-organization reusable workflow, so `billet cache conformance install` renders the whole gate into the consumer repository as `billet-cache-conformance.yml`, pinning the resolved billet commit, the runner label, the runner version (default `runnerrelease.Pinned()`) and the guest contract, and refuses any `inputs` expression in the rendered YAML. `.github/workflows/cache-conformance.yml` is the matrix it runs: host and container save/restore, BuildKit through container and loopback drivers, the passthrough kill switch, pinned and embedded clients, and a poisoned-clients suite. An interception-enabled image or runner release is not promoted until a candidate passes it.

**Caches are a deliberate cross-job channel, and `tiers[].cache.publish` gates publication (#226, ADR-013).** `trusted-only`: a trusted pool publishes and an untrusted one discards, with the pre-#226 keys unchanged byte for byte. `default-branch`: a write publishes only when the completion's `server.CacheAuthority` (decided once, by `server.DecideCacheAuthority`, from the JobStarted binding and GitHub's record of the run; see `billet-github-protocol`) is `Proven` and `PublishDefault` for the session's exact lease, owner and repository (`authorisesPublication`), into `<ns>.scoped/<trust>/<owner>/<repo>/<arch>/<kind>/…`, a root no legacy or guest-chosen key reaches. `off`: nothing. The default is by trust: untrusted with a repository scope is `default-branch` (a repository target is materialised as the scope at load), everything else `trusted-only`. Reads are the pool's, before the job is known, which is why default-branch requires a static repository. Docker image stores are scoped by deployment, site and architecture, so a private image pulled by one trusted job is readable by every later job in that boundary. Sticky-disk keys are exact and may cross repositories, so prefix ordinary keys with the repository. Nothing prevents a trusted job leaking into its own cache: do not cache secrets. Registry mirrors (`registry_mirrors` for Docker Hub, GHCR and Quay) serve public content with no upstream credential, three instances because one proxy accepts one upstream; BuildKit uses all three and Docker Engine only the Hub mirror.

**Guest volumes never become host file authority.** Ordinary sticky-disk requests refuse both `docker-images/` and `actions-cache/`, because the latter holds filesystems mounted by the host to serve Actions archives. Lookup and download each open the archive through `unix.Openat` against the mounted directory descriptor with `O_NOFOLLOW` and `O_NONBLOCK`, then verify that the descriptor names a bounded regular file; checking the pathname with `os.Stat` follows a guest-written symlink, and `os.Root.OpenFile` resolves an internal symlink even with `O_NOFOLLOW` (measured on macOS, 2026-09-06). The namespace refusal and descriptor refusal are independent defenses, each covered by a regression test.

**Sticky disks and the builder actions.** `actions/stickydisk` mounts a copy-on-write ext4 volume for one job (`key`, `path`, `size-gb`, `publication: cas | last-write-wins`, `discard-marker`, output `cache-hit`) and publishes in a post step without changing the job result. `setup-docker-builder` starts an isolated BuildKit daemon whose whole state lives on a sticky disk (`resolve-policy.sh` reads the tier's `buildkit_cache_mount_limit` ceiling first); `stop-docker-builder` quiesces BuildKit before its disk commits and enforces `mount-limit-bytes`; `build-push-action` runs `docker/build-push-action` against that builder and never writes `secrets` to the disk. Firecracker reserves five hot-attach slots per guest (`provider.MaxVolumes`); EC2 attaches owned volumes to the one-job instance at runtime. Guests request a deployment-, site- and architecture-scoped `/var/lib/docker` volume before the runner starts, and Docker 29 is kept on `overlay2` because the containerd image store keeps content outside that fenced volume. Published generations remain for eight inactive days; failures, cancellations, no change, untrusted work and unknown results discard the clone.

**Every cache is on by default where the tier can have it, and a default that cannot run is off, never refused.** `Tier.EffectiveCache` turns the Git, Bazel and Go caches on for a Linux-only Firecracker tier (`servesGuestCaches`), the Actions cache where `actionsByDefault` holds, and the Docker store and sticky disks everywhere; Go test results stay off. Only a cache a tier turns on explicitly (`explicitGuestCaches`) is held to where it can run, including the node-level refusal of a node without `node.cache`; otherwise every existing Firecracker node file without a cache listener would stop loading.

**Default-branch publication is deferred, journaled and off the command path.** `SettleCompleted` (called from `Runner.DestroyCompleted` with the authority) records a durable `publishIntent` on each dirty attachment and never waits behind a session already `closing`; `cleanupSession` in the cache loop runs `publishDeferred`/`releaseCASVolume` before any discard, through the phases snapshotting, snapshotted, publishing, published, abandoned, bounded by `publishWindow` (30 minutes, the writer's wait included). A crash mid-phase abandons rather than guesses, because a snapshot consumes the clone (`Journal.Consumed`). The authority is not re-decided at publication, because the binding it came from is settled and deleted soon after the completion; a default branch renamed inside the window is the recorded residual. A clone larger than its tier's `max_size` (`store.VolumeSizer`) is discarded and the job starts cold; if the discard fails the clone is kept and used.

**Go and Bazel share a content-addressed host volume per session (`casvolume.go`).** It is cloned from the scoped key's newest generation, mounted on the host under `sessionPathID` (a hash of the bearer, never the bearer, which a mount table and a mount's argv expose; a session recorded before this keeps its token), and served at `/v1/cas/{go|bazel}/{ac|cas}/<sha256>` and over the Remote Execution API to the session's bearer, outside the one-operation admission, bounded by `casAdmit` (16) with `casRequestLife` deadlines. A `cas` object is stored only under the digest of its bytes; an `ac` record is the job's claim, at most 1MiB; above 90% full a write answers 507, a miss to the client. THE LOCK ORDER IS `session.mu` THEN `hv.io`: a transfer holding `io` never takes `session.mu`, so a write is marked `Dirty` durably when it is ADMITTED (`openCASHandle(write)`), which is also what lets a restart before the completion still publish it; `releaseCASVolume` waits for `io` at most `casReleaseWait` and comes back on a later pass. Publication merges: if the key moved since the clone, the newest generation is cloned (recorded in `hostVolume.Merge` before it is mounted), the job's missing objects copied in, and that published, so concurrent jobs' writes both survive; a failed discard keeps the record (`discardCASVolumes` is done only when every step succeeded).

**The Go helper and the Bazel credential helper are billet itself, in the guest.** `billet cache gocacheprog` (`internal/gocacheprog`) speaks cmd/go's cacheprog protocol, keeps a local directory for DiskPaths, re-fetches a damaged local output, keeps a served object only when its bytes are its entry's, and turns into a plain local cache on any refusal: a build never fails because of it. The opt-out is `GOCACHEPROG=` (empty), because the go command prefers it to `GOCACHE`. `billet cache credential-helper` answers the bearer from the environment only for the node's host, so no bazelrc carries it. The Remote Execution API lives in `internal/node/reapi`, the only importer of gRPC and the API's generated code (depguard `remoteapis`); it answers a result only while every blob it and its output Trees name is present, refuses an upload whose bytes or size do not match its digest, and bounds a batch read per digest so client-chosen sizes cannot overflow its limit.

**The Git proxy serves github.com fetches from a mirror, and only what GitHub would give that job (`gitproxy.go`).** Routing and serving are pinned to measurement (git 2.51.0, 2026-09-25): `url.insteadOf` drops checkout's github.com-scoped header, so `billet cache git-credential`, run by git in the repository after the node's 401, hands the node the session bearer as the user and that header as the password; an identity `pushInsteadOf` keeps pushes direct; git keeps its old base URL when it follows a redirect on that retry, so the node follows a renamed repository itself (`gitProxy.follow`). Every advertisement is authorised by GitHub with the job's header (numbered, so a later refusal ends an earlier grant), the mirror (per trust, owner and repository) is fetched to GitHub's refs with `--prune` under a node-wide cap of two fetches and a watchdog for the tier's ceiling and the disk's fill, and served under protocol v0 only: v2 serves any object present, and v0's check walks commits, so a fetch is served from the mirror only when every want is a commit or a current ref's object and its advertisement was served from the mirror; anything else, a partial clone's blob fetch included, goes to GitHub whole. The header reaches git through `GIT_CONFIG_*` only. Mirrors unused seven days are reaped, and a mirror in use is passed over.

**What each build cache did is observed like the image store.** `alloc.BuildCache` (`warm`, `cold`, `disabled`, `unavailable`, `unused`) for sticky disks, Git, Bazel and Go (migration 55), kept per session at the most telling outcome (`noteBuildCache`; CAS hits and uses are atomics on the volume, for the lock order) and reported once, when the session ends (`settledBuildCaches`), `unused` only for a tier that enabled the cache and only from the process that saw the whole session. `billet cache status` counts them per tier.

## Measured facts

- ZFS clone reachable from one machine only; RBD clone mapped from a second kernel client.
- Clone + map + mount: ~350ms for 10GiB; sequential reads 4.5GB/s at depth; 4k sync writes 14x slower than local on fio; real builds 1.02x, 2.36x, 4.07x.
- `rbd info -weirdpool/x`: `unrecognised option`; `client.billet` with a `client.` prefix authenticates as `client.client.billet`.
- The destination pool's `rbd_default_clone_format` governs a clone.
- `CreateSnapshot` + `ClientToken`: `UnknownParameter` (HTTP 400), every settlement failed, every job ran cold (2026-09-03).
- A failed writer lease held its key fifteen minutes; the waiting writer polled about twenty times a second for six minutes.
- Site acceptance (2026-09-03): two nodes at one site reuse one generation, a second site starts cold and cannot reach the first's store, and the same label falls back across sites.
