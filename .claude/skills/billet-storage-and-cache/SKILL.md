# Sites, stores and caches

## What this area is

A site is a place where compute and its storage share a fast network (`sites[]`, `store: ceph | ebs-s3`). A node reports its site at registration, a tier may pin one, and the control plane refuses a node whose provider cannot use the site's store. `internal/store` is the contract every cache implementation satisfies: immutable named generations, copy-on-write clones held under active leases, a writer lease for publication and a fenced pointer advanced by compare-and-swap. `internal/store/ceph` drives RBD through the `rbd` command for firecracker sites; `internal/store/ebss3` uses EBS snapshots and an S3 pointer for EC2 sites. On the node, `internal/node/actions_cache.go`, `actions_proxy.go` and `actions_volume.go` intercept `actions/cache` traffic for Linux firecracker tiers. `actions/stickydisk`, `setup-docker-builder`, `stop-docker-builder` and `build-push-action` are the published actions. `docs/reference/decisions/adr-003-ceph-rbd.md` records the cluster and its measurements; `docs/operating/actions-cache.md` is the operator page.

## Rules

**Storage is a property of the site, not of the compute backend.** `node.ceph` is a sibling of `node.firecracker`, because two hosts in one place map the same pools, and that sharing is the whole reason Ceph replaced ZFS (a ZFS clone exists only on the machine that took it, verified by mapping a clone from a second kernel client). It is required for firecracker and refused for every other backend. `node.ceph.user` defaults to `billet` and `admin` is refused, because `admin` is what `rbd` picks for itself when nothing names an identity and an admin key can delete a pool.

**A cache writer lease is not a capacity lease.** A `WriterLease` lasts across quiesce, filesystem verification and the fenced pointer CAS; a capacity lease stays charged until compute is proved gone. Reusing one lifetime for the other strands machine capacity behind a cache commit or lets an expired compute holder publish. Publication is guarded by three things at once: the expected generation, a live writer lease, and a monotone `FencingToken` whose zero value authorises nothing. A generation record is written before the current pointer, so an interrupted commit leaves the prior pointer or a complete new one. A `Candidate` needs a `Filesystem` with type, UUID and a proven-clean flag; non-empty alone proves neither.

**A writer lease that will not publish is released, and a release is exact.** `Store.ReleaseWriter` gives a lease back on every failure between acquisition and the pointer advance, on both backends. It removes only a record matching the lease's identity, expiry and fence, moves no fence and no pointer, and is a silent no-op for anything else, because a consumed, superseded or foreign lease already leaves the key free and a release runs on a failure path where a second error buries the first. Before it existed a failed publication held the key for the lease's remaining fifteen minutes and the next writer polled S3 every 100ms with nothing in the log; the wait is now a doubling back-off from 500ms to 30s, never longer than the holder's remaining lease, announced once per lease through `store.WriterHeldError`, which unwraps to `ErrConflict`. An Actions receipt is the one place a lease outlives the frame that took it: a fresh lease counts only once the receipt is durable, and whether the old lease is live is the store's question, so it is released unconditionally before re-acquiring.

**Ceph is driven through the `rbd` command, and every naming rule is pinned to what rbd does.** The Go binding is cgo over librados, which would end the single static binary; every call is a process, so the store is for operations measured in tens per job, never per block. A pool beginning with `-` is refused because billet builds positional `pool/image` specs and `rbd info -weirdpool/x` answers `unrecognised option`, not because of `-p`; identity rules written from a false premise were removed, keeping only the `client.` prefix, which measurably authenticates as `client.client.billet`. Ceph creates pools named `a/b`, `a@b` and `a b`, so "is this legal" is never the question; "does billet address it correctly" is.

**Clone v2 is a requirement, and two settings decide it.** On clone v1 a snapshot must be protected before it is cloned and a protected snapshot with a live clone can be neither unprotected nor removed, so a generation any running job holds would be undeletable. `billet check` refuses such a cluster. `require-min-compat-client` is the floor and `rbd_default_clone_format` overrides it, cluster-wide or per pool, and measured, the destination pool's value governs a clone; billet reads both for both pools and names the cause with the command that removes it (`ceph config rm client …` does not remove a pool-level override). The release rule is "not one of the releases older than mimic", because that set can never grow, and `unknown` (Ceph's enum zero, which the setter refuses) counts as older. Replication is reported and not judged.

**A real build on RBD costs 2%, and the fio number that said otherwise measured a machine doing nothing but IO.** `go build` cold 1.02x, fsync-per-file 2.36x, a cold read of 40,000 small files 4.07x (IOPS-bound, the opposite of what the synthetic table predicted, and the cache-hydrate path). Clone, map and mount is about 350ms for a 10GiB image; sequential reads reach 4.5GB/s at depth. Readahead and stride alignment moved nothing.

**The ebs-s3 store's first real publication was refused twice by things every fake accepted.** EC2's `CreateSnapshot` takes no `ClientToken` (`UnknownParameter`), so the token travels as the `sh.billet.snapshot-token` tag and idempotency is billet's: an attempt looks for a snapshot carrying its token before creating one and again after a failed call. The token names the operation (key plus volume), never the attempt, so a restarted attempt finds what a previous one made; a refusal AWS parsed is never retried; an ambiguous answer is reconciled against eventually consistent `DescribeSnapshots` for about a minute; a snapshot in error state counts as the token spent; two snapshots carrying one token are refused. And `ec2:CreateVolume` from a snapshot authorises the snapshot as well, so `BilletCacheCloneSource` grants it on the snapshot ARN conditioned on the owner tag. The hot path never deletes; `Delete` exists only for `billet decommission`'s purge. State objects are namespaced by deployment and site, and pre-release objects without an owner are ignored rather than migrated. And a 404 on a state read is an empty cache only when S3 says `NoSuchKey`: every 404 used to be, so a bucket that did not exist read exactly like a cold cache, every job fetched cold, the cache path fails open by design and `billet check`'s bucket probe reported that the bucket answered. `internal/awss3` holds that rule and the measurement behind it (`billet-providers-aws`).

**The Actions cache is a DNS remap of one origin, serving three methods.** `intercept: true` on a Linux firecracker tier with a static `cache_scope` and a `node.cache` listener; docker, EC2, macOS and mixed-provider tiers are refused. Only `CreateCacheEntry`, `FinalizeCacheEntryUpload` and `GetCacheEntryDownloadURL` on the CacheService are served locally; everything else, all of `ArtifactService` included, is spliced upstream with the runtime authorization untouched, because `ACTIONS_RESULTS_URL` carries artifact metadata and is in the release path. The origin is `results-receiver.actions.githubusercontent.com`; a blanket proxy variable would funnel the runner's whole traffic through one relay. The interception CA is minted per node (`wirecert.LoadOrCreateCA` under `actions-interception`), propagated through the runner's job hook into job and action containers, and never given to untrusted jobs. Limits: `actionsArchiveLimit` 10GiB, `actionsVolumeSize` 22GiB, `actionsArchiveCount` 32, `actionsRequestLimit` 64KiB. BuildKit `type=gha` from a container-driver builder works with NO workflow change: the guest image installs a `docker` shim at `/usr/local/bin/docker` (`internal/guestassets/docker-shim.sh`) that rewrites `ACTIONS_RESULTS_URL` for build invocations only (`build`, `buildx`, `bake`, `compose build`), because the buildx client points BuildKit wherever that variable says in its own process and the runner sets it per step where GITHUB_ENV loses; and the plaintext adapter that does the TLS to the node binds the guest's DOCKER GATEWAY rather than loopback, the one address both the guest and every container on its bridge can dial, so no `network=host` is needed. The node mints blob URLs naming a loopback or private address and nothing else; the adapter refuses any other bind, link-local and unspecified by name (Python counts those as private, Go does not). Only build invocations are rewritten because the results origin also carries artifacts and logs the adapter does not serve. A workflow may still name it with `url_v2=${{ env.BILLET_ACTIONS_CACHE_URL }}`. Inside a `container:` job the same shim fronts the image's own client: on an interception tier the runner runs billet's container hook (`internal/guestassets/container-hook.js`, a wrapper that bind-mounts `/opt/billet/bin/docker` read-only into the job container and delegates every command to GitHub's reference docker hook, vendored and pinned by `container-hook.pin`), and the job hook prepends `/opt/billet/bin` to `GITHUB_PATH`. The shim is installed twice on the host and detects a sibling shim by the marker on its line 2, never by path, because two copies comparing paths exec each other forever; it is never mounted over an image's own client. Tiers without interception keep the runner's built-in docker path. The adapter is identified by `X-Billet-Cache-Client: billet-loopback`, which is a routing hint and not a credential. The protocol is reverse-engineered from the official TypeScript client (GitHub has never published the `.proto` files), so every failure is a miss or a warning, never a failed job, and it fails open by two routes.

**A store and a listener are halves of one thing, and `billet check` is where the mirror is caught.** `node.cache` is what a guest talks to; without it the node builds no store, hands out no `BILLET_CACHE_ENDPOINT`, and every job runs cold with nothing published — measured 2026-09-04 on a lane whose config had `node.ebs_s3`, an `ebs-s3` site and pinned tiers and no listener (`/dev/root 77G` for `/var/lib/docker`, `cache: COLD`, an empty bucket, `purged 0 snapshot(s), 0 volume(s), 0 state object(s)`), while check printed that the bucket answered. Config validates only the other direction, so `judgeNodeCache` (`cmd/billet/cachecheck.go`) reports the mirror: `node.ebs_s3` with no listener FAILS the check, because that block backs nothing else; `node.ceph` with no listener is reported and not refused, because `image_pool` still boots every guest, `cache_pool` is required, and `billet init --provider firecracker` writes exactly that. It is a check verdict rather than a load refusal because `billet decommission` purges what the cache left behind and `billet init iam` renders its grants, and both read a store block on a config whose listener has gone.

**The kill switch is central and consulted before every local operation.** `billet cache enable|disable --org|--repository` writes `SetActionsCacheEnabled`; nodes read it over `GET /v1/nodes/{node}/cache-policy` (`ActionsCacheAllowed`).

**The conformance workflow is consumer-owned and pinned.** A workflow-restricted runner group cannot authorise a job defined by a cross-organization reusable workflow, so `billet cache conformance install` renders the whole gate into the consumer repository as `billet-cache-conformance.yml`, pinning the resolved billet commit, the runner label, the runner version (default `runnerrelease.Pinned()`) and the guest contract, and refuses any `inputs` expression in the rendered YAML. `.github/workflows/cache-conformance.yml` is the matrix it runs: host and container save/restore, BuildKit through container and loopback drivers, the passthrough kill switch, pinned and embedded clients, and a poisoned-clients suite. An interception-enabled image or runner release is not promoted until a candidate passes it.

**Caches are a deliberate cross-job channel, and trust gates publication.** A trusted job's writes publish; an untrusted job hydrates from the trusted baseline and its clone is discarded without failing the job. Docker image stores are scoped by deployment, site and architecture, so a private image pulled by one trusted job is readable by every later job in that boundary. Sticky-disk keys are exact and may cross repositories, so prefix ordinary keys with the repository. Nothing prevents a trusted job leaking into its own cache: do not cache secrets. Registry mirrors (`registry_mirrors` for Docker Hub, GHCR and Quay) serve public content with no upstream credential, three instances because one proxy accepts one upstream; BuildKit uses all three and Docker Engine only the Hub mirror.

**Sticky disks and the builder actions.** `actions/stickydisk` mounts a copy-on-write ext4 volume for one job (`key`, `path`, `size-gb`, `publication: cas | last-write-wins`, `discard-marker`, output `cache-hit`) and publishes in a post step without changing the job result. `setup-docker-builder` starts an isolated BuildKit daemon whose whole state lives on a sticky disk (`resolve-policy.sh` reads the tier's `buildkit_cache_mount_limit` ceiling first); `stop-docker-builder` quiesces BuildKit before its disk commits and enforces `mount-limit-bytes`; `build-push-action` runs `docker/build-push-action` against that builder and never writes `secrets` to the disk. Firecracker reserves five hot-attach slots per guest (`provider.MaxVolumes`); EC2 attaches owned volumes to the one-job instance at runtime. Guests request a deployment-, site- and architecture-scoped `/var/lib/docker` volume before the runner starts, and Docker 29 is kept on `overlay2` because the containerd image store keeps content outside that fenced volume. Published generations remain for eight inactive days; failures, cancellations, no change, untrusted work and unknown results discard the clone.

## Measured facts

- ZFS clone reachable from one machine only; RBD clone mapped from a second kernel client.
- Clone + map + mount: ~350ms for 10GiB; sequential reads 4.5GB/s at depth; 4k sync writes 14x slower than local on fio; real builds 1.02x, 2.36x, 4.07x.
- `rbd info -weirdpool/x`: `unrecognised option`; `client.billet` with a `client.` prefix authenticates as `client.client.billet`.
- The destination pool's `rbd_default_clone_format` governs a clone.
- `CreateSnapshot` + `ClientToken`: `UnknownParameter` (HTTP 400), every settlement failed, every job ran cold (2026-09-03).
- A failed writer lease held its key fifteen minutes; the waiting writer polled about twenty times a second for six minutes.
- Site acceptance (2026-09-03): two nodes at one site reuse one generation, a second site starts cold and cannot reach the first's store, and the same label falls back across sites.
