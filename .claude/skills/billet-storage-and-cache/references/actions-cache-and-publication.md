# The Actions cache, the kill switch and publication

Part of the `billet-storage-and-cache` skill. Each rule is stated in full, with the measurement or incident behind it.

**The npm cache is a second remapped origin, on by default for every firecracker Linux tier since 2026-10-25, answering only anonymous reads from the node's own store (ADR-020).** `cache.npm.enabled` (on by default since 2026-10-25, as every cache is; `false` turns it off for a tier whose jobs run a client in the runner's own process that ignores `NODE_EXTRA_CA_CERTS` and the system store, which fails TLS rather than missing) on a Linux firecracker tier; named elsewhere it is refused at load like any explicit guest cache. It needs no trust and no cache scope, because the store holds only what `registry.npmjs.org` gives a request without a credential, fetched by the node itself (`internal/node/npm_proxy.go`), so one store per node (`<state>/npm-registry`, `npmStoreLimit` 10GiB, least recently served evicted) serves every tier and trust class. It travels as `CacheSpec.Npm` (wire 31, `VersionNpmCache`; an older node ignores it and npm goes direct) and reaches the guest as the `npm-proxy` metadata key beside `actions-ca-pem`, the same CONNECT tunnel as the results origin, each host its own switch in `serveConnect`. What the store may answer is `classifyNpmRequest`'s closed set (a `GET`, or a `HEAD` of a held entry; no credential, query or range; three exactly parsed path shapes; an `Accept` from npm's own two), everything else spliced whole. Freshness is the registry's own (`s-maxage`, else `max-age`, less its `Age`), a tarball capped at `npmTarballCeiling` (24h); a fetch is one attempt with `npmHeaderWait` (8s) to headers and `npmBodyIdle` (10s) between body bytes, one retry on a new connection while nothing reached the client, a stale entry for `npmStaleWindow` (1h) only when the registry gave no answer and its directives allow, else its 5xx or the node's 504. The kill switch's `npm` kind splices. The guest half (#646: the remap in `/etc/hosts` only, dnsmasq with `--no-hosts`, a passthrough relay on `127.0.2.1:443`) and the per-job outcome on the lease (#649: `npm_cache` on leases and history, wire 32) have shipped. The guest remaps the registry in `/etc/hosts` only, and only once the container resolver (dnsmasq with `--no-hosts`, started wherever the Actions or the npm cache is on) is in place, because without it a container on a user-defined network resolved the remap to its own loopback through `systemd-resolved`; and its relay runs with `--guest-processes-only`, tunnelling only a socket of the runner's uid held in the relay's own mount namespace and relaying every other connection to the registry, because a `--network host` container copies the guest's `/etc/hosts` and refused the node's certificate (both measured in a guest, 2026-10-23). A job's npm outcome is `warm`, `cold`, `disabled` (the kill switch said no), `unavailable` (no store, a handshake the guest refused, or a kill switch that could not be read) or `unused`; it is held back while a request is in flight, unless one was already warm, and reported by the last request to end.

**The Actions cache is a DNS remap of one origin, serving three methods.** `cache.actions` (or its deprecated spelling `intercept: true`) on a Linux firecracker tier with a static `cache_scope` and a `node.cache` listener; it is on by default only where its scope already holds (`Tier.actionsByDefault`), and explicitly enabled on docker, EC2, macOS or a mixed-provider tier it is refused. Only `CreateCacheEntry`, `FinalizeCacheEntryUpload` and `GetCacheEntryDownloadURL` on the CacheService are served locally; everything else, all of `ArtifactService` included, is spliced upstream with the runtime authorization untouched, because `ACTIONS_RESULTS_URL` carries artifact metadata and is in the release path. The origin is `results-receiver.actions.githubusercontent.com`; a blanket proxy variable would funnel the runner's whole traffic through one relay. The interception CA is minted per node (`wirecert.LoadOrCreateCA` under `actions-interception`) and propagated through the runner's job hook into job and action containers; an untrusted pool gets it only under `publish: default-branch`, where every call first asks the plane for the job's authority (`GET /v1/nodes/{node}/leases/{lease}/cache-authority`), splices while unproven, keys archives under `<ns>.scoped/untrusted/<owner>/<repo>/<arch>/actions/<sha(ref)>/<sha(version)>/<key>`, restores own ref then base then default, and creates only under its own ref where `WriteOwnRef` holds (`actionsKeysFor`). Limits: `actionsArchiveLimit` 10GiB, `actionsVolumeSize` 22GiB, `actionsArchiveCount` 32, `actionsRequestLimit` 64KiB. BuildKit `type=gha` from a container-driver builder works with NO workflow change: the guest image installs a `docker` shim at `/usr/local/bin/docker` (`internal/guestassets/docker-shim.sh`) that rewrites `ACTIONS_RESULTS_URL` for build invocations only (`build`, `buildx`, `bake`, `compose build`), because the buildx client points BuildKit wherever that variable says in its own process and the runner sets it per step where GITHUB_ENV loses; and the plaintext adapter that does the TLS to the node binds the guest's DOCKER GATEWAY rather than loopback, the one address both the guest and every container on its bridge can dial, so no `network=host` is needed. The node mints blob URLs naming a loopback or private address and nothing else; the adapter refuses any other bind, link-local and unspecified by name (Python counts those as private, Go does not). Only build invocations are rewritten because the results origin also carries artifacts and logs the adapter does not serve. A workflow may still name it with `url_v2=${{ env.BILLET_ACTIONS_CACHE_URL }}`. Inside a `container:` job the same shim fronts the image's own client: on an interception tier the runner runs billet's container hook (`internal/guestassets/container-hook.js`, a wrapper that bind-mounts `/opt/billet/bin/docker` read-only into the job container and delegates every command to GitHub's reference docker hook, vendored and pinned by `container-hook.pin`), and the job hook prepends `/opt/billet/bin` to `GITHUB_PATH`. The shim is installed twice on the host and detects a sibling shim by the marker on its line 2, never by path, because two copies comparing paths exec each other forever; it is never mounted over an image's own client. Tiers without interception keep the runner's built-in docker path. The adapter is identified by `X-Billet-Cache-Client: billet-loopback`, which is a routing hint and not a credential. The protocol is reverse-engineered from the official TypeScript client (GitHub has never published the `.proto` files), so every failure is a miss or a warning, never a failed job, and it fails open by two routes.

**A store and a listener are halves of one thing, and `billet check` is where the mirror is caught.** `node.cache` is what a guest talks to; without it the node builds no store, hands out no `BILLET_CACHE_ENDPOINT`, and every job runs cold with nothing published — measured 2026-09-04 on a lane whose config had `node.ebs_s3`, an `ebs-s3` site and pinned tiers and no listener (`/dev/root 77G` for `/var/lib/docker`, `cache: COLD`, an empty bucket, `purged 0 snapshot(s), 0 volume(s), 0 state object(s)`), while check printed that the bucket answered. Config validates only the other direction, so `judgeNodeCache` (`internal/ops/host/cachecheck.go`) reports the mirror: `node.ebs_s3` with no listener FAILS the check, because that block backs nothing else; `node.ceph` with no listener is reported and not refused, because `image_pool` still boots every guest, `cache_pool` is required, and `billet init --provider firecracker` writes exactly that. It is a check verdict rather than a load refusal because `billet decommission` purges what the cache left behind and `billet init iam` renders its grants, and both read a store block on a config whose listener has gone.

**The kill switch is central, per cache, and consulted before every local operation.** `billet cache enable|disable --org|--repository [--kind docker|sticky|actions|git|bazel|go|all]` writes `cache_blocks(kind, …)` (migration 54; `'*'` is every cache, and a block an older binary wrote was carried as `actions`); nodes read it over `GET /v1/nodes/{node}/cache-policy?kind=` (`CachePolicy.CacheAllowed`), where could-not-tell is refusal. A content-addressed cache asks again every `casPolicyAge` (30s) while in use, and every publication asks again immediately before `PublishCAS`. A session that names no repository is nothing a block can name, so `sessionKindAllowed` allows it rather than ask the ledger, which refuses a repository-less lookup.

**What the cache did for a job is recorded as an observation, from a closed vocabulary, first observation kept.** `alloc.ImageCache` (`warm` with the generation, `cold`, `unavailable`, `unused`) is what the guest's Docker image-store clone answered, observed in `attachDockerStore`; `alloc.ActionsCache` (`served`, `spliced`, `disabled`, `unavailable`, `off`, `unused`) is what interception did for the FIRST CacheService call, recorded where the disposition is FINAL: `actionsResponse` records only what it decides itself (the kill switch, a client billet does not serve), and `actionsProxy.respond` records `served` once the handler answered, `spliced` when a failed handler is retried through GitHub, and `unavailable` when a reservation-bound call failed and could not go upstream, a blob leg on a URL billet signed included, which is observed only for that failure (#694): storage that refused a block, an archive this process could not mount again after a restart (`errActionsArchiveLost`, answered 502 rather than 403 as an unknown URL is, and the same when it is finalized rather than `{"ok": false}`), a policy or job authority that could not be read for a blob URL billet signed (`errActionsPolicyUnreadable`, a local failure and not a splice, since GitHub knows nothing of the URL; the kill switch stays a refusal), or an archive that failed to read while its answer was being written (`limitedFile.Read`, after the request's disposition was recorded, which only marks the session, so the record takes it up when the session next writes or settles). A body the guest cut short (`errActionsBodyCut`, marked by `actionsGuestBody`, metadata bodies included) or a request that ran out of time or was cancelled is not billet's failure and observes nothing, on every branch of `respond` through its one predicate, because a client that retries and succeeds would otherwise read as failed; artifact traffic and a blob leg billet answered observe nothing either. A failure is marked on the session without its lock (`actionsFailed`) before the observation waits for the lock, and `absorbActionsFailure` takes it up in the next merge, settlement or write of the record, so a renewal holding the lock across storage for longer than an observation waits cannot leave the job settled as `served`; a cleanup reports what it took up after its own settlement before it deletes the record. The `CacheService` keeps the observation on the durable session (`cacheObserved`, with a `Reported` flag) beside the lease id and epoch the runner scoped the session with at launch, tells its `CacheObserver` (the `node.Runner`, which prefers the lease it holds for the instance in `running`, `launching` or `custody` because that epoch is current, and otherwise uses the session's) with a 2-second bound, marks a CacheService call in flight from dispatch to recorded outcome (the first one durably, `ActionsPending`, so a crash inside it leaves the half unknown after a restart rather than settled as unused) so settlement never writes `unused` over it, records the outcome under a detached bounded context because the guest's request may already be cancelled, never writes a record for a session cleanup has finished (`persistSession` refuses), and settles a session it loaded from disk (`recovered`) with its unobserved halves left unknown rather than `unused`, because a process that did not witness the guest's whole life cannot say what it never asked for (`off` still follows from the scope), and `settleObservation` fills in `unused`/`off` and resends anything unreported when the session ends. The runner calls `SettleObservation` in `destroy` BEFORE it forgets the request, because `Cleanup` runs after that mapping is gone. The ledger writes it onto the lease (fenced) and the history row (unfenced) in one transaction (`alloc.RecordCacheObservation`), the statements keep the first value, except that the Actions half's `unavailable` replaces an earlier one there as it does in the node's record, because a save that failed after a served restore was recorded as `served` and nothing showed it was lost (#694), and the archive carries it; an empty token means nothing was observed and is never rendered as a miss.

**A CONNECT never waits on a session's lock, and a block in transfer holds only its archive, shared (#694).** The guest's passthrough (`actions-proxy.py`) gives the node `CONNECT_TIMEOUT` (10 s) to answer a CONNECT and then fails open to GitHub's own addresses, since it cannot see the request inside the TLS it relays; GitHub's results service answers a `/_billet/actions-cache/` path it never issued with Go's `404 page not found`, which the toolkit's upload treats as final. Measured on ubuntu-01 on 2026-10-26: a ~2 GB `actions/cache@v5` save stopped at 17% with that 404, and the node logged four `unexpected EOF` block failures in the same second, the toolkit aborting its other in-flight blocks. The cause was the locking, not the volume: `serveActionsBlob` held `archive.mu` for a block's whole transfer, the next block waited for it while still holding the session's lock, and `authenticateProxy` waited on that lock, so every new tunnel of the job (one request per tunnel, so every block) queued behind the transfer in front of it. So `authenticateProxy` reads only what is fixed when the session is made and the lock-free `closing` mirror, `serveActionsBlob` lets the session's lock go before it waits on the archive and checks `closing` again after, and the archive's lock is an `RWMutex` taken only through `lockShared` and `lockExclusive`: a block, a download and a HEAD hold it shared, and a single-shot upload, the block-list commit, the finalization and the session's cleanup hold it alone. A waiting exclusive holder admits no new shared one (`exclusiveWaiting`), because a lock taken by polling `TryLock` announces no waiting writer and blocks arriving one after another would keep a commit out until its request expired. Any other holder of the session's lock across storage (`RenewActive` through the site's cache index, a finalization's trim and publish) still delays a handler, never a tunnel. A save reserved and never finalized is logged when its session's cleanup discards it.

**The conformance workflow is consumer-owned and pinned.** A workflow-restricted runner group cannot authorise a job defined by a cross-organization reusable workflow, so `billet cache conformance install` renders the whole gate into the consumer repository as `billet-cache-conformance.yml`, pinning the resolved billet commit, the runner label, the runner version (default `runnerrelease.Pinned()`) and the guest contract, and refuses any `inputs` expression in the rendered YAML. `.github/workflows/cache-conformance.yml` is the matrix it runs: host and container save/restore, BuildKit through container and loopback drivers, the passthrough kill switch, pinned and embedded clients, and a poisoned-clients suite. An interception-enabled image or runner release is not promoted until a candidate passes it.

**Caches are a deliberate cross-job channel, and `tiers[].cache.publish` gates publication (#226, ADR-013).** `trusted-only`: a trusted pool publishes and an untrusted one discards, with the pre-#226 keys unchanged byte for byte. `default-branch`: a write publishes only when the completion's `dispatch.CacheAuthority` (decided once, by `server.DecideCacheAuthority`, from the JobStarted binding and GitHub's record of the run; see `billet-github-protocol`) is `Proven` and `PublishDefault` for the session's exact lease, owner and repository (`authorisesPublication`), into `<ns>.scoped/<trust>/<owner>/<repo>/<arch>/<kind>/…`, a root no legacy or guest-chosen key reaches. `off`: nothing. The default is by trust: untrusted with a repository scope is `default-branch` (a repository target is materialised as the scope at load), everything else `trusted-only`. Reads are the pool's, before the job is known, which is why default-branch requires a static repository. A running job's call waits for the plane's binding before it splices (`awaitBinding`): the plane answers a lease it has not bound with an authority that names no job, a job it has bound and cannot prove with its job, and the node waits on the first for up to `actionsBindingWait`, once per session. Measured 2026-10-17 on the reference deployment: JobStarted reached the plane a median of 18 s and at most 51 s after GitHub started the job, setup-go restored about 20 s in, and the spliced restore took 540 MB from GitHub over a shaped home line instead of from the site's store. Docker image stores are scoped by deployment, site and architecture, so a private image pulled by one trusted job is readable by every later job in that boundary. Sticky-disk keys are exact and may cross repositories, so prefix ordinary keys with the repository. Nothing prevents a trusted job leaking into its own cache: do not cache secrets. Registry mirrors (`registry_mirrors` for Docker Hub, GHCR and Quay) serve public content with no upstream credential, three instances because one proxy accepts one upstream; BuildKit uses all three and Docker Engine only the Hub mirror.

**Guest volumes never become host file authority.** Ordinary sticky-disk requests refuse both `docker-images/` and `actions-cache/`, because the latter holds filesystems mounted by the host to serve Actions archives. Lookup and download each open the archive through `unix.Openat` against the mounted directory descriptor with `O_NOFOLLOW` and `O_NONBLOCK`, then verify that the descriptor names a bounded regular file; checking the pathname with `os.Stat` follows a guest-written symlink, and `os.Root.OpenFile` resolves an internal symlink even with `O_NOFOLLOW` (measured on macOS, 2026-09-06). The namespace refusal and descriptor refusal are independent defenses, each covered by a regression test.

**Every cache is on by default where the tier can have it, and a default that cannot run is off, never refused.** `Tier.EffectiveCache` turns the Git cache on for a Linux-only Firecracker tier (`servesGuestCaches`), the Bazel and Go caches for such a tier only where it can publish them (`publishesContent`: trusted under `trusted-only`, or `default-branch`), the Actions cache where `actionsByDefault` holds, and the Docker store and sticky disks everywhere; Go test results stay off. The Bazel and Go keys are scoped by trust, so an untrusted pool that publishes nothing reads a key nobody writes; measured 2026-10-04 on the reference deployment, an untrusted, unscoped tier's Go cache was cold 177 times and warm never in a day, and because `GOCACHEPROG` takes precedence over `GOCACHE` the build cache the workflow restored itself was ignored, so lint jobs ran out of time. Only a cache a tier turns on explicitly (`explicitGuestCaches`) is held to where it can run, including the node-level refusal of a node without `node.cache`; otherwise every existing Firecracker node file without a cache listener would stop loading.

**Default-branch publication is deferred, journaled and off the command path.** `SettleCompleted` (called from `Runner.DestroyCompleted` with the authority) records a durable `publishIntent` on each dirty attachment and never waits behind a session already `closing`; `cleanupSession` in the cache loop runs `publishDeferred`/`releaseCASVolume` before any discard, through the phases snapshotting, snapshotted, publishing, published, abandoned, bounded by `publishWindow` (30 minutes, the writer's wait included). A crash mid-phase abandons rather than guesses, because a snapshot consumes the clone (`Journal.Consumed`). The authority is not re-decided at publication, because the binding it came from is settled and deleted soon after the completion; a default branch renamed inside the window is the recorded residual. A clone larger than its tier's `max_size` (`store.VolumeSizer`) is discarded and the job starts cold; if the discard fails the clone is kept and used.
