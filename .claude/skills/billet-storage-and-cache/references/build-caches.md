# Sticky disks, the Go and Bazel caches and the Git proxy

Part of the `billet-storage-and-cache` skill. Each rule is stated in full, with the measurement or incident behind it.

**Sticky disks and the builder actions.** `actions/stickydisk` mounts a copy-on-write ext4 volume for one job (`key`, `path`, `size-gb`, `publication: cas | last-write-wins`, `discard-marker`, output `cache-hit`) and publishes in a post step without changing the job result. `setup-docker-builder` starts an isolated BuildKit daemon whose whole state lives on a sticky disk (`resolve-policy.sh` reads the tier's `buildkit_cache_mount_limit` ceiling first); `stop-docker-builder` quiesces BuildKit before its disk commits and enforces `mount-limit-bytes`; `build-push-action` runs `docker/build-push-action` against that builder and never writes `secrets` to the disk. Firecracker reserves five hot-attach slots per guest (`provider.MaxVolumes`); EC2 attaches owned volumes to the one-job instance at runtime. Guests request a deployment-, site- and architecture-scoped `/var/lib/docker` volume before the runner starts, and Docker 29 is kept on `overlay2` because the containerd image store keeps content outside that fenced volume. Published generations remain for eight inactive days; failures, cancellations, no change, untrusted work and unknown results discard the clone.

**Go and Bazel share a content-addressed host volume per session (`casvolume.go`).** It is cloned from the scoped key's newest generation, mounted on the host under `sessionPathID` (a hash of the bearer, never the bearer, which a mount table and a mount's argv expose; a session recorded before this keeps its token), and served at `/v1/cas/{go|bazel}/{ac|cas}/<sha256>` and over the Remote Execution API to the session's bearer, outside the one-operation admission, bounded by `casAdmit` (16) with `casRequestLife` deadlines. A `cas` object is stored only under the digest of its bytes; an `ac` record is the job's claim, at most 1MiB; above 90% full a write answers 507, a miss to the client. THE LOCK ORDER IS `session.mu` THEN `hv.io`: a transfer holding `io` never takes `session.mu`, so a write is marked `Dirty` durably when it is ADMITTED (`openCASHandle(write)`), which is also what lets a restart before the completion still publish it; `releaseCASVolume` waits for `io` at most `casReleaseWait` and comes back on a later pass. Publication merges: if the key moved since the clone, the newest generation is cloned (recorded in `hostVolume.Merge` before it is mounted), the job's missing objects copied in, and that published, so concurrent jobs' writes both survive; a failed discard keeps the record (`discardCASVolumes` is done only when every step succeeded). A FAILED ATTACH BACKS OFF (`casRetryAt`, `casAttachBackoff`, five minutes, in memory only): the attach clones under the site's one cache index lock, and when a failure was remembered by nothing every request of the build ran it again, so one failure became a stream of lock attempts that starved every other session's cache work on 2026-10-03, including the Docker image store a guest's runner waits on before it starts (#320). Refused requests answer 503, which the Go helper reads as a miss; a 403 would turn its remote cache off for the rest of the build.

**The Go helper and the Bazel credential helper are billet itself, in the guest.** `billet cache gocacheprog` (`internal/gocacheprog`) speaks cmd/go's cacheprog protocol, keeps a local directory for DiskPaths, re-fetches a damaged local output, keeps a served object only when its bytes are its entry's, and turns into a plain local cache on any refusal: a build never fails because of it. The opt-out is `GOCACHEPROG=` (empty), because the go command prefers it to `GOCACHE`. `billet cache credential-helper` answers the bearer from the environment only for the node's host, so no bazelrc carries it. The Remote Execution API lives in `internal/node/reapi`, the only importer of gRPC and the API's generated code (depguard `remoteapis`); it answers a result only while every blob it and its output Trees name is present, refuses an upload whose bytes or size do not match its digest, and bounds a batch read per digest so client-chosen sizes cannot overflow its limit.

**The Git proxy serves github.com fetches from a mirror, and only what GitHub would give that job (`gitproxy.go`).** Routing and serving are pinned to measurement (git 2.51.0, 2026-09-25): `url.insteadOf` drops checkout's github.com-scoped header, so `billet cache git-credential`, run by git in the repository after the node's 401, hands the node the session bearer as the user and that header as the password; an identity `pushInsteadOf` keeps pushes direct; git keeps its old base URL when it follows a redirect on that retry, so the node follows a renamed repository itself (`gitProxy.follow`). Every advertisement is authorised by GitHub with the job's header (numbered, so a later refusal ends an earlier grant), the mirror (per trust, owner and repository) is fetched to GitHub's refs with `--prune` under a node-wide cap of two fetches and a watchdog for the tier's ceiling and the disk's fill, and served under protocol v0 only: v2 serves any object present, and v0's check walks commits, so a fetch is served from the mirror only when every want is a commit or a current ref's object and its advertisement was served from the mirror; anything else, a partial clone's blob fetch included, goes to GitHub whole. The header reaches git through `GIT_CONFIG_*` only. Mirrors unused seven days are reaped, and a mirror in use is passed over.

**What each build cache did is observed like the image store.** `alloc.BuildCache` (`warm`, `cold`, `disabled`, `unavailable`, `unused`) for sticky disks, Git, Bazel and Go (migration 55), kept per session at the most telling outcome (`noteBuildCache`; CAS hits and uses are atomics on the volume, for the lock order) and reported once, when the session ends (`settledBuildCaches`), `unused` only for a tier that enabled the cache and only from the process that saw the whole session. `billet cache status` counts them per tier.
