# Sticky disks, the Go and Bazel caches and the Git proxy

Part of the `billet-storage-and-cache` skill. Each rule is stated in full, with the measurement or incident behind it.

**Sticky disks and the builder actions.** `actions/stickydisk` mounts a copy-on-write ext4 volume for one job (`key`, `path`, `size-gb`, `publication: cas | last-write-wins`, `discard-marker`, output `cache-hit`) and publishes in a post step without changing the job result. `setup-docker-builder` starts an isolated BuildKit daemon whose whole state lives on a sticky disk (`resolve-policy.sh` reads the tier's `buildkit_cache_mount_limit` ceiling first); `stop-docker-builder` quiesces BuildKit before its disk commits and enforces `mount-limit-bytes`; `build-push-action` runs `docker/build-push-action` against that builder and never writes `secrets` to the disk. Firecracker reserves five hot-attach slots per guest (`provider.MaxVolumes`); EC2 attaches owned volumes to the one-job instance at runtime. Guests request a deployment-, site- and architecture-scoped `/var/lib/docker` volume before the runner starts, and Docker 29 is kept on `overlay2` because the containerd image store keeps content outside that fenced volume. Published generations remain for eight inactive days; failures, cancellations, no change, untrusted work and unknown results discard the clone.

**Go and Bazel share a content-addressed host volume per session (`casvolume.go`).** It is cloned from the scoped key's newest generation, mounted on the host under `sessionPathID` (a hash of the bearer, never the bearer, which a mount table and a mount's argv expose; a session recorded before this keeps its token), and served at `/v1/cas/{go|bazel}/{ac|cas}/<sha256>` and over the Remote Execution API to the session's bearer, outside the one-operation admission, bounded by `casAdmit` (16) with `casRequestLife` deadlines. A `cas` object is stored only under the digest of its bytes; an `ac` record is the job's claim, at most 1MiB; above 90% full a write answers 507, a miss to the client. THE LOCK ORDER IS `session.mu` THEN `hv.io`: a transfer holding `io` never takes `session.mu`, so a write is marked `Dirty` durably when it is ADMITTED (`openCASHandle(write)`), which is also what lets a restart before the completion still publish it; `releaseCASVolume` waits for `io` at most `casReleaseWait` and comes back on a later pass. Publication merges: if the key moved since the clone, the newest generation is cloned (recorded in `hostVolume.Merge` before it is mounted), the job's missing objects copied in, and that published, so concurrent jobs' writes both survive; a failed discard keeps the record (`discardCASVolumes` is done only when every step succeeded). A FAILED ATTACH BACKS OFF (`casRetryAt`, `casAttachBackoff`, five minutes, in memory only): the attach clones under the site's one cache index lock, and when a failure was remembered by nothing every request of the build ran it again, so one failure became a stream of lock attempts that starved every other session's cache work on 2026-10-03, including the Docker image store a guest's runner waits on before it starts (#320). Refused requests answer 503, which the Go helper reads as a miss; a 403 would turn its remote cache off for the rest of the build. A DAMAGED GENERATION STARTS OVER, ON THE STORE'S PROOF ABOUT THE GENERATION ITSELF: when a clone of the newest generation will not mount, the node asks the store's `GenerationDamaged`, which maps the generation's own snapshot read-only and runs `e2fsck -f -n`, and only an exit status with the uncorrected-errors bit (4) starts an empty volume in its place (`startFresh`, `Supersedes`), as a full generation does. The job's copy is never the evidence: Clone copies a generation whose lineage is at its limit or unrecorded, and a damaged copy says nothing about a sound generation. A check that could not tell (8 alone, a signal), and a store without the check (ebs-s3), keep the generation. A merge whose newest generation the store proves damaged publishes the job's own volume in its place, unmounting it before the snapshot and discarding only the clone of the damaged generation. Before this, one damaged generation held the Go cache from 2026-10-05 to 2026-10-13, because publication merges into the newest generation and could never replace it. `TestAFirecrackerNodesCacheStoreChecksGenerations` proves the check on the store the assembly builds, the way #317's capability had to be.

**The Go helper and the Bazel credential helper are billet itself, in the guest.** `billet cache gocacheprog` (`internal/gocacheprog`) speaks cmd/go's cacheprog protocol, keeps a local directory for DiskPaths, re-fetches a damaged local output, keeps a served object only when its bytes are its entry's, and turns into a plain local cache on any refusal: a build never fails because of it. The opt-out is `GOCACHEPROG=` (empty), because the go command prefers it to `GOCACHE`. `billet cache credential-helper` answers the bearer from the environment only for the node's host, so no bazelrc carries it. The Remote Execution API lives in `internal/node/reapi`, the only importer of gRPC and the API's generated code (depguard `remoteapis`); it answers a result only while every blob it and its output Trees name is present, refuses an upload whose bytes or size do not match its digest, and bounds a batch read per digest so client-chosen sizes cannot overflow its limit.

**The Git proxy serves github.com fetches from a mirror, and only what GitHub would give that job (`gitproxy.go`).** Routing and serving are pinned to measurement (git 2.51.0, 2026-09-25): `url.insteadOf` drops checkout's github.com-scoped header, so `billet cache git-credential`, run by git in the repository after the node's 401, hands the node the session bearer as the user and that header as the password; an identity `pushInsteadOf` keeps pushes direct; git keeps its old base URL when it follows a redirect on that retry, so the node follows a renamed repository itself (`gitProxy.follow`). Every advertisement is authorised by GitHub with the job's header (numbered, so a later refusal ends an earlier grant), and a job GitHub authorised is served any object its repository's mirror (per trust, owner and repository) holds, because GitHub serves an object no ref reaches by its name, superseded pull-request merge commits and fork commits included (measured 2026-10-21, ADR-018); a partial clone's lazy blob fetch is served from the mirror with it. A MIRROR IS ONE REPOSITORY'S BY GITHUB'S ID, NEVER BY ITS NAME: a name passes to another repository once the first is renamed or deleted, so every advertisement asks `GET /repos/{owner}/{repo}` with the job's header (accepted there, measured 2026-10-21) and no grant carries the answer forward, a mirror is stamped `billet-repository` with that id when it is made, `claimMirror` renames aside one stamped otherwise, unstamped, or carrying `billet-unverified` (unless the refresh that wrote it is still running) before anything is served, into `<root>/.discarded/` (no repository name starts with a dot), and deletes it in the background, the reaper taking leftovers older than ten minutes; `billet-unverified` is written before every fetch and removed only when GitHub names the same repository after it, because git cannot fetch by id (`/repositories/<id>` is not found over git), so a failed fetch, a name that changed hands or an API that could not say leaves the mirror unserved and replaced, durably across a restart (written through `durablefile` before git starts); a serve that fails mid-answer writes `billet-broken` instead, which no refresh clears, and an in-process quarantine holds the mirror if the disk refuses that mark; the last checks before an answer commits and after an advertisement is read re-read the stamp and both marks; a name handed away and back within one fetch is accepted (ADR-018: only an organisation admin who can already grant the access could arrange it), a fetch is served only from a mirror stamped with its grant's id, and a name the API will not tie to an id is GitHub's to answer with no mirror made. NOTHING THE MIRROR CANNOT DO FAILS A FETCH: a want or shallow boundary it lacks (one `cat-file --batch-check`, full object names only, since cat-file reads anything else as a revision), a negotiation it cannot read, a v2 request, or an `ERR` or silence as upload-pack's first line (read before any byte reaches the client) sends the buffered request to GitHub whole. A REFRESH BELONGS TO NO REQUEST: one per mirror at a time, on its starting request's context without its cancellation (ended only by `gitRefreshLife` or `gitProxy.close`, which tests call before their state directory goes), fetched to GitHub's refs: only those the starting request's advertisement moved, added or dropped (`planGitFetch`: the moved refs by name with `--no-tags`, the old values and the default branch's tip as `--negotiation-tip` so a new or rebased branch brings only its own commits, the dropped ones deleted first through `update-ref --stdin` against the value seen, so a new ref can take a dropped one's place), and every ref with `--prune` for a new mirror, an advertisement asked for no later than the mirror's last refresh finished (`gitMirror.fetchedAt`, the proxy's question number then, so no advertisement older than the mirror removes a ref that refresh brought, its own included), a name `narrowRefName` refuses, more than `gitNarrowMost` (256) refs or a narrow fetch that failed, under a node-wide cap of two fetches and a watchdog for the tier's ceiling and the disk's fill, with `gc.auto=0` and `maintenance.auto=false` so no detached gc keeps the header, after removing lock files and temporary packs a killed fetch left; an advertisement waits for it at most `gitRefreshWait` (10 s) and then relays GitHub's own, and joins one that began before GitHub answered only to compare the refs again after it (the 2026-10-21 incident was one slow fetch, under an unbounded per-repository mutex, holding every checkout of the repository until its ten-minute cut). The proxy reaches GitHub over its own HTTP/1.1 transport with every request body read whole first: GitHub answers `408` to a body idle ten seconds, and one shared HTTP/2 connection let one download starve every other job's request. A git request ends after `gitIdleLimit` (3 min) with no byte moved, or at `gitRequestLife` (2 h), never at the other caches' fixed ten minutes, and ends with one `a git request` log line naming its route and reason. The header reaches git through `GIT_CONFIG_*` only. Mirrors unused seven days are reaped, and a mirror in use is passed over.

**A guest reaches its build caches through a relay that waits out a node restart (#374).** A node handing over leaves its guests running while its cache listener is gone until the next process starts, and a `git fetch` refused in that gap fails the job, because nothing in Git falls back from an `insteadOf` rewrite (the Go helper falls back to a local cache, the Actions cache fails open to GitHub; Git does neither). So the agent starts `billet-actions-proxy --mode node-relay` as a socket-activated unit on the docker gateway (`172.17.0.1:41322`, `BILLET_CACHE_RELAY` block), and once it is serving repoints `cache_endpoint` at it: the runner's `BILLET_CACHE_ENDPOINT`, the git rewrite and its credential helper, bazelrc and its credential helper and the Go helper all name the relay, which splices each connection to the node unchanged and redials a refusing node every `NODE_RELAY_RETRY` for up to `NODE_RELAY_WAIT` (ten minutes). The node reads no `Host` except the Git proxy's redirect, which then names the relay, so nothing node-side changes. Only a plain-HTTP endpoint goes through it, since an https one names the node in its certificate, and a relay that does not start leaves the node's address in place. The Docker image store is attached before Docker and keeps the node's own address, as does its end-of-job commit.

**What each build cache did is observed like the image store.** `alloc.BuildCache` (`warm`, `cold`, `disabled`, `unavailable`, `unused`) for sticky disks, Git, Bazel and Go (migration 55), kept per session at the most telling outcome (`noteBuildCache`; CAS hits and uses are atomics on the volume, for the lock order) and reported once, when the session ends (`settledBuildCaches`), `unused` only for a tier that enabled the cache and only from the process that saw the whole session. `billet cache status` counts them per tier.
