# Sites, stores and discards

Part of the `billet-storage-and-cache` skill. Each rule is stated in full, with the measurement or incident behind it.

**Storage is a property of the site, not of the compute backend.** `node.ceph` is a sibling of `node.firecracker`, because two hosts in one place map the same pools, and that sharing is the whole reason Ceph replaced ZFS (a ZFS clone exists only on the machine that took it, verified by mapping a clone from a second kernel client). It is required for firecracker and refused for every other backend. `node.ceph.user` defaults to `billet` and `admin` is refused, because `admin` is what `rbd` picks for itself when nothing names an identity and an admin key can delete a pool.

**A cache writer lease is not a capacity lease.** A `WriterLease` lasts across quiesce, filesystem verification and the fenced pointer CAS; a capacity lease stays charged until compute is proved gone. Reusing one lifetime for the other strands machine capacity behind a cache commit or lets an expired compute holder publish. Publication is guarded by three things at once: the expected generation, a live writer lease, and a monotone `FencingToken` whose zero value authorises nothing. A generation record is written before the current pointer, so an interrupted commit leaves the prior pointer or a complete new one. A `Candidate` needs a `Filesystem` with type, UUID and a proven-clean flag; non-empty alone proves neither.

**A candidate is verified as it is published, not only as it was written.** `Snapshot` checks the source volume through the kernel device that wrote it, then freezes a clone of the staging snapshot or, at the lineage limit, a flattened clone of it (never `rbd cp`, below). `verifyCandidate` then maps the frozen candidate (`handle@generation`) read-only on a device of its own, runs the same `e2fsck -f -n`, and requires the filesystem UUID the source check found, before the pointer can move; a failure removes the candidate through `cleanupSnapshotFailure`. On 2026-10-05, while the cluster was timing out and the node restarted, a compaction published a Go cache generation holding 4 MiB of data whose journal superblock e2fsck calls corrupt (exit 12, measured 2026-10-13); the source check had passed. Every clone of it failed to mount and every merge into it failed for eight days. A CANDIDATE RECORDED BEFORE THIS IS CHECKED WHEN IT IS PUBLISHED: `Snapshot` sets `Filesystem.CheckedAsPublished`, which a journal written by an older release decodes as false, and `PublishCAS` checks such a candidate before it takes the index lock, and counts the check's time against the writer lease, because a publication journaled before an upgrade resumes without another `Snapshot`, and a restart in the middle of a publication is how the damaged generation came to be. EVERY READ-ONLY MAP OF A GENERATION'S SNAPSHOT GOES THROUGH `withGenerationMap`, under `generationMapSlot` (one per process, shared by every `Client`, since a node holds several) and, through `WithGenerationMapLock`, an flock on `ceph-generation-maps.lock` in `node.lock_dir` (a directory only billet's account can write; the file is made under a temporary name, set 0660 on its descriptor whatever the umask, and linked into place, which never replaces one already there, because a lock_dir may be SETGID and shared by two accounts and a crash must not leave a file only one of them can open; without a lock_dir the exclusion is the process's alone), so while both are held every such mapping on the host is the caller's: a map that failed (the kernel can finish one after the command's bound) is cleaned up by unmapping them all under a context of its own, and `Evict` first sweeps what a crash or a failed unmap left behind, because eviction keeps every image the host maps. Both unmap only a mapped snapshot of an image whose name is exactly one billet gives a generation (`cacheImageName`, kind `g`): a lookalike an operator mapped by hand is not billet's. The cleanup starts no unmap once its `c.wait` budget is spent, and one already started runs to its own bound, so the slot is held for at most the budget plus one unmap. `rbd device list --format json` names a mapped snapshot in `snap` and an image's head as `-` (20.2.3, 2026-10-13). `GenerationDamaged` (the optional `GenerationChecker`) checks a published generation's own snapshot the same way: true is proof of damage, false with an error could-not-tell.

**A writer lease that will not publish is released, and a release is exact.** `Store.ReleaseWriter` gives a lease back on every failure between acquisition and the pointer advance, on both backends. It removes only a record matching the lease's identity, expiry and fence, moves no fence and no pointer, and is a silent no-op for anything else, because a consumed, superseded or foreign lease already leaves the key free and a release runs on a failure path where a second error buries the first. Before it existed a failed publication held the key for the lease's remaining fifteen minutes and the next writer polled S3 every 100ms with nothing in the log; the wait is now a doubling back-off from 500ms to 30s, never longer than the holder's remaining lease, announced once per lease through `store.WriterHeldError`, which unwraps to `ErrConflict`. An Actions receipt is the one place a lease outlives the frame that took it: a fresh lease counts only once the receipt is durable, and whether the old lease is live is the store's question, so it is released unconditionally before re-acquiring.

**Ceph is driven through the `rbd` command, and every naming rule is pinned to what rbd does.** The Go binding is cgo over librados, which would end the single static binary; every call is a process, so the store is for operations measured in tens per job, never per block. A pool beginning with `-` is refused because billet builds positional `pool/image` specs and `rbd info -weirdpool/x` answers `unrecognised option`, not because of `-p`; identity rules written from a false premise were removed, keeping only the `client.` prefix, which measurably authenticates as `client.client.billet`. Ceph creates pools named `a/b`, `a@b` and `a b`, so "is this legal" is never the question; "does billet address it correctly" is.

**Clone v2 is a requirement, and two settings decide it.** On clone v1 a snapshot must be protected before it is cloned and a protected snapshot with a live clone can be neither unprotected nor removed, so a generation any running job holds would be undeletable. `billet check` refuses such a cluster. `require-min-compat-client` is the floor and `rbd_default_clone_format` overrides it, cluster-wide or per pool, and measured, the destination pool's value governs a clone; billet reads both for both pools and names the cause with the command that removes it (`ceph config rm client …` does not remove a pool-level override). The release rule is "not one of the releases older than mimic", because that set can never grow, and `unknown` (Ceph's enum zero, which the setter refuses) counts as older. Replication is reported and not judged.

**A real build on RBD costs 2%, and the fio number that said otherwise measured a machine doing nothing but IO.** `go build` cold 1.02x, fsync-per-file 2.36x, a cold read of 40,000 small files 4.07x (IOPS-bound, the opposite of what the synthetic table predicted, and the cache-hydrate path). Clone, map and mount is about 350ms for a 10GiB image; sequential reads reach 4.5GB/s at depth. Readahead and stride alignment moved nothing.

**The ebs-s3 store's first real publication was refused twice by things every fake accepted.** EC2's `CreateSnapshot` takes no `ClientToken` (`UnknownParameter`), so the token travels as the `sh.billet.snapshot-token` tag and idempotency is billet's: an attempt looks for a snapshot carrying its token before creating one and again after a failed call. The token names the operation (key plus volume), never the attempt, so a restarted attempt finds what a previous one made; a refusal AWS parsed is never retried; an ambiguous answer is reconciled against eventually consistent `DescribeSnapshots` for about a minute; a snapshot in error state counts as the token spent; two snapshots carrying one token are refused. And `ec2:CreateVolume` from a snapshot authorises the snapshot as well, so `BilletCacheCloneSource` grants it on the snapshot ARN conditioned on the owner tag. The hot path never deletes; `Delete` exists only for `billet decommission`'s purge. State objects are namespaced by deployment and site, and pre-release objects without an owner are ignored rather than migrated. And a 404 on a state read is an empty cache only when S3 says `NoSuchKey`: every 404 used to be, so a bucket that did not exist read exactly like a cold cache, every job fetched cold, the cache path fails open by design and `billet check`'s bucket probe reported that the bucket answered. `internal/awss3` holds that rule and the measurement behind it (`billet-providers-aws`).

**A Firecracker node on AWS metal attaches its site's volumes to its own instance, and detaches one only on proof nothing holds it (ADR-030, #827).** `ebss3.NewAttached` takes the instance and zone from the identity document and refuses a store in another zone, since EC2 answers `InvalidVolume.ZoneMismatch`. A create or clone is attached under the first device name EC2 does not already use (`/dev/sdf` to `/dev/sdz`, then `/dev/xvdba` to `/dev/xvdbz`), retrying only "Attachment point … is already in use", because a name outside EC2's scheme shares its code. The device is found by the serial its NVMe controller reports (`vol<id without the dash>`), never by the name asked for, and it appeared 0.26 to 0.54 s after the attach was accepted, before EC2 described it attached (2026-11-09). EBS detached a MOUNTED ext4 volume without refusing, in 4.4 s, and the journal aborted, so `detachLocal` first proves the device unheld (`blockfs.Unheld`: a device with a partition is refused, since a partition's openers have a number of their own; an exclusive open, which a mount or a stacked device refuses; every thread's descriptor table and every process's mappings (`map_files`, since a shared mapping outlives its descriptor) scanned for its device number; and every configured loop device's backing asked of the kernel (`LOOP_GET_STATUS64`'s `lo_rdevice`), never read from its pathname, which can name another file; could-not-tell refuses; mappings are read at `/proc/<tid>/map_files` for every thread, since an exited leader shows none). It does not see a device registered in an io_uring whose descriptor was then closed: refusing every ring would refuse Firecracker's async block engine, and on a pool host the only opener of a cache device is billet's VMM, which keeps its descriptor), refuses a volume attached to another instance, never forces, and waits for EC2 to describe it available. A snapshot of a self-attached volume is proved and verified on the host before it is detached, and a publication retried after its detach attaches the volume here again and proves it again, never publishing on the earlier proof. Its IAM attaches only volumes by billet's owner tag and only instances by the deployment's pool-owner tag: the cache's attach grant is held to volume ARNs, since on `*` it would also allow any instance carrying billet's owner tag. Its registration says it uses the site's ebs-s3 store (`RegisterRequest.site_store`, wire 48), and the plane accepts Firecracker at an ebs-s3 site only on that word, so a node that kept its caches on its own Ceph cannot split a site. A z1d.metal took 30 volumes beside its root and refused the 31st with `AttachmentLimitExceeded`; its instance store held `/dev/sdb` and `/dev/sdc` without counting (2026-11-10). The node's eviction pass sweeps an attachment no session names once it is thirty minutes old, because a volume is attached before its session records it.

**A recorded device number is never acted on until the kernel's table proves it is still the volume's.** A kernel reuses an rbd device's number as soon as it is unmapped, so a `Volume.Device` kept across a failure or a restart can name anyone's disk. Measured on the reference node on 2026-11-04: a publication's retry for one job ran `e2fsck -f -n` on `/dev/rbd39`, which `rbd device list` showed was another job's running root disk (`Last mounted on: /`, its findings changing between captures seconds apart), and reported it "not clean"; had it looked clean, the next step unmapped it. `snapshotAt` unmaps and, on a later failure, discards its volume, and the node retried from the record until the publication's window ended: in the seven days before, 153 real `verify candidate` failures were followed by 1,831 `identify` failures on a free number and 301 `not clean` on a reused one. `Client.MappedDevice` answers from `rbd device list` by the image's name, in the pool's default namespace, and its head (`snap` `-`), never a mapped snapshot of it. A row that does not say whose it is, or a head with no device, is `storecontract.ErrDeviceUnknown`. `ErrVolumeGone` means the pool's own listing no longer names the image, which is what a failed snapshot's cleanup leaves (`rbd status` is no witness: it answers ENOENT for a pool that will not open and for an image whose parent is missing, and either can still hold writes), because it has a job's writes thrown away: `rbd device list` skips a device whose attributes it could not read and still succeeds, and a mapping's watch can lapse while the kernel re-registers it (Ceph 20.2.3 `krbd.cc` and the kernel's `rbd_watch_errcb`, read from source, not reproduced), so neither a missing row nor an absent watcher says the kernel let go. An image still listed with no row is `ErrDeviceUnknown`, retried until the publication's window ends. `publishDeferred` abandons at once on gone; `RestoreMounts` and a merge's source mount refuse an unproved device; `releaseCASVolume` asks again on unknown, and proves the source before it clones the newest generation so a retry leaves nothing behind. `cloneWithin` proves a clone whose discard failed before using it, because a discard unmaps first and can fail after that. A store whose device is the volume's own name, as ebs-s3's is, implements nothing: `DeviceProver` is optional.

**A discard is storage, not compute, and never runs on the node's command path (#223).** A teardown that proves the compute gone only closes the cache session (`CacheService.Close`, durable before it returns) and signals `ClosedSessions`. The volumes are discarded by the cache service's own loop in `internal/app/nodecache.go`, which runs `RetryClosed` on that signal and every five minutes. `Recover` likewise only closes the sessions of compute the inventory proves absent (`ReconcileInventory`), and a failure there is a warning, never a reason to refuse work. Measured 2026-09-25: every `rbd rm` of a finished job's clone failed for an hour (`exit status 16`, image still open, or no answer). Run in line on the node's serial command queue, each failure delayed the next launch until launches took four to five minutes. Made fatal in `Recover`, it kept the fleet's only Linux host from taking work for thirty-five minutes.

**On Ceph, a discard moves to the trash and the node's sweep deletes (#280, #292).** `rbd rm` deletes every data object before it returns; killed at the 15-second rbd bound it left the name listed by `rbd ls` with `rbd info` answering ENOENT and the objects still there, and about 1,260 discarded `cache-v-*` volumes accumulated that way. So a root disk (`removeClone`) and a writable cache volume (`discardCacheVolume`, which refuses anything but a `cache-v-` name billet gave: Discard and Create's and Snapshot's cleanup, where the caller owns the volume; it runs `snap purge` first and leaves listed a volume whose snapshots it could not purge, because a failed Snapshot can leave its staging snapshot behind and the node's session cleanup then Discards that volume, and in the trash that snapshot makes every `trash rm` answer ENOTEMPTY forever) go to the cache pool's trash with `rbd trash mv`, and `Client.PurgeTrash`, handed to the background by the node's `Sweep` through `provider.TrashPurger`, deletes them with `rbd trash rm` under `PurgeTimeout` (30 minutes) per image, skipping ENOTEMPTY (every retired writer whose generation is live) and absent images, and joining every other failure. Its trash scope is `billet-*` and names matching `billetCacheImage` exactly (`cache-[vg]-<second>-<24 hex>`, only `v` from the trash). A generation NEVER goes to the trash: `rbd rm` refuses a parent a clone still reads before it deletes anything, and the trash would refuse nothing. Eviction removes an expired generation with `rbd rm`, because it sees only its own host's mappings, so rbd's refusal to remove an image still open (EBUSY) is what protects another node's job, and `rbd trash mv` makes no such refusal; an expired writable volume it moves to the trash instead, after the lock, on `ReclaimOrphans`' proof (below, #305); a failure on one image of either kind is reported and the pass goes on; and it never deletes from the trash under the cache lock, so a pass alternates a `PurgeTrash` outside the lock with a round of generations under it, purging first because the leaf of a lineage a compaction cut off is a retired writer, while a round removes a generation (`evictionRounds`, `maxCacheCloneDepth`), the rounds together holding the lock for at most `evictionLockBudget`, the pass's budget and not each round's, because a writer whose lock retry is in flight when a round releases the lock can miss every gap between rounds (`evictionRoundGap`, four retry delays, which lets one in most of the time but proves nothing); a lock whose release failed may still be held, so it ends the pass, and why a pass stopped is reported apart from the per-image failures, whose number is capped (#799). The same purge finishes half-removed images (`finishHalfRemoved`): a `cache-v-` or `cache-g-` name billet gave, named more than `halfRemovedAfter` (an hour) ago and found unopenable by an earlier sighting at least `halfRemovedRecheck` (fifteen minutes, longer than `cacheCompactionLimit`, the bound on the slowest command that creates a cache image) before, each sighting timed when rbd answered and never at the pass's start (a pass can spend half an hour on removals first), on this node's own clock (the name's time is the creating node's clock), so it is not an image another node is creating, that `rbd ls` lists and `rbd info` cannot open (ENOENT; any other answer is could-not-tell and keeps it), is removed with `rbd rm` under the same bound. The proof is that nothing can open it, and rbd refused to start removing a parent with a child. Not modelled against a real cluster: whether an interrupted `rbd rm` leaves a directory entry or a hidden `REMOVING` trash entry; `rbd rm` by name finishes either. Eviction, Snapshot, retirement and Discard likewise act only on the exact names billet gives (`cacheImageName`, `isCacheVolume`), never on a prefix: `cache-v-<second>-by-hand` or `cache-v-ns/cache-g-…` is not billet's. EVERY DISCARD UNMAPS FIRST, inside `discardCacheVolume`, because `trash mv` ignores watchers and a volume this host still maps answers every purge with EBUSY for good. Only `Discard` used to unmap; a failed create discarded directly, and on 2026-10-03 a `device map` that passed its bound was completed by the kernel afterwards, so the trashed volume stayed mapped until it was unmapped by hand. A map that timed out is could-not-tell, not "nothing mapped". The kernel can still finish such a map after the discard's own device list, which nothing here closes. A PURGE ASKS ONLY WHAT CAN HAVE CHANGED: a trash entry a child held (ENOTEMPTY) is remembered with the time and the count of cache images this client had removed before it asked, and is asked about again only once `rbd rm` has removed a cache image since (Evict's generations, a failed snapshot's candidate, a finished half-removed image) or `trashHeldRecheck` (an hour) has passed, which covers a child another node removed; any other failure is asked about every pass, and an entry the trash no longer lists is forgotten. Likewise `finishHalfRemoved` asks `rbd info` about an image it found openable no sooner than `openableRecheck` (the half-removed recheck) later, so an image whose removal is cut short after an openable sighting is eligible for its first unopenable sighting that much later, is sighted by the pass that reaches it, and still needs the second sighting the recheck after; a pass cut short by its budget or its context keeps both memories for the images it did not reach. Passes run one at a time (`purgeSlot`, a one-token channel, so a caller waiting behind a long pass can still be cancelled), and one never reads the holds another has taken out to rebuild; a pass cancelled before it reaches any image keeps the last resume point. Asking every pass forked about 1,400 processes a second on an idle node (measured-facts.md, 2026-10-12).

**A superseded generation outlives its last use by an hour, not its key's retention (#799).** Retention (seven days, eight for a Docker image store, from the pointer's `retention_hours`) is for a key's current generation, the one a new job reads. A generation whose record names its key while that key's pointer names another is evicted once `supersededGrace` (an hour) has passed since its `used_at`, because no new job reads it and a job that does hold it holds an active record or a mapping, which keep it; the grace covers a job that read the old pointer lock-free and clones that generation a moment later, which otherwise gets a miss. Only a positive reading counts: a generation with no record, a record that names no key, or a key with no pointer keeps the full retention. Measured on the reference deployment on 2026-11-07: `billet-cache` held 5.9 TiB of 7.3 TiB and Ceph went backfillfull. One Go build cache key, published by every job, held 845 generations under the seven-day retention (2.69 TiB of their own data), and the retired writers between them, which the trash cannot delete while a generation is cloned from them, held 3.34 TiB more; the current generations of every key together held 11 GiB. Each publication is cloned from the one before, so a key's history is one lineage that only a compaction cuts, and that lineage unwinds a writer and a generation at a time, which is why `Evict` alternates the purge and its rounds (above). THE FULL PASS ALONE COULD NOT KEEP UP, so the node also sweeps superseded generations on their own (`Client.EvictSuperseded`, `runEviction` in `internal/app/nodecache.go`): every `supersededSweepEvery` (ten minutes), with the same rounds and purges and `supersededSweepBudget` (thirty seconds) of the lock, reaching only generations the index proves superseded, doing none of the full pass's index bookkeeping and leaving its resume point alone. Measured on 2026-11-08, after v0.34.0: the pool held about 4,300 generations, nearly all one per Actions cache key, and a six-hourly pass reached about 1,100 before its five minutes ran out, so the Go key's 160 new generations in twelve hours were reached about once a day while the pool grew by 1.2 TiB.

**A compaction is a clone and a flatten, never `rbd cp`.** Of a snapshot of a clone with object-map, which every cache image has since #394, `rbd cp` copies that clone's own layer, leaves every object only a parent holds as zeros, and exits 0 (Ceph 20.2.0, kernel 7.0, 2026-11-04; the same copy of a clone without object-map, or of the clone's head, is whole). So every candidate at the lineage limit failed `verifyCandidate`, with e2fsck's 4, 8 or 12, and removed itself, and the key's lineage could never move. A generation gains two levels each publication (the writable clone, then the candidate), so a long-lived key got there in four: on the reference node four generations in use sat at lineage 7 on 2026-11-04, and its journal shows no Docker image store or build cache publishing from 2026-10-24 on, while the 2,066 generations at lineage 1, mostly Actions caches, went on being made. `compactCacheImage` clones the snapshot and flattens the clone: whole, sparse, and private until published, where `rbd deep cp --flatten` wrote 40 GiB for a 20 GiB image holding 980 MiB. A flatten cut short has its partial image removed there, on a detached bound of 45 seconds rather than left to the caller's cleanup, because the dead flatten's watcher makes `rbd rm` wait about half a minute and a partial image left behind keeps its parents in the trash for days. Depth is not the trigger, a chain of two shows it, and neither is load or Firecracker. `realcompaction_test.go` holds both halves against a real pool (`BILLET_CEPH_TEST_POOL`), and the fake refuses `cp` outright. Measured in measured-facts.md.

**Every cache image carries object-map, and every command that changes one keeps the kernel client (#394).** `cacheImageFeatures` is Ceph's default set, named rather than inherited from `rbd_default_features`, and `Create` and every cache clone pass it: without object-map a deletion removes every object the image's size could hold, which made the trash purge saturate the cluster (measured-facts.md, 2026-10-05). A clone takes the features explicitly, so a chain created `layering`-only gains them at its next clone. Object-map brings exclusive-lock, which the kernel holds while a volume is mapped, so every snapshot, removal, `trash mv` and image-meta write on a cache image runs under `noBlocklist`; the lock images (the publish lock and the cache index) stay `layering` alone, because Ceph documents exclusive-lock as incompatible with the advisory locks taken on them, and their `lock rm` runs under `noBlocklist` too: the locker is the `rbd lock add` that already exited, so a blocklist entry fences nothing and cost an OSD map epoch at every release of the cache index (#845). `objectmap_test.go` holds both rules over a create, snapshot, publish, clone and discard.

**Past a fill of the pool, the generations unused longest go ahead of their retention.** Retention bounds an archive's age, not the pool's size. A workflow that names a key per commit adds a generation per run that nothing reads again, and seven days of them fill the pool. Measured on the reference deployment on 2026-11-12: billet's own CI saved a race+cover Go build cache of about 1.56 GB per job per run under a key naming the commit; 2,514 of them held about 3.9 TB of a 4.9 TiB pool, `percent_used` read 0.885, and osd.1 passed Ceph's 85% nearfull. So every superseded sweep then calls `Client.EvictUnderPressure` (`sweepSuperseded` in `internal/app/nodecache.go`). It reads the cache pool's `percent_used` from `ceph df` (the pool's share of what its fullest OSD can still take, which nearfull and full are measured against), and past `pressureFill` (0.75) it evicts, in the same rounds and purges as every pass and under `pressureSweepBudget` (two minutes) of the lock, a generation a pointer names, or one in the lineage behind a pointer it removed (below), that nothing holds and has gone unused for `pressureIdle` (an hour, the superseded grace's reason). It takes them least recently used first, whatever their retention, by the later of the pointer's and the generation record's use (a restore of a named generation refreshes the record alone). It removes the pointers naming each generation it removes. A pointer left naming a removed generation would make `Current` and `Match` hand it out, an Actions save of that key refuse as already there, and a build cache's publication try to clone it, all for the rest of the key's retention. Every round of every pass and sweep, whatever the fill, removes a pointer whose generation is no longer in the pool, so a pointer removal that failed after its generation went, or a process stopped between the two, is repaired by the next superseded sweep even when the removal brought the pool below its threshold; the pointer was written after its generation existed, and the round holds the lock every publication takes. The lineage behind a removed generation is pressure's too, once the purge has deleted the writer between, and only on proof it was published. `PublishCAS` writes a record only while the key's pointer names what the record calls `Previous`, so when pressure removes a generation the process remembers (`pressureLineage`, for `pressureLineageKept`, the longest retention) the key and generation each of its records names as `Previous`. A generation every one of whose records is remembered so is a candidate, and its own removal proves the next one behind it. Nothing else no pointer names is: `PublishCAS` writes the generation record before the pointer, so a candidate whose publication stopped between the two looks the same, and its Actions receipt may still publish it. A timestamp is no proof: a later generation of the same key published with no pointer before it and then removed leaves the key unpointed again, so the stopped candidate's retry expects what it finds (Codex round five, 2026-11-12). A restart forgets the proofs, and the full pass then takes the lineage at its retention. Only an active record holds a generation under pressure. Anything pressure tries and does not remove (a failure, a generation a child still reads, one used since) is left for `pressureRetryAfter` (an hour), because pressure always starts from the oldest and those would otherwise lead every sweep and spend its budget. Expired deferrals are pruned at each sweep. A fill it cannot read is an error and evicts nothing. The node logs every sweep that found the pool past its threshold, with the fill and the count evicted. CI's own key became one per job per UTC day, saved only from main or a release branch (#867).

**Storage background work yields to jobs (#394).** The purge reads the host's IO pressure (`/proc/pressure/io`, `full avg10`) before each deletion and, past `purgePressureLimit` (10%), waits `purgeQuietPoll` at a time for at most `purgeQuietMax`, then deletes anyway, and a whole pass, both its trash deletions and its half-removed finishes, yields for at most `purgePassYieldMax` (ten minutes) shared by its workers, so a host that is always busy still purges; an unreadable file paces nothing, and a client built `withRunner` reads nothing of the test host. A guest's disk is a mapped RBD device on the node, so its IO waits count there whether the OSDs are local or not. The image import writes the guest image (80 GiB, written in full) at `importWriteRate` (128 MiB/s, about eleven minutes, inside the thirty-minute `kernelLockWindow` a pull holds across it) on a rolling per-chunk deadline that banks no time lost to a stall, and syncs every `importFlushEvery` (256 MiB): unpaced, it went into the page cache as fast as the source could be read, peaked at 140 GB of memory and landed on a saturated cluster (2026-10-04). `librbd` QoS options do not apply, because the import writes through a kernel-mapped device rather than `rbd import`; measured, `rbd import --rbd_qos_write_bps_limit` is honoured, but the head is written in place.

**An intact orphan volume is reclaimed by an operator, on proof, through the trash (#301).** An `rbd rm` killed while deleting data objects but before its header leaves an image `rbd info` still opens, and the half-removed finisher (ENOENT only) never touches it; the reference deployment's Linux node listed 4,542 `cache-v-*` images over nine days, every sampled one intact (2026-09-30). `billet cache orphans` (`internal/ops/cache/cacheorphans.go`) lists them and `--reclaim` moves them with `rbd trash mv` for `PurgeTrash` to delete; `ceph.Client.ReclaimOrphans` (`internal/store/ceph/orphans.go`) decides, oldest first, and an image qualifies only when ALL of these hold: an exact writable-volume name (`cacheImageName` kind `v`; a generation is never a candidate), named at least `--older-than` ago (`DefaultOrphanAge` six days, past the five days GitHub documents for a self-hosted job, floor `OrphanMinimumAge` 24 hours) AND created that long ago by the cluster's clock (`rbd info`'s `create_timestamp`, which the OSD sets in `cls_rbd` create and rbd prints with ctime in the local zone, read from the v19.2.2 source; the name carries the creating node's clock, which may be behind) both by this node's clock and against `clusterNow`, the latest `create_timestamp` among the eight newest-named images (a lower bound on the cluster's clock that no node's clock enters, the latest rather than the first because a name's order is its creator's clock; the same two clocks judge `used_at`). Recent by this node's clock is a keep verdict; old by it but recent against `clusterNow` is could-not-tell, because a reference too old to prove age proves nothing else (a pool whose only image is the orphan is that case), and no readable reference at all makes every candidate could-not-tell; named by no cache custody record on this node (`node.ReadCacheSessionRecords`, a byte search of every record so a field the reader does not know still protects; an unreadable entry, a directory, a link or a torn installed record refuses the whole pass, and no error names a record's file, which is its session's bearer) and by nothing in the cache index (read as json; rbd prints one object, or nothing for an index without metadata, and anything else refuses the pass), `rbd snap ls --all` empty (a snapshot in any namespace may be a generation's lineage), no entry of this host's `rbd device list` naming it (an entry without pool and name is could-not-tell), `rbd status` naming an empty `watchers` array, and THEN no `billet.cache.used_at` on the volume within the bound: Snapshot on any node writes it before it unmaps the volume to publish, so read after the watcher check it catches a volume whose watcher is gone because its job is publishing; that comparison is against the publishing node's clock, so a node behind by more than the bound can lose that one publication (Snapshot's `snap create` answers ENOENT and the cleanup discards), never the job. A pass takes (moves, or lists as reclaimable) at most `--limit` volumes and every kept one is asked about on the way without counting, because counting the kept ones let the half-removed images the purge is still finishing, oldest of all, use up every pass's limit; an image-meta list on the volume that answers ENOENT is `no longer listed`, never "no use time", because `metaGet` reads a missing image and a missing key alike. Any other rbd answer is `could not tell`, keeps the image and exits 1, and a `trash mv` that errored is `move not confirmed` (it may have happened) and exits 1 too. `rbd trash mv` does NOT refuse an image in use: librbd's `Trash::move` checks no watchers and refuses only when it cannot take an exclusive lock, which a volume `Create` makes (`layering` only) does not have and a krbd mapping of a clone hands over on request unless mapped `exclusive` (read from the Ceph v19.2.2 source, not measured), so the watcher check is the guard, and the age bound is what makes a map between the check and the move impossible, since nothing maps a volume after the job that named it. `rbd rm` and `rbd trash rm` do refuse an image with watchers (`PreRemoveRequest`, EBUSY). EVICTION TAKES THE SAME PROOF for every expired `cache-v` (#305): `Evict` removes generations under the cache lock, then calls `judgeVolumes`, the pass `ReclaimOrphans` runs after validating its options, with `Reclaim`, the eviction age floored at `OrphanMinimumAge`, `evictionVolumeLimit` (1,000) and the node's sessions, OUTSIDE the lock, because the proof costs about six rbd calls a volume and `rbd trash mv` needs no index consistency. Its `rbd rm` of a large volume used to be killed by the 15-second bound under the lock and end the pass, so a backlog built up instead of being evicted. The sessions come from `ceph.WithCacheSessions`, which `startNodeCache` (`internal/app/nodecache.go`) passes as `CacheSessionNames(cfg)` (`node.ReadCacheSessionRecords` afresh each pass, a structural test proving the wiring); without it, or when the records cannot be read, every volume is kept and `Evict` says so. Every `could not tell` and `move not confirmed`, and every generation failure, is joined into `Evict`'s error, the first ten by name and the rest counted (`evictionFailures`), because one unreadable cluster clock keeps every volume alike. Because a failed generation removal no longer ends the pass, the generations' part starts no new work once it has held the lock for `evictionLockBudget` (five minutes from the moment the lock is held, index-record removals included, inside `cacheLockWaitLimit`, the longest a writer waits for the lock; the generation in hand still finishes under the command bound), names how many wait for the next pass outside the ten-name cap, and the next pass resumes after the last generation it reached (`evictResume`), so slowly failing generations at the front of the order cannot spend every pass's budget. The node runs eviction in its own goroutine (`startNodeCache`), started after the first `RenewActive`, because a pass can take many minutes and the cleanup loop finishes closed sessions, whose publications are abandoned after `publishWindow` (30 minutes). A volume with a snapshot is kept, never `snap purge`d as eviction once did, because the snapshot may be a generation's lineage; a failed Snapshot's leftover staging snapshot is the session cleanup's Discard to clear.

**A kernel mapping no job accounts for is unmapped on proof, never forced, and counted (#494).** The reference node kept eight `cache-v-*` mappings no job held for ten days, through every restart, from the 2026-10-03 incident in which its kernel client was blocklisted; each also kept its volume from eviction (`judgeOrphan` keeps a mapped volume), and each unmapped cleanly with a plain `rbd device unmap` on 2026-10-14. `ceph.Client.SweepKernelMappings` (`internal/store/ceph/kernelmaps.go`), run by the node's `evictPass` (`internal/app/nodecache.go`) before `Evict` so the same pass can reclaim a released volume, unmaps a mapping only when ALL of these hold: in the cache pool's default namespace (`pool/name` addresses nothing else), the head (snap `-`; a row that does not say which snapshot it maps is could-not-tell) of an exact writable-volume name (`cacheImageName` kind `v`); named at least `VolumeMapAge` (six hours) ago by this host's clock, which bounds when it was mapped because a writable volume is mapped only by `Create` or `Clone` under a fresh name (`lockedAt` is this host's clock) and never mapped again (`Snapshot` unmaps it, `RestoreMounts` reuses the recorded device), and its custody record follows within the cache handler's bound plus a lineage copy and a map; named by no cache custody record, read afresh before the table so a session that ends meanwhile unmaps its own; found so by an earlier pass of the same process at least `mapSightingGap` (an hour) before on the monotonic clock, keyed by device and image, because the name is wall-clock and a clock stepped forward by six hours would age a volume still waiting for its record (Codex review, 2026-10-16; a restart only delays a release); recorded as mapped by this node (`billet.cache.mapped_by`, which `Create` and `Clone` write before they map when the client has `WithMapOwner`, and which `nodeCacheStore` gives as the deployment and node name; ALWAYS written after a clone, because a clone copies its parent's metadata), read through `image-meta list` so a missing key (not this node's, kept as `not recorded as this node's`) is told from a missing image, which is then looked up by its exact name in the cache pool's trash: a writable volume goes there only once disposed of and a trashed image cannot be mapped again, so its mapping is a leftover whoever made it (the 2026-10-03 map the kernel finished after the failed Create trashed the volume; Opus review, 2026-10-16), and an image in neither, or a trash that cannot be read, is could-not-tell; because the mapping table is the host's and the custody records this node's, so another identity's volume on the same host is in none of them (Codex review, 2026-10-16); and the kernel agrees, since a non-forced unmap succeeds only when nothing has the device open. HOLDERS AND MOUNTS PROVE NOTHING: on the reference node `/sys/block/rbdN/holders` was empty and the host's `/proc/mounts` listed nothing for every mapping, live jobs' volumes included (2026-10-16), because the node's unit mounts in its own namespace and a VMM opens its device inside its jail, so the kernel's EBUSY is the only "held" proof and is a verdict (`held open`, kept and warned about by name), never retried as `unmapDevice` retries a teardown racing a VMM's exit. The unmap names the image (`rbd device unmap pool/name`), never `/dev/rbdN`, whose number the kernel gives the next map; at most once per image a pass, because `rbd device unmap <spec>` releases whichever mapping comes first; runs on `context.WithoutCancel` under `MapTimeout`, for `unmapDevice`'s blocklisting reason; none starts once the pass is cancelled, checked again after the owner read, the last moment before the unmap is detached; and the node cache's stop cancels the eviction context and waits for a sweep in flight (`awaitSweep`), because the unit's `KillMode=mixed` kills an unmap the process exits under: beside the listener's shutdown, not after it, and a pass the stop has cancelled ends after its sweep, because `Evict`'s own generation-map sweep unmaps outside the slot the stop waits on, and on a handover no longer than the listener's grace (`nodeCacheSweepWait`, decided when the stop runs by `nodeCacheSweepWaitFor`, since a stop that asks to drain overrides node.stop's handover as the loop's `DrainRequested` does, and from the one answer `Run` latches for both, `latchedDrainRequest`, because the request is a file read twice and a request arriving between the loop's reading and the cache's would have the cache wait a drain's bound out of a handover's leases; Codex review, 2026-10-16), because nothing renews the handed-over leases until the next process registers and a longer wait would have the reaper quarantine the running jobs; on a drain, `MapTimeout` plus five seconds. Only `evictPass` calls the sweep (`TestOnlyTheEvictionPassSweepsTheKernelMappings`); no other billet path unmaps an image no session or jail names, so nothing else resolves the same spec meanwhile. Without a session reader, or with records it cannot read, a pass unmaps nothing. `KernelMappings` is the read-only half: `billet check` prints its counts and names the unaccounted (never failing the check, could-not-tell when not root), and the node serves `billet_node_rbd_mappings{state}` from it at every scrape (`internal/app/nodemetrics.go`).

**A golden's system disk is the builder's clone, renamed in place, and nothing that sweeps the cache pool takes it (#508).** A Firecracker capture publishes its root disk with `Client.PublishRoot`: `snap create` of the clone as a generation (`g` and the UTC time, the image pool's naming), then `rename` of the clone to `golden-<the builder's lease id>` (a lease id, as root clones are `billet-<lease>`, because a snapshot's name is its capturer's and the pool is shared), both in the cache pool and both keeping the kernel client, because the paused guest's device still maps it. A restore clones that generation (`CloneGolden`) as a job clones an image-pool one. It is renamed rather than copied because a golden is the size of its image: the reference deployment's `ubuntu-2404-x64` is 80 GiB, fully allocated, while the rename costs two calls (a 256 MiB flatten took 1.7 s; the rename path, snapshot and rename together, about 2 s). Measured on the reference node, 2026-10-21, Ceph 20.2: a rename of a clone that is mapped and held open succeeds; the kernel keeps the name it mapped (`rbd device list` and `/sys/bus/rbd/devices/N/name` still give the old one), so the builder's teardown unmaps by the old name as before, and its `trash mv` of the old name answers "No such file or directory", which `removeClone` already reads as done; a fork of `golden@g...` holds the builder's disk byte for byte; and `snap rm` of a generation a fork still clones succeeds, Ceph keeping its data in the snapshot trash namespace until the fork goes. The name keeps it out of every sweep: the trash purge deletes only `billet-*` root disks and `cache-*` volumes, and the orphan report keeps a name billet does not give its volumes, which also means nothing removes a golden yet: its retention, and pinning it while restores run from it, are #508's still to do. A golden stays a copy-on-write child of the image-pool generation its builder booted, so that generation's data outlives a reap for as long as the golden does. `WithdrawRoot` renames a golden back and removes its generation, for a capture whose files were not published, and the publication's own failures undo themselves the same way, because a command cut short can have taken effect: a failed `snap create` removes the snapshot it may have made, and a failed `rename` is renamed back from whichever name holds the clone. A golden whose files are already visible (a sync after the rename failed) keeps its disk. Only an undo that itself fails leaves a `golden-*` disk no published snapshot names; the error says so, and it is the retention's to reclaim with the rest.

**A breaker per node and store stops jobs asking a store that has stopped answering, and decides nothing else (#531).** `internal/node/storebreaker.go`: three different sessions failing within five minutes, with no volume handed over between them, open it (a window that outlasts three deadlines, or a site launching one job at a time ages its first failure out before its third), on what a job waits on (Clone, Create, Match and Current, the first byte of a content-addressed read, and a publication's timeouts). ONE SESSION COUNTS ONCE, because a job can make the store refuse it and must not be able to turn every other job's caches off (a key the store would refuse is refused at the attach for the same reason). Past a call's limit `watch` counts it as a timeout while it still waits, because a read of a volume whose OSDs have gone waits in the kernel and nothing can cancel it. ErrMiss, ErrConflict and a missing object are the store answering, and a cancelled caller or a request's own deadline says nothing, because a guest names its own deadline (a gRPC client's `grpc-timeout` reaches the context). NEVER COUNTED: Discard, RenewActive, eviction, the purge and the sweeps, because on 2026-09-25 every `rbd rm` failed for an hour while clones worked; and a publication's refusal, only its timeouts (`countedPublication`), because a candidate that is not clean is one job's bad write, and the reference node logged 8 to 535 of those a day from 2026-10-24, which would have sent every job cold. While it is open every cache answers at once with the store unasked and records `bypassed` (`lease.ImageCacheBypassed` and its two siblings, which an older plane hears as `unavailable`; wire 46). A probe every 30 s (`store.Current` of a key nothing publishes, bounded at 10 s, where only an answer counts) moves it to probation, not closed, because the index can answer while its lock is out of reach: `admit` lets one job at a time ask for a volume or publish, asked right before the store is so that nothing that goes on to ask nothing holds the trial; only a volume handed over or a pointer moved closes it (`storeCall.decides`, never a lookup or a clone's miss, which are lock-free), since a quiet node's only way back may be a publication; a failure reopens it, and a job that went away holds its trial for one deadline. Blob legs and reads of a mounted volume use `allow`, which waits for closed, and `billet_cache_breaker_open` reads 0 on probation. In memory only: a restart starts closed. PAST THE DEADLINE THE JOB GOES ON AND THE CALL DOES NOT STOP (`acquireVolume`): the store's calls run off the request on a context of their own, the handler answers at `storeDeadline`, and `finishLateAcquisition` puts what comes back into the session's durable `Late` and discards it, while `session.acquiring` keeps the session from finishing under a call still out and caps each session at one, since a guest hanging up on each request would otherwise start a store call per request. Only `handOver`'s Clone and Create count, never the discard an oversized clone needs inside the same acquisition. A breaker never decides capacity, custody or teardown, and a timeout is never "the volume is gone". What a node's breaker is doing reaches `billet status` through `POST /v1/nodes/{node}/cache-store` (`forNewWork`, since a superseded process's word would be read as its replacement's) and `node_cache_stores` (migration 82), read under the registration in force as `node_inventory` is, and re-sent at every registration (`LoopOptions.Registered`). A service nobody guards (`GuardStore` not called) asks as it always did; `guardNodeStore` in `internal/app/nodecache.go` guards every Firecracker and EC2 node. With no monitors at all, or with the cache pool's OSDs stopped, a Firecracker node launches nothing, because its root disk is an RBD clone in the cache pool (`CloneRoot`; measured 2026-11-05, the rehearsal in `docs/reference/records/cache-breaker.md`): that is capacity, not this, and the breaker never hears of it. `docs/reference/records/cache-breaker.md` holds the rehearsal.
