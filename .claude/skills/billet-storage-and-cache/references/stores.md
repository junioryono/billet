# Sites, stores and discards

Part of the `billet-storage-and-cache` skill. Each rule is stated in full, with the measurement or incident behind it.

**Storage is a property of the site, not of the compute backend.** `node.ceph` is a sibling of `node.firecracker`, because two hosts in one place map the same pools, and that sharing is the whole reason Ceph replaced ZFS (a ZFS clone exists only on the machine that took it, verified by mapping a clone from a second kernel client). It is required for firecracker and refused for every other backend. `node.ceph.user` defaults to `billet` and `admin` is refused, because `admin` is what `rbd` picks for itself when nothing names an identity and an admin key can delete a pool.

**A cache writer lease is not a capacity lease.** A `WriterLease` lasts across quiesce, filesystem verification and the fenced pointer CAS; a capacity lease stays charged until compute is proved gone. Reusing one lifetime for the other strands machine capacity behind a cache commit or lets an expired compute holder publish. Publication is guarded by three things at once: the expected generation, a live writer lease, and a monotone `FencingToken` whose zero value authorises nothing. A generation record is written before the current pointer, so an interrupted commit leaves the prior pointer or a complete new one. A `Candidate` needs a `Filesystem` with type, UUID and a proven-clean flag; non-empty alone proves neither.

**A writer lease that will not publish is released, and a release is exact.** `Store.ReleaseWriter` gives a lease back on every failure between acquisition and the pointer advance, on both backends. It removes only a record matching the lease's identity, expiry and fence, moves no fence and no pointer, and is a silent no-op for anything else, because a consumed, superseded or foreign lease already leaves the key free and a release runs on a failure path where a second error buries the first. Before it existed a failed publication held the key for the lease's remaining fifteen minutes and the next writer polled S3 every 100ms with nothing in the log; the wait is now a doubling back-off from 500ms to 30s, never longer than the holder's remaining lease, announced once per lease through `store.WriterHeldError`, which unwraps to `ErrConflict`. An Actions receipt is the one place a lease outlives the frame that took it: a fresh lease counts only once the receipt is durable, and whether the old lease is live is the store's question, so it is released unconditionally before re-acquiring.

**Ceph is driven through the `rbd` command, and every naming rule is pinned to what rbd does.** The Go binding is cgo over librados, which would end the single static binary; every call is a process, so the store is for operations measured in tens per job, never per block. A pool beginning with `-` is refused because billet builds positional `pool/image` specs and `rbd info -weirdpool/x` answers `unrecognised option`, not because of `-p`; identity rules written from a false premise were removed, keeping only the `client.` prefix, which measurably authenticates as `client.client.billet`. Ceph creates pools named `a/b`, `a@b` and `a b`, so "is this legal" is never the question; "does billet address it correctly" is.

**Clone v2 is a requirement, and two settings decide it.** On clone v1 a snapshot must be protected before it is cloned and a protected snapshot with a live clone can be neither unprotected nor removed, so a generation any running job holds would be undeletable. `billet check` refuses such a cluster. `require-min-compat-client` is the floor and `rbd_default_clone_format` overrides it, cluster-wide or per pool, and measured, the destination pool's value governs a clone; billet reads both for both pools and names the cause with the command that removes it (`ceph config rm client …` does not remove a pool-level override). The release rule is "not one of the releases older than mimic", because that set can never grow, and `unknown` (Ceph's enum zero, which the setter refuses) counts as older. Replication is reported and not judged.

**A real build on RBD costs 2%, and the fio number that said otherwise measured a machine doing nothing but IO.** `go build` cold 1.02x, fsync-per-file 2.36x, a cold read of 40,000 small files 4.07x (IOPS-bound, the opposite of what the synthetic table predicted, and the cache-hydrate path). Clone, map and mount is about 350ms for a 10GiB image; sequential reads reach 4.5GB/s at depth. Readahead and stride alignment moved nothing.

**The ebs-s3 store's first real publication was refused twice by things every fake accepted.** EC2's `CreateSnapshot` takes no `ClientToken` (`UnknownParameter`), so the token travels as the `sh.billet.snapshot-token` tag and idempotency is billet's: an attempt looks for a snapshot carrying its token before creating one and again after a failed call. The token names the operation (key plus volume), never the attempt, so a restarted attempt finds what a previous one made; a refusal AWS parsed is never retried; an ambiguous answer is reconciled against eventually consistent `DescribeSnapshots` for about a minute; a snapshot in error state counts as the token spent; two snapshots carrying one token are refused. And `ec2:CreateVolume` from a snapshot authorises the snapshot as well, so `BilletCacheCloneSource` grants it on the snapshot ARN conditioned on the owner tag. The hot path never deletes; `Delete` exists only for `billet decommission`'s purge. State objects are namespaced by deployment and site, and pre-release objects without an owner are ignored rather than migrated. And a 404 on a state read is an empty cache only when S3 says `NoSuchKey`: every 404 used to be, so a bucket that did not exist read exactly like a cold cache, every job fetched cold, the cache path fails open by design and `billet check`'s bucket probe reported that the bucket answered. `internal/awss3` holds that rule and the measurement behind it (`billet-providers-aws`).

**A discard is storage, not compute, and never runs on the node's command path (#223).** A teardown that proves the compute gone only closes the cache session (`CacheService.Close`, durable before it returns) and signals `ClosedSessions`. The volumes are discarded by the cache service's own loop in `cmd/billet/main.go`, which runs `RetryClosed` on that signal and every five minutes. `Recover` likewise only closes the sessions of compute the inventory proves absent (`ReconcileInventory`), and a failure there is a warning, never a reason to refuse work. Measured 2026-09-25: every `rbd rm` of a finished job's clone failed for an hour (`exit status 16`, image still open, or no answer). Run in line on the node's serial command queue, each failure delayed the next launch until launches took four to five minutes. Made fatal in `Recover`, it kept the fleet's only Linux host from taking work for thirty-five minutes.

**On Ceph, a discard moves to the trash and the node's sweep deletes (#280, #292).** `rbd rm` deletes every data object before it returns; killed at the 15-second rbd bound it left the name listed by `rbd ls` with `rbd info` answering ENOENT and the objects still there, and about 1,260 discarded `cache-v-*` volumes accumulated that way. So a root disk (`removeClone`) and a writable cache volume (`discardCacheVolume`, which refuses anything but a `cache-v-` name billet gave: Discard and Create's and Snapshot's cleanup, where the caller owns the volume; it runs `snap purge` first and leaves listed a volume whose snapshots it could not purge, because a failed Snapshot can leave its staging snapshot behind and the node's session cleanup then Discards that volume, and in the trash that snapshot makes every `trash rm` answer ENOTEMPTY forever) go to the cache pool's trash with `rbd trash mv`, and `Client.PurgeTrash`, handed to the background by the node's `Sweep` through `provider.TrashPurger`, deletes them with `rbd trash rm` under `PurgeTimeout` (30 minutes) per image, skipping ENOTEMPTY (every retired writer whose generation is live) and absent images, and joining every other failure. Its trash scope is `billet-*` and names matching `billetCacheImage` exactly (`cache-[vg]-<second>-<24 hex>`, only `v` from the trash). A generation NEVER goes to the trash: `rbd rm` refuses a parent a clone still reads before it deletes anything, and the trash would refuse nothing. Eviction removes an expired generation with `rbd rm`, because it sees only its own host's mappings, so rbd's refusal to remove an image still open (EBUSY) is what protects another node's job, and `rbd trash mv` makes no such refusal; an expired writable volume it moves to the trash instead, after the lock, on `ReclaimOrphans`' proof (below, #305); a failure on one image of either kind is reported and the pass goes on; and it never deletes from the trash under the cache lock, so a chain is reclaimed over eviction passes as the purge removes the writers between its links. The same purge finishes half-removed images (`finishHalfRemoved`): a `cache-v-` or `cache-g-` name billet gave, named more than `halfRemovedAfter` (an hour) ago and found unopenable by an earlier sighting at least `halfRemovedRecheck` (fifteen minutes, longer than `cacheCompactionLimit`, the bound on the slowest command that creates a cache image) before, each sighting timed when rbd answered and never at the pass's start (a pass can spend half an hour on removals first), on this node's own clock (the name's time is the creating node's clock), so it is not an image another node is creating, that `rbd ls` lists and `rbd info` cannot open (ENOENT; any other answer is could-not-tell and keeps it), is removed with `rbd rm` under the same bound. The proof is that nothing can open it, and rbd refused to start removing a parent with a child. Not modelled against a real cluster: whether an interrupted `rbd rm` leaves a directory entry or a hidden `REMOVING` trash entry; `rbd rm` by name finishes either. Eviction, Snapshot, retirement and Discard likewise act only on the exact names billet gives (`cacheImageName`, `isCacheVolume`), never on a prefix: `cache-v-<second>-by-hand` or `cache-v-ns/cache-g-…` is not billet's. EVERY DISCARD UNMAPS FIRST, inside `discardCacheVolume`, because `trash mv` ignores watchers and a volume this host still maps answers every purge with EBUSY for good. Only `Discard` used to unmap; a failed create discarded directly, and on 2026-10-03 a `device map` that passed its bound was completed by the kernel afterwards, so the trashed volume stayed mapped until it was unmapped by hand. A map that timed out is could-not-tell, not "nothing mapped". The kernel can still finish such a map after the discard's own device list, which nothing here closes.

**Every cache image carries object-map, and every command that changes one keeps the kernel client (#394).** `cacheImageFeatures` is Ceph's default set, named rather than inherited from `rbd_default_features`, and `Create`, both cache clones and compaction's `rbd cp` pass it: without object-map a deletion removes every object the image's size could hold, which made the trash purge saturate the cluster (measured-facts.md, 2026-10-05). A clone takes the features explicitly, so a chain created `layering`-only gains them at its next clone. Object-map brings exclusive-lock, which the kernel holds while a volume is mapped, so every snapshot, removal, `trash mv` and image-meta write on a cache image runs under `keepKernelClient`; the publish lock image stays `layering` alone, because Ceph documents exclusive-lock as incompatible with the advisory locks taken on it, and its `lock rm` keeps the blocklist that is its fence. `objectmap_test.go` holds both rules over a create, snapshot, publish, clone and discard.

**Storage background work yields to jobs (#394).** The purge reads the host's IO pressure (`/proc/pressure/io`, `full avg10`) before each deletion and, past `purgePressureLimit` (10%), waits `purgeQuietPoll` at a time for at most `purgeQuietMax`, then deletes anyway, and a whole pass, both its trash deletions and its half-removed finishes, yields for at most `purgePassYieldMax` (ten minutes) shared by its workers, so a host that is always busy still purges; an unreadable file paces nothing, and a client built `withRunner` reads nothing of the test host. A guest's disk is a mapped RBD device on the node, so its IO waits count there whether the OSDs are local or not. The image import writes the guest image (80 GiB, written in full) at `importWriteRate` (128 MiB/s, about eleven minutes, inside the thirty-minute `kernelLockWindow` a pull holds across it) on a rolling per-chunk deadline that banks no time lost to a stall, and syncs every `importFlushEvery` (256 MiB): unpaced, it went into the page cache as fast as the source could be read, peaked at 140 GB of memory and landed on a saturated cluster (2026-10-04). `librbd` QoS options do not apply, because the import writes through a kernel-mapped device rather than `rbd import`; measured, `rbd import --rbd_qos_write_bps_limit` is honoured, but the head is written in place.

**An intact orphan volume is reclaimed by an operator, on proof, through the trash (#301).** An `rbd rm` killed while deleting data objects but before its header leaves an image `rbd info` still opens, and the half-removed finisher (ENOENT only) never touches it; the reference deployment's Linux node listed 4,542 `cache-v-*` images over nine days, every sampled one intact (2026-09-30). `billet cache orphans` (`cmd/billet/cacheorphans.go`) lists them and `--reclaim` moves them with `rbd trash mv` for `PurgeTrash` to delete; `ceph.Client.ReclaimOrphans` (`internal/store/ceph/orphans.go`) decides, oldest first, and an image qualifies only when ALL of these hold: an exact writable-volume name (`cacheImageName` kind `v`; a generation is never a candidate), named at least `--older-than` ago (`DefaultOrphanAge` six days, past the five days GitHub documents for a self-hosted job, floor `OrphanMinimumAge` 24 hours) AND created that long ago by the cluster's clock (`rbd info`'s `create_timestamp`, which the OSD sets in `cls_rbd` create and rbd prints with ctime in the local zone, read from the v19.2.2 source; the name carries the creating node's clock, which may be behind) both by this node's clock and against `clusterNow`, the latest `create_timestamp` among the eight newest-named images (a lower bound on the cluster's clock that no node's clock enters, the latest rather than the first because a name's order is its creator's clock; the same two clocks judge `used_at`). Recent by this node's clock is a keep verdict; old by it but recent against `clusterNow` is could-not-tell, because a reference too old to prove age proves nothing else (a pool whose only image is the orphan is that case), and no readable reference at all makes every candidate could-not-tell; named by no cache custody record on this node (`node.ReadCacheSessionRecords`, a byte search of every record so a field the reader does not know still protects; an unreadable entry, a directory, a link or a torn installed record refuses the whole pass, and no error names a record's file, which is its session's bearer) and by nothing in the cache index (read as json; rbd prints one object, or nothing for an index without metadata, and anything else refuses the pass), `rbd snap ls --all` empty (a snapshot in any namespace may be a generation's lineage), no entry of this host's `rbd device list` naming it (an entry without pool and name is could-not-tell), `rbd status` naming an empty `watchers` array, and THEN no `billet.cache.used_at` on the volume within the bound: Snapshot on any node writes it before it unmaps the volume to publish, so read after the watcher check it catches a volume whose watcher is gone because its job is publishing; that comparison is against the publishing node's clock, so a node behind by more than the bound can lose that one publication (Snapshot's `snap create` answers ENOENT and the cleanup discards), never the job. A pass takes (moves, or lists as reclaimable) at most `--limit` volumes and every kept one is asked about on the way without counting, because counting the kept ones let the half-removed images the purge is still finishing, oldest of all, use up every pass's limit; an image-meta list on the volume that answers ENOENT is `no longer listed`, never "no use time", because `metaGet` reads a missing image and a missing key alike. Any other rbd answer is `could not tell`, keeps the image and exits 1, and a `trash mv` that errored is `move not confirmed` (it may have happened) and exits 1 too. `rbd trash mv` does NOT refuse an image in use: librbd's `Trash::move` checks no watchers and refuses only when it cannot take an exclusive lock, which a volume `Create` makes (`layering` only) does not have and a krbd mapping of a clone hands over on request unless mapped `exclusive` (read from the Ceph v19.2.2 source, not measured), so the watcher check is the guard, and the age bound is what makes a map between the check and the move impossible, since nothing maps a volume after the job that named it. `rbd rm` and `rbd trash rm` do refuse an image with watchers (`PreRemoveRequest`, EBUSY). EVICTION TAKES THE SAME PROOF for every expired `cache-v` (#305): `Evict` removes generations under the cache lock, then calls `judgeVolumes`, the pass `ReclaimOrphans` runs after validating its options, with `Reclaim`, the eviction age floored at `OrphanMinimumAge`, `evictionVolumeLimit` (1,000) and the node's sessions, OUTSIDE the lock, because the proof costs about six rbd calls a volume and `rbd trash mv` needs no index consistency. Its `rbd rm` of a large volume used to be killed by the 15-second bound under the lock and end the pass, so a backlog built up instead of being evicted. The sessions come from `ceph.WithCacheSessions`, which `startNodeCache` (`internal/app/nodecache.go`) passes as `CacheSessionNames(cfg)` (`node.ReadCacheSessionRecords` afresh each pass, a structural test proving the wiring); without it, or when the records cannot be read, every volume is kept and `Evict` says so. Every `could not tell` and `move not confirmed`, and every generation failure, is joined into `Evict`'s error, the first ten by name and the rest counted (`evictionFailures`), because one unreadable cluster clock keeps every volume alike. Because a failed generation removal no longer ends the pass, the generations' part starts no new work once it has held the lock for `evictionLockBudget` (five minutes from the moment the lock is held, index-record removals included, inside `cacheLockWaitLimit`, the longest a writer waits for the lock; the generation in hand still finishes under the command bound), names how many wait for the next pass outside the ten-name cap, and the next pass resumes after the last generation it reached (`evictResume`), so slowly failing generations at the front of the order cannot spend every pass's budget. The node runs eviction in its own goroutine (`startNodeCache`), started after the first `RenewActive`, because a pass can take many minutes and the cleanup loop finishes closed sessions, whose publications are abandoned after `publishWindow` (30 minutes). A volume with a snapshot is kept, never `snap purge`d as eviction once did, because the snapshot may be a generation's lineage; a failed Snapshot's leftover staging snapshot is the session cleanup's Discard to clear.
