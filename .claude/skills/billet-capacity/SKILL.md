# Capacity, leases, and custody

These are the rules that keep billet from promising a machine it does not have. Break one and the symptom is a job assigned to a host with no room, or capacity that is never handed back.

### Capacity is escrowed BEFORE a listener advertises

Each tier is its own GitHub scale set with its own `maxCapacity`. If listeners advertise independently, GitHub can fill all of them at once and the host is overcommitted with nothing to stop it. Reserve against the global ledger first, advertise second. Capacity is a **vector** — CPU, memory, macOS licence slots, disk — never one integer.

`internal/alloc` owns this, and three details are load-bearing:

- **The headroom check and the insert are ONE transaction.** Checking outside it is a read followed by a hopeful write. Measured: moving the check out produced **28 grants against a ceiling of 4** under concurrency. `TestConcurrentReservationsNeverOvercommit` is the guard.
- **A lease's `node` stays NULL until a node binds it, but `target_node` is set at ESCROW.** The two answer different questions: the target is where billet decided the work goes, the node is where it actually went. Capacity is charged on `COALESCE(node, target_node)`, because a reservation aimed at a machine has already spent it — counting only bound leases let a tier escrow against the same host repeatedly in the window before its first launch, which is the overcommit the escrow exists to prevent, moved down from the deployment to the machine.
- **Every reservation names a machine.** It used to be set only for a tier that pinned itself, which left an ordinary lease charged to the deployment and to no host — so the fleet's remaining room never shrank and billet advertised the same slots repeatedly. `Bind` was always a verifier and needed no change; it simply started always having a target to verify against.
- **What a tier advertises is `min(deployment ceiling, Σ over eligible machines)`.** The fleet term stops billet promising more than the machines can hold; the ceiling keeps a one-box install behaving as it did, since a host detecting more threads than its config allows would otherwise win.
- **A REMOTE lease is charged for the SHAPE, not the tier request.** The node registers its ordered shapes — `node.ec2.instance_types`, or `node.codebuild.compute_types` — placement picks the first fitting one and stores both the immutable requested resources and the charged shape on the lease. A fallback is a new purchase decision and must resize the charge atomically against both the node and deployment ceilings before the request is sent. A budget refusal may try another declared shape; it may never reach the API first and reconcile the overspend later. **The predicate is `RunsOnHost`, not `== ec2`**, and it was `!= ProviderEC2` until a second remote backend existed: a third one added without touching that line would be charged the smaller TIER request while buying the shape, which is the same overcommit recreated silently on a machine nobody can see.
- **The epoch is a fence, and a reclaim bumps it.** Without that, a holder declared dead and replaced keeps writing to a lease someone else now owns — an orderly takeover becoming two concurrent owners of one slot. Every write presents its epoch; a stale one is refused.

The state machine is written down in `validTransitions` rather than implied by scattered UPDATEs, and terminal phases have no successors: a lease that released its capacity must never move backwards and re-acquire it, which is what a double-admit looks like from the inside.

### What is advertised follows demand: one discovery slot beyond the assigned count, capped at escrow

The listener holds the escrow in states — `held` (free), `acquiring` (promised to a request billet has claimed from GitHub but has not yet been given, keyed by request id), and `running` (assigned) — plus `adopted` for restart-survived compute. What it ADVERTISES is `min(total escrowed capacity, targetCapacity)`, and `targetCapacity` keeps exactly ONE backed discovery slot beyond the work GitHub reports assigned: `max(TotalAssignedJobs, acquiring+running+adopted) + 1`. This is demand-following, and it replaced an earlier model that advertised the whole escrowed maximum unchanged. The reason is fairness between tiers on one deployment: a zero-capacity scale set receives no work and no statistics, so a tier must advertise at least one slot to ever be discovered — but an idle tier that advertised its ENTIRE free escrow would hold capacity every peer tier could be using and starve them for as long as it stayed idle. One discovery slot is enough to be found; the advertisement then climbs with assigned work and is always capped by escrow, so the sum across listeners is still bounded by the budget and the escrow-before-advertise invariant is untouched.

The warm pool behind the advertisement is reconciled to `desired = TotalAssignedJobs` by `reconcilePool`: it launches runners up to desired and retires the surplus, and the assignment-deficit skip in `handle` (`TotalAssignedJobs − active`) uses the same `alloc.ActiveRunnerLeases` count. **That count is where a genuinely hard invariant lives, and it is not yet fully solved.** The question the count must answer is "how many runners can GitHub still route a job to", and the true signal is whether each runner's GitHub registration has been removed — but the count is phase-based (`phase NOT IN ('capacity','done','failed')`) and the lease carries no durable deregistration flag. So it over-counts a completed-job `teardown` corpse against the deficit (a dropped-job path when a new job is assigned while an old destroy retries), while excluding `teardown`/`quarantine`/`retiring` by phase would under-count against a runner whose deregistration has NOT completed — an ambiguous-launch custody teardown or a reaped-but-still-registered idle runner — and let the grow loop launch a replacement against a live runner, a double-schedule whose losing side is also a dropped job. The correct fix is a durable per-lease deregistration signal set when `RemoveRunner` succeeds, counted as `not deregistered`; until then neither the include nor the exclude phase-predicate is safe in every case. The deficit-skip on `active ≥ TotalAssignedJobs` is separately fine: the `Assigned` message itself is the causal signal that authorises acting, not the reverted statistics-timer below.

**`acquiring` exists because a promise is not a count.** Capping acquisitions at "how many free leases are there right now" is an instantaneous measure, and an acquisition is an obligation that lasts until the assignment arrives. Leaving the lease in `held` while the claim is in flight let one lease back two consecutive offers, let a lease promised to one request be consumed by the assignment of another, and let the heartbeat spend it out from under a claim already on the wire. Reserving it under the mutex *before* the network call fixes all three at once, which is the tell that they were one bug rather than three.

**A HEARTBEAT PASS'S BUDGET STARTS AFTER IT HOLDS THE MUTEX, AND THE ORDER IS THE WHOLE POINT.** Each pass gets its own deadline so the allocator calls made under `l.mu` cannot run on unboundedly — the loop's context is already detached from `Run`'s caller, so cancellation will not end them, and what does is this deadline, which the allocator's context-aware SQLite operations honour. Created at the TICK instead, that deadline is spent WAITING FOR BILLET'S OWN LOCK — so the pass reaches `heartbeatHeld` already expired, asks the allocator nothing, and `renew` then reads its own silence as the allocator's. Past the TTL that is `renewalStale`, which drops the lease out of `running` and parks it in the cleanup set for a destroy: an ordinary stall — `assign` and the completion paths hold this mutex across allocator writes, while `launch` deliberately does not — manufacturing the conclusion that a healthy job's lease may already have been reaped, and tearing down somebody's build for it. Measured, not reasoned about: holding the mutex across a pass reproduces it, and it is what a CI failure of `TestACancellationInsideTheLongPollStillDrains` turned out to be — a 700ms stall against that test's 300ms TTL produced its exact message, `Running() = 0, want 1`, under the old ordering and not under the new one. **The stall has to be ESTABLISHED rather than slept through, and the seam has to BE the lock**: the first version of the regression test started the loop and then held the mutex, which proves nothing about where the loop was, and a tick landing after the sleep let the mutant survive; a hook merely placed above the lock is no better, because it proves only that it ran and the goroutine can be descheduled between it and the deadline. `Listener.heartbeatLock` replaces the acquisition itself, so standing in it proves everything the pass sequences BEFORE the lock has already happened — which under the wrong ordering is the deadline, and the stall then burns a budget that already exists. It is the same could-not-tell/no collapse below, wearing the clothes of a timeout: a `Heartbeat` that returned the pass's own expired context is not the allocator declining to confirm the lease. Bounding the ALLOCATOR CALLS is what the deadline is for, and they do not begin until the lock is held.

**Heartbeats must not be bounded by the poll.** A long poll was assumed to be about 50 seconds against a 90 second TTL, which reads like ample margin. **Measured against a real organization on the first poll billet ever made, it ran ~88 seconds** — two seconds inside the TTL — and the vendor's HTTP client permits far longer once slow responses and retries are counted. Renewal that happens only *between* polls stops for as long as one poll lasts. The reaper then terminalises the leases, another tier escrows the capacity, and the poll returns an assignment backed by a lease this listener no longer holds. Tying renewal to the poll makes the safety of the whole escrow depend on a timeout billet does not control.

**Derive the cadence from the allocator's actual TTL, never from `DefaultLeaseTTL`.** A cadence computed from the default is correct only for a default-configured allocator; under a shorter TTL every lease expires between beats and advertised capacity climbs — measured at six times the budget before a test caught it. Nothing in the type system will catch this.

That makes heartbeat the only writer concurrent with the poll loop, so the escrow takes a mutex, and `assign` holds it **across** the allocator write. Releasing it around the write to keep heartbeats snappy looks obviously right and is not: it opens a window where the write succeeds but a concurrent heartbeat has already dropped the lease, leaving the assignment durable in the ledger and tracked nowhere in memory. A transient heartbeat error **keeps** the lease — only `ErrFenced` and `ErrLeaseNotFound` mean it is genuinely someone else's. Dropping on a busy database removes the lease from the release path too, so the ledger keeps counting it until the reaper expires it.

The message lifecycle closes: `Available` → acquire, `Assigned` → consume escrow, `Completed` → release. Idempotency uses billet's durable scheduler id: GitHub's ordinary positive `runnerRequestId` when present, or a collision-free negative id transactionally assigned to the stable `jobId` when the direct-assignment path sends `runnerRequestId: 0`. Zero is never a scheduler identity. An offered job still sends the original wire id to `AcquireJobs`; if distinct offers share one wire id, billet must refuse because the response cannot distinguish which promise landed. Acknowledging `Completed` without releasing leaves the lease open until the reaper expires it, withholding capacity and recording the wrong conclusion against it.

### A commitment made to a remote service cannot be revoked by a local timer

`acquiring` is the one escrow state with no way back on its own: every exit needs GitHub to say something. That reads exactly like a leak — a lease renewed forever because a message went missing — and the obvious fix is to age it out. **That fix was written, reviewed, and reverted, and the reason generalises well beyond this listener.**

`AcquireJobs` is one-way. There is no decline or release endpoint on the session client, and `DeleteMessage` acknowledges a *notification* rather than refusing a job. So releasing the escrow on a timer hands nothing back to GitHub. It only means billet has forgotten it owes a runner while GitHub still expects one — the freed slot goes to another tier, and the assignment, when it arrives, has nothing behind it. A fix for a capacity leak had created a way to drop live work.

The reasoning that produced it was sound and the premise was not. The question asked was *can this state end on its own?* The question that mattered was **are we entitled to end it unilaterally?** When a local record mirrors a commitment held by someone else, only they can release it; the local timer can report, and that is all. So a stale promise is reported and kept — it is capacity billet genuinely still owes — and the real remedy is to invalidate the session so GitHub itself redelivers.

**The second attempt is the instructive one, because it looked like it had escaped this.** Instead of a timer it released a promise when GitHub's own statistics reported the scale set had no job outstanding of any kind — apparently authorised by the party holding the commitment, with a staleness check only to avoid racing an in-flight acquisition. It was the same bug. The staleness check bounds how old *billet's promise* is; it says nothing about how old the *statistics* are, and the response carries no observation time, generation, or request identity to pin them to. Elapsed local time was still doing the authorising, now paired with a snapshot of unknown freshness — plus a quiet assumption that those counters are exhaustive, atomically maintained, and scoped as expected.

So: **a freshness check on your own record is not a causal fence on someone else's snapshot.** To act on remote state you need something that provably postdates your own action — a version, an observation time, a per-request status. Absent that, more samples and longer thresholds are the same guess with more decimal places. When the API does not offer one, the honest answer is to leave the gap open, report it, and go and measure the real system.

The same distinction decides how loudly to fail. An assignment with no escrow behind it **declines and carries on**, because that is reachable by ordinary races and stopping the control plane strands every tier's capacity over one job. A scale-set response that is not a subset of its request **stops the listener**, because no race can produce it: it means the API broke, billet can no longer tell which remote commitments are real, and stopping is itself the remedy since a fresh session makes GitHub redeliver. Match the blast radius to whether the condition is a race or a broken contract.

### Compute is unaccounted for until proven otherwise, and that is a state with a name

`internal/node/custody.go`. A **custody** entry is a lease whose compute billet cannot account for and which nothing else in the process is managing. Two things produce one and they are the same situation from different sides:

- **Adopted** — a container survived a restart. The runner inside is talking to GitHub on its own and may well finish the job.
- **Discarded** — a launch failed ambiguously and its cleanup was not confirmed.

Both heartbeat the lease so the reaper leaves it alone; both release only when the compute is confirmed gone. The rules that were each learned by getting them wrong:

- **A negative observation is not automatically a causal result.** A `docker ps` issued right after a lost `docker run` can overtake the daemon and see nothing, so compute never causally observed waits through `strayGrace`, measured from the first successful miss rather than from when custody began. A host backend's successful launch or inventory sighting is causal and makes its first later absence trustworthy. A remote backend is eventually consistent rather than monotonic, so every absence stays behind the full `strayGrace`; a provider error or later sighting resets that interval. Its prompt causal path is an explicit terminal record from a targeted lookup, which fleet inventory excludes so it does not reconcile an hour of historical corpses. A successful synchronous `Destroy` is immediate proof.
- **A DRAIN'S COMPUTE BARRIER USES THE SAME ABSENCE RULE AND TAKES NONE OF CUSTODY'S SHORTCUTS.** `alloc.Quiescence` answers from the ledger and cannot see compute whose lease has already gone — a listener that loses a running lease keeps an in-memory obligation to destroy what it launched, and a launch whose lease was reclaimed can create compute it then fails to destroy. Neither is in the ledger, neither survives a restart, and both leave an instance carrying billet's own name on the host's provider. So a second barrier ASKS: a durable singleton request (`compute_barrier`, scoped to the admission generation) that the control plane observes, dispatching `nodeapi.CommandInventory` through each node's serial queue. **What makes the answer causal is `nodes.dispatch_generation`**, advanced durably BEFORE a launch enters that host's queue and under the same hold of `Plane.mu` — an observation is recorded only while that number and the node epoch are both unchanged, so a launch dispatched after the question makes the acknowledgement match nothing. The alternative, where a launch INVALIDATES an acknowledgement, races the response it is invalidating and loses. **`computeAbsenceGrace` is deliberately the same five minutes as `strayGrace` and `quarantineGrace`** — one question, one answer — and unlike custody it applies to EVERY backend, because the host-backend shortcut is granted only to a causally observed entry and a barrier has no observation of the class it exists for. A host's own ordinary sweep saying it holds compute BEATS a completed run — the two coexist whenever a create was accepted but not yet listed, and no fence moves — which may block and can never clear. What establishes a run is TWO observations spanning the grace (`observed_at − empty_since`), never one plus elapsed time: a host that answers empty once and then disconnects must not age into a proof, and both fences still match in exactly that case. An error, a non-empty list, or either fence moving ends the run rather than ageing it. A host below `nodeapi.VersionComputeBarrier` is never asked and is reported as unprovable; the expected set is bounded by `billet nodes decommission`, whose forced form stays durably marked UNPROVEN so an exclusion can never read as a proof.
- **Adoption renews the lease at the moment it adopts.** Billet may have been down longer than a lease TTL, and the control plane reaps BEFORE its first tend — so leaving the renewal to the tick let the reaper terminalize the lease that had just been adopted.
- **"Could not verify" is not "safe to destroy."** Only `ErrLeaseNotFound` proves a lease is gone. Any other read error aborts recovery, having destroyed nothing.
- **Serializing a mutation is not serializing a transition.** Holding the lock for the flag write and releasing it before the backend calls is the same race, one line down.
- **A staged CodeBuild registration has FOUR removers, and only the fourth may use the ledger.** The node removes it on a conclusive launch refusal, a confirmed teardown, and custody settlement — each a proof about the compute. The fourth is the control plane's sweep over the path the node registered, which removes a registration only once the ledger has held its lease TERMINAL for longer than the service's own build-plus-queued ceilings (`codebuild.ServiceInventoryWindow`); an unknown lease is kept and named, never read as gone, and a ledger error stops the pass. The provider's inventory is never consulted, because "no build" and "not yet appeared" are one observation there.
- **A cleanup obligation is owed to the COMPUTE, not to the lease.** Only a successful destroy discharges a pending completion retry. Losing the lease — fenced, reaped — changes who owns the capacity; it does not make the container stop running, and GitHub will not redeliver the completion that would ask again. If no lease remains, skip the release and keep destroying.

  Written down because the opposite was committed for one round and the argument for it was seductive: the capacity really is someone else's, so the record looks like litter. Two separate rules were being conflated. No record is CREATED for a request this listener never held — a restart loses the map while leases live on, and those retries could accomplish nothing. That says nothing about a record created when the listener DID hold the lease.
- **"Could not X" usually collapses two different facts, and only one is evidence.** A heartbeat that returns ErrFenced is the allocator SAYING the lease is not ours; a heartbeat that times out is the database saying nothing at all. Returning one boolean for both made a listener that briefly lost its ledger forget the containers it had launched. The same shape recurs everywhere in this codebase — a failed destroy is not proof the container survived, an absent `docker ps` row is not proof it is gone. When a call can fail for reasons that mean opposite things, the return type has to be able to say so.
- **A claim and an obligation expire differently.** Losing a lease ends this listener's claim on the CAPACITY. It does not end its obligation to destroy the container it started, and the two have been conflated three separate times: once for pending cleanup records, once for running leases dropped by the heartbeat, once at shutdown. Whenever a record is removed because "it is not ours any more", ask what was launched under it.
- **A bound shorter than the work it bounds causes the failure it prevents.** The shutdown grace was 90 seconds against a node command timeout of TEN MINUTES, so an ordinary slow destroy tripped the watchdog, stopped renewal, and let the reaper reclaim capacity whose container was still being destroyed — precisely what the grace existed to avoid. Before choosing a timeout, find the longest legitimate operation underneath it and make the bound larger, or make the work smaller.
- **Concurrency against a serial queue can be worse than sequence.** A node runs commands one at a time and each command's timeout starts when it is QUEUED, so firing twenty destroys at once starts twenty ten-minute clocks against a queue that serves them in turn: the later ones expire while the node is working happily through the earlier ones, and healthy jobs are recorded as failures. Fan-out needs a bound chosen against the SERVER's concurrency, not the client's patience.
- **An OPTIONAL capability cannot carry a safety invariant.** The reversed change above was defended with "both shipped runners implement `Sweeper`, which destroys compute no lease is holding." True, and irrelevant: `Sweeper` is a type assertion on `Runner`, so that reasoning makes correctness depend on which implementation is plugged in, and billet is meant to be extended by strangers. If safety rests on a capability, the interface must require it — otherwise assume the implementation without it, and let the capability be a backstop rather than the mechanism.
- **Time warns; it does not authorise a teardown.** Held compute has NO bound by default (`DefaultMaxCustody = 0`) and warns hourly. Elapsed time is not evidence that a job stopped making progress — billet imposes no job limit and self-hosted runners run past GitHub's six-hour default — so killing live work must be authorised by a completion, an observed exit, or an operator. An operator who knows their longest job can set one with `node.WithMaxCustody`; a job killed by it is archived as FAILED, not done.

  **The SHUTDOWN drain now follows the same rule, and used to be the exception that disproved it.** `server.drain_timeout` bounded how long a stopping listener waited and then destroyed whatever was still running — a timer authorising exactly the teardown this bullet says time cannot authorise. It is now a reporting threshold with no deadline behind it: a stop leaves running work alive with its lease charged, and the next control plane re-adopts it. `destroyAll`'s `includeRunning` parameter is where the two cases are separated, and `billet force-destroy` is the only thing that passes true — asserted structurally, because nothing in the type system separates the two booleans.
- **Declared prices report exposure; they do not gate admission.** The ordered shape allowlist plus node and deployment resource ceilings are the enforceable policy. `billet check` bounds one configured node; `billet status` bounds the registered REMOTE fleet by the tighter of the shared deployment ceiling and the sum of node ceilings, including disconnected registrations because their instances may still be billable. AWS Budgets is the account-wide backstop. **The query is keyed on `RunsOnHost`, not on `== ec2`, and it was the latter** — so a deployment whose only cloud capacity was `codebuild` printed no cost line at all, and the ABSENCE of a cost line is exactly what a fleet that costs nothing looks like. Any backend declaring priced shapes is costed by the same code, which is the same generalisation `nodeRow.cost` needed one file over.

- **A RESERVED FLEET'S CLAIM ENDS ONLY AT A PROVEN DECOMMISSION, and two narrower rules shipped first — both read as obviously right.** A reserved CodeBuild fleet is one shared pool, so two nodes naming it each register its whole capacity and the deployment promises GitHub more concurrent jobs than AWS will run. Only the control plane can see that (the two config files are on two machines), so the fleet rides the registration and the ledger refuses a second claimant. The first version scoped that refusal to `live = 1` — but **liveness says nothing about remote compute**: `ForgetEveryNode` marks every host not-live whenever a control plane STARTS, and a node that merely disconnected is not-live while its builds keep running, so a differently named node could take the fleet across an ordinary restart. The second scoped it to `decommissioned_at = ''` — but **`--force` is not a proof either**: it exists precisely for the host nothing could ask and records `decommission_proven = 0` so every later drain keeps saying so. What releases a claim is `decommission_proven = 1`, which is the drain's compute barrier. The ordinary replacement needs none of this because it reuses the node NAME, which the query excludes. **The generalisation: permission to hand over shared capacity comes from what is PROVED, never from what is broken** — the `ca retire` guard learned the same thing over three rounds, and this is the third place it has been needed.
- **A live custody holder is released THROUGH that holder, not underneath it.** Custody and accepted teardown are durable lease phases with `held_at`, so `billet status` and `billet leases` can name the node and age. `leases release --force` resolves quarantine immediately because no holder exists; for custody or teardown it sets a request the node observes as `ErrForceRelease` on heartbeat, then the node drops its local entry and terminalizes the lease. The operator assertion replaces proof, but ordering still prevents a process from believing it owns capacity the control plane already resold. **A holder that DIED never observes that request, and that is not the trap it reads as**: a custody or teardown lease is renewed by the node's janitor and by nothing else, so the process dying stops the renewals, the reaper quarantines the lease within one TTL, and the same command releases it from there — measured against the real CodeBuild backend, not reasoned about. The lease records the INCARNATION of the process holding it (`leases.holder_incarnation` beside `nodes.incarnation`, migration 45) — never its registration epoch, which moves on every registration including the same process registering again after a control-plane restart, so an epoch comparison would call every surviving lease's holder replaced after each one. `billet leases` can then say a holder was REPLACED; that is a report, never a verdict, because a different process is equally a superseded one still draining, and what separates the two is whether the lease keeps being renewed. Two things the reproduction found instead. **A restart re-adopting a still-running TEARDOWN must keep that phase**: `teardown → custody` is not a transition, and an adoption that reported custody was refused on every tend, renewing the lease each time and never reaching the build. **And the teardown's OUTCOME has to outlive the process that decided it**, which a second review round caught in the fix for that: a launch that failed ambiguously holds `outcome = failed` in its custody entry while the ledger records only the phase, and teardown serves a completed job and a failed launch alike — so a restart reconstructing the outcome from the phase archived `done` for a runner that never registered. The node now writes `alloc.LaunchFailedReason` (and the other reasons billet writes for itself) through `MarkFailure` as soon as this entry's epoch is current — a successful heartbeat OR a re-adopted quarantine, since either can go on to settle the lease in the same tend — and again the moment an outcome flips to failed later (a busy runner found retired), always BEFORE anything touches the provider; adoption reads `FailureReason` back as it always did. **The disruption token is decided by the EXACT reason, never by a prefix** (a third round caught both halves): a launch that never ran, a retired runner and an operator's forced release carry none, a job destroyed under the custody bound carries `DisruptionHeldPastLimit` because billet ended a running job, and anything else — including text that merely starts with `billet:`, since the reason arrives over the wire from a node — keeps the `reclaimed` token an external reclaim must have. `ForceRelease` records `ForceReleasedReason` in the same statement that requests or applies it, unless an earlier reason already explains the failure. The idempotent report of a hold also re-records the holder (`RefreshLeaseHolder`), or the process that died would stay the durable holder while its replacement tended the compute. **And a completion bound to a replaced incarnation is the state the acceptance record actually hit**: the plane rightly refuses to hand the destroy to a replacement process, and the listener read that as an ordinary failed destroy and kept RENEWING the `busy` lease while it retried — never expired, never quarantined, never settled, held by nobody, refused by `--force`. Renewal is what a party holding COMPUTE does, and a listener holds none: on `ErrHolderUnavailable` it now parks the obligation without the lease, so whoever holds the compute renews it or the reaper quarantines it. **The completion then CORRECTS and never SETTLES**: the replacement host's own inventory, a fresh observation after the grace, settles the quarantined lease provisionally through the ordinary reconcile, and the bound completion's retry only corrects that verdict to GitHub's (`SettleCompletionOnTerminalLease`). A first version let the completion settle an open quarantine from the plane's CACHED inventory snapshot, and a review caught why that is the one-observation-plus-a-clock shape this file keeps removing: the snapshot has no ordering against the quarantine, so one taken before a build became visible and never refreshed would free the capacity under a running build. **Every completion path that cannot reach its holder is correction-only** — replaced, never replaced, or forgotten by a restarted plane — so the not-owned branch that settled from the cached snapshot is gone too, and `ResolveQuarantineForCompletion` with it. **The owner record ends with the lease**: kept while the lease is open so a draining superseded process keeps its entitlement, dropped when the completion finds the lease terminal, which is safe only because the wire answers a superseded process asking about an ended lease with `not_found` — except the runner-removal route, which PERFORMS the removal for it — and for a current process whose owner record a restart dropped — when the history row attributes the job to the asking node (membership alone let a node withdraw another host's runner), since a replacement's inventory can settle a lease while the superseded process still runs the guest and routing-before-compute holds after the lease is over; a node never reads a refusal as a removal. **A job start repairs the token of a reason that landed before it** (the two are unordered), and **a parked launch failure keeps its reason across the reaper** through `ResolveQuarantineFailed` and a backfill onto a failed row nothing explains. **Inventory's provisional verdict reads the result GitHub already recorded**: a lease whose completion was delivered before its teardown holder died settles as `done`, not as a provisional failure nothing will correct. **A conclusive launch failure archives `LaunchFailedReason`** through `alloc.ReleaseFailed`, and **the disruption token consults `job_history.started_at`** before the reason's text, so a node cannot suppress the token for a job the ledger saw start; `force-released` is refused over the wire.

### A clean exit withdraws; silence still means nothing

A node that drains and exits used to say nothing, and the plane could not tell a clean exit from a partition — so it kept the host in placement until `staleAfter`, and every job aimed there in that window waited it out before being placed on the other host at the site (measured at five minutes on the site acceptance). The silence window cannot be shortened: a crash and a partition are one observation from the plane, and the compute barrier and custody both depend on that caution. What closes the gap is a **deliberate, authenticated withdrawal** — `POST /v1/nodes/{node}/withdraw`, wire 19 — from the one authority on the node's intent, sent by `stopGracefully` AFTER its wait, on every exit (idle, drained, hurried) and never by a superseded process.

- **It releases nothing and marks nothing.** `alloc.NodeWithdrawn` sets `live = 0` and does not call `markNodeDisruptedTx`, touch `drained` or the decommission columns, or discard the barrier run. A lease escrowed against the host in the last instant is answered "nothing started" by the plane and handed back by the listener, exactly as after silence.
- **Two fences, and the second is not redundant.** The UPDATE matches on the registration epoch AND the incarnation. The epoch proves no registration landed since the plane read it; the incarnation proves the process asking is the one that registration recorded. A superseded process still holds the certificate and the name, and its withdrawal must not take the replacement out of the fleet — `forNewWork` refuses it at the guard and `Plane.Withdraw` again under the lock.
- **Ledger first, memory second.** Placement escrows against the ledger's live set long before the plane's map is consulted, so the durable half is what stops the next job being aimed here. A ledger that cannot record the withdrawal leaves the node exactly where it was, and the node asks again a bounded number of times before exiting anyway — a stop is never a failure.
- **The hurried exit withdraws too.** The compute stays running and its leases stay charged, which is the documented outcome of a second signal; what changes is only that nothing new is aimed at a process that will not poll again.
- **Checked where it is emitted.** An older control plane answers the route with a bare 404, so a node negotiated below `nodeapi.VersionNodeWithdrawal` stops as before and says the plane is too old to be told.

### A restart waits for its own message session

**A MESSAGE SESSION IS SINGLE-HOLDER AND GITHUB WILL NOT HAND IT OVER — measured against a real organization, not read.** Opening a second session for a scale set whose first was abandoned answers `409 Conflict ... RunnerScaleSetSessionConflictException ... already has an active session for owner`. So the recovery path a restart depends on is NOT "take over", it is "wait for the abandoned one to expire".

**`runTier` returned that error, which meant a control plane killed and restarted did not start at all** — every upgrade, every crash, every `systemctl restart` — and took its tier's listener with it while saying nothing actionable. `server.openSession` waits on `ErrSessionHeld` and reports it as the ordinary state it is; every other reason a session cannot open is still returned at once, because only this one resolves by itself.

**Nothing is lost in the window.** GitHub queues a job for 24 hours with no runner available, and running compute is held by its node and re-adopted — the cost is scheduling latency, which ADR-001 already accepts. What is NOT known is how long GitHub takes to expire an abandoned session; the conformance run in `internal/integration` records the refusal, not the timeout.

**This is what a live conformance test is FOR, and it found the defect on its first real run.** The test RECORDS rather than asserts: an earlier version treated the refusal as a failure, which is the same collapse the capacity code keeps removing — a measurement is not a pass/fail, and calling it one hides the finding it was written to make.

### An inventory that shrinks is capacity that gets resold

A node's `List` is what the control plane reconciles against, and it frees the capacity of every lease ABSENT from it. So the dangerous failure of a provider's `List` is not an error — an error stops reconciliation — it is an answer that is short, empty and successful.

Three ways the firecracker backend could have produced one, all found in review rather than by a test:

- **A path derived at startup from something an operator can change.** The jailer names its chroot after the resolved firecracker binary, and the reference host installs that binary as a versioned filename behind a stable symlink precisely so a version can be bumped. Retarget it, restart billet — which is documented, and which billet promises leaves running jobs running — and every guest started before the bump sits in a directory the new process does not read. Billet now enumerates every directory a jailer has built in, and the owner marker is what keeps that safe.
- **Teardown removing the evidence.** `Destroy` continued past a VMM it could not stop, removing the jail — which holds the pid file, the only handle for ever stopping it. The guest then runs a job nothing can find, nothing can kill, and that `List` no longer reports.
- **An identity mismatch collapsed into a verdict.** A socket answering for a DIFFERENT microVM was read as "this one is not running", and the caller destroys what is not running. Neither answer was available; that is what an error is for.

The general form, and it applies to any backend: **ask what makes a row appear in the inventory, then ask what could make that thing stop being true while the compute keeps running.**

### GitHub does not requeue a job whose runner vanished mid-execution

**A scale-set runner is a pool member, not the job that caused scale-up.** GitHub's `JobStarted` is the authoritative binding between a registration and the job it actually consumed. Billet journals that binding separately from the launch request, resolves completion through the physical runner's lease, and then reconciles idle surplus to `TotalAssignedJobs`. A completed physical runner and the different idle runner originally reserved for that job are two settlements, not alternatives. Scale-down selects only durable `idle` members, removes the GitHub registration before destroying compute, and keeps both compute and capacity when removal fails; `retiring` is the crash-recovery journal. A contradictory started identity quarantines that member rather than stopping unrelated tiers.

**Quarantine from before durable runner identity is recovered against GitHub, never guessed.** The quarantined lease and deterministic instance name are the restart-safe starting point. An exact busy ephemeral organization runner is journaled with its exact ID before it stays in custody, so a configured custody deadline can still remove routing before compute; its empty actual-job fields let a delayed authoritative `JobStarted` complete the binding. An absent or exact idle ephemeral runner is removed remotely and then claimed for retirement with an atomic check that refuses to overwrite an authoritative started binding, including one written during the remote lookup or deletion. When no row existed, that same transaction inserts a `retiring` tombstone so a later queued `JobStarted` cannot recreate the identity after recovery has already returned. Multiple matches, missing response fields, a non-ephemeral identity, an unexpected status, or an API failure all keep the guest and its capacity charged.

Checked against the vendored `scaleset` README, after I asserted the opposite in a commit message and had to retract it. Reassignment is documented for a job *"assigned to your scale set but not acquired by a runner in time"* — GitHub cancels and requeues that, up to 3 times. It says **nothing** about a job a runner has already started.

So force-killing a container that is running a job is a **deliberate job failure**, not a recovery, and "a graceful shutdown does it too" is not a defence: a graceful shutdown is a choice the operator made. This is why restart recovery adopts.

### So billet ATTRIBUTES a lost job rather than acting on one, and the evidence is recorded where it is OBSERVED

This was originally scoped as "re-run a job billet believes was lost" and is deliberately not that. A re-run is a side effect on somebody's repository — a deploy, a release, a migration, run a second time — and every runner in this ecosystem fails-and-stops on a lost runner, so matching them is the principle of least surprise as well as the safe choice. What billet owes the person whose build went red is the one thing only billet knows: what its own infrastructure was doing at the time.

**Two facts, recorded separately, with no verdict stored between them.** `leases.disruption` is a token from a closed set (`alloc.Disruption`) naming what billet's infrastructure did, carried into `job_history`; `job_history.result` is GitHub's own conclusion, written by the listener when the completion arrives. `billet leases failures` shows rows where the result is not `succeeded` and a disruption exists, and its footer says out loud that the pairing is circumstantial and that nothing was re-run. Deriving rather than storing a verdict is what keeps one source of truth per fact — and a view that reads as an accusation is worse than no view, because the next thing anybody does is stop believing it.

**A disruption is written in the transaction that OBSERVES it, never reconstructed at completion from a snapshot.** The obvious implementation — at completion, look at `nodes.live` and the lease's phase and decide — is wrong for a reason the ledger makes invisible: `ForgetEveryNode` sets `live = 0` across the whole fleet whenever a control plane starts, because liveness is the plane's judgement and a plane that has just started has not formed one. A verdict derived later would blame an unreachable host for every failure replayed across a restart. So `NodeGone` marks its host's leases, `ResolveQuarantineFor` marks the guest it found absent, and `MarkFailure` marks the reclaim — each fenced by whatever already fences that path — and `ForgetEveryNode` marks nothing.

**The guard that matters is "GitHub has not reported on this job yet".** An ordinary EC2 teardown outlives its completion by minutes, and a host forgotten in that window would otherwise be reported to the author of a perfectly ordinary test failure as billet's fault. `disruptionGuard` refuses a lease that already carries a recorded result, refuses a phase where nothing was ever running, and keeps the FIRST observation — a later disruption is a consequence of the earlier one at least as often as it is a separate event, and only the earliest can still have been causal.

**`holder-lost` is deliberately NOT a disruption, and the reason generalises.** A reap that quarantines an `online`/`busy` lease proves the CONTROL PLANE stopped renewing — the listener is the renewer, not the guest — so the usual cause is billet's own process or its SQLite going away while the job carried on talking to GitHub. Restart recovery adopts exactly those guests and they routinely finish green. Recording it would misread billet restarting as somebody's broken build. Ask what the signal proves about the COMPUTE, not about billet's bookkeeping.

### An instance is named for its lease, and the name is the only durable link

`provider.InstanceName` / `provider.LeaseOf`. Nothing writes "this container belongs to that lease" anywhere, so after a crash the name is all reconciliation has. Two consequences:

- The instance carries **billet's** name, never GitHub's runner name. They are different identities and conflating them made every orphan unattributable.
- Docker's `--filter name=X` is a **SUBSTRING** match — measured, not assumed: `billet-abc` really does return `billet-abcdef`. `Find` compares exactly afterwards.

### A lease must be renewed by exactly one party, and there are three handovers

Custody exists because a remote launch has three outcomes and one of them is UNKNOWN. Every defect in this area has been a moment where the count of parties renewing a lease was zero — never two, which is harmless, because `Heartbeat` is idempotent and a released lease answers `ErrLeaseNotFound`.

The three moments, each of which cost a review round to find:

- **While the provider is still working.** The plane gives up after the command timeout and tells the listener the node has custody, so the listener stops. The node is inside `provider.Launch` and adopts nothing until it returns. The node now renews from the moment it commits to launching (`r.launching`), which is the first instant either side can be sure something may exist.
- **When the report arrives too late.** The plane records a TOMBSTONE for every launch it abandons — on timeout and on re-registration — so a late success is answered with "this lease is yours" instead of 204. Without the tombstone the node files the instance in its ordinary running set, which nothing renews.
- **When the result races the timeout.** Both select branches are live at once. `settle` drains the result channel while holding the plane mutex, which is what makes the answer exact: `Result` sends under the same lock, so the send has either completed or not started.
