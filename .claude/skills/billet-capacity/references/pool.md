# The pool of rented bare metal

Part of the `billet-capacity` skill. ADR-028 is the design; `internal/pool` is the scaler, `internal/hostsource` the contract its sources implement, and `pool_orders` (migration 73) its ledger. `docs/operating/bare-metal-pool.md` is what an operator reads.

**A pool order is committed before its source is asked, and read back before anything else is done about it (ADR-028).** `Pool.order` writes the row with `RecordPoolOrder`, then mints the order's single-use join token, then calls `Source.Order`. The next step's first act is `resume` on every order still `ordering`: `Source.Find` by the order's identifier, which the source recorded on the host (EC2's `ClientToken` and `sh.billet.pool-order` tag, phoenixNAP's hostname). An answer that is not a host and not a refusal leaves the order `ordering`; it never decides anything by itself. `ErrNotSent` is the one failure that proves no host exists (a local refusal, or a quota or stock read before the request), and it is recorded as refused, like the source's own refusals. Every move of an order is one way and starts from one state (`movePoolOrder` refuses with `ErrPoolOrderMoved` otherwise), so two processes cannot both decide what became of one order.

**A lost answer is sent again only inside the source's deduplication window; past it, the order is uncertain and a person decides.** `hostsource.Terms.IdempotentFor` is that window, counted from the order's first attempt as the ledger recorded it: ten minutes for AWS (billet's bound, inside what the ec2 provider measured `ClientToken` keeping), zero for phoenixNAP, whose API takes no idempotency key. A resend carries a fresh join token, so its user data differs from the first attempt's; EC2 answers a resend whose first attempt landed with `IdempotentParameterMismatch`, which the source reports as an error, which leaves the order `ordering` for the next read back to find. An absent listing alone never licenses ordering again, because an order still in flight can land after a list that did not show it. `billet pool abandon --reason` closes an uncertain order once a person has looked in the source's own console.

**Nothing is ordered on an architecture while an order there is unknown, and demand grows the pool one host at a time while any placed host has not joined.** An order being ordered or uncertain may hold a host the floor or the demand already counts, so `Step` skips the architecture entirely while one exists, floor or no floor (Codex found the floor ordering past an unknown order). Demand is a Firecracker tier with an architecture whose capacity report is fresh (within `DefaultDemandFreshness`, five minutes), not in error, and says `HostShortage`: work it could not buy for, with only hosts to blame (`RoomRefusal.HostOnly`), on a count in hand (`demandKnown`) and not draining. `WhyNoRoom` judges the share and the ceiling against the tier's own shape even where no host can place it or its hosts are full, because it used to return before judging them and their zero values read as room: a spent ceiling beside a full host published a shortage, and the pool would have ordered a host nothing could buy (Codex, round 3). A recovered session or an ended launch makes the count unknown while the refusal it kept survives, and the report is stamped fresh, so the shortage needs the count too. Not `Waiting`: a tier no host can place never waits in the admission queue, so its `Waiting` is zero for exactly the shortage a pool exists to fill (Codex found the pool unable to grow from an empty fleet that way). A missing, stale or failed report makes the reading `ErrDemandUnknown`: growth for demand waits and the floor is kept, because a report can be a previous controller's, written before this one's listeners polled. A placed host is on its way until a node joins from it (`node_name`, which the join writes), so until the join lands demand grows the pool by one host at most. A choice its source refused is passed over for `refusal_backoff`.

**An order records its source's scope and is read back only there; a resend the source refuses is uncertain, not refused.** `Source.Scope` is where the source orders (`aws:<account>:<region>:<subnet>:<zone>`, `phoenixnap:<client id>`), recorded on the order. The account is in it because a shared subnet admits several accounts, each blind to the others' instances, and it is asked at every `Scope`, never kept, because credentials can rotate into another account without a restart. A config or credentials changed since, or a source no longer configured, makes `resume` mark the order uncertain rather than read it back anywhere else, because a read there could miss the host it placed. A scope that cannot be read is could-not-tell: nothing is ordered, and nothing resolved, on it. A pool launch makes one HTTP attempt (`callOnce`), so a refusal is never the second attempt of a launch whose first may have landed, and its request has no `GetBody`, because Go's HTTP/2 client replays a rewindable body after some stream errors from the peer inside one `Do` (go1.26.0's `h2_bundle.go`, by its source, not probed against AWS). A first attempt's refusal, or a failure before it was sent (a token not minted, a boot not rendered), refuses the order. A resend's refusal does not: it says nothing about the first attempt, which may have placed a host, so the order is uncertain. The prelude is written through a quoted heredoc to a file removed by an EXIT trap and run by `bash -euo pipefail` of its own, so its failure stops the boot before the token is spent and its `set -x` or `exit` never reaches the join; a NUL in it or a join argument is refused, because bash drops it. The boot is rendered once at assembly with a token-length stand-in, so a prelude too long for EC2's user data stops the start rather than every order.

**Not built yet:** the join that links a host to its node, automated admission, and release on proof (`NewDrainedProof`, `NewUnjoinedProof`), which needs that link. Until then a pool host is drained and released by hand.
