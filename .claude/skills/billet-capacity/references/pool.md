# The pool of rented bare metal

Part of the `billet-capacity` skill. ADR-030 is the design; `internal/pool` is the scaler, `internal/hostsource` the contract its sources implement, and `pool_orders` (migration 75) its ledger. `docs/operating/bare-metal-pool.md` is what an operator reads.

**A pool order is committed before its source is asked, and read back before anything else is done about it (ADR-030).** `Pool.order` writes the row with `RecordPoolOrder`, then mints the order's single-use join token, then calls `Source.Order`. The next step's first act is `resume` on every order still `ordering`: `Source.Find` by the order's identifier, which the source recorded on the host (EC2's `ClientToken` and `sh.billet.pool-order` tag, phoenixNAP's hostname). An answer that is not a host and not a refusal leaves the order `ordering`; it never decides anything by itself. `ErrNotSent` is the one failure that proves no host exists (a local refusal, or a quota or stock read before the request), and it is recorded as refused, like the source's own refusals. Every move of an order is one way and starts from one state (`movePoolOrder` refuses with `ErrPoolOrderMoved` otherwise), so two processes cannot both decide what became of one order.

**A lost answer is sent again only inside the source's deduplication window; past it, the order is uncertain and a person decides.** `hostsource.Terms.IdempotentFor` is that window, counted from the order's first attempt as the ledger recorded it: ten minutes for AWS (billet's bound, inside what the ec2 provider measured `ClientToken` keeping), zero for phoenixNAP, whose API takes no idempotency key. A resend carries a fresh join token, so its user data differs from the first attempt's; EC2 answers a resend whose first attempt landed with `IdempotentParameterMismatch`, which the source reports as an error, which leaves the order `ordering` for the next read back to find. An absent listing alone never licenses ordering again, because an order still in flight can land after a list that did not show it. An order whose shape its source no longer declares cannot be sent again, so a lost answer for it is uncertain at once. An uncertain order is read back at every step where it was placed, and only there, never sent again: a host its source now lists there places it (`UncertainPoolOrderFound`), so a host whose answer was lost joins rather than asking for good. `billet pool abandon --reason` closes an uncertain order once a person has looked in the source's own console.

**Nothing is ordered on an architecture while an order there is unknown, and demand grows the pool one host at a time while any placed host has not joined.** An order being ordered or uncertain may hold a host the floor or the demand already counts, so `Step` skips the architecture entirely while one exists, floor or no floor (Codex found the floor ordering past an unknown order). Demand is a Firecracker tier with an architecture, not pinned to one node (no host the pool orders is that node), whose capacity report is fresh (within `DefaultDemandFreshness`, five minutes), not in error, and says `HostShortage`: work it could not buy for, with only hosts to blame (`RoomRefusal.HostOnly`), on a count in hand (`demandKnown`) and not draining. `WhyNoRoom` judges the share and the ceiling against the tier's own shape even where no host can place it or its hosts are full, because it used to return before judging them and their zero values read as room: a spent ceiling beside a full host published a shortage, and the pool would have ordered a host nothing could buy (Codex, round 3). A recovered session or an ended launch makes the count unknown while the refusal it kept survives, and the report is stamped fresh, so the shortage needs the count too. Not `Waiting`: a tier no host can place never waits in the admission queue, so its `Waiting` is zero for exactly the shortage a pool exists to fill (Codex found the pool unable to grow from an empty fleet that way). A missing, stale or failed report makes the reading `ErrDemandUnknown`: growth for demand waits and the floor is kept, because a report can be a previous controller's, written before this one's listeners polled. A placed host is on its way until a node joins from it (`node_name`, which the join writes), so until the join lands demand grows the pool by one host at most. A choice its source refused is passed over for `refusal_backoff`.

**An order records its source's scope and is read back only there; a resend the source refuses is uncertain, not refused.** `Source.Scope` is where the source orders (`aws:<account>:<region>:<subnet>:<zone>`, `phoenixnap:<client id>`), recorded on the order. The account is in it because a shared subnet admits several accounts, each blind to the others' instances, and it is asked at every `Scope`, never kept, because credentials can rotate into another account without a restart. A config or credentials changed since, or a source no longer configured, makes `resume` mark the order uncertain rather than read it back anywhere else, because a read there could miss the host it placed. A scope that cannot be read is could-not-tell: nothing is ordered, and nothing resolved, on it. A pool launch makes one HTTP attempt (`callOnce`), so a refusal is never the second attempt of a launch whose first may have landed, and its request has no `GetBody`, because Go's HTTP/2 client replays a rewindable body after some stream errors from the peer inside one `Do` (go1.26.0's `h2_bundle.go`, by its source, not probed against AWS). A first attempt's refusal, or a failure before it was sent (a token not minted, a boot not rendered), refuses the order. A resend's refusal does not: it says nothing about the first attempt, which may have placed a host, so the order is uncertain. The prelude is written through a quoted heredoc to a file removed by an EXIT trap and run by `bash -euo pipefail` of its own, so its failure stops the boot before the token is spent and its `set -x` or `exit` never reaches the join; a NUL in it or a join argument is refused, because bash drops it. The boot is rendered once at assembly with a token-length stand-in, so a prelude too long for EC2's user data stops the start rather than every order.

**A pool host joins on its source's word only when every check vouches for its key; a contradiction holds its order, and could-not-tell waits for a person (ADR-030).** A pool needs `server.bootstrap_listen`, and its hosts dial `server.PoolEnrollAddr()` (`pool.bootstrap_addr`, else the router's `enroll_addr`, else a `bootstrap_listen` that names neither a wildcard nor loopback, which a rented host would dial as itself; `join_server` and `bootstrap_addr` may be neither either), because the node wire wants a certificate an ordered host does not have and a TLS answer ends its join. Every send of an order mints a token bound to it (`NewPoolJoinToken`, `join_tokens.pool_order`, migration 76), because a resend under EC2's `ClientToken` returns the host that booted with the first send's, so any live token of the order admits it, and only under the order's name (`alloc.PoolNodeName`); a request naming anything else is refused and spends nothing, and an operator's token under a `pool-` name is refused too. The host writes `joinconsole.Line` (a leaf both the host and its source import, because `hostsource` may not import `nodeapi`) to `/dev/console` (opened `O_NOCTTY`) before every ask and sends its EC2 identity document, read over IMDSv2 until one is read (`billet join --pool-order`, `awscreds.InstanceIdentity`). The plane's enrollment handler asks the ledger before the source: the order must be placed and joined by no node (a key that joined while its request was on its way takes the ordinary path, which hands over its certificate), the token live or the one the request already recorded (a lapsed token of an open order holds the order there and then when nothing can join from it any more, `HoldLapsedPoolJoin`, and is recorded for a person, so it waits on no pool loop, which a config naming no pool any more does not run; otherwise it asks again, never refused; an uncertain order asks again too), and a held order is answered pending without asking anything. A request the per-order budget defers is `VerdictDeferred`, told to ask again, never could-not-tell, so nothing is recorded or spent on it; a hold applies only to the order as the plane read it (`HoldPoolJoin`'s `seen`). Then `pool.Joins` asks the order's source through `hostsource.Witness`, at most once per order every 15 s and one ask at a time whatever key a caller presents (`DefaultJudgeEvery`), each ask bounded to 5 s inside the listener's 10 s write timeout (`JudgeTimeout`). `awsmetal` vouches only when EC2 says the instance is running, the enrollment's peer is its private address (unchecked behind a router, where the document stands for it), the document verifies under AWS's certificate for the region (`internal/awsidentity`, RSA-SHA256 over `signature`, measured 2026-11-06) and names that instance, account, address and launch, and the console names only this key for the order; it contradicts only on a positive answer about the host itself, and a different address or launch time is could-not-tell, which a NAT or a proxy would explain. Only a whole console line is read (below). A reason never quotes an AWS answer. Vouched, the plane signs the request and `AdmitPoolEnrollment` records it approved, the certificate's serial, the link from order to node (key and serial, comparing the hold it read) and retires the order's other tokens in one transaction, handing the certificate over only after it commits; a retry with the same key gets the first certificate. Contradicted, the order is held (`join_hold`, a column, because migration 75's states are frozen, set only on an order a node may still join from) and nothing is spent; a conflict (another key holds the name) is held in the transaction that found it. A held order, a contradiction and a conflict are answered pending, so the host keeps asking while a person looks, and the answer quotes nothing the source said; a held order's request is recorded pending under its order without spending a token (`RecordHeldPoolRequest`), so a person has its key to approve even after every token lapsed, and a verdict is never reused across a move of the order (`judgedKey.moved`), so a release is not undone by a contradiction cached before it. A person approves a request already recorded (`billet nodes approve`, which links and clears the hold), releases the hold (`billet pool unhold`, `ReleasePoolJoin`), or releases the host. Could-not-tell (a failed read, a console not yet showing the line, two keys on it, a document billet cannot verify, which a rotated certificate makes) records the request pending under its order, so a person can approve it and the next ask is judged again. A source with no channel to its hosts (phoenixNAP) is always could-not-tell. Each step first holds every placed order nothing can join from any more (no live token, no request waiting), and a held order is no longer on its way, so it does not stop growth for demand.

**A pool host is released only on proof, sealed in the transaction that reads it, with its node's certificates revoked first (ADR-030).** `billet pool release` (`alloc.RequestPoolRelease`) takes a joined host out of placement at once (`MarkNodeDrainedForRelease`); `UpsertNodeRegistration` keeps `drained` while the order's release stands or it is sealed, released or gone, because a registration in flight when the seal commits would otherwise put back a host the source is about to take. The pool's step seals it (`SealPoolRelease`) only once the host holds no lease, quarantine or custody, and either its node never registered (never placeable) or was decommissioned on the compute barrier's proof (`decommission_proven`) with no inventory of its current epoch since reporting compute, and nothing its node said since contradicting the release: `pool_orders.release_contradicted`, set by an inventory reporting compute (`recordInventoryTx`, `ContradictPoolRelease`) and by the node arriving to register (`InvalidateBarrierRun`, ahead of every refusal, its read `ArrivalHasProof` covering an uncontradicted order as well as a barrier run, which `Decommission` deletes), and cleared only by a proved `Decommission` in its own transaction (`ClearPoolReleaseContradiction`); an inventory that contradicts a pool node also deletes its barrier run, so that decommission cannot be proved by a run older than the contradiction, and an order the release links (`LinkPoolOrderNode`) is contradicted at the link, its node's run deleted with it, because what its node said before was never recorded; migration 78 starts every linked placed or sealed order contradicted and deletes its node's run, for the same reason about the billet before it. It is the release's alone and never touches `decommission_proven`: clearing that brought a surrendered CodeBuild fleet claim back and turned a proof into an unproven exclusion the drain accepts (Codex, 2026-11-07). A node with no row held nothing whatever it said arriving. An inventory is never the proof: it is stamped when it arrives, a running launch is in none, and the barrier writes inventories out of order with the node's sweeps; a two-report design was tried and withdrawn in review (Codex, 2026-11-07). A host draining alone needs a per-node ask the node answers after its launches settle, fenced by epoch and dispatch generation, which is owed; until then a joined host is released after `billet drain --wait`, its node stopped (a decommission refuses a live node), a `billet nodes decommission` that says proved, and `billet resume`. `billet pool release <order>` with no reason, or a second one with a reason (`ErrPoolReleaseAsked`), runs `SealPoolRelease` itself, so a release finishes with no pool loop running. The seal revokes the node's certificates (`revokeNodeTx`, by serial and by cutoff) and moves the order to `sealed` in the same transaction; a host nothing joined from is sealed by the asking itself, on `CountPoolOrderAdmissions` being zero (an approved request under its order or name, or any certificate issued for the name), with its tokens retired; an unlinked order something was admitted for is linked to its derived name by the asking (`LinkPoolOrderNode`) and released as joined, so a certificate `billet ca issue` handed out before `pool-` was reserved is revoked at its seal. The proof is `internal/releaseproof`, a leaf, because `ledgerwriters` refuses `hostsource` to `alloc`; a sealed row stands for it after its transaction (`releaseproof.Sealed`), so a release asked again is the same release, and `PoolReleaseProof` reads a joined host's holdings again at every ask (`releaseHoldingsTx`), after the source's scope is read, never before (a scope is a round trip of its own): a contradiction after the seal answers `ErrPoolReleaseContradicted`, the source is not asked, and a person closes the order. The order is `released` when the source took it back, only where it was placed (its scope), and `gone` only on `Source.Gone`'s own terminal answer asked there, or a person's `billet pool close` of a sealed or released order, whose reason says so: phoenixNAP never answers gone. A draining order whose node can never prove itself again (dead, or its credential lost, which `ca issue` will not reissue for a `pool-` name) is closed by `billet pool close --force` (`ForceClosePoolOrder`): refused while anything holds the host, its node's certificates revoked, the node excluded from the fleet unproven (`DecommissionNode`, proven 0, as `nodes decommission --force` records it, so later drains do not wait on it) and its order gone in one transaction, the reason saying unproven. `billet ca issue` refuses a `pool-` name, and both registration `drained` CASEs fence a sealed order's derived name (`'pool-' || order_id`) too; `RegisterNode` refuses a node of a sealed, released or gone order in its own transaction (`PoolHostReleased`, `ErrPoolHostReleased`, mapped to `ErrRefused` in `nodeplane`), so a registration in flight at a seal or a forced close cannot clear the exclusion. A person's approval records its certificate inside the approval's transaction (`ApproveEnrollment`), so a refused approval leaves no certificate that would make an unjoined order read as joined. A sealed or released host counts against the maximum, and towards neither the floor nor demand. **Not built yet:** automatic shrink (it needs an idle measure, or a host ordered for demand is released the step after) and the pool's IAM (a pool host's `GetConsoleOutput` among it).

**Only a whole console line names a key, and nothing a pool host's join prints can be one.** A line is read from a newline to a newline (`SHA256:` and 43 characters, then the line's end, a carriage return before it allowed), never from the edge of what was read, which can begin part way through a line or end before its newline, because the console's newest 64 KiB can end inside one, and because boot output reaches the same console: text a network answer wrote, quoted inside another line or after a carriage return, would otherwise name a key the host never wrote, and before round 9 of the join's review a status reason from the unverified authority fetch could do exactly that (Codex, 2026-11-06). So the host writes its line after a newline, a pool host's join prints through `joinconsole.Guard` and returns `joinconsole.GuardError` (the line's start without its hyphens, a carriage return as `\r`, a line past 64 KiB cut and guarded in parts), and nothing the authority's unverified answer wrote is quoted (`FetchCA` names the status code only, and `EnrollNode` prints the deployment only once it is a deployment's id). `FetchCA` returns only the certificate the fingerprint names, never the bundle it came in, because enrollment trusts what it returns and a root appended on the unverified connection would see the token, the request and a pool host's signed identity (Codex, 2026-11-06).
