# Buying capacity: advertisement, purchase and the admission order

Part of the `billet-capacity` skill. Each rule is stated in full, with the measurement or incident behind it.

**Capacity is bought when a runner starts, and it is a vector.** Each tier is its own scale set with its own `maxCapacity`, and every tier advertises at once (`steadyAdvertisement`: committed work raised to `Allocator.AdvertisedCeiling`, which reads configuration only, so the number does not flicker with live headroom). GitHub.com assigns jobs directly (`JobAssigned`, request id 0, no offer, no `AcquireJobs`) and only to a scale set advertising capacity, and there is no way to decline an assignment; so the advertisement is permission to be assigned, not a promise of a machine. The advertisements together exceed the fleet by design, and an assignment that finds no room waits at GitHub. `Allocator.Escrow` reserves against the global ledger first (vCPU, memory, per-tier concurrency, macOS licence slots), and the headroom check and the insert are one transaction: measured, moving the check outside produced 28 grants against a ceiling of 4. `TestConcurrentReservationsNeverOvercommit` is the guard. Every reservation names a machine (`target_node` at escrow, `node` at bind) and capacity is charged on whichever is set, or a tier could escrow against the same host repeatedly before its first launch. Nothing runs without a lease: the invariant is enforced at the purchase, never at the advertisement.

**Nothing is reserved for an idle tier, and there is no rotation (#140).** v0.10.0 escrowed one slot per tier to advertise and wasted the catalogue's capacity (#116); v0.11.0 rotated one shared discovery turn across tiers, which on GitHub.com left each idle tier assignable for about one poll in eighteen minutes, and a job queued against an idle tier went unassigned for hours. Both are gone. Capacity is bought at three points and nowhere else: per offer in `handle` (`refillEscrowTo(targetCapacityFor(len(Available)))`, the classic `JobAvailable` path), per pool launch in `reconcilePool` (`backPoolSlot`, one lease at a time, launched before the next is bought), and per unpromised request-id assignment (`backAssignment`). `reconcilePool` sizes the pool to `TotalAssignedJobs`. Escrow bought and not used is released after the message against `targetCapacity`/`messageCapacityTarget`, never beneath the advertisement, because the advertisement is no longer backed. A seal or a drain buys nothing: `refuseIfSealed` fails closed on an unreadable admission read, and `refillEscrowUngated` treats it as "buy nothing", so an assignment in flight when a seal lands waits until it lifts (the host-upgrade fence relies on the seal being absolute). A more frequent `Escrow` error still stops the listener, as it always did. Ordering between tiers waiting on the same returning room is `admissionQueue` (`internal/server/admissionorder.go`), one per control plane, shared by every listener through `listenerOpts` and set from `server.admission_order` (`config.AdmissionOrder`, `fair` by default). IT GATES PURCHASES AND NEVER ADVERTISEMENTS, which is the whole lesson of #140: v0.11.0 rotated which tier could advertise, and a tier that is not advertising is never assigned the work the scheduler would have scheduled. Under `fair` the longest-waiting tier holds freed room until its shape fits (head-of-line blocking on purpose, and deadlock-free because there is one winner chosen by a wait it cannot extend); it is bounded by the longest running job ONLY WHILE THE WAITER'S LISTENER IS THERE TO BUY, which on 2026-09-23 it was not: the longest waiter's listener sat on a dead broker connection for 18 minutes, could neither buy nor clear its wait, and every tier sharing its host declined every assignment with 78 of 136 vCPU free. So a waiter is dated by its last admission progress (`waits` at every refused reconciliation, `launchBegins` and `launchEnds` at each end of every launch, never a mere successful exchange, because a held message is redelivered every poll while reconciliation is skipped). A launch still in flight is NOT progress. Until 2026-09-25 it was, and a waiter launching eight slots one at a time into a node whose command queue took four to five minutes a launch held every tier for twenty minutes. The two marks sit inside `Listener.launch`, so the pool and direct-assignment paths both carry them. Then `mayBuy` lets another tier past a waiter with no progress for `WaiterAllowance` (three minutes, two of the longest measured long polls, a policy choice) while the waiter keeps its `since` and takes the line back the moment it progresses; the transitions are logged once each and only when a buyer really got ahead (`letPast`), and `billet status` prints NO ADMISSION PROGRESS PUBLISHED from the published `waiting_progress`: an observation rather than the queue's decision, because a stalled listener cannot publish its own stall and the queue can see a launch mark before the next publication. This weakens fairness, never capacity: the queue releases, destroys and promises nothing (`admissionliveness_test.go`); under `fill` anything that fits buys. A tier is recorded as waiting by `reconcilePool` when it could not buy for demand it has, and released when its demand is met OR when GitHub's count says the work is gone — a record that outlived its demand would hold the fleet behind nothing, which is worse than the starvation it prevents. The first refusal dates the wait, ties break by label, and a nil queue (a standalone listener) admits everything. A PLACE IS WON FOR ONE PURCHASE, NOT FOR A BACKLOG (#248): a successful escrow re-dates a waiting buyer to now (`admissionQueue.bought`, called from `refillEscrowUngated`), so waiting tiers take turns one purchase each and a large shape at the head still holds freed room until it fits. Before that, a tier whose demand kept arriving was never `served`, and its launches counted as progress, so it was never stalled either: on 2026-09-25 a repository's CI backlog held the line for thirty minutes while an organization's tier of the same shape on the same host started nothing, and no bypass warning was logged. `refillEscrow` has no production caller and stages escrow in tests. EVERY PURCHASE OF A LEASE ASKS IT, not only the pool path: `backAssignment` and the offer path gate on `mayBuy` too, because on GitHub.com the work arrives as direct assignments and a stream of small ones took every fragment of room a large tier was accumulating (#157). What it does not gate is `alloc.Resize`, the remote fallback growing an EXISTING lease to the shape the cloud sold: that is re-authorised against the ceiling and every floor, the order admitted the lease already, and the resize is asked for by the node (the plane's resize route, or the in-process runtime) and the queue is handed only to listeners, so nothing on that path holds it (a wiring fact, not a layering one: `nodeplane` imports `server`) — so a fallback to a larger shape can take pot a waiter was accumulating. A TIER HOLDS THE LINE ONLY WHERE ROOM COULD REACH IT: `waits` is recorded only when `alloc.AdmissionView` says the tier could grow once current work ends, so a tier at its own cap, pinned to a host that is gone, or with a shape no live host fits waits without freezing the fleet. `CanGrow` errs towards true where the model is uncertain, because a tier wrongly excluded is starved while one wrongly included only waits its turn, and it is three questions in order. The modelled total is compared with what the tier holds ON THE MODELLED FLEET (`countOpenPerTier`, where a lease stranded on a departed host counts for nothing, as it does for a floor). Then its own `max_concurrent` is compared with EVERY open lease (`countOpenByTier`), live host or not, because that is how the cap is enforced: counted on the live fleet alone, a tier whose whole cap sits on a departed host is told it can grow and holds the order behind a purchase the allocator refuses. Anything the model refuses is re-asked as `headroom`, the room the allocator would grant this instant. The model charges floors through `reserveFloors`, the same function the allocator charges them with, so only what is OUTSTANDING is held; holding every configured floor in full re-placed one already backed elsewhere and excluded the tier whose only host the model then spent. `Nodes` are the hosts an empty fleet could place the tier's SHAPE on, not every host the policy would consider, or a waiter would block tiers a host it cannot use can really serve. A waiter blocks a tier when they share such a host OR when `CeilingShared` holds for both: that is a fact about the DEPLOYMENT, the ceiling being smaller than what the live hosts could hold ONCE WHAT IS CHARGED OFF THE FLEET IS PAID (`ceilingSharedOver`, over `usage` minus `usageByNode` on the live hosts, because a lease stranded on a departed host holds the ceiling where no live host can use it), and not about a tier — asking instead whether the ceiling cut one tier's own total said no for an 8 vCPU tier on one host and a 4 vCPU tier on another under an 8 vCPU ceiling, which fit under it separately and not together, and the small one starved the large one on a host it never touched. A waiter's hosts are refreshed at every refusal while its PLACE is dated from the first, and an unknown host set competes with everyone. The view is read AFTER the purchases when the record is written, because a tier that reached its cap inside the loop could still grow when the loop began; a read that fails keeps the tier eligible with an unknown host set, which is not a way past the order but competes with every waiter.

**A target's share is a narrower deployment ceiling (#192).** `Limits.Shares` (from `config.Config.TargetShares`, passed at every `alloc.Limits` the CLI builds) caps what one target's tiers hold together. `readShareUsage` sums `UsageByTier` over the tiers the catalogue gives each target; a lease whose tier left the catalogue is charged against EVERY share (its target cannot be told, and forgetting it sells its room twice). `reserveFloors` holds each target's outstanding floors only up to that target's remaining share, at the charged shape (the placer's deployment room is set to the share budget), and returns what it held per target, so `headroomWithPlacer` and `Resize` subtract a sibling's floor from the share and an impossible remote floor cannot take the deployment from other targets. `headroomWithPlacer` narrows the placer's deployment room to the share; `Resize` authorises as if the lease's current shape had been returned; the admission model bounds a tier by the whole share less its siblings' floors. `TierAdmission.TargetShared` makes one target's share a pot like `CeilingShared` (siblings pinned to different hosts compete), and `ShareBound` says the share, measured at the cheapest charged shape rather than the request, is what stops the tier now. `competes(buyer, waiter)` is directional: only a share-bound WAITER stops holding another target's buyers, never a buyer's own full share, and only when both targets are known. The flag is the waiter's last view, so it can be one poll stale in the direction that favours the other target.

**Status separates ownership from phase.** Migration 50 carries dated listener observations with exact discovery and pending lease IDs, the last sent advertisement and the last completed exchange. `CapacityReport` joins that observation to still-open ledger rows, reports unclassified capacity as unknown, and separates pending, launching, idle, running, cleanup, configured floors and additional headroom. A pooled runner's lease stays `launching` from its launch to its teardown (nothing in production advances a lease to `online` or `busy`), so idle and running are read from each launched lease's `pool_runners` row in the same snapshot: before that, a busy fleet read as every lease launching and running 0 (#291). A launched lease with no row is still launching; a row naming another tier, or a status the report does not know, is unknown. A failed exchange is ambiguous; neither headroom nor a missing report means zero advertised capacity. These records decide no scheduling or release.

**A commitment made to a remote service cannot be revoked by a local timer.** `AcquireJobs` is one-way; there is no decline. Ageing out a stale `acquiring` promise was written, reviewed and reverted: it hands nothing back to GitHub, it only makes billet forget it owes a runner, and the assignment arrives with nothing behind it. A second attempt released on GitHub's own statistics and was the same bug, because a freshness check on your own record is not a causal fence on somebody else's snapshot. A stale promise is reported and kept; invalidating the session is what makes GitHub redeliver.

**A pool member GitHub cannot route work to is retired on GitHub's per-registration word, never on the aggregate.** `reconcilePool`'s surplus is judged against `TotalAssignedJobs`, which only a message carrying statistics refreshes, so a quiet tier freezes it and a member whose runner never takes a job is never surplus: on 2026-09-30 one held its lease for ten hours, and a draining node's restart for two of them, because the drain waits for everything the node holds (#287, #288). `retireOfflineMembers` (`internal/server/offline_member.go`) asks GitHub's REST runner record through the registry's `InspectRunner` (the scale-set client's, built on `InspectScaleSetRunner`) about one member idle past `offlineIdleAfter` per `offlineInspectEvery`, and treats two consecutive answers of present, offline and not busy spanning `offlineGrace` (dated when each answer arrived) as naming a candidate, never as permission: no number of REST reads stops GitHub delivering a job the instant after one. The permission is GitHub acknowledging a DELETE of the exact inspected runner id (`WithdrawRunner`, never `RemoveRunner`, whose name lookup answering "absent" returns success without sending a DELETE), which the Actions service refuses with `JobStillRunningException` while a job runs (the refusal ARC's runner controller relies on; billet has not measured it itself). It is asked BEFORE the member is journaled retiring, so a refusal, an absent runner or any error leaves it idle and a late JobStarted still binds; after an acknowledged DELETE a failed ledger claim is retried on later reconciles without inspecting again, and only a controller restart inside that window leaves the member idle with no registration. Online-and-idle, busy, absent and could-not-tell all keep the member and reset the run, and the watch lives in memory so a restart only delays a retirement. THE ID IS GITHUB'S, READ BY THE EXACT NAME: a remote node's JIT mint journals the registration's id, but the listener's own launch path journals a member with a name and no id, which the first version skipped. Each offline answer carries the id GitHub holds for `billet-<lease id>` (`RunnerState.ID`); both must name the same id, an answer naming none (or another than an id the pool did journal) is no evidence, that id is the one withdrawn, and the cleanup's `RemoveRunner` is handed it (the cached member on a retried claim, `destroyCompleted` keeping a job's id for the same name) so a registration that took the name since is refused rather than deleted by name. AND IT HAD NEVER RUN AT ALL, which is what held a node's drain for nine hours on 2026-10-02 (#317): the listener finds the inspector by asserting its registry, which is `app.Provisioner`, not the scale-set client, and the adapter forwarded only `RemoveRunner`, so the assertion failed in every deployment while the unit tests handed the listener a fake that implemented both. The same gap hides `server.RunEvidence` from `runTier` (asserting the provisioner) and the node plane (asserting `NodeJIT`), so no `publish: default-branch` cache has ever been proved in a deployment; it is left unforwarded on purpose until the proof refuses a tag named like the default branch whose reusable workflow resolves to the same commit (#318), because forwarding it is what would make that reachable. A capability found by type assertion is proved on the value the assembly builds (`TestTheAssembledProvisionerOffersTheOfflineMemberRetirement` and the `var _` assertion in `internal/app`), never on a fake.
