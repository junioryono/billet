# Custody, quarantine, drains and sessions

Part of the `billet-capacity` skill. Each rule is stated in full, with the measurement or incident behind it.

**Compute billet cannot account for is a named state, never resold.** `internal/node/custody.go` holds adopted compute (survived a restart; the runner may finish the job) and discarded compute (an ambiguous launch whose cleanup was not confirmed). Both renew the lease; both release only when the compute is proved gone. A negative observation is not automatically causal: a `docker ps` right after a lost `docker run` can overtake the daemon, so an uncausal absence waits through `strayGrace`; a remote backend waits the full grace every time. "Could not verify" is not "safe to destroy"; only `ErrLeaseNotFound` proves a lease gone. A cleanup obligation is owed to the compute, not the lease: losing the lease changes who owns the capacity, not whether the container runs.

**`Recover` runs at every registration, not only at start, so what it finds includes this process's own jobs (#227).** `Holding()` counts `running` as well as custody and `launching`, and a drain ends only when all three are empty. So an instance is in `running` or in custody, never both: every custody installer drops the matching `running` entry (`forgetRunningLocked`), because custody's `finish` removes only its own entry. When recovery or the sweep proves an orphan destroyed, `forgetRunning` drops it too. An unconfirmed teardown keeps its entry, because the compute may still be there. Measured 2026-09-25: a node the control plane had forgotten re-registered, destroyed eleven finished jobs' VMs as orphans, kept all eleven in `running`, and its drain ninety minutes later waited six and a half hours on compute that was gone. A goroutine dump showed nothing in flight: `waitForHolding` was ticking `Tend` over an empty custody map, and the hour-old custody warning never fired. `waitForHolding` asks `Holding()` every `holdingCheckEvery` (2 s, or the sweep interval if that is shorter) and runs `Tend` only on the sweep cadence (#240): asked once per five-minute sweep, a drained host stayed out of service for up to five minutes after its last VM was destroyed, measured in the v0.12.11 rollout, and a rollout paid that per host.

**A drain waits for compute, not for entries.** `Runner.Holding` counts custody, launches and running entries, and a running entry is removed only by a Destroy the plane sends after GitHub reports the job over; a guest whose VMM ended with no such report (a crash, an operator's kill, a runner that never took a job) kept a draining node out of service on 2026-09-30 (#287). `noteStopped` (`internal/node/stopped.go`), run by every Sweep, dates a running entry whose instance the provider lists as `Ended` (execution observed finished: firecracker's VMM proved gone, docker's `exited` or `dead`; never merely `!Running`, which a paused guest mid-job also is), and a later sweep that still sees it stopped `strayGrace` on marks it proved; `Holding` then stops counting it. Nothing is released or destroyed on that proof, because a stopped guest is also what a job that finished normally looks like while its Destroy is on the way: the entry stays for that Destroy, and what a drained process leaves behind is the next process's Recover to destroy.

**Quarantine holds capacity for compute nobody has accounted for.** A lease that had compute and stopped heartbeating is quarantined, still charged to its host, and leaves only on proof: the node's destroy report, an inventory that omits it after the grace, or an operator's `leases release --force`. `ResolveQuarantineFor` settles from a fresh observation; a first version settled a completion from the plane's cached inventory snapshot, which has no ordering against the quarantine and would free capacity under a running build. Every completion path that cannot reach its holder corrects a verdict something else recorded (`SettleCompletionOnTerminalLease`) and never settles one. A lease whose completion GitHub already delivered settles as `done`, not as a provisional failure.

**Time warns; it does not authorise a teardown.** Held compute has no bound by default (`DefaultMaxCustody = 0`) and warns hourly; billet imposes no job limit and GitHub does not requeue a job whose runner vanished after starting (checked against the vendored client's README: reassignment covers a job "not acquired by a runner in time" and nothing more). `server.drain_timeout` used to bound the shutdown wait and then destroy what was left; it is now the point where `warnDrainOverrun` starts repeating every fifteen minutes. `destroyAll` takes `includeRunning`; a shutdown passes false, and `billet force-destroy` is the only caller of true, asserted structurally by `TestOnlyTheForceOperationDestroysRunningWork` because nothing in the type system separates the two booleans. Force refuses unless an operator sealed admission, fixes its target set when the request is taken (a standing flag would be a timer wearing different clothes), and archives forced leases as `failed`.

**A listener's drain does not wait for an anonymous pool slot that never started a job (#220).** GitHub hands such a slot no job while its tier drains. Measured 2026-09-25: slots launched a minute before a host upgrade's drain sat idle for sixteen minutes with jobs queued for their tier. The drain waited on them until a second signal ended it, because the drain-time reconcile retires only surplus beyond `TotalAssignedJobs`, and the declined assignments kept that count above them. `idleMembersOnly` ends the drain when every entry left in `running` has no `runningJobs` identity (a runner launched for an assigned job is still waited for) and the ledger records it `PoolRunnerIdle` with no actual request. That must still hold after a further completed poll, because a Started for the slot can be in the next message. The slots are left registered and charged, exactly as the second signal leaves them, and the successor adopts them. A pool read that fails keeps the drain waiting.

**A drain is two barriers, and the second asks the machines.** `alloc.Quiescence` answers from the ledger and cannot see compute whose lease has already gone (an in-memory destroy obligation, a launch whose lease was reclaimed); both leave an instance carrying billet's name on the host's provider. So `billet drain --wait` writes a durable barrier request the control plane observes, and the plane queues `CommandInventory` behind each host's serial queue. What makes an answer evidence is the fence: `nodes.dispatch_generation` is bumped durably before a launch enters the queue, under the same hold of `Plane.mu` (`BumpDispatch`), and an observation is recorded only while that number and the epoch are unchanged. A proof is two observations spanning `computeAbsenceGrace` (`observed_at − empty_since`), never one observation and a clock: the first version compared `now` against `empty_since + grace` and a host that answered empty once and disconnected aged into proof. A host saying it holds compute beats a completed run and may block but never clear (`provenBy` is the single definition the report and the decommission read). `Plane.ArrivingForRegistration` discards the host's stored run before a registration is judged, on both wiring paths, before the body is decoded and before revocation is checked, because a permanently refused registration is still an authenticated host reporting live compute. A host below `VersionComputeBarrier` is reported as unprovable; `billet nodes decommission` bounds the expected set and its `--force` records the exclusion as durably unproven.

**An unsealed server stop is a handoff, not a drain (#365, #368).** `cmd/billet` sets `server.WithStopHandoff`, so a listener cancelled while `state.AdmissionOpen` (`Listener.handsOff`, one bounded ledger read; a failed read, a sealed deployment or a listener without the option drains as before, and a fenced controller still takes `abandon`) returns from its loop at once. Its teardown joins the cleanup loop and runs `destroyAll(…, false, …)` for the destroys it already owes, then stops: it starts no `Session.Close` (one a session recovery already started is not undone) and calls no `releaseAll`. Stopping a deployment for good is sealing it first; a package removal stops the services without sealing, because sealing from a package hook would seal a deployment other controllers may serve, and a marker file the hook writes for the server was tried and dropped (a root hook writing into the service account's directory follows a planted symlink, and the directory is not fixed by the config). A cancellation that ends `Run` before its loop is decided the same way (`noteStop`). It is the fenced controller's `abandon` made deliberate, and it rests on the same recovery: running jobs are re-adopted, held escrow is reaped once its renewal stops, and the successor waits out GitHub's hold on the open session (60 to 92 s measured) while GitHub, still seeing the last advertisement, keeps assigning into it and redelivers those messages to the new session. Measured 2026-10-04 on the reference deployment: a consumer converge's SIGTERM drained the controller from 02:39 to 04:12 behind one long job, its 90-minute job limit cancelled it, and nothing launched. Worse, GitHub cancels a declined request after exactly five minutes and re-offers the job only to a scale set with room; the drain had lowered the advertisement, so the 28 requests declined in the three minutes before it began came back to the next session as `canceled` with no runner and their jobs stayed queued until they were re-run. A sealed drain still lowers the advertisement and can still strand a job declined just before the seal, which is the deployment leaving on purpose.

**A node hands over on a stop only when its config says so (#374).** `node.stop: handoff` (`NodeConfig.HandsOverOnStop`, read into `LoopOptions.HandOverOnStop`) makes `stopGracefully` take the second signal's ending at once while compute is held: withdraw and return, nothing destroyed and nothing moved into custody, because nobody supersedes this node and its next process adopts what it finds when it registers. Absent or `drain` keeps the drain, and that default is deliberate: until 2026-10-04 every adoption on the reference deployment's Linux node was the same process re-registering, never a new process, let alone a new version, adopting guests another one launched. What makes it possible is measured: the jailer puts each VMM in a cgroup of its own (`/firecracker-v1.16.1/<id>`), outside `billet-node.service`, so `KillMode=mixed` on the unit's stop does not reach the guests. That host's Linux node was otherwise drained 20 to 35 minutes on each of eight restarts in a day, most of them a consumer's converge, launching nothing for any tier meanwhile. The guest cache is part of it. The unit's mount namespace dies with the process, so `CacheService.RestoreMounts` mounts a recovered session's recorded volumes again before anything serves; a volume it cannot mount is marked `lost` for that process and refused, never served from the directory beneath it. The cache listener is bound at startup but served only from `LoopOptions.Ready` (after the first registration whose recovery succeeded, or at the start of a drain that never saw one), its mounts restored first in that same goroutine with each bounded by `restoreMountLimit`, so stalled storage delays only the cache, because before then the kill switch answers could-not-tell, which it reads as disabled. On a handover the listener's `Shutdown` waits `nodeCacheStopGrace` (a sixth of the lease TTL, since nothing renews the handed-over leases until the next process registers); hijacked Actions tunnels are not waited for and fail open. An operation that must not leave guests behind holds a drain request for its whole length: while `/var/run/billet-node-drain` (`nodeDrainRequestPath`) exists, every node process that stops drains (`LoopOptions.DrainRequested`, `nodeDrainRequested`), and so does one that cannot tell. Three earlier shapes were wrong: a signal raced the SIGTERM after it, a config check read the policy being installed rather than the one running, and a pid binding let a replacement systemd started mid-operation hand over. A handoff returns only when `withdraw` reports that the withdrawal landed, since the plane transfers ownership only from a recorded withdrawal; otherwise it drains. A process stopped before its first successful recovery does not believe an empty `Holding()`, because it cannot yet see the guests a previous process left and, once registered, may already own them: it recovers first (`recoverBeforeDrain`, which registers if it never did and starts the janitor before recovering), for as long as it takes when a drain was requested and `unrecoveredStopAttempts` times otherwise, so a node whose provider is broken can still be stopped to be mended. A process that never registered was given nothing and stops at once; one whose registration the plane forgot was given something, so the test is `Client.EverRegistered`, not the wire version a forgotten registration clears. Handoff is refused at load for anything but `node.provider: firecracker`. The role's `request-node-drain.yml` writes it, whatever the config says, before a networking change, the next stop after a config change (the ordinary restart and the endpoint migration on `billet_config_install.changed`, and the transaction when `cmp` finds its candidate config differs or cannot tell), the transaction's and the ordinary stop of a node that will not run here again, and a ledger rollback; `release-node-drain.yml` removes it at the end of network.yml and of the rollback, and unconditionally once services.yml has left the node where the converge wants it, so a failed or resumed converge's request does not outlive the next one; `cmd/billet/nodedrainrole_test.go` holds request, stop and release in order at every site. `local down` writes it before stopping any Linux node, whatever the config on disk says, because the running process may have loaded another policy, and `local up` removes it; `preremove.sh` writes it, leaves it, and refuses the removal when it cannot. A request left by a failed operation only makes later stops drain.

**A clean exit withdraws; silence still means nothing.** `stopGracefully` sends `POST /v1/nodes/{node}/withdraw` after its wait on every exit and never from a superseded process. `alloc.NodeWithdrawn` writes `live = 0` fenced on epoch and incarnation, releases nothing, marks no disruption and discards no barrier run; the plane writes the ledger first and drops the node from memory second. Before it existed a stopped host kept receiving placements for one `staleAfter` window, about four and a half minutes measured. The window cannot be shortened, because a crash and a partition are one observation.

**A restart waits for its own message session, and so does a failover.** GitHub answers a second session for a scale set whose first was abandoned with `409 Conflict` (`ErrSessionHeld`), measured against a real organization under the old holder's name and under another host's; `openSession` waits it out, because that is the one refusal that resolves by itself. The bracket below is the ORIGINAL owner's wait; a differently named successor was measured only as far as the refusal. Measured 2026-09-04 on eight runs: the abandoned session was still refused at 60 seconds every time and open at 91 on three of them and 92 on the other five (a bracket, not an expiry), and the successor was then handed the id the abandoned session had been holding, carrying the same one assigned job (the run that compared identities rather than counts found the same run id and the same stable workflow-job id). Nothing is lost in the window: GitHub queues a job for 24 hours.

**A tier whose session fails keeps everything it holds while it reopens (#207).** A poll that fails past the client's retries no longer returns from `Listener.Run` (which cancels every listener, and every teardown); `recoverSession` replaces the session in place. Running leases keep their heartbeat and their compute, promises stay owed, and the cleanup loop keeps retrying, because a broker outage is not evidence about any machine. Only idle `held` escrow goes back, and only after the old session closed, since until then GitHub can assign against the advertisement it carries; when the close fails or outlives its grace it is kept until a poll lands, and the teardown neither closes a session the recovery already closed nor starts a second close beside one still in flight, and while a recovery is under way its own close runs aside too, so an open stuck on the client's per-target mutex cannot hold a stopping listener. It runs during a drain too, on the drain's context, because a drain ends on completions and only a session delivers them. A fenced listener never enters it, and one fenced while it waits stops at the next attempt.
