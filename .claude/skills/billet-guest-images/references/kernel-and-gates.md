# The kernel and the gates before publication

Part of the `billet-guest-images` skill. Each rule is stated in full, with the measurement or incident behind it.

**The kernel and the filesystem are a matched pair.** A guest booted with a different kernel fails mid-job, so they are published together and the generation records which kernel proved it (`SetKernel`, `KernelFor`), under the same cluster lock reaping takes. A pull keeps the kernel in `/var/lib/billet/kernels` named by version and digest, installed durably before the remote half exists (`billet-backup-restore` for the ordering and the kernel lock). `images reap` refuses while any generation's kernel is unknown, because such a generation boots something on disk indistinguishable from an orphan.

**One machine's guest is chosen in one table, in the build and again in the gate that holds it (ADR-022).** The build and the gate each read `uname -m` once, because the build runs GitHub's scripts on the image and the gate executes the image's binaries in a chroot, so neither can work on another machine's image. `build-guest-image.sh`'s table names the plan, toolset, base, runner tarball, Go architecture, toolcache directory, apt source and image name; `check-guest-image.sh`'s names what the image is held to, and `TestTheBuildAndTheGateChooseTheSameGuestForEachMachine` holds the two to each other by running both tables as each machine. A machine neither knows is left empty and refused. GitHub's arm64 scripts are not uniform about the machine's name, and the gate follows what they write rather than a rule: the toolcache directory of node, go, Python and Ruby is `arm64` and the JDK's `temurin-<v>-jdk-arm64`, the variable is `GOROOT_<major>_<minor>_AARCH64`, but `JAVA_HOME_<v>_X64`, the Java toolcache's `x64` link and marker, and the firewall bundle's `x64` directory are the same on every machine, because `install-java-tools.sh` and `install-awf.sh` hard-code them. `check_image_machine` reads `e_machine` from a binary out of each place the build gets one (`ELF_BINARIES`: Ubuntu's base, billet's build, the runner's tarball), after the header says it is a 64-bit little-endian ELF, and refuses a manifest naming another machine, since a mismatch boots and then fails when the agent execs the runner.

**A kernel is its machine's file, chosen from its own config (ADR-022).** Firecracker loads an ELF `vmlinux` on x86_64 and a PE `Image` on aarch64, so `build-guest-kernel.sh` builds the machine's target from the machine's base config and installs either as `vmlinux-billet`, and `write-image-manifest.sh` refuses to describe a kernel its `ARCH`'s VMM cannot load (an x86-64 ELF, or arm64's magic at offset 56), because nothing else looks at that file before a boot. The aarch64 config starts from Firecracker's `microvm-kernel-ci-aarch64-6.1.config` at v1.16.1 and `scripts/guest-kernel-aarch64.config` is the result of building it, as `guest-kernel.config` is for x86. `required-builtins-aarch64.txt` adds what Firecracker's aarch64 machine is made of (device tree, GICv3, the architected timer, PSCI, the serial port through the device tree, the PL031 clock); the gate chooses it from the config's `CONFIG_ARM64`, never from the host, because the gate also runs on a cached kernel, refuses a config naming neither machine, and requires at least one option of each list it reads, so one list cannot answer for another.

**The kernel gate's verdict is its exit status, and billet's own rule is the artifact-level claim.** moby's `check-config.sh` is vendored at `scripts/kernel/check-config.sh` with commit and sha256 in `check-config.pin`, verified and copied into a private directory before it runs; its status is captured before anything filters the output. That status is also about the build host (cgroup v1, `apparmor_parser`, `root_maxkeys`, a missing `sysctl`), so the gate names those lines when it fails. Every option in `scripts/kernel/required-builtins.txt` must be `=y` and the config may contain no `=m` line, because a microVM has no initramfs; that file is also what the build enables, so the set list and the check list cannot diverge. The workflow runs the gate itself, not only through the build script, because the kernel is cached on its inputs and `actions/cache` saves in its post step even when a later step failed.

**The gate refuses an image that carries any of the five, and one without its completer or a manifest that declares what its template offers (#584).** `check-guest-component.sh` holds the one list of what each component leaves in an image (its paths and its job-environment variables) and the components' names, which the build, the gate and a test against `config.ImageComponents` all read. `check_components_left_out` asks it `absent` of every name (a dangling link counts, and an unreadable job environment is could-not-tell), `check_completer` requires every completer file, executable only what is executed (`COMPLETER_EXECUTED`; GitHub's sourced helpers are ordinary files in the template), and `Helpers.psm1` reading its own tests, and a test runs the build's `install_completer` and then the gate so the two cannot disagree, and `check_manifest_components` requires schema 3 under completion contract 1 declaring exactly what the machine's template offers, each with a positive whole space. What a template offers is `check-guest-component.sh offered PLAN`, which parses the plan and answers 2 for one it cannot read: the five on x64, Firefox alone on arm64, because GitHub's arm64 template has no step for the other four. The Android SDK checks and CodeQL's toolcache, executable and `pinned-version` checks moved to `check-guest-component.sh present`, which the trial runs against a completed copy; `TOOLCACHE_TOOLS` no longer names CodeQL, and the coverage test adds it back only as the vehicle for a declared `*`.

**The gate refuses an image that ships a tool without the license text the tool's license asks for (#584).** The image redistributes what GitHub's template installs, and four tools installed outside apt ask for their license with every copy: the GitHub Copilot CLI, whose release tarball holds only the binary; the agentic workflow firewall bundle, a bare `awf-bundle.js`; Miniconda, whose installer places `LICENSE.txt` in its prefix; and Packer, whose zip places `LICENSE.txt` beside the binary in `/usr/local/bin` (both read from the vendors' downloads on 2026-10-21). `install_image_notices` fetches the two GitHub licenses from the tag of the version the toolcache directory names, refusing a version that is not a plain semver before it builds a URL from it, and writes `/opt/billet/IMAGE_NOTICES` naming each tool and where its license is; a missing license fails the build. `check_image_notices` derives what it requires from what the image carries (every `copilot-cli/*/*/bin/copilot`, every `awf-bundle.js`, Miniconda's prefix, Packer's binary), so a tool the template stops installing asks for nothing and a fourth firewall version asks for its own license. Every path the gate reads is resolved inside the image (`image_resolve`, `image_entries`, `image_present`), the version and architecture directories included, and the notices it searches are the file it validated. A test against the builder's own root follows an image's absolute link onto the builder: an image-only link, at the tool or at a directory above it, hid a tool, and a directory or a link to a builder file passed `-s` as a license (Codex, 2026-10-21). A tool ships if anything is at its path, a link included, and a license counts only as a non-empty regular file. `image_resolve` refuses a link it cannot read rather than dropping the component. The build itself trusts the root it built, as every host-side step after the template does, so the gate, not the build, is what finds a tool behind a linked directory. Packages installed with apt carry theirs in `/usr/share/doc/<package>/copyright` and are not listed. `scripts/guest_image_notices_test.go` runs both halves against fixtures.

**The source manifest is written while apt still has its lists, and the gate holds it to exactly what dpkg installed (#584).** `scripts/runner-images/source-manifest.py` runs in the booted build machine after the last `apt-get install` and before the lists are removed, the one point where python3-apt can say which sites carry each installed version, and writes `/opt/billet/IMAGE_SOURCES.tsv`: package, architecture, version, source, source version, origin and license. An origin of `none` means only dpkg's own record has the version, as for git from the PPA GitHub's template removes after installing it. The license column is `gnu`, `other` or `unclassified` (no readable copyright file), never a guess that a package is not under a GNU license. `check_image_sources` reads the image's own `/var/lib/dpkg/status` with awk the way dpkg's parser does (a field name in any case, the value trimmed, continuation lines skipped, the source from `Source: name (version)` defaulting to the package and its version), so it needs no dpkg on the machine running it. It refuses a package dpkg did not finish installing or removing whatever the manifest says, a manifest that misses an installed package, names one only configuration is left of, or gives another version, architecture or source, and a row with an empty cell; with `SOURCES_EXPORT` set (the workflow sets it to the copy in `out/`), it refuses an exported copy that is not the image's byte for byte, and the publisher refuses one without its header or with no row; its pass line counts the GNU-licensed packages and how many of those come from no source apt still names. The release carries the same file as `image-sources.tsv`. Measured 2026-10-21 through Launchpad's API: a superseded version in Ubuntu's primary archive stays downloadable from `launchpad.net/ubuntu/+archive/primary/+sourcefiles/` after the archive removes it from its pool, and a superseded version in the git-core PPA does not (404 for 2.54.0, superseded 2026-08-11; 200 for the published 2.55.0 under its epoch, `1:2.55.0-0ppa1~ubuntu24.04.2`). So a PPA package's source can only be taken while the build runs.

**Every guest release carries the corresponding source of what it redistributes under a GNU license, fetched at each exact version from where that version is kept (ADR-019).** GPLv2 counts source as distributed only when it is offered from the same place as the binaries, so a pointer to Launchpad is not enough for git, Linux and much of Ubuntu. Both a written offer and stopping publication were rejected; ADR-019 says why. `scripts/fetch-image-sources.py` runs in the build job after the pack step. It reads `out/image-sources.tsv` and fetches every source a row marks `gnu` or `unclassified` from where that version is kept:

- **Ubuntu's archive:** Launchpad's `ubuntu/+archive/primary/+sourcefiles/<source>/<version>/`.
- **The template's PPAs:** the table `PPAS`, which a test holds to `install-git.sh`'s `GIT_REPO`. Launchpad keeps only a PPA's published version.
- **PostgreSQL's packages** (a version with `.pgdg`): `apt-archive.postgresql.org`'s pool, which keeps every version.
- **Temurin:** the `-jdk-sources` tarball Adoptium publishes beside each release. The deb version `21.0.12.1.0+1-0` is the tag `jdk-21.0.12.1+1`, and `8.0.504.0.0+1-0` is `jdk8u504-b01`.
- **The kernel:** the tarball `scripts/kernel/linux.pin` names, the one line `build-guest-kernel.sh` reads too, with `out/vmlinux-billet.config`.

Every file is streamed to disk and checked against its `.dsc`'s `Checksums-Sha256`, Adoptium's `.sha256.txt` or the pin, and one that does not match is not kept. A source it cannot fetch and verify fails the build, naming each. A 404 is final; anything else is retried five times. An `unclassified` row (no readable copyright file) is fetched unless `scripts/runner-images/reviewed-licenses.tsv` names its source with a license that asks for no source, its evidence and a date. The workflow then:

- tars the result and splits it with `split-image.sh`;
- writes `out/image-sources.parts`: the whole tar with its sha256 and size, then each part, `.part000` upwards, with its sha256;
- writes `out/image-sources-index.tsv`: per source and version, each file `fetched` with its sha256 and size, or `reviewed` with `-` for the rest. The guest kernel's source is named `guest-kernel`, apart from Ubuntu's `linux` source package, which the cloud base carries too.

Before it tags, the publisher checks five things:

- that the parts the list names, contiguously numbered and joined in order, are the whole tar the first line describes;
- that the published index is the archive's own `./index.tsv`, byte for byte;
- that the index accounts for exactly the `(source, source_version)` pairs `image-sources.tsv` marks `gnu` or `unclassified`, with none of the `gnu` ones marked reviewed;
- that the index names one guest kernel;
- that a last list line with no newline is read too, which `while read` alone skips.

Each check exists because Codex showed one that a part list or index could pass without it (2026-10-21): a list missing its last part, a list of one space, an unrelated index. The fetcher names each directory by the whole version, epoch included, so two versions differing only in their epoch are two sources. It refuses an output directory that is not empty, so nothing an earlier run left is indexed. Measured 2026-10-21, against build 39574003320's manifest on the shared test host: 440 sources and the kernel, 1342 files, 3,406,676,484 bytes, 5 minutes 13 seconds, 47 MB resident. Launchpad answered an epoch's `:` quoted as `%3A`, and Adoptium and PGDG a `+` quoted as `%2B`. The workflow runs from main and builds the release the stable channel names, so its seam test lists `fetch-image-sources.py` and `linux.pin`. A release older than the one carrying them cannot be built by main's workflow, which is right: such a tree builds an image billet may not publish.

**Two halves of a gate before an image is published.** Contents, by loop-mounting read-only: the runner is the version the manifest claims, Docker with Buildx and Compose, the GitHub CLI (`check_github_cli`: on GitHub's image, outside its declaration, so the declared-package check cannot see it missing; found missing by a workflow's 127 on 2026-09-22), the agent's contract matches, the units that must start are enabled, root is locked, and everything under `/home/runner` belongs to the runner account (`files_not_owned_by`). An image shipped `/home/runner/.config/NuGet` owned by root, written during an install step, and every job whose tool creates `~/.config/<tool>` failed with EACCES (measured inside a guest 2026-09-21). The build exports `HOME=/root` first, since `chroot` keeps the caller's environment, but that alone did not stop it: the next build, from v0.12.3, still wrote the directory and the gate refused it. The likeliest writer is PowerShell's NuGet provider (reached by the toolcache's module installs), which prefers `XDG_CONFIG_HOME` to `HOME`, and a CI runner sets that to `/home/runner/.config`; the build now unsets the XDG directories too, but that was read from the provider's source, not measured. What holds whichever it was is ordering: the build's last act on the image before step 6 is `chown -R runner:runner /home/runner`, and a test pins that it comes after GitHub's build and step 5. The gate runs the image's binaries in a chroot of the read-only mount, so it gives that chroot what a booted guest has: `/proc`, a tmpfs `/dev` holding only the harmless character devices (Ubuntu's cloud root filesystem ships `/dev` empty), and a scratch tmpfs `/tmp` for `HOME` (pwsh creates `~/.cache` first and aborts on a read-only home); dotnet tools are GitHub's `/etc/skel` installs, so their probes run with the job `PATH` from `/etc/billet-image-env` and the runner's `HOME`; and a failing run's own first lines are kept in the verdict. Boot is `images pull --verify` on a node. The agent drops to `runner` and sets `HOME`, `USER` and `LOGNAME` explicitly, because a service is not a login session.
