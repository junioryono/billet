# Publication, verification and pulling

Part of the `billet-guest-images` skill. Each rule is stated in full, with the measurement or incident behind it.

**The manifest is the only thing that needs signing, and it is verified before it is parsed.** Every asset is checked against a digest the manifest names, which is worth nothing without the signature binding the manifest to the workflow that produced it. `imagesource.PolicyFor`: the default source requires a signature by the identity `https://github.com/junioryono/billet/.github/workflows/guest-image.yml@refs/heads/main` (every literal quoted, anchored; the first version ended `@refs/.+` and accepted `refs/pull/N/head`) from issuer `token.actions.githubusercontent.com`; a non-default `images.source` with nothing configured is an error, not a skip, because "verify if an identity is configured" fails open exactly when an operator points at a mirror. `--skip-signature-verification` is deliberate. The trust root is vendored (`trusted_root.json`) because a node may be air-gapped and sigstore-go refreshes its TUF cache when it expires. Sideloading with `--from <dir>` applies the same policy and copies assets into staging while hashing, because a file verified in place can be replaced before it is read. The publish job never trusts a download's own success: `actions/download-artifact` stopped extracting the 21GB runner-images artifact part way and reported success twice (2026-09-29/30, 108GiB free; actions/download-artifact#454), so `scripts/fetch-guest-artifact.sh` fetches the zip through the REST API and holds it to the digest GitHub published for the artifact, and `publish-guest-release.sh` holds every asset to the manifest's sha256 and pushes the dated tag only after all of them are proved.

**Manifest schema 2 splits the rootfs into ordered parts, and the reader shipped before the writer.** A release asset caps at 2GiB, so `RootfsMultipart` carries up to `MaxParts` (64) parts of `MaxPartBytes`, assembled by `AssembleRootfs`; `Validate` refuses both-or-neither forms. A reader accepts exactly the schemas it knows, so publishing a schema it does not is a flag day the fleet cannot pull its way out of; `SchemaVersion` is deliberately behind what it reads. The channel pointer (`current.json` plus its bundle, read from raw.githubusercontent.com to spare the anonymous REST budget) expires after ten days so a rewritten branch cannot pin a fleet to an old genuine channel; a signature mismatch across CDN generations refetches once before failing closed. There is no rolling `guest-latest` release, because release immutability freezes a tag and GitHub's `latest` alias belongs to the binary installer. `write-image-manifest.sh` writes schema 3 when `build-info.env`'s `LEFT_OUT` names components: the components from the trial's `components.json`, whose names must equal `LEFT_OUT`, each with a positive space, under completion contract 1; it refuses an unsplit image (schema 3 is the multipart layout) and a build that skipped the trial.

**A verification acts as the probe's holder only while its lock's name still leads to the file it locked.** The probe's name is the same on every run, so the lock in `node.lock_dir` (`billet-imageverify-<deployment>.lock`) is what keeps two verifications from being one microVM, and a flock excludes only a process that opens the same inode. When the directory was removed under the holder (#175: the node unit's stop, while it declared the directory a `RuntimeDirectory`), a second verification locked a fresh file and destroyed the first one's live probe. `takeProbeLock` compares the locked descriptor with the path after the flock and takes it again once if the name moved between the open and the flock; `probeLock.hold()` is asked again, as a guard whose failure ends the act, before the pre-launch cleanup, before the launch and before each destroy of the probe. A name that moved is taken again without waiting when nobody else holds it (so a node restart alone costs nothing), and a lock another verification now holds refuses: a probe it may no longer own is left for the next verification's pre-launch cleanup. The promotion is not guarded, because the verdict it records rests on a report authenticated by the run's own secret. This narrows the window on a host still running the old units (the second verification's cleanup cannot see the first one's orphaned lock); the tmpfiles entry closes it (`billet-lifecycle`).

**A tier says `@verified` or an exact generation, never a bare name.** `@verified` resolves to the newest generation proved to boot, intersected with the generations that still exist, contract-relative (`NewestVerifiedForContract`), so a fleet takes up a new image with no config edit and rollback is `images unpromote`. It refuses when nothing has passed, rather than booting something unproven. A launch resolves the alias first, so the log names the generation. `images verify` boots a probe on a root disk grown the way a launch grows it (the largest `disk` a firecracker tier asks for, else 80GiB, or `--disk`; the provider's own resize2fs, so a superblock resize2fs refuses fails verification rather than every launch: g20260926055218 booted and reported on an ungrown disk, then failed every launch for about 90 minutes, #261), reads a report over its own listener, checks that the runner, Docker and Buildx answered at all rather than matching today's major and that the root filesystem the guest booted is the grown one, and records itself (`MarkVerified`, `RecordVerification`) under the publication lock; `images pull --verify --result-file` records the imported generation only after every verification succeeds. `images compatible` proves a generation speaks this binary's `GuestContract` (currently `"10"`) without downloading, boot-verifying an already imported match before fetching another, and exit 2 means images need a compatible generation; the host-upgrade transaction runs it. `images due` reads age from the generation's UTC name so every node carries the timer (exit 2 means nothing to do); `images reap --keep` replans under the publication lock and refuses to remove a generation whose verification or contract changed after the preview.

**A node takes up a newer published image by itself, and the same image is never imported twice.** `billet images refresh` (`internal/ops/images/imagesrefresh.go`, run daily by `billet-images-refresh.timer` or the Mac's `sh.billet.images` agent) resolves the channel manifest through `resolveImageManifest` (the network half of a pull, factored out so nothing is downloaded to answer), and for each configured firecracker image compares `manifest.BuiltAt` with `NewestGeneration(...).Built`: a generation is named for its import time, always after the build it came from, so newest-older-than-built proves a newer image and needs no new Ceph metadata. When newer it runs `images pull --verify` then `images reap --keep 3`; a failed pull reaps nothing; `--dry-run` reports. On tart it runs `pullTartImages` (absent only, a moving tag is not re-pulled); docker, ec2 and codebuild are nothing to do; `release.automatic: false` is nothing to do. The seams are `openRefreshStore`, `fetchImageManifest`, `refreshPull` and `refreshReap`. `generationDue` (the age of the newest generation against the build cadence) is what `images due` and `billet check` report and decides no pull; `billet check` on a firecracker node names each image's newest generation and says when the timer is not enabled. The Go host transaction's `imaged` step (`Host.PrepareImages`, after the stop and before the fence) runs the role's image step: the staged candidate's `images compatible --result-file` then `images pull --verify` per listed image, because the guest contract is the candidate's; `pullTartImages` on a Mac.

**An image that leaves components out is completed in a microVM before it is imported, or not imported at all (#584).** A manifest of schema 3 declares the components of GitHub's image it leaves out because their licenses forbid billet redistributing them (android-sdk, codeql, firefox, google-chrome, microsoft-edge), each with the space it needs, and the completion contract its completer speaks (`imagesource.CompletionContractV1`); a build that cannot run the contract refuses the image before downloading it, in both staging branches and in the refresh. The pull intersects the declared components with `images.accept` (`planCompletion`). Before the kernel lock, `completeImage` grows the unpacked file by the accepted components' space (a truncate, so the node parses no filesystem), attaches it through a loop device, and boots a trusted completion microVM under the probe identity and lock. Its root is the newest generation verified under this binary's guest contract whose paired kernel is on this node. Otherwise it is the image as published, imported by the pull's `asPublished` under the kernel lock as a completion root (`ImportCompletionRoot`). That is a snapshot of the same image under `ceph.CompletionRootPrefix` (`c`, not the generations' `g`), so rbd makes it atomically and nothing that deals in generations sees it: not @verified, the refresh, reap, verify or promote. `ResolveGeneration` refuses it even named exactly, so no tier boots it. Only a spec marked `provider.Spec.CompletionRoot` resolves it, through the disk's `ResolveCompletionRoot`. It records its owner (`CompletionRootOwnerKey`, the node's name), and `RemoveCompletionRoots` removes that node's roots before and after every completion, whatever the completion came to, and never another node's, which may be booting that node's completion. The removal is safe under a live clone because clone v2 keeps a removed parent snapshot in the trash until the clone is gone. Measured against the first design, a staging image under a fixed name, which a real image of that name, a concurrent pull or a trashed clone each broke (review of 2026-10-19). `refuseIncomplete` still stops `images verify --record` and `images promote` on a generation lacking what the deployment accepts. `refreshDue` pulls again while the newest generation lacks an accepted component or carries one no longer accepted. The loop device is detached only after `destroyProbeProved` sees `TeardownStopped`. Otherwise the device and the staging directory are left in place (`errCompletionLeftRunning`). The report listener refuses a report past `maxGuestReportBytes` rather than cutting it, because a cut report reads as a shorter one that ends cleanly, and `checkCompletionReport` bounds each line too. The file is passed as the microVM's second disk (`provider.Spec.Volumes`, `/dev/vdb` in the guest). `completionCommand` is the guest's half of the contract. It mounts and grows the disk, binds /proc, /sys, /dev, /dev/pts and /run, and runs the image's `/opt/billet/complete/run <component>...` chrooted, with `BILLET_COMPLETION_REPORT`. Then it unmounts, runs `e2fsck -f -y`, and posts `prepared=`, `unmounted=`, `fsck=` and the completer's `installed=<name> <version>` and `failed=<name>` lines. `checkCompletionReport` imports nothing unless every step reported 0 and every accepted component installed with a recordable version, and never quotes the guest. The generation records `ceph.ComponentsKey` (what the image left out, and the version installed of each accepted component) inside the import's lock, and an image that left nothing out records none. Vendor code never runs on the node, and the node never mounts a filesystem the completion wrote. Chosen on 2026-10-19 over a systemd-nspawn container on the node, which would have run vendor installers on the node's kernel and network. The provider changed in one place: `provider.Spec.CompletionRoot` and firecracker's `resolveRoot`, which sends a marked spec to the disk's optional `ResolveCompletionRoot` and every other spec to `ResolveGeneration`; attaching the image as a second disk needed nothing new. A root's name is reserved under the publish lock, before the head is touched: a name a snapshot or an owner key already holds is refused. Its owner key is written before its snapshot, so a crash leaves a few bytes of metadata rather than a root nobody reclaims. `RemoveCompletionRoots` removes only roots its own listing saw, and leaves an owner key whose snapshot it did not see, because that may be an import between its owner write and its snapshot. The next reservation clears such keys, whoever owns them: it runs under the publish lock every import writes its key and snapshot inside, so there a key with no snapshot is never an import in flight. Every such judgement rests on a listing that was read: rbd answers a snapshot listing with ENOENT when a snapshot is removed while it lists, so an ENOENT counts as no snapshots only once `rbd info` says the image itself is absent (derived from Ceph's source, 2026-10-19, not measured). A failed `snap create` clears that key only once a listing proves the snapshot absent, withdraws a snapshot the create made anyway, and keeps the key when nothing can tell. `NeededKernels` keeps each existing root's kernel from the kernel reaper. The probe lock is held from the removal of leftovers, through the root's publication and the launch, to the removal of the root, and that last removal runs only after a successful `hold`, so two pulls on one node cannot remove each other's.

**`billet check` describes each tier's generation against `images.accept`, and an image that needs a newer billet says so (#584).** `ReportImageComponents` (internal/ops/images/componentscheck.go) resolves each image reference this node's microVM tiers boot through `ResolveGeneration`, the one place `@verified` is resolved, proves the generation exists (`Generations`, which reads a listing's ENOENT as absence only once the image is, so a missing pin is never read as an image that left nothing out), and reads that generation's components record: the versions it was completed with, what its image left out unaccepted, what it lacks that is accepted and what completes it (the refresh timer, a pull by hand under `release.automatic: false`, a pin that has to move, or the verification of a newer generation that already matches, compared as `refreshDue` compares, against the newest generation, because a refresh does not pull again for it; a newer generation under another guest contract is for a binary speaking that contract to boot, never this one's to verify), and what it carries that is no longer accepted. A generation with no record says nothing. `ReportChannelImage` fetches the signed manifest, so `billet check` runs it only with its network probes, names a `release.version` pin rather than promising an automatic upgrade, and tells `imagesource.ErrNeedsNewerBillet` (a schema above the newest this build reads, or a completion contract it cannot run) from a fetch that failed, which is could-not-tell. `ParseManifest` reads the exact top-level `schema` before the strict key check, only to refuse, and a schema named twice, or a document not closed or followed by anything, is left to the strict path's refusal: a newer schema may carry a key this build has never heard of, and the key check would otherwise call it a malformed document rather than one a newer billet reads. A schema below the oldest is no billet's and is not `ErrNeedsNewerBillet`. `billet init` writes `images.accept: []` for a Firecracker host, in the plain config and in the hybrid render's Firecracker host, with each component and its license link above it (`imagesAcceptYAML`); `TestAGeneratedFirecrackerConfigAcceptsNoComponentAndNamesEach` fails when `config.ImageComponents` gains a name the block does not describe.

**A license accepted in the control plane's `images.accept` reaches every node at registration, and either list accepts (#584).** The plane is given the server's `cfg.Images.Accepted()` (`nodeplane.WithImageAcceptance`, in `internal/app`'s control plane) and every registration's answer carries it from wire 33 (`VersionImageAcceptance`). After every accepted registration, the main loop's and the one a stop makes to recover (`recoverBeforeDrain`), `recordRegistration` writes it through `internal/imageaccept`, a leaf, to `<node.state_dir>/image-acceptance.json` under the node's deployment, durably and 0600, with `carried` false on a wire below 33, because silence is not "accepts none". A write that fails removes the record, so the commands refuse rather than read an answer the node no longer holds. It lives under `node.state_dir`, not the unit's runtime directory, because the refresh timer runs as its own root process and may run after a boot before the node has registered. `acceptedComponents` (internal/ops/images/acceptance.go) is the one read for `images pull`, `refresh`, `verify --record`, `promote` and `billet check`: the node's own list together with the record's, when the record is this node's deployment's (`app.PeekNodeDeploymentID`) and carried; a record that was not carried is the node's own list alone. With no record of this deployment's (none, or another deployment's), every node refuses until it has registered (`errAcceptanceUnknown`), a single host's included: a `server:` section in the node's file proves neither that the node dials that control plane (a node with `node.tls` may dial another machine's) nor that the control plane read this file (two files on one host can differ), so it is no substitute (Codex review, 2026-10-24). A pull meeting `errAcceptanceUnknown` alone still installs the verified kernel, under the kernel directory's lock, and then refuses having imported no generation, because a fresh node's first pull is what puts the kernel its `kernel_image` names on the host, which `billet local up`'s preflight needs before the node can start and register (Codex review, 2026-10-24). It imports nothing because an explicit tier pin resolves an unverified generation unchanged, so an image as published would be bootable without what the deployment accepts, and a refresh would take it as up to date. A node registers within seconds of starting, and `host-upgrade`'s `images pull --verify` runs after the node has registered under the release it replaces, which wrote a record from this release on. `images verify --record` asks again after its boot, and `images pull` immediately before its import, after the completion and the wait for the kernel directory's lock, refusing to import when the plan it would make now differs, because each can take many minutes in which a registration may record a different list. `imageaccept.Remove` syncs the directory before it reports, so a crash cannot bring back a withdrawn answer. Union, not the record alone, because a deployment that accepted a component on a node before its control plane said anything (ubuntu-01, 2026-10-23) would otherwise lose it at the upgrade that starts sending the plane's empty list. A record that cannot be read or parsed, a deployment that cannot be told, no record of this deployment's, and a name this build does not install each refuse, never the node's own list alone, since a generation completed with less and promoted moves every tier onto it. A node takes up a change at its next registration, which a control-plane restart causes on every node (the plane forgets the fleet).

**A per-node rebuild timer is gone on purpose.** It needed root, a large machine and hours on every node, had every operator discover the thirty-day rule alone, and made N machines build one byte-identical artifact. `scripts/build-guest-image.sh` remains for a custom or air-gapped build, on a machine with systemd-nspawn.

**The AMI is the same contract on the other backend.** `AMIContract` is the analogue of `GuestContract`; the tag is a promotion added by `CreateTags` after billet booted the image, and contract 2 means the toolcache GitHub's declaration names with the variables that make it findable. Both architectures meet it; CodeQL has no arm64 bundle and is recorded in `.billet-unpublished`. `billet check` reports an unstamped image as needing a rebuild.
