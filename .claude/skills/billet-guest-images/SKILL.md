# Guest images, kernels and the runner deadline

## What this area is

A Firecracker job boots a golden image: an Ubuntu 24.04 rootfs with Docker, the Actions runner and a small agent that reads its registration from the metadata service. It lives in Ceph as an RBD image with immutable snapshots called generations, and every job gets a copy-on-write clone. billet builds it once, centrally (`.github/workflows/guest-image.yml`, weekly), signs the manifest with Sigstore, publishes a dated `guest-YYYYMMDD-HHMMSS` prerelease and advances a signed pointer on the `release-channel` branch; a deployment pulls it with `billet images pull`. The EC2 backend boots an AMI built by `billet ami build` from the same declaration. `internal/runnerimages` vendors GitHub's `toolset-2404.json` and the installer; `internal/imagesource` fetches and verifies; `internal/runnerrelease` knows which `actions/runner` is installed and how close to refusal it is. `docs/reference/decisions/adr-005-runner-image-parity.md` records what parity costs.

## Rules

**Parity with GitHub's image is a rebuild, not a copy.** GitHub does not publish the image its runners boot (`actions/runner-images` is Packer source targeting Azure; each release's only asset is a ~50KB JSON). It publishes the recipe, so billet vendors `toolset-2404.json` pinned by upstream commit plus its own sha256 (`PinnedCommit`, `PinnedSHA256`, `VerifyToolset`), and both the shell build and the Go side read it, verifying the digest on both paths. Costs measured: the guest image is 15.0GiB used (2.6GB before), the EC2 image 26.8GiB on x64 and 24.9GiB on arm64 (the Android SDK the guest omits). Retention is per guest contract, so `--keep 3` at `size=2` is about 90GiB per contract, and two contracts are live during a migration.

**The toolcache installers are one file with one seam** (`install-toolcache.sh`, `billet_tc_run`, `BILLET_TC_ARCH`, `.billet-unpublished`); see `billet-shell-gates` for the chroot seam, the architecture spellings and the three states of "found nothing".

**The kernel and the filesystem are a matched pair.** A guest booted with a different kernel fails mid-job, so they are published together and the generation records which kernel proved it (`SetKernel`, `KernelFor`), under the same cluster lock reaping takes. A pull keeps the kernel in `/var/lib/billet/kernels` named by version and digest, installed durably before the remote half exists (`billet-backup-restore` for the ordering and the kernel lock). `images reap` refuses while any generation's kernel is unknown, because such a generation boots something on disk indistinguishable from an orphan.

**The kernel gate's verdict is its exit status, and billet's own rule is the artifact-level claim.** moby's `check-config.sh` is vendored at `scripts/kernel/check-config.sh` with commit and sha256 in `check-config.pin`, verified and copied into a private directory before it runs; its status is captured before anything filters the output. That status is also about the build host (cgroup v1, `apparmor_parser`, `root_maxkeys`, a missing `sysctl`), so the gate names those lines when it fails. Every option in `scripts/kernel/required-builtins.txt` must be `=y` and the config may contain no `=m` line, because a microVM has no initramfs; that file is also what the build enables, so the set list and the check list cannot diverge. The workflow runs the gate itself, not only through the build script, because the kernel is cached on its inputs and `actions/cache` saves in its post step even when a later step failed.

**Two halves of a gate before an image is published.** Contents, by loop-mounting read-only: the runner is the version the manifest claims, Docker with Buildx and Compose, the agent's contract matches, the units that must start are enabled, root is locked. Boot, under Firecracker on the runner that built it: the guest is served a metadata contract it must refuse, and its refusal on the console proves the kernel booted this filesystem, systemd reached its target, the network and metadata service answered, and the agent parsed what it got. A pass is that sentence, because Firecracker exits 0 on some guest-side failures. The agent drops to `runner` and sets `HOME`, `USER` and `LOGNAME` explicitly, because a service is not a login session.

**The manifest is the only thing that needs signing, and it is verified before it is parsed.** Every asset is checked against a digest the manifest names, which is worth nothing without the signature binding the manifest to the workflow that produced it. `imagesource.PolicyFor`: the default source requires a signature by the identity `https://github.com/junioryono/billet/.github/workflows/guest-image.yml@refs/heads/main` (every literal quoted, anchored; the first version ended `@refs/.+` and accepted `refs/pull/N/head`) from issuer `token.actions.githubusercontent.com`; a non-default `images.source` with nothing configured is an error, not a skip, because "verify if an identity is configured" fails open exactly when an operator points at a mirror. `--skip-signature-verification` is deliberate. The trust root is vendored (`trusted_root.json`) because a node may be air-gapped and sigstore-go refreshes its TUF cache when it expires. Sideloading with `--from <dir>` applies the same policy and copies assets into staging while hashing, because a file verified in place can be replaced before it is read.

**Manifest schema 2 splits the rootfs into ordered parts, and the reader shipped before the writer.** A release asset caps at 2GiB, so `RootfsMultipart` carries up to `MaxParts` (64) parts of `MaxPartBytes`, assembled by `AssembleRootfs`; `Validate` refuses both-or-neither forms. A reader accepts exactly the schemas it knows, so publishing a schema it does not is a flag day the fleet cannot pull its way out of; `SchemaVersion` is deliberately behind what it reads. The channel pointer (`current.json` plus its bundle, read from raw.githubusercontent.com to spare the anonymous REST budget) expires after ten days so a rewritten branch cannot pin a fleet to an old genuine channel; a signature mismatch across CDN generations refetches once before failing closed. There is no rolling `guest-latest` release, because release immutability freezes a tag and GitHub's `latest` alias belongs to the binary installer.

**A tier says `@verified` or an exact generation, never a bare name.** `@verified` resolves to the newest generation proved to boot, intersected with the generations that still exist, contract-relative (`NewestVerifiedForContract`), so a fleet takes up a new image with no config edit and rollback is `images unpromote`. It refuses when nothing has passed, rather than booting something unproven. A launch resolves the alias first, so the log names the generation. `images verify` boots a probe, reads a report over its own listener, checks that the runner, Docker and Buildx answered at all rather than matching today's major, and records itself (`MarkVerified`, `RecordVerification`) under the publication lock; `images pull --verify --result-file` records the imported generation only after every verification succeeds. `images compatible` proves a generation speaks this binary's `GuestContract` (currently `"10"`) without downloading, boot-verifying an already imported match before fetching another, and exit 2 means images need a compatible generation; the host-upgrade transaction runs it. `images due` reads age from the generation's UTC name so every node carries the timer (exit 2 means nothing to do); `images reap --keep` replans under the publication lock and refuses to remove a generation whose verification or contract changed after the preview.

**The runner deadline starts at the first release newer than yours.** GitHub refuses a self-hosted runner about 30 days after a newer release (`runnerrelease.Grace`, warning at `Warn`), and billet's runners cannot self-update (`DisableUpdate = True` in every JIT config, measured). `billet runner check` once counted from `/releases/latest`, so every later release moved a deadline that had passed: 2.334.0 went stale when 2.335.0 shipped 2026-06-08, and counting from 2.336.0 on 2026-07-20 reported a month in hand for a fleet refused six weeks earlier. `runnerrelease.Resolve` is the one calculation over the installed version and the stable release history, asked by `runner check` and `images pull`. The clock starts at the earliest newer release by publication, not version (measured: v2.285.3 was published 2023-01-30, eleven days after the higher v2.301.1), so the walk scans the whole bounded window rather than stopping at the installed tag, and its bound is the installed release rather than a higher number; running out of budget is recorded (`HistoryComplete`) rather than read as an ending. A version the history does not name is its own answer (`InstalledKnown`): expiry is provable, days remaining are not, and `Current` means only "nothing newer was found" so it is asked after `InstalledKnown`. Exit codes: 0 nothing to do, 2 rebuild due, 3 GitHub already refusing; failing to reach GitHub is an error, not one of the three. `images pull` refuses only a proved expiry (`--allow-stale` skips the lookup) and reports image age as maintenance information (`AgeNotice`, fourteen days) that decides nothing. The pin lives on one line of `internal/runnerrelease/pinned.txt` with its checksum; `runner-release.yml` opens a PR when a release lands, and merging is the gate. The scheduled build installs whatever GitHub has published and records it on the image, which is what `runner check` reads.

**The AMI is the same contract on the other backend.** `AMIContract` is the analogue of `GuestContract`; the tag is a promotion added by `CreateTags` after billet booted the image, and contract 2 means the toolcache GitHub's declaration names with the variables that make it findable. Both architectures meet it; CodeQL has no arm64 bundle and is recorded in `.billet-unpublished`. `billet check` reports an unstamped image as needing a rebuild.

**A per-node rebuild timer is gone on purpose.** It needed root, debootstrap and an hour on every node, had every operator discover the thirty-day rule alone, and made N machines build one byte-identical artifact. `scripts/build-guest-image.sh` remains for a custom or air-gapped build.

## Measured facts

- Guest image 15.0GiB; EC2 image 26.8GiB x64, 24.9GiB arm64.
- A guest boots, takes its registration and runs a container in about ten seconds.
- `actions/runner` history: v2.285.3 published 2023-01-30, after v2.301.1 on 2023-01-19; one releases page is ~5MB and reaches back five years, so the walk bound is two pages.
- The macOS Xcode image is about 87GB to pull; `ubuntu-runner-arm64` 11.3GB compressed.
- `check-config.sh` exits 1 for host facts unrelated to the config; `grep | head -30` on its 2.9MB output exits 141.
