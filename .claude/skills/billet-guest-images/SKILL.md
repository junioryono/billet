# Guest images, kernels and the runner deadline

## What this area is

A Firecracker job boots a golden image: an Ubuntu 24.04 rootfs with Docker, the Actions runner and a small agent that reads its registration from the metadata service. It lives in Ceph as an RBD image with immutable snapshots called generations, and every job gets a copy-on-write clone. billet builds it once, centrally (`.github/workflows/guest-image.yml`, weekly), signs the manifest with Sigstore, publishes a dated `guest-YYYYMMDD-HHMMSS` prerelease and advances a signed pointer on the `release-channel` branch; a deployment pulls it with `billet images pull`. The EC2 backend boots an AMI built by `billet ami build` from the same declaration. `scripts/runner-images` vendors GitHub's `actions/runner-images` tree at one commit and the guest build runs it; `internal/runnerimages` vendors GitHub's `toolset-2404.json` and the EC2 toolcache installer; `internal/imagesource` fetches and verifies; `internal/runnerrelease` knows which `actions/runner` is installed and how close to refusal it is. `docs/reference/decisions/adr-005-runner-image-parity.md` records what parity costs.

## Rules

**The guest image is GitHub's own build, run on Ubuntu's own base (#250).** GitHub does not publish the image its runners boot, only the Packer template that builds it for Azure. `scripts/runner-images/upstream/` vendors that tree at one commit (`COMMIT`, equal to the toolset pin), every file held to its git blob id and every directory to its tree id (`BLOBS`, `TREES`). `plan.json` is the template's provisioner list, derived by a test-side reader and pinned; `scripts/run-runner-images.sh` runs it step by step, with Packer's environment, through a target driver. The target is Ubuntu's pinned cloud root filesystem (`base.pin`, its SHA256SUMS signature checked against Canonical's key), booted with `systemd-nspawn --boot` inside the image file the build writes through. Everything billet does differently is one reviewed file, `differences.tsv`: a `skip`, or a `prepare:<name>` the runner performs just before a step, each with its reason; an entry naming a step the plan no longer has stops the build before anything runs. So parity holds by construction, and the gate checks GitHub's paths (`/usr/bin/yq`, apt's ruby), not billet's.

**The template drifts from what it downloads, and each drift is carried as a difference until the pin moves.** A pinned template installs whatever its scripts fetch today, so a script that built GitHub's July image can fail in September: `install-python.sh`'s unpinned `pip install pipx` took pipx 1.17.7, which needs packaging 26 and cannot replace Debian's 24.0, fixed upstream in be22fc2981aa after the pin, and carried as `prepare:pipx-pin` until the bump to the `ubuntu24/20260920.314` release (e7563390) took GitHub's own pin and retired it. Before adding a difference, look for GitHub's own fix after the pin (`gh api repos/actions/runner-images/compare/<pin>...main`) and copy its effect. Bumping `COMMIT` retires such entries; it moves the toolset pin with it, which the EC2 build also reads. Pin to an `ubuntu24/<date>.<n>` image release's own commit (it sits on a `releases/ubuntu24/<date>` branch, not on `main`), the newest GitHub no longer marks a prerelease. A bump also brings GitHub's new tests and new assumptions about Azure, each of which becomes a difference: that bump's `configure-environment.sh` runs `update-grub` under `bash -e` for ext4 root options GRUB passes on Azure, and the cloud root filesystem has no GRUB, so `prepare:grub-absent` installs a stand-in that answers the call and removes itself; its tests assert those options on `/proc/cmdline` and the root mount, which the build's container shows as the builder's, and that apt goes through GitHub's mirror list; each such test is marked `-Skip` by name through `skip_upstream_test`, which refuses unless exactly one test has that name, so a renamed test stops the build at its prepare. Diff `scripts/runner-images/upstream/` against the new commit and read every changed script and test for what it assumes, because only a real build would otherwise find it, an hour in. Upstream bugs GitHub ships are parity too: `install-bazel.sh` writes `USE_BAZEL_FALLBACK_VERSION=silent:` with no version, because it reads a `bazel --version` line Bazel 9 no longer prints, and the gate holds the variable, not a value GitHub's image lacks.

**The nspawn driver proves what it stops, three ways, before the workspace is touched.** `scripts/runner-images-nspawn.sh` starts the machine in a transient unit with `--keep-unit`, `DevicePolicy=closed` (only `/dev/net/tun` and terminals; with every capability and no user namespace a block class would be the builder's own disks), `--network-veth` and owned FORWARD rules on the exact link `ve-<machine>` (names of at most twelve characters, so the link name fits). A stop is proved by the unit inactive or failed, the machine unregistered (`No machine`), and the unit's `cgroup.events` saying `populated 0` under a cgroup v2 root it can read, a missing cgroup counting as gone only where its parent can be searched; anything it cannot read is "cannot tell", never stopped. Before clearing a workspace the build finds every machine by what it holds (machined's `RootDirectory` equal to this rootfs), stops it through the unit machined names, and refuses on a failed listing, an unreadable or empty property, or a machine gone before its root was read. The listing is split with parameter expansion and the recovery is called inside an `if`, where errexit does not reach, so every failure is returned explicitly. nspawn mounts its own tmpfs on `/tmp` capped at a tenth of memory, which the toolset's downloads fill; `SYSTEMD_NSPAWN_TMPFS_TMP=0` keeps the image's `/tmp`, and `start` proves it is not a tmpfs.

**The build runs on a fleet tier, not a hosted runner.** GitHub's image does not fit a hosted runner's disk, so `guest-image.yml` runs on `billet-image-builder-ubuntu-2404` (16 vCPU, 64GiB, 320GiB), a Firecracker guest with no `/dev/kvm`: nspawn needs none, and the in-CI Firecracker boot is gone. Every generation is still booted by `images pull --verify` before it can become `@verified`. The EC2 AMI still builds from the declaration with the shared toolcache installers (`install-toolcache.sh`, `billet_tc_run`, `BILLET_TC_ARCH`, `.billet-unpublished`); see `billet-shell-gates` for that seam.

**The kernel and the filesystem are a matched pair.** A guest booted with a different kernel fails mid-job, so they are published together and the generation records which kernel proved it (`SetKernel`, `KernelFor`), under the same cluster lock reaping takes. A pull keeps the kernel in `/var/lib/billet/kernels` named by version and digest, installed durably before the remote half exists (`billet-backup-restore` for the ordering and the kernel lock). `images reap` refuses while any generation's kernel is unknown, because such a generation boots something on disk indistinguishable from an orphan.

**The kernel gate's verdict is its exit status, and billet's own rule is the artifact-level claim.** moby's `check-config.sh` is vendored at `scripts/kernel/check-config.sh` with commit and sha256 in `check-config.pin`, verified and copied into a private directory before it runs; its status is captured before anything filters the output. That status is also about the build host (cgroup v1, `apparmor_parser`, `root_maxkeys`, a missing `sysctl`), so the gate names those lines when it fails. Every option in `scripts/kernel/required-builtins.txt` must be `=y` and the config may contain no `=m` line, because a microVM has no initramfs; that file is also what the build enables, so the set list and the check list cannot diverge. The workflow runs the gate itself, not only through the build script, because the kernel is cached on its inputs and `actions/cache` saves in its post step even when a later step failed.

**Two halves of a gate before an image is published.** Contents, by loop-mounting read-only: the runner is the version the manifest claims, Docker with Buildx and Compose, the GitHub CLI (`check_github_cli`: on GitHub's image, outside its declaration, so the declared-package check cannot see it missing; found missing by a workflow's 127 on 2026-09-22), the agent's contract matches, the units that must start are enabled, root is locked, and everything under `/home/runner` belongs to the runner account (`files_not_owned_by`). An image shipped `/home/runner/.config/NuGet` owned by root, written during an install step, and every job whose tool creates `~/.config/<tool>` failed with EACCES (measured inside a guest 2026-09-21). The build exports `HOME=/root` first, since `chroot` keeps the caller's environment, but that alone did not stop it: the next build, from v0.12.3, still wrote the directory and the gate refused it. The likeliest writer is PowerShell's NuGet provider (reached by the toolcache's module installs), which prefers `XDG_CONFIG_HOME` to `HOME`, and a CI runner sets that to `/home/runner/.config`; the build now unsets the XDG directories too, but that was read from the provider's source, not measured. What holds whichever it was is ordering: the build's last act on the image before step 6 is `chown -R runner:runner /home/runner`, and a test pins that it comes after GitHub's build and step 5. The gate runs the image's binaries in a chroot of the read-only mount, so it gives that chroot what a booted guest has: `/proc`, a tmpfs `/dev` holding only the harmless character devices (Ubuntu's cloud root filesystem ships `/dev` empty), and a scratch tmpfs `/tmp` for `HOME` (pwsh creates `~/.cache` first and aborts on a read-only home); dotnet tools are GitHub's `/etc/skel` installs, so their probes run with the job `PATH` from `/etc/billet-image-env` and the runner's `HOME`; and a failing run's own first lines are kept in the verdict. Boot is `images pull --verify` on a node. The agent drops to `runner` and sets `HOME`, `USER` and `LOGNAME` explicitly, because a service is not a login session.

**The manifest is the only thing that needs signing, and it is verified before it is parsed.** Every asset is checked against a digest the manifest names, which is worth nothing without the signature binding the manifest to the workflow that produced it. `imagesource.PolicyFor`: the default source requires a signature by the identity `https://github.com/junioryono/billet/.github/workflows/guest-image.yml@refs/heads/main` (every literal quoted, anchored; the first version ended `@refs/.+` and accepted `refs/pull/N/head`) from issuer `token.actions.githubusercontent.com`; a non-default `images.source` with nothing configured is an error, not a skip, because "verify if an identity is configured" fails open exactly when an operator points at a mirror. `--skip-signature-verification` is deliberate. The trust root is vendored (`trusted_root.json`) because a node may be air-gapped and sigstore-go refreshes its TUF cache when it expires. Sideloading with `--from <dir>` applies the same policy and copies assets into staging while hashing, because a file verified in place can be replaced before it is read. The publish job never trusts a download's own success: `actions/download-artifact` stopped extracting the 21GB runner-images artifact part way and reported success twice (2026-09-29/30, 108GiB free; actions/download-artifact#454), so `scripts/fetch-guest-artifact.sh` fetches the zip through the REST API and holds it to the digest GitHub published for the artifact, and `publish-guest-release.sh` holds every asset to the manifest's sha256 and pushes the dated tag only after all of them are proved.

**The build job checks out the release the stable channel names, never `main`.** An image that reaches the guest channel fans out to every deployment on its next refresh, and `main`, gated as it is, is not a tree a fleet should inherit unreviewed at 04:17 on a Monday. So `guest-image.yml`'s build job resolves the stable channel (the same pointer deployments follow) and builds that tree; a tag named by hand must be an immutable, published, non-prerelease release; a dispatch with `source=main` builds for testing and cannot publish. The workflow file itself stays on `main`, because every deployed binary verifies the channel's signature against this workflow running on `refs/heads/main` (`imagesource.PublishRef`); only the tree the build checks out moves. That leaves YAML on `main` driving scripts from an older tree, so the seam between them is frozen by a test in `scripts/scripts_test.go` rather than left to drift. The dated guest tag points at the source release's commit, the provenance the closed manifest schema cannot carry. Never recreate a rolling guest release: its tag and assets freeze on first publication, and the publisher creates the dated tag before `gh release create --verify-tag` so a conflicting tag fails rather than relabelling the build.

**Manifest schema 2 splits the rootfs into ordered parts, and the reader shipped before the writer.** A release asset caps at 2GiB, so `RootfsMultipart` carries up to `MaxParts` (64) parts of `MaxPartBytes`, assembled by `AssembleRootfs`; `Validate` refuses both-or-neither forms. A reader accepts exactly the schemas it knows, so publishing a schema it does not is a flag day the fleet cannot pull its way out of; `SchemaVersion` is deliberately behind what it reads. The channel pointer (`current.json` plus its bundle, read from raw.githubusercontent.com to spare the anonymous REST budget) expires after ten days so a rewritten branch cannot pin a fleet to an old genuine channel; a signature mismatch across CDN generations refetches once before failing closed. There is no rolling `guest-latest` release, because release immutability freezes a tag and GitHub's `latest` alias belongs to the binary installer.

**A tier says `@verified` or an exact generation, never a bare name.** `@verified` resolves to the newest generation proved to boot, intersected with the generations that still exist, contract-relative (`NewestVerifiedForContract`), so a fleet takes up a new image with no config edit and rollback is `images unpromote`. It refuses when nothing has passed, rather than booting something unproven. A launch resolves the alias first, so the log names the generation. `images verify` boots a probe on a root disk grown the way a launch grows it (the largest `disk` a firecracker tier asks for, else 80GiB, or `--disk`; the provider's own resize2fs, so a superblock resize2fs refuses fails verification rather than every launch: g20260926055218 booted and reported on an ungrown disk, then failed every launch for about 90 minutes, #261), reads a report over its own listener, checks that the runner, Docker and Buildx answered at all rather than matching today's major and that the root filesystem the guest booted is the grown one, and records itself (`MarkVerified`, `RecordVerification`) under the publication lock; `images pull --verify --result-file` records the imported generation only after every verification succeeds. `images compatible` proves a generation speaks this binary's `GuestContract` (currently `"10"`) without downloading, boot-verifying an already imported match before fetching another, and exit 2 means images need a compatible generation; the host-upgrade transaction runs it. `images due` reads age from the generation's UTC name so every node carries the timer (exit 2 means nothing to do); `images reap --keep` replans under the publication lock and refuses to remove a generation whose verification or contract changed after the preview.

**The runner deadline starts at the first release newer than yours.** GitHub refuses a self-hosted runner about 30 days after a newer release (`runnerrelease.Grace`, warning at `Warn`), and billet's runners cannot self-update (`DisableUpdate = True` in every JIT config, measured). `billet runner check` once counted from `/releases/latest`, so every later release moved a deadline that had passed: 2.334.0 went stale when 2.335.0 shipped 2026-06-08, and counting from 2.336.0 on 2026-07-20 reported a month in hand for a fleet refused six weeks earlier. `runnerrelease.Resolve` is the one calculation over the installed version and the stable release history, asked by `runner check` and `images pull`. The clock starts at the earliest newer release by publication, not version (measured: v2.285.3 was published 2023-01-30, eleven days after the higher v2.301.1), so the walk scans the whole bounded window rather than stopping at the installed tag, and its bound is the installed release rather than a higher number; running out of budget is recorded (`HistoryComplete`) rather than read as an ending. A version the history does not name is its own answer (`InstalledKnown`): expiry is provable, days remaining are not, and `Current` means only "nothing newer was found" so it is asked after `InstalledKnown`. Exit codes: 0 nothing to do, 2 rebuild due, 3 GitHub already refusing; failing to reach GitHub is an error, not one of the three. `images pull` refuses only a proved expiry (`--allow-stale` skips the lookup) and reports image age as maintenance information (`AgeNotice`, fourteen days) that decides nothing. The pin lives on one line of `internal/runnerrelease/pinned.txt` with its checksum; `runner-release.yml` opens a PR when a release lands, and merging is the gate. The scheduled build installs whatever GitHub has published and records it on the image, which is what `runner check` reads.

**The AMI is the same contract on the other backend.** `AMIContract` is the analogue of `GuestContract`; the tag is a promotion added by `CreateTags` after billet booted the image, and contract 2 means the toolcache GitHub's declaration names with the variables that make it findable. Both architectures meet it; CodeQL has no arm64 bundle and is recorded in `.billet-unpublished`. `billet check` reports an unstamped image as needing a rebuild.

**A node takes up a newer published image by itself, and the same image is never imported twice.** `billet images refresh` (`cmd/billet/imagesrefresh.go`, run daily by `billet-images-refresh.timer` or the Mac's `sh.billet.images` agent) resolves the channel manifest through `resolveImageManifest` (the network half of a pull, factored out so nothing is downloaded to answer), and for each configured firecracker image compares `manifest.BuiltAt` with `NewestGeneration(...).Built`: a generation is named for its import time, always after the build it came from, so newest-older-than-built proves a newer image and needs no new Ceph metadata. When newer it runs `images pull --verify` then `images reap --keep 3`; a failed pull reaps nothing; `--dry-run` reports. On tart it runs `pullTartImages` (absent only, a moving tag is not re-pulled); docker, ec2 and codebuild are nothing to do; `release.automatic: false` is nothing to do. The seams are `openRefreshStore`, `fetchImageManifest`, `refreshPull` and `refreshReap`. `generationDue` (the age of the newest generation against the build cadence) is what `images due` and `billet check` report and decides no pull; `billet check` on a firecracker node names each image's newest generation and says when the timer is not enabled. The Go host transaction's `imaged` step (`Host.PrepareImages`, after the stop and before the fence) runs the role's image step: the staged candidate's `images compatible --result-file` then `images pull --verify` per listed image, because the guest contract is the candidate's; `pullTartImages` on a Mac.

**A per-node rebuild timer is gone on purpose.** It needed root, a large machine and hours on every node, had every operator discover the thirty-day rule alone, and made N machines build one byte-identical artifact. `scripts/build-guest-image.sh` remains for a custom or air-gapped build, on a machine with systemd-nspawn.

**The guest carries billet itself, for the build caches (#226).** `install_guest_billet` builds `/opt/billet/bin/billet` from the checked-out tree with the newest go the image's toolcache installed, because the hosted build runner's own go is removed to make room and the workflow's seam with the release tree is frozen, and installs `/opt/billet/bin/bazel-credential-helper` beside it. The agent reads the MMDS leaf `guest-caches` (`go`, `go-test-results`, `bazel`, `git`, derived by the node from the tier's cache block and sent only beside a cache session) and, only when the image carries billet, configures each cache in the block between `BILLET_GUEST_CACHES_BEGIN`/`END`, which `scripts/guest_agent_caches_test.go` executes: `GOCACHEPROG=/opt/billet/bin/billet cache gocacheprog` and `GOFLAGS=-count=1` unless test results are shared, `/etc/bazel.bazelrc` with the remote cache and the credential helper (never the bearer), and `/etc/gitconfig` with the `insteadOf` rewrite of `https://github.com/`, an identity `pushInsteadOf`, and `billet cache git-credential` as the node's credential helper. The container hook runs where it has something to add: the docker shim only under interception (`BILLET_CONTAINER_SHIM`), and under the go cache a read-only mount of the binary and the helper's variables, where the job's own env wins. `check-guest-image.sh` refuses an image missing the binary, the wrapper or the agent's wiring. No `GuestContract` bump: every piece is additive, and an older image simply builds cold.

## Measured facts

- Guest image built from GitHub's template: `contents: 53779M used, 22176M free of 81920M`, the same within a few megabytes on three builds (2026-09-28, image builder); usable space is about 0.927 of `SIZE_MB`. EC2 image 26.8GiB x64, 24.9GiB arm64.
- The first trials on the builder ran 22, 66, 71 and then all 84 template steps: a TLS stall to `azcliprod.blob.core.windows.net` that did not recur (the path MTU is a clean 1500), the pipx pin, and nspawn's `/tmp` tmpfs.
- A guest boots, takes its registration and runs a container in about ten seconds.
- `actions/runner` history: v2.285.3 published 2023-01-30, after v2.301.1 on 2023-01-19; one releases page is ~5MB and reaches back five years, so the walk bound is two pages.
- The macOS Xcode image is about 87GB to pull; `ubuntu-runner-arm64` 11.3GB compressed.
- `check-config.sh` exits 1 for host facts unrelated to the config; `grep | head -30` on its 2.9MB output exits 141.
- The shipped image's apt source names TWO HTTPS mirrors (`archive.ubuntu.com`, then `mirrors.edge.kernel.org`) with `Acquire::Retries 3` and 30-second timeouts in `/etc/apt/apt.conf.d/90billet-fetch`, written by `install_cloud_base` before GitHub's build; since the `ubuntu24/20260920.314` pin GitHub's `configure-apt.sh` writes `zz-retries` (one retry, 15-second timeouts on x64, for fast failover), which apt reads last, so those are the image's effective values from that step on and GitHub's apt tests assert them; GitHub's `configure-apt-sources.sh` rewrites only `azure.archive.ubuntu.com` URIs, so it leaves them as they are. Two URIs in one deb822 stanza are two repositories: apt fetches both index sets and takes a package from whichever lists the version (measured on a guest 2026-09-11 with the first URI black-holed and a 5 s timeout: strict update failed in 13 s naming the dead mirror, lenient update passed in 13 s, a package installed from the second in 4 s), while `mirror+file:` with a priority list did not finish a strict update in nine minutes under the same black hole. `Acquire::Retries` retries the failing URI and the timeout is per read, not per download. Measured 2026-09-11: every `archive.ubuntu.com` IPv4 address refused port 80 for hours from two unrelated networks (the reference deployment's site and AWS), two answered nothing on 443 either, and a job's apt stalled 30 s per attempt on one of those (`docs/reference/records/shared-uplink.md`).
