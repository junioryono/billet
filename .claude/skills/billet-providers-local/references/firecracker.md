# Firecracker

Part of the `billet-providers-local` skill. Each rule is stated in full, with the measurement or incident behind it.

**Every guest runs under the jailer**, chrooted, dropped to its own uid, in a cgroup, under seccomp, and the jailer names its chroot after the resolved `--exec-file`: the reference host installs `firecracker-v1.16.1` behind a stable symlink, so the jail is at `/srv/jailer/firecracker-v1.16.1/<id>/root`, and `List` enumerates every directory a jailer has built in rather than the path the config names, or every guest started before a version bump sits where the new process does not look.

**`jailer --daemonize` exits 0 for a VM that died on startup** (a pid file and a socket beside a VMM that exited 1), so `Launch` believes the VMM's own API and nothing else. The registration travels in MMDS v2, placed before `InstanceStart`, which is why the backend drives the API rather than a `--config-file` (a config file starts the machine as it is read). A unix socket address is a fixed-size field, so the API socket six components below the chroot base is refused at construction.

**The jailer creates a per-VM cgroup only when given a `--cgroup`, and the two cgroup forms cannot coexist on a host** (`CgroupMove … Resource busy`). It also enables a controller along the path (`+memory` in every ancestor's `cgroup.subtree_control`) only for the controllers its keys name (`write_values` in v1.16.1's `cgroup.rs`), so with `cpu.weight=100` alone a job's cgroup has no memory or io accounting. `WithJobAccounting` (what `node.monitoring` passes) adds `memory.max=max` and `io.weight=default 100` only for a controller `probeAccounting` proved at construction, because the jailer refuses a launch whose key names a file the kernel lacks, and `io.weight` exists only with blk-iocost; the proof for io is `io.weight` in a child that already has io enabled. A node that does not ask launches with the argv it always had. A node that asks on a host that did not prove both controllers does not start: `Node.open` refuses through `requireJobAccounting`, and `billet check` through the same `RequireJobAccounting` before it opens /dev/kvm, naming each controller as missing or could-not-tell (an unreadable `cgroup.controllers` or mount table refuses rather than reading as missing), because a controller never asked of the jailer is a group recorded unmeasured on every job. `billet images` builds its probe's provider through `NewProvider` and is not held to it. Since the refusal trusts the io probe, `io.weight` counts only as a regular file in a child whose `cgroup.type` is `domain` (or `domain threaded`): a directory of that name, a threaded child and a child gone since the listing each say nothing, the scan goes on past them, and io reads as missing only from a domain child still there without the file. `node.firecracker.cpu_placement` (`compact`, `spread` or `packed`) adds `cpuset.cpus=<list>` as one more key of the same form, so the jailer enables cpuset along the path the same way: on `ubuntu-01` (2026-10-23, v1.16.1) the first pinned launch moved `firecracker-v1.16.1/cgroup.subtree_control` from `cpu io memory` to `cpuset cpu io memory`, the guest ran on exactly the cpus claimed, and unpinned launches beside it were unaffected. The cpus are claimed like a uid or tap (`.billet-cpus/<n>` under the chroot base, holding the jail id, recorded in the jail's resources), so restart adoption, crash reaping and orphan release are the claims' own; a guest that does not fit runs unpinned with a warning, never refused, and `New` refuses a placement on a host whose topology cannot be read whole or whose cgroup root lists no cpuset controller.

**There is no API action that kills a microVM.** The API has `FlushMetrics`, `InstanceStart` and `SendCtrlAltDel`, and a real guest ignored the last for twenty seconds. billet signals the VMM after proving the pid is still that microVM's (the `--id <jail id>` pair in `/proc/<pid>/cmdline`), re-checks with the pidfd held, sends SIGKILL and nothing gentler first, waits for the pid to stop being that microVM's, and treats an unreadable `/proc` entry as could-not-tell. SIGTERM does nothing: `--new-pid-ns` makes the VMM its namespace's init, Firecracker installs no SIGTERM handler, and the kernel drops a default-disposition signal sent to a namespace init from an ancestor namespace (measured 2026-09-30, v1.16.1 under the jailer: `SigCgt 0000000441801449`, `kill -TERM` ignored for over two minutes, `kill -KILL` immediate). billet passes `--new-pid-ns` because the jailer's documentation says the pid file is written only then, and a future version honouring its docs must not make "no pid file" read as "nothing running". Teardown never continues past a VMM it could not stop, because removing the jail removes the pid file that is the only handle for ever stopping it.

**The kernel is linked into each jail and stays root-owned.** Chowning the jail tree chowned the host's one kernel to an account every VMM shares; chown the chroot alone. The owner marker stays root-owned too, because `List` and `Find` trust it.

**Two defects survived every unit test and died on the first real launch**: `os.Stat().Sys()` holds a `*syscall.Stat_t`, not the structurally identical `*unix.Stat_t`, and the shutdown action above. That is the argument for `realfirecracker_test.go` existing at all. The generation's recorded kernel wins over the node's configuration (`kernelForGeneration`), a recorded name that is not a plain base name is refused because cluster metadata is writable by any client with pool access, and an unpaired generation falls back to `node.firecracker.kernel_image`.

**A capture is published by copy, with the host it was taken on, and a restore refuses any other host before the load.**

- **Capture:**
  - **Before pausing,** `Capture(ctx, id, snapshot)` refuses:
    - a jail started by another Firecracker build (`j.execName != p.execName`), since no restore here could load it;
    - a VMM whose running executable digests differently from the binary at the configured path, i.e. a build replaced while the guest ran. The process is the one serving the jail's API socket, named by the kernel (`SO_PEERCRED` on a fresh connection, its uid required to be the microVM's), held by a pidfd while `/proc/<pid>/exe` is opened and proved alive after (`apiPeerExecutable`, Linux only). The pid file and command line are the jail's to write, so they decide nothing here. This is a compatibility label that catches an honest VMM whose build was upgraded under it, not an authentication of the capture's sender: a VMM that has been taken over writes every byte of the snapshot anyway, and the restore side (billet's own build, jailed, with the loaded shape checked) is what contains a hostile one. Capture only a guest you trust, because every fork inherits it;
    - a jail kernel that is not a regular file billet's account owns, opened without following a link (`linkedByBillet`);
    - a jail with no `billet-shape`. That record is written beside the jail root at launch (vCPUs, memory, the exact generation the root disk was cloned from and the host device it is mapped at) and bounds the capture; a shape without the generation or the device is refused, because the system disk could not be published;
    - a root disk that cannot keep a golden's system disk (`goldenDisk`), and a snapshot name that could not name one (`@`, `/` or surrounding space), so a node that cannot publish never stops a guest.
  - **It then describes the host,** so a host that cannot describe itself never stops a guest.
  - **Every connection Capture makes checks whose VMM answers** (`newVMMAPIAs`: the kernel's `SO_PEERCRED` uid must be the microVM's), because the socket is in the jail root and a guest that has run could make it a link to another lease's socket, which root would follow. So is every other call to a VMM: `awaitAPI` at launch, `runState` (List, Find, recovery) and cache drive attach and detach all use `p.apiAs(socket, res.UID)`. A refused peer is `errVMMPeer`, which `runState` returns as an error (neither running nor stopped) and `awaitAPI` returns at once rather than polling out the boot wait. Tests whose fake VMMs answer as the test's account use `withAPIAs(answeringAsAnyone)`.
  - **It takes the store's publish lock before pausing,** polling so the wait ends with its context, because a capture queued behind another's copy would otherwise hold a paused guest and its lease lock indefinitely. The lock file stays in the store for good.
  - **Its own output names:** the VMM writes `capture.state` and `capture.mem`, never `snapshot.*`. A restored jail holds those names as billet's read-only links, and asking the VMM to overwrite them fails after the pause.
  - **Copy, never rename:** `publishCapture` copies the files out of the jail. A renamed file would be the VMM's own inode, which its account may still hold open for writing.
  - **Judging each source:** it is opened without following a link and must be a regular file owned by the microVM's uid (`jailWritten`, a seam the harness relaxes because only root can create files as a jail uid).
  - **Bounds:** the memory file must be no larger than the recorded memory and the state file no larger than `maxCapturedState`. Each is copied in chunks with a cancellation check between them, and must be the same inode at the same size afterwards.
  - **Publishing:** under that lock, each publish sweeps any `.staging-*` a killed publish left. The copies go into a fresh `.staging-` directory as 0444 files owned by billet, each made read-only *before* its sync, beside `compatibility.json`. The directory is renamed into place with `RENAME_NOREPLACE` (`RENAME_EXCL` on darwin), so a published name, even an empty directory, is never replaced. Then the store and the directory above it are synced. A failed publish removes its staging and says so if it cannot.
  - **Its own system disk, published in place, while the guest is paused** (#508). A restored kernel's page cache describes the disk its memory was taken with, so after the memory snapshot and before the files are published, `Capture` fsyncs the host device the shape names (`flushDevice`: a block device under `/dev`, opened without following a link, never a path in the jail root) and asks the disk to `PublishRoot` the builder's clone as `golden-<the builder's lease id>`, whose answer, `golden-<lease>@g<UTC time>`, the record names. Named after the lease, not the snapshot, because the cache pool is shared by every node of a site and can be by several deployments, and a snapshot's name is whatever its capturer chose (#508, 2026-10-22). The fsync is there because billet configures Firecracker's default block cache type, `Unsafe`, which advertises no flush to the guest and never fsyncs the backing file, so the guest's writes can sit in the host's page cache; on the reference node (2026-10-21) a write held open on a freshly mapped krbd device reached the cluster before any snapshot every time, which is the per-device dirty limit at work and no promise. A publication of the files that fails withdraws the disk (`WithdrawRoot`), so the builder's teardown discards its clone as it would any other, and a withdrawal that fails says the disk stays published with no snapshot naming it.
- **The compatibility record (`fingerprint.go`):**
  - **Fields:** every distinct CPU identity in `/proc/cpuinfo` (vendor, family, model, model name, stepping, microcode; the arm64 implementer and part) and a digest of the sorted feature flags; the host kernel's uname release and version; a SHA-256 of the Firecracker binary; and a SHA-256 of the guest kernel. Digests are cached by inode, size, modification and change time. A read is judged without the change time, by what a write moves: every launch hard-links the guest kernel into its jail and a link moves the change time, so a digest taken while another launch linked the kernel was refused as "changed while it was being read" (8 of 10 concurrent restores on the reference node, 2026-10-22, found by `TestRealFirecrackerRestoresAGoldenAsManyForks`). The captured files `copyOut` copies keep the whole identity, because the jailed account that wrote them could reset their modification time.
  - **Why exact equality:** Firecracker's own rule is that snapshots resume only on an identical software and hardware configuration, and it checks just a CRC of the state file. A mismatch is otherwise not a refused load but a guest that misbehaves after it resumes.
  - **Format 2 names the disk:** `image`, the generation the captured guest's root disk was cloned from, and `disk`, the golden's system disk. A format 1 record names no disk, so it is refused like any other format.
  - **Format 3 carries the evidence** (#508 item 2, 2026-10-22): `deployment`, `builder` (the captured lease) and the SHA-256 of the state and memory, computed in `copyOut` from the bytes as they are copied, so it costs no second read. `Capture` answers it as an `Evidence`, which the caller keeps: the control plane's ledger, once #509 adds the golden-build lease, carried back by the command that asks for a restore. A format 2 record is refused with "capture the golden again", because it records no evidence.
- **Restore:**
  - **Only the golden the caller expects** (`Restore(spec, snapshot, want Evidence)`, `compatibility.expected`). Missing evidence (any field empty), a record whose deployment is not this node's (even when the evidence agrees with it), and a record whose builder, disk or digests differ from the evidence are each `errSnapshotNotExpected`, checked in `goldenOf` before anything is claimed and again in `placeSnapshot` through the directory the files are linked from, because the name could hold another snapshot by then. The expectation is the caller's, never read from the record, which is what is being checked. The files are not digested again at every restore: the store is billet's, writable by nobody else and its files 0444, the host Firecracker's threat model trusts, and digesting a guest's memory would add about 0.7 s per GiB to a restore that takes under half a second (Go's SHA-256 ran at 1.4 to 1.5 GB/s on the reference node's EPYC 7763 from memory, 2026-10-22, so more from a cold disk); a golden moved to another node is digested on arrival (#508, item 5).
  - **The disk is the snapshot's, read before anything is claimed** (`goldenOf`): a record naming no disk or no generation, or a generation of another image than the restore spec's (compared before the `@`, so a tier naming `@verified` restores its own image's golden), is `errSnapshotIncompatible` with no jail, clone or VMM made. The spec's image then becomes the record's generation, so the kernel is the one the golden was verified against, and the root disk is `CloneGolden` of the record's disk rather than a clone of the tier's image.
  - **Checked before linking:** `placeSnapshot` reads the record through the held snapshot directory, judged as the other published files are and read in full up to a bound. Unknown fields and other formats are refused. It compares the record with this host, using the digest of the guest kernel this restore resolved. It also requires the restore spec's vCPUs and memory to equal the record's, because the snapshot fixes the guest's shape and admission charges by the spec. Because the state file is what the captured VMM wrote, and Firecracker restores as many vCPUs as it says, `restore` also asks the freshly started VMM for `/machine-config` after the paused load and refuses (`errNotRestorable`) a guest of another shape before giving it metadata or resuming it.

**A pid file is read as a file and nothing else (`readPIDFile`).** It sits in the jail root, so the jailed account can replace it with a FIFO (a plain read then never returns, under the lease's locks) or a link. It is opened with `O_NOFOLLOW|O_NONBLOCK`, refused unless regular, and refused, not truncated, past 64 bytes.
  - **Refusals:** a mismatch, a missing record or an unparseable one is `errSnapshotIncompatible`, naming the field. A record that cannot be read is could-not-tell.

**A restore loads paused, links its snapshot read-only, and is configured only by the jailer.** `Restore` takes `Launch`'s whole path (lease lock, lifecycle record, claimed jail, clone, unwind) and changes only the last step. The published `snapshot.state` and `snapshot.mem` are hard-linked into the chroot after it is chowned, as the kernel is, and are never chowned themselves, because every fork of a golden maps the one memory file and a jailed uid that owned it could rewrite what every later fork resumes from. `placeSnapshot` works through descriptors: the snapshots directory and the snapshot's own directory are opened without following a symlink and must be owned by the account billet runs as and writable by no one else, each file is opened for its identity alone through `regularfile.OpenIdentityAt` (O_PATH on Linux, so a device published by mistake is never opened) and judged through that descriptor (a regular file, mode 0444, owned by billet), then linked by `linkat` relative to the directories held, and the link is then proved to be that inode. Absent, a symlink, or the wrong shape is `errSnapshotNotPublished`; an inspection that failed for any other reason is returned without that sentinel, because could-not-tell is not no. **A teardown deletes a tap only when the kernel proves it is billet's.** `addTap` creates every tap with `user <jail uid>`, and the kernel reports that owner in `/sys/class/net/<tap>/owner` for as long as the device exists (a device that is not a tap has no such file and reads as -1; verified on the reference node, where each `bt-N` reads its jail's uid). `removeTap` is the one decision, used by Destroy, the unwind and orphan cleanup (`removeTapLocked` from `releaseOrphaned`), and it returns what must stay claimed rather than a yes or no: no claim on the name, or one naming another jail, deletes nothing; no device deletes nothing and the name goes back; a device whose owner is not in the jail uid range, or is a jail uid another lease holds, is left alone and its name kept (a launch handed it would fail on the device, `errTapTaken`); a tap owned by any jail uid, whoever holds that uid now (billet creates a tap only under a name it claimed, and this jail holds that name's one claim, so such a tap is this jail's or a leftover of an earlier holder whose jail is gone), or by an out-of-range uid whose claim names this jail (a range changed under a running microVM), is deleted, and its name goes back only if it went; a device with no owner, or one outside the range that is not this jail's, is left and its name kept; a claim or owner that cannot be read deletes nothing, keeps the name and says could not tell. `claimedBy` reports a claim it cannot read rather than releasing from an incomplete inventory. Only the name is ever kept, as before this rule; that a kept name is still reaped once its jail is gone, and that the uid owning a stuck tap can be handed out again, are properties of the claims as a whole, tracked in #522. So a launch that fails before its tap (the clone, the growth, the build, placing a snapshot) needs no marking at all: the device under the name is absent or somebody else's, and every later teardown asks the kernel again. There is no second record to fall out of step with the device after a crash, a failed write or a rollback to an earlier billet, which deletes a tap under its claim by name exactly as before. Earlier designs that recorded "no tap made" in the jail's record, then in a mark beside the claim, each left a window where a teardown read stale evidence; review found both. A link that would cross filesystems is refused rather than copied, since a copy writes the whole memory again and loses the page cache the forks share (measured on 2026-10-16, v1.16.1: ten forks of a 2 GiB guest were 227 MiB PSS together). `restore` always loads with `resume_vm: false`, then checks that the VMM reports `Paused` under the jail id, puts the lease's MMDS document, resumes and confirms `Running`, because the MMDS data store is `{}` after any load (measured). Nothing configures logging or metrics after the jailer's `--log-path`, because Firecracker answers both with 400 once a snapshot is loaded (measured). `network_overrides` points the restored guest at the tap billet allocated, and the `restore` primitive can also pass `vsock_override` for a socket of its own (both measured to work), though `Restore` sets no vsock yet because a cold launch configures none, and `clock_realtime` only corrects a guest that keeps time on `kvm-clock`: with the guest kernel's default `tsc` it was accepted and changed nothing (measured). A restore never grows the root disk, because the restored kernel has it mounted at its captured size. Writing a Full snapshot answers only after the memory is written and fsynced (4.0 s for 2 GiB), so `capture` runs that one call on `snapshotTimeout`, not `apiTimeout`. Restored forks keep the golden's MAC and address, so more than one on a shared bridge needs the per-workspace network namespaces of #510. `TestRealFirecrackerRestoresACapturedMicroVM` restores a captured guest through the real jailer (2026-10-16 on the reference node: 334 ms from request to running, 224 ms of it the clone).
