# The controller claim, locks, fences and the watermark

Part of the `billet-state` skill. Each rule is stated in full, with the measurement or incident behind it.

**On a shared ledger the claim authorises the migration, not the directory flock.** A second PostgreSQL host takes its own directory's lock happily, so a server about to be refused as a second controller, and `billet check` run from that host, upgraded the shared schema on the way to finding out. A non-admin open takes the controller exclusion before it migrates and is refused with `ErrControllerHeld` at the open. An operator command still migrates an unheld ledger and gives the exclusion straight back, or every `billet local backup` would be a window in which no control plane can start.

**The claim's epoch is a fence read inside every write transaction.** `ClaimController` records the epoch after its own transaction commits; `checkLeadership` re-reads `controller_claim` on every later `Tx` before `fn` runs and returns `ErrLeadershipLost` if it moved. It is exact rather than advisory because writers already serialise (SQLite's write lock at BEGIN IMMEDIATE, `pg_advisory_xact_lock` in `beginWrite`). Three things it must not do: read `sql.ErrNoRows` as permission (this handle claimed, so the row existed); read a storage error as evidence either way (it refuses as the storage fault); or ask a handle that never claimed. The deployment binding (`ErrForeignLedger`) is written in the same transaction as the epoch, measured: split, a process pointed at another deployment's rows advanced the epoch, was refused, and fenced the real controller out of its own ledger on the way past.

**Refusing the write is not stopping the process.** Every background writer is patient with an error it cannot classify, which is right for a blip and wrong here: a replaced controller would go on polling GitHub and running the cleanup loop that calls `Runner.Destroy`, which touches no ledger. `markFenced` sets the flag and closes `LeadershipLostSignal` at the same instant; `internal/app`'s `stopWhenReplaced`, started by `BecomeController`, cancels the plane, `retryCleanup` refuses once fenced, and a fenced plane exits non-zero without destroying compute, closing its session or handing back capacity, because a successor demonstrably exists and performs all three. An unreadable claim deliberately does not abandon: it is no evidence of a successor, and the destroys skipped are for jobs GitHub already concluded. Cost measured: one single-row read per write, 8.3µs to 15.8µs on SQLite, 419µs to 585µs on loopback PostgreSQL, for an empty transaction.

**An election is a process that waits for the claim.** On PostgreSQL the exclusion is a session advisory lock, so a controller is dead when its session is, decided by the database; there is no lease, renewal, timeout or failure detector. `server.controllers: active-passive` makes a refused controller wait in `AwaitController`, which waits out `ErrControllerHeld` and nothing else. A standby is the control plane stopped at one call: everything authoritative is a method of the `app.Controller` that only `ControlPlane.BecomeController` returns, so a step taken before the claim does not compile (`internal/app/proofs_test.go` holds that nothing else makes a `Controller` or its proofs); `alloc.New` stays in `app.OpenControlPlane`, before it, so a bad tier stops the process at startup. `READY=1` is sent before the wait or systemd kills the standby at `TimeoutStartSec`. The per-transaction schema re-check comes off before the promotion migration, or a standby cannot promote onto a ledger no controller had migrated.

**A promotion is as fast as the database's keepalives, and that is the operator's to set.** The election is a session advisory lock, so a partitioned leader holds the claim until PostgreSQL notices its TCP session is dead: with the server defaults (`tcp_keepalives_idle` two hours) a standby waits hours. `scripts/promotion-rehearsal.sh` runs the pair against `postgres:18-alpine` with `tcp_keepalives_idle=10 tcp_keepalives_interval=5 tcp_keepalives_count=3`, partitions the leader with `docker network disconnect`, and records partition-to-promotion and the old leader's exit and restart as a standby when the partition heals; the numbers are in `docs/reference/records/host-rehearsals.md`.

**Locks and fences are four different things.** The directory lock excludes a second control plane. `LockDeployment` excludes a second process on the same deployment identity (a copied state directory locks happily, because a copy is a different inode); failing to place it is an error rather than a downgrade (`allow_unlocked_deployment` is the explicit opt-in), it never lives in a cache directory (unlinking a held lock file detaches the path from the inode and the next process locks a fresh file), a shared `lock_dir` must be setgid and the lock's gid must match the directory's, and it is claimed before `state.Open` or a process about to be refused first migrates the ledger. The maintenance fence closes the ledger to new handles and to one already open (`Tx` and `View` consult it on entry); `WriteMaintenanceFence` reports whether this call created it, because only the creator may clear it. `WriterBarrier` proves a transaction that began before the fence has finished. `PeekLedger`, `PeekAdmission`, `PeekMigrations` and `PeekDeploymentID` read without a lock, a migration or the fence, for callers that hold the lock already.

**The release watermark refuses a proved downgrade at every open, and only the control plane raises it.** Migration 48 adds the `release_watermark` singleton and `nodes.highest_release`. Every `Open*` takes `...OpenOption`; `WithRunningRelease` names the binary, and an open that names nothing gets neither the check nor the record (which is what every test opening a throwaway ledger wants; `internal/app/ledger.go` passes it on every mode, the control plane's three and the operator and report opens, asserted structurally by that package's test; the decision open alone names no release, on purpose). `enforceReleaseWatermark` runs after migrate or verify, guarded by `releaseWatermarkApplied` because a standby or a probe may be looking at a schema before 48: a proved older release is `ErrReleaseBehind` for any handle (proved through `version.Compare`, which orders `v0.9.1` and `0.9.1` alike from v0.9.2 on; before that a release binary's bare `0.9.1` was could-not-tell against everything and the mark was neither enforced nor, being gated on `IsRelease`, ever recorded on a release binary, measured 2026-09-05); a proved newer one is recorded by NOBODY AT OPEN and by `ClaimController` inside the same transaction as the binding and the epoch (`raiseReleaseWatermarkIn`, so a failure to record leaves no claim and no published epoch behind), for a handle whose `openMode.records()` (not admin, not standby, not the maintenance probe) or a promoted standby (`DB.recordsRelease`), because a newer binary pointed at a foreign ledger must be refused by the binding with the mark untouched; could-not-tell records nothing. A revalidating handle re-reads the mark inside every write transaction (`checkReleaseWatermarkIn`, beside the schema re-check), since an older admin handle open across a newer controller's claim would otherwise write. `SetReleaseWatermark` is the one write that lowers it, allowed on a maintenance handle and, on PostgreSQL where that handle is a read-only probe, on an admin handle. `OpenPostgresProbe` is the standby's open with the fence bypass: verify-not-ahead, no claim, no migration, every `Tx` refused, for the host transaction's probe on an external ledger.

**A controller's retirement is one row the two controllers contend for, and a `done` row is never deleted.** Migration 51's `controller_retirement` (primary key the deployment; `retiring` and `survivor` are INVENTORY names; `run` the reserving holder; `state` in `reserved`, `intent`, `done`; `transition_id` minted at the reservation and immutable; `reserved_at`, `updated_at`, `completed_by`, `completed_at`) is written by `state.ReserveRetirement` BEFORE a request collects any evidence, read-then-write inside one `DB.Tx` so the single writer decides between two requests: no row inserts, this host's `reserved` row is adopted (the run re-bound, the id and the reservation time kept), a `done` row refuses `ErrRetirementDone` for the life of the deployment (a deployment that retired one controller has no survivor for a second), anything else `ErrRetirementReserved` with the row so the caller's sentence names the holder. Every later write is conditional on the state it leaves and answers `ErrRetirementMoved` on zero rows (`AdvanceRetirementToIntent` by host, id and `reserved`; `CompleteRetirement` by host, survivor, id, reservation and `reserved|intent`, or a RECONSTRUCTION from the document on positive absence, since a ledger restored from before the reservation still belongs to a deployment that retired this host; `ReleaseRetirement` by host, run and `reserved`, the one delete). The state words reach the statements as parameters (`RetirementReserved` etc.), never as literals, and the reservation time is compared as the STRING the row holds, never re-formatted. `ReadRetirementIn` serves `rollout.Store.StatusSnapshot`, so `rollout status --json` reports the row (`retirement`, null when none) from the same read transaction as the binding. `ErrSchemaAhead` is the typed ahead-schema refusal `refuseUnknownVersions` now wraps, so a retiring host at R beside a survivor that migrated to R+1 maps it to `pending` rather than refusing.
