# Migrations and the query set

Part of the `billet-state` skill. Each rule is stated in full, with the measurement or incident behind it.

**Migrations are published bytes.** A migration is identified by its version and a sha256 over its statement bytes (the text between `-- +billet:statement` and `-- +billet:end`, `0`-separated), and that sum sits in every deployment's `schema_migrations`; `Open` refuses a recorded sum that disagrees. So that text may never change, reformatting included: commit `ef84c7b` added two comment lines inside migration 1's `CREATE TABLE` and every ledger written before it stopped opening, found on the reference host. Migrations 1 to 42 keep the tab indentation they inherited from Go raw strings; it looks wrong and it is correct. `migrationsAreFrozen` in `migrationfreeze_test.go` holds every published sum; when it fails after a change to an existing file, revert the file, never the table. `.gitattributes` pins the files to LF because a checkout conversion changes every checksum.

**The markers are billet's own and a near miss is refused.** A format a third-party tool recognises is one it may normalise. A padded open marker would silently skip the statement after it and a padded close marker silently join into the one before, so `parseMigrationStatements` checks for that first. The parse error is stored on the `timeline` that `loadTimeline` returns and surfaced by `timeline.require()`, not fatal at construction, because a guard that dies during construction never runs; every test iterating the set must ask whether it loaded or it passes vacuously (found by mutation). `checkStatement` runs in production on every open, so a new refusal there is a flag day; a rule about what a new migration may contain belongs in a test.

**Versions are dense from 1 and that is load-bearing.** `state.LatestSchemaVersion()` is one `int` in the release manifest, and the upgrade fence refuses a candidate below the installed ledger's maximum; that is a sound proxy only while versions are dense. A binary carrying `{1..42, 44}` and a ledger holding the same both say 44, the fence passes, and a later binary applies 43 after 44 there and before 44 on a fresh deployment. `TestMigrationVersionsAreDenseFromOne` asserts the whole property; the weaker "above the published maximum" was vacuous in every green tree and permitted the gap, measured. `RefuseUnknownVersions` is the one cold reader (the restore planner calls it before any ledger is open), so it calls `sqliteTimeline.require()` itself; ungated it answered from an empty set and accepted an archive whose applied set was empty.

**The PostgreSQL timeline is derived.** DDL is the only unportable half (`STRICT`, `CHECK (x IN (0,1))` booleans, table rebuilds around SQLite's `ALTER` limits), so `pgmigrations` carries a twin of every file with the same version and name and its own checksum. `TestEveryPostgresMigrationIsItsSQLiteTwinTranslated` re-derives four declared substitutions and compares statement bytes both ways, lexically aware rather than by regexp (a global replacement would rewrite `SET kind = 'INTEGER'` and bless it). Nothing compares a checksum across timelines.

**One query set serves both engines, generated once with the PostgreSQL engine.** With integer casts spelled `BIGINT`, sqlc's two engines emit byte-identical Go differing only in `?N` versus `$N`, and modernc.org/sqlite executes `$N` correctly, so a `$N` constant runs on both and a `?N` constant does not. sqlc's schema is the migration directory itself, so a migration is an input to code generation: run `make sqlc` after adding one, and `sqlc diff` in CI catches forgetting. A statement must be portable (`max(a, b)` is a scalar on SQLite and an aggregate on PostgreSQL; `GREATEST` is the trap facing the other way); the answer is the portable spelling, never a second query set. Casts are `BIGINT`, never `INTEGER` (`int4` on PostgreSQL, `int64` on SQLite; `TestEveryIntegerCastIsBigintSoBothEnginesAgree`). Query files are ASCII, because sqlc rewrites `@named` parameters on byte offsets and one em dash turned `force_destroy` into `roy` in an error naming neither file nor character (`TestQueryFilesAreASCIIOnly`). Never `SELECT *` (`-- wildcard-ok: <reason>` is the escape; `TestNoQueryUsesAWildcardProjection`). Closed vocabularies reach a statement as parameters, except the two Go slices `sqlc.slice()` cannot express on SQLite (`forceDestroyPhases`, `quiescencePhases`), which are pinned both ways by tests.

**`ReadOps` and `WriteOps` are hand-written on purpose.** sqlc emits one `*Queries` carrying every method; binding that to the reader would turn the compile-time read/write split into a runtime one. `ReadQueries` returns `ReadOps` through `readOnlyDBTX`, whose `ExecContext`/`PrepareContext` refuse; the generated `DBTX` demands `PrepareContext` even under `emit_prepared_queries: false`, so `Querier` stays two methods and is adapted. Only `state`, `alloc` and `rollout` may import `ledgerdb`, for types; `forbidigo` bans `ledgerdb.New` outside `internal/state`'s direct members.

**A bounded list is written in one statement, packed, never one INSERT a row.** A write transaction holds SQLite's only writer slot or PostgreSQL's advisory write lock for every round trip it makes, so a loop of single-row INSERTs is paid for by every other writer, once per row and per network round trip. A portable statement cannot take a list (sqlc's `sqlc.slice()` and `:copyfrom` are not available on both engines), so `RecordJobDestinations` (migration 59, up to 257 rows a job) takes its rows as one string of fixed-width records built by `alloc.packDestinations` and cuts it apart with a recursive CTE whose every step carries the REST of the string: both engines find a character offset in TEXT by scanning from its start, so indexing into the whole string is quadratic. Measured 2026-10-09 on an M2 Max, a 257-row report against PostgreSQL 18 on loopback took 18 ms one INSERT a row, 57 ms indexed and 14 ms carrying the rest, and on SQLite 3.7 ms one a row and 4.4 ms carrying the rest; the single statement wins by 256 round trips on any real network. `TestReadOpsHoldsExactlyTheQueriesThatOnlyRead` classifies a statement that opens with `WITH` as a mutation when INSERT, UPDATE, DELETE or REPLACE appears anywhere in it outside a comment.

**The gate that proves the set still fits the schema is `TestEveryGeneratedQueryPreparesAgainstTheMigratedSchema`.** It prepares every query constant against a real migrated ledger. SQLite's prepare resolves a missing column, a missing table, a syntax error and an `ON CONFLICT` whose unique index a migration removed (PostgreSQL defers that to EXECUTE), and sqlc models no indexes at all, so nothing else here would catch that class.

**Raw SQL is banned mechanically.** The `rawsql` analyzer reports any call executing SQL from Go across the module; 25 sites carry `//billet:ignore rawsql` and a row in `internal/state/queries/README.md` (the inspection querier's admitted forwarders and its never-connecting refusal row, the pragma reads, `PRAGMA table_info`, the `sqlite_master` queries sqlc has no catalogue for, `PeekLedger`'s dynamically quoted `COUNT`, `VACUUM INTO`, the bookkeeping DDL, the migrator executing published bytes, `readOnlyDBTX`'s forwarders). `TestTheAllowlistTableNamesEveryRawStatement` compares the two in both directions.

**Migrations 53 to 55 carry #226's cache evidence and outcomes.** 53 (`job_cache_identity`) adds the JobStarted identity (`job_owner`, `job_repository`, `job_workflow_ref`, `job_event`) to `pool_runners`, and the completion's own `job_id` and identity to `pending_completions`, so a restarted controller compares two independent records rather than rebuilding one from the other; `StartPoolRunner` and `BindPoolRunnerJob` fill an identity once and never replace it, and the completion upsert keeps it for a redelivery of the same message. 54 (`cache_blocks_by_kind`) rebuilds the kill switch as `cache_blocks(kind, scope_type, owner, repository, disabled_at)`, carrying every older row as `actions` and using `'*'` for every cache; `ListCacheBlocks` is a `ReadOps` query. 55 (`build_cache_observations`) adds `sticky_cache`, `git_cache`, `bazel_cache` and `go_cache` to `leases` and `job_history`, first observation kept by the statements, and `ListCacheOutcomes` windows the history on `assigned_at`. The rewind tests in `state_test.go` drop each of these, because an upgrade test that rewinds to an old version must take back every column and table added since or the replay fails as a duplicate column.

**The ledger is not authoritative for cache generation pointers.** Those live in the site store (`billet-storage-and-cache`).
