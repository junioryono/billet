# The engines, transactions and open modes

Part of the `billet-state` skill. Each rule is stated in full, with the measurement or incident behind it.

**The engine is a seam and the invariants are not.** Four things hold above the `backend` interface whichever engine is under it: one authoritative process; one writer within the process (a single-connection writer pool); durability verified rather than assumed (`Open` reads the pragmas back and fails closed if `journal_mode` is not WAL, which is what catches a network filesystem); and contention retried rather than returned. SQLite must be on local storage.

**Every write transaction begins IMMEDIATE, and that is not tuning.** A deferred `BEGIN` takes its read snapshot at the first read and asks for the write lock later; once a second writer exists, anything committing in between leaves the first holding a snapshot SQLite cannot promote (`SQLITE_BUSY_SNAPSHOT`, error 517, which `busy_timeout` cannot rescue). Contention is matched on SQLite's error code, never its message, and the two callers get opposite patience: a control plane retries until its context ends (`busyRetryInterval`), an operator command gives up after `adminBusyLimit` because a person is waiting. A read-only operation belongs on `DB.View` (the query-only reader pool), never `DB.Tx`, or it reserves the single writer slot while it scans; `CertRevokedFor` and `Headroom` were once in contention with scheduling for that reason. On PostgreSQL the writer pool's `lock_timeout` is 50ms so contention comes back to `beginWrite`'s loop, and that loop covers the BEGIN and the advisory lock only; the migration transaction is the one write that waits for its locks instead (`SET LOCAL lock_timeout = 0` in `beginMigration`), bounded by the 30s startup budget wherever it runs, promotion included, because DDL takes locks the advisory lock does not cover and a 50ms cap failed the open under CI's parallel schema builds (#75). A migration cut off at that deadline names the migration, the budget and, per engine, what to look at. `DB.Reader()` returns a narrow `Querier`, never `*sql.DB`.

**A ledger writer reaches no network.** The depguard rule `ledgerwriters` refuses `net/http`, `os/exec` and every upper layer inside `internal/state`, `internal/alloc` and `internal/rollout`, because a call inside a transaction holds the writer slot for as long as it takes.

**Three open modes, and what each may do.** `Open` is the control plane: it takes the exclusive directory lock (`billet.lock`, a flock so a crash releases it) and migrates. `OpenAdmin` is an operator command: it proceeds without the lock when a plane holds it (the lock stops two control planes, not two processes), still takes it when free (a fresh install runs `ca issue` before any server), and when it cannot take it verifies the schema instead of migrating, returning `ErrSchemaBehind` naming which side to restart, then re-verifies inside every transaction. `OpenMaintenance` is the one typed entry that crosses the maintenance fence (`billet.maintenance`), used by the host-upgrade probe and by `local recover`'s seal; `OpenAdmin` honours the fence. `OpenPostgresStandby` holds no exclusion and refuses every `Tx` with `ErrStandby` until `ClaimController` succeeds, because the epoch fence protects a controller that was replaced and does nothing for one that never claimed. `OpenInspect` and `OpenPostgresInspect` (`inspect.go`) are the fourth mode, a construction path of their own and never a flag on the admin one: they validate everything an open validates (the migration set readable first, the schema exactly the binary's with an interior hole or an edited early checksum refused by name, the fence, the watermark, the binding through the caller's `verifyLedgerIdentity`) and mutate nothing (no `MkdirAll`, no `Chmod`, no directory lock, no integrity scan, no claim, no migration, no watermark write), on SQLite through `mode=ro` plus `query_only` on both pools and never `immutable=1`, on PostgreSQL through `default_transaction_read_only=on` on both pools with the durability check told not to refuse its own read-only writer; `Tx` answers `ErrInspect` before any transaction begins and so does `ClaimController`, before the backend's advisory lock is asked for; an absent ledger is `ErrNoLedger` from an `Lstat` and never a created file; the read-transaction revalidation of an unlocked handle is kept, so a version written after the open refuses the next `View`, and an inspection's `View` re-reads the release watermark inside its transaction too (`checkReleaseWatermarkIn`), so a newer release that claimed the same-schema ledger after the report's open refuses the next read as it refuses a fresh open. A REVALIDATING READ RE-CHECKS THE SCHEMA UNDER THE POLICY THE HANDLE WAS ADMITTED WITH: a standby and the upgrade probe (`db.standby`) use `verifySchemaNotAhead`, every other unlocked handle the exact `verifySchemaIn`; `View` once applied the exact check to every unlocked handle, and the watermark check inside a standby's or probe's own open reads through `View`, so a stamped candidate over a ledger one migration behind was refused `ErrSchemaBehind` at its open before it could claim and migrate, and every PostgreSQL host upgrade carrying a migration rolled back at the probe (found by review with migration 50, the first migration since the watermark check; `TestAStandbyRevalidatesUnderItsOwnSchemaPolicy`, `TestThePostgresProbeReadsALedgerOneMigrationBehind`). AN INSPECTION'S READS ARE EXPLICIT READ ONLY, REPEATABLE READ TRANSACTIONS AND NOTHING ELSE (`readTxOptions`): PostgreSQL's `default_transaction_read_only` is a session setting a statement can undo (measured 2026-09-09: `set_config` on a pooled connection, then an UPDATE, wrote a row through the read-only pool; inside a transaction begun READ ONLY the same UPDATE is SQLSTATE 25006), so `Reader()` on an inspection refuses (`inspectReader`), the package's own untransacted reads go through the unexported `bareReader()` that `TestEveryUntransactedReadIsAccountedFor` inventories beside `Reader`, and `View` hands its callback `inspectQuerier`, which admits a statement only when it is EXACTLY one of the statements sqlc generated for `ReadOps` (`generatedReads`, learned once by calling every `ReadOps` method against a recording adapter) and then holds that text to its shape (the `-- name: X :one|:many` header, X a `ReadOps` method, a non-empty body beginning SELECT or WITH, no session-effect function such as `set_config` or `pg_advisory_lock`), because a callback holding the bare transaction could COMMIT it and write in autocommit, or take a session advisory lock rollback never releases, and because a grammar alone is not enough: PostgreSQL decodes `U&"pg\005ftry_advisory_lock"` to the function a substring scan never sees; `TestTheInspectionAdmissionMatchesTheGeneratedQueries` reads every generated constant and holds that the rule admits every read, refuses every other statement, and that the recorded set is exactly the reads' constants. A refused `QueryRowContext` answers with a `Row` from `refusalRows`, a database whose connector never connects, so a refusal costs no ledger connection (four `View`s refusing together deadlocked a four-connection pool when the refusal ran a statement on it, and a statement run inside the transaction would abort a PostgreSQL one); `TestARefusedRowBorrowsNoConnection` holds it. `ScaleSets` reads through `View` for the same reason. The `onOpenSideEffect` seam in `state.go` names every mutation an open can make (`mkdir`, `chmod`, `lock`, `integrity`, `claim`, `migrate`, `watermark`) and `inspect_test.go` asserts an inspection fires none, because the state afterwards cannot tell a mutation undone from one never made; the directory-lock fixtures run against a real second process (`TestInspectHelperProcess`). Measured with the bundled driver (2026-09-09): a read-only open of a cleanly stopped WAL ledger CREATES `billet.db-wal` and `billet.db-shm` owned by the opener and leaves them, a crashed ledger's WAL-resident row is visible, and a live controller's later commits are visible to a later `View`; that is why `billet rollout status` runs as the identity directory's owner and as nobody else: root re-executes itself as the owner, the owner runs in place, and on a SQLite ledger any other account (an operator with group access, say) is refused before the open, since its sidecars would be that account's exactly as root's would.

**An open's own startup budget is a deadline, and a caller can tell it from its own.** `startupTimeout` bounds the ping, the backend's preparation, the schema check and a migration, and `TestAnOpenThatTimesOutOnItsOwnBudgetSaysSo` pins that it surfaces as `context.DeadlineExceeded` (a listener that accepts and answers nothing). That is what lets the retirement's tail read a deadline NEITHER of its own contexts set as the ledger being out of reach, rather than as a refusal.

**Unreachability is a property of the ERROR, never of the step that produced it, and its rule is MEASURED.** `state.Unreachable(err)` is written from `TestUnreachableIsMeasuredAgainstPgxsOwnShapes` (pgx v5.10.0 against PostgreSQL 18, 2026-09-13, every case through database/sql, each asserting the SHAPE it produced as well as the verdict), because two of its rows are what reading alone gets wrong: a WRONG PASSWORD (28P01) and a MISSING DATABASE (3D000) arrive INSIDE a `ConnectError`, and `context.DeadlineExceeded` satisfies `net.Error` (pgx wraps it in `errTimeout`). So the order is the server's own `PgError` FIRST, then cancellation, then a certificate the CLIENT refused (a `ConnectError` with no SQLSTATE under it, the same shape of actionable mistake as the password), then `ConnectError` / `ErrBadConn` / `ErrUnexpectedEOF` / `net.Error`. THE AVAILABILITY SQLSTATES ARE AN ALLOWLIST, never a class prefix: `08001`, `08003`, `08006`, `08007`, `53300`, `57P01`, `57P02`, `57P03` — because class 08 also holds `08004` (the server refusing this client) and `08P01` (a protocol violation), and class 57 also holds `57014` (a statement the server cancelled, which a `statement_timeout` produces) and `57P04` (a dropped database), every one of which is the caller's to fix. A failed ping is not the place for any of this: `file is not a database (26)` is positive evidence the ledger answered and is broken. EVERY ONE OF THOSE QUESTIONS IS ASKED OF THE WHOLE ERROR, and the same way for each: `errors.Join` puts unrelated failures beside each other and billet's own opens join a startup failure with their close, so `Unreachable` requires EVERY INDEPENDENT BRANCH of the tree to establish an availability failure (each branch judged with the evidence of the nodes above it, because `ConnectError` and `net.OpError` both unwrap and a split that looked only underneath would discard the measured shapes) and `OnlyCause` requires every leaf to be the sentinel. A rule that asked one of them loosely would let an outage joined with this host's pools failing to close read as a row a survivor may finish, hiding a fault that host must fix. `ErrSchemaAhead`, `ErrSchemaBehind` and `ErrReleaseBehind` are the other half of a retirement tail's pending list — a ledger that answered and said something this binary may not write — and everything else refuses.

**`OpenPostgresCompletion` writes one row and is not a control plane.** It is the retired host's open: `admin` plus `completion`, which takes the directory lock, CLAIMS NOTHING and MIGRATES NOTHING, verifies the schema is exactly this binary's (ahead and behind both refuse, which is what lets the caller hand the write to the survivor), checks the watermark without raising it, and revalidates inside every transaction. An admin open would have done both whenever the controller exclusion happened to be free — a survivor that is down at that moment is exactly when — and a host whose controller has been retired taking the deployment's claim, or migrating a shared schema with a binary frozen at the release it retired on, is the opposite of what a retirement is for. It is a construction path of its own beside `OpenAdmin` and `OpenInspect`, never a flag on one, and `records()` excludes it.

**The writer slot is observed from inside `DB.Tx`, and the observer must return at once.** `DB.Observe` sets a `state.Observer` (#356 Phase 6), told how long each write waited for the single writer slot (`WriteWaited`, from before `beginWrite` to the slot won), how long it held it and whether it committed (`WriteHeld`, after the commit or the rollback, so the hold ends when the transaction does), and each busy retry (`WriteRetried`, beside the `onBusyRetry` hook). It is the measurement the writer slot's saturation is judged by. The interface is declared here in plain types and satisfied by `internal/metrics` structurally, so the ledger imports no metrics library (`ledgerwriters`). The observer is called on the writer's own goroutine, the wait and the retries before the transaction exists and the hold after it ends, so an implementation must return at once and must never reach the ledger. Nil is the default and tells nothing. It is atomic, because the endpoint attaches it after writers already run. A read through `View` uses no writer slot and is told nothing. Tests: `internal/state/observer_test.go` (both outcomes, removal, and a real busy retry against a second handle holding the slot).
