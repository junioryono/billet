# The ledger

## What this area is

`internal/state` owns the durable control-plane store: `DB`, the open modes, transactions, the migrator, the locks and fences, the controller claim, admission, pending completions, force-destroy records and the cache kill switch. SQL lives only in `internal/state/queries/*.sql` (including `internal/alloc`'s and `internal/rollout`'s), compiled by sqlc (pinned, `SQLC_VERSION`) into `internal/state/ledgerdb` and bound by `internal/state/queryset.go`. Migrations are files in `internal/state/migrations` (SQLite) and `internal/state/pgmigrations` (PostgreSQL), 47 of each, discovered by `go:embed`. `docs/reference/decisions/adr-008-state-backends.md` and `adr-009-controller-election.md` record the decisions.

## Rules

**The engine is a seam and the invariants are not.** Four things hold above the `backend` interface whichever engine is under it: one authoritative process; one writer within the process (a single-connection writer pool); durability verified rather than assumed (`Open` reads the pragmas back and fails closed if `journal_mode` is not WAL, which is what catches a network filesystem); and contention retried rather than returned. SQLite must be on local storage.

**Every write transaction begins IMMEDIATE, and that is not tuning.** A deferred `BEGIN` takes its read snapshot at the first read and asks for the write lock later; once a second writer exists, anything committing in between leaves the first holding a snapshot SQLite cannot promote (`SQLITE_BUSY_SNAPSHOT`, error 517, which `busy_timeout` cannot rescue). Contention is matched on SQLite's error code, never its message, and the two callers get opposite patience: a control plane retries until its context ends (`busyRetryInterval`), an operator command gives up after `adminBusyLimit` because a person is waiting. A read-only operation belongs on `DB.View` (the query-only reader pool), never `DB.Tx`, or it reserves the single writer slot while it scans; `CertRevokedFor` and `Headroom` were once in contention with scheduling for that reason. `DB.Reader()` returns a narrow `Querier`, never `*sql.DB`.

**A ledger writer reaches no network.** The depguard rule `ledgerwriters` refuses `net/http`, `os/exec` and every upper layer inside `internal/state`, `internal/alloc` and `internal/rollout`, because a call inside a transaction holds the writer slot for as long as it takes.

**Three open modes, and what each may do.** `Open` is the control plane: it takes the exclusive directory lock (`billet.lock`, a flock so a crash releases it) and migrates. `OpenAdmin` is an operator command: it proceeds without the lock when a plane holds it (the lock stops two control planes, not two processes), still takes it when free (a fresh install runs `ca issue` before any server), and when it cannot take it verifies the schema instead of migrating, returning `ErrSchemaBehind` naming which side to restart, then re-verifies inside every transaction. `OpenMaintenance` is the one typed entry that crosses the maintenance fence (`billet.maintenance`), used by the host-upgrade probe and by `local recover`'s seal; `OpenAdmin` honours the fence. `OpenPostgresStandby` holds no exclusion and refuses every `Tx` with `ErrStandby` until `ClaimController` succeeds, because the epoch fence protects a controller that was replaced and does nothing for one that never claimed.

**On a shared ledger the claim authorises the migration, not the directory flock.** A second PostgreSQL host takes its own directory's lock happily, so a server about to be refused as a second controller, and `billet check` run from that host, upgraded the shared schema on the way to finding out. A non-admin open takes the controller exclusion before it migrates and is refused with `ErrControllerHeld` at the open. An operator command still migrates an unheld ledger and gives the exclusion straight back, or every `billet local backup` would be a window in which no control plane can start.

**The claim's epoch is a fence read inside every write transaction.** `ClaimController` records the epoch after its own transaction commits; `checkLeadership` re-reads `controller_claim` on every later `Tx` before `fn` runs and returns `ErrLeadershipLost` if it moved. It is exact rather than advisory because writers already serialise (SQLite's write lock at BEGIN IMMEDIATE, `pg_advisory_xact_lock` in `beginWrite`). Three things it must not do: read `sql.ErrNoRows` as permission (this handle claimed, so the row existed); read a storage error as evidence either way (it refuses as the storage fault); or ask a handle that never claimed. The deployment binding (`ErrForeignLedger`) is written in the same transaction as the epoch, measured: split, a process pointed at another deployment's rows advanced the epoch, was refused, and fenced the real controller out of its own ledger on the way past.

**Refusing the write is not stopping the process.** Every background writer is patient with an error it cannot classify, which is right for a blip and wrong here: a replaced controller would go on polling GitHub and running the cleanup loop that calls `Runner.Destroy`, which touches no ledger. `markFenced` sets the flag and closes `LeadershipLostSignal` at the same instant; `cmd/billet`'s `stopWhenReplaced` cancels the plane, `retryCleanup` refuses once fenced, and a fenced plane exits non-zero without destroying compute, closing its session or handing back capacity, because a successor demonstrably exists and performs all three. An unreadable claim deliberately does not abandon: it is no evidence of a successor, and the destroys skipped are for jobs GitHub already concluded. Cost measured: one single-row read per write, 8.3µs to 15.8µs on SQLite, 419µs to 585µs on loopback PostgreSQL, for an empty transaction.

**An election is a process that waits for the claim.** On PostgreSQL the exclusion is a session advisory lock, so a controller is dead when its session is, decided by the database; there is no lease, renewal, timeout or failure detector. `server.controllers: active-passive` makes a refused controller wait in `AwaitController`, which waits out `ErrControllerHeld` and nothing else. A standby is `runServer` stopped at one line: everything authoritative happens below `becomeController`, asserted structurally by `TestEverythingAuthoritativeHappensAfterTheControllerClaim`; `alloc.New` stays above it so a bad tier stops the process at startup. `READY=1` is sent before the wait or systemd kills the standby at `TimeoutStartSec`. The per-transaction schema re-check comes off before the promotion migration, or a standby cannot promote onto a ledger no controller had migrated.

**Migrations are published bytes.** A migration is identified by its version and a sha256 over its statement bytes (the text between `-- +billet:statement` and `-- +billet:end`, `0`-separated), and that sum sits in every deployment's `schema_migrations`; `Open` refuses a recorded sum that disagrees. So that text may never change, reformatting included: commit `ef84c7b` added two comment lines inside migration 1's `CREATE TABLE` and every ledger written before it stopped opening, found on the reference host. Migrations 1 to 42 keep the tab indentation they inherited from Go raw strings; it looks wrong and it is correct. `migrationsAreFrozen` in `migrationfreeze_test.go` holds every published sum; when it fails after a change to an existing file, revert the file, never the table. `.gitattributes` pins the files to LF because a checkout conversion changes every checksum.

**The markers are billet's own and a near miss is refused.** A format a third-party tool recognises is one it may normalise. A padded open marker would silently skip the statement after it and a padded close marker silently join into the one before, so `parseMigrationStatements` checks for that first. The parse error is stored on the `timeline` that `loadTimeline` returns and surfaced by `timeline.require()`, not fatal at construction, because a guard that dies during construction never runs; every test iterating the set must ask whether it loaded or it passes vacuously (found by mutation). `checkStatement` runs in production on every open, so a new refusal there is a flag day; a rule about what a new migration may contain belongs in a test.

**Versions are dense from 1 and that is load-bearing.** `state.LatestSchemaVersion()` is one `int` in the release manifest, and the upgrade fence refuses a candidate below the installed ledger's maximum; that is a sound proxy only while versions are dense. A binary carrying `{1..42, 44}` and a ledger holding the same both say 44, the fence passes, and a later binary applies 43 after 44 there and before 44 on a fresh deployment. `TestMigrationVersionsAreDenseFromOne` asserts the whole property; the weaker "above the published maximum" was vacuous in every green tree and permitted the gap, measured. `RefuseUnknownVersions` is the one cold reader (the restore planner calls it before any ledger is open), so it calls `sqliteTimeline.require()` itself; ungated it answered from an empty set and accepted an archive whose applied set was empty.

**The PostgreSQL timeline is derived.** DDL is the only unportable half (`STRICT`, `CHECK (x IN (0,1))` booleans, table rebuilds around SQLite's `ALTER` limits), so `pgmigrations` carries a twin of every file with the same version and name and its own checksum. `TestEveryPostgresMigrationIsItsSQLiteTwinTranslated` re-derives four declared substitutions and compares statement bytes both ways, lexically aware rather than by regexp (a global replacement would rewrite `SET kind = 'INTEGER'` and bless it). Nothing compares a checksum across timelines.

**One query set serves both engines, generated once with the PostgreSQL engine.** With integer casts spelled `BIGINT`, sqlc's two engines emit byte-identical Go differing only in `?N` versus `$N`, and modernc.org/sqlite executes `$N` correctly, so a `$N` constant runs on both and a `?N` constant does not. sqlc's schema is the migration directory itself, so a migration is an input to code generation: run `make sqlc` after adding one, and `sqlc diff` in CI catches forgetting. A statement must be portable (`max(a, b)` is a scalar on SQLite and an aggregate on PostgreSQL; `GREATEST` is the trap facing the other way); the answer is the portable spelling, never a second query set. Casts are `BIGINT`, never `INTEGER` (`int4` on PostgreSQL, `int64` on SQLite; `TestEveryIntegerCastIsBigintSoBothEnginesAgree`). Query files are ASCII, because sqlc rewrites `@named` parameters on byte offsets and one em dash turned `force_destroy` into `roy` in an error naming neither file nor character (`TestQueryFilesAreASCIIOnly`). Never `SELECT *` (`-- wildcard-ok: <reason>` is the escape; `TestNoQueryUsesAWildcardProjection`). Closed vocabularies reach a statement as parameters, except the two Go slices `sqlc.slice()` cannot express on SQLite (`forceDestroyPhases`, `quiescencePhases`), which are pinned both ways by tests.

**`ReadOps` and `WriteOps` are hand-written on purpose.** sqlc emits one `*Queries` carrying every method; binding that to the reader would turn the compile-time read/write split into a runtime one. `ReadQueries` returns `ReadOps` through `readOnlyDBTX`, whose `ExecContext`/`PrepareContext` refuse; the generated `DBTX` demands `PrepareContext` even under `emit_prepared_queries: false`, so `Querier` stays two methods and is adapted. Only `state`, `alloc` and `rollout` may import `ledgerdb`, for types; `forbidigo` bans `ledgerdb.New` outside `internal/state`'s direct members.

**The gate that proves the set still fits the schema is `TestEveryGeneratedQueryPreparesAgainstTheMigratedSchema`.** It prepares every query constant against a real migrated ledger. SQLite's prepare resolves a missing column, a missing table, a syntax error and an `ON CONFLICT` whose unique index a migration removed (PostgreSQL defers that to EXECUTE), and sqlc models no indexes at all, so nothing else here would catch that class.

**Raw SQL is banned mechanically.** The `rawsql` analyzer reports any call executing SQL from Go across the module; 21 sites carry `//billet:ignore rawsql` and a row in `internal/state/queries/README.md` (the pragma reads, `PRAGMA table_info`, the `sqlite_master` queries sqlc has no catalogue for, `PeekLedger`'s dynamically quoted `COUNT`, `VACUUM INTO`, the bookkeeping DDL, the migrator executing published bytes, `readOnlyDBTX`'s forwarders). `TestTheAllowlistTableNamesEveryRawStatement` compares the two in both directions.

**Locks and fences are four different things.** The directory lock excludes a second control plane. `LockDeployment` excludes a second process on the same deployment identity (a copied state directory locks happily, because a copy is a different inode); failing to place it is an error rather than a downgrade (`allow_unlocked_deployment` is the explicit opt-in), it never lives in a cache directory (unlinking a held lock file detaches the path from the inode and the next process locks a fresh file), a shared `lock_dir` must be setgid and the lock's gid must match the directory's, and it is claimed before `state.Open` or a process about to be refused first migrates the ledger. The maintenance fence closes the ledger to new handles and to one already open (`Tx` and `View` consult it on entry); `WriteMaintenanceFence` reports whether this call created it, because only the creator may clear it. `WriterBarrier` proves a transaction that began before the fence has finished. `PeekLedger`, `PeekAdmission`, `PeekMigrations` and `PeekDeploymentID` read without a lock, a migration or the fence, for callers that hold the lock already.

**The release watermark refuses a proved downgrade at every open, and only the control plane raises it.** Migration 48 adds the `release_watermark` singleton and `nodes.highest_release`. Every `Open*` takes `...OpenOption`; `WithRunningRelease` names the binary, and an open that names nothing gets neither the check nor the record (which is what every test opening a throwaway ledger wants; `cmd/billet/ledger.go` passes it on all six helpers, asserted structurally). `enforceReleaseWatermark` runs after migrate or verify, guarded by `releaseWatermarkApplied` because a standby or a probe may be looking at a schema before 48: a proved older release is `ErrReleaseBehind` for any handle; a proved newer one is recorded only when `openMode.records()` (not admin, not standby, not the maintenance probe) and by `ClaimController` at a standby's promotion; could-not-tell records nothing. `SetReleaseWatermark` is the one write that lowers it and is refused off a maintenance handle. `OpenPostgresProbe` is the standby's open with the fence bypass: verify-not-ahead, no claim, no migration, every `Tx` refused, for the host transaction's probe on an external ledger.

**The ledger is not authoritative for cache generation pointers.** Those live in the site store (`billet-storage-and-cache`).

## Measured facts

- `SQLITE_BUSY_SNAPSHOT` (517) appeared the moment operator commands were admitted alongside the plane, with deferred transactions.
- Leadership check cost: 8.3µs→15.8µs SQLite, 419µs→585µs loopback PostgreSQL, per empty write transaction.
- sqlc's two engines: byte-identical Go with `BIGINT` casts; modernc.org/sqlite binds `$N` positionally, a repeated `$1` once, and a `$2` appearing before `$1` correctly.
- A single em dash in a query comment shifted every parameter offset after it.
- Splitting the deployment bind from the epoch: the incumbent's next write came back "host-b now holds it at epoch 2".
- The lease deregistration column (migration 30), compute barrier (37), rollout (39-42), controller claim (44), deployment binding (45), CodeBuild sweep (46), holder incarnation (47), release watermark and highest node release (48).
