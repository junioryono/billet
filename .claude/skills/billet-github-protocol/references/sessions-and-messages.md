# Sessions, messages and runners

Part of the `billet-github-protocol` skill. Each rule is stated in full, with the measurement or incident behind it.

**The scale-set client is the answer to most protocol questions, and usually the only one.** The API is not documented elsewhere. Everything in `internal/scaleset` is translation (vendor types in, billet types out); `provision.go` reconciles one scale set per tier before any listener starts, `quiet.go` and `runner_lookup.go` find and remove runners. `internal/fakeactions` stands in for the service in tests and is deliberately not a simulator: it answers the handshake and serves what a test tells it to.

**A message session is single-holder, GitHub will not hand it over, and eight runs bracketed the wait between 60 and 92 seconds.** Opening a second session for a scale set whose first was abandoned answers `409 Conflict … RunnerScaleSetSessionConflictException … already has an active session`, measured against a real organization, and measured again on 2026-09-04 under a DIFFERENT owner with the same refusal: the conflict is the scale set's, not the holder's name, so a promoted standby on another host meets the same refusal and enters the same wait. How long a differently named successor then waits is NOT measured: only the original owner was followed through to an opening, because one abandoned session answers one owner's wait. `openSession` waits on `ErrSessionHeld` (`sessionRetryFor`) and returns every other reason at once; a control plane killed and restarted used to not start at all. Nothing is lost while it waits: GitHub queues a job for 24 hours with no runner available. The abandoned session was still refused at 60 seconds on each of eight runs on 2026-09-04 and open at 91 on three of them and 92 on the other five (`TestLiveSessionReplacement`, 30-second polls, so the expiry is bracketed rather than named), which is a measurement rather than a promise, so the wait stays a loop rather than a sleep.

**An unacknowledged message IS redelivered to a new session, and that is measured rather than assumed.** On 2026-09-04 a session holding one `JobAssigned` message was abandoned without being closed, and the successor was handed the same message id back on all eight runs. WHAT WAS COMPARED MATTERS: seven of those compared the id and the per-kind counts, and the eighth compared the job identities the message carries and found the same one assigned job — same run id, same stable workflow-job id, `runnerRequestId` zero on both deliveries. Every recovery path is nevertheless written to be safe without it: idempotence is what makes the redelivery harmless, and `internal/e2e`'s `TestARedeliveredAssignmentDoesNotStartASecondRunner` pins that a redelivered exchange after a restart starts no second runner and releases no adopted lease. The measurement also showed the successor's opening statistics reporting one assigned job and one BUSY runner for a job no runner had ever taken, which is one more reason statistics are recorded and not acted on.

**The message lifecycle is idempotent on billet's durable scheduler id.** GitHub's positive `runnerRequestId` when present, or a collision-free negative id assigned transactionally to the stable `jobId` when the direct-assignment path sends zero; zero is never an identity. `DeleteMessage` acknowledges a notification and does not decline a job; `AcquireJobs` is one-way with no decline or release, which is why a promise to GitHub cannot be revoked by a local timer (`billet-capacity`). A scale-set response that is not a subset of its request stops the listener, because no race produces it and a fresh session makes GitHub redeliver; an assignment with no escrow behind it declines and carries on, because ordinary races reach it.

**A scale-set runner is a pool member, not the job that caused scale-up.** GitHub registers a JIT runner into a scale set and may give it any job waiting there, so trust and cache scope are properties of the pool (wire version 12 is the floor for that reason), and `JobStarted` is the authoritative binding between a registration and the job it consumed. billet journals that binding separately from the launch, resolves completion through the physical runner's lease, and reconciles idle surplus to `TotalAssignedJobs`. A completion that names NO runner is a job cancelled before any runner took it (read in one controller's journal, 2026-09-22), and its request id is the launch identity of the runner launched for it, which GitHub may have given another job: when that runner is bound to a different job, or is busy with one not yet known (recovered after a restart, awaiting its delayed `JobStarted`), the completion is `detached` (`resolveActualJob`) and `handle` settles, records, tears down and acknowledges nothing on its lease, only marking the job finished; an idle launch runner is still retired by it. Before this, the cancellation tore down the runner mid-job (GitHub refused the removal), recorded `canceled` on its lease so the real result was later refused as a contradiction, and acknowledged its completion source; that journal holds 29, 82 and 59 mid-job removal refusals on 2026-09-17, 21 and 22 (#189). Scale-down removes the GitHub registration before destroying compute and keeps both when removal fails. GitHub does not requeue a job whose runner vanished after starting: its own README documents reassignment only for a job not acquired in time.

**JIT registrations are single-use and cannot update themselves.** Every JIT config GitHub mints carries `Ephemeral = True` and `DisableUpdate = True` (measured against the live API), which is why the runner-release deadline is billet's to watch (`billet-guest-images`). The registration is delivered off argv on every backend (`billet-security`), and a node may mint exactly the registration for a launch it holds.

**One target, one connection, so the connection is health-checked.** Each target's `scaleset.New` builds one retryable client, and every listener, JIT mint, describe and runner lookup of that target multiplexes over its HTTP/2 connection to the broker. The vendored client gives each HTTP attempt a 5-minute timeout and retries it four times, and Go's HTTP/2 client sends no health pings unless asked, so a half-open connection is reused by every attempt of every listener: on 2026-09-23 the organization target's six listeners heard nothing from about 15:58 to 16:16:40 UTC, their attempts failing at 5-minute intervals, until all six failed at one instant on one local port (`read tcp 10.0.0.1:54616->…:443: read: connection timed out`) and a new connection carried messages four seconds later. `newValidatedRetryableHTTPClient` sets `http.Transport.HTTP2` (`SendPingTimeout` 30 s, `PingTimeout` 15 s), which Go 1.26's bundled HTTP/2 honours (1.24 documented the field as having no effect), keeping the `*http.Transport` the upstream client asserts; `broker_health_test.go` silences a live connection through a proxy without closing it and requires the request to fail within the ping allowance and the next one to dial a new connection. It does not bound an exchange whose peer answers PINGs but never the request, and HTTP/1.1 falls outside it.

**A poll that fails past the client's retries is one tier's trouble, and the listener reopens its session rather than stopping the deployment (#207).** The vendored client retries a `GetMessage` for about twenty-five minutes (five attempts of up to five minutes, plus backoff) before the error reaches billet, and the listener used to return it, which cancels every listener of every target: one broker problem drained the whole control plane, and a drain waits for running jobs. `server.runTier` now hands every listener `WithSessionReopen` over `openSession`, and `recoverSession` closes the failed session (bounded by the close grace), opens a new one (waiting out `ErrSessionHeld` when the close did not land), and retries with backoff (`sessionReopenFirst` 5 s doubling to `sessionReopenMax` 5 min, reset by the first poll that answers), logging every failed attempt at Error with the tier. The close and the open run aside and are awaited, because the vendored client takes a per-target mutex (`Client.mu`, held across a request's retries by every other call on that target) that no context reaches; a close still running when the grace ends is an unknown outcome that releases nothing, and a later attempt or the teardown waits for that same call rather than starting another. A recovery the start of a drain cut short resumes, on the drain's context, before the next poll, since the session in hand is the one being replaced. The new session is a restart's view of the queue: the cursor starts at zero, the hold on an undelivered message is dropped because GitHub redelivers what was not acknowledged, and the statistics are the new session's, even none. What still returns, and so still stops every tier, is what the deployment must stop for: a response wrapping `ErrUntrustworthySession`, a lost controller claim (`state.ErrLeadershipLost` or the listener's fence, checked before every close and open, and by `openSession` before every attempt including each wait on a 409), an open that itself answers with either (returned as itself even mid-drain, never collapsed into the cancellation), a misconfigured listener, and every other listener failure (an `Escrow` error, a failed acknowledgement or `AcquireJobs`, which are not yet recovered this way). `sessionrecovery_test.go` pins both sides.

**The policy client owns its HTTP client, and no request it makes is unbounded.** The policy is read before every JIT mint, so a stalled policy request holds its target's registrations. `NewRunnerGroupPolicyClientAt` is the one constructor: it builds an `*http.Client` and transport of its own (dial, TLS-handshake, response-header and overall bounds, the same HTTP/2 health check as the scale-set client from #205), never `http.DefaultClient`, whose transport is process-wide and has no timeout. Every request goes through `exchange`, which adds a per-request context bound and reads the body whole up to `maxPolicyResponse`; a larger body is refused rather than truncated, because a prefix of it can be a valid document the whole is not. A timeout at any stage, a body that broke off, a body past the bound and a caller's wait behind another token exchange are `errNoAnswer` or a `*url.Error`, both `Undecided`, never a refusal or an absence. The token exchange is admitted one at a time through a channel, not a mutex, so a waiting caller gives up with its own context (#206). `TestThePolicyClientReachesNoProcessWideDefault` parses the package to hold that.
