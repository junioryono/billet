# Identity and authorities

## What this area is

A deployment is named by a 32-hex identity (`internal/deploymentid`, `deploymentid.Validate`) minted once per state directory and recorded in the ledger's binding. The control plane is its own certificate authority: `internal/wirecert` mints one CA per deployment (`CALifetime` 10 years, `LeafLifetime` 1 year, `ClockSkew` 1 hour, `ExpiryWarning` 30 days), issues node bundles, rotates and retires authorities and serves the TLS configs. `internal/wireshare` carries an authority between controllers through an `awsssm` store. `internal/github` creates the App through the manifest flow, signs App JWTs, resolves the installation and verifies the App. The commands are in `cmd/billet` (`main.go`'s `ca` dispatch, `enroll.go`, `githubapp.go`, `appkey.go`, `appkeypublish.go`, `casync.go`, `identitystore.go`, `githubaccess.go`).

## Rules

**Destruction is scoped by deployment identity, never by node name.** The identity labels every piece of compute: Docker labels, EC2 `sh.billet.owner` tags, firecracker jail markers, tart marker files, CodeBuild `BILLET_OWNER` overrides. Node names default to the hostname, so two billets on one machine share one; labelling by name let one installation enumerate the other's containers. A copied state directory keeps the original's identity on purpose (its containers carry that label) and `state.LockDeployment` is what makes the copy collide. The identity is refused rather than sanitised, because a sanitised value names a different deployment from the one attached to running compute.

**A node's identity and deployment come from its certificate.** The CN decides which node a request is from and the organization which deployment; a node's state directory mints an identity when it has none, which is right for a control plane and wrong for a node, so `state.AdoptDeploymentID` writes the certificate's answer down and refuses to overwrite a different one. The server's own certificate is minted per boot and never stored. A CA directory holding one of its two files is refused rather than repaired; minting a replacement is a new authority and every node certificate stops verifying at once.

**An empty CA directory is ambiguous, so `authority-created` remembers.** "No files" reads as day one and day one mints a replacement that drops the whole fleet while the plane looks healthy. The marker lives outside the `ca` directory so that directory going missing is detectable; deleting the marker is how an operator starts over on purpose (`ErrAuthorityLost`). A CA's subject must name this deployment (`parseCA` refuses another's) and its key must be its certificate's key.

**A rotation is an overlap, not a switch, and it is published in an order a lock-free reader can trust.** `billet ca rotate` has the new authority issue node certificates while the old one still signs what the control plane presents and both are trusted; nodes adopt the new one through ordinary renewal; `billet ca retire` drops the old one once the fleet has moved. The files are `ca.crt`/`ca.key` and `ca-previous.crt`/`ca-previous.key`. `ca-previous.crt` says a rotation started; `ca-previous.key` says it is committed. Rotate writes certificate then key, Retire removes key then certificate, and `LoadServing` reads in that same order, so a certificate with no key beside it always means not committed. Reading `ca.crt` before `ca.key` leaves exactly one possible tear (the new key beside the old certificate), which `repairPair` resolves by asking whether the key pairs. `LoadServing` is one call rather than four walks so a retire cannot land between reads and produce a plane presenting a retired authority while trusting only the new one, the one failure here that is not fail-closed; it also re-reads `ca.crt` at the end and starts over if it moved (`servingReadAttempts`), because a whole rotate-and-retire can pass between two reads. A waiting reader lock was rejected: `local backup` holds `LockAuthority` across a `VACUUM`, and a control plane that will not start during a backup is worse than the diagnostic.

**`Rotate` and `Retire` take `LockAuthority` themselves.** Exported entry points enforce their own rule (the `alloc.New` argument). `Rotate` refuses if either previous file already exists, with two different messages, because `ca retire` is gated on the certificate and says "no rotation is running" when only a key is left; billet does not remove that key but does say, from having read both, whether it is a byte-identical copy of the installed `ca.key`. Measured: a second flock on a separate descriptor in the same process is denied (EWOULDBLOCK on darwin), so a holder must not call anything that takes it again. `createCA` falls back to loading an existing key (right for two processes racing to initialise) and would make a rotation a no-op, so `Rotate` mints aside and renames into place; clearing the files and calling `LoadOrCreateCA` would leave the authority momentarily missing while the marker says one exists.

**Retire proves the current pair took over, and derives permission from what is proved.** Three narrower rules shipped first: "is something missing" let an absent `ca.key` through and deleted the only matching key; "does `ca-previous.key` match `ca.crt`" let a coherent authority from another deployment through. Now there is one way through: `ca.crt` and `ca.key` read, parse, match and name this deployment; everything else refuses. Retire removes a previous pair only when `parseCA` proves it this deployment's own, except a lone previous certificate (public, the ordinary crashed-rotation leftover). The new authority records the fingerprint of the one it replaced in an organizational unit prefixed `billet-replaces:` (billet has no OID arc), so a second self-minted CA with the same deployment id is not retired as the predecessor; an authority claiming nothing falls back rather than refusing, because that is every deployment that rotated before this shipped. A deletion is authorised only by bytes all accounted for: the one-PEM-block proof checks the block starts where the file does, carries no headers and is the expected type, because `pem.Decode` skips forward to the first BEGIN and discards a remainder; and `parsePair` checks the certificate signed itself, because one assembled around the real public key satisfied every other check.

**Revocation is by serial and renewal by the certificate being replaced.** `billet nodes revoke <node>` withdraws every credential a machine holds (a node renews itself, so the bundle you issued names a serial it stopped presenting); `billet ca revoke <node> --cert` withdraws one; a certificate issued in a later second is unaffected so a rebuilt machine keeps its name. The one residual: a legacy certificate whose serial was never recorded is caught by a whole-second cutoff, which is a comparison between two clocks; if you cannot enumerate what a compromised host holds, rotate. Renewal is authenticated by the existing certificate (a revoked one cannot renew), the private key never crosses the wire, the subject comes from the identity, the renewal is verified before it is installed and written before it is used. `billet ca issue` hands out the trust bundle, not only the issuer, because during an overlap the new authority issues and the old one is presented. `billet ca issue --lifetime` (`wirecert.CA.IssueNodeFor`; bounded in wirecert to [`MinIssuedLifetime` = 20m, `LeafLifetime`], because a node renews on a five-minute sweep once a third of the life remains, so the final third has to outlast a sweep; ten minutes, the first floor chosen, left a three-minute window) issues a short leaf for a short-lived host or a rotation rehearsal; renewals and the control plane's own certificate keep `LeafLifetime`. `RenewalDue` measures a leaf from its issue, not from its `NotBefore`: `leafTemplate` backdates `NotBefore` by `ClockSkew` (an hour), and counting that hour as life made a twenty-minute leaf look eighty minutes long and due the moment it was issued, so a rehearsal's nodes renewed onto the old authority before the rotation (found in review, 2026-09-04). `scripts/ca-rotation-rehearsal.sh` is the rotate-then-retire sequence across two renewing nodes on a packaged host, and after `ca rotate` the control plane must be RESTARTED to present the overlap, which the command's own output says.

**The CA is a slow cliff.** A leaf may not outlive its authority, so once the CA has less than a leaf lifetime left every certificate it issues is quietly shorter than the last, renewals come round faster, and then every node expires on the day the authority does. `billet ca show` warns once that starts; it does not report whether a rotation is running.

**A shared identity is replication over the file layout; moving the authority into a store is the refused answer.** A promoted standby with an empty `ca` directory would mint a rival authority through `LoadOrCreateCA`. The obvious fix is wrong: `wirecert`'s safety argument is a state machine over five file names resting on cross-key write ordering, per-file durable visibility, `O_EXCL` and a crash-releasing flock, none of which survives a remote key/value store. `internal/wireshare` makes the store a channel: `Publish` what you hold, `Adopt` when you hold nothing, and never write over a local authority (a host holding a different one is refused naming both fingerprints; `ca sync --force` moves the old directory aside rather than deleting a key). The ordering in `runServer` is asserted structurally by `TestTheAuthorityIsAdoptedBeforeTheWireAndPublishedAfterIt`: adopt after the claim and before `serveNodeWire`, publish after it. Two controllers do not converge on their own: `ca rotate` and `ca retire` publish, and the other host runs `billet ca sync`. The IAM grant for the store has no delete; the prefix is the boundary and `kms:Decrypt` is confined to `kms:ViaService`.

**The App private key is issued once, never deleted by pathname, never rendered.** `reserveKeyFile` reserves a sibling staging file with `O_EXCL` and `writeKeyAtomically` publishes it with an `os.Link` that fails rather than replaces (no rename fallback, because Go's `os.Rename` has no no-clobber form). Nothing is deleted unless it is known not to be a key: `inspectKey` answers present, absent or unverifiable, and only absent permits a deletion; the staging name is re-inspected after `O_EXCL` fails; "not a valid key" is not "safe to clobber". A credential is never declared lost while its bytes are in memory, so a failed check writes the PEM to a fresh `O_EXCL` file and reports where it landed. `billet check` proves the key works (regular file, no group/other bits, bounded read, parsed, through one `O_NONBLOCK` descriptor). `App` redacts on every rendering path (`String`, `GoString`, `Format`, `MarshalJSON`, `LogValue`, value receivers). Publishing to the identity store happens after the file is on disk, never instead, so every failure leaves a file `billet github-app store-key --from` can publish.

**Onboarding refuses everything it can before it touches GitHub.** `planConfigEdit` decides a missing config, a `github:` holding a list and an unwritable directory before `github.Onboard`, because the key is spent the moment the App exists. The one-time code is redacted structurally from every error in the chain (a `*url.Error` is rebuilt, `errors.Join` trees are walked, an opaque leaf whose text carries the secret is replaced); nothing derived from the conversion response body is rendered, because that body is the one place a private key travels. A code that does not redeem is discarded only on 404 and retried round-robin otherwise (422 also means the endpoint was spammed; 429 says nothing about the code), because discarding on anything else was a kill switch that left the App created and its key unrecoverable. The accepted residual is argv: the callback URL reaches `open`/`xdg-open` as an argument, so a local process can delay onboarding up to `ManifestTTL` and can neither obtain nor destroy the key.

**An App that holds a permission billet never requested is refused, so a job needing a permission billet did not ask for is another App's job.** `Installation.PermissionMismatches` reports both directions and `billet check` (so `billet local up`) refuses on either: a missing permission breaks runner registration later with an error that never mentions permissions, and an extra one falsifies the credential-isolation claim. Measured 2026-09-04: the acceptance lane's App was given `actions: write` so the lane could dispatch a workflow, and every rehearsal's `local up` refused `actions: granted write, but billet never requested it`. The dispatch needs `actions: write`, which is outside billet's set, so it is done by a dedicated second App installed on that one repository with `actions: write` and the mandatory `metadata: read`, nothing billet uses; widening the App billet runs with is never the answer.

**Every token billet mints is scoped to an installation, so losing the installation looks like nothing.** An uninstalled App, or a stale `installation_id`, fails several wrappers deep in the vendored client as a bare `404 Not Found` on `/access_tokens`, and the packaged unit restarted on it 42,940 times on the reference host. `billet check` always answered it (`github.VerifyAppAt`); `explainGitHubAccess` now asks after a failure, never replaces the original error (asserted by prefix as well as `errors.Is`), never claims to have found the cause, and separates an unreachable GitHub from a refused credential. A control plane authenticates under two issuers (the runner-group policy client signs with `app_id`, the scale-set client with `client_id` when set), so the healthy report says which it tested (`TestAVerifiedAppDoesNotVouchForAClientIdItNeverUsed`).

## Measured facts

- 42,940 restarts on a bare 404 from `/access_tokens` after an App was uninstalled.
- A second flock on a separate descriptor in one process: refused (EWOULDBLOCK, darwin).
- Retire guard: three narrower rules each let a wrong key through before the positive rule was written.
- `pem.Decode` skips to the first BEGIN and returns a remainder; a second private key appended after a legitimate one parsed clean and was unlinked with the file.
- A real rotation across two packaged nodes on twenty-minute leaves (2026-09-04): both renewed on the same sweep 808s after issue, 787s after the rotation, at the one-third boundary; `ca retire` without `--force` prints its confirmation and exits 0 having retired nothing, and rounds the rotation's age to the hour.
- Onboarding status handling: `{404, 422}` left the kill switch open for a 414; "every 4xx" swallowed a valid code on 429; only 404 establishes a code is unusable.
