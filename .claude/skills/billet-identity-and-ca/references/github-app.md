# The GitHub App

Part of the `billet-identity-and-ca` skill. Each rule is stated in full, with the measurement or incident behind it.

**The App private key is issued once, never deleted by pathname, never rendered.** `reserveKeyFile` reserves a sibling staging file with `O_EXCL` and `writeKeyAtomically` publishes it with an `os.Link` that fails rather than replaces (no rename fallback, because Go's `os.Rename` has no no-clobber form). Nothing is deleted unless it is known not to be a key: `inspectKey` answers present, absent or unverifiable, and only absent permits a deletion; the staging name is re-inspected after `O_EXCL` fails; "not a valid key" is not "safe to clobber". A credential is never declared lost while its bytes are in memory, so a failed check writes the PEM to a fresh `O_EXCL` file and reports where it landed. `billet check` proves the key works (regular file, no group/other bits, bounded read, parsed, through one `O_NONBLOCK` descriptor). `App` redacts on every rendering path (`String`, `GoString`, `Format`, `MarshalJSON`, `LogValue`, value receivers). Publishing to the identity store happens after the file is on disk, never instead, so every failure leaves a file `billet github-app store-key --from` can publish. One key per target: the `default` target's store parameter is `github-app-key` and a further target's `github-app-key-<name>` (`GitHubTarget.KeyName`); the default key file beside the config is `app-private-key.pem` for `default` and `app-private-key-<name>.pem` otherwise; the archive carries `github/<name>/app-private-key.pem` per target (schema 3) and the host role installs each at `/etc/billet/app-private-key-<name>.pem`.

**Onboarding refuses everything it can before it touches GitHub.** `planConfigEdit` decides a missing config, a `github:` holding a list, a `targets:` entry it cannot place and an unwritable directory before `github.Onboard`, because the key is spent the moment the App exists; `--target NAME` writes the named `targets:` entry (created with its `name` when absent) and `default` writes `github:`, with exactly one of `org`/`repository` left in the block. The owner's account type is resolved first (`ResolveOwnerType`), because a manifest posted to the wrong form costs an App while a failed lookup costs nothing. The one-time code is redacted structurally from every error in the chain (a `*url.Error` is rebuilt, `errors.Join` trees are walked, an opaque leaf whose text carries the secret is replaced); nothing derived from the conversion response body is rendered, because that body is the one place a private key travels. A code that does not redeem is discarded only on 404 and retried round-robin otherwise (422 also means the endpoint was spammed; 429 says nothing about the code), because discarding on anything else was a kill switch that left the App created and its key unrecoverable. The accepted residual is argv: the callback URL reaches `open`/`xdg-open` as an argument, so a local process can delay onboarding up to `ManifestTTL` and can neither obtain nor destroy the key.

**An App that holds a permission billet never requested is refused, so a job needing a permission billet did not ask for is another App's job.** `Installation.PermissionMismatches` reports both directions and `billet check` (so `billet local up`) refuses on either: a missing permission breaks runner registration later with an error that never mentions permissions, and an extra one falsifies the credential-isolation claim. Measured 2026-09-04: the acceptance lane's App was given `actions: write` so the lane could dispatch a workflow, and every rehearsal's `local up` refused `actions: granted write, but billet never requested it`. The dispatch needs `actions: write`, which is outside billet's set, so it is done by a dedicated second App installed on that one repository with `actions: write` and the mandatory `metadata: read`, nothing billet uses; widening the App billet runs with is never the answer.

**Every token billet mints is scoped to an installation, so losing the installation looks like nothing.** An uninstalled App, or a stale `installation_id`, fails several wrappers deep in the vendored client as a bare `404 Not Found` on `/access_tokens`, and the packaged unit restarted on it 42,940 times on the reference host. `billet check` always answered it (`github.VerifyAppAt`); `explainGitHubAccess` now asks after a failure, never replaces the original error (asserted by prefix as well as `errors.Is`), never claims to have found the cause, and separates an unreachable GitHub from a refused credential. A control plane authenticates under two issuers (the runner-group policy client signs with `app_id`, the scale-set client with `client_id` when set), so the healthy report says which it tested (`TestAVerifiedAppDoesNotVouchForAClientIdItNeverUsed`).
