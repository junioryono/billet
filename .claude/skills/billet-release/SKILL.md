# Releases and upgrades

## Releases

Semantic version tags, because Go gives no choice: a module version must be `vX.Y.Z`, so a date-stamped tag is not a version Go will ever resolve. Staying on `v0` also keeps the module path free of a `/vN` suffix, which is required from major version 2 onwards.

One branch per MINOR version, carrying every patch on it:

```
main ──●──●──●──●──●──●──▶
        \              \
         \              release/v0.4 ── v0.4.0
          release/v0.3 ─┬─ v0.3.0   (cut)
                        ├─ v0.3.1   (hotfix)
                        └─ v0.3.2   (hotfix)
```

Cut with the **Cut Release** workflow (Actions → Run workflow). Blank version cuts the next minor; supply one to bump deliberately. A hotfix is a commit on the existing `release/vX.Y` branch and a press of the same button with the patch version typed in — then **merge that branch back into main**, or the next release reverts the fix.

`cut-release.yml` creates the tag and CALLS `release.yml` rather than relying on the tag push to trigger it. Before tagging, it rewrites both the internal composite-action refs and `ansible_collections/junioryono/billet/galaxy.yml` to the exact release version; a collection installed from a Git tag still reports the version in that file. A ref pushed with `GITHUB_TOKEN` does not start another workflow — GitHub's recursion guard — which is why a release button usually needs a PAT or an App. A `workflow_call` is not an event, so billet needs no repository secrets.

GitHub release immutability is enabled on the repository and is part of the release contract, not an optional hardening step. It locks the published tag and assets and creates GitHub's release attestation. `release.yml` first proves the release is immutable, then polls the repository attestation API for GitHub-initiated bundle URLs at the tag ref's digest and asks `gh release verify --format json` to fetch, decompress, cryptographically verify and exact-tag-filter the bundle. The REST response carries `bundle_url`, not the bundle itself; treating it as inline JSON makes the gate fail after publication. The exact-tag filter matters for lightweight tags because several tags can share one commit digest and another release's older attestation is not propagation of this one. The ref digest is an annotated tag object when the tag is annotated and the target commit when it is lightweight; forcing `^{tag}` rejects a lightweight hotfix only after its release has already published. An authenticated HTTP 404, a valid response with no GitHub release bundle, or `gh release verify` reporting that no bundle matches this exact tag is retried within the wall-clock deadline; authentication, authorization, throttling, server, transport, malformed-response and cryptographic-verification failures stop immediately. The verifier is checked out from `github.workflow_sha`, the immutable commit that defined the caller workflow, because a workflow called from main may build a maintained release branch whose tree predates the helper; billet's caller and reusable release workflow are always resolved from the same repository commit. The setting applies only to releases created after it was enabled; do not describe an older release as immutable merely because the repository is protected now.

Guest images use the same repository-wide immutability and therefore publish only dated `guest-YYYYMMDD-HHMMSS` prereleases. Never recreate a rolling guest Release: its tag and assets freeze on first publication. The publisher creates the dated tag at the exact built commit and pushes it before `gh release create --verify-tag`, so a conflicting pre-existing tag fails rather than relabeling the build. After proving the dated release immutable, the workflow signs a ten-day channel statement carrying that fact and fast-forwards `current.json` plus its Sigstore bundle on `guest-channel`; pullers authenticate and freshness-check the statement through raw.githubusercontent.com without sharing GitHub's anonymous REST limit. The two files can briefly come from different CDN generations while the branch advances, so a signature mismatch refetches the pair once before failing closed. The branch is only transport—the signature, expiry and immutable assertion are the trust boundary, so an unsigned edit or an old signed replay is refused. The unprivileged build job has read-only contents access, persists no checkout credential and holds no OIDC permission; only the main-guarded publication job downloads its checked artifact, signs it, publishes it and advances the channel. Marking guest releases as prereleases keeps the repository-wide latest alias reserved for binary installation.

## Updating a running host

Use the `junioryono.billet.host` role for an in-place release upgrade. It inspects the controller's candidate digest, allocates one unique recovery journal, copies the candidate and every generated result into that journal, and rechecks the immutable copy before any later task uses it; never stage a host transaction in a shared cache path. Before it replaces desired-state files, it preserves the installed configuration, units and binary, records their metadata, service identity, exact supported systemd enablement and prior active-service state in a manifest, derives the ledger from the installed `server.state_dir`, and refuses any implicit server or node state-directory move. It accepts only distinct dedicated state directories below `/var/lib/billet`, refuses redirected configuration or unit inputs, reloads systemd before inspecting and refusing an installed service identity change ahead of account or state ownership mutation, and reloads again before refusing effective service drop-ins plus masked, linked, alias, or transient service states whose overlay, symlink topology, or in-memory definition the journal cannot replace and reproduce. Check mode does neither reload: it probes `NeedDaemonReload` and refuses stale Billet unit policy instead of changing the live manager. It resolves an omitted node name from the TLS certificate before applying node-pinned tier policy, then proves every distinct configured Firecracker image eligible for this node satisfies the candidate's guest contract, boot-verifying an already imported matching generation before downloading another compatible immutable replacement. It claims `/var/lib/billet/upgrades/active` with a no-replace hard link before any live mutation, stops the node first so compute drains, stops the server after custody is settled, removes `/usr/bin/billet` so a concurrent operator cannot enter through either version, establishes and durably flushes the maintenance fence, commits the stopped-ledger snapshot in the unique recovery directory, installs the journaled candidate, and validates and migrates with the new binary as the only ledger writer. After loading candidate units, it rechecks effective drop-ins immediately before validation and readiness probing. Explicit `--upgrade-probe` units then prove the server can open the fenced ledger and the node can initialize its provider while neither process polls, registers, dispatches, or accepts workload. Transactional candidate units use systemd notification readiness, and each process sends `READY=1` only after its probe initialization completes; process liveness for a fixed interval is not a substitute. An ordinary converge preserves each installed unit's readiness type so a collection update neither imposes notification on an unchanged legacy binary nor removes it from an already upgraded service and triggers a needless restart. Only after explicit readiness and stability does the role install steady-state units without a maintenance bypass, persist desired enablement, flush every mutated host filesystem, and write the durable commit record. The shared finalizer opens administration, replaces probes with full services in server-then-node order, proves their stability, and removes the active pointer last. Journal schema remains backward-readable: a committed version-2 journal carrying a legacy transient label can finalize because finalization does not restore the old definition, while an uncommitted one is left fenced for manual recovery instead of attempting an impossible rollback.

The candidate binary is installed only after both old services stop, the old executable is hidden, no billet process remains, the maintenance fence exists, and the ledger snapshot has its completion marker. The fence makes already-open operator handles refuse transactions throughout backup, migration, probing, and possible restoration; the staged validator and explicit quiescent probes receive the narrow bypass, while installed steady-state units never do. If a task fails, the same recovery routine requests both processes to stop and proves each service terminal with zero main/control PIDs and a conclusively empty or absent cgroup before it modifies the ledger. It validates the completed snapshot before deleting current ledger entries, disables candidate units and removes their known persistent and runtime links while their files still exist, restores the prior configuration, units, identity, binary, exact enablement and ledger, flushes all restored filesystems, and writes the rollback decision before the finalizer opens administration and returns only the previously active services. A failed first installation has `not-found` prior units, so its links must still be removed and finalization must skip rather than stop the absent restored services. If Ansible or the host is interrupted while the active pointer exists, the next converge validates its journal before account or package mutations and either rolls back an uncommitted transaction or only finalizes one whose durable upgrade or rollback record already exists. A commit record is the point after which recovery must never restore the snapshot: the fence may already have opened and admitted operator writes. The finalizer retains the active pointer until full services remain stable, so a crash after opening the fence or starting only the server retries committed startup without rollback and without restarting a full service already running. A compatible verified generation remains published because publication is fleet-wide and another upgraded host may already depend on it; immutable unused generations are left for ordinary retention. Missing, redirected, malformed, foreign-owned, or inconclusive recovery evidence leaves the active pointer and recovery directory untouched instead of guessing at privileged state. A second converge with the same binary is read-only for the transaction: it validates the host without draining or restarting either service. Do not share candidate artifacts across journals, accept a symlink-backed service state rollback cannot reproduce, move binary installation before the fence and completed ledger snapshot, remove candidate files before their enablement links, let probes poll or dispatch workload, treat `Type=exec` liveness as readiness, record either commit before flushing the entire mutated host state, open the fence before a durable decision, or remove the active pointer before full-service stability; those orderings violate the single-writer or crash-recovery invariant.

The CLI pieces used by the transaction are intentionally useful outside Ansible. With no explicit image, automatic image commands resolve certificate-derived node identity before tier selection, and `billet images compatible` checks every distinct configured Firecracker image, returns success when all selected generations record the candidate guest contract, boot-verifies an already imported matching generation or backfills an older verified generation before downloading another, and returns status 2 after `--result-file PATH` records every floating image that needs a compatible generation. `billet images pull --verify --result-file PATH` writes the exact imported generation only after every requested verification succeeds. Exact incompatible pins are refused because promotion cannot change what they name. Manual promotion and unpromotion hold the same publication lock as verification and reaping; reap replans under that lock and refuses to remove anything whose verification or contract changed after the operator's preview. `@verified` resolution and retention are contract-relative, so publishing a new-contract generation does not make nodes still running the prior binary select it or let a reap remove the last generation they can boot during a rolling upgrade.

Installing the package directly remains available, but the package replaces the binary and units and deliberately does not enable or start either service. A manual operator is responsible for reproducing the same drain, compatibility, backup, validation, migration, restart, and rollback order; installing a new binary over a running control plane is not a supported transactional upgrade.

## What a release publishes, and what follows it

Every release publishes a SIGNED MANIFEST beside its archives — `release-manifest.json` and its `.sigstore.json` bundle — carrying every artifact's digest and the four facts that decide whether a candidate may replace a running build: the node-wire range it speaks, the ledger schema it expects, the guest contract its images must satisfy, and the release it can be rolled back to. `checksums.txt` answers "did these bytes arrive intact" and nothing else, and every one of those four has to be readable BEFORE anything stops.

**It is built and signed inside GoReleaser's `signs` stage, and that ordering is forced rather than chosen.** Release immutability freezes a release's assets the moment it is published, so `gh release upload` after the fact is refused — correctly, by the property the pipeline exists to have. `release.extra_files` is what puts both files in the release, and `scripts/releasemanifest_test.go` asserts the whole arrangement structurally, because a manifest that is built and never uploaded produces a green release with a channel pointing at a tag containing nothing to verify.

**Every compatibility fact is read out of the packages that define it**, by `scripts/mkreleasemanifest`, never typed into YAML. A workflow that restated the wire range would publish a manifest describing a build nobody made on exactly the release where somebody bumped one and forgot the other — which then fails closed on every deployment in the field for a reason no diagnostic could explain. `state.LatestSchemaVersion` is derived from the migration list for the same reason.

**The channel is the only thing in the contract that moves**, which is why it is signed, expiring and self-describing. `scripts/advance-release-channel.sh` runs AFTER the immutability gate, because the statement asserts that the release is immutable and that has to be a finding rather than a claim — GitHub's immutability applies only to releases created after it was enabled. The statement names its own channel (serving `candidate.json` at `stable.json`'s address would otherwise move a fleet with every byte authentic and the wrong document), carries a ten-day expiry so an old copy cannot be replayed onto the branch, and refuses to regress: a hotfix cut on an older minor publishes its artifacts and leaves the pointer alone.

**A rollout resolves the channel ONCE and persists the manifest's DIGEST.** A channel that advances mid-rollout must not retarget work already underway, and recording only the version would let it. `billet rollout start` is where that resolution happens; nothing downstream consults the channel again.

## Rolling a fleet

`billet rollout` is one durable decision: one immutable target, and where every controller and node has got to on the way to it. Starting the same rollout twice finds the one that is running; a DIFFERENT target while one is open is refused, because work is already underway against the first.

**`internal/rollout.Coordinator` is what drives it**, on a slow tick inside the control plane, and every transition it makes is driven by an OBSERVATION rather than by elapsed time: a host is converged because it registered reporting the target release. It does not upgrade the controller — a process cannot install its own successor — it OBSERVES that the running binary is the target and only then begins on the nodes, which is what makes the rollout server-first. A host that cannot receive the upgrade command (its negotiated wire predates `VersionNodeUpgrade`) is BLOCKED once with both ways out named, rather than retried forever burning the cohort's only slot.

**AN EPOCH OF ZERO MEANS "NOT RECORDED", SO A FIRST REGISTRATION MUST NOT PRODUCE ONE.** `RegisterNode` took the column default and wrote zero for a node's first registration, which is the ORDINARY sequence — a node registers, an operator starts a rollout, the host is dispatched at epoch zero — and the rollout then declined to conclude anything about it forever. Every such host would have held its cohort slot until a person intervened. The insert now writes 1 explicitly, matching what every other recorded-at-registration field in that row means by zero (an absent release, a wire version of zero: the binary that wrote me did not record this).

**A REGISTRATION EPOCH IS THE ONLY CAUSAL EVIDENCE THE COORDINATOR HAS, and four of the six defects in one review round came from not having it.** The host runs its own transaction; the control plane sees the instruction going out and registrations coming back, nothing else. So: a host that has not started yet and a host that installed the target, failed and rolled itself back are IDENTICAL in every field — both live, both reporting the old release — and the first version left the second in `draining` forever, holding the cohort's only slot, never counting against the failure budget, silently stopping the rollout. `alloc.NodeWire.Epoch` is what separates them, because a registration bumps it and nothing else does; the dispatch records the epoch it was sent against (`rollout_nodes.dispatch_epoch`, migration 37) and a HIGHER one on the old release is the rollback. An UNRECORDED epoch (zero, from a row written before the column) concludes nothing — "I cannot tell" must not become "it rolled back". The residual is a host restarted mid-drain by something other than the upgrade, which reads as a rollback: an operator retries it, and no job dies for it.

The other three were the same shape — a conclusion drawn from evidence that does not support it. **The liveness check must come BEFORE the convergence check**: `Release` is what a host said at its LAST registration, so a node that came up on the target, failed and vanished reports the target forever, and reading convergence off that closed a rollout over an offline fleet. **The phase walk resumes from the phase it finds** rather than replaying from `draining`, because each Advance is its own transaction and a crash partway then produced a transition the state machine correctly refuses, wedging that host permanently. And **`completeIfConverged` runs after EVERY pass**, not only when a host has just converged, because the last outstanding component can become terminal through an operator's `exempt` or `decommission` — which runs no convergence at all, and left the rollout open forever blocking the next one.

**Observations and dispatches are TWO PASSES, and interleaving them made the failure budget depend on what the hosts were called.** With a cohort of two and a budget of one, an alphabetically earlier pending host was dispatched before a later draining host's rollback — already in the same snapshot — had been looked at: billet held the evidence its tolerance was spent and disturbed another machine anyway. The first pass settles every host already acted on, the ledger is RE-READ (the copies are stale by then), and only the second dispatches. A spent budget gates the dispatch and nothing above it, or one failed host leaves a fleet unable to finish updating the ones that succeeded.

**A `rolling_back` node is reconciled BEFORE the target check.** The record is two transactions, so a failure between them leaves a node in a phase whose only exits are `rolled_back` and `blocked`; a host sitting there that then reports the target went to `converge`, which cannot resume from a phase off the walk, and every later pass repeated the same no-op. Finishing the record first puts it in `rolled_back`, from which reporting the target recovers it.

**`Finish` returns `ErrOutstanding` and the coordinator suppresses ONLY that.** Completion is attempted every pass, so "a host has not converged yet" is what it hears on every tick but the last — but swallowing every error meant a corrupted row or a broken ledger came back as a successful pass forever, visible nowhere.

**`draining → rolling_back` is a real edge in the table** for the same reason: the coordinator's view of a NODE is coarser than the node's own, so the only phases it records from outside are the instruction and the outcome, and a host that restored its previous release never showed billet an `installing` to fall back from.

**Tell the host first, record `draining` second.** The reverse marked a host draining and then failed to reach it, leaving it draining with no updater running — and nothing retries a draining host, because a drain is exactly the state that legitimately takes as long as it takes. This order's own window is survivable: a crash between the dispatch and the record has the coordinator tell the host again, and the second updater is refused by the claim on `/var/lib/billet/upgrades/active`.

The per-component state machine is in `internal/rollout/phase.go`, written down rather than implied. Two edges carry everything and are asserted structurally over the table: **installing is reachable only from `ready_to_install`**, so a binary is never replaced under a running job, and **committed is reachable only from `verifying`**, because the only thing separating "the binary is in place" from "the component works" is the verification. `draining` has no timeout and nothing in the package can give it one.

**Completion means every required component reports the target, or an operator recorded a decision about it.** `Finish` refuses otherwise — including when the controller itself is behind, which an operator watching node phases would not notice. `exempt` and `decommissioned` are distinct: an exemption says this host is not part of this rollout, a decommission says the host is gone, and collapsing them would let a rollout complete while a live host kept an old protocol open with nothing recording that anybody decided so.

## `billet host-upgrade` replaces billet on one machine

A control plane cannot install its own successor: the moment it stops, whatever was going to finish the job has stopped too. So this is a separate short-lived program, exec'd detached, with everything it is midway through on the disk rather than in its memory.

`internal/hostupgrade` owns the ORDER over a narrow interface, because the order IS the safety content and none of the operations under it can be exercised in a test. `TestAHealthyUpgradeRunsInOrder` asserts the whole sequence rather than a property of it — the failure mode is a step MOVING, which no "did it snapshot" assertion would notice.

Two orderings carry the rest. **The ledger is snapshotted before it is migrated**, because a migration is the one step putting the old binary back cannot undo — the old binary refuses a schema it has never heard of. **The fence opens only after the commit record**, because opening it admits operator writes against the new ledger and restoring the snapshot would then discard them. A rollback unwinds exactly what the journal says was reached, ledger first for the same reason.

**AN ANSWER THAT NEVER ENDED IS NOT AN ACCEPTANCE.** `ReadString` returns what it has TOGETHER WITH the error, so bytes spelling `accepted` arrive identically whether the updater finished writing or died halfway through the word — and taking them at face value records a host as draining on the strength of a sentence nobody finished, after which the rollout waits forever for a machine that never took the job. Only a read that found the newline counts. That makes the two byte limits load-bearing: the writer bounds its payload at `MaxAckBytes` and appends the newline, so the reader takes `MaxAckBytes+1` or it would cut the terminator off a maximal answer and refuse it.

**A SPAWN IS NOT AN ANSWER, and treating it as one let a single host wedge a rollout forever with nothing saying why.** The updater is detached because it has to outlive the node it stops — so every refusal it makes BEFORE touching anything (a digest disagreeing with the fleet's decision, an incompatible candidate, a superseded generation, a claim another upgrade holds) was invisible to the control plane, which recorded the host as draining and waited: the host keeps running, stays live, reports the same release, and no registration ever contradicts it. `billet host-upgrade --ack-fd` answers one line on an inherited descriptor — `node.AckAccepted` or `node.AckRefused` plus the reason — the instant the claim and the journal are durable, which is the last point at which nothing has been touched. EOF with nothing written is a REFUSAL, because that is precisely the case a silent spawn hid. The vocabulary lives ONCE, in `internal/node`, and `cmd/billet` uses it: two copies of a protocol whose job is to be recognised is the two-pins problem, and the failure would be a rollout waiting forever on an updater that had answered.

**`Process.Release` DOES NOT REPARENT A CHILD, and using it here filled the process table one refusal at a time.** The node stays the parent, so an updater that exits is a zombie until the node exits — which the original comment assumed was imminent, because a SUCCESSFUL updater stops that very service. A REFUSED one does not: the node keeps running and the rollout retries every few minutes. `go func() { _ = cmd.Wait() }()` reaps it, and waiting neither signals the child nor ties it to the parent's lifetime, so the detachment is unaffected.

**The claim bounds concurrency and nothing else, so the generation needs its own durable mark.** `/var/lib/billet/upgrades/active` is released the moment an upgrade commits or completes a rollback, so a delayed instruction from a superseded rollout arriving one second later finds nothing in its way and installs the release the operator moved away from. `last-decision` is the high-water mark, written BEFORE the transaction starts — what it protects against is a second instruction, and the window that matters is the whole unbounded length of the first. Equal is allowed (a redelivery), strictly older is refused, and an unfenced operator run is never fenced.

**Doing nothing is still acting on a decision.** The already-running fast path accepted before touching the fence, so a machine could satisfy generation 10 with its mark still at 4 — after which a delayed generation 9 passed a stale fence and DOWNGRADED it. Both acceptance branches now record first, and `TestNoUpgradeAcceptsADecisionItDidNotRecord` asserts that structurally, because `startHostUpgrade` resolves a signed channel before either branch and cannot be reached from a unit test: testing `recordDecision` and `checkDecision` directly — the first version — left every test passing with the call deleted.

**THE CLAIM IS A RECORD AND THE TRANSACTION LOCK IS A LOCK, and conflating them left `--resume` able to enter a LIVE upgrade.** `active` is durable so a crashed machine can find what it was running; that is exactly why its presence cannot mean "a process is working on this", since resume exists to adopt a claim whose owner is gone. So the claim excludes a second `start` and NOTHING else — a resume run beside a live detached updater, or two resumes, both entered `hostupgrade.Run`, stopping services the other was starting and advancing one journal. A flock is the opposite shape: the kernel drops it when the holder dies. Taken NON-BLOCKING everywhere, because what it guards contains an unbounded drain. **Lock order is transaction lock, then `decision.lock`, never the reverse.** And `actOnResolved` REQUIRES it already held rather than taking it — a probe that took it to ask "is anybody upgrading" refused every ordinary upgrade against its own caller's lock, because a flock is held by the open file description and a second acquisition in the same process conflicts exactly as another process would.

**A crash between publishing the claim and recording the generation leaves a resumable transaction the fence has never heard of**, and finishing it lets a delayed older instruction pass a stale mark afterwards. A resume settles that before any side effect.

**A STEP RECORDS WHAT COMPLETED, SO THE WORK AFTER IT IS ALREADY IN FLIGHT — and `Reached(StepStopped)` reads exactly like the right question while being the wrong one.** Preserving the binary, stopping the node, stopping the server and hiding the binary ALL run inside one step and only then is `stopped` written, so a journal sitting at `staged` may describe a host with both services down and no billet on the path. Abandoning that releases the claim and leaves the host stopped with nothing resumable and nothing recording why — the worst state this area can produce, and the first version of the boundary produced it. Only `Step == StepClaimed` is conclusive: the work after it is a download into the transaction's own directory. Everything later resolves toward FINISHING, because a superseded release on one host is a rollout that dispatches again while a stopped host is one a person has to find.

**The transaction lock is taken before the NETWORK, not just before the work.** Resolving a signed channel talks to a mirror that can hang past the node's 90-second acknowledgement, after which the rollout retries every few minutes — so with the lock taken after the resolve, each retry started another process stuck in the same place, and a retry that overtook the original could complete an upgrade and let the original wake and run a second transaction over it. Taken first, one stuck process holds it and every retry is refused at once.

**THE JOURNAL IS PUBLISHED BEFORE THE CLAIM POINTER IS, and the reverse order was a race against billet's own recovery.** `--resume` treats "a claim with no journal" as a transaction that never began and CLEARS it — which is right, because the journal precedes anything being staged, stopped or fenced. But while the pointer was published first there was a live window in which a running updater was exactly in that state, so a resume landing there released the claim of an upgrade about to stop services and left a second one free to run on top of it. Writing the journal into a staged directory first makes that state unreachable rather than recoverable. Two racing claims stay correct: both stage, both write a journal, one wins the symlink, and the loser removes its own having touched nothing.

**`releaseClaim` takes the directory it is releasing.** Unlinking whatever claim happens to exist means a finishing transaction can remove the pointer of an upgrade that claimed after it, leaving a live updater with no exclusion. A readlink-and-compare is not atomic with the unlink and nothing in POSIX offers one, but it shrinks the window from the whole length of a transaction to two syscalls.

**The high-water mark has its OWN lock, and it is not the claim.** The claim excludes two transactions; the mark is also touched by the path that finds the release already installed, which runs no transaction and has nothing to claim. So the two exclusions cover different sets, and using the claim for both left generation 10 and generation 9 free to read 4, write 10, then write 9 over it — an atomic rename makes each write whole and does nothing for read-then-write. `checkAndRecordDecision` is the pair under one acquisition. **What a test can prove here is that the exclusion is real** (held from outside, the call blocks); that the pair is ONE acquisition is not deterministically observable, so it rests on that function being the only caller-facing way to do both.

**A claim with no journal is the one state nothing recovers from by itself**, and it is reachable by a full disk. `start` refuses because the claim exists, `--resume` has nothing to continue, and the acknowledgement said only that the updater declined. Since the journal precedes anything being staged, stopped or fenced, that state provably means nothing was touched — so `--resume` releases the claim and says so, and a failing `journal.Write` gives it back immediately.

**A GENERATION OF ZERO MEANS "AN OPERATOR IS AT THE KEYBOARD", so the two modes must not be mixable.** Everything the mark protects rests on `generation > 0` meaning "this came from a rollout" — and an instruction naming a `--rollout` with no `--generation` is neither mode: it installs over an arbitrarily high mark while looking like a person running the command. Both that and a negative generation are refused before anything else happens.

**Nothing deletes a path a file on disk named.** `abandonClaim` is the only operation here that removes a tree, and its path arrives from a journal — a file that can be truncated, hand-edited or restored from another machine. A resume overwrites `journal.Dir` with the directory the CLAIM pointed at, `releaseClaim` refuses an empty name rather than unlinking whatever claim exists, and the removal is bounded to a direct child of the upgrade root. The failures are asymmetric and both bad: a wrong name makes `releaseClaim` quietly decide the claim is somebody else's and leaves the machine stuck, and makes `RemoveAll` act somewhere nobody intended.

**Three answers, not two, for the fence's own file.** Absent means "no fenced upgrade yet" and is fine; unreadable or unparseable means the fence is not working, and answering zero for that hands a stale instruction permission to overwrite the evidence that a newer decision exists. A fenced instruction refuses; an operator's unfenced run does not, which is what keeps this from wedging a host.

**A VERSION IS A NAME AND THE MANIFEST IS THE BYTES, and `internal/provenance` is what lets a host say which it has.** A registration carries the version its binary was BUILT as; two builds can share one and a moved tag makes them identical, so convergence read off the version alone accepted weaker evidence than the decision it was converging. The record is written by `host-upgrade` at commit and by `install.sh` at install, and carries the manifest digest AND the sha256 of the binary — **the hash is what makes it evidence**, because a record naming only a version is defeated by exactly the case the digest exists to catch. A binary replaced by hand reports NOTHING rather than inheriting the last upgrade's provenance, since a rollout reads nothing correctly and reads a wrong digest as certainty. Hashed ONCE per process, and it must describe the bytes that process STARTED with: `os.Executable` resolves a path on macOS, so a later replacement would otherwise be hashed in place of the one running.

**EVERY LINK OF THE ATTESTATION IS CHECKED, and the one that was ASSUMED is the one that mattered.** `billet release record` verified that the manifest names the archive and that the archive hashes to it — and then hashed whatever `--binary` pointed at, because its one caller happened to extract that binary from that archive. An assumption is not a chain: the three paths arrive independently, so a caller passing some other billet would have produced a record attesting that those bytes came from a manifest saying nothing about them. It now streams the single regular member called `billet` out of the archive and compares hashes, refuses a LINK by that name (it resolves to whatever the extracting side already had, so it is not a member of that archive at all), refuses two members with one name, and checks the archive's SIZE against the entry as well. The manifest is read ONCE and its digest taken from those bytes: parsing one read and reopening the path to hash it is two reads of something a rename can change between, which records a document nobody checked.

**THE ARCHIVE IS READ EXACTLY ONCE, AND EVERY WAY THAT READ CAN LIE HAS ITS OWN REFUSAL.** Five review rounds went into `archiveContains` and each one found the previous round's fix. Hashing the archive and then reopening it to read its member is two reads of one file; holding a single descriptor across them closes the RENAME and nothing else, because another writer can still modify the same inode between the passes — so archive A supplies the hash the manifest accepts while archive B supplies the binary recorded as having come from it. There is one pass: every byte is teed into the digest on its way to the decompressor, the file's SIZE is passed in and the bytes read must equal it, and the size is checked BEFORE anything is hashed because the fstat already answered it. A digest of a prefix is not a weaker answer, it is a DIFFERENT file's digest presented as this one's, and an earlier version bounded the final drain by `maxArchiveBytes` — which bounds decompressed tar data and says nothing about how many raw bytes remain — so a large enough remainder was truncated and the prefix hash returned.

**A GZIP READER IS MULTISTREAM BY DEFAULT AND TAR STOPS AT THE FIRST END-OF-ARCHIVE MARKER**, which together let a file carry a second `billet` that the duplicate refusal never sees while the manifest legitimately names the whole thing. `Multistream(false)` plus `Reset` returning `io.EOF` is how a second stream is refused, and every remaining decoded byte after the end marker must be tar's zero padding — that is the same hole one layer in, and draining it is also the only thing that makes gzip verify its own CRC, which nothing did while the walk stopped at the member it wanted. The reader handed to gzip is a `bufio.Reader` deliberately: `gzip.NewReader` wraps anything that is not a `flate.Reader` in a buffer it owns and `Reset` then builds a FRESH one, discarding bytes the old buffer already pulled out of the file, which would leave the multistream check asking about a position the file is not at.

**A LIMIT THAT RUNS OUT READS AS A CLEAN END OF ARCHIVE, and that mistake was made twice nine lines apart.** The decompressed stream is limited HARD and counted, so overflow is refused and named rather than truncated into something tar reports as a corrupt file; the bound is re-checked after the read that ENDS the walk, which no check inside the loop covers; and when the bound bites it is reported in preference to the error it caused, because cutting the stream off makes tar and gzip cry corruption about a file that is intact and merely too large. The entry counter is incremented AFTER a successful `Next()` — before it, the pass that ended the walk counted as an entry and an archive with exactly `maxArchiveEntries` members was refused for carrying "more than" that many.

**THE BOUNDS ARE VARS SO TESTS CAN SHRINK THEM, and two guards are deliberately not mutation-checked and say so where they are.** `hashReader`'s limit and the bytes-read-equals-size check are reachable only by a file that CHANGES between the fstat and the read: for any file this walk accepts, nothing may follow the stream and nothing may hide behind the end marker, so the stream IS the file and the count matches by construction. That is not deterministically stageable and is exactly what a concurrent writer or a network filesystem does on its own. Everything else has a gate and a test, and three of those tests had to be rewritten because the fixture made the thing under test unobservable — a same-length corruption is caught by gzip's CRC before the file hash is consulted (so the hash fixture patches the gzip header's MTIME, which changes the digest and leaves length, checksum and decompressed bytes alone); a small trailing append is invisible because gzip reads through a 4KiB `bufio`; and the decompression bound cannot be observed through the ERROR, because the precedence rule above makes a counting-only walk report the same bound after doing all the work. That last one was measured: the first version of the test passed against a build with the limit removed.

**THE INSTALLER HANDS THE ATTESTATION TO BILLET, because it cannot make one.** `install.sh` verifies its download against a checksums file fetched from the SAME PLACE as the manifest, so hashing whatever came back from a URL called `release-manifest.json` and recording it would have produced a host that converges a rollout as PROVED on bytes that manifest never named — a claim stronger than its evidence, which is the class of defect this whole area removes. `billet release record --manifest --archive --binary` parses the manifest with the reader every other path uses, finds the entry for this platform, and refuses unless the archive hashes to what that entry says. A refusal does not fail the install: the host reports nothing, which is what every host did before.

**A DIGEST IS ONLY TAKEN FROM A PAIRING THAT HAS THE FIELD.** Below `VersionNodeDigest` the protocol has no such field, so a value in it is not something that pairing can mean — and taking it anyway lets a caller speaking wire 12 supply evidence a rollout treats as proof, or as grounds to BLOCK a host. Dropped rather than refused, because "cannot say" is a state everything downstream already reads correctly.

**The `already on this version` shortcut consults the MANIFEST too**, or the one repair a blocked host has does nothing. A rollout blocks a host whose manifest disagrees and tells the operator to run `host-upgrade`; that command saw the versions agree and left the machine as it was, so the rollout blocked it again forever. Only a POSITIVE disagreement reinstalls — a host that cannot say is left alone, since reinstalling on "cannot tell" drains the whole fleet to fix a diagnostic.

**A BLOCKED HOST TAKES TWO COMMANDS TO REPAIR, and the blocker has to say both.** Nothing automatic leaves `blocked` — the walk refuses to advance a phase only a person may leave — so a message that fixes the machine and omits `billet rollout retry` is one somebody follows and then reports as not working. `--reinstall` is the other half: the ordinary shortcut asks whether the installed manifest DISAGREES, and a record that has since been damaged answers "cannot tell" while the control plane still holds the disagreeing digest it reported earlier, leaving the host blocked while the command it was told to run does nothing.

**Three answers, and the middle one is why it ships.** Naming the decided manifest is proved; naming a DIFFERENT one is BLOCKED (right version, bytes nobody chose — billet failing to prove something, which is what blocked means); naming NOTHING converges on the version with the absence recorded in `rollout_nodes.converged_digest`. That last case is the whole installed fleet on the day the field ships, including the hosts that would deliver the build able to name one — refusing there is a rollout that can never complete.

**`safeDigest` REFUSES where `safeRelease` REPAIRS, and the difference is what the fields do.** A release is a diagnostic, so mangling an odd one into a printable token is free. A digest is COMPARED, so a mangled one is not a harmless string — it is a disagreement the node never claimed, and the host gets cordoned over a stray character. Anything that is not 64 hex characters becomes empty, which is the answer billet already has for a host that cannot say.

**The whole spec reaches the updater's ARGV, not just the version.** `--manifest-sha256` is what makes a node install the manifest the ROLLOUT resolved rather than whatever the channel says by the time the node acts — the fleet resolves once, to one digest, precisely so every host installs the same bytes, and a node re-resolving for itself defeats that the moment a channel advances mid-rollout. `node.upgradeArgs` is a function so a test can see it: a review found three of the four fields built and then dropped, while a test asserting the spec reached the Upgrader INTERFACE whole passed the entire time. An operator's own run pins nothing and is not refused; an empty digest is "nobody pinned this", not "pinned to nothing".

**A FAILURE IS RECORDED BEFORE THE RESTORING STARTS AND THE STEP STILL NAMES THE LAST FORWARD STEP, so an interrupted rollback reads as an upgrade in progress.** A crash between restoring the ledger or the binary and recording `rolled_back` leaves a journal saying `migrated` about a machine that has already been put back — and resuming that through `advance` finds every remaining step's work done, probes the RESTORED OLD binary, records a COMMITTED upgrade to a release the host is not running, and releases the claim. Nothing afterwards knows the record is false. `Run` treats a non-empty `Failure` on a journal that has not reached a decision as exactly this and re-enters `rollBack`; re-entering costs nothing, because every action in a rollback is a restore.

**An unprovable rollback is its own outcome.** Nothing about the machine is then known — either release, either schema, compute that may or may not exist — so it is CORDONED with its journal intact rather than reported as rolled back, which would have a rollout return it to service. The claim on `/var/lib/billet/upgrades/active` is released for a committed or rolled-back machine and deliberately NOT for a cordoned one.

**The claim is a symlink to the recovery DIRECTORY.** Hard-linking the journal file reads as tidier and is wrong: the journal publishes through a rename, so after the very first step the pointer would name a stale copy while the real record moved on.

Node side: wire version 14 carries `CommandUpgrade`, gated on `VersionNodeUpgrade`, and does not move `MinVersion` — a 12- or 13-speaking node is never sent one and goes on working exactly as before. The node starts the updater DETACHED and reports only that it started, because a node executes commands one at a time and each command's timeout starts when it is QUEUED: an inline upgrade would hold the single slot for as long as the drain takes, and every other command to that host would expire behind it, including the destroys that let the drain finish. `setsid` rather than `setpgid`, so closing the shell that started the node does not send SIGHUP into a binary swap.

**Not verified on a real host.** Every method of `cmd/billet/hostupgrade.go`'s `systemdHost` stops a service, replaces a binary or migrates a database. What IS verified is the sequence they are called in.

## The node wire is a range, and a rollout is server-first

`internal/nodeapi` declares `MinVersion` and `Version` — the oldest wire this build still speaks and the newest. A node sends both, plus its release; the control plane picks the highest version both speak and records that on the node's ledger row. So **the control plane is upgraded first and nodes converge onto it one at a time**, and there is no window in which both halves must be replaced together. An equality check is what made that impossible, and it is what shipped through v0.3.26: bumping the protocol refused every node in the field, permanently, because `ErrRefused` is not something a node retries.

**The bridge runs one way, and that is a property of the wire rather than a policy choice.** The control plane decodes request bodies with `DisallowUnknownFields` while a node decodes responses leniently. An old node's registration is a subset of a new server's struct and decodes cleanly; a new server's response decodes on an old node. The reverse does not: a new node's body reaches an old server's strict decoder and is rejected before any version check can run. So a node is never rolled ahead of its control plane — it is refused, and the node's own error carries its range so the message says which side to upgrade rather than `json: unknown field "min_version"`.

**`billet status` is what says when an old protocol may be retired**, under `protocol`: each host's negotiated version and release, and whether anything is still below the control plane's newest. **A host this deployment cannot reach still counts** — its compute may be running and it will come back speaking whatever it spoke before — so it blocks retirement rather than being written off. So does a host whose row this binary did not write, and one whose row a NEWER binary wrote; neither is reported as *old*, because that is a claim the ledger cannot support, and all three block retirement. **`billet nodes decommission <node>` is what forgets a host for good**, and it closes the window that host was holding open. It refuses a host this deployment is still talking to — forgetting one billet can reach means its next registration creates a fresh row with a new epoch, which fences every lease the current incarnation is tending and counts its capacity twice — and it refuses any host still holding a lease, which is NOT overridable because a decommissioned host is excluded from what every tier's floor believes is already met while its capacity stays charged either way. `--force` overrides the REACHABILITY refusal only, and records the exclusion as durably UNPROVEN — which every later drain and `billet status` repeat rather than reporting the fleet clear. `billet rollout decommission` is the same act plus the rollout's own record, and tolerates the one case the fleet-level command refuses: a name in the rollout with no fleet row at all, which is a machine something already removed and which would otherwise leave a rollout nothing could resolve. Do not lower `MinVersion` past a version the log in `nodeapi` records as semantically unsafe: the floor is a promise about MEANING, not about whether the fields still parse, and lowering it to make an old fleet connect is exactly the change somebody makes under upgrade pressure.

`MinVersion` is 12 and `Version` is 13. Version 13 added the range and the release and changed nothing a server sends, which is what makes 12 a version a 13 control plane genuinely speaks rather than one it merely tolerates.

The node drain is safe because SIGTERM stops it taking new work and waits for the compute already running here, while still answering the control plane — without which the drain is useless, since what removes a finished job is a Destroy that arrives over that same command poll. It is NOT instant: it takes as long as the longest job still running, and there is no bound on that.

**A second signal ends the WAIT, not the process, and it destroys nothing** (`internal/nodeclient/loop.go`). The node stops waiting and exits; the containers it was holding keep running, `Recover` re-adopts them when the node starts again, and the control plane's reaper reclaims their leases once they expire. Destroying them on the way out would kill jobs that are still running to reclaim capacity that comes back on its own.

**NEITHER HALF DESTROYS A RUNNING JOB ANY MORE, and the server's teardown is where that changed.** `destroyAll` takes an `includeRunning` flag: `cleanup` holds destroys that a completion ALREADY ASKED FOR, so tearing one down ends nothing, while `running` holds jobs still executing. A shutdown passes false. What used to happen is the reverse — the drain ran out, the teardown destroyed whatever was left, and `releaseAll`'s own comment argued that "a failed build beats containers nobody is tracking". That argument has been overturned: billet stopping is not evidence that the work on its hosts should end.

**`billet force-destroy` IS THE ONE OPERATION THAT ENDS RUNNING WORK, and it is the only caller of `includeRunning: true`** — asserted structurally by `TestOnlyTheForceOperationDestroysRunningWork`, because nothing in the type system separates the two booleans and the next person adding a teardown path could pass true with no test failing anywhere. It refuses unless an operator has already sealed admission with `billet drain`: the command enumerates a set, shows it to a person and acts on their answer, so a job admitted in between would be destroyed without ever appearing in the list that was approved. A local-down seal will not do, because the next `billet local up` clears it.

**The target set is fixed when the request is taken, and that is the safety property rather than an implementation detail.** A standing "destroy running compute" flag would destroy every job launched after it, which is a timer authorising a teardown wearing different clothes. Enumerating the leases up front bounds the request, makes it idempotent across a control-plane restart, and produces the diagnostic — every affected job, lease and node — that the operator has to read before confirming. Forced leases archive as `failed`, never `done`: a job whose runner was destroyed while it was executing did not finish. A lease a node has taken CUSTODY of is not touched; `billet leases release --force` is the operation for that, because it goes through the holder rather than underneath it.

So a stop LEAVES the running jobs, keeps their leases charged, and the next control plane re-adopts them through `ServiceableRunnerLeaseIDs`. The capacity staying charged is part of the contract rather than a leak — freeing a slot whose container is still on the host is the overcommit the ordering exists to prevent, and capacity the reaper reclaims late is recoverable where a failed build is not.

**`drain_timeout` decides when billet TALKS, not when it stops.** It has no maximum and no deadline behind it; `warnDrainOverrun` repeats every fifteen minutes for as long as the drain runs, because a threshold crossed silently is a fleet that looks wedged and an operator whose next move is to kill the process. A second signal ends the WAIT — the work survives it.

Two earlier versions of this paragraph were wrong in opposite directions: one said a second signal "tears down properly" and destroys the running jobs, then a correction said the server's teardown is "the half that ends jobs". Both described real behaviour at the time, and the sort of wrong they were costs an operator a fleet's worth of builds — so check the code before restating any of it.

## Deployment

`deploy/` holds the systemd units and the packaged config; GoReleaser's `nfpms` section turns them into `.deb` and `.rpm` (not `.apk`: Alpine uses BusyBox `adduser` and OpenRC, so a package built from these scripts and units could not install). Three things there are load-bearing and were each found by installing a package rather than by reading one:

- **`--config /etc/billet/billet.yaml` is explicit in both units.** billet's default config path is per-user and deliberately never reads the working directory; a unit that relied on the default would find nothing.
- **`lock_dir` is set in the packaged config.** billet derives its default from `HOME`, which a service does not have, so without this billet refuses to start rather than run without the lock that stops two processes managing one host's containers.
- **`TimeoutStopSec` is no longer sized from `drain_timeout`**, because a drain has no bound to size it from. It decides how long systemd waits before SIGKILLing a drain that is still going. That loses billet's own bookkeeping — leases stop being renewed and the reaper quarantines them — but not the jobs: the guests keep running and the next process re-adopts them, which is the same outcome as a crash and is why the number is no longer safety-critical.
- **The node unit runs as root; the server does not.** Docker socket access is already host-root, while Firecracker additionally needs TAP creation, device nodes, cgroups, chroots and verified process signalling. The jailer drops each VMM to its per-guest uid; running the host custodian as `billet` makes a valid Firecracker config fail only when its first job arrives. Keep `/srv/jailer` writable through the unit's `ProtectSystem=strict` sandbox.

The package **does not enable or start anything**. `/var/lib/billet` is created by postinstall rather than shipped, so a package removal cannot delete the deployment identity and the mTLS CA.
