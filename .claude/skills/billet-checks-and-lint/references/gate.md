# The gate and CI

Part of the `billet-checks-and-lint` skill. Each rule is stated in full, with the measurement or incident behind it.

**A green `make check` is necessary, not sufficient.** CI additionally proves `go mod tidy` leaves no diff, runs the suite against a real PostgreSQL and re-runs `internal/alloc` with `BILLET_TEST_LEDGER=postgres`, runs `govulncheck`, cross-builds every node target, runs `sqlc diff`, the Ansible scenario targets, the package and restore rehearsals, every terraform gate and the Sphinx build. A change touching `.tf` files needs `make tf-fmt-check tf-validate tf-test tf-lint tf-scan` before pushing; those are outside `check` because they need terraform, tflint and trivy installed (`make tools` installs the pins).

**Lint runs twice, and the second pass is the one that speaks for production.** A linter only analyses the files it would compile. billet is developed on darwin and runs on linux, so `make lint` runs golangci-lint for the host and again with `GOOS=linux GOARCH=amd64` (CI's architecture, not this Mac's arm64: `syscall.Stat_t.Nlink` is uint16 on darwin, uint32 on linux/arm64 and uint64 on linux/amd64, so `uint64(st.Nlink)` is a required conversion on two of them and an unnecessary one CI refuses on the third, and a `//nolint:unconvert` that quiets amd64 is an unused directive `nolintlint` refuses on arm64; the one spelling that passes everywhere is a generic widening, `widen[T ~uint16 | ~uint32 | ~uint64](v T) uint64`, as `cmd/billet/convergeguard.go` does; measured 2026-09-09), and `make lint-custom` runs `billetlint` for darwin/arm64 and linux/amd64. A `uint64(stat.Rdev)` in the firecracker backend is a redundant conversion on linux and a required one on darwin; it passed locally and failed CI, and three defects on one branch had that shape.

**Coverage instrumentation is part of the gate.** `make test` runs `-race -count=1 -covermode=atomic`. The atomic counters change goroutine timing enough to reorder interleavings a plain `-race` build schedules the same way every time; a launch handed to teardown mid-flight was invisible without the flag and reliable with it. A local gate weaker than CI trains you to trust it.

**A finding is fixed, or suppressed with a reason that names the linter.** `nolintlint` runs with `require-explanation` and `require-specific`, so a bare `//nolint` is itself a finding, and `allow-unused: false` reports a directive that no longer covers anything. Write `//nolint:<linter> // <reason>`. billet's own analyzers use `//billet:ignore <analyzer> // <reason>` with the same three rules: a bare directive is reported, an unused one is reported, and a trailing directive covers only its own line while a directive alone on its line covers the line below. If several exceptions want the same reason, the code is asking for a helper (`readAppliedMigrations` replaced three `rows.Close()` annotations).

**When a bug is a class, encode it, in this order.** A golangci-lint setting (a `forbidigo` ban, a `depguard` rule) is cheapest. A `go/analysis` analyzer in `tools/lint` is next, wired into CI only if it measures about zero current violations, because an analyzer that arrives with a backlog is one people route around (`wsl_v5` measured 5882 findings on this tree and was rejected on that number alone; a linter that wants every test named after the function under test flagged about half the suite, because billet names tests for the invariant they assert). A test over source text is third: `TestNoGoBodyIsWrittenOnOneLine` in `scripts/` refuses one-line bodies, `TestQueryFilesAreASCIIOnly` and `TestNoQueryUsesAWildcardProjection` in `internal/state` police the query files. What needs judgment goes in a skill.

**`make cross` before anything touching a build tag.** A node is deployed by copying one static file, so a build-tag mistake on a platform nobody develops on is invisible until it reaches that machine. Production tags: `internal/state/lock_unix.go`, `internal/regularfile/open_linux.go`/`open_other.go`, `owner_unix.go`/`owner_other.go`, `internal/state/searchdir_{darwin,freebsd,linux,other}.go`, `internal/provider/firecracker/pidfd_linux.go`/`pidfd_other.go`. Tests carry exactly one `//go:build` line (`unix`); everything else is gated by environment variables and `t.Skip`.

**`no-mutants` runs first and `tests-kept` runs outside.** `scripts/check-no-mutants.py` refuses to proceed while a `.bak` sits beside a tracked Go file, because an interrupted mutation run leaves the original holding a mutant that compiles and mostly passes; it is first because it cannot be a false alarm. `scripts/check-tests-kept.py` reports `Test` functions HEAD has and the tree does not; it is deliberately not in `check` because deleting a test is sometimes right, and it exists because a scripted edit once swallowed a neighbouring test with every gate green.

**`sqlc` and `sqlc-check` are outside `check` for the opposite reason to the terraform gates.** The generated query code is committed precisely so an ordinary build never downloads sqlc; CI installs the pin (`SQLC_VERSION` in the Makefile, read by the workflow so the two cannot drift) and runs `sqlc diff` as a step of the lint job, beside `make cross` and govulncheck. Run `make sqlc` after editing `internal/state/queries` or adding a migration, because sqlc reads the migration history as its schema.

**Go comments wrap at 88 columns; Markdown never wraps.** Go source follows the surrounding file. Every `.md` and `.txt` file is one paragraph per line.

**Superseded CI runs are force-cancelled.** `ci.yml`'s concurrency group asks GitHub to cancel an older run of the same ref, but a run whose jobs are queued for self-hosted runners ignores an ordinary cancel and keeps its place in the fleet's queue. `.github/workflows/cancel-superseded.yml` runs on a GitHub-hosted runner on every same-repository PR push, and force-cancels each unfinished CI run on that branch whose head is not the pushed commit. NEVER ON `main`: a `main` run is the check on what merged, and cancelling it for the next merge left `main` with no completed run across nine merges on 2026-09-25. So `ci.yml` sets `cancel-in-progress` only for `pull_request`; on `main` the concurrency group lets the running run finish and keeps only the newest pending one.

**A local gate shares the machine: one gate per user at a time across projects, `go test -p 4`, under `nice`.** Measured on a 12-core, 32 GiB Mac on 2026-10-05: `go test -race ./...` at go's default `-p` (one package per CPU) peaked at 3.36 GiB resident over 96 processes and took 38 minutes, and beside a container VM configured for 24 GiB it pushed swap from 33.4 to 39.4 GiB; DNS and the VPN client stalled with everything else, and the system killed background shells for want of memory. At `-p 4` the same step peaked at 0.99 GiB over 56 processes and finished sooner (2049s against 2299s, on the same loaded machine). `make check` therefore runs its steps (`check-unlocked`) under `scripts/with-check-lock.sh`, which makes the lock's directory and holds `~/.cache/dev-gate.lock` (or `$XDG_CACHE_HOME/dev-gate.lock` when that is absolute; a relative one would give every checkout a lock of its own) through `lockf` on macOS or `flock -o` on Linux (without `-o` a process the gate left running would keep the lock). `CHECK_LOCK` is empty by default and the script works the path out, in the shell, because make's word functions split an `XDG_CACHE_HOME` holding spaces into another path. The path is shared on purpose with other repositories' gates, because the starvation measured was two projects' suites at once, so a second gate waits and says so in one line. It is a courtesy and never a gate: with no lock tool, no absolute `XDG_CACHE_HOME` and no `HOME`, a directory that cannot be made or a lock that cannot be taken, the run goes ahead and says it is not serialised. That includes the waiting take after a free probe: the command's first act under the lock is removing a marker the script wrote in a directory made for that run alone (`mktemp -d`; beside the lock, a directory replaced under it or another container's run of the same pid could stand in for it), and the command runs only once that removal succeeded, so a take that failed (or a removal that failed) leaves the marker and the command then runs unlocked, while a command that ran and failed keeps its own status and is never run twice. A run inside a command holding the same lock (a gate running another gate, directly or through another lock) runs under it, or it would wait forever for the ancestor waiting on it: the script hands its locked command `DEV_GATE_LOCK_HELD`, one `PID:PATH` line per lock held by it and its ancestors, and a run honours an entry only while that PID is among its ancestors (read with `ps`, the holder compared before the walk stops at pid 1 so a container's first process can hold), so a process a gate left behind carries no lock with it. A process tree `ps` cannot read is could-not-tell, never not-an-ancestor, and the run goes ahead unlocked rather than risk waiting on the ancestor holding its lock; a lock path holding a newline, which one line of the list cannot carry, runs unlocked too. The list is split on newlines with globbing off rather than read from a here-document, whose temporary file can fail to be written and leave the walk silently empty, and every status the script reads is taken inside an `if`, because bash takes errexit from an exported `SHELLOPTS` and several of those statuses are answers (measured on macOS's `/bin/sh`: a bare one exited 1 and never ran the command); and the script sets no shell option at all, because bash rewrites an exported `SHELLOPTS` when one changes and the command inherits it: a `set +e` took the command's errexit away and a `set -u` gave it nounset. The command runs in a subshell that execs it, waited for by a shell under the lock, so one ended by a signal reports 128+n (macOS lockf reports any signalled child as 70) and a program is never swapped for a shell builtin of the same name. A lock path that exists and is not a regular file (a FIFO's open waits for a writer) runs unlocked, and the diagnostics go through `printf`, because `echo` in dash and in macOS's `/bin/sh` reads a backslash in a path as an escape. A relative lock path is made absolute first, or the same name in two directories would read as one lock. All of these were found by review on 2026-10-06. A dry run, a question or a touch (`make -n`, `-q`, `-t`) takes no lock: the recipe reaches the sub-make through `CHECK_SUBMAKE = $(MAKE)`, which GNU make does not treat as recursive, so under those modes the line is printed or skipped and never run (a line naming `$(MAKE)` would run and wait behind a whole gate). Make decides this itself; reading `MAKEFLAGS`' first word, the round-one fix's approach, took `make check CHECK_LOCK=/tmp/x` for a touch on GNU Make 3.81 and ran it unlocked. `make -n check-unlocked` lists the steps. The cost is the jobserver: make hands it only to a line it treats as recursive, so on GNU Make 3.81 to 4.3 `make -j check` runs the steps one at a time, and the `+` the sub-make's warning suggests must never be added, because it would bring the `-n` wait back; `make check CHECK_SUBMAKE='$(MAKE) -j4'` runs them in parallel. Outside CI (`CI` unset) the race suite runs `-p $(TEST_PARALLEL)` (4) and the test and lint steps run under `nice -n 10`; `make check TEST_PARALLEL= NICE=` lifts both and still takes the lock. Under CI both are forced empty whatever the environment says, and CI runs the targets one by one rather than `make check`, so its commands are unchanged but for a doubled space where `-p` was. golangci-lint keeps a machine-wide lock of its own and by default exits with an error when another run holds it, so a lint another project ran outside the gate lock failed this gate on 2026-10-06; both lint passes carry `--allow-serial-runners`, which waits for that lock instead. `nice` rather than `taskpolicy`: the same package took 37s under `nice -n 10` against 27s to 119s unprioritised as the load moved, but 205s clamped to the utility QoS and 485s at background QoS, which also throttle disk I/O; a gate that slow fails its own time-bound tests. `scripts/check_lock_test.go` executes the script and the Makefile's recipe: the exit status is the command's; a second run waits for the first, which holds the lock until the second has said so and is waiting in the lock tool (a stand-in in front of `PATH` records each blocking take, because the message is printed before the take), and prints one line; a path with spaces is one path; an empty lock argument is the shared path, under an absolute `XDG_CACHE_HOME` holding spaces and never under a relative one; a directory that cannot be made, or no `HOME`, still runs the command; a leftover child, alive until released and acknowledging its release, does not keep the lock (on Linux removing `-o` fails it; macOS lockf already closes the descriptor in its child); `make check` takes the shared lock under an `XDG_CACHE_HOME` holding spaces, takes it with overrides on its command line and hands those overrides to the sub-make, whose printed race test line carries `nice -n 10` and `-p 2` locally and neither under `CI`, and `make -n check` waits for nothing while another gate holds it; a nested run under the same lock finishes, and so does one nested through another lock; a run whose `DEV_GATE_LOCK_HELD` names a holder that is not its ancestor waits for it; one relative path in two directories is two locks; a take refused after the probe, a marker that cannot be removed, or no private directory to put it in, still runs the command once, with its status; a nested run that cannot read its ancestry, and a lock path with a newline, run unlocked and say so; under an inherited `SHELLOPTS=errexit` the command behaves exactly as it does run directly; a FIFO at the lock path runs unlocked; a command killed by SIGTERM reports 143; `test` under the lock is the program on `PATH`, not the builtin; a diagnostic carries a path holding `\c` whole; a failing command runs once; a call with no command is refused. Every test's lock holder and nested make runs in a process group of its own and is killed as a group, so none outlives its test. Each of these mutants fails one of them: the lock dropped from the exec, the waiting message removed, the probe's silencing removed, the directory never made, the unmakeable directory exiting, the default ignoring `XDG_CACHE_HOME` or taking a relative one, the no-`HOME` fallback removed, the Makefile choosing the path with `$(filter)`, the recipe naming `$(MAKE)` directly, the nested-run check or the handed-over variable removed, only the nearest lock handed down, the ancestry never matching or not asked, the relative path left relative, an unreadable tree read as not-an-ancestor or could-not-tell falling through to the take, the newline check removed, no private directory going ahead, a run that says it waits and goes ahead a second later, `set +e` or `set -u` added, a bare status, the command run as `"$@"` in the inner shell, the FIFO check removed, the command exec'd under the lock tool, diagnostics through `echo`, the marker check removed or reduced to the status alone, the command run although its marker stayed, the override not reaching `-p`, the CI override of `NICE` removed, and the round-one `MAKEFLAGS` check restored (caught on GNU Make 3.81; GNU Make 4.x writes `MAKEFLAGS` in a shape that check read correctly for these cases).
