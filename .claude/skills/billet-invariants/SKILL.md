# Invariants

Rules that hold across billet, each of which cost something to learn.

### The control plane has exactly ONE authoritative writer

**AND ON A SHARED LEDGER, THE CLAIM AUTHORISES THE MIGRATION — NOT THE DIRECTORY LOCK.** `openDir`'s old rule was "migrating is the lock holder's job", which is exactly right while the ledger is a file: SQLite must be on local storage, so holding the directory excludes every controller that could open it. On PostgreSQL it authorises the wrong process — a second host takes its OWN directory's lock happily, so a `billet server` about to be refused as a second controller first upgraded the shared schema, and so did `billet check` run from that host. So a non-admin open takes the controller exclusion BEFORE it migrates, and is refused with `ErrControllerHeld` at the open rather than at a later claim. The ordering is only possible because the exclusion needs no schema: an advisory lock is a server operation, and only the RECORD half of a claim needs a table. An operator command still migrates an UNHELD ledger (somebody has to create the schema on a deployment whose server has never started) and gives the exclusion straight back — holding it would turn every `billet local backup` into a window where no control plane can start, refused by a diagnostic quoting whichever holder the claim row last recorded rather than the command in the way. `DB.unlocked` and `DB.revalidate` are therefore separate: they are only equal while the ledger is a file.

**A STANDBY IS A CONTROL PLANE THAT HAS NOT CLAIMED, AND THE EPOCH FENCE DOES NOT PROTECT IT.** `checkLeadership` exempts a handle whose `claimedEpoch` is zero — deliberately, because `migrate` runs before any claim and `OpenAdmin` holds none — so the fence protects a controller that has been REPLACED and does nothing whatever for one that has NEVER claimed. `state.OpenPostgresStandby` therefore returns a handle whose every `Tx` is refused with `ErrStandby` until `ClaimController` succeeds; reads are allowed. Structural rather than a rule the standby runtime remembers, which is the `readOnlyDBTX` argument one seam over: auditing which goroutines a standby starts is a fence with a hole per goroutine.

**AND THE LEDGER RECORDS WHICH DEPLOYMENT IT BELONGS TO** (migration 45), written by the first claim in the SAME transaction as the epoch and compared by every later one. Two hosts with different `identity_dir` contents could otherwise share one capacity record — each admitting nodes against its own authority, both charging capacity into one ledger. Splitting the bind from the epoch reads as an obvious tidy-up and was MEASURED: with the bind in a second transaction, a process pointed at another deployment's rows advances the epoch, is then refused, and has fenced the real controller out of its own ledger on the way past.

Corrupting the capacity ledger means double-admitting jobs onto a machine that cannot hold them, and the failure is quiet — jobs are accepted, then the host OOMs or thrashes.

- **An exclusive `flock` on the state directory excludes a second CONTROL PLANE, not a second process.** SQLite's own single-writer rule prevents simultaneous *writes*; it does not prevent two billet processes both long-polling GitHub and taking turns writing conflicting decisions. That is what the lock is for, and a second `state.Open` must not start at all. `flock` rather than a PID file, so a crash releases it automatically.
- **An operator command is not a control plane, and opens through `state.OpenAdmin`.** It makes no scheduling decisions and commits bounded transactions, so it proceeds WITHOUT the lock when a plane holds it — otherwise every command that reaches the ledger fails against a live deployment, including `leases release --force`, whose whole purpose is reclaiming capacity on a running one. It still takes the lock when free, because a fresh install runs `billet ca issue` before any server exists and two commands must not race to create the schema.
- **Without the lock it VERIFIES the schema rather than migrating it**, and re-verifies inside every transaction. A newer binary's CLI must never upgrade a schema a running plane is mid-transaction against, and the check at open is only true of the plane that was running then — a restart onto a newer binary can migrate underneath a command already in flight.
- **Writes go through `DB.Tx` on a one-connection pool.** An allocation decision is read-current, decide, record — one transaction, not a read followed by a hopeful write.
- **Every write transaction is IMMEDIATE (`_txlock`), and this is not tuning.** A deferred `BEGIN` takes its read snapshot at the first read and asks for the write lock later, so once a second writer exists, anything committing in that window leaves the first holding a snapshot SQLite cannot promote: `SQLITE_BUSY_SNAPSHOT`, which `busy_timeout` cannot rescue because waiting cannot make an old snapshot current. Measured as error 517 the moment operator commands were admitted.
- **A read-only operation belongs on `DB.View`, never `DB.Tx`.** IMMEDIATE means a read routed through `Tx` reserves the single writer slot while it scans. That put `CertRevokedFor` — which runs on every authenticated node request — and `Headroom` in contention with scheduling, and a growing `PRAGMA quick_check` in front of every operator command until the scan was made the control plane's alone.
- **Contention is a RACE, not a verdict.** `SQLITE_BUSY` is retried rather than returned, because an escrow error stops the listener, which cancels every other listener, whose shutdowns destroy every job on the host. Matched on SQLite's error CODE, never its message: "database is locked" is the text for both plain BUSY and BUSY_SNAPSHOT. The two callers get opposite patience — a control plane never gives up, an operator command has a person waiting and stops with advice rather than hanging.
- **`DB.Reader()` returns a narrow `Querier`, never `*sql.DB`.** Handing out the pool would let any caller write through a connection that is supposed to be read-only.
- **The database MUST be on local storage.** SQLite's WAL is explicitly unsafe on a network filesystem. `Open` reads the pragmas back and fails closed if `journal_mode` is not WAL, which is what catches an NFS state directory.

### Ledger SQL lives in named query files, and nine statements are exempt

Production SQL for the control-plane store is written in `internal/state/queries/*.sql`, compiled by sqlc into `internal/state/ledgerdb`, and bound by `internal/state/queryset.go`. **All of it lives in that one directory**, `internal/alloc`'s and `internal/rollout`'s included, because every guard below is written once against it and then covers every domain. Only those three packages may import the generated package — depguard enforces it — and they import it for its parameter and row TYPES: a `*Queries` in a caller's hands is the whole ledger without the lock, the single writer, `BEGIN IMMEDIATE`, the busy retry or the fence, so the handle always comes from `state.ReadQueries` / `state.WriteQueries`.

- **The schema sqlc reads is a migration directory itself.** No flattened `schema.sql`, so there is no second source of truth to regenerate — and, as a consequence, **a migration is an input to code generation**. Adding one may change generated code; `make sqlc` then, and `sqlc diff` in CI is what catches forgetting.
- **ONE QUERY SET SERVES BOTH ENGINES, and generation runs once with the PostgreSQL one.** Measured: with integer casts spelled `BIGINT`, sqlc's two engines emit byte-identical Go from the same file, differing only in `?N` against `$N` — and modernc.org/sqlite executes `$N`. A `$N` constant runs on both engines and a `?N` constant does not, which is the whole reason for the choice; PostgreSQL is not privileged, and `TestEveryGeneratedQueryPreparesAgainstTheMigratedSchema` is what proves the constants still run on SQLite. **A statement therefore has to be PORTABLE**: `max(a, b)` is a two-argument scalar on SQLite and an aggregate on PostgreSQL, `GREATEST` is the trap facing the other way, and the answer to a statement that will not generate is the portable spelling — never a second query set. See `docs/adr-008-state-backends.md`.
- **The cast is spelled `BIGINT`, never `INTEGER`.** `INTEGER` is `int4` on PostgreSQL and types as `int32` while SQLite types it `int64`, so a query whose Go type depended on which engine generated it would make the shared adapter a lie. A parameterised `LIMIT` is cast for the same reason. `TestEveryIntegerCastIsBigintSoBothEnginesAgree` enforces it, about the WIDTH rather than the one keyword.
- **`ReadOps` and `WriteOps` are hand-written on purpose.** sqlc emits one `*Queries` carrying every method, and binding that to the reader would turn the compile-time read/write split into a runtime one. `ReadQueries` returns `ReadOps`, which has no mutation in its method set; `readOnlyDBTX` refuses `ExecContext`/`PrepareContext` underneath as a second line. `Querier` stays at two methods — the generated `DBTX` wants `PrepareContext`, and a prepared INSERT is still an INSERT.
- **Query files are ASCII.** sqlc rewrites `@named` parameters on byte offsets, so one multi-byte character corrupts every statement after it in the file, and the parse error names neither the file nor the character. The migrations are exempt: they are schema, get no rewriting, and their prose needs the dashes.
- **Never `SELECT *`.** The star resolves at generation time, so a migration silently changes the Row type of every starred query. `-- wildcard-ok: <reason>` is the escape hatch and the reason is mandatory.
- **THE BAN IS MECHANICAL, AND DEFAULT-DENY.** `tools/lint`'s `rawsql` analyzer reports any call that executes SQL from Go, in every non-test, non-generated file in the module — so a new package that reaches the ledger is refused rather than silently admitted. It decides from the callee's SIGNATURE rather than its name (`url.URL.Query` exists, and several packages here call it), which is what makes a hand-rolled wrapper interface covered instead of an escape hatch. Thirteen sites are exempt, each carrying a reasoned `//billet:ignore rawsql` and a row in `internal/state/queries/README.md`: the four pragma reads, `PRAGMA table_info`, the two `sqlite_master` queries (not in sqlc's catalogue), `PeekLedger`'s dynamically-quoted `COUNT` (the table is the variable), `VACUUM INTO`, the embedded bookkeeping DDL, the migrator executing a migration's published bytes, and `readOnlyDBTX`'s two forwarders. `TestTheAllowlistTableNamesEveryRawStatement` compares the table against the directives in both directions, because a directive with no row is an exemption nobody reviewing the table knows about and a row with no directive describes one that is no longer taken.
- **PHASES AND OTHER CLOSED VOCABULARIES REACH A STATEMENT AS PARAMETERS, not as literals**, wherever the set is a fixed list of Go constants — then there is no second spelling to drift from. Two lists could not be written that way, because they are Go SLICES whose length may change and `sqlc.slice()` is not available on SQLite: `forceDestroyPhases` and `quiescencePhases` are literals in `internal/state/queries/forcedestroy_leases.sql`, pinned by `TestTheForceDestroyStatementIsWhatTheGoSliceSays` and `TestTheDrainStatementIsWhatTheGoSliceSays` in both directions. The other unavoidable duplication is the disruption guard, which SQL cannot compose: it is written out in two statements and compared by `TestBothDisruptionStatementsPinTheirWholeStatement`.
- **The gate that matters is `TestEveryGeneratedQueryPreparesAgainstTheMigratedSchema`.** sqlc does not model indexes, so an upsert whose unique constraint a migration removed generates cleanly, compiles, and passes `sqlc diff` — nothing fails until SQLite prepares it on a real write. SQLite's prepare resolves the `ON CONFLICT` arbiter (Postgres's `PREPARE` does not; it defers to EXECUTE), which is what makes the check possible without executing anything.

### Migrations are append-only and identified by version + checksum

**THERE ARE TWO TIMELINES, AND THE POSTGRESQL ONE IS DERIVED.** DDL is the only unportable half of the ledger — `STRICT`, an `INTEGER` column with `CHECK (x IN (0,1))` standing in for a boolean, and the table rebuilds that work around SQLite's `ALTER` limits — so `internal/state/pgmigrations` carries a twin of every file in `internal/state/migrations`. Same versions, same names, its own checksums. Adding a migration means adding both, and `TestEveryPostgresMigrationIsItsSQLiteTwinTranslated` prints the second one: it re-derives four declared substitutions and compares STATEMENT BYTES in both directions, which is stronger than comparing schemas because two files can produce identical catalogues and still disagree about what they *do*. The versions match across timelines on purpose — `state.LatestSchemaVersion()` is one published `int` that two binaries compare across an upgrade without knowing each other's backend — and nothing compares a checksum across timelines, because they are over one engine's own bytes.

Never edit or reorder an existing migration; add a new one. `migrate` verifies a recorded checksum against the binary's SQL and refuses on mismatch, and refuses a database carrying a version this binary has never heard of. Counting applied rows is not a version — a deleted row reruns a migration, a forged row skips one, and inserting one in the middle silently reruns the tail.

**They are files, and the statement bytes are published.** `internal/state/migrations/NNNN_name.sql`, discovered by `go:embed`, parsed by `internal/state/migrationfiles.go`:

```
-- prose, freely editable, above the first marker and between statements
-- +billet:statement
<published bytes>
-- +billet:end
```

The checksum covers the bytes between the markers, `0`-separated, so **that text may never be reformatted** — not the indentation, not a comment inside a `CREATE TABLE`, not the order of two statements. Migrations 1–42 keep the tab indentation they inherited from having been Go raw string literals nested in a struct literal; it reads oddly and it is correct. Commit `ef84c7b` is why the rule is written this strongly: two explanatory lines added inside migration 1's `CREATE TABLE` left every existing ledger refusing to open, with a diagnostic accusing the operator of editing migrations.

`migrationsAreFrozen` in `migrationfreeze_test.go` pins all 42 published sums. Adding a migration adds a line and the test prints the line to add; **changing a line there is almost never the answer** — the honest fix is a new migration. If a checksum test ever fails after a change to an existing file, revert the change rather than the table.

Four things about the mechanism that are not obvious from reading it:

- **The markers are billet's own, not goose's.** A format a third-party tool recognises is a format that tool may normalise, and the bytes are load-bearing.
- **A near-miss marker is refused, not tolerated.** A padded open marker reads as an ordinary comment and silently skips the statement after it; a padded close marker silently joins into the statement before it. Both change published bytes with nothing saying so, which is why `parseMigrationStatements` checks for that case *before* it compares markers.
- **The parse error is stored (`migrationLoad`), not fatal.** A guard that dies during construction never runs, so a duplicate version must still let the freeze test execute and name the two files. The corollary is that any test iterating `migrations` has to ask whether it loaded first — `loadedMigrations(t)` — or it passes vacuously in exactly the situation it exists for. That was found by mutation, not by reading.
- **Versions stay sequential and dense — 1..N, no gaps.** `state.LatestSchemaVersion()` is published as a single `int` in the release manifest, and the upgrade fence refuses a candidate below the installed ledger's maximum. One number is a sound proxy for "knows every applied version" only while versions are dense; a binary carrying `{1..42, 44}` publishes 44, an installed ledger holding the same reports 44, the fence passes, and a later binary that fills in 43 applies it *after* 44 there and *before* 44 on a fresh deployment — two ledgers, identical recorded versions and checksums, different schemas. Density is also what **forces** the collision that makes the scheme work: two branches must both reach for the same integer, so CI names them and the one that has not shipped renumbers. `TestMigrationVersionsAreDenseFromOne` is the guard, and the distinction matters: the first version of it asked only whether a *new* version sat above the published maximum, which was vacuous in every green tree (the freeze test requires every migration to be published, so the comparison never ran) *and* permitted 44-without-43. Measured — a tree with exactly that gap passed both version tests. Asserted in CI rather than in the parser on purpose: a gap is an authoring mistake here, and a released binary refusing to start over one would take a fleet down for something a test should have caught.

Two seams that are not obvious from the migrator:

- **`state.RefuseUnknownVersions` is the one COLD entry point into the version rule.** `internal/deployarchive`'s restore planner calls it before anything has opened a ledger, so unlike every other reader it is not downstream of `openDir`'s gate — it calls `requireMigrations` itself. Without that, a binary whose embedded set failed to load answered from an *empty* known set and was wrong in both directions: an archive carrying migrations was refused as "written by a newer version" (sending an operator after a newer binary for a fault in the one they have), and an archive whose applied set was empty was **accepted**, which the planner reads as permission to install a ledger this binary could never open.
- **Tightening the parser's statement predicate after a migration has shipped is a flag day.** `checkStatement` runs in production, on every open, over files that are already published — so a new refusal there does not reject a bad commit, it stops every control plane that has the file. A rule about what a *new* migration may contain belongs in a test; only a rule no published statement can possibly violate belongs in the parser.

### Cache TLS interception defaults OFF, per tier

`ACTIONS_RESULTS_URL` carries **artifact** metadata as well as cache traffic, so anything in that path is in the user's release path. `Tier.Intercept` is opt-in, and tiers that publish release artifacts or hold deployment secrets must not enable it. A mistake here does not slow CI down; it breaks a deploy.

The protocol is reverse-engineered — GitHub has never published the `.proto` files — so the cache must **fail open to a miss** on any error, never fail a job, and a conformance suite must run the real `actions/cache`, `upload-artifact` and `download-artifact` against live GitHub to catch drift. Both are requirements on the cache when it is built (P4); neither exists yet, and nor does the cache.

**The plaintext cache adapter binds the guest's docker gateway and nothing further out.** It exists for a container-driver BuildKit that cannot trust the node's CA, and a container reaches the guest only through its bridge gateway, so that is where the adapter listens; the node mints signed blob URLs naming a loopback or private address only, and the adapter refuses any other bind. What exposes it inside the guest is the job's own containers on a trusted tier, which is the boundary interception already accepts. The `docker` shim in the guest image is what points a build at it with no workflow change; it rewrites `ACTIONS_RESULTS_URL` for build invocations only, because that origin also carries artifacts and logs the adapter does not serve.

### The macOS guest limit is enforced against `guest_os`, never a label

Keying the limit off a label matching `macos` means a tier named `sonoma-arm64` escapes it entirely, and a Linux tier named `builds-macos-artifacts` gets capped for no reason. `Tier.GuestOS` is the explicit field, a macOS tier pins a `node` unless it lists several providers (the owned-Mac-plus-managed-fleet shape, where the hosts are the declared `nodes[]` policies for each backend and the tier's `max_concurrent` is bounded by what they permit between them; a reservation stays pinned), and per-node totals are summed at load. Warm instances count.

The config check is a **guard, not the enforcement point**: the allocator holds a single host-wide count of running plus warm macOS guests at runtime, because two individually-valid tiers still share one physical Mac. Both read the effective limit from the same `NodePolicy`, so there is one number rather than two that drift.

**The limit is per host and configurable; `DefaultMacOSVMLimit` is a default, not a ceiling.** Apple's standard licence permits two macOS guests per Apple-branded host, which is what a config that says nothing gets. But what a host may run is a deployment decision, not a fact about the hardware — an Apple Silicon machine can serve macOS guests, Linux arm64 guests, or both — so `nodes:` carries a per-host `guest_os` allowlist and `macos_vm_limit`. Raising the limit is permitted because billet cannot know what licence or hardware agreement an operator has; it is an assertion about their licence, which is why the diagnostic names Apple only when the limit came from the default.

**AND THE DEFAULT IS ABOUT AN APPLE HOST SOMEBODY OWNS, WHICH IS NOT THE ONLY WAY TO REACH A MAC.** A `codebuild` node reaches Apple silicon through a reserved-capacity `MAC_ARM` fleet AWS operates under its OWN agreement, so Apple's per-host allowance is not billet's to apply — and applying it silently caps a five-instance managed fleet at two concurrent builds while blaming Apple in the diagnostic. The default is therefore keyed on `ProviderKind.RunsOnHost`: a backend that runs work on the machine gets Apple's number when nothing was declared, and a remote one gets no cap of its own, because its cap is the fleet capacity the operator declared through `node.max_vcpu`/`node.max_memory` and its shape list. A CONFIGURED `macos_vm_limit` still applies to either; what changed is what silence means. This is the shape to look for whenever a default encodes a fact about hardware: ask whether the hardware is the thing being described, or the thing somebody happens to own.

Two rules keep that from becoming a footgun. A tier pinned to a host that does not permit its guest OS is a load-time error rather than a job that queues forever with nothing saying why. And `macos_vm_limit > 0` together with a `guest_os` allowlist excluding macOS is rejected instead of silently resolving — a config that reads as "two macOS guests" must not schedule none.

**Placement is checked where the host is known, and again at the launch boundary.** Config validation cannot see every placement: an *unpinned* tier names no host, so nothing ties it to the allowlist, and a scheduler that simply picked a node with free capacity would put a Linux guest on a macOS-only Mac. `nodeplane.pick` is where a host is first chosen and it checks the tier's allowlist there; `Bind` is where the allocator durably validates that choice, and it is the one that has to hold, because a node cannot route around it. The load-time guard covers what it can prove — a pinned tier, or an unpinned one against a host declaring the *same provider*, since a Firecracker tier can never land on a Tart host and comparing guest OS alone would make one macOS-only Mac an error for every x64 Linux tier in the deployment.

`Bind` alone is not enough, for two reasons that each looked fine in isolation:

- **Nothing required it.** `assigned → launching` succeeded on an unbound lease, so a caller could pick a host outside the allocator and every check inside `Bind` would never run. Every phase that presumes a running host — `launching`, `online`, `busy` — now requires a bound node. Gating only the `launching` edge is not sufficient either: a row left in `launching` by an older binary would walk on to `online` untouched.
- **Binding is not launching.** A lease can be bound while still in `capacity`, so a policy tightened in between would let the instance start on a host that no longer permits it. Placement is re-checked on entry to those phases against policy in force *then*, making the guarantee "legal now" rather than "was legal once". Only a repeated `Bind` is grandfathered, because it changes nothing.

**A lease whose placement facts are unverifiable fails closed.** A row predating the `provider` column records `""`, and tolerating that would be a bypass rather than a compatibility courtesy — such a lease may still be *unbound*, so it is not old work already placed but unplaced work whose backend nothing can check. `Reap` and `Release` deliberately do not consult these checks, so a lease refused this way can always be cleaned up; failing closed on something unrecoverable would just strand capacity.

That rule is also what protects rows that no migration can classify. `macos_slot` only became truthful at migration 5, which added it defaulting to `0` without a backfill, so a macOS lease older than that is indistinguishable from a Linux one. Migration 7 repairs what it can and the rest are refused rather than guessed at.

The lease's `guest_os` is recorded at reserve time for the same reason as `target_node` and `macos_slot`: a tier redefined underneath an in-flight lease must not reclassify what that lease is allowed to bind to.

**`NodePolicy` is deep-copied when the allocator is built.** `GuestOS` is a slice and `MacOSVMLimit` is a pointer, so copying the map alone still shares both — letting a caller widen an allowlist or raise a cap after construction, moving a licence limit out from under leases already counted against it. `NodePolicy.Clone` owns that, so there is one place to get it right.

### A rule about someone else's API is pinned to measured behaviour, not to reasoning

The runner-group validator began as an allowlist of "URL-safe" characters and was wrong in both directions: it rejected `team=platform`, `who?`, and every non-ASCII name — `Grupo-Ñ`, `研发` — while missing `;` entirely. The client interpolates the name unescaped into a path, then `url.Parse`s it, reads `Query()`, and re-`Encode`s it, so the only question that matters is whether a character survives that round trip. Running it settled it in a minute: `&` `#` `;` `%` `+` do not, everything else does. `;` is the one no amount of reasoning would have produced (Go's `ParseQuery` has rejected it as a separator since 1.17).

The test asserts the **property**, not the list: every name the validator accepts is put through the client's exact transformation and must come out unchanged. When a rule encodes an assumption about code you do not own, pin it to what that code does — a probe costs a minute, and a plausible-sounding character list is exactly the kind of thing that is confidently wrong.

### `created` is not `running`

`docker ps` reports created/running/paused/restarting/removing/exited/dead. A container that exists but was never started never will be — whatever would have started it is gone — so adopting it holds a lease open forever for a job that cannot begin. It is the one state that looks alive and is not.

An **unrecognised** state still counts as running. The asymmetry is deliberate: the caller destroys what is not running, and a state billet has never heard of is not evidence that a job is over.

### One representation per configuration value, and the choice is per field

Validation examining a trimmed copy while the consumer uses the raw string has now been found **three times** in `internal/config`, and it is silent every time: the config loads, and then something on another machine — or GitHub — disagrees about what it named.

Two answers, and which one applies is decided by whether anything outside this process has an opinion about the value.

- **A path, pool, region or endpoint is NORMALIZED, and the result is written back.** `CephConfig.normalize`, `EC2Config.normalize`, `EBSS3Config.normalize`, `RegistryMirrors.normalize`, `trimNodeName` in `applyDefaults`. `image_pool: "  tank  "` passed the shape check and was handed to `rbd` with its padding, which is the bug that produced this rule. Normalizing is only safe because it happens once, before every validation AND every consumer, and the loaded config carries the result.
- **An IDENTITY is REFUSED.** `sites[].name`, `tiers[].site`, `node.site`, `github.org`, `tiers[].runner_group` — see `checkIdentityPadding`. A site name is matched against what a node's registration presents on a different machine; an organization is matched against what GitHub has. Trimming those changes which deployment or which organization the config names, invisibly. The operator sees their own bytes instead.

The one that shipped: `validateSites` trimmed to build its authority set, `nodeplane.WithSites` keyed the map on the raw name, and `alloc`'s placement compared raw. A deployment declaring `" home "` authorised `tiers[].site: home` at load and then refused every node reporting `home`, forever, with nothing at startup saying why.

**A rule about a string that leaves this process is pinned to both boundaries it crosses, not one.** `github.org` goes into the scale-set client's config URL by UNESCAPED concatenation and into the REST path through `url.PathEscape`. Only the first can be damaged, and sweeping printable ASCII through both — the `runnerGroupUnsafe` method — returned exactly `#%/?`: `/` makes the vendored client resolve a REPOSITORY and report nothing at all, `#` and `?` truncate the name to what precedes them, `%` decodes. Surrounding whitespace survives both intact, so it is refused as an identity mistake and **the comment says so** — a rule whose stated reason is untrue is worse than no rule.

**And config validation cannot test any of this itself.** depguard forbids `internal/config` from importing another billet package, tests included, so a package-local test can only assert the validator's own copy. The cross-layer proofs live in `internal/integration`, assemble the pieces the way `cmd/billet` does, and assert the operational consequence — a node registers, a request reaches GitHub naming the right organization.

### Never guess at a byte size

`config.ByteSize` parses with exact integer arithmetic on a restricted grammar. It used `strconv.ParseFloat`, which accepts `NaN`, `Inf`, hex and exponents, and loses precision above 2^53 — and converting any of those to `int64` is implementation-defined and can come out **negative**, which silently disables the capacity ceiling. Reject what cannot be represented exactly.
