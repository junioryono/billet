# Automatic updates and the release watermark

Part of the `billet-releases-and-upgrades` skill. Each rule is stated in full, with the measurement or incident behind it.

**A deployment updates itself unless `release.automatic` is written `false`.** `config.ReleaseConfig.Automatic` is a `*bool` whose nil is true, read only through `AutomaticUpdates()`; it is the one switch for the starter, the scheduled updaters and the image refresh. `internal/rollout.Starter` runs beside the coordinator hourly and is network-free: `internal/app/rolloutwiring.go`'s `channelResolver` resolves the channel and runs `releasesource.Compatibility` through the same `app.ResolveTarget` the command uses, and `app.ReleasePolicyFor` is the one answer to what a manifest must be signed by (it honours `release.signing_identity`; the `--skip-signature-verification` waiver still wins). A tick starts nothing over an open rollout, nothing for a fleet already on the target (a host reporting no release is not on it), never an older release, and never a digest an operator aborted (`Store.NewestForTarget` for the sentence, and `StartRequest.RefuseAbortedTarget` for the refusal that holds, inside `Start`'s own transaction as `ErrAbortedTarget`, until the channel moves); a resolution failure is said once per six hours and waited out. `server.WithRolloutStarter` is what wires it, asserted structurally by `rolloutstarterwiring_test.go`.

**The controller's own upgrade is a root timer, and `--from-rollout` is what it runs.** The server is unprivileged, so `billet-upgrade.timer` (packaged, enabled by postinstall, rendered and enabled by the Ansible role; `sh.billet.upgrade` on a Mac, installed by `local up`) runs `billet host-upgrade --from-rollout` every five minutes: `rolloutInstruction` reads the open rollout, or the newest finished one, through `openStateAdmin` (`readFleetDecision`): it exits 0 saying why when there is no control plane here, `automatic: false`, no decision, an aborted one, a host already on the target, or a completed rollout whose target is older without `AllowDowngrade`; otherwise, converged controller phase or not, it runs `startHostUpgrade` with the rollout's pin, digest, id, generation and `AllowDowngrade`, under every existing fence, because a PostgreSQL standby is a controller host the phase says nothing about and its timer fires into a ledger whose rollout may already have completed. A completed rollout is taken ONCE: its generation must exceed this host's SETTLED mark (`settled-decision`, raised by `settleCommitted` in `finishHostUpgrade` when the journal reads committed, a required step whose failure is a non-zero exit rather than the lost diagnostic a provenance failure is, and by the on-target no-op, never by an attempt that rolled back, so a rolled-back standby is asked again while a host an operator moved by hand is not moved back every five minutes); the on-target no-op (`settleOnTarget`, under the host transaction lock so it cannot bless another updater's unproven candidate) raises `last-decision` too, exactly as `actOnResolved`'s does, so a delayed older decision cannot pass the fence. `readFleetDecision` opens through `openStateForDecision`, the one open in `ledger.go` that names no release (exempted by name in `ledgerrelease_test.go`), because a standby's timer is the older binary the leader's watermark would refuse; it still cannot read a schema newer than its binary, and it opens only an EXISTING SQLite ledger (`state.LedgerPath`), since the package enables the timer before the server has ever run and an operator open would mint a root-owned ledger. An operator's own run on a control-plane host settles through the fleet's last completed generation (`Journal.SettlesThrough`, `settlesThrough`), so a host a person deliberately put elsewhere is not moved back by the timer; a timer process overtaken by a dispatched updater that installed the same manifest (`provenance.Installed()` equals the target digest) settles and does nothing instead of reinstalling. `ledgerHost.downgradeTo` is set only for a PROVED downgrade (`version.Compare(ToVersion, FromVersion)`), never on the flag alone, or an upgrade run with `--allow-downgrade` would raise an external ledger's mark before a probe that has no snapshot to undo it. The watermark itself is written inside the claim's transaction (`raiseReleaseWatermarkIn`), never after it. The instruction is re-read in `actOnResolved` after the claim and before the ack (`confirmFleetDecision`, `fromRollout`), refusing `ErrSuperseded` if the rollout was aborted or replaced in the meantime. It takes no other target flag and no ack path. A standby PostgreSQL controller is not a node in a rollout, so it runs the timer too. `hostPathsFor(hostOS)` is the one answer to where the binary and the upgrade root live (`/usr/bin/billet` and `/var/lib/billet/upgrades`; `/usr/local/bin/billet` and `/usr/local/var/lib/billet/upgrades` on a Mac), and `provenance.DefaultPathFor` the record's.

**The ledger records the newest release that has served it, and every open refuses a proved older binary.** Migration 48's `release_watermark` singleton; `state.WithRunningRelease` on every open in `cmd/billet/ledger.go` (asserted structurally by `ledgerrelease_test.go`); `enforceReleaseWatermark` after the schema is settled. Only the control plane proper records (`openMode.records()`: not admin, not standby, not the probe), and only in `ClaimController` after the deployment binding, or a `billet check` from a newer laptop binary, or a newer server pointed at a foreign ledger, would fence the running server out of its own restart; a promoted standby records there too, and a revalidating admin handle re-reads the mark inside every write. `version.Compare` is the one ordering, and it orders BOTH spellings of a release, `v0.9.1` and `0.9.1`, because the release build stamps GoReleaser's `{{.Version}}` (bare) and releases through v0.9.1 reported, journaled and registered that form; `version.Version()` now spells a release as its tag, `version.Same` is equality across the spellings (never `==` on a release string), `version.IsRelease` stays the tag grammar for pins and the watermark, and `version.Canonical` turns a bare report into the tag before it is recorded (`alloc.highestRelease`). Could-not-tell (a dev build) neither refuses nor records. `cmd/billet/hostupgrade.go` reads the running release through the `runningRelease` seam so a test can stand a release in for "(devel)"; the from-rollout and downgrade tests now use the bare shape production had. A deliberate downgrade is `--allow-downgrade` on `rollout start` (persisted in `Policy.AllowDowngrade`) and `host-upgrade` (on the journal): `ledgerHost.Migrate` lowers the mark through `SetReleaseWatermark`, the one write allowed to move it backwards, on a maintenance handle after the snapshot that keeps the higher mark for a rollback; on an external ledger, where `migrated` is skipped and the maintenance open is a read-only probe, `ledgerHost.ProbeReady` lowers it through the operator handle first. `checkDowngrade` refuses an unnamed downgrade before anything drains, and precedes the claim (`downgrade_test.go`); `rollout start --allow-downgrade` additionally refuses a target before v0.9.2 (`checkConvergibleDowngrade`, wired between the downgrade check and `Store.Start` and asserted structurally), because a control plane downgraded to a release that names itself without the v runs the old coordinator, never sees itself on the target and dispatches no node; `host-upgrade --version <tag> --allow-downgrade` is the one-host route it names. The role's own downgrade check accepts both spellings in its pattern (`billet_release_tag`, `^v?...`), or an older candidate read as "not a release" slipped past it. Nodes carry `highest_release`, reported by `billet status` as `DOWNGRADED` and never refused, because the coordinator's rollback inference IS an older re-registration.
