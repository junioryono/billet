# The host-upgrade transaction

Part of the `billet-releases-and-upgrades` skill. Each rule is stated in full, with the measurement or incident behind it.

**`billet host-upgrade` is a separate detached program with everything on disk.** `internal/hostupgrade` owns the order over a narrow interface: `claimed → staged → stopped → imaged → fenced → snapshotted → installed → migrated → probed → committed | rolled_back`. `imaged` is the candidate proving this host's guest images compatible with it (`images compatible` from the STAGED binary, its exit status the answer: 0 nothing to do, 2 pull these, anything else could not tell and refuses) and pulling a generation for each that is not through `images pull --verify`; it sits after the stop, because nothing may launch against a generation mid-import, and before the fence, because a pull records in the cluster rather than the ledger, and it has no unwinding. That is the Go half of what the Ansible role's transaction already did (`services.yml`, "Pull, boot-verify, and promote every compatible guest needed"). The ledger is snapshotted before it is migrated (the one step the old binary cannot undo); the fence opens only after the commit record (opening admits operator writes a snapshot restore would discard); a rollback unwinds exactly what the journal says was reached, ledger first. `TestAHealthyUpgradeRunsInOrder` asserts the whole sequence, because the failure mode is a step moving. The journal is fsynced with its directory, `Reached` is the resume decision in one place, and a journal with a failure recorded before the rollback finished is re-entered through `rollBack` rather than advanced, or a resume would probe the restored old binary and record a committed upgrade to a release the host is not running. An unprovable rollback is cordoned (`ErrCordoned`) with its journal intact. Before the claim and before the node is told the job was taken, `actOnResolved` calls `refuseUnmetUnitRequirements`: it judges the candidate's VERSION against the loaded node unit from this build's table, `deploy.NodeRuntimeRequirements` (`billet/registration` since v0.11.0, the first release that publishes the record; a release whose order cannot be told is held to every entry), because a rollout installs no units (#168). It is a preflight refusal, answered to the node, so the rollout backs off and retries. TWO PLACES IT MUST NOT BE, each found in review: inside `Run`, a refusal is a rollback, and a decided journal reaches every step, so the services would be started and the uplink restarted on a host nothing touched; after acceptance (which precedes the download, so the staged candidate was asked there), a refusal leaves the coordinator waiting in `draining` on a host that never moves, and on a resumed journal at `staged`, which may be inside its stopped step, giving the claim back deletes the only copy of the binary it hid. A node unit `not-found` or `masked` holds nothing; a requirement a later release adds is that release's table to declare (`TestTheUnitRequirementsAreJudgedBeforeTheClaim`).

**One transaction, two service managers, three ledgers.** `newHostFor` picks `systemdHost` on Linux and `launchdHost` on darwin and refuses anything else before the ack; both embed `ledgerHost` (fence, snapshot, migrate, provenance, probes). The Mac host boots out with `StopAndProve` (every pid proved gone), bootstraps with `StartAndProve`, preserves the two plists from the converger's agents directory beside the binary and config, and refuses before the ack when `/usr/local/bin` is not writable by this account (`checkBinaryDirWritable`; the Mac setup chowns it). A `Setsid` child survives its agent's bootout (measured, `realscheduled_test.go`). The transaction's image step, `Host.PrepareImages` (the `imaged` step, after the stop and before the fence), is the candidate's `images compatible --result-file` then `images pull --verify` per listed image on firecracker, `pullTartImages` on tart. On a PostgreSQL ledger the journal carries `Ledger: external` and `advance` records `fenced`, `snapshotted` and `migrated` as reached without doing them, `rollBack` restores no ledger and `finish` clears no fence; the probe is `state.OpenPostgresProbe` (the standby's open across the fence, writes refused, nothing claimed or migrated), and the migration happens when the candidate claims. The rollback boundary there is the candidate's start.

**Two answers over a Unix socket, and a spawn is not an answer.** `ExecUpgrader.AckDir` is the node's private writable state directory, wired from `cfg.Node.StateDir`; `StartUpgrade` listens at `upgrade-ack-<random>` and closes the listener on every return, which unlinks the socket. `--ack-path` replaces `--ack-fd` (the node launches its own binary, so the two ends share a version). The updater dials with a five-second bound and writes one bounded `AckAccepted` or `AckRefused` line when it has accepted responsibility or refused preflight; a missing listener is best effort and never holds the claim. Accept and read each have a ninety-second deadline: never connecting is "did not say within", connected EOF is "stopped without saying why", and a read without its newline is not an acceptance (`MaxAckBytes` plus one). Under systemd (`linux` and `INVOCATION_ID` present), `launch` runs `systemd-run --unit=billet-host-upgrade-<rollout>-g<generation> --service-type=oneshot --collect --quiet --no-block --property=TimeoutStartSec=88200 -- <binary> host-upgrade ...`: the root unit escapes the node's read-only mount namespace and cgroup, its name prevents concurrent redelivery, and `CombinedOutput` reports launcher failures immediately. `--no-block` matters because a oneshot's start job lasts the transaction; the node waits only on the socket. The transient unit receives the configured PostgreSQL DSN environment variable through `--setenv=NAME` without its value in argv; `internal/ops/host/nodeupgrade.go` reads the name from `cfg.Server.LedgerDSNEnv()`. Present `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, and `AWS_SESSION_TOKEN` variables are forwarded the same way, because the candidate server probe resolves an SSM App key before it can succeed and must retain the configured AWS identity. The fake service manager clears the inherited environment and forwards every explicit entry so DSN, access key, secret and session-token forwarding are observable together. Instruction, config and conflicting-flag refusals answer immediately after flag parsing. `ExecUpgrader.Check` runs at node startup and in its candidate probe, refusing an absolute state-directory path whose generated socket name exceeds 107 bytes on Linux or 103 on macOS (measured with Go `ListenUnix`, 2026-09-06). Off systemd the updater remains a `setsid` child, reaped by a background `Wait` (`Process.Release` does not reparent). Systemd nodes through v0.9.2 need one manual move onto the fixed dispatcher, because FROM launches the transaction. The full rehearsal needs the fix in FROM, not just TO.

**The probe answers by exiting or by saying it is ready, the candidate says which, and the fence is cleared under the reason it was written with.** Two callers run `--upgrade-probe` with opposite contracts: the Ansible role runs it as a `Type=notify` unit's own ExecStart and stops it itself, so there it holds until told; `billet host-upgrade` runs it as a plain child and waits for it to exit. The role's unit passes `--upgrade-probe-hold` and nothing else does, and only after asking the staged candidate's `-h` whether it lists the flag (a downgrade renders the older shape); `holdProbe` prints the readiness line and holds ONLY on that flag, so the line and the silent zero exit are disjoint protocols. NOTIFY_SOCKET is NOT the tell, because a node's detached updater inherits its unit's socket and so would the candidate. `runCandidate` asks the candidate's `-h` the same question (`candidateHoldsOnFlag`): one that lists the flag is judged by its exit status alone and a readiness line from it is refused as a broken protocol; one that does not is a release through v0.9.0, its line means "stop me" and is its only proof (silent exit zero is a could-not-tell, refused); it answers SIGTERM by exiting zero, so its exit status is its verdict and a signalled death is a refusal whoever sent it; SIGKILL is always sent before the reap because output closing is not exit (the shipped probes hold their descriptors until exit, so a closed output is a zombie the kill cannot change; one that closed its output and kept running is killed and refused); the deadline is `runCandidate`'s own and never `exec.CommandContext`'s, whose kill runs beside `Wait` and on a kernel without pidfd may reach a reused number, so every signal precedes the one `Wait`. A candidate whose exit never arrives after SIGKILL returns `hostupgrade.ErrUnsafeToRestore`, and so does an output (the probe's or the usage question's) still held open once the candidate has gone, or one that could not be read to its end, because the open pipe proves a live descendant and the unread one proves nothing; those verdicts outrank what the candidate said or how it exited; `Run` cordons without restoring, since a rollback over a live process is the one outcome worse than a hung probe. The usage question owns its pipe like the probe does, bounded by `probeUsageWaitDelay`; the role wraps its own copy of the question in `timeout -k 10 60` and refuses a non-zero exit before stopping anything. The candidate is reaped only after the last signal it might be sent, so its pid is anchored by the zombie on every platform (`Wait` runs after the stop, never beside it); nothing is signalled by process-group number; anything still holding the candidate's output past `probeOutputGrace` fails the probe, and a process that closed the output before detaching is not seen. The parent owns the output pipe and reads it to its end before any verdict; the readiness line is matched whole (`serverProbeReadyLine`, `nodeProbeReadyFormat`); a silent candidate fails at `candidateProbeDeadline`. Before v0.9.1 each half waited for the other and every self-upgrade hung at the probe with the services stopped. The maintenance fence is written and cleared under `fenceReason`, one string, because `state.ClearMaintenanceFence` refuses any other; the commit and the rollback each used to name their own outcome there and both cordoned. Both were found by the rollout rehearsal on 2026-09-05, not by a test: the fake host ignored the reason, and `internal/hostupgrade/fence_test.go` now lets the real ledger judge it.

**The uplink shaper is moved onto the binary the transaction leaves, last, and its failure decides nothing.** `billet-uplink.service` (the host role's, running `billet uplink shape`) is a billet process outside the node and the server, so no other step touches it, and on 2026-10-16 a Linux node moved from v0.16.5 to v0.16.6 by a rollout kept its shaper on the deleted old binary after the commit: the shaper's own check for a replaced executable runs once a minute, and an operator restarted it first. `Host.RestartUplink` is deferred in `finish` and in `finishRollback`, so it runs after the services on every way out of either (a committed upgrade whose services failed still has the candidate installed; a rollback put the preserved binary back as a new file, and the shaper may by then run the candidate). On systemd it is `Converger.RestartIfRunning`: only `LoadState=loaded`, exactly `UnitFileState=enabled` and an `ActiveState` of `active`, `activating` or `reloading` restarts (then `ProveStable`); not installed, masked, not enabled or not running is left alone and printed; any state systemd did not state is an error. Its error is a `log.Warn` naming `systemctl restart billet-uplink.service` and never fails, rolls back or cordons (`internal/hostupgrade/uplink_test.go`); the launchd host has no shaper. The package scripts restart nothing, by design, so a package upgrade still relies on the shaper's own check.

**A host keeps its three newest decided recovery directories (`pruneRecoveries`).** After a committed or rolled-back transaction releases its claim, and whenever the controller's `--from-rollout` tick finds nothing to do under the lock it holds (never on a guarded host), older `upgrade-*` directories whose own journal, read through the root's descriptor and judged like any journal, records a decision are removed through descriptors, never following a link; the claim's target (compared by identity, so a relative pointer still protects it), a directory that is not the same one before and after its journal was read, an undecided or unreadable journal and the role's directories are kept, and a failed removal is reported without changing the outcome. A removal goes through a descriptor proved to be the judged inode, and unlinks the journal last, after flushing the directory (unlink order is not the order a power cut preserves), so a removal cut short still carries its proof. It never descends into a mount: `requireSameMount` refuses another device, and on Linux a mount root by `statx` (`STATX_ATTR_MOUNT_ROOT`, a kernel that cannot say being could-not-tell), because `O_NOFOLLOW` does not stop a descent into a bind mount and an rmdir refuses one only after its contents are gone (Codex, round 5) and the next pass judges it again and finishes it; a staging rename tried first (`.removing-<name>`) made the prefix itself a permission nothing had proved (Codex, rounds 2 and 3). Listings open their own descriptor of `.` (`listDir`): a second `ReadDir` on a descriptor already read answers nothing, which hid every candidate once the first version listed the root twice. Measured: 45 committed transactions held 6.7 GB of a 15 GB controller root at 98% (2026-10-13), because retention had been left to a person on a fleet that updates itself. Then the v0.16.1 -> v0.16.3 upgrade that shipped the prune removed none of the 46 (2026-10-14), because the transaction is carried out by the binary installed before it; the idle timer tick is what reaches a host whose last upgrade was carried out by a release that did not prune.

**The claim bounds concurrency; the decision mark fences generations; the transaction lock is a lock.** `/var/lib/billet/upgrades/active` is a symlink to the recovery directory (the journal publishes through a rename, so a hard link would go stale), released on commit or rollback and not on cordon, published after the journal (the reverse let a resume clear the claim of a live upgrade). `last-decision` is the high-water mark written before the transaction starts: equal is a redelivery, strictly older is refused (`ErrSuperseded`), unreadable refuses a fenced instruction and never an operator's unfenced run (`ErrUnreadableDecision`); both acceptance branches record first (`TestANoOpUpgradeRecordsTheDecisionBeforeAcceptingIt`), because a no-op that accepted before touching the fence let a delayed older generation downgrade a machine. The mark has its own lock (`decision.lock`), because the already-installed path runs no transaction and has nothing to claim; `checkAndRecordDecision` is one acquisition. The transaction flock is taken non-blocking before the network, because resolving a channel can hang past the node's acknowledgement and every retry started another stuck process; lock order is transaction lock then `decision.lock`. A generation of zero means an operator is at the keyboard; a `--rollout` with no `--generation` is refused.
