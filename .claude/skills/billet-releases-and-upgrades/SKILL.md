# Releases, rollouts and host upgrades

## What this area is

A release is a semantic-version tag (`vX.Y.Z`, because Go resolves nothing else; staying on `v0` keeps the module path free of a suffix) cut from a `release/vX.Y` branch by the `cut-release.yml` workflow, built by `release.yml` through GoReleaser (`.goreleaser.yaml`), and published as immutable archives, `.deb`/`.rpm` packages, a signed `release-manifest.json` and a moving `v0` tag. `internal/releasesource` reads manifests and channel statements; `internal/provenance` records which manifest produced the installed binary. `internal/rollout` is one durable fleet decision and its coordinator; `internal/hostupgrade` is the journaled transaction that replaces billet on one machine; `cmd/billet/upgradedecision.go` is the fence between them. `docs/reference/decisions/adr-006-rollouts.md` and `docs/operating/upgrades.md` are the design and the operator page.

## Rules

**What a release publishes.** Builds are `CGO_ENABLED=0` for linux/darwin × amd64/arm64 minus darwin/amd64 (matching `make cross`), `-trimpath -s -w`, with version, commit and date injected into `internal/version` (a `-trimpath` build with `-buildvcs` can silently produce `(devel)`). Archives are `billet_<version>_<os>_<arch>` (a contract `install.sh` derives from `uname`) carrying `README.md`, `LICENSE`, `billet.example.yaml` and both plists (a Mac has no package). `nfpms` builds deb and rpm only, depending on `e2fsprogs` and `kmod`, shipping the four units and `billet-rbd.conf`, the config template at `/usr/share/billet/billet.yaml` (not under `/usr/share/doc`, which slim Debian images path-exclude) and `/etc/billet` as a 0750 directory; `/var/lib/billet` is deliberately not packaged so a removal cannot delete the identity and CA key. There are no `before.hooks`, because a `go mod tidy` there edits `go.mod` during the build. The snapshot version is `0.0.0-SNAPSHOT-<sha>` because Debian requires a leading digit.

**The manifest is built and signed inside GoReleaser's `signs` stage, and that ordering is forced.** Release immutability freezes assets at publication, so an upload after the fact is refused; `release.extra_files` is what puts `release-manifest.json` and its `release-manifest.sigstore.json` bundle in the release, asserted structurally by `scripts/releasemanifest_test.go`. `scripts/mkreleasemanifest` reads every compatibility fact out of the packages that define it (the wire range, `state.LatestSchemaVersion`, the guest contract, the rollback target), never from YAML; a snapshot writes the manifest and does not sign it (keyless signing needs an OIDC identity). `checksums.txt` answers "did these bytes arrive" and nothing else; every one of the four facts has to be readable before anything stops.

**A release manifest is signed as `release.yml@refs/heads/main`, and the policy says so.** The cut button runs on `main` and calls `release.yml`, and a Fulcio certificate names the requesting workflow under the ref of the run that requested it, so the SAN is `.github/workflows/release.yml@refs/heads/main` (measured on v0.6.0's bundle, 2026-09-04 UTC); a hotfix tag pushed by hand runs it under `refs/tags/vX.Y.Z`. `releasesource.PublishRefPattern` accepts exactly those two. Before 2026-09-04 it accepted `refs/heads/release/vX.Y` or `refs/tags/vX.Y.Z` on the belief that release.yml "runs against the tag", so every binary through v0.6.0 refuses every manifest billet has published: `rollout start`, the automatic starter and `host-upgrade --version` all fail on those releases with "the manifest's signature does not satisfy this source's policy", and a fleet on them has to be moved by the Ansible role or the package once. The first rollout rehearsal found it in its first step. `release.yml`'s job runs only when `github.repository` is this repository, because a reusable workflow called from a foreign repository would be issued that same identity over the caller's source; the verifier also requires `SourceRepositoryURI` to name billet for both default release and image policies (`internal/imagesource/verify.go`). The source binding is necessary even with the current workflow guard: older tagged reusable workflows remain callable. An explicitly configured different signing identity keeps its operator-selected trust policy.

**`cut-release.yml` calls `release.yml` rather than relying on the tag push.** A ref pushed with `GITHUB_TOKEN` starts no workflow (GitHub's recursion guard), and a `workflow_call` is not an event, so billet needs no PAT. Before tagging it rewrites the internal composite-action refs and `galaxy.yml` to the release version. One branch per minor carries every patch; a hotfix is a commit on `release/vX.Y` plus the same button with the patch version, then merged back into main or the next release reverts it. `release.yml` proves the release immutable, then polls the attestation API for a GitHub-initiated bundle at the tag ref's digest and runs `gh release verify` with an exact-tag filter (several tags can share one commit; `bundle_url` is a URL, not inline JSON); the verifier is checked out from `github.workflow_sha`. Then `scripts/advance-release-channel.sh` publishes a signed, expiring (ten days), self-naming channel statement (`stable.json`, `candidate.json`) that refuses to regress, so a hotfix on an older minor leaves the pointer alone.

**A deployment updates itself unless `release.automatic` is written `false`.** `config.ReleaseConfig.Automatic` is a `*bool` whose nil is true, read only through `AutomaticUpdates()`; it is the one switch for the starter, the scheduled updaters and the image refresh. `internal/rollout.Starter` runs beside the coordinator hourly and is network-free: `cmd/billet/rolloutwiring.go`'s `channelResolver` resolves the channel and runs `releasesource.Compatibility` through the same `resolveTarget` the command uses, and `releasePolicyFor` is the one answer to what a manifest must be signed by (it honours `release.signing_identity`; the `--skip-signature-verification` waiver still wins). A tick starts nothing over an open rollout, nothing for a fleet already on the target (a host reporting no release is not on it), never an older release, and never a digest an operator aborted (`Store.NewestForTarget` for the sentence, and `StartRequest.RefuseAbortedTarget` for the refusal that holds, inside `Start`'s own transaction as `ErrAbortedTarget`, until the channel moves); a resolution failure is said once per six hours and waited out. `server.WithRolloutStarter` is what wires it, asserted structurally by `rolloutstarterwiring_test.go`.

**The controller's own upgrade is a root timer, and `--from-rollout` is what it runs.** The server is unprivileged, so `billet-upgrade.timer` (packaged, enabled by postinstall, rendered and enabled by the Ansible role; `sh.billet.upgrade` on a Mac, installed by `local up`) runs `billet host-upgrade --from-rollout` every five minutes: `rolloutInstruction` reads the open rollout, or the newest finished one, through `openStateAdmin` (`readFleetDecision`): it exits 0 saying why when there is no control plane here, `automatic: false`, no decision, an aborted one, a host already on the target, or a completed rollout whose target is older without `AllowDowngrade`; otherwise, converged controller phase or not, it runs `startHostUpgrade` with the rollout's pin, digest, id, generation and `AllowDowngrade`, under every existing fence, because a PostgreSQL standby is a controller host the phase says nothing about and its timer fires into a ledger whose rollout may already have completed. A completed rollout is taken ONCE: its generation must exceed this host's SETTLED mark (`settled-decision`, raised by `settleCommitted` in `finishHostUpgrade` when the journal reads committed, a required step whose failure is a non-zero exit rather than the lost diagnostic a provenance failure is, and by the on-target no-op, never by an attempt that rolled back, so a rolled-back standby is asked again while a host an operator moved by hand is not moved back every five minutes); the on-target no-op (`settleOnTarget`, under the host transaction lock so it cannot bless another updater's unproven candidate) raises `last-decision` too, exactly as `actOnResolved`'s does, so a delayed older decision cannot pass the fence. `readFleetDecision` opens through `openStateForDecision`, the one open in `ledger.go` that names no release (exempted by name in `ledgerrelease_test.go`), because a standby's timer is the older binary the leader's watermark would refuse; it still cannot read a schema newer than its binary, and it opens only an EXISTING SQLite ledger (`state.LedgerPath`), since the package enables the timer before the server has ever run and an operator open would mint a root-owned ledger. An operator's own run on a control-plane host settles through the fleet's last completed generation (`Journal.SettlesThrough`, `settlesThrough`), so a host a person deliberately put elsewhere is not moved back by the timer; a timer process overtaken by a dispatched updater that installed the same manifest (`provenance.Installed()` equals the target digest) settles and does nothing instead of reinstalling. `ledgerHost.downgradeTo` is set only for a PROVED downgrade (`version.Compare(ToVersion, FromVersion)`), never on the flag alone, or an upgrade run with `--allow-downgrade` would raise an external ledger's mark before a probe that has no snapshot to undo it. The watermark itself is written inside the claim's transaction (`raiseReleaseWatermarkIn`), never after it. The instruction is re-read in `actOnResolved` after the claim and before the ack (`confirmFleetDecision`, `fromRollout`), refusing `ErrSuperseded` if the rollout was aborted or replaced in the meantime. It takes no other target flag and no ack path. A standby PostgreSQL controller is not a node in a rollout, so it runs the timer too. `hostPathsFor(hostOS)` is the one answer to where the binary and the upgrade root live (`/usr/bin/billet` and `/var/lib/billet/upgrades`; `/usr/local/bin/billet` and `/usr/local/var/lib/billet/upgrades` on a Mac), and `provenance.DefaultPathFor` the record's.

**The ledger records the newest release that has served it, and every open refuses a proved older binary.** Migration 48's `release_watermark` singleton; `state.WithRunningRelease` on every open in `cmd/billet/ledger.go` (asserted structurally by `ledgerrelease_test.go`); `enforceReleaseWatermark` after the schema is settled. Only the control plane proper records (`openMode.records()`: not admin, not standby, not the probe), and only in `ClaimController` after the deployment binding, or a `billet check` from a newer laptop binary, or a newer server pointed at a foreign ledger, would fence the running server out of its own restart; a promoted standby records there too, and a revalidating admin handle re-reads the mark inside every write. `version.Compare` is the one ordering, and it orders BOTH spellings of a release, `v0.9.1` and `0.9.1`, because the release build stamps GoReleaser's `{{.Version}}` (bare) and releases through v0.9.1 reported, journaled and registered that form; `version.Version()` now spells a release as its tag, `version.Same` is equality across the spellings (never `==` on a release string), `version.IsRelease` stays the tag grammar for pins and the watermark, and `version.Canonical` turns a bare report into the tag before it is recorded (`alloc.highestRelease`). Could-not-tell (a dev build) neither refuses nor records. `cmd/billet/hostupgrade.go` reads the running release through the `runningRelease` seam so a test can stand a release in for "(devel)"; the from-rollout and downgrade tests now use the bare shape production had. A deliberate downgrade is `--allow-downgrade` on `rollout start` (persisted in `Policy.AllowDowngrade`) and `host-upgrade` (on the journal): `ledgerHost.Migrate` lowers the mark through `SetReleaseWatermark`, the one write allowed to move it backwards, on a maintenance handle after the snapshot that keeps the higher mark for a rollback; on an external ledger, where `migrated` is skipped and the maintenance open is a read-only probe, `ledgerHost.ProbeReady` lowers it through the operator handle first. `checkDowngrade` refuses an unnamed downgrade before anything drains, and precedes the claim (`downgrade_test.go`); `rollout start --allow-downgrade` additionally refuses a target before v0.9.2 (`checkConvergibleDowngrade`, wired between the downgrade check and `Store.Start` and asserted structurally), because a control plane downgraded to a release that names itself without the v runs the old coordinator, never sees itself on the target and dispatches no node; `host-upgrade --version <tag> --allow-downgrade` is the one-host route it names. The role's own downgrade check accepts both spellings in its pattern (`billet_release_tag`, `^v?...`), or an older candidate read as "not a release" slipped past it. Nodes carry `highest_release`, reported by `billet status` as `DOWNGRADED` and never refused, because the coordinator's rollback inference IS an older re-registration.

**One transaction, two service managers, three ledgers.** `newHostFor` picks `systemdHost` on Linux and `launchdHost` on darwin and refuses anything else before the ack; both embed `ledgerHost` (fence, snapshot, migrate, provenance, probes). The Mac host boots out with `StopAndProve` (every pid proved gone), bootstraps with `StartAndProve`, preserves the two plists from the converger's agents directory beside the binary and config, and refuses before the ack when `/usr/local/bin` is not writable by this account (`checkBinaryDirWritable`; the Mac setup chowns it). A `Setsid` child survives its agent's bootout (measured, `realscheduled_test.go`). The transaction's image step, `Host.PrepareImages` (the `imaged` step, after the stop and before the fence), is the candidate's `images compatible --result-file` then `images pull --verify` per listed image on firecracker, `pullTartImages` on tart. On a PostgreSQL ledger the journal carries `Ledger: external` and `advance` records `fenced`, `snapshotted` and `migrated` as reached without doing them, `rollBack` restores no ledger and `finish` clears no fence; the probe is `state.OpenPostgresProbe` (the standby's open across the fence, writes refused, nothing claimed or migrated), and the migration happens when the candidate claims. The rollback boundary there is the candidate's start.

**A refused dispatch records its reason, and `rollout status --json` is the ledger's own account.** Migration 50 adds `rollout_nodes.last_refusal`, with three behaviours and no fourth: the coordinator's failed-dispatch path writes the error's text (`AdvanceRequest.Refusal`, bounded to 4096 bytes at a rune boundary with ` [cut]` and made valid UTF-8, since PostgreSQL's `text` refuses invalid bytes), the accepted-dispatch path clears it (`ClearRefusal`, and only after the dispatch was accepted, so a reader during the dispatch still sees the old refusal), the convergence walk's commit clears it too (the accepted dispatch's clear is a write that can fail after the updater is already running, and a host an operator moved by hand after a refused dispatch is stuck on nothing: the record means the refusal the host is still stuck on, never a history), and every other advance leaves it as it is, because an empty parameter cannot stand for "keep what is there" when clearing is a write of exactly that empty value (`SetLastRefusal` is the statement's own guard; both flags together are refused). The text report shows it under `DETAIL` after a blocker, an exemption and a rollback result. `billet rollout status --json` (`cmd/billet/rolloutstatus.go`, `schema` 1, the field set pinned by name in `rolloutstatus_test.go`) reports the ledger's deployment binding positively from the ledger and never from the host's identity file (which it peeks only to refuse a foreign ledger and never mints), the open rollout or else the newest finished one with its nodes, and every registered host's CURRENT registration (`Store.Registrations`, from `nodes` and never from a rollout row's dispatch epoch), all through `state.OpenInspect` (`openStateInspect`, the one open in `cmdRolloutStatus`, asserted structurally) so the check job of a converge can read every controller without migrating, locking, claiming or minting; a read that fails is the command's failure with nothing printed, never an empty fleet. Run as root over an identity directory owned by another account it re-executes itself as that account (`runAsLedgerOwner`, behind the `statusEUID`, `statusOwnerOf` and `statusReexec` seams), because the bundled driver's read-only open of a stopped ledger creates root-owned sidecars the service account then cannot open; an owner that cannot be read is a refusal, not "run in place". `--environment-file` reads the PostgreSQL DSN through `environmentFileValue`'s restricted grammar whenever it is named, on every backend, and the value reaches no argument, no report and no error (pgx redacts the password in its own parse error, measured 2026-09-09).

**The Ansible role gives way to the rollout.** `upgrade-inspect.yml` refuses a converge over a symlink claim (the Go transaction's) naming `--status` and `--resume`; `account.yml` compares the two binaries' `version` output and refuses a proved downgrade before the drain unless `billet_allow_downgrade`; `billet_automatic_updates` (default true) renders and enables the two timers wherever they apply; the role's own transaction still refuses a PostgreSQL host, and its message says the timer does that upgrade. `make unit-parity` compares the timers' directives too. A fleet on automatic updates pins `billet_version` for a host's first install and then leaves the binary to rollouts.

**A rollout resolves the channel once and persists the manifest's digest.** `billet rollout start` records one immutable target; a channel advancing mid-rollout must not retarget work underway. A different target while one is open is refused (`ErrOpen`). The coordinator (`internal/rollout.Coordinator`, on a slow tick inside the control plane) makes every transition from an observation, never elapsed time: a host is converged because it registered reporting the target. It does not upgrade the controller (a process cannot install its own successor, and this one is unprivileged; the root timer below does that); it observes the running binary is the target and only then begins on the nodes, which is what makes a rollout server-first. An earlier `WithSelfUpgrader` that had the coordinator exec `host-upgrade` from the server process was removed for that reason: as the service account it cannot stop a unit or write `/usr/bin`, and its every attempt would have rolled back and cordoned the controller. Phases: `pending → draining → ready_to_install → installing → verifying → committed`, with `rolling_back → rolled_back` (not terminal) and `blocked` (a cordon only a person leaves). `installing` is reachable only from `ready_to_install` and `committed` only from `verifying`, asserted structurally; `draining` has no timeout.

**A registration epoch is the only causal evidence the coordinator has.** A host that has not started and a host that installed, failed and rolled itself back are identical in every field; the dispatch records the epoch it was sent against (`rollout_nodes.dispatch_epoch`) and a higher one on the old release is the rollback, while an unrecorded epoch concludes nothing. A first registration writes epoch 1, because zero means "not recorded" and a host dispatched at zero was never concluded about. The liveness check comes before the convergence check (a node that came up on the target and vanished reports the target forever). Observations and dispatches are two passes with a ledger re-read between, or the failure budget depended on what hosts were called. `completeIfConverged` runs after every pass, because `exempt` and `decommission` run no convergence. `Finish` returns `ErrOutstanding` and the coordinator suppresses only that. Tell the host first, record `draining` second; the reverse marked a host draining with no updater running.

**`billet host-upgrade` is a separate detached program with everything on disk.** `internal/hostupgrade` owns the order over a narrow interface: `claimed → staged → stopped → imaged → fenced → snapshotted → installed → migrated → probed → committed | rolled_back`. `imaged` is the candidate proving this host's guest images compatible with it (`images compatible` from the STAGED binary, its exit status the answer: 0 nothing to do, 2 pull these, anything else could not tell and refuses) and pulling a generation for each that is not through `images pull --verify`; it sits after the stop, because nothing may launch against a generation mid-import, and before the fence, because a pull records in the cluster rather than the ledger, and it has no unwinding. That is the Go half of what the Ansible role's transaction already did (`services.yml`, "Pull, boot-verify, and promote every compatible guest needed"). The ledger is snapshotted before it is migrated (the one step the old binary cannot undo); the fence opens only after the commit record (opening admits operator writes a snapshot restore would discard); a rollback unwinds exactly what the journal says was reached, ledger first. `TestAHealthyUpgradeRunsInOrder` asserts the whole sequence, because the failure mode is a step moving. The journal is fsynced with its directory, `Reached` is the resume decision in one place, and a journal with a failure recorded before the rollback finished is re-entered through `rollBack` rather than advanced, or a resume would probe the restored old binary and record a committed upgrade to a release the host is not running. An unprovable rollback is cordoned (`ErrCordoned`) with its journal intact.

**Two answers over a Unix socket, and a spawn is not an answer.** `ExecUpgrader.AckDir` is the node's private writable state directory, wired from `cfg.Node.StateDir`; `StartUpgrade` listens at `upgrade-ack-<random>` and closes the listener on every return, which unlinks the socket. `--ack-path` replaces `--ack-fd` (the node launches its own binary, so the two ends share a version). The updater dials with a five-second bound and writes one bounded `AckAccepted` or `AckRefused` line when it has accepted responsibility or refused preflight; a missing listener is best effort and never holds the claim. Accept and read each have a ninety-second deadline: never connecting is "did not say within", connected EOF is "stopped without saying why", and a read without its newline is not an acceptance (`MaxAckBytes` plus one). Under systemd (`linux` and `INVOCATION_ID` present), `launch` runs `systemd-run --unit=billet-host-upgrade-<rollout>-g<generation> --service-type=oneshot --collect --quiet --no-block --property=TimeoutStartSec=88200 -- <binary> host-upgrade ...`: the root unit escapes the node's read-only mount namespace and cgroup, its name prevents concurrent redelivery, and `CombinedOutput` reports launcher failures immediately. `--no-block` matters because a oneshot's start job lasts the transaction; the node waits only on the socket. The transient unit receives the configured PostgreSQL DSN environment variable through `--setenv=NAME` without its value in argv; `cmd/billet/nodeupgrade.go` reads the name from `cfg.Server.LedgerDSNEnv()`. Present `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, and `AWS_SESSION_TOKEN` variables are forwarded the same way, because the candidate server probe resolves an SSM App key before it can succeed and must retain the configured AWS identity. The fake service manager clears the inherited environment and forwards every explicit entry so DSN, access key, secret and session-token forwarding are observable together. Instruction, config and conflicting-flag refusals answer immediately after flag parsing. `ExecUpgrader.Check` runs at node startup and in its candidate probe, refusing an absolute state-directory path whose generated socket name exceeds 107 bytes on Linux or 103 on macOS (measured with Go `ListenUnix`, 2026-09-06). Off systemd the updater remains a `setsid` child, reaped by a background `Wait` (`Process.Release` does not reparent). Systemd nodes through v0.9.2 need one manual move onto the fixed dispatcher, because FROM launches the transaction. The full rehearsal needs the fix in FROM, not just TO.

**The probe answers by exiting or by saying it is ready, the candidate says which, and the fence is cleared under the reason it was written with.** Two callers run `--upgrade-probe` with opposite contracts: the Ansible role runs it as a `Type=notify` unit's own ExecStart and stops it itself, so there it holds until told; `billet host-upgrade` runs it as a plain child and waits for it to exit. The role's unit passes `--upgrade-probe-hold` and nothing else does, and only after asking the staged candidate's `-h` whether it lists the flag (a downgrade renders the older shape); `holdProbe` prints the readiness line and holds ONLY on that flag, so the line and the silent zero exit are disjoint protocols. NOTIFY_SOCKET is NOT the tell, because a node's detached updater inherits its unit's socket and so would the candidate. `runCandidate` asks the candidate's `-h` the same question (`candidateHoldsOnFlag`): one that lists the flag is judged by its exit status alone and a readiness line from it is refused as a broken protocol; one that does not is a release through v0.9.0, its line means "stop me" and is its only proof (silent exit zero is a could-not-tell, refused); it answers SIGTERM by exiting zero, so its exit status is its verdict and a signalled death is a refusal whoever sent it; SIGKILL is always sent before the reap because output closing is not exit (the shipped probes hold their descriptors until exit, so a closed output is a zombie the kill cannot change; one that closed its output and kept running is killed and refused); the deadline is `runCandidate`'s own and never `exec.CommandContext`'s, whose kill runs beside `Wait` and on a kernel without pidfd may reach a reused number, so every signal precedes the one `Wait`. A candidate whose exit never arrives after SIGKILL returns `hostupgrade.ErrUnsafeToRestore`, and so does an output (the probe's or the usage question's) still held open once the candidate has gone, or one that could not be read to its end, because the open pipe proves a live descendant and the unread one proves nothing; those verdicts outrank what the candidate said or how it exited; `Run` cordons without restoring, since a rollback over a live process is the one outcome worse than a hung probe. The usage question owns its pipe like the probe does, bounded by `probeUsageWaitDelay`; the role wraps its own copy of the question in `timeout -k 10 60` and refuses a non-zero exit before stopping anything. The candidate is reaped only after the last signal it might be sent, so its pid is anchored by the zombie on every platform (`Wait` runs after the stop, never beside it); nothing is signalled by process-group number; anything still holding the candidate's output past `probeOutputGrace` fails the probe, and a process that closed the output before detaching is not seen. The parent owns the output pipe and reads it to its end before any verdict; the readiness line is matched whole (`serverProbeReadyLine`, `nodeProbeReadyFormat`); a silent candidate fails at `candidateProbeDeadline`. Before v0.9.1 each half waited for the other and every self-upgrade hung at the probe with the services stopped. The maintenance fence is written and cleared under `fenceReason`, one string, because `state.ClearMaintenanceFence` refuses any other; the commit and the rollback each used to name their own outcome there and both cordoned. Both were found by the rollout rehearsal on 2026-09-05, not by a test: the fake host ignored the reason, and `internal/hostupgrade/fence_test.go` now lets the real ledger judge it.

**The claim bounds concurrency; the decision mark fences generations; the transaction lock is a lock.** `/var/lib/billet/upgrades/active` is a symlink to the recovery directory (the journal publishes through a rename, so a hard link would go stale), released on commit or rollback and not on cordon, published after the journal (the reverse let a resume clear the claim of a live upgrade). `last-decision` is the high-water mark written before the transaction starts: equal is a redelivery, strictly older is refused (`ErrSuperseded`), unreadable refuses a fenced instruction and never an operator's unfenced run (`ErrUnreadableDecision`); both acceptance branches record first (`TestANoOpUpgradeRecordsTheDecisionBeforeAcceptingIt`), because a no-op that accepted before touching the fence let a delayed older generation downgrade a machine. The mark has its own lock (`decision.lock`), because the already-installed path runs no transaction and has nothing to claim; `checkAndRecordDecision` is one acquisition. The transaction flock is taken non-blocking before the network, because resolving a channel can hang past the node's acknowledgement and every retry started another stuck process; lock order is transaction lock then `decision.lock`. A generation of zero means an operator is at the keyboard; a `--rollout` with no `--generation` is refused.

**A version line names a build or the read is an error.** `executableVersion` (cmd/billet/convergeguardprepare.go) reads the FIRST LINE alone of `<binary> version`, requires `billet <token> ...`, and takes the token as a release (`version.Canonical`) or as one of the COMPLETE development forms the version package prints (`(devel)`, `(unknown)`; a Go pseudo-version judged by Go's own parser, `golang.org/x/mod/module.IsPseudoVersion`, in exactly the three shapes `cmd/go` mints, with the twelve-hex revision required on top because x/mod admits any length, and `module.PseudoVersionTime` and `module.PseudoVersionBase` required to answer on the token without its build suffix, because the shape check admits a month of thirteen and a `vX.Y.0-0.` base with no predecessor (round 11); a dirty checkout at a release tag, `vX.Y.Z+dirty`, or any build suffix on a release base, which the version package passes through and Canonical refuses; a GoReleaser snapshot `X.Y.Z-SNAPSHOT-<hash>`; every one a valid semantic version); a hand-written regexp admitted `v0.10.1-<stamp>-<hash>` (the timestamp-only form needs a `vX.0.0` base) and `v0.10.1-rc10.<stamp>-<hash>` (a prerelease base needs its own `.0.`), which both read as no release to compare, and refused the dirty tag, which blocked every candidate (round 10, 2026-09-10); a prefix alone or text after it is an error and never "a build with no release to compare", because `billet\n  go go1.26.0` once read as a development build and the downgrade judgement was skipped over it (2026-09-10).

**The claim is one name with three shapes, and a converge holds it as a directory.** `cmd/billet/convergeguard.go`: `billet converge-guard hold|release|status|recover|holder`. `active` a symlink is a Go transaction, a regular file a pre-R role transaction, a DIRECTORY holding `guard.json` (holder, claimed_at, hostname, release_executable, release_executable_sha256) a converge guard, a directory without the record an `unpublished-guard`; `classifyClaim` reads it by `Lstat` with no lock and creates nothing, and a directory was chosen because every pre-R reader refuses one and none can release it. ## Measured facts

- Every release up to and including `v0.3.26` predates `terraform/` and carries no module; an equality check on the wire version shipped through v0.3.26 and refused every node in the field on a bump.
- `gh release verify`'s REST response carries `bundle_url`, not the bundle.
- `Process.Release` filled the process table one refused updater at a time.
- `ReadString` returns bytes together with the error, so `accepted` without a newline is not an acceptance.
- A gzip reader is multistream by default and tar stops at the first end-of-archive marker; `Multistream(false)` plus a drained tail is what refuses a second `billet` member.
- launchd's default `ExitTimeOut` is five seconds; the units' `TimeoutStopSec` is 88200.
- `billet-upgrade.service` is `Type=oneshot` with `NotifyAccess=none`, so a child it runs has no `NOTIFY_SOCKET`; the v0.9.0 candidate's probe waited seventeen minutes at `ctx.Done()` under it before a SIGQUIT dump showed why (2026-09-05).
- The fence written as `host upgrade` refused `host upgrade committed` and `host upgrade rolled back` alike; the rollback cordoned the rehearsal controller with its services stopped and the timer's next tick refused on the fenced ledger (2026-09-05).
- The inspector's three scheduled units (`billet-upgrade.timer`, `billet-backup.timer`, `billet-backup.service`) are in `release inspect`'s services map with their six runtime facts only (`scheduledUnits`, `inspectScheduledUnit`, a custom `MarshalJSON`), `LoadState=not-found` a positive absent presence that keeps a running pid, and they are exempt from the binding, the shape rule and the executable comparison, which are `server`'s and `node`'s alone.
