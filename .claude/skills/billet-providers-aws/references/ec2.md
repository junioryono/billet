# ec2

Part of the `billet-providers-aws` skill. Each rule is stated in full, with the measurement or incident behind it.

**`ClientToken` is durable.** Measured still refusing a changed relaunch of the same lease long after the fact, so `clientTokenFor` is a safety property: an ambiguous retry cannot start two machines. A shape AWS has none of (`InsufficientInstanceCapacity`) falls through to the next declared shape, but only after a synchronous refusal that launched nothing; after an ambiguous failure it stops.

**`TerminateInstances` returns when the request is accepted.** The machine keeps running for a minute or two, so `Destroy` returns `TeardownRequested`, the node keeps the lease charged, a targeted lookup's explicit `terminated` record is causal proof, and absence otherwise has to stay uninterrupted through the remote-consistency window. Waiting inside the teardown was never the fix, because a node runs one command at a time.

**The AMI is verified by booting it, and the tag is the promotion.** Every other claim a build makes is checked on a builder that has been apt-installed and never rebooted; the Docker gate read `overlayfs` off exactly that machine while the image reports `overlay2`. `billet ami build` launches the produced image, reads its report through the console (`GetConsoleOutput`, nonce-bound, no key pair, no inbound access), and only then writes `AMIContract` with `CreateTags`; `ErrPromotionUncertain` is the third value for a failure after the tag. A `TagSpecification` on `CreateImage` is authorised as a separate `ec2:CreateTags` check keyed on `ec2:CreateAction`, measured with `create-image --dry-run`. The verifier proves the runner, each architecture's toolchains (`rustc`, `cargo`, `swift`, `go`, `node`, `python3`, `java`, `dotnet`, `pwsh`, and `ghc` on x64) and each recorded component (its executables run and its directories read) as the runner account under the job's own `env -i` (`billet-shell-gates`), and finds as root none of a component the image does not record, since an operator's base image may already hold one. An AMI id is region-scoped. Measured 2026-08-28: provisioning 3m54s, snapshot to available 11m06s, console report 4m40s after the verifier launched.

**AMI contract 3 is an image that launches the runner through `billet-exec-env` (#352).** The entry point, the build's `Runner.Listener --version` check and the verifier's `billet_as_runner` all use `privilegeDrop`, which ends in `env -i /usr/local/bin/billet-exec-env`, followed by the command and `runnerEnvStream`, and all build `billet_env` through `writeRunnerEnv`, so the verifier proves on the booted artifact the helper every job goes through, and its `entrypoint` step proves the installed `/usr/local/bin/billet-runner` and `billet-exec-env` are executable and carry the sha256 of `entryPointScript()` and `guestassets.ExecEnvScript`, by digest because the verification script is user data and embedding both files left it under its 4096-byte headroom (measured: 15707 bytes), because the verifier brings its own launch, a working helper says nothing about the file a job runs, and a search for the launch line passes a file whose privilege drop or stream is damaged around it. An AMI at contract 2 still runs jobs, with the registration in an argument list until the runner starts; `billet check` warns and names that, and `billet ami verify` cannot stamp an old image 3 because the helper is not on it. `billet-security` holds the mechanism.

**AMI contract 4 is GitHub's template build with billet's EC2 layer, completed with what `images.accept` names (ADR-022).** The image records the components it installed in `/etc/billet-image-components`, `name:version` joined by commas and empty for none, and the promotion's one `CreateTags` writes `sh.billet.components` beside the contract, so an image never carries the contract without that record; the verifier reports the file, the build's own verdict must name the same list, and a list naming a component nobody accepted refuses the build before `CreateImage`. A component the architecture's template does not install (on arm64, everything but Firefox) is left out and said. `billet check` names a contract-3 image's gap: it was built by billet's installers, lacks much of GitHub's image, and carries the Android SDK (and on x64 CodeQL) whatever was accepted.

**User data is 16384 bytes, gzipped, and `packUserData` is the gate.** The registration is shell-quoted into it (a single-quoted assignment, the one construct with no parsing left; a quoted heredoc inside `$( )` died on a quote in the value), `HttpTokens=required` and `HttpPutResponseHopLimit=1` keep a container inside the job from the metadata service, and `instance_profile` is optional because a profile is readable from inside the guest. Cold-start timing is measured from an epoch billet puts in the user data: three cold runs reached the first job step in 47.6 to 58.7 seconds, which is why `warm_pool` stays refused.

**Spot warnings are one queue per node.** The router resolves the warned instance's `sh.billet.node` tag and targets that node's queue; the queue basename must equal the node's identity, and a shared queue is refused because one consumer hides a message for the visibility timeout. The terraform module's `spot_node_names` creates the further queues and widens the node grant, the router grant and the router's served set from the same list, so a second spot node never needs an out-of-band IAM edit (`billet-infra-terraform-ansible`). The queue HOST is refused unless its DNS suffix is the one `node.ec2.region`'s partition serves: the validator used to admit both, so a `cn-north-1` node could name `sqs.cn-north-1.amazonaws.com` — not a host — while `billet init iam` derived `arn:aws-cn:sqs:...` from the same region, leaving a correct policy in front of a queue the node never reached and a two-minute warning that never arrived. A live FIS interruption exercised the path. Untrusted work needs `node.ec2.untrusted_security_group_ids`; an instance isolates the kernel, not the VPC.

**The builder's owner tag is the deployment's, and the policy's pattern comes from the same function that stamps it.** `ec2.BuilderOwner(deployment, name)` produces `billet-ami-build-<deployment>-<name>`, and `ec2.BuilderOwnerPattern` is what every builder statement matches; an empty deployment yields the bare prefix, which is the account-wide mode. They are one function apart because they were two, and the drift was the whole of #56: the runtime's owner carried the deployment id and the builder's did not, so a value-scoped policy isolated a deployment's job instances and left its BUILDERS reachable by every other deployment in the account. Measured with `iam:SimulateCustomPolicy` (2026-09-04): a role scoped to one deployment is allowed on its own builder, implicitly denied on another's, and implicitly denied on an ordinary job instance of its own; the same holds at create time against `aws:RequestTag`, which AWS authorizes separately, so both moved together. `billet ami build` takes the id from `--deployment` or the config's state directory and SAYS on stderr when it has neither, because the account-wide value it then stamps is one a value-scoped grant denies at `RunInstances` with nothing naming the reason.

**`awspolicy` is one generator with three consumers and a measured boundary.** The ownership boundary is per deployment when the owner is known and account-wide otherwise; the tag boundary is destructive integrity and the per-deployment KMS key is confidentiality. Validated against a live account with `iam:SimulateCustomPolicy` in both modes. `Inputs.Build` once emitted the runtime statements unconditionally, so a controller that launches nothing held `ec2:RunInstances` (hence `NoCompute`), and the terraform module hand-wrote the grant until `internal/tfpolicy`'s drift test began reading the generator's rendering.

**`ec2:CreateVolume` from a snapshot authorises the snapshot as well** (the `ebs-s3` store found it: `aws:RequestTag` is not in the snapshot's context, so the one statement conditioned on the new volume's tag denied every clone). `BilletCacheCloneSource` grants it on `arn:<partition>:ec2:*::snapshot/*` conditioned on the owner tag.

**`ec2:RunInstances` on `*` authorises every snapshot a block-device mapping names**, so the runtime grant is also a read of every snapshot in the account — the control plane's ledger snapshots, identity and CA key included. It cannot be narrowed (one call makes several resource types), so `awspolicy` bounds it with the one DENY it renders: `ec2:RunInstances` on `arn:<partition>:ec2:*:*:snapshot/*`, `Null` true on the owner tag account-wide and `StringNotEquals` on the owner value per deployment. Two things measured 2026-09-04 rather than read: a NEGATED operator evaluates true when the key is absent, so one `StringNotEquals` catches the untagged snapshot too; and `arn:aws:ec2:*::snapshot/*` — the documented account-less shape, and what the acceptance role's hand-written guard uses — answers ALLOWED for an ARN written with an account, while the wildcard-account form denies both. EC2 was asked directly under a throwaway role holding the generated document, three `run-instances --dry-run` calls: billet's own launch shape is `DryRunOperation`, the same request with the ledger snapshot in a mapping is an explicit deny naming `arn:aws:ec2:us-west-2::snapshot/snap-…`, and the PREVIOUS rendering allowed that same request — which is the exposure, measured rather than argued. So a snapshot the mapping NAMES is evaluated and the AMI's own backing snapshot is not — measured for the image the lane boots and the request billet sends, and if AWS ever changed it the failure is a refused launch rather than a widened grant. EC2 renders the resource account-less, which the wildcard account matches.

**The builder checks the runner tarball against the pin before it unpacks it, and an unpinned release needs `--runner-sha256` (#180).** Until 2026-10-16 the provisioning script ran `curl … && tar xzf` on the actions/runner release with nothing between, so the runner that executes every job an AMI serves was trusted on TLS and whatever redirects curl followed, while the guest image build checked the same release against `internal/runnerrelease/pinned.txt`. `BuildSpec.RunnerSHA256` now carries the digest, `layerScript` refuses one that is not 64 lowercase hex before a builder exists, and the layer checks it in an `if ! printf … | sha256sum -c -; then … exit 1; fi` rather than an `&&` chain, because under `set -e` a failing `&&` list does not stop the script and the build would run on to its success verdict (`billet-shell-gates`). `PinnedRunnerSHA256` maps `x64` and `arm64` to actions/runner's `linux-x64` and `linux-arm64` through `RunnerPlatform` and reads runnerrelease's table, so both backends check one answer. `billet ami build` resolves the digest before it reads the config: the pin for the pinned release (a supplied digest that disagrees is refused), the operator's `--runner-sha256` for any other release, and a refusal naming the tarball when neither exists. `TestTheRunnerIsCheckedBeforeItIsUnpacked` executes the rendered fragment against a genuine, a tampered and a missing tarball under sh, dash and bash, with and without `set -e`.

**The AMI build's bootstrap, template steps, component installers and layer run with `HOME=/root`, because neither cloud-init's user data nor a system unit has a HOME.** The bootstrap, the template's driver (`scripts/ami/ami-target.sh`, for every template step), the completer's steps and billet's layer each set it, and `build-ami.sh` itself does not, so a command added there that needs a HOME sets one: GitHub's scripts and the runner's own tooling are written for a root login shell, and before the template build, Composer's installer refused to start without HOME and every `billet ami build` died about twelve minutes in with a build that never stopped itself (#211, measured 2026-10-17). The figures that set the defaults are in [measured-facts.md](measured-facts.md): a template build takes 1 h 44 min on x64 and 1 h 29 min on arm64, the snapshot the largest and least predictable part, which is why `--timeout` is three hours; a finished x64 image holds 51 GiB, which is why the bootstrap insists on 60 free and the flag on 70, and why the default root is 120. On 2026-10-17 a build given `--runner-version 2.336.0` with another release's digest printed `runner.tar.gz: FAILED` and the refusal, unpacked nothing and never powered off: #180's check, on a real builder.
