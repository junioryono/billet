# Windows on EC2

Part of the `billet-providers-aws` skill. The decision and its measurements are [ADR-023](../../../../docs/reference/decisions/adr-023-windows-on-ec2.md).

**A lease's guest OS decides the boot script, and the AMI is held to it in both directions.** `provider.Spec.GuestOS` comes from the lease, an empty one is Linux, and `checkGuestOS` refuses a disagreement before anything is sent. Either boot script is text nothing on the other image runs, so the instance would boot, look healthy, register nothing and hold its lease. `billet ami build --os` is held to the base image the same way in `launchBuilder`, and `billet check` fails a tier whose `guest_os` and AMI disagree (`ec2TierGuestOSMismatch`).

**User data runs as the local Administrator, not SYSTEM.** Measured on Windows Server 2025 with EC2Launch 2.5.2 (`whoami` from user data, 2026-11-04). A directory restricted to SYSTEM and `runner` denied a script running there, which is what a first draft of the entry point would have done to itself; the ACL names `BUILTIN\Administrators` too.

**COM1 does not exist on the stock AMI, and EC2Launch does not use it.** The AMI boots with EMS on, so SAC owns the port: `[IO.Ports.SerialPort]::GetPortNames()` is empty and opening `\\.\COM1` fails. EC2Launch writes its console lines through a private `DeviceIoControl` on `\\.\EC2WinUtil`, which has no public contract and is not something to rely on. `bcdedit /ems {current} off`, `bcdedit /bootems {current} off` and a reboot make COM1 appear (measured 2026-11-04). So a build reboots once before it can report anything, and a failure before that reboot stops the machine, which billet reads as a builder that powered off with no verdict. The setting persists through `CreateImage`, which is how the verifier reports, and costs a job instance its SAC.

**A line reaches `GetConsoleOutput` only while the port stays open.** Open, `WriteLine`, `Close` in a row reported success and reached nothing: three such writes and forty ticks never appeared, while thirty lines written to a port held open all did, on one c7i.large (2026-11-04). The driver holds one port for the whole build. It also means one process holds COM1 at a time, so the bootstrap closes it before the driver opens it.

**`ec2launch reset --shutdown`'s exit status says nothing.** It answered 1 and "Shutdown was initiated but did not complete" for a machine that then stopped with `Client.InstanceInitiatedShutdown` (EC2Launch 2.5.2, 2026-11-04). The driver reads failure as the machine still being up fifteen minutes later.

**A page file in the image costs a job its assignment.** A snapshot's blocks reach a new volume as they are read, and Session Manager reads `pagefile.sys` early in boot. On an image built with one, the system log stood still for 5 min 6 s between the network driver loading and session start (user data at 369 s of uptime, both samples, almost no CPU), under a second on a warm reboot of the same volume, and GitHub cancels an assignment unstarted after five minutes, so billet retired each runner mid-boot and no job started. With no file and auto-managed paging restored: 91 s (c7i.xlarge, 2026-11-04). So the build runs with paging off and restores it with no file; the verifier refuses an image that boots with none. `VolumeInitializationRate` also moves that boot (85 s at 300, 112 s at 200), and it is needed too: see the next rule.

**A Windows launch asks for a provisioned read of its snapshot.** With no page file a real job still started 311 s after launch, its assignment taken up 14 s inside GitHub's five minutes, because every file the listener loads is the first read of its blocks. With `VolumeInitializationRate` 200 the same job started 121 s after launch (`launch_to_runner_ms` 85969, `runner_to_job_start_ms` 35244, c7i.xlarge, 2026-11-04). It is charged per launch on the snapshot's full size, the same from 100 to 200 MiB/s, about $0.09 on a 36 GiB image, so 200 is the top of the cheaper band (`windowsVolumeInitRate`). A builder and a verifier do not ask, since neither has an assignment to lose.

**A Windows image is `reset`, not sysprepped.** Both run their own user data on a new instance and both keep EMS off. Launch to the first line of a new instance's user data on c7i.xlarge, two samples each, 2026-11-04: the stock AMI about 62 s, an image made after `reset` about 113 s, an image made after `sysprep` about 247 s. ADR-023 has what a generalised image would buy.

**The scheduled task needs an explicit execution limit and priority.** `New-ScheduledTaskSettingsSet`'s default stops a task after three days, which would end a runner under a job still running, and its default priority of 7 is below normal, which every process of every job would inherit, so the runner's asks for 4 and the verifier's check refuses anything but `Normal`. A task inherits nothing from the process that starts it, which is why the registration travels in a file the service script reads and deletes before any step exists.

**A step's preference does not cross a process.** The driver's `$ErrorActionPreference` stops nothing in the PowerShell it starts, and `exit $LASTEXITCODE` with nothing having set a status exits 0, so a `Move-Item` that failed in an inline step read as success until the wrapper set the preference itself. Only inline steps get it. GitHub's scripts are written for Packer's default: with `Stop` forced on them, `Configure-BaseImage.ps1` died at `Set-ExecutionPolicy`'s complaint about the step's own `-ExecutionPolicy Bypass`, which under `Continue` it survives (2026-11-04).

**Amazon's AMI is not Azure's.** It carries the AWS Tools on the module path, so GitHub's `Install-Module AWSPowerShell` refuses to clobber them (`prepare-aws-tools.ps1`), and it has no `D:` drive, so the template's `temp_dir` is on the imaged root and the driver removes it. A difference like these is one line in `differences-windows.tsv`, never an edit to GitHub's script.

**GitHub's steps read the account's profile.** `Configure-PowerShell.ps1` writes a profile that installs and imports PowerHTML, and `Install-PyPy.ps1` calls `ConvertFrom-HTML` with no import of its own, so a step's PowerShell must load the profile (`Invoke-Step` passes no `-NoProfile`) and nothing may remove it before the layer does. A builder that had lost it failed at that step with `ConvertFrom-HTML` not recognized (2026-11-04).

**EC2Launch keeps the user data it ran.** Each run leaves `UserScript.ps1` under `EC2Launch*` in SYSTEM's temp directory (`C:\Windows\system32\config\systemprofile\AppData\Local\Temp`), although the script runs as Administrator (EC2Launch 2.5.2, 2026-11-04). The first boot's copy holds the presigned URL and that boot ends in a reboot, so nothing removes it unless the driver's cleanup does, which is why a listing that fails there fails the build.

**A failed start ends the instance's charge, not the lease.** A boot script whose command fails, and a listener that ends with no job-started mark, stop the instance, because a Windows licence bills by the hour; its volume still bills. The lease stays charged until a Destroy, as for a Linux boot that fails (`TestAStalePromiseIsReportedAndKept`). `List` reports a stopped instance as `Ended`, so a drain does not wait on it, and that authorises nothing else.

**A build's own output reaches the console only as a bounded tail on failure.** A builder in an egress-only group has no other way to say why it failed; `billet-build-log` lines precede the verdict so the last complete block is still the verdict, and billet parses nothing else. Without it the first real build's failure would have read as a step number.

**A file named `*_windows.go` builds only on Windows.** This backend's Windows code runs on every operating system a node does, so its files are `windows.go`, `windowsbuild.go` and `windowsverify.go`, and `scripts/runner_images_winplan_test.go`. The first version of each was silently absent from a Linux build.

**The tests run PowerShell 7's parser, not 5.1's.** Everything before the template installs PowerShell 7 runs under Windows PowerShell 5.1, which no Linux CI lane has, so `pwsh` catches what is broken in both and only a real build proves the rest.
