# The suites: end to end, replay, real, live and the rehearsals

Part of the `billet-testing` skill. Each rule is stated in full, with the measurement or incident behind it.

**The end-to-end suite assembles billet the way `cmd/billet` does.** `internal/e2e` opens its control plane with `app.OpenControlPlane` and walks the steps `runServer` walks (`assemble_test.go`), and its node processes run `app.NewNodeClient`, `app.NewNodeRunner` and `app.RunNodeLoop`, as `billet node` does (ADR-015); the hand-copied adapter it began with had already drifted (it dereferenced a scale set the client returns as nil). What a test must change is steered through `app.Steering` (an allocator clock or lease TTL, node-plane pacing, scheduler pacing, an ordered provisioner), each applied after what the assembly sets, and an in-process runner through `ScheduleOptions.NodeRunner`; the wire-protocol scenarios (enrollment, mTLS, revocation, restore) still build a plane alone, on purpose. `internal/fakeactions` answers the handshake and serves what a test tells it to; it is deliberately not a simulator of GitHub, has no production callers and must acquire none. It exists because the worst defect in the project (`AcquireJobs` called with ids from `JobAssigned` instead of `JobAvailable`) lived in the relationship between billet and the wire, where billet's types agreed with billet's mistake. The one thing steered there is the allocator's clock, through `alloc.WithClock` in `app.Steering`. A stack can run over another backend through `withBackend(kind, build)`; the simulated one (`internal/provider/simulated`, `internal/e2e/simulated_test.go`) needs no docker daemon, so its scenarios run wherever the tests do, and it steers the provider's clock rather than the ledger's, because jumping the ledger past the lease TTL while heartbeats arrive on wall time would measure the reaper. Every scenario that is about the plane and the wire rather than about docker (lifecycle, wire, multiday, compute barrier, restart) runs through `forEachBackend`, once on docker and once on the simulated backend over one shared `simulated.Host` per leg, so a restarted stack (`sameBackend`) re-adopts what the previous process launched and a second deployment is on the same machine; the docker leg skips without a daemon and the simulated leg never does. A scenario stays docker-only when its subject is docker itself: the generated docker config launch.

**The replay harness drives a workload through the real scheduler at compressed time, and steers exactly two things.** `internal/replay` takes a trace of arrivals (tier, repository, workflow, duration; synthetic from `MorningBurst`, `MonorepoFanOut` and `LongTail`, or exported from a repository's Actions history by `scripts/export-actions-trace.sh`) and drives it through a scripted Actions service into the real listener, allocator, placer, node wire and node runtime over `internal/provider/simulated`, then reads every job back from `job_history` and joins it to the trace on the request id; a job the ledger has no row for is reported as missing, never filled in. What is steered: one virtual `Clock` that the allocator and every simulated provider read (the plane, the heartbeat and the node loops stay on wall time, because a plane on the simulated clock would expire a node parked across a jump of hours), and the order in which tiers open their sessions and contest freed room (fixed to the fleet's tier order, since escrow is placement and goroutine order would otherwise decide where a tier's first job lands). The reaper never ticks, for the multi-day scenario's reason. Determinism comes from delivering one event at a time to quiescence, where quiescence means every listener is parked on an empty queue with its advertisement unchanged since its last poll, because the listener hands surplus escrow back only after a poll carrying the smaller number has returned. When any tier has waiting work, the harness nudges every listener, including positive-advertisement donors: a donor parked forever cannot complete the withdrawal that releases its backing. Discovery rotation creates multiple unused escrow rows per tier; the capacity sweep must include them all. The four proofs that must stay green: two replays of one trace place and date every job identically; pack and spread leave different footprints; the ledger's own intervals never overcommit a host or the deployment (dropping the host term from `placer.roomFor` fails it); and every trace job has a ledger row (swallowing one completion fails it). The suite replays three hundred jobs by default; `BILLET_REPLAY_JOBS=2000` is the acceptance-size run, about a minute and a half on a laptop without the race detector and too slow for CI's shared race-instrumented test job, so CI runs it in its own `replay` job without `-race`; `-replay.out DIR` keeps each run's records and summary. The record's provider, charged shape, site, price and cache observations are the history row's own columns (migration 49, read through `ReadJobPlacement`); cost is derived from the recorded price or, for a host-backed lease that records none, from the fleet's per-host rate and labelled `fleet-rate`; locality is derived from placement and named as such, because a simulated guest observes nothing about the cache. It has no production importer, proved by the same importer walk `internal/importcheck` runs for `fakeactions` and the simulated backend. `Options.DirectAssignment` replays GitHub.com's protocol instead of the offer and acquisition GHES keeps (#140): a job is assigned to its tier's scale set as `JobAssigned` with `runnerRequestId: 0` as soon as the set advertises room for it, nothing is offered and an acquisition is a test failure, an assignment billet cannot back stays assigned for the next runner the tier starts (so a tier with unpaired assignments is nudged like one with offers), and the report joins each job on its GitHub job id, since billet gives such a job a request id of its own; `report.ByJobID` counting every job is what proves the mode ran (`TestADirectAssignmentReplayKeepsEveryProof`).

**A replay can be of a deployment's own history, and is judged by its tail (#526).** The trace format is `internal/jobtrace`'s, one copy that `billet jobs export` writes from a ledger (a read-only report; names replaced by stable stand-ins unless `--names`, run ids too) and the harness reads; the replay keeps type aliases for it. THE SCRIPTED GITHUB CARRIES EACH ARRIVAL AS THE JOB'S QUEUE TIME on every message, standing in for the REST read a deployment makes (#582), so a replayed deployment's ledger exports back exactly the trace it was given, which `TestTheLedgerExportRoundTrips` proves through `Options.AfterRun` (four jobs at one instant pin the export's tie order: arrival, then billet's first assignment, then request id in allocation order, then GitHub's job id, then lease; stand-ins are numbered in that order, not the read's). `FleetFromDocument` turns an exported fleet into a replayable one, leaving out a remote backend and naming it, since the simulated backend cannot model a catalogue of shapes bought per job, and refusing a tier pinned to one. `Options.Until` is a horizon: no event after it is delivered, a job that arrived by it and had not started is still queued (kept out of every percentile, #525's rule) when the ledger recorded it or the scripted GitHub still holds it, and lost otherwise, and a later arrival is outside the window. THE PLANE RECORDS EVERY START AND COMPLETION IT DELIVERS, and a recorded job whose delivered start or completion the ledger never wrote is lost (`LostStarts`, `LostCompletions`), never still queued: judged from what was sent, not from a deadline rebuilt from the ledger's times. The report adds p90, p99 and p99.99 (nearest rank in integers, as `jobs wait` computes it), queue wait per charged shape and the backlog still queued per tier shape, utilization over time against the room (the ceiling, or the hosts when less) and empty host-hours, all from the ledger's own charges, and `Declined`, the jobs billet refused to buy for at least once (an offer acknowledged unacquired, or a direct assignment acknowledged with no runner minted), counted once a job because how often a waiting job is offered again is the harness's nudge cadence, not GitHub's, and counted by the harness because nothing in the ledger records a decline. Four seeded adversarial generators (`Burst`, `IdleBacklog`, `QuietBesideSaturated`, and `WideShapeMix` on `WideFleet`, a whole-host tier beside 2 to 16 vCPU tiers at an offered load near 0.85) run at about thirty jobs each in the ordinary suite. A fleet may declare `Targets` (the first the `github` block, named `default`) and each tier its `Target`, which `buildStack` writes as a config does, one scale-set client per target against the one scripted service, so a weight reaches the allocator through `TargetWeights`; `ContendedTargets` offers each tier alone more than the fleet holds, and `ChargedByTarget`, `ContestedWindow` and `TargetTable` read what each held from the ledger's charges. `Compare` replays one trace under several admission orders (`DefaultPolicies`, and through `BILLET_REPLAY_POLICY` the placements of `RecordPolicies`; `BILLET_REPLAY_SEED` seeds the wide mix, because one seed's p99 of a hundred jobs is mostly noise) into a Markdown table, two comparisons of one trace giving one table, measuring each policy's utilization and empty host-hours over its own span and printing that span beside them (over one shared span the same jobs charge the same share by construction, and the policy that finished sooner is counted empty while the other drains), and fails rather than tabulating a replay the report cannot speak for (`Report.unspeakable`: an overcommit, a lost job, a lost start or completion, one never started or finished with no horizon). IT COMPARES UNDER DIRECT ASSIGNMENT: under GHES's offers a tier's unmet demand is the offers it did not acquire, which no reconciliation counts, so no tier ever waits and fair is fill (#686; the first wide comparison gave the two identical tables to the nanosecond), and `TestFairHoldsTheLineWhereFillDoesNot` holds the comparison to telling them apart; the record-size runs are `BILLET_REPLAY_COMPARE=wide` (`BILLET_REPLAY_JOBS`, default 2000) and `=file` with `BILLET_REPLAY_TRACE` and `BILLET_REPLAY_FLEET` (`BILLET_REPLAY_POLICY` replays one policy alone, so a long comparison runs a process per policy), run by hand on the shared Linux host with `TMPDIR` on tmpfs, because a replay is bound by its ledger's fsyncs (the reference week took about five hours a policy on disk, and about three with the two side by side on tmpfs), and recorded in `docs/reference/records/replay-policies.md`.

**Generated shell is executed, never pattern-matched.** `scripts/` holds thirty-odd Go test files that run the build scripts against fixtures; `internal/provider/codebuild/buildspec_test.go` parses the buildspec and runs its commands under `/bin/sh`; the EC2 boot script is run with the runner command replaced by one that prints what it would have read.

**Real and live tests skip without their resource and never spend money by accident.** `real*_test.go` files assert that what billet says matches what the real system does, because the firecracker backend's two launch-killing defects survived every unit test and died on the first real run. Gates: `realdocker_test.go` needs `docker` on PATH; `store/ceph/realcompaction_test.go` needs `BILLET_CEPH_TEST_POOL`, `rbd` and the keyrings of both `admin` and billet's own user, and writes to that pool; `realtart_test.go` needs `tart` (each test gets its own `TART_HOME`); `realguest_test.go` needs `BILLET_TART_GUEST_TESTS=1` (`BILLET_TART_GUEST_IMAGE`, `BILLET_TART_SOFTNET_TESTS=1`, `BILLET_TART_XCODE_TESTS=1` widen it); `realfirecracker_test.go` needs root plus `BILLET_TEST_GOLDEN_IMAGE`, `BILLET_TEST_BRIDGE`, `BILLET_TEST_KERNEL`, `BILLET_TEST_CACHE_POOL`, `BILLET_TEST_IMAGE_POOL`, `BILLET_TEST_CEPH_USER`; `realcodebuild_test.go` and `holdergone_live_test.go` need `BILLET_TEST_CODEBUILD_PROJECT` and AWS credentials; `realwalk_test.go` adds `BILLET_TEST_CODEBUILD_WALK=1` and records rather than asserts; the two `reals3_test.go` files (`internal/provider/ec2` for a presigned URL, `internal/awss3` for the two codes a 404 carries) need `BILLET_S3_TEST_BUCKET` and `BILLET_S3_TEST_REGION`; `internal/provider/ec2/live_test.go` needs `BILLET_LIVE_EC2_REGION` and friends; `internal/integration/sessionreplacement_test.go` needs `BILLET_LIVE_ORG` and `repositoryscope_live_test.go` needs `BILLET_LIVE_REPOSITORY`, each with `BILLET_LIVE_APP_ID`, `BILLET_LIVE_INSTALLATION_ID`, `BILLET_LIVE_APP_KEY` and `BILLET_LIVE_SCALE_SET`, and both record a JSON report under `BILLET_LIVE_REPORT_DIR` rather than asserting what GitHub answers; `internal/lifeops/launchd/reallaunchd_test.go` needs the macOS `launchctl`, and each test derives its own label because a launchd agent is not gone when its test ends. `internal/ops/host/codebuildchecklive_test.go` is named live but drives a fake endpoint; it exists because a structural test proves a judgement is called and not that its result reaches the output. `internal/node/gitproxy_live_test.go` runs the Git proxy against github.com and needs `BILLET_LIVE_GIT_REPOSITORY`, a private repository the run may push to, force-push, open a pull request in and delete branches from (a session-prefixed one in the shared test organization, deleted afterwards, with Actions turned off, which the test checks: one seeded with billet's history queued billet's CI on billet's own labels in the test organization on 2026-10-22), and `BILLET_LIVE_GIT_TOKEN`, which the shared App cannot mint because billet's App reads no contents, so it is a person's token piped to the host on stdin and never written down, and the test refuses to run while any git tracing variable is set, because a trace writes the credentials git sends; `BILLET_LIVE_GIT_LOAD=1` adds the load run (`BILLET_LIVE_GIT_LOAD_CHECKOUTS`, default 50), which ran on 2026-10-22 and is recorded in ADR-018.

**A test that changes routes and sysctls runs in a network namespace that is thrown away.** `internal/egress/realegress_linux_test.go` (`BILLET_TEST_EGRESS_NETNS=1`) routes public addresses such as 8.8.8.8 into a namespace of its own, turns on IPv6 and forwarding, and deletes firewall tables, which on a shared host breaks the network of every session using it. Build the test binary with `go test -c` and run it under `sudo unshare -n`, not as `go test` in the host's own namespace. It needs root, nft and a kernel with the bridge family, and CI does not run it. It brings up its namespace's loopback itself, because a resolver reaches its upstream over it and every name would otherwise time out as if the rules had dropped it, and clears out what a killed run left, because a named namespace is a file under `/run/netns`, which `unshare -n` does not hide. For the same reason two runs on one host collide, even each under its own `unshare -n`. On 2026-11-04 a session queued it on the shared test host outside a namespace and stopped it while it was still waiting for the heavy lock.

**PostgreSQL is tested against a real server or not at all.** `BILLET_TEST_POSTGRES_DSN` gates `internal/state` and `internal/alloc`; `internal/ops/host/localbackup_test.go` fails rather than skips when `CI` is set and the DSN is missing. CI runs `postgres:18-alpine` as a service and then re-runs only `./internal/alloc/` with `BILLET_TEST_LEDGER=postgres`, without `-race`.

**Coverage is a signal, not a goal.** `.codecov.yml`: project target `auto` (no regression from base, 1% threshold), patch target 80% (5% threshold), and only `cmd/billet/main.go` ignored, which is why nothing carrying real semantics may live in that file. A hard 85% on a project at 79% fails every PR and is learned to be ignored.

**A benchmark measures the ledger the run exercises, and a change to the hot paths shows its numbers before and after.** `internal/alloc`'s benchmarks (renewal alone, contended and batched, purchase, headroom, placement over 4, 32, 128 and 256 hosts, and the target fleet of ADR-023 with a tier falling back to a remote shape, with outstanding floors, and with a job's writes after its purchase) open their ledger through the same helper the tests do, so `BILLET_TEST_LEDGER=postgres` measures PostgreSQL, and `internal/nodeplane`'s `BenchmarkPlaneDispatch` measures a command's round trip through the plane. `scripts/gates/bench.sh` runs both three times; a change to escrow, placement, headroom or renewal puts the benchstat comparison of a run before and after in its pull request. The numbers measured on 2026-10-08 and 2026-10-25, on SQLite and on a PostgreSQL on its own machine, each on network block storage and on NVMe, and the decisions made on them are in `docs/reference/records/ledger-write-budget.md`. A benchmark's setup asserts what it builds (every escrow it needs succeeds), so a refusal is never timed as the work.

**A fuzz target states a property a broken parser would violate, seeds from what billet really reads, and is searched nightly.** Ten targets cover the parsers that take bytes billet does not control: `FuzzConfigParse` (billet.yaml), `FuzzParseMigrationStatements` (published migration bytes), `FuzzPlaneDecode` (every body a node-wire route decodes strictly), `FuzzDecode` (a guest report and the batches the in-VM agent sends, internal/guestreport), `FuzzStepLine`, `FuzzPIDStat` and `FuzzJUnitParse` (the runner's log, a process's stat line and a job's JUnit files, which the in-VM agent reads, internal/guestagent), `FuzzVersionCompare`, `FuzzEndpointParse` and `FuzzParseWithName`. Not crashing is the floor, and agreeing with itself is not much more: review of the first version showed that a decoder with `DisallowUnknownFields` removed, a migration parser keeping only its first statement, and a `Compare` answering backwards each still passed a property of the shape "what it returns, it returns again". So each property is checked against something independent of the code under test: the plane's decode against an ordinary `json.Unmarshal` of the same bytes, plus an injected unknown field and a limit one byte short that must both be refused; migration statements written between markers must come back exactly, every one, in order; version order against the three numbers read by hand; an endpoint's canonical spelling through `ParseCanonical`; a command's name moved to the front of its flags by its parsed position; a guest report's decode against a plain inflate and an ordinary `json.Unmarshal`, its bytes against `json.Marshal` of the value, and its bounds and orders walked by hand, every refusal an `*Error` whose text is drawn from a closed set; and what the agent parses from a guest against the guest report's own encoder, which must take every mark, row and suite a parse keeps, with a comm held to the bytes between the stat line's first `(` and its last `)`. A seed set that never reaches the interesting branch proves nothing there, so `FuzzConfigParse` asserts at setup that its valid seed parses. Seeds are real inputs (the golden wire fixtures, every migration, `billet.example.yaml` and the packaged template), so the search starts from what billet meets. `go test` replays the seeds and anything committed under a package's `testdata/fuzz/`, so they run in `scripts/gates/test.sh` and on every pull request; the search past them runs nightly on main (`.github/workflows/fuzz.yml`, ten minutes a target) and locally with `FUZZTIME=1m scripts/gates/fuzz.sh`, which reads the workflow's list. `TestEveryFuzzTargetIsSearchedNightly` parses every test file of the module and holds the Fuzz functions it finds equal to that list. A property the search breaks is either a bug, fixed with the failing input committed as a seed, or a property stated too widely. Both happened on 2026-10-08. Two bugs: the plane's decoder accepted a body with anything after its first JSON value, unread (fixed: one value and nothing after it), and a tier with two oversized cache volumes was refused naming either one, whichever a map iterated first, so the same file read differently on each run (fixed: a fixed order). And two properties stated too widely: moving a command's name across a `--`, and a statement body holding a marker line, change the input's meaning (properties narrowed, parsers right). An oracle that reads the parser's own output is not independent: the version order is checked against digit strings read from the inputs, and a migration made only of bodies a migration may hold must parse, or a parser refusing everything passes by refusing.

**The host rehearsals run the real commands on packaged hosts under real systemd, and each needs a real App.** `scripts/rehearsal-lib.sh` starts privileged `ubuntu:24.04` containers with systemd as PID 1 (the shape `scripts/test-systemd-lifecycle.sh` measured), installs a `.deb`, issues certificates as the service account and asserts on unit state, journals and files, never on an exit code alone. `scripts/rollout-rehearsal.sh` moves two hosts from one PUBLISHED release to the next by `billet rollout start` and the controller's upgrade unit, then refuses a downgrade candidate that cannot serve the ledger before any host is touched (`BILLET_REHEARSAL_FROM`/`_TO`, a pair that crosses a ledger migration); `recover-rehearsal`, `ca-rotation-rehearsal` (twenty-minute leaves through `billet ca issue --lifetime`) and `promotion-rehearsal` (a PostgreSQL pair partitioned with `docker network disconnect`, keepalives set on the server) use the tree's own package from `scripts/gates/dist.sh`. `retirement-rehearsal` adds a node on the retiring PostgreSQL controller, moves both nodes to the survivor, and submits a retained-node request built from fresh real inspections after reservation; it uses the tree's package too. All five skip without `BILLET_REHEARSAL_APP_CONFIG` and `BILLET_REHEARSAL_APP_KEY`, because a control plane cannot start without GitHub and nothing honest stands in for it; nothing runs them on a schedule (`rehearsals.yml` was removed on 2026-09-25 with the test organization's App), so they are run by hand before a release that touches what they drive. The architecture is the docker daemon's, not `uname -m`'s, so they run on a Mac's Docker Desktop too. Three rules the first review round wrote down: a registration is proved by the server journal's `node registered node=<name>` line after a clock mark taken before the boundary, never by the name appearing in `billet status`, which prints every node the ledger knows whether or not one has connected; a negative assertion captures the producer's exit status and greps a here-string, because `cmd | grep -q` under `pipefail` and `|| true` both turn "could not tell" into the absence being asserted; and a teardown that fails fails the run, since a green rehearsal that left a scale set behind hides the one thing an operator has to act on. Results go in `docs/reference/records/host-rehearsals.md`.
