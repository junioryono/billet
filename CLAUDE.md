# billet

Self-hosted GitHub Actions runners on your own hardware, with a colocated cache. Go, Apache-2.0, single static binary. Pre-alpha.

## Architecture

One binary, two roles. `billet server` is the control plane: it long-polls GitHub's Runner Scale Set API for assigned jobs, owns the capacity ledger, and tells nodes what to launch. `billet node` is a compute host: it runs a provider and launches instances. A single machine runs BOTH, as two processes reading one config file and talking over loopback. There is no combined mode.

```
cmd/billet/          the binary: server | node roles, plus the whole operator CLI
internal/config/     billet.yaml schema + validation (a leaf package — imports nothing of ours)
internal/state/      SQLite control-plane store: capacity ledger, job history, process lock
internal/github/     App Manifest onboarding, App JWT, installation resolution
internal/alloc/      capacity allocator, placement, lease state machine
internal/server/     scale-set listeners, scheduler
internal/node/       node runtime: provider driver, capacity reporting, custody
internal/nodeplane/  the mTLS node wire: registration, command dispatch, incarnations
internal/provider/   firecracker | tart | ec2 | codebuild | docker  (all built)
internal/store/      site storage: ceph/ drives RBD through the rbd command
docs/                reference-hardware.md — the two hosts billet is measured against: the bare-metal Linux box and the Mac
```

Layering is enforced by `depguard` in `.golangci.yml`, not by convention: `provider` and `store` are siblings that may not import each other or the scheduler, and `config` may not import any other billet package.

## Commands

```bash
make check     # build + vet + fmt-check + lint + race test — the pre-commit gate
make build     # ./bin/billet
make test      # go test -race -count=1 ./...
make cover     # coverage profile + HTML report
make lint-fix  # auto-fix what can be auto-fixed
make lint-custom # billet's own analyzers (tools/lint), and the tests proving they still detect
make sqlc      # regenerate internal/state/ledgerdb from internal/state/queries
make sqlc-check # prove the committed query code is what sqlc generates
make cross     # build every target a node can run on — catches build-tag mistakes
make dist      # build the release artifacts locally, exactly as a tag would
make tf-fmt-check tf-validate tf-test tf-lint tf-scan  # the terraform gates — run before pushing a .tf change
```

`make check` is the gate and must be clean before every commit. The terraform gates are deliberately outside `check` (they need terraform/tflint/trivy installed — `make tools` installs the pinned scanners); CI runs them on every PR, so a green `check` alone does not cover a `.tf` change. **`sqlc` and `sqlc-check` are outside it too, and for the opposite reason to the terraform gates**: the generated query code is committed precisely so an ordinary build never downloads sqlc, and CI installs the pin and runs `sqlc diff` in its own job. `lint-custom` IS in `check`, because a nested Go module needs nothing installed. When the gate fails, fix the cause; a lint failure is never suppressed with `nolint` (see the `billet-linting` skill).

## Writing prose: no early line breaks

**Never hard-wrap Markdown, GitHub issue bodies, PR descriptions, or commit message bodies at a fixed column.** Write each paragraph as one long line and let the renderer wrap it. A hard-wrapped paragraph is unreadable in a GitHub textarea, produces a diff on every edit where whole paragraphs reflow, and makes a one-word change look like a rewrite. This applies to `CLAUDE.md`, every `SKILL.md`, `README.md`, `docs/**`, issues, PRs, and comment bodies.

Go source comments are the exception: those follow the surrounding file, which wraps at 88 columns.

## Comments in Go

Types and functions get a doc comment; cut it to what the name does not already say. A comment inside a function survives only where it marks something a reader would otherwise get wrong — an ordering requirement, a unit, a "this must not move". Do not narrate what the next line plainly does, and do not write the history of the code ("this used to…", "the first version…"): state the rule that holds now, and keep the failure it prevents only where that failure is the reason.

## Working style

Deliver what was asked, at the scope asked. Make routine judgment calls yourself and check in only when two readings of the request would produce materially different work. If the request looks mistaken, say so in a sentence and continue rather than quietly narrowing or widening it.

Prefer reading a whole file over sampling it. Most of the mistakes in this repo's history came from patching a region without seeing what surrounded it.

Delegate to a subagent only for a genuinely independent, wide investigation. Do not delegate work you can finish in a handful of tool calls, and do not use a subagent to double-check your own work.

Report what happened, not what should have happened: if a test fails, say so and show the output; if you skipped part of a task, say which part.

## Gotchas

- **`config` is a leaf package.** It imports nothing else in billet, and `depguard` enforces it. Validation rules that `alloc` also needs are exported from `config` and called from both, never copied.
- **`alloc.New` cannot assume its catalogue came through `config.Load`.** It is exported, so it re-applies the safety-critical rules itself. A rule enforced in only one of the two has a second entry point that does not enforce it.
- **The example config and the packaged config are both tested.** `billet.example.yaml` and `deploy/billet.yaml` are parsed by the config test suite, so a renamed or moved key breaks the build rather than an operator's install.
- **Two commands write `/etc/billet/billet.yaml` under different rules, and that is a decision rather than an accident.** `billet init` GENERATES a whole config, so it may replace an existing one only where `initconfig.PlanReRun` proves the bytes are its own output (or under `--force`), and otherwise writes the fresh generation to `<path>.new`; `billet github-app create --config` EDITS the file in place, setting five scalars under `github:` and preserving every other value, the comments, the mode and the owner — because the App identity is exactly the thing that has to land in a config an operator already has, and no generator can merge it for them. What made the pair a trap was silence: nothing said which rule was about to apply, so both are now stated in `configEditRule`, which `github-app create` prints before it opens a browser and `init` prints in the branch that writes a `.new`. The edit's own failures were worse, because they landed LAST: a `--config` that does not exist, a `github:` key holding a list, and a directory billet cannot write all surfaced as `could not update <path>` with the App already registered, its one-time private key already spent, and the command exiting 0 — after which re-running mints a SECOND App rather than recovering, and the one early read that existed (`defaultKeyPath`) was skipped whenever `--key-path` was given. `planConfigEdit` decides all of it before `github.Onboard`, and its structural check is the REAL renderer against a probe identity rather than a second opinion about acceptable YAML, because a separate reading agrees today and drifts on the next field added to the block. Do not add a third writer of that path without deciding which of the two rules it follows.
- **A loopback `server.listen` serves plain HTTP.** That is the single-machine shape, and setting `node.tls` against it is a config error rather than an upgrade.
- **A CONNECTION BUDGET TAKEN BEFORE THE HANDSHAKE CANNOT SEPARATE AUTHENTICATED CALLERS FROM ANONYMOUS ONES, and that is why the node wire is two listeners.** `/v1/ca` and `/v1/enroll` must serve a machine that has not enrolled, so they cannot require a certificate; while they were on `server.listen` its cap was SHARED with them, and a caller that completed a handshake, asked for the authority and idled held a slot until `IdleTimeout` — about **4.3 requests a second** emptied 512, after which `limitedListener.Accept` blocks acquiring a permit BEFORE the underlying accept, so a healthy node's socket sits in the kernel backlog until its own handshake timeout fires. The fleet is down and nothing in the process is misbehaving. Reserved capacity looks like the fix and is not: the permit is taken before the handshake because the handshake is itself work an anonymous caller can ask for, and which caller holds a certificate is not known until after it — so any pre-handshake quota is shared by construction and a small anonymous one only makes the attack cheaper. The only separation that holds is the TLS layer refusing a certless connection, which forces the bootstrap routes onto their own port: `wirecert.ServerTLS` is `RequireAndVerifyClientCert` and `nodeplane.Handler` registers no unauthenticated route, while `server.bootstrap_listen` carries `nodeplane.BootstrapHandler` under `wirecert.BootstrapTLS` (`NoClientCert`, since nobody there has one and asking only parses a chain a stranger chose). **Its ABSENCE is the refusal** — no address, no network enrollment, and `billet ca issue` remains the way in — and the port is meant to be closed between enrollments, because nothing a running fleet does goes through it. Three things about bounding it were measured rather than read: the handshake deadline is DERIVED, `Server.tlsHandshakeTimeout` being the minimum of the POSITIVE `ReadHeaderTimeout`/`ReadTimeout`/`WriteTimeout` (the node wire has no `WriteTimeout` on purpose, so its bound is the 10s header timeout, and zeroing the other two would make it unlimited); the enrollment route needs a CONCURRENCY bound as well as a connection one, because recording a request begins `BEGIN IMMEDIATE` against SQLite's single writer, the connection the node wire also needs; and Go's `http.Server` withholds the whole response until an announced request body arrives even for a handler that never reads it, so "announce a Content-Length and send nothing" cannot prove that `/v1/register` authenticates before it decodes — wrap `r.Body` and count. **SPLITTING THE LISTENERS WAS ONLY HALF OF IT, and the half it missed was worse: the permit was taken in `Accept`, BEFORE the handshake, where nobody has presented anything — so opening sockets and sending no TLS bytes at all spent the FLEET's budget**, ~52 connections a second holding all 512 for the handshake timeout while `Accept` blocked ahead of the kernel accept. `handshakingListener` (`cmd/billet/handshakelistener.go`) is the answer: accept unconditionally, bound handshakes separately under an EXPLICIT deadline, and charge the server's budget only for what verified. It wraps the tracking conn BENEATH the `tls.Conn`, because `http.Server` type-asserts to `*tls.Conn` to populate `Request.TLS` and a wrapper on the outside authenticates nobody and rejects the entire fleet. **Releasing a permit is a RECEIVE, so releasing one that was never taken blocks forever** — measured: dropping the `charged` guard did not fail a test, it hung the closing goroutine, which on a public port is a control plane accumulating stuck goroutines every time somebody fails to connect. The release is now non-blocking as well, so that mistake degrades into an accounting error a test can see. What is guaranteed is that anonymous traffic can never displace an ADMITTED node; what is best effort is a handshake SLOT, since pre-authentication the two are indistinguishable — a flood can still get a node's handshake refused, but it is refused instantly and the node redials rather than waiting on a backlog. That residual is not closable in userspace and is what a rate limiter in front is for.
- **EVERY TOKEN BILLET MINTS IS SCOPED TO AN INSTALLATION, so losing the installation looks like nothing in particular.** An App uninstalled from its organization — or an `installation_id` left behind by a reinstall — fails several wrappers deep inside the vendored scale-set client as a bare `404 Not Found` on `/access_tokens`, naming neither the App, the org, nor anything to do; the packaged unit then restarts on it forever. Measured on the reference host: **42,940 restarts** on that 404. `billet check` had always answered it (`github.VerifyAppAt` produces the sentence), and nothing on the path that actually fails ever asked — which is the shape to look for, not the specific bug: billet already owning the diagnostic and never reaching for it where it is needed. `explainGitHubAccess` now asks after a failure, and three of its rules are what keep a diagnostic from being worse than none — it never replaces the original error (asserted by PREFIX as well as `errors.Is`, since reordering satisfies matching and still buries the account of what billet was doing), it never claims to have found the cause (`Run` covers the whole lifetime and billet has no typed handle on the vendored client's errors, so it asks rather than answers), and it separates an unreachable GitHub from a refused credential, because reporting a 502 as "your App is not installed" sends an operator to reinstall something that was never broken. **A CONTROL PLANE AUTHENTICATES UNDER TWO ISSUERS** — billet's runner-group policy client signs with `app_id`, the scale-set client with `client_id` when one is set — so a check that signs with one may not vouch for the other, and where `client_id` is configured the healthy report says which of the two it actually tested.

- **`make cross` before anything touching build tags.** The `flock` state lock is `//go:build unix`; CI cross-builds linux/amd64, linux/arm64 and darwin/arm64.
- **`set -e` is IGNORED for a pipeline preceded by `!`, so `! cmd | grep -q .` is not a check.** POSIX specifies it, and it was measured on `/bin/sh` rather than read: the line after a failing `! printf x | grep -q .` executes and the script exits 0. billet's shell is full of gates that must end a build — `scripts/check-guest-image.sh`, `scripts/build-guest-image.sh`, and the provisioning script `internal/provider/ec2/build.go` generates — and every one of them written that way computes the right answer and then lets the build succeed. Write the failing path as an `if` with an explicit `exit 1` and a message saying what is wrong; `!` inside an `if` CONDITION is fine, since the condition's status is consumed rather than inherited. The same gate had already been wrong once for a different reason: `grep -qFf anchor.crt bundle` reads one pattern per LINE and succeeds if any matches, and every certificate shares `-----BEGIN CERTIFICATE-----`, so it matched a bundle containing a different certificate entirely. A shell gate is worth executing in a test against both a passing and a failing fixture, not pattern-matching in the Go that emits it. **AND A GATE IN THE MIDDLE OF A `;`-CHAIN IS NOT A GATE AT ALL, WHICH IS THE SAME RULE ONE SEPARATOR OVER.** Measured under dash in `ubuntu:24.04`: in `mkdir …; curl …; sha256sum -c -; tar -xzf …`, a FAILING checksum prints `FAILED`, execution carries straight on into `tar`, the archive extracts, and the whole command exits **0** — so the generated CodeBuild buildspec would have installed and run a runner tarball billet never pinned, with the verification visible in the log and doing nothing. The trailing `test -x` behind it does not save you either: a tarball that extracted HAS a `run.sh`, so the gate passes on exactly the payload it exists to refuse (it does still catch a download that failed outright, which is the case it was written for). `set -e` fixes it and depending on `set -e` is the trap, because a buildspec's commands are run by CodeBuild rather than by a script billet controls — and billet's own comment claimed the chain did not rely on it while it relied on nothing else. Chain the steps with `&&`, which short-circuits and leaves the compound non-zero under either regime. **The reason no test could see it is worth more than the fix**: the harness that EXECUTES the buildspec adds `set -e` itself (correctly — that is how CodeBuild treats a phase), so the one instrument capable of catching this had the defect masked by its own realism, and the fetch path was otherwise only ever `sh -n`'d. A test for a gate that must hold WITHOUT some ambient setting has to withhold that setting.
- **EC2 user data is 16384 bytes and base64 is the wrong way to spend it.** billet gzips the provisioning script past that limit (cloud-init decompresses it), and the toolcache pushed the script from 11.6KB to 35KB plain. Measured against the real files: base64 of the shared installers and the pinned declaration gzips to **27235** — over by more than ten kilobytes — because base64 costs 33% BEFORE gzip and destroys the redundancy gzip lives on. The same bytes in quoted heredocs, with whole-line comments stripped, land at **11327**. The strip has to be WHOLE-LINE: `s/#.*$//` treats `${v#v}` and `${version#go}` as comments when they are parameter expansions, and the result fails `bash -n` — an earlier "it fits" measurement was taken against exactly that wreckage. The budget is SHARED, which is why `maxCACertPEM` is 8 KiB rather than 32: with the toolcache present a 32652-byte bundle takes the payload to 24239 compressed, so the old bound promised something every such build would refuse. `packUserData` is the real gate, since deliverability depends on everything else in the script.
- **The toolcache installers are ONE file, sourced by the guest build and carried to the EC2 builder.** `internal/runnerimages/install-toolcache.sh` is ~650 lines where nearly every line is a trap that cost a debugging session, so a second copy for the second backend is the two-pins problem wearing different clothes. The seam is one function: `billet_tc_run` is `chroot "$BILLET_TC_ROOT" "$@"` for the guest, which assembles a filesystem it is not running, and `"$@"` for the AMI, which IS the target. They are bash — arrays, `declare -n`, `${x/y/z}` — so a `/bin/sh` caller runs a bash driver that SOURCES the file, because a function definition does not cross a process boundary. Deleting the chroot is not a subtle failure: the guest build would install five JDKs onto the BUILD HOST, report success, and ship an image with none of it, and no test that READS the script can see that.
- **Every toolcache vendor spells the architecture differently, and the record has THREE states rather than two.** `internal/runnerimages/install-toolcache.sh` builds both x64 and arm64 from one `BILLET_TC_ARCH`, and not one of the six translations is derivable from another: node and Python use `@actions/tool-cache`'s own name (`x64`/`arm64`), go and temurin use dpkg's (`amd64`/`arm64`, one of them inside a filesystem path), **pypy calls arm64 `aarch64`** where every neighbour says arm64, and **ruby-builder suffixes arm64 while leaving x64 completely bare** — which is why upstream's own `-${arch}` pattern resolves nothing for x64. Two traps in opposite directions, so a single substitution breaks both. The architecture is REQUIRED rather than defaulted, because an unset one defaulting to x64 builds an x64 toolcache onto an arm64 image: every entry structurally complete, every binary the wrong format, and nothing failing until a job execs one. And `/opt/hostedtoolcache/.billet-unpublished` — which both gates accept a declared line's absence for, and ONLY when named there exactly — must be written by the narrowest question available, because "my query found nothing" is three facts: the vendor published nothing (record it: CodeQL has no arm64 bundle, ruby-builder has no 4.0), the vendor published something billet cannot verify (record it: pypy ships aarch64 builds for 3.9 and 3.10 that its checksums page does not cover, measured — 115 aarch64 lines and neither of those releases), and billet's selector has gone stale against a rename or a platform bump (FATAL, because the line is published and billet simply cannot find it). Collapsing the third into the first ships an image with none of a runtime past a gate that accepts the record. That distinction has been needed three times in one file.
- **`env` resolves EXECUTABLES, not builtins, and this Mac hides it.** billet's privilege drop ends in `env -i PATH=… "$@"`, so whatever follows it is resolved by env rather than by a shell — and env can only exec a FILE. `command -v`, `type`, `cd` and any shell function are builtins and are simply not found there. What makes it expensive is the platform: **`/usr/bin/command` EXISTS on macOS** (one of Apple's builtin stubs, link count 15) and does not on Ubuntu, so `env -i PATH=… command -v sh` exits **0** here and **127** on the image. An artifact gate emitted as `<drop> command -v "$1"` therefore passed every local run and would have failed EVERY verification of EVERY real image, reporting each one as missing a declared global that was installed correctly — a gate refusing correct artifacts, which is the failure ADR-005 names, because the next thing anybody does is delete the check. The form that works is `sh -c 'command -v "$0" >/dev/null' <cmd>`, since `sh -c script name` sets `$0` and the command word never reaches env's exec path. The rule for anything added to a dropped-privilege check is not "it is on PATH" but "it is a file"; `internal/provider/ec2/gateexec_test.go` asserts exactly that, structurally, because a fixture cannot.

- **A probe on the development Mac is not evidence about the builder, and this cost four rounds in one piece of work.** Each was a different mechanism and each reported success: a suppressed `apt-get update` made a probe report "0 lines" from a file it had never fetched; an `ldd` jail copied the very library it was testing for; a fake chroot prefixed only `argv[1]`; the shell's `grep` is **ugrep**, which reads UTF-16 transparently where GNU grep cannot, so a broken decoder looked correct. The `env` gotcha above is the fourth, and the first one CI caught that a local `make check` could not — same commit, same test, opposite verdicts, the only difference being `/usr/bin/command`. Run the probe in `ubuntu:24.04` (or read the bytes with the builder's own tools) before believing it, and prefer an assertion about bytes or emitted argv over a pipeline that happened to work somewhere.

- **A GATE'S VERDICT IS ITS EXIT STATUS, AND THE GUEST KERNEL'S WAS BEING PRINTED INSTEAD.** `scripts/build-guest-kernel.sh` named moby's `check-config.sh` as its Docker compatibility test, ran it only if somebody had happened to leave a copy beside the work directory — which no release run ever did, so every published kernel printed `skipped` and shipped — and, on the branch that did run it, ended in `| grep -Ei missing | head -30 || echo "NOTHING MISSING"`. MEASURED in `ubuntu:24.04` with `CONFIG_VETH=y` removed: the checker exits **1**, that pipeline prints all fifteen `missing` lines AND THEN `NOTHING MISSING`, and the build continues and exits **0** — under `pipefail` the checker's failure becomes the pipeline's status and `|| echo` fires on the failure path. The text is misleading in both directions, because a PASSING kernel legitimately reports about a dozen OPTIONAL features missing. So `scripts/check-guest-kernel-config.sh` captures the status BEFORE anything filters the output, and the checker is VENDORED at `scripts/kernel/check-config.sh` with its commit and sha256 in `check-config.pin`, verified before it is executed (`internal/runnerimages`' shape: commit is provenance, digest is integrity). **THAT STATUS IS NOT PURELY ABOUT THE CONFIG**, read at the pinned revision: it is also 1 for a cgroup v1 hierarchy that is not properly mounted, for apparmor enabled without `apparmor_parser`, and for `kernel.keys.root_maxkeys <= 10000`, and `check_sysctl` aborts the whole script under `set -e` where `sysctl` is missing — all facts about the BUILD HOST. The gate requires 0 anyway and names those lines when it fails, because an unexplained refusal of a correct artifact is what gets a check deleted (ADR-005). **Billet's own rule is the artifact-level claim and depends on no host fact**: every option in `scripts/kernel/required-builtins.txt` must be `=y` and the config may contain NO `=m` line at all — one rule that covers every flag moby grades, because a microVM has no initramfs and moby accepts `=m` for all of them; restating moby's list with a tighter rule attached would be a second copy that drifts. That file is also what the build ENABLES, so the list that is set and the list that is checked cannot diverge. **AND THE WORKFLOW RUNS THE GATE ITSELF, not only through the build script**: the kernel is cached on its inputs, `actions/cache` saves in its post step even when a later step failed, and the build script does not run on a hit — so a kernel that failed the gate would come back and publish unchecked. **THE GATE'S OWN SUMMARY WAS THE LAST PLACE THE TRAP HID**: printing the optional-feature lines as `grep -Fi missing "$out" | head -30` is MEASURED at exit **141** on a 2.9MB file under `set -euo pipefail` — head leaves after thirty lines, grep takes SIGPIPE, and a PASSING kernel fails the gate over its own diagnostic, depending on how much the checker happened to print. One `awk` reads to the end and has nothing to signal. And the checker is COPIED into the gate's private directory before it is hashed, because hashing a path and executing that path are two lookups of a name: the digest would vouch for bytes other than the ones that ran.

- **GITHUB'S THIRTY DAYS START AT THE FIRST RELEASE NEWER THAN YOURS, and billet counted from two other timestamps.** `billet runner check` used `/releases/latest`'s `published_at + 30 days`, so every later release moved an already-passed deadline forward: 2.334.0 went out of date when 2.335.0 was published 2026-06-08 (window closes 2026-07-08), and counting from 2.336.0 on 2026-07-20 reported 2026-08-19 — a fleet GitHub had refused for six weeks, described as having a month in hand. `billet images pull` refused at `built_at + 30 days`, which is evidence about NEITHER direction: an image built the day a release shipped is still current a year later if nothing else ships, and one built yesterday around a runner three releases behind is already refused. `runnerrelease.Resolve` is now the ONE calculation over `(installed version, stable release history)` and both commands ask it. Three things about it are load-bearing. **The clock starts at the EARLIEST newer release by PUBLICATION, not by version** — a backport published after a later minor is newer than the installed release and did not open the window. **A version the fetched history does not name is its own answer** (`InstalledKnown`), not "current": the true window opened at or before the earliest release billet can see, so the computed deadline is an UPPER BOUND — `Expired` and `Due` stay sound there and "days remaining" does not, which is why `runner check` proves an expiry and otherwise reports that it could not establish the position. **And 30 days is the ORDINARY window rather than a guarantee**, since a critical security release may be enforced at once and GitHub publishes no minimum-version endpoint — so import refuses only on a proved expiry, says `cannot determine` when it could not ask, and image age survives as maintenance information (`imagesource.AgeNotice`, about billet's weekly build) that decides nothing. Two things a review then found, both reading as obviously safe. **STOPPING THE PAGE WALK AT THE INSTALLED TAG IS UNSOUND**, because it assumes version order matches publication order — and actions/runner's own history disproves it: MEASURED on one page, **v2.285.3 was published 2023-01-30, eleven days AFTER the higher v2.301.1 on 2023-01-19**, so a fleet on 2.285.3 that stopped at its own tag never sees the release that opened its window and answers later than the truth. The whole bounded window is scanned; a page is ~5MB and one page reaches back FIVE YEARS, so the bound is two. **AND `Current` MEANS ONLY "NOTHING NEWER WAS FOUND"**, which is equally true of a version the history does not name — so asking it before `InstalledKnown` printed "which is the current release" and exited 0 for precisely the version billet could not place.

- **A REMOTE RECORD MAY NOT NAME A LOCAL FILE THAT IS NOT DURABLE YET.** `billet images pull` installed the paired kernel and then committed Ceph generation metadata naming that exact filename — and the install synced the file, changed its mode AFTER that sync, renamed it, and returned without ever flushing the containing directory. `fsync(2)` says plainly that flushing a file does not flush the directory entry that names it, so a power loss in between leaves a COMPLETE, remotely visible generation whose kernel disappeared in recovery: every node resolves a verified generation and cannot boot the kernel it was verified against, re-pulling repairs only the local half, and the cluster keeps advertising a pair that never existed. The ordering is now one primitive, `internal/durablefile`: **metadata change → file sync → atomic rename → containing-directory sync**, with the caller's write callback in front of it so a digest can refuse before anything is renamed. Two decisions in it are not obvious. A failure anywhere up to the rename leaves NOTHING behind, but a failed DIRECTORY SYNC leaves the file — the entry may already be durable, an unlink is no more durable than the rename was, and the retry re-verifies the content and flushes again; so `installKernel`'s "already there" branch must flush the directory too, or the retry that is supposed to repair the state is what certifies it. And the mode is set BEFORE the sync, because a chmod behind it is metadata nothing committed and the file can come back 0600 — unreadable by whatever boots it. The property that matters is not the primitive but the ORDER at the call site, so `cmd/billet` reaches the cluster through a `generationPublisher` interface and the installer is a package variable: `TestAPullDoesNotPublishAGenerationBeforeTheKernelIsDurable` fails each local step in turn and asserts `ImportGeneration` was NEVER REACHED, because "an error came back" is satisfied by a command that published first and complained afterwards. **AND FLUSHING A DIRECTORY DOES NOT COMMIT THE DIRECTORY** — the same defect one level up, found by a review: `Install` flushes the entries INSIDE the kernel directory, and on a fresh host nothing else creates that directory, so a crash could take the whole thing away while every step reported success. `durablefile.MkdirAll` flushes every ancestor, and does so even when the directory already exists, because a previous run may have created it and died before its parent was committed. The reuse branch has the same shape: a kernel installed by the OLD implementation can hold the right bytes at **0600** — the mode was set after the sync that would have committed it — so "already there" re-applies the mode and flushes the file through ONE `O_NOFOLLOW` descriptor rather than re-addressing the pathname three times, since this runs as root and a symlink under that name would be hashed as one file and chmod'ed as another. **AND THAT WALK MUST FOLLOW THE RESOLVED PATH AS WELL AS THE NAME**, because `os.MkdirAll` follows symlinked components while a lexical walk climbs the string: a kernel directory on another volume (`/var/lib/billet` a link to `/mnt/vol/billet`, the ordinary way a large artifact directory is moved) would have its lexical parents flushed and the entries that actually name it never committed. Both are walked. Two smaller ones from the same round, each MEASURED rather than reasoned about: `O_RDWR` on a kernel an operator left **0444** fails with permission denied while a chmod and an fsync both succeed through a read-only descriptor — asking for access billet does not need refuses a correct artifact, which is the failure ADR-005 names; and a test hook that fails EVERY directory sync aborts at the first ancestor and never reaches the branch it is named for, which is how deleting the reuse branch's own flush survived a mutation run. **A THIRD ROUND THEN FOUND THE SAME PIPEFAIL TRAP ONE BRANCH OVER FROM WHERE IT WAS FIXED**: the MODULE refusal still printed through `grep … | head -20`, MEASURED at exit **141** on a 3.2MB config — so the sentence saying WHY, and the deliberate `exit 1`, were never reached. The verdict stayed a refusal, which is exactly why it survived a reading. Three more from that round, each the same rule from a different side: a chmod to the mode a file ALREADY HAS still fails on a read-only mount (measured: EROFS, while both fsyncs succeed), so attempting it unconditionally refuses a correct kernel; the two ancestry walks flushed the same physical directory twice, and a redundant fsync that failed would reject a directory the first one had committed; and the page walk needed a bound that TERMINATES, which is the installed RELEASE rather than a higher version NUMBER — everything below it was published earlier and was already available when it shipped, while stopping at a higher number is the unsound thing the measured v2.285.3/v2.301.1 pair rules out. Running out of that budget is recorded (`HistoryComplete`) rather than read as an ending, because it takes away "nothing to do" and leaves the expiry proof standing.

- **AND A DURABLE FILE IS NOT A FILE NOTHING ELSE WILL DELETE, WHICH IS THE SAME BROKEN STATE REACHED BY A RACE INSTEAD OF A POWER LOSS.** The durability rule above proved a pull publishes nothing remote until the kernel is committed; it did not exclude a concurrent `billet images reap`, which computes the kernels a surviving generation needs FROM THE GENERATIONS THAT EXIST WHEN IT LOOKS — and between `installKernel` and `ImportGeneration` returning, nothing anywhere names the file the pull has just installed. So the reap correctly calls it an orphan, unlinks it, and the pull then publishes a generation naming a kernel that is gone. **The Ceph publish lock does not cover that interval and could not be made to**: it makes generation removal and generation publication exclude each other, while the install happens before `ImportGeneration` takes it and `reapKernels` runs after `Reap` has released it — and it is CLUSTER-WIDE with a six-hour stale bound, so holding it across one machine's disk work would serialize every node's publishing on a fact about one directory. **Re-checking the file just before the import is not a mitigation**, because the reap can unlink it a microsecond later; it would read as a proof and not be one. Nor does an open descriptor help — the reuse branch hashes, chmods and flushes through one and every step still succeeds after the pathname is gone. **A DESCRIPTOR PROVES THE BYTES; IT DOES NOT PROVE THE NAME, and the name is what a generation records.** The answer is billet's FOURTH lock discipline, `cmd/billet/kernellock.go`: an flock on `<kernel dir>/.billet-kernels.lock`, held by the pull from before the install through a successful `ImportGeneration` and by the reap from before it reads the generation set through the deletion. **It is keyed on the DIRECTORY** (the tart store lock's rule, for the same reason — two deployments on one host can share one, `--kernel-dir` overrides the config on either command, and a symlinked directory resolves to the same FILE where a key derived from the path would spell two), and **it WAITS** where `state.LockDeployment` refuses, also for the tart store lock's reason: a second holder is ordinary maintenance rather than a second control plane, and the ansible host role runs `billet images pull --verify` inside a transactional upgrade a refusal would roll back. It announces the wait once before blocking, because a bounded wait nobody can see is a command that looks wedged and then gets killed. **THE REAP TAKES IT AT THE TOP, ABOVE `store.Reap`, AND THE NARROWER SCOPE IS THE TRAP**: taken only around the kernel half, a reap holding the publish lock while a pull holds the kernel lock makes that pull's `ImportGeneration` fail outright, since `TakePublishLock` never waits — so the rule is that this lock is ALWAYS outside the publish lock, which holds only because nothing that takes the publish lock wants this one (`RecordVerification`, `MarkVerified`, `UnmarkVerified` never touch the kernel directory, and `--verify` releases this first). **`--dry-run` takes no lock**, deliberately: taking one means CREATING a file, so a preview would start refusing on a read-only kernel directory over an operation that changes nothing, and the plan that is acted on is re-derived inside the exclusion anyway. Two more. `billet images verify` needs none — it records either the already-recorded kernel or `configuredKernelName`, and `PlanKernelReap` protects both. And **the reaper must never unlink the lock**: the filename pattern already excludes it, so `reapKernelDir`'s explicit skip is redundant TODAY and is kept because unlinking a HELD lock file does not release the flock — it detaches the PATH from the locked inode, after which the next billet locks a fresh file under that name and both run, which is the failure that moved the deployment lock out of a cache directory. Proved by mutation in exactly that shape: removing the skip alone leaves the test green, removing it AND widening the pattern turns it red. **A SEPARATE DEFECT MADE THE WHOLE THING CONDITIONAL AND HAD TO GO FIRST**: `billet images pull`'s `--kernel-dir` defaulted to the CONSTANT while the reaper, `configuredKernelName` and the LAUNCH all resolved `node.firecracker.kernel_dir`, so a host that set that key installed kernels where the launch does not look and the reaper does not either — and a lock keyed on the directory excludes the two commands only when they resolve the same one. `nodeKernelDir` is the one answer, and it already said so.
- **`grep -q` under `pipefail` returns the WRITER's SIGPIPE, not "not found".** Measured: `printf big | grep -qxF <early match>` exits **141**, a late match exits 0, and no match exits 1 — because `grep -q` leaves the instant it matches and `pipefail` then reports the pipeline as the writer's status. So `if ! printf … | grep -q …` reads a value that IS present as absent, intermittently, depending on whether the writer finished; that is a gate failing a build over something the image has, in a way that will not reproduce. Use a here-string, which has no writer to signal. The same shape killed an EC2 build through `awk '{print; exit}'` on pypy's 106KB checksums page while identical code passed in a container. Related: grep's status is three-valued — 0 found, 1 not found, **anything above 1 could not look** — and folding an error into "not found" is the same could-not-tell/no collapse the credential paths already removed.
- **A MIGRATION'S STATEMENT BYTES ARE PUBLISHED, AND THE PROSE AROUND THEM IS NOT.** The migrations live in `internal/state/migrations/NNNN_name.sql`, discovered by `go:embed` and parsed by `internal/state/migrationfiles.go`. A migration is identified by its version AND a sha256 over its statement bytes with a `0` separator between them, and that sum sits in every deployment's `schema_migrations`; `Open` refuses a recorded sum that disagrees with what the binary contains. So **the text between `-- +billet:statement` and `-- +billet:end` may never change, for any reason, reformatting included** — commit `ef84c7b` added two explanatory lines inside migration 1's `CREATE TABLE`, which SQLite could not have cared less about, and every ledger written before it stopped opening; it was found on the reference host. Migrations 1–42 therefore carry the tab indentation they inherited from having been Go raw string literals nested in a struct literal: it looks wrong and it is correct. `migrationsAreFrozen` in `migrationfreeze_test.go` holds all 42 published sums and is what turns a reformat into a CI failure rather than a fleet that will not start; it is also the *proof* of the extraction, because no approximate extraction can satisfy it. Three consequences worth keeping. **The file format is billet's own rather than goose's**, because a format a third-party tool recognises is a format that tool may decide to normalise, and the parser refuses a near-miss marker (padded, indented) instead of reading it as a comment — a padded OPEN marker silently skips the statement after it, a padded CLOSE marker silently joins into the one before it, and both change published bytes with nothing saying so. **The parse error is STORED rather than fatal** (`migrationLoad`), because a guard that fails during construction never runs: a tree with two migrations claiming one version must still be able to execute the freeze test and be told which two collided — which in turn means every test that iterates the set has to ask whether it loaded, or it passes vacuously exactly when something is wrong (found by mutation: a parser change turned 104 tests red and left the whitespace guard green). And **versions stay sequential and DENSE — 1..N with no gaps**, which is load-bearing rather than tidy: `state.LatestSchemaVersion()` is published in the release manifest as a single `int` and the upgrade fence refuses a candidate below the installed ledger's maximum, which is a sound proxy for "knows every applied version" only while the versions are dense — a binary carrying `{1..42, 44}` publishes 44, an installed ledger holding the same reports 44, the fence passes, and a later binary that fills in 43 applies it AFTER 44 there and BEFORE 44 on a fresh deployment, leaving two ledgers with identical recorded versions and checksums and different schemas. That is also why a timestamp scheme was rejected. Density is what FORCES the collision the scheme relies on, so `TestMigrationVersionsAreDenseFromOne` asserts the whole property rather than "above the published maximum" — the weaker form was vacuous in every green tree AND permitted 44-without-43, measured. And **`state.RefuseUnknownVersions` is the one COLD reader of the set** (`internal/deployarchive`'s restore planner calls it before any ledger is open), so it gates on `requireMigrations` itself; ungated it answered from an empty known set and accepted an archive whose applied set was empty, which the planner reads as permission to install a ledger this binary could never open.
- **LEDGER SQL IS GENERATED FROM NAMED QUERY FILES, AND A MIGRATION IS AN INPUT TO THAT GENERATION.** `internal/state/queries/*.sql` holds one named statement per operation for the WHOLE ledger — `internal/alloc`'s and `internal/rollout`'s included, because every guard on the query set is written once against that one directory and then covers every domain, and **the ban is now mechanical**: the `rawsql` analyzer in `tools/lint` refuses a call that executes SQL from Go anywhere in the module, default-deny, with thirteen reasoned `//billet:ignore rawsql` exemptions in `internal/state` and none anywhere else (it decides from the callee's SIGNATURE rather than its name, because `url.URL.Query` exists and a name-only rule is either noisy or stale); sqlc (pinned, `SQLC_VERSION`) compiles them into `internal/state/ledgerdb`, which `internal/state/queryset.go` binds and a depguard rule keeps importable from those three packages and nowhere else, for its parameter and row types only — the HANDLE comes from `state.ReadQueries`/`state.WriteQueries`, so there is one implementation of the read-only refusal and one place listing every query in exactly one of the two halves. sqlc owns exactly that translation: the process lock, the single writer, `BEGIN IMMEDIATE`, the busy retry, the pragmas, the fence and the migrations all stay hand-written. **The schema sqlc reads is a MIGRATION DIRECTORY ITSELF, not a flattened dump** — measured, its catalogue is identical to one derived from a real migrated database's DDL, rebuilds and `RENAME COLUMN` included — which removes the second source of truth a `schema.sql` would have been, and means adding a migration can change generated code. Since ADR-008 it reads `internal/state/pgmigrations`, because generation runs once with the PostgreSQL engine; **THE TWO TIMELINES ARE THE ONE PLACE BILLET CARRIES THE SAME IDEA TWICE**, DDL being the only unportable half, and what makes that survivable is that the PostgreSQL set is DERIVED — every file is its SQLite twin under four declared substitutions, re-derived and compared BYTE FOR BYTE in both directions by `TestEveryPostgresMigrationIsItsSQLiteTwinTranslated`, which is stronger than a schema comparison because two files can produce identical catalogues and still disagree about what they DO. The translation is LEXICALLY AWARE rather than a regexp: a global replacement would rewrite `UPDATE t SET kind = 'INTEGER'` and the derivation test would bless it, comparing the corruption against itself. The versions and names are identical across timelines on purpose, which is what leaves `state.LatestSchemaVersion()` a single published int and the upgrade fence untouched; only checksums differ, and nothing compares one across timelines. `sqlc diff` in CI is what says so, and explicit column lists (never `SELECT *`, enforced by a test) are what keep an ordinary `ALTER TABLE ADD COLUMN` from changing a byte. Three things were measured rather than read, and each cost a round: **the generated `DBTX` demands `PrepareContext` even under `emit_prepared_queries: false`**, so `Querier` stays two methods and is ADAPTED to it by `readOnlyDBTX`, whose `ExecContext`/`PrepareContext` refuse — widening `Querier` would have handed away the compile-time read/write split for a codegen convenience, and the split is restored by `ReadOps`/`WriteOps`, hand-written interfaces over the one generated `*Queries`. **`sqlite_master` is not in sqlc's catalogue**, which is why the schema-verification and `PeekLedger` queries are among the allowlisted raw statements (with the pragmas, `VACUUM INTO`, the bookkeeping DDL, the dynamically-quoted `COUNT` and the migrator executing published bytes — all listed in `internal/state/queries/README.md`). And **a query file must be ASCII**: sqlc rewrites `@named` parameters into numbered placeholders by slicing on BYTE offsets, so one em dash in a comment shifted every offset after it and turned `force_destroy` into `roy` — reported as an ANTLR `extraneous input 'roy'` naming neither the file nor the character, on queries far from the one carrying the dash. It needs both halves (the same dash with positional `?` generates cleanly), so the rule is that the files are ASCII, and `TestQueryFilesAreASCIIOnly` names the rune. The migrations themselves are unaffected — they are schema, get no parameter rewriting, and their prose is full of em dashes. **What proves the whole set still fits the schema is `TestEveryGeneratedQueryPreparesAgainstTheMigratedSchema`**, which parses the generated Go for every query constant and prepares each against a real migrated ledger: SQLite's prepare resolves a missing column, a missing table, a syntax error AND an `ON CONFLICT` whose unique index is gone (PostgreSQL's `PREPARE` defers that last one to EXECUTE; SQLite's does not), and sqlc does not model indexes at all — so that is the one class nothing else here would catch.
- **THE CONTROLLER CLAIM'S EPOCH IS A FENCE, AND `DB.Tx` READS IT INSIDE EVERY WRITE TRANSACTION.** A `pg_try_advisory_lock` stops a SECOND controller STARTING and does nothing about the one already running: the lock lives in a session billet does not control the lifetime of, so a server restart, an `idle_session_timeout`, a pooling proxy or a partition releases it and **the holding process finds out about none of it**, because nothing uses that connection again — after which a replacement claims legitimately while the first is still polling GitHub and dispatching launches. Detection cannot close that (the window between the partition and the observation stays, and a watchdog that stops a healthy control plane over a blip is its own failure), so `checkLeadership` refuses instead: `ClaimController` records the epoch AFTER its own transaction commits, and every later `Tx` re-reads `controller_claim` on that transaction and returns `ErrLeadershipLost` if it moved. **IT IS EXACT RATHER THAN ADVISORY BECAUSE WRITERS ALREADY SERIALIZE** — SQLite takes its write lock at `BEGIN IMMEDIATE`, PostgreSQL takes `pg_advisory_xact_lock` in `beginWrite`, and a successor's claim goes through `DB.Tx` and takes the same one — so an epoch that still matches inside our transaction proves no successor committed before us and none can commit before our COMMIT. It sits BEFORE `fn`, or a fenced controller's closure runs, decides, and keeps whatever it built with only the commit refused. **THREE THINGS IT MUST NOT DO, each the could-not-tell/no collapse this file already records elsewhere**: `sql.ErrNoRows` is a refusal rather than permission (this handle claimed, so the row existed); a read ERROR is reported as the storage fault and refuses, because a database error is evidence about leadership in neither direction and answering it with `ErrLeadershipLost` stops a healthy plane while answering it with nil lets a fenced one write; and a handle that never claimed is not asked at all, since `migrate` runs before any claim and `OpenAdmin` deliberately holds none — fencing operator commands would refuse `billet leases release --force` against exactly the live deployment it exists for. **WHAT IT PROVES IS NARROWER THAN "ONLY ONE CONTROLLER EVER WROTE"**, and that is the ordinary fencing-token limit: it cannot stop a predecessor writing BEFORE a successor claims, only guarantee that afterwards it writes nothing more. **REFUSING THE WRITE IS NOT STOPPING THE PROCESS, AND THAT GAP IS THE HALF A REVIEW FOUND.** Every background writer in the control plane is deliberately patient with an error it cannot classify — a heartbeat KEEPS its lease, the reaper logs and retries, a cleanup retry backs off — which is right for a database blip and wrong for this: a replaced controller would go on polling GitHub, holding its message session and running the cleanup loop that calls `Runner.Destroy`, **which never touches the ledger and is therefore fenced by nothing**. So `markFenced` closes `LeadershipLostSignal` at the same instant it sets the flag, `cmd/billet`'s `stopWhenReplaced` selects on it and cancels the plane, and `retryCleanup` refuses outright once fenced so a tick landing inside that window starts nothing. A channel rather than a polled flag, because every path that could do the polling is one the process may sit inside for a whole long poll. **A FENCED CONTROL PLANE THEN ACTS ON NOTHING, WHICH IS DELIBERATELY A HARD KILL** — the listener's teardown asks `state.DB.LeadershipLost` (the flag is set BEFORE the channel closes, so anything woken by the signal reads it correctly) and destroys no compute, closes no message session and hands back no capacity, because each is an authoritative act it no longer has the right to take and the successor performs all three correctly: guests are re-adopted, GitHub expires the abandoned session through the path `openSession` already waits out, and the successor's startup `Reap` reclaims the leases. **AN UNREADABLE CLAIM IS NOT THAT CASE AND DELIBERATELY DOES NOT ABANDON**, which is the reverse of the usual fail-closed reasoning and was argued rather than assumed: what makes abandoning safe is that a successor DEMONSTRABLY EXISTS and owns every obligation being dropped, an unreadable row is no evidence of one, and the destroys skipped are for jobs GitHub has already concluded — so refusing to finish them because a query timed out strands containers for a build that ended. The WRITE is still refused, which is where the could-not-tell has to be answered no. It exits NON-ZERO on purpose, so `Restart=on-failure` either takes the deployment back (right when the successor was itself transient) or meets `ErrControllerHeld` naming the holder — exiting 0 would leave a healed partition with no controller at all. Cost, MEASURED rather than asserted: one single-row read per write transaction, 8.3µs→15.8µs on SQLite and 419µs→585µs on loopback PostgreSQL for an EMPTY transaction, and lost in the run-to-run variance of a real `Reserve`+`Release`. What still has no election behind it is the promotion; that is the election's next phase.
- **AN ELECTION IS A PROCESS THAT WAITS FOR THE CLAIM, AND EVERYTHING AUTHORITATIVE HAPPENS BELOW ONE LINE.** The fence above shipped with no promotion behind it; the primitive was already there, because PostgreSQL releases a session advisory lock when the session ends — so a controller is dead when its SESSION is, decided by the database, and nothing here has a lease, a renewal, a timeout or a failure detector. `server.controllers: active-passive` makes a refused controller WAIT instead of exiting, and `DB.AwaitController` waits out `ErrControllerHeld` and nothing else: a ledger bound to another deployment, a schema this binary cannot read and a database that will not answer resolve by nothing, and retrying them would turn a misconfiguration into a process that sits there reporting itself healthy. It is a config key rather than a flag or a default because the alternatives each delete something — automatic waiting deletes the loud restart-loop diagnostic that today reports two units misconfigured as active, and a `--standby` flag makes the two hosts asymmetric so a unit file names a role its host stops having after the first failover. **A STANDBY IS `runServer` STOPPED AT ONE LINE**, not a second implementation: it opens a handle that cannot write, builds everything that merely validates configuration, installs its signal handler (it may wait for days), and calls `becomeController` — with every authoritative act below that call and a structural test saying so. `alloc.New` stays ABOVE it deliberately, for the opposite reason: it validates config and reaches the ledger for nothing, so a bad tier should stop the process at startup rather than at a failover. `READY=1` is sent BEFORE the wait or systemd kills the standby at `TimeoutStartSec=120` forever, so `notifySystemd` grew a `STATUS=` sibling naming the machine that holds the claim. **THREE THINGS WERE MEASURED RATHER THAN REASONED ABOUT.** The per-transaction schema re-check has to come off BEFORE the promotion migration and not after — while set it refuses the very migration the handle has just earned the right to make, so a standby could not promote onto a ledger no controller had migrated. The latch's unwind had a SURVIVING MUTANT, because the obvious assertion ("a standby whose claim was refused still cannot write") is satisfied by a function that never unwound anything: a claim refused by the EXCLUSION returns before the latch is ever cleared, and the only path that reaches the unwind is one that gets past the exclusion and then fails, which is a ledger bound to another deployment. And splitting the deployment bind from the epoch — an obvious tidy-up — lets a process pointed at another deployment's rows advance the epoch, be refused, and FENCE THE REAL CONTROLLER OUT OF ITS OWN LEDGER on the way past; the incumbent's next write came back "host-b now holds it at epoch 2". **THE CLAIM AUTHORISES THE MIGRATION, NOT THE DIRECTORY FLOCK**: on PostgreSQL a second host takes its own directory's lock happily, so a server about to be refused — and `billet check` run from that host — upgraded the shared schema on the way to finding out. An operator command still migrates an UNHELD ledger and gives the exclusion straight back, because holding it would make every `billet local backup` a window in which no control plane can start.

- **A SHARED IDENTITY IS REPLICATION OVER THE FILE LAYOUT, AND MOVING THE AUTHORITY INTO A STORE IS THE REFUSED ANSWER.** A promoted standby has to present a certificate the fleet already trusts, and `LoadServing` reaches `LoadOrCreateCA`, which CREATES one when the directory is empty — so a host that has never held this deployment's CA mints a RIVAL authority at promotion and drops the entire fleet while looking healthy. The obvious fix is to put the authority in the store and read it from there, and it is wrong for a reason worth keeping: `wirecert`'s safety argument is a state machine over five FILE NAMES (`ca-previous.crt` says a rotation STARTED, `ca-previous.key` says it is COMMITTED, the current pair installs key-then-cert and is read cert-then-key so exactly one tear is possible), and every clause of it rests on cross-key write ordering, per-file durable visibility, `O_EXCL` and a crash-releasing flock. None survives a remote key/value store, so an interface underneath those functions would keep the code and discard every reason it is correct. `internal/wireshare` makes the store a CHANNEL instead: publish what you hold, adopt when you hold NOTHING, and **never write over a local authority** — a host holding a different one is refused naming both fingerprints, because billet cannot tell a host left behind by a rotation from one pointed at the wrong deployment, and `--force` still MOVES the old directory aside rather than deleting a private key. The ordering in `runServer` is the load-bearing part and is asserted structurally: adopt after the claim and BEFORE `serveNodeWire` or the wire mints the rival first, publish AFTER it or a first controller publishes nothing. What it costs is stated rather than implied — two controllers do not converge on their own. The App key follows the same shape one credential over: `github-app create` writes it to disk exactly as it always did and publishes AFTER, because a publication straight from memory has one failure mode with no way back (the App registered, the key gone) and every failure now leaves a file `billet github-app store-key` can publish. `internal/awsjson` was extracted from the codebuild backend to carry all of this — and the extraction's own trap is the one CLAUDE.md already records for `awscreds.IMDS`: codebuild's client KEEPS its five renderings even though the credential moved one level down, because `api` is an UNEXPORTED field and reflect refuses to call methods through one.

- **A WORKFLOW THAT CHANGED ONLY `runs-on` MUST WORK, AND THE ONE PLACE THAT WAS NOT TRUE WAS A CONTAINER-DRIVER BUILDKIT.** Interception remaps the results origin by DNS and hands the node's CA to the runner and its job containers, but a builder made with buildx's `docker-container` driver is a stock `moby/buildkit` image with its own trust store, so a plain `cache-to: type=gha` died with `x509: certificate signed by unknown authority` (measured on the first live conformance run of a consumer repository, which had never passed). Blacksmith sidesteps the same problem by not intercepting BuildKit at all. Billet's answer keeps the acceleration, and it is two facts rather than a certificate: the buildx CLI points BuildKit wherever `ACTIONS_RESULTS_URL` says IN ITS OWN PROCESS, and the runner sets that variable per step from the job message, where GITHUB_ENV loses to it — so the guest image installs a `docker` shim (`internal/guestassets/docker-shim.sh`, at `/usr/local/bin/docker`) that rewrites it for build invocations only and execs the real client, and the plaintext adapter binds the guest's DOCKER GATEWAY rather than loopback, the one address both the guest and every container on its bridge can dial, so no `network=host` is needed. The node mints blob URLs naming a loopback or private address and nothing else. Only build invocations are rewritten because the results origin also carries artifacts and logs, which the adapter deliberately does not serve, and `docker run -e ACTIONS_RESULTS_URL` forwards the client process's value into a container. The shim resolves the real client as the next `docker` on PATH behind itself, with builtins only, and exits 127 rather than exec'ing itself. A build launched from inside a `container:` job uses that container's own client and still needs the explicit `url_v2` form.
- **Never guess a byte size.** Use `config.ByteSize`; a bare int of bytes is how a memory limit ends up 1024x wrong.
- **A node's contribution is DETECTED only for a backend that runs work on that machine.** `ProviderKind.RunsOnHost` is the one reader of that distinction. An `ec2` node is an orchestrator — it calls an API and the compute appears in a region — so `node.max_vcpu`/`node.max_memory` are required rather than defaulted, and the overcommit warning is skipped because there is nothing local to compare against. The ORDER of a tier's `providers:` list is what makes home fill first. Those two numbers are hard RESOURCE budgets, not price budgets: the node registers its ordered shapes, placement charges the first fitting shape rather than the smaller tier request, and every fallback is authorised atomically against the node and deployment ceilings before the request reaches AWS. The allowlist in `RunsOnHost` is deliberately keyed on the host backends, so a second remote backend nobody remembers to add is treated as remote. **A `codebuild` node is the second such orchestrator, and it is what made the allowlist earn its keep**: it declares its purchasable shapes through the SAME ordered mechanism, so `nodeRow.cost` had to stop asking `!= ProviderEC2` and start asking whether the backend runs on the host — a third remote backend charged the smaller TIER request instead of the shape it buys is an overcommit nobody can see. **AND THE MACOS LICENCE CAP IS THE ONE DEFAULT THAT COULD NOT BE REUSED**: `NodePolicy.MacOSLimit()` answers Apple's two-per-host allowance for a host nothing was declared about, which is right for a Mac somebody owns and WRONG for a fleet AWS operates under its own agreement — left alone it caps a five-instance managed macOS fleet at two concurrent builds and blames Apple in the diagnostic. So the DEFAULT is keyed on `RunsOnHost` and the diagnostic names Apple only when it is true; a configured cap still applies, and what changed is what silence means.
- **billet signs its own AWS requests rather than taking the SDK, and that is measured.** A program doing nothing but constructing an EC2 client and calling `RunInstances` once builds to **13.2MB against a whole billet of 21.8MB**, and pulls 15 modules against billet's 4 direct ones — carried by every node in a fleet, including the bare-metal hosts the cloud backend exists to fall back FROM. - **A CA rotation is read WITHOUT a lock, and what makes that safe is the ORDER it publishes in.** `billet ca rotate` mutates the authority in a sequence, and the only reader that can land inside it is a control plane STARTING — `SignNodeCSR` signs with the in-memory `*CA` and reads nothing. Taking `LockAuthority` there was the obvious move and is wrong twice over: it is non-blocking on purpose, so a reader would need a WAITING acquisition, and `billet local backup` holds it across the whole ledger `VACUUM` — a control plane that will not start because a backup is running is worse than the diagnostic being fixed. So the sequence is made one where every instant is a state a reader answers correctly. **`ca-previous.crt` says a rotation was STARTED and `ca-previous.key` says it is COMMITTED**: Rotate writes the certificate then the key, Retire removes the key then the certificate, and a reader takes them in that same order — so a certificate with no key beside it ALWAYS means “not committed”, and both fallbacks go the safe way (an absent previous key means present with the current authority, a present previous certificate means trust one more thing). The current pair is the hard half, because two renames cannot be one operation: reading `ca.crt` BEFORE `ca.key` makes a new certificate proof the new key is already in place, which leaves exactly ONE possible tear — the new key beside the old certificate — and `ca-previous.key`, synced before the first rename, is that certificate's key. `repairPair` resolves it by ASKING whether the key pairs, so the repair cannot fire in any committed state and a genuinely mismatched pair still returns `ca.key is not the key for ca.crt`. Reading the pair the other way round produces the opposite tear, whose missing half has already been renamed away. Two consequences worth keeping: `ca retire` REFUSES while `ca-previous.key` is the only key matching `ca.crt` (a rotation crashed between the renames — removing it turns a recoverable interruption into a control plane that cannot start), and the startup read is ONE call, `wirecert.LoadServing`, because four separate walks of the directory let a `ca retire` land between two of them and produce a server PRESENTING a certificate from the retired authority while trusting only the new one — which starts, looks healthy, and no node can verify. That is the only failure in this area that is not fail-closed, and it is why `ServingCA` and `TrustBundle` are unexported. **The ordering bounds what a reader sees INSIDE one rotation and nothing more**, so `LoadServing` also RE-READS `ca.crt` and starts over if it moved: a whole rotation AND its retirement can pass between two of a reader's own reads, and the result is a control plane serving the authority an operator has just retired — the same not-fail-closed shape one seam over. Two more that a review caught and that read as safe: `ca retire`'s guard must ask **"is the current pair CONCLUSIVELY whole"** rather than "is something missing", because an absent `ca.key` beside a `ca.crt` the previous key matches is a deployment one `cp` from recovery and the first version deleted the key; and **`billet ca issue` must hand out the TRUST BUNDLE, not the authority that signed the leaf** — during an overlap the new authority issues and the old one is presented, so a bundle carrying only the issuer strands the very node an operator is adding, through the one path that is not the wire (the wire's enroll and renew responses always carried it). **Three rounds of narrower rules produced the retire guard's shape and each read as safe**, so the rule is stated positively: retiring assumes the CURRENT pair took over, so there is one way through — ca.crt and ca.key read, parse, match AND name this deployment — and everything else refuses. Asking "is something missing" let an absent `ca.key` through; asking "does ca-previous.key match ca.crt" then let a coherent authority from ANOTHER deployment through, where `parseCA` refuses to start and `parsePair` does not, so the previous pair beside it was the only authority on the host that meant anything. Both were the same mistake — deriving permission from what is broken rather than from what is proved. And **`WriteFileAtomic` REPLACES its destination**, so publishing the previous pair through it gave up the `O_EXCL` that used to refuse a leftover `ca-previous.key`: `Rotate` now checks BOTH previous paths, which is enough only because `LockAuthority` is held across the look and the write — and the two halves get DIFFERENT refusals, because only one of them has a command behind it: `billet ca retire` is gated on the CERTIFICATE and exits 0 saying "no rotation is running" when that is absent, so answering a leftover KEY with "finish it with `billet ca retire`" left an operator holding two commands and no way forward. Billet does not remove that key either — a private key whose certificate is gone is bytes nothing on the host explains — but it does answer the question that decides it, from having READ both files: a leftover byte-identical to `ca.key` is a copy of an authority that is still installed. **And retire only ever removes a previous pair it can PROVE is this deployment's own** — a healthy current pair says the rotation completed and says nothing whatever about what is under the previous names, so `parseCA` is run over those too before a private key is unlinked; the one exception is a previous CERTIFICATE with no key, which is the ordinary crashed-rotation leftover, is public, and is exactly what an operator runs the command for. **A deletion may only be authorised by bytes that were ALL accounted for**: `pem.Decode` returns a remainder and `parsePair` discards it — right for loading, where a bundle may carry several certificates, and wrong for a proof that ends in an unlink, because a second private key appended after a legitimate one parses fine and then goes with the file. A subject match proves the pair is an authority for THIS DEPLOYMENT and not that it is the generation the rotation replaced, so **the new authority records the fingerprint of the one it replaced in its own certificate** — an organizational unit prefixed `billet-replaces:`, because billet has no registered OID arc to hang an extension from and a made-up private OID is somebody else's to allocate. It travels with `ca.crt` through backup and restore for free, which a fifth file would not: the archive's entry set is CLOSED and its schema is compared for equality, so a new file there is a flag day. An authority that claims NOTHING is not refused — that is every deployment that rotated before this shipped, and refusing would leave them mid-rotation with no command that finishes it — so it falls back and the next rotation records one. Two things the review of that found and both are the same shape as the rule they qualify: **`pem.Decode` SKIPS FORWARD to the first BEGIN line**, so the one-block proof in front of the unlink has to check that the block starts where the FILE does, carries no headers and is the expected type — reading only the remainder left two places to hide a second private key; and **`parsePair` never checked that an authority SIGNED ITSELF**, so a certificate anybody assembled around the real public key satisfied every check while carrying whatever claim its author liked. Both now hold, and the second is free: every leaf verification on the wire already depended on it.
- **A deployment is FOUR things, and `billet local backup`/`restore` treat them as one.** The SQLite ledger, the deployment identity, the GitHub App private key and the node-wire authority: a ledger without its identity is a fresh authority that cannot see the compute the old one launched, an identity without the CA cannot issue a node certificate, and a CA without the App key cannot get a token — so a subset is a deployment that starts, looks healthy, and is not, which is why the requirement is worded as a REFUSAL. Nothing is ever overwritten: each piece is absent (installed), byte-identical (already done), or different (**preserved and refused**), with no flag that overrides it, and the App-key install goes through `reserveKeyFile`/`writeKeyAtomically` rather than a second implementation of a publication GitHub cannot repeat. The authority allowlist includes `authority-created` — which lives OUTSIDE the ca directory so its absence is detectable — and `ca-previous.key`, which signs what the control plane PRESENTS until the fleet has renewed; half of either pair refuses the backup. **Backup, `ca rotate` and `ca retire` share `wirecert.LockAuthority`**, because rotate mutates five files in sequence and a reader without it captures a key from one generation beside a certificate from another; the exported entry points take it themselves. `VACUUM INTO` is the ledger mechanism and its constraints are measured — it cannot run in a transaction, is refused on the query-only pool, REFUSES an existing destination (a free no-clobber), creates the file **0644**, and holds the single writer slot while it runs. **Restore's exclusion is three local mechanisms and one thing only a person can assert**: the directory lock (no control plane holds it), the maintenance fence (which reaches a handle an operator command ALREADY has open, since `Tx` and `View` consult it on entry), the writer barrier (a transaction that began before the fence has finished) — and `--old-controller-fenced`, because none of the three reaches another machine and two controllers on one identity, CA and App credential diverge from the moment both are up. It takes `LockAuthority` too, since it writes the files a rotation mutates. **The plan is RE-DERIVED inside that exclusion and only that one is acted on**: the planner is lock-free by design and its output is printed for a person to read, so acting on it meant deleting a ledger because it was empty when somebody looked. Authority planning walks the ALLOWLIST rather than the archive, or a `ca-previous.crt` the target has and the archive lacks is never looked at and the next start reads it as an active rotation. Publication goes file-by-file INTO the directory rather than renaming one into place, or the restorer would hold the OLD `billet.lock` inode while a server locks the new one. A failed restore leaves the ledger **fenced** with its journal, so nothing can start on a half-restored deployment; re-running resumes and `--abandon` removes only what that run created and can still prove it wrote. The presence of `billet.db` cannot be the refusal — a preflight `billet check` creates one — so what proves a directory committed is the identity and the marker, and what proves the ledger replaceable is that every table is empty. **A RESTORE RUNS AS ROOT AND HANDS BACK WHAT IT WROTE**, which nothing did until the restore was REHEARSED on a real packaged host: the command has no choice about being root, because the App key lands in root-owned `/etc/billet`, and `StateDirectory=` repairs recursively only when the TOP directory's owner is wrong — which after a restore it is not. `billet local up` was the documented next step and repaired `preflightState`, the five files `billet check` creates, and no part of the authority; so a deployment restored perfectly and the control plane could not open one file of it. `lifeops.RepairPaths` takes its set from the PLAN just executed rather than from a list beside the repair, and the three additions no action publishes are the `ca` DIRECTORY — a root-owned 0700 one cannot be TRAVERSED, so the authority under it is unreachable however its files are owned — and the two lock files the command created by taking them. Failing to repair is reported and still exits 0, because the restore is complete by then and the next thing an operator reaches for after "the restore failed" is `--abandon`, which deletes what that run installed. **The rehearsal is the evidence and the unit test is the reading**: `internal/e2e`'s `TestARestoredDeploymentServesTheFleetThatTrustedTheOldOne` proves a restored control plane SERVES the fleet that trusted the old one and never leaves the process, while `make restore-rehearsal` drives the real `.deb`, the real service account and the real commands — and only the second could see any of this.
- **`billet local recover` PUTS A DEPLOYMENT BACK OVER ITSELF, and three of its steps were found by RUNNING it.** Restore refuses a commissioned deployment because its ledger is a live capacity record; this is the operation for the case that leaves out, and the design argued it must be separate rather than a flag on restore. It refuses unless the archive is the host's OWN deployment — the identity on disk against the manifest, the same check restore makes — so it can never relabel one; it SEALS and waits on `alloc.Quiescence`, because a seal stops admission and says nothing about what is already running; and it refuses while anything is outstanding unless `--accept-failing-jobs`, which names every job by tier, node, phase and run id. **The intent guard has to sit ABOVE `planLedger`'s absent-ledger branch**, or a recover against an uncommissioned host plans as an ordinary install — caught only because SEALING creates a ledger, so the executor's re-plan refused what the printed plan had allowed. **The deployment must be sealed AGAIN after the ledger is replaced**: the first seal lived IN the ledger that was just replaced, and the archive's admission row is whatever it was when the backup was taken — open — so without this a recovered control plane takes new work immediately while its nodes hold compute it has never heard of. **And an abandon must put the SUPERSEDED ledger back**, or it removes the ledger the run installed and leaves the operator's own under a name nothing looks at, in a directory whose fence is about to come down. The superseded name comes from the ARCHIVE rather than the clock, so a resumed run recomputes it and recognises the rename it already did rather than moving a second ledger aside — and it carries the manifest DIGEST as well as the timestamp, because RFC 3339 seconds collide for two backups taken back to back and the no-clobber write then refuses the second one's upload. **An adversarial review then found five more, all the same shape: a guarantee true on either side of a gap and not inside it.** THE FENCE MUST OUTLIVE THE PUBLICATION — clearing it and then sealing leaves an interval where a control plane can start on the archive's open ledger, so `Execute` leaves a recovery fenced (`Result.Unfinished`), the command seals through `state.OpenMaintenance` (the one typed fence crossing; `OpenAdmin` honours the fence, and the lock `OpenMaintenance` takes is one `Execute` has released), and `deployarchive.Finish` lifts it — a failed seal now leaves the directory fenced, which is the safe direction. THE SIDECARS MOVE BEFORE THE LEDGER, because a supersede that moved `billet.db` first and crashed left the re-plan reading an ordinary INSTALL and putting the archive's database beside a `-wal` from a different one, which SQLite replays. AN ABANDON MOVES THE SET AS ONE THING, or the superseded `-wal` lands beside a ledger it correctly KEPT. AND A RESUME MUST NOT RE-QUIESCE, because quiescing opens through `OpenAdmin` and the first attempt's own fence refuses it. **A second review round found four more, and every one of them was a state between two steps.** THE JOURNAL RECORDS HOW FAR THE RUN GOT, because a recovery that published and then failed to seal or to lift its fence had NO WAY FORWARD: the re-run plans afresh, the restored ledger is no longer the archive's (sealing wrote to it), so it decides on a SECOND supersede and finds the first one's destination occupied — refused, correctly, by the rule that a superseded ledger is never written over. `phasePublished` is what lets the retry skip publication and finish; `phaseFinished` is written BEFORE the fence comes down, so the journal outlives it by one step and a crash on either side leaves something the next run recognises — and an `--abandon` refuses a `finished` journal outright, because undoing a complete, sealed recovery removes the restored credentials and puts back the ledger the operator deliberately replaced. `Finish` PROVES THE SEAL rather than documenting it: it is an exported entry point that lifts the fence, and the fence is the only thing standing between the archive's open admission row and a control plane, so it opens through `OpenMaintenance` and refuses anything but an operator seal — the two tests named for that invariant were, until this, demonstrations that it did not hold. AN ABANDON RECONCILES THE WHOLE LEDGER SET rather than reading the superseded ledger as a marker: the sidecars move FIRST, so a crash between a `-wal` and the ledger leaves the operator's `billet.db` where it was and its write-ahead log under the superseded name — and “nothing was superseded” then reopens that database without a log holding committed transactions. There are exactly two states it may act on (the supersede completed, or it stopped before the ledger moved), every destination is checked before anything moves, and a directory sync sits between the sidecars and the ledger because nothing orders two renames. AND A `--from-backup` RETRY MUST NOT BE REFUSED BY THE COPY ITS OWN FIRST ATTEMPT KEPT — the fetched archive is kept deliberately and the destination is named after it, so the second run compares the bucket's manifest with the one on disk and reuses a proven-identical directory; anything else still gets the ordinary refusal, and a directory carrying this manifest over an archive that does not verify is named, because `Fetch` writes no-clobber and cannot repair it. **A third round then found that two of those fixes had the same defect as what they replaced, and it is worth stating as the rule: an operation that decides not to act must not return the answer that means "this directory is ready to start".** `putSupersededBack` answered nil for every state it could not resolve, and `abandonLocked` reads that as done — so it removed the journal and lifted the fence over a directory with NO `billet.db` in it, which a control plane then repopulates with a fresh, empty ledger. Every unresolvable state is now an error that leaves the fence and the journal standing, and a `ReplaceLedger` abandon additionally REFUSES if it ends with no ledger at all, because that is what lifting the fence actually promises. **The put-back moves the ledger FIRST, which is the opposite of `supersedeLedger`, and both orders are chosen by what a RESUMED run looks at**: going forward the ledger's presence at the SOURCE is what makes a re-plan return to `supersedeLedger`, and coming back its presence at the CANONICAL name is what says the set is home. Sidecars-first left a canonical `-wal` beside a superseded LEDGER — which the foreign-log guard reads as unexplainable, so the retry refused. The order is not observable from any end state (each order handles the partial states it produces), so what pins it is `Result.Restored`. **`Finish` asks everything under ONE acquisition of the directory lock**, through `state.PeekAdmission` — a reader that takes no lock, does not migrate and does not consult the fence, which exists because `OpenAdmin` honours the fence this is about to lift and `OpenMaintenance` crosses it but takes the lock the caller already holds. Reaching for `OpenMaintenance` BEFORE the lock was the first shape and it migrated a ledger before anything had established the operation was even this caller's, and left a window between the answer and the lock. It also now refuses a journal whose phase is still `publishing`: the seal says nothing about whether the files landed. **A journal is validated against a CLOSED schema and a CLOSED phase set before any of it is read**, or a downgrade acts on a newer binary's record — the phase decides whether a recovery skips sealing, quiescence and publication altogether, and `InProgress` did not consult `journalSchema` at all. And the final unlink's directory sync is deliberately not a failure: the fence is already durably down, so both outcomes are safe, and reporting it sent an operator to re-run a command that would then plan a second supersede against an occupied destination. **A fourth round found that the forward order was INTENDED rather than durable**, which is the same distinction one layer down: `supersedeLedger` moved the sidecars before the ledger and synced once at the end, so a power loss could persist the LEDGER's rename and lose the `-wal`'s — leaving no ledger at the source, a stale log at the canonical name, and a re-plan that reads the directory as an ordinary INSTALL and puts the archive's database on top of it. The sync now sits between the sidecars and the ledger, and `planLedger` REFUSES an absent ledger whose sidecars are still there, because that state is reachable from any build that got the ordering wrong and billet cannot tell whose log it is. Two smaller ones from the same round: `requireSealed` compares the MODE rather than asking `Admission.Sealed()`, which answers true for a row billet could not read — the ledger's CHECK constraint makes that unreachable today and the comment says so, because the two are not the same question and only the constraint separates them; and the reuse branch's `chmod` goes through an `O_NOFOLLOW` descriptor, since the checks and the change were addressing a pathname rather than one object and this command runs as root. What is left open deliberately is `os.Rename` REPLACING a destination that appears after the check: the LEDGER's cannot appear (`openDir` consults the fence before `sql.Open` creates one, and the opener that crosses a fence takes the lock the caller holds), and a sidecar that does is a derived file from a reader predating the fence — so the no-replace syscall pair is documented where the fix would go rather than written. **A fifth round found the postcondition was still a proxy, three depths in**: "something is at billet.db", then "a regular file is", are both satisfied by an empty file somebody drops in while the directory is fenced — after which the next control plane initialises it as a fresh capacity record, past the command whose job was putting the real one back. `supersedeLedger` now records the ledger's DIGEST before it moves anything and the abandon compares what it left against that; an empty recorded digest means nothing was superseded, which is its own real state. The lesson is the one the `ca retire` guard took three rounds to learn, in a second place: derive permission from what is PROVED, never from what is merely present. Two more from that round: `strayLedgerSidecars` folded every `Lstat` error into "absent", which is the could-not-tell/no collapse ending in a database installed beside a log billet failed to look at; and the torn-state remedy named `--abandon` unconditionally, which does nothing without a journal. **And a sixth round found the same proxy ONE FILE OVER**: proving `billet.db` is the right one proves nothing about the LEDGER, because SQLite replays a `-wal` it finds beside a database — so a log substituted under the superseded name travels back alongside a correct ledger and is replayed into it. The journal records the digest of the WHOLE SET, and the abandon accounts for it in BOTH directions: a canonical file whose digest differs is refused, and so is one that is present with nothing recorded about it, because "my record says nothing about this" is not permission. The journal is **schema 2** as a result, carrying those digests and the operation's INTENT — a schema-1 journal has neither, so accepting one silently would leave the deployment-losing path open in the file that authorises it, and pre-1.0 may break an on-disk format as long as the refusal says what to do. The intent is recorded rather than inferred from the fence, which `Finish` takes down one step before removing the journal, and it is what lets a diagnostic name the `--abandon` that will actually undo something instead of the one that clears a fence and returns. **A seventh round found the identity of those files was the path's SPELLING**, so a recovery started against `/srv/billet` and abandoned through a symlink to it recorded and looked up different keys, reported the ledger it had just put back as one that never came home, and left the deployment fenced for a person — a refusal of correct state, which is the failure that gets a check deleted. The key is the BASE NAME, which is unambiguous within one state directory and is all it has to be. Two more from the same round: the proof now runs BEFORE the rename rather than after it, because an empty record beside a superseded file is not "nothing was superseded" but billet being unable to say what that file is — checking afterwards leaves the window where it is already beside the ledger; and `Abandon` compares the journal's INTENT with its own, since `understood` proves a journal names AN operation and not that it names THIS one, and `Intent.String()` aliased every invalid value to `restore`. **An eighth round found a REFUSAL that deadlocked both commands**, which is the same shape as everything above wearing the opposite face: `abandonLocked` raised the CALLER's fence and only then read the journal, so a restore's abandon meeting a recovery's journal left a `billet local restore` fence over it — permanently, because a fence raised over a published journal is deliberately not cleared on a refusal — and `billet local recover --abandon` then could not fence the directory at all. Two commands, neither able to proceed, produced by the check whose job is sending an operator to the right one. Ownership is now established BEFORE any fence is written, which needs nothing the fence provides: the journal is a plain file and the call holds the directory and authority locks. The round also took the journal to **schema 3**, because round 7 changed what the digest keys MEAN under a number that was already in use — a format whose meaning changes silently is worse than one that changes number, since every reader believes it understands the file — and made `Intent` validated at every exported mutation, since a `Plan` anybody can construct could publish a journal recording an operation billet does not have. **One race is bounded rather than closed and the bound is the safe direction**: the fence stops transactions and the writer barrier proves none is mid-write, but neither reaches a connection that was already open and then CLOSES — SQLite checkpoints the WAL into the database on the last close, rewriting the file whose digest was just recorded. Nothing in userspace holds that off (the lock an admin handle skips is the one that would), so the abandon REFUSES a ledger it cannot vouch for and names the checkpoint in the message, rather than opening a deployment over the wrong one.
- **AN ARCHIVE ON THE DISK IT PROTECTS IS NOT A BACKUP, and billet owns BOTH ENDS of one narrow S3 hop rather than either.** The directory stays the contract — the manifest's digests exist so anyone's tooling can carry it, and omitting `backup:` is a supported answer — but with `backup.s3` set, a backup uploads what it just wrote and `--from-backup` restores straight from it. THE FETCH IS WHY BOTH ENDS: on the day this is used the machine is new and holds the binary alone, so upload-only means installing another tool mid-outage; and an `s3://` URL could not have replaced the config anyway, because it carries no region and SigV4 signs one into every request. **There is NO DELETE anywhere on the path** — not in `internal/archivestore`, not in the IAM `internal/awspolicy` generates — so the credential on the one host that also holds the App key and the node-wire CA cannot destroy the copies that exist to survive losing that host; retention is the bucket's, and its lifecycle rule expires NONCURRENT versions only, because expiring current objects removes backups on a timer. Every write is no-clobber (`If-None-Match: *`), **the manifest is published LAST** so an interrupted upload is not something a listing will offer as a backup, the local archive is written and verified FIRST so a failed upload never leaves an operator with neither, and credentials are env-or-IMDSv2 only. `billet check` reports the newest archive's age, because an unwatched backup is no more a backup than an untested one. Two things the Terraform side got wrong first and are worth not repeating: `Inputs.Build` emitted the runtime statements unconditionally, so a controller that launches nothing came out holding `ec2:RunInstances` (hence `NoCompute`); and the module hand-wrote the grant in HCL, which is the second source of truth `internal/tfpolicy`'s drift test exists to prevent — it reads the generator's committed rendering, exactly as `fleet-ec2` does.
- **The Linux arm64 half is measured too, and the published base image cannot do it.** A real workflow ran in a native arm64 Ubuntu 24.04 guest on the Mac: a service container initialised and reached, and `docker build` producing an image that asserts `aarch64` — Docker Engine 29.7.2, `linux/arm64`, 4 vCPU, 7913MB. Both are things a macOS guest CANNOT do (no nested virtualization, no container runtime), which is why the Linux tier exists rather than being a nicety. **`ghcr.io/cirruslabs/ubuntu` is not the image for it**: measured, it carries neither the Actions runner nor Docker, so it cannot run a job at all — `ubuntu-runner-arm64` is the one with both, at 11.3GB compressed against a 40GB virtual disk. A macOS Xcode image is 81GB in the same store, so a host that runs both tiers needs room for both AND for tart's own reclamation to leave them alone.
- **One process writes the launch verdict, and billet DERIVES the rest.** What billet may say about a failed launch comes from a CLOSED vocabulary its own launcher wrote into a status file in the guest — never the guest's stdout or stderr, because the registration travels on that delivery's stdin and a guest whose shell is `cat >&2` reflects a live credential into a node log, while a job dispatched the moment the runner registers is running WHILE the liveness proof is still sampling and can choose those bytes too. Every record carries the VM name, because a guest's home comes from a cloned image and a stale record would otherwise abandon a launch that was fine. The launcher records `launching` before its identity check and `started` before its pid; **billet reads the status and the pid in ONE query and derives the verdict**: `launching` without a pid is conclusive, because that marker precedes the identity check by a long way, while `started` without one is TRANSIENT the first time — the two files are written in the opposite order to the one they are read in — and conclusive only if a second observation still finds no pid, rather than having the delivery's handshake correct the file — that made two writers of one file and an unavoidable interleaving where the correction lands on a verdict that had just become true, and checking again before writing only moves the race one instruction. Two shell details cost a debugging round each: a trailing `[ -s pid ] && printf pid` makes the whole query exit non-zero when there is no pid, which reads as "could not ask" and silently disabled the conclusive `command-missing` exit; and `command-missing` must survive whatever else is written, because retrying a tier command the guest does not have burns the node's single command slot for the full ten-minute timeout on every job.
- **A cancelled command is not a returned one, and every timeout in this package was advisory until that was measured.** `exec.CommandContext` kills the process it started and then `Wait` blocks until the output pipes close — which anything that process spawned holds open. A `tart list` whose child slept for sixty seconds took all sixty despite a 300ms deadline, so a bound on the node's single command slot was decorative. `cmd.WaitDelay` is what makes it real.
- **`tart stop` REQUESTS a stop; it does not complete one.** Reading the state once immediately afterwards catches a VM mid-transition and reports it as still running, which fails the teardown and makes the caller retry something that was about to succeed. Destroy polls until the state settles, bounded by `stopWindow`. What it ACCEPTS is unchanged and must stay so: only a `tart list` row that says stopped, never an omitted row. That poll widened the gap between deciding whose VM it is and acting on it, so the ownership MARKER is re-read immediately before the delete. An `os.SameFile` against the directory billet started with stood beside it and was removed: **inode reuse defeats it** — CI demonstrated the case on Linux, where removing a directory and recreating it under the same name reuses the inode, so `os.SameFile` answered "the same file" about a directory that had been replaced, and the test for it could not pass on the platform CI runs. A check that cannot be tested and that an ordinary property of the filesystem defeats is worse than its absence, because it reads as proof. **A residual race is left open deliberately and is documented where the fix would go**: `tart delete` resolves a NAME, so a VM appearing under it in the microseconds after the check is what would be destroyed. Renaming the VM aside and deleting the new name closes that, was written, and was REVERTED — a quarantine name is a durable state that `List`, the cross-check, the next `Launch` and a resuming `Destroy` must all reason about, and getting any of them wrong frees a running guest's capacity or deletes somebody else's VM. One review round of that mechanism produced three defects of exactly that shape. **That race is now closed by a lock over the STORE rather than by a cleverer sequence of CLI calls**: `$TART_HOME/.billet/store.lock`, flocked by every billet process around a mutation of a LEASE NAME — the `rename` that publishes one and the `delete` that removes one, and deliberately NOT the clone that creates a `.staging` name or the deletes that clear one, because a staging name carries a lease id no other billet generates and `checkSpec` reserves the suffix so nothing can be launched under it (writing the rule as "every name mutation" was false, and it put cleanup behind a lock it did not need, where losing the lock leaks a multi-gigabyte clone nothing reclaims) — so the ownership re-read and the delete are one act, and the only operation that could put a different VM under that name takes the same lock. Keyed on the STORE and not on a deployment, because two deployments on one Mac share the store and serializing anything needs both of them in one collision domain; a FRESH DESCRIPTOR PER ACQUISITION, because a second flock on the SAME fd SUCCEEDS (measured) and a cached one would make every acquisition after the first a silent no-op while two goroutines each believed they held it. It WAITS on contention where `state.LockDeployment` refuses, and for the opposite reason: there a second holder means a second control plane, here it means somebody is midway through a rename. Three properties of tart were measured before putting a file in its directory: a dot-directory at the top of TART_HOME is invisible to `tart create`/`list`/`get`, `tart prune` targets only `caches` or `vms` (its own `--entries` vocabulary, so ordinary traffic cannot unlink the path out from under a holder — the failure that ruled out a cache directory for the deployment lock), and `tart rename` already refuses an occupied target, so the guard under the lock is the better DIAGNOSIS rather than the only refusal. What stays open is a process that does not take the lock — an operator running `tart delete` by hand — and nothing billet owns can change that, because tart has no lock and billet does not own the store.
- **A restart re-adopts the guest, a TERM drains, and both are measured against a real job rather than reasoned about.** SIGKILL a tart node mid-job and the guest keeps running: the next node reports `found=1 adopted=1`, holds the capacity, leaves the runner alone, and the job finishes green on the SAME VM name. SIGTERM is a different thing entirely and the distinction is easy to test wrong — it is a DRAIN (`not taking new work, waiting for the compute already running here grace=6h`), so the node OUTLIVES the job, destroys the VM itself and leaves nothing to adopt. A restart test that sends TERM therefore proves the drain path while looking like it proved adoption; the crash path needs a kill that cannot clean up.
- **Untrusted work runs only under `node.tart.untrusted_isolation`, and billet owns the guest's resolver because billet is what broke it.** The setting's ABSENCE is the refusal — the same rule as `node.firecracker.untrusted_bridge`, since a tart VM isolates the KERNEL and not the network, and tart's default NAT reaches the host and lets a guest ARP-spoof the bridge. `softnet` is the one mechanism billet drives; **`Accepts` and the flag builder are one function on purpose**, because written as two, a mechanism added to the config and not to the launch path is admitted and then booted on the DEFAULT network — untrusted work on the trusted bridge, reported as isolated. Softnet blocks the private address space, which includes the vmnet gateway the guest's DHCP resolver points at: measured, egress and TCP/443 keep working while name resolution dies, so nothing looks wrong and every job fails to clone. billet therefore configures a public resolver in the guest before delivering the registration (before, because the registration is single-use and a runner that cannot resolve has already spent it) and **proves resolution rather than assuming the mechanism applied** — three spellings exist (systemd-resolved, plain resolv.conf, macOS `networksetup`, since on macOS resolv.conf is generated by configd and read by nothing), all best-effort, and the verification is what turns a silently-stopped mechanism into a launch error. Both guest kinds are measured in `realguest_test.go`. **AND THE SETTING IS NOT FREE TO NAME SPECULATIVELY, WHICH IS WHERE IT DIVERGES FROM THE BRIDGE IT OTHERWISE MIRRORS.** `billet init --provider firecracker` always writes `untrusted_bridge`, with a comment saying nothing attaches to it yet, because an unused bridge costs nothing — but `checkTartHost` is FATAL when the isolation is named and softnet carries no setuid-root grant, since a node that OFFERS to confine a fork's job on a host that cannot confine it is worse than one that refuses. So `billet init --provider tart` writes `untrusted_isolation` ONLY for a generation whose tiers are untrusted, and the trusted form explains in a comment how to add it; writing it unconditionally would fail `billet check` on a host that has done nothing wrong, over a mechanism nothing in the file uses. **AND IT IS REFUSED ANYWHERE BUT APPLE SILICON** — a NOTE would be the firecracker branch's answer, and the difference is that firecracker HAS a cross-machine path (`--emit ansible`, which the Linux-only role reads) while there is none to a Mac, so what a note would leave behind is a file wrong in three ways at once: the ceiling measured here, the node name from this hostname, and the paths from this platform. Two other things a tart generation cannot guess: **the node NAME**, because a macOS tier must pin the host Apple counts its two-guest limit against and a stock Mac's hostname (`Junior's MacBook Pro.local`) is not a legal node name — sanitising one into existence would name a host the operator never chose and would meet again the first time `billet ca issue` disagreed, so it is refused by flag; and the **catalogue shape**, because an unset `max_concurrent` on a macOS tier inherits the HOST's limit, so TWO generated macOS tiers sum to 4 against a limit of 2 and `validateMacOSHostLimits` refuses the file — one tier at the host's own limit is what the licence actually is. `config.MinMacOSGuestMemory` is the third measured constant of this family, beside `DefaultMacOSVMLimit`: below 4GiB Virtualization.framework answers `LessThanMinimalResourcesError` and there is no smaller guest to fall back to, and `provider.Spec` carries no guest OS so config validation is the ONLY layer that can hold that rule.
- **Nothing the guest wrote is ever quoted into a billet error, and the argument for doing it anyway was wrong twice.** A launch failure destroys the VM immediately, so an error that merely NAMES `$HOME/billet-runner.log` points at a file on a machine that no longer exists — but quoting that log's HEAD is not the fix, and shipping it was a defect a review caught. The reasoning was that a runner which never survived startup cannot have run a job yet: GitHub can dispatch the moment the runner registers, which is while `proveRunning` is still taking its second sample, and the log is a PATHNAME in a filesystem the guest controls, so a job can unlink it, leave a symlink to anything readable, and choose the bytes billet prints into the node's log. Bounding the read bounds the volume, not the sensitivity. What billet quotes is a token from a CLOSED SET that billet's own launcher wrote before exec (`command-missing`, `started`), validated against that set — so a guest that overwrites the file can at most make billet print one of billet's own sentences. `command-missing` is also treated as conclusive by the delivery loop, because retrying a command the guest does not have burns the node's single command slot for the full ten-minute timeout on every job.
- **The guest agent DOES kill its exec session's process group, and escaping it is a race the first fix lost.** Measured on a real `ghcr.io/cirruslabs/ubuntu` guest, not reasoned about: `nohup` — bare or in a subshell — a double fork, and `systemd-run --user` (there is no user bus under the agent) all leave the runner dead three seconds later, while `tart exec` exits 0 and `tart list` still reports the VM running. Only a genuine **`setsid`** survives, and macOS guests have no `setsid` binary, so the fallback is perl's `POSIX::setsid` (measured working on macOS 26; `getsid` is not exported, `setsid`'s return is the answer). Even setsid fails if the delivering shell returns immediately — the child is killed in the window BEFORE it calls `setsid()` — so the script **waits for the launcher to announce its pid** before writing the sentinel and exiting; one 0.1s tick was enough, and removing that wait makes `realguest_test.go` fail. Because every one of those failures reported SUCCESS, the durable half is that billet does not believe the delivery's exit code at all: `proveRunning` asks the guest whether the recorded pid is alive and turns a silently-queued job into a launch error — which also catches a tier command that exits immediately, the docker default-command bug one backend over. **Both halves are now measured in a real guest of each kind**: Linux (`setsid`) and macOS (perl fallback), and the macOS run found the bug in the TEST rather than the code — `pgrep -fc` is a Linux spelling, macOS pgrep has no `-c`, so the count came back empty and "no runner survived" was a detector that could not see. Guest assertions ask through billet's own `billet_birth` instead. **Two host limits were measured and are encoded rather than assumed**: Virtualization.framework refuses a macOS VM under **4GiB** (`LessThanMinimalResourcesError`), and a **third** concurrent macOS guest is refused with "The number of VMs exceeds the system limit (other running VMs: …)" — which is where `config.DefaultMacOSVMLimit = 2` actually lands, so the constant is pinned to behaviour and not to a licence reading. Because `tart run` is detached and its exit status is never believed, a VM that refuses to start used to surface as a delivery timeout against a guest agent that never existed; `Launch` now waits for the VM to be running and quotes the host's own reason out of the run log. **When measuring any of this, `pgrep -f <marker>` matches its own invoking shell** (whose command line contains the marker); split the literal (`billet-surv[i]vor-marker`) or every mechanism reports one survivor and the probe proves nothing.
- **Storage is a property of the SITE, not of the compute backend.** `node.ceph` is a sibling of `node.firecracker` rather than a field inside it, because two hosts in one place map the same pools — that sharing is the entire reason Ceph replaced ZFS. It is required for `provider: firecracker` and REFUSED for every other backend: a container has nowhere to attach a block device and an ec2 node's compute runs in a region that cannot reach the cluster, so a storage block on either is a deployment that believes it has a cache and does not. `node.ceph.user` defaults to `billet` and `admin` is refused, which matters more than it looks — `admin` is what the `rbd` command picks for itself when nothing names an identity, and an admin key can delete a pool. billet shells out to `rbd` rather than linking librados, because the Go binding is cgo and would end the single static binary. **Every rule about a Ceph name is pinned to what running rbd does, and the first version of them was not** — a pool beginning with `-` is refused because billet builds POSITIONAL `pool/image` specs and `rbd info -weirdpool/x` answers `unrecognised option`, NOT because of `-p`, which consumes whatever token follows it; the identity rules written from the same false premise were removed, keeping only the `client.` prefix, which measurably authenticates as `client.client.billet`. Ceph is far more permissive than it looks — it creates pools named `a/b`, `a@b` and `a b` — so "is this legal" is never the question; "does billet address it correctly" is.
- **A cache writer lease is not a capacity lease.** The former lasts only across quiesce, filesystem verification and fenced pointer CAS; the latter stays charged until compute is proved gone. Reusing one lifetime for the other either strands machine capacity behind a cache commit or lets an expired compute holder publish. The Ceph cache index issues monotonically newer fences, records active-clone leases before releasing its lock, and writes a generation record before it writes the current pointer. That ordering is the crash guarantee: an interrupted commit leaves the prior pointer or a complete new one, never a pointer to unfinished bookkeeping. A writer lease whose publication will not happen is RELEASED rather than left to expire (`Store.ReleaseWriter`), and a release is the one operation that touches the writer record without touching the fence.
- **The node wire is a RANGE, and the bridge runs one way because of how each side decodes.** `internal/nodeapi` declares `MinVersion` (12) and `Version` (13); registration picks the highest both builds speak and records it on the node's ledger row, which is what `billet status` reads under `protocol`. What makes the direction a fact rather than a policy: the control plane decodes request bodies with `DisallowUnknownFields` (`nodeplane/http.go`) while a node decodes responses with a plain decoder (`nodeclient/client.go`). So an old node's registration is a SUBSET of a new server's struct and decodes cleanly, and a new server's response decodes on an old node — but a new node's body hits an old server's strict decoder and is rejected before any version check can run. Hence: upgrade the server first, roll nodes at leisure, and a node-first attempt is REFUSED rather than made to work. The node adds its own range to every registration failure unconditionally, because otherwise an operator meets `json: unknown field "min_version"` with nothing saying which half to touch. `MinVersion` is a promise about SEMANTICS, not about whether fields parse — 11 and below decide a pooled runner's trust from the assignment that caused it to launch, which GitHub may reassign — so lowering the floor to make an old fleet connect is offering to be wrong. A declaration has THREE answers, not two — absent, valid, and CONTRADICTORY — and collapsing the third into the first is what the first version did: an absent `min_version` means the peer speaks EXACTLY the one version it named, but a peer declaring a minimum of 14 and a newest of 12 was normalised to "speaks exactly 12" and served a version it had just said it does not implement. Both a zero floor and an impossible one are refused before any of registration's side effects run. And an absent `release` is REPORTED, not refused — it decides nothing about capacity, fencing, identity, custody or destruction, so taking a working host out of the fleet over a diagnostic field costs more than the field is worth; `VersionNodeRelease` is what lets the report tell an old build with none to give from a current one that owes it. The release is the one FREE-FORM string a node puts in an operator's report, and a node is authenticated without being trusted to behave, so it is reduced to a version token on ingest — stored verbatim it is a newline away from forging a whole row of `billet status`, in the output an operator reads to decide whether a protocol is safe to retire. `billet status` also never claims an age it cannot know: a row this binary did not write and a row written by a NEWER binary are each their own state, and both block retirement without being called old.
- **A DRAIN IS TWO BARRIERS, AND THE SECOND ONE ASKS THE MACHINES — THE ORDER OF ONE WRITE IS WHAT MAKES ITS ANSWER MEAN ANYTHING.** `alloc.Quiescence` answers from the ledger and states its own limit: it cannot see compute whose lease has already gone. A listener that loses a running lease keeps an in-memory obligation to destroy what it launched, and a launch whose lease was reclaimed can create compute it then fails to destroy — neither is in the ledger, neither survives a restart of the process holding it, and once `billet local down` STOPPED SERVICES on that barrier the central safety claim of the command rested on a check blind to the class. Both leave an instance carrying the name billet gave it, so the host's own `provider.List` still has it, which is why an inventory query is the instrument and the ledger can never be. **What was rejected first is worth knowing, because both attempts read as safe.** Nodes already report provider-truth inventory on every sweep (the sweep's inventory is durable and epoch-fenced), so the obvious move is to stamp it and consult it while sealed — and that is wrong twice over: SEALING PREVENTS NEW LEDGER COMMITMENTS, NOT THE EXECUTION OF ONES THAT EXIST (an `Assigned` job must still launch, `reconcilePool` runs while quiesced, a launch may already be queued), and the stamp would describe RECEIPT time rather than snapshot time — the node lists its provider and THEN posts, so a snapshot taken before a fence arrives after it. A timestamp cannot repair an ordering the protocol never established. The second rejected shape was "a later launch INVALIDATES the acknowledgement", which races the response it is invalidating: nonce N is queued, a launch clears N, and the node then writes N back as valid while that launch is still behind it. **So the fence is a monotonic per-node `dispatch_generation`, advanced durably BEFORE a launch enters that host's queue and under the SAME hold of `Plane.mu`** — outside that hold a launch can advance it, let a barrier read the new value and queue itself ahead, then append behind it. A crash between the bump and the enqueue over-invalidates, which is the safe direction; a failed bump fails the LAUNCH, because dispatching unfenced is what lets a stale answer be believed. The acknowledgement is then accepted only while epoch AND generation are unchanged, so a later launch makes the write match nothing rather than needing to undo anything. **`computeAbsenceGrace` is deliberately the same five minutes as `strayGrace` and `quarantineGrace`, and takes none of custody's shortcuts**: what is stored is a CONTINUOUS run — an error, a non-empty list or a moved fence deletes it — and the host-backend fast path is refused here because custody grants a prompt absence only to a CAUSALLY OBSERVED entry, which a barrier by definition has none of. **A REGISTRATION DISCARDS THE HOST'S STORED RUN BEFORE THE REQUEST IS EVEN JUDGED**, through `Plane.ArrivingForRegistration` — which BOTH paths call, because `handler.register` assembles the sequence itself rather than going through `Plane.Register`, and one version of this fix went on the path every real node does NOT take. It runs before `checkRegistration` — and on the real wire before the BODY IS DECODED and before the certificate is AUTHORIZED, on its own common name — because a PERMANENTLY refused registration is still an authenticated host reporting live compute and the node does not retry, so a proof left standing there stays standing; `decode` is strict, so an unknown field from a node rolled ahead of the control plane is refused before any semantic check, and `authenticated` checks REVOCATION, which is an operator taking a machine's credentials back and says nothing about whether it is still running compute — hence `certificateName`, which reads the verified chain without that check. A loopback wire has no certificate, so there NOTHING can name the host and every run goes, at the very TOP rather than after the body is read — which closes the method check, the strict decoder and maxBody in one placement, since each refuses before a body exists and "could not tell who arrived" must not read as "nothing changed". Both forms answer 503 when they FAIL, because `decode` writes its own 400 first and an invalidation attempted after it could only be logged while the node reads that 400 as permanent and stops retrying. The route is deliberately NOT method-qualified either, since `POST /v1/register` lets ServeMux answer 405 before the handler runs and a certificate holder that reached the path has arrived whatever verb it used. And `InvalidateBarrierRun` READS BEFORE IT WRITES, which is not tuning: running ahead of the revocation check means a credential an operator took back could otherwise reserve SQLite's single writer on every request and starve every scheduling decision — rolling a control plane past an old node's protocol range is exactly that shape. It is deliberately not subject to "a refusal changes nothing", which governs the IN-MEMORY inventory: that returns only from a successful registration, while a barrier run returns from the loop asking again — `beginRegistration` already clears the in-memory inventory for the same reason, and the ledger's epoch does not move until `RegisterNode` lands, so in between a completed run reads as current to the SEPARATE PROCESS running the drain, where `p.registering` is invisible; the dispatch fence beside it stops a superseded process ANSWERING and cannot invalidate a proof already stored. **A HOST SAYING IT IS RUNNING SOMETHING BEATS A COMPLETED RUN**, and it is the one place the ordinary sweep's telemetry is consulted — the two coexist because a create the provider accepted but has not yet listed is invisible to the barrier's own samples, so a run completes around it and NO FENCE MOVES; it may BLOCK and could never CLEAR, since believing `node_inventory` when it says empty is the design rejected above, and `provenBy` is the single definition the fleet report and the decommission transaction both read so they cannot disagree about one host. **THE PROOF IS TWO OBSERVATIONS, NEVER ONE OBSERVATION AND A CLOCK**: the run's proven span is `observed_at − empty_since`, so an empty answer must land at or after the far end of the grace and the current time does not enter the predicate. Comparing `now` against `empty_since + grace` shipped in the first version and is elapsed wall-clock authorising a claim about a machine — it failed exactly where the grace exists to help, because a host that answered empty ONCE and then disconnected aged into proved with both fences still matching, nothing having happened to move them. Two things bound what it can promise: a host below `nodeapi.VersionComputeBarrier` is never asked (a refusal is not an inventory, and asking burns its single command slot for the full command timeout) and is reported as unprovable; and "every registered node" never converges, because a node row is durable and a start marks the fleet unreachable rather than removing anything — so `billet nodes decommission` bounds the expected set, requires a current proof, and its `--force` form records the exclusion as DURABLY UNPROVEN, which every later drain and `billet status` name rather than reporting the fleet clear. It writes `nodes.drained`, a column the schema has carried since migration 1 that both placement queries read and nothing had ever written. THREE RESIDUALS ARE LEFT OPEN AND SAID SO: two hosts under one name defeats the invalidation, because the refused arrival discards the proof once and the OTHER process rebuilds it over the next few barrier rounds — billet cannot tell them apart, which is what ErrSuperseded's own diagnostic says, and a durable per-name blocker would leave one misconfigured registration permanently unprovable; a registration that BEGINS and then FAILS leaves no durable trace, so the incumbent can re-prove while whatever was arriving is unaccounted for — a durable unsettled-registration fence would close it and its own failure mode is worse, since one failed registration would then block every later drain until a person intervened; and `local down` re-reads the clearance immediately before the first stop, which NARROWS rather than closes the gap between a read in one process and a stop in another's world. Closing that needs the control plane to refuse registrations for the duration of the stop. `--without-compute-proof` is the named escape on both commands and prints a DIFFERENT conclusion; `local down` also skips the stage, saying so, when this host's control plane is not running, since that is what would ask. **MEASURED ON THE REFERENCE HOST, and the measurement changed how the scenario has to be written: a live billet destroys a stray within a reap interval — 45ms after the lease went terminal the node logged `destroying an instance whose lease is gone` — so a test that releases a lease under a running container is racing billet's own orphan sweep and passes or fails on load.** That is correct behaviour and it is also the point: the window this barrier exists for is the one where the host that WOULD sweep is the host being stopped, so `internal/e2e/computebarrier_test.go` runs a real job to completion, stops the control plane, and only then puts a real container carrying a lease name the ledger never issued. **Stopping the control plane is NOT what makes that safe** — cancelling it does not recall a `CommandSweep` the node has already been given, and the node executes commands on its own goroutine — so the stack's reaper tick is set to an hour and no sweep is ever dispatched. Two smaller traps came out of the same review: `provider.List` reports EXITED containers and `Runner.Instances` reports their lease ids just the same, so a stray must be asserted `Running` or a command that returns immediately satisfies every assertion; and a node's drain has no timeout, so the harness's stop has to be reachable from cleanup as well as from the happy path or a failed assertion becomes a hang. The whole chain is real there — a real dispatch, the real node wire, a real container runtime — and the one thing steered is the allocator's clock, through `alloc.WithClock`, moved forward once after the ledger is empty because five minutes of wall clock per run is a test nobody runs.
- **RENEWING A LEASE IS WHAT A PARTY HOLDING COMPUTE DOES, AND A LISTENER THAT RENEWS ONE IT CANNOT REACH THE HOLDER OF BUILDS A LOOP WITH NO EXIT.** The holder-gone defect was recorded at acceptance as billet correctly refusing to free capacity it could not prove idle, with a fresh ledger as the escape. Reproduced against the real CodeBuild backend over the real wire, it was two defects. The one the acceptance actually hit: a completion is bound to the process that launched the build, that process was killed, and the plane refuses to hand the destroy to the replacement (right — a replacement truthfully knows nothing, `TestBoundCompletionIsNotTakenByAReplacementIncarnation`). The listener read `ErrHolderUnavailable` as an ordinary failed destroy and kept the lease in `running` — RENEWED on every heartbeat pass — while it retried. A renewed lease never expires, so it is never quarantined, so the replacement's inventory can never settle it, so every retry gets the same answer for as long as the control plane runs: capacity charged, `billet leases` showing nothing held, `--force` refusing the lease as busy. **The fix is only who renews**: on `ErrHolderUnavailable` the listener parks the obligation WITHOUT the lease (`parkUnreachable`); whoever holds the compute renews it — a draining superseded process, a replacement that adopted the build — and if nobody does the reaper quarantines it within a TTL, which is the identical protection one phase over. The plane then lets the bound completion CORRECT, never settle: when the recorded holder is not the current incarnation (`holderReplacedLocked`) it asks `SettleCompletionOnTerminalLease`, which only rewrites a verdict something else already recorded — the replacement host's ordinary inventory reconcile, a fresh observation after the grace, is what settles the quarantined lease provisionally as `failed`, and the completion's retry corrects that to GitHub's outcome. A first version let the completion settle an open quarantine from the plane's CACHED inventory snapshot, and a review caught that the snapshot has no ordering against the quarantine: one taken before a build became visible and never refreshed (every later listing failed) would free the capacity under a running build. That is the one-observation-plus-a-clock shape the compute barrier removed, one seam over. **THE SAME SHAPE WAS STILL IN THE PLANE'S OTHER BRANCH, and a fifth round took it out**: `dispatchBound`'s not-owned branch — a control plane restarted and forgot the launch, and the host's inventory has not re-adopted the lease — also settled from the cached snapshot, so every completion path that cannot reach its holder (replaced, never replaced, or forgotten) is now correction-only through `SettleCompletionOnTerminalLease`, and `ResolveQuarantineForCompletion` is gone. What settles is a fresh inventory after the grace, or an operator's `--force`; a completion for a host nobody replaced finishes on the forced release rather than answering unavailable for the life of the process. **The owner record ENDS WITH THE LEASE** rather than living until the plane restarts: `MayMutateLease` reads it to keep a draining process entitled to its own renew and release, so it stays while the lease is open, and is dropped when the completion finds the lease terminal — safe only because the wire's `forOwnLease` answers a SUPERSEDED process asking about a lease the ledger has ended with `not_found` (the ledger's own truth, and what custody already treats as done) instead of a refusal it cannot act on — for every route but one. **The runner-removal route PERFORMS the removal instead** (`forOwnOrEndedLease`) — for a superseded process, and for a current one whose owner record a restart or an inventory dropped, which a seventh round found falling through to the placement check's not-found and retrying forever, and ONLY when the history row that outlives the lease attributes the job to the asking node, because an eighth round found membership alone let any registered node name another host's ended lease and withdraw its runner (`alloc.EndedLeaseNode`) — because routing-before-compute holds after the lease is over: a replacement's inventory can settle a lease while the superseded process still runs the guest (two hosts under one name), and that process must withdraw the registration GitHub can route work to before it destroys the guest. The first version answered `not_found` there too and let the node read it as a removal it never performed, which a review caught; the node insists on the removal, and measured, without the wire performing it a superseded process's drain never ended. **AND A START REPAIRS THE TOKEN OF A REASON THAT LANDED BEFORE IT**: GitHub's messages and the node wire are unordered, so `launch-failed` can be recorded after the job began and before JobStarted is processed; `recordJobStartTx` looks back on the busy edge, on a pooled runner's start and on repeated reports of either. **AND A PARKED LAUNCH FAILURE KEEPS ITS REASON ACROSS THE REAPER**, which reaches a parked release first — quarantining a `launching` lease, failing an escrow-only one outright, at a moved epoch the fenced release cannot reach — so `ResolveQuarantineFailed` and `ReleaseFailed`'s terminal branch explain a failed row nothing explains yet (`BackfillFailureReason`). **INVENTORY'S PROVISIONAL VERDICT READS THE RESULT GITHUB ALREADY RECORDED**: the listener writes `job_history.result` before it dispatches any destroy, so a teardown holder that dies with the completion delivered leaves a lease carrying GitHub's word, and `ResolveQuarantineFor` settles such a lease as `done` with no provisional marker — no correction is coming, because the completion already came; the first version archived those jobs as `failed`. **A CONCLUSIVE LAUNCH FAILURE ARCHIVES ITS REASON** through `alloc.ReleaseFailed`, one transaction for the release and `LaunchFailedReason`, on the direct path and the parked retry alike. **AND THE DISRUPTION TOKEN IS DECIDED BY THE LEDGER'S EVIDENCE BEFORE THE REASON'S TEXT**: `job_history.started_at` is written when a lease reaches `busy`, so `launch-failed` or `runner-retired` sent over the wire for a job the ledger saw start — the forgery round four left open — records `reclaimed` like any other text, and `MarkFailure` refuses `force-released`, which only the operator's command writes. What a node can still choose is WHICH disruption a job that ran carries, and every one of them is a disruption. The draining superseded process is covered end to end (`TestASupersededProcessDrainsTheJobItHoldsWhileTheCompletionWaits`), the whole scenario runs against real CodeBuild under `BILLET_TEST_CODEBUILD_PROJECT` (`holdergone_live_test.go`), and the real-process re-run is in `docs/aws-acceptance.md`. **The issue's own hypothesis — a killed custody/teardown holder leaving `force=requested` forever — did NOT reproduce**: nothing renews such a lease once its process dies, it is quarantined within a TTL, and `release --force` releases it from there, so `ForceRelease` keeps its semantics (an epoch that moved is equally a superseded process draining, and resolving underneath it is the double-owner the fence exists to prevent). What that reproduction found was a restart re-adopting a still-running TEARDOWN as custody, which `validTransitions` refuses, so every tend failed and the build was never stopped; the adoption keeps the phase it found. **AND THE FIX FOR THAT HAD THE SAME SHAPE ONE LAYER DOWN**: a teardown's OUTCOME lived only in the custody entry of the process that decided it, the ledger recorded the phase, and teardown serves a completed job and a failed launch alike — so the restart archived `done` for an ambiguous launch that never ran. The node now writes `alloc.LaunchFailedReason` through `MarkFailure` as soon as its epoch is current — a heartbeat or a re-adopted quarantine — and before anything touches the provider, adoption reads it back, and the disruption token is chosen by the EXACT reason: none for a launch that never ran, a retired runner or a forced release, `held-past-limit` for a job billet destroyed under the custody bound, and `reclaimed` for everything else including text that merely starts with `billet:` (the reason arrives over the wire, so a prefix rule was forgeable — a third review round). A forced release records `ForceReleasedReason` with the request. The idempotent hold report re-records the holder (`RefreshLeaseHolder`) so the process tending a lease is the one named. `leases.holder_incarnation` beside `nodes.incarnation` (migration 45) records the INCARNATION of the process holding the compute at Bind and on entry to custody/teardown — never the registration epoch, which the same review caught: the epoch moves on every registration and the same process registers again after every control-plane restart, so an epoch comparison would have reported every surviving lease's holder as replaced after an ordinary restart. `billet leases` renders it as `process <incarnation>, REPLACED by <incarnation>`, and `billet status` lists running leases whose holder was replaced under `bound` — a REPORT, never a verdict. All of it is in `internal/e2e/holdergone_test.go`, which runs the real listener, plane, wire, node loop and CodeBuild provider against a fake AWS and needs no Docker.
- **A DRAIN NEVER DESTROYS A RUNNING JOB, AND NOTHING TIMES IT OUT.** The listener's shutdown used to bound its wait by `drain_timeout` and then destroy whatever was still running, which made a timer the thing that failed somebody's build — and GitHub does not requeue a job whose runner vanished after starting. A job may run for days and billet imposes no job limit, so elapsed time is not evidence that one stopped making progress. `destroyAll` now takes `includeRunning`: `cleanup` holds destroys a completion ALREADY ASKED FOR, so tearing one down ends nothing, while `running` holds work still executing — a shutdown passes false and only an operator passes true. What a stop leaves behind is deliberate: the guests keep running, the node keeps holding them, the leases stay CHARGED (freeing a slot whose container is live is the overcommit the ordering exists to prevent), and the next control plane re-adopts them through `ServiceableRunnerLeaseIDs`. A second signal ends the WAIT and not the work. **`billet force-destroy` is the ONE thing that passes `includeRunning: true`**, and `TestOnlyTheForceOperationDestroysRunningWork` asserts that structurally — nothing in the type system separates the two booleans, so the next teardown path added could pass true with no test failing anywhere and the loss would be somebody's build during the next restart. It refuses unless admission is already sealed by an operator, and its target set is FIXED when the request is taken: a standing flag would destroy every job launched after it, which is a timer authorising a teardown wearing different clothes. `drain_timeout` survives as the point where `warnDrainOverrun` starts saying the drain is long, repeating every fifteen minutes because a threshold crossed silently is a fleet that looks wedged and an operator whose next move is to kill the process; it has no maximum, since a value too large now costs a quieter log rather than a build. The `TimeoutStopSec` in the packaged units is no longer sized from it — a SIGKILL mid-drain loses billet's bookkeeping, not the jobs.
- **A NODE THAT EXITS CLEANLY WITHDRAWS FROM PLACEMENT, AND SILENCE STILL MEANS NOTHING.** `systemctl stop` on an idle node is a SIGTERM, which drains and exits in under a second — and nothing told the control plane. It kept the host in `Plane.nodes` (so `pick` chose it) and the ledger kept `live = 1` (so escrow set `target_node` to it), and the next job for that site sat on the stopped host until `expireStaleLocked` forgot it a `staleAfter` later, at which point the queued launch was answered "nothing started" and GitHub reassigned: five minutes late, measured on the site acceptance. Shortening the silence window was never the fix, because a partition and a crash are the same observation from the plane and the compute barrier and custody both rest on that caution. What was missing was a message from the one authority on the node's intent: `POST /v1/nodes/{node}/withdraw` (wire 19, `nodeapi.VersionNodeWithdrawal`), sent by `stopGracefully` AFTER its wait on every exit — idle, drained, or cut short by a second signal — and never by a superseded process. **A withdrawal releases nothing and marks nothing.** `alloc.NodeWithdrawn` writes `live = 0` fenced on BOTH the registration epoch and the incarnation (a superseded process still holds the certificate and the name) and deliberately does not call `markNodeDisruptedTx`, touch `drained`, or discard the barrier run; `Plane.Withdraw` writes the ledger FIRST and drops the node from memory second, so a ledger blip leaves the host placeable until the ledger answers or the host goes silent — today's behaviour, not a new one. Commands the node never took are answered "nothing started", as after silence; one still in flight is tombstoned as a re-registration tombstones it. It is checked where it is EMITTED: an older control plane answers the route with a bare 404, so a node negotiated below 19 stops as before and says the plane is too old to be told.
- **Registration and the operator CLI both work against a running control plane.** `Plane.Register` never asks whether a host was declared — it negotiates a mutually supported protocol version, then checks a non-empty name, the deployment identity, a non-zero contribution, that the site is one the deployment declares, and that the node's provider matches that site's authoritative store (`WithSites`, wired from `cfg.Sites`), after which the allocator requires a provider and refuses a provider or site change while leases are outstanding. So `nodes:` is policy about hosts rather than a roster of them. Operator commands reach the ledger through `state.OpenAdmin`, which does **not** take the exclusive state-directory lock when a control plane already holds it — the lock stops two control planes, not two processes, and a one-shot command is not one. It still takes the lock when free (a fresh install runs `ca issue` before any server), and when it cannot, it VERIFIES the schema instead of migrating: a newer CLI must never upgrade a database a running plane is mid-transaction against, so it returns `ErrSchemaBehind` naming which side to restart. Only `runServer` uses `state.Open`. Two rules follow from a second process writing: every write transaction begins IMMEDIATE (`_txlock`), because a DEFERRED one that reads first cannot promote its snapshot once anything else commits and fails with `SQLITE_BUSY_SNAPSHOT` — which `busy_timeout` cannot rescue; and contention is retried rather than returned, because an escrow error stops the listener and destroys every job on the host — the control plane retrying until its context ends, an operator command giving up after `adminBusyLimit` because a person is waiting on it. A read-only operation therefore belongs on `DB.View` (the query-only pool), never `DB.Tx`, or it reserves the single writer slot while it scans. Tiers are read at startup and each becomes one scale set, and `nodes:` is snapshotted into `alloc.New`, so changing either needs a restart.

## Decisions written down

`docs/adr-001-control-plane-hosting.md` — where the control plane runs and what stores its state. A single small EC2 with SQLite on EBS, recovered by EC2 auto-recovery (NOT an ASG — an ASG launches a fresh instance that does not reattach the data volume). DynamoDB was considered and rejected for now: feasible, saves nothing, costs a rewrite of the two most invariant-dense packages.

The fact that resized that decision: **GitHub queues a job for 24 hours when no matching runner is available.** A dead controller delays CI rather than failing it, so the requirement is "recovers in minutes", not HA.

`docs/adr-002-cloud-compute-backend.md` — which AWS service runs a job, and why billet signs its own requests. EC2 instance-per-job, because a GitHub Actions job runs Docker and Fargate cannot (*"privileged containers or access are currently unavailable on Fargate"* — so no Docker-in-Docker, and no block device for the caching plane either). Lambda is capped at 15 minutes against a 6-hour job. CodeBuild's native webhook runner integration would replace billet rather than serve it; a Billet-owned API provider that preserves escrow and placement became the CodeBuild backend (ADR-007). The SDK was rejected on a measurement: 13.2MB and 15 modules for one `RunInstances`, against a whole billet of 21.8MB and 4 direct dependencies, carried by every node including the bare-metal ones this exists to fall back from.

**An ec2 node is a serial launch queue.** The node runtime executes one command at a time (`Poll` → `execute` → `Report`), which is unremarkable for a backend where one node is one machine's worth of jobs and very visible for one where a single node can represent 64. The command timeout is 10 minutes, ample at normal latencies and tighter under throttling-plus-retries. Run several ec2 nodes if that binds; each is separately registered with its own budget.

`docs/adr-003-ceph-rbd.md` — why every cache is an RBD image in a Ceph cluster on the nodes' own NVMe, and why the ZFS pool it replaced was destroyed rather than kept beside it. A ZFS clone exists only on the machine that took it, which was the storage half of billet being a one-machine product; the property was verified by mapping a clone from a second kernel client. It also records what building it measured: clone + map + mount is ~350ms for a 10GiB image, sequential reads reach 4.5 GB/s at depth (the ≈2 GB/s the caching plane assumes), and 4k synchronous writes are 14x slower than the same disks locally on a synthetic benchmark — a number the build measurements below put in its place. Two findings there are load-bearing rather than trivia: **clone v2 is a requirement, not a preference** (as `cephadm` leaves a cluster, a snapshot must be protected before it can be cloned, and a protected snapshot with a live clone cannot be deleted — so eviction would be blocked by ordinary traffic), and Ubuntu 26.04's uutils coreutils breaks `cephadm bootstrap` in a way that reads as a Ceph bug.

**The cluster is a precondition billet CHECKS, not one it hopes for.** `billet check` refuses a cluster that would clone the old way, because on clone v1 a protected snapshot with a live clone can be neither unprotected nor removed — so a cache generation any running job holds would be undeletable and eviction would be blocked by ordinary traffic. Refusing now is a judgement about when the cost lands: nothing clones yet, so the fix is one command on an empty cluster.

**TWO settings decide it and either can be the cause**, which is the trap: `require-min-compat-client` is the floor, and `rbd_default_clone_format` overrides it — settable cluster-wide OR per pool, and measured, the DESTINATION pool's value is the one that governs a clone. billet reads both, for both pools, and names whichever is the cause with the command that removes it, because `ceph config rm client …` does not remove a pool-level override. Checking the floor alone was the first version and it was a proxy for the property, which is the mistake this area kept producing: the floor standing in for the format, one pool standing in for both, and a value validated in one of its two consumers.

The release rule is written as "not one of the releases OLDER than mimic", because that set can never grow while a list of recent releases goes stale on the next Ceph release and starts refusing correct clusters. That direction is fail-open, so the answer must first be release-shaped, and `unknown` — Ceph's enum zero value, which the setter refuses — counts as older, because a cluster that was never told takes the old format and its operator needs the same one command. Pool replication is reported and not judged: how many copies to keep is the operator's decision, but it is invisible from the config file.

**A real build on RBD costs 2%, and the fio number that said otherwise was measuring a machine that does nothing but IO.** Measured: `go build` with a cold cache 1.02x, fsync-per-file 2.36x, and a COLD read of 40,000 small files **4.07x** — the expensive one, and the opposite of what the synthetic table predicted, because 40,000 small reads are IOPS-bound rather than sequential. That is also the cache-hydrate path, and the baseline that decides whether a sticky disk is worth having is re-fetching over the network, not a local disk a second machine cannot see. Readahead and ext4 stride alignment moved nothing; the defaults are what the numbers were taken on.

`docs/adr-005-runner-image-parity.md` — why matching GitHub's hosted runner image is a REBUILD and not a copy, and what that costs. **GitHub does not publish the image its runners boot**: `actions/runner-images` is Packer source whose only builder targets Azure, and every image release's only asset is a ~50KB `internal.<image>.json` — checked against the releases API, not inferred. What it does publish is enough to rebuild: `toolset-2404.json` declares every apt package, toolcache line, JDK, NDK and pinned version, and about eighty plain bash installers sit beside it. So billet vendors that declaration into `internal/runnerimages`, pinned by upstream commit plus its own sha256, and BOTH the shell build and the Go side read it — two hand-maintained package lists in two languages is the `runnerrelease` bug wearing different clothes. The digest is verified on both paths, because a check on only the Go side leaves the thing that actually builds the image trusting whatever is on disk. The costs it accepts, and the numbers an operator inherits — measured now rather than projected: the guest image is **15.0GiB** used against 2.6GB before, and the EC2 image is **26.8GiB** on x64 and 24.9GiB on arm64, the difference being the Android SDK the guest deliberately omits. Retention is **per guest contract**, not per cluster, so `--keep 3` at `size=2` is about **90GiB of content per contract** plus any pinned generations — during a contract migration two contracts are live at once, which is the number to size a cluster against rather than the single-contract one; a release asset caps at 2 GiB so the rootfs is published as ordered parts under manifest schema 2; and the reader learned that schema and SHIPPED before the writer emits it, because a reader accepts exactly the schemas it knows and publishing one it does not is a flag day the fleet cannot pull its way out of. It also records why **an AMI is verified by BOOTING it**: every other claim a build makes is checked on a builder that has been apt-installed, part-configured and never rebooted, and the Docker gate read `overlayfs` off exactly that machine while the image itself reports `overlay2` — so `billet ami build` launches the produced image, asserts on it, and only then writes the contract tag with `CreateTags`. The tag IS the promotion; an image billet has not booted carries none. Measured end to end on 2026-08-28: provisioning 3m54s, snapshot-to-available 11m06s, and a complete console report 4m40s after the verifier launched, reporting `docker_driver=overlay2` on the fresh boot. **A TagSpecification on CreateImage is authorized as a SEPARATE `ec2:CreateTags` check** keyed on `ec2:CreateAction`, which the bundled builder policy did not list — measured with `create-image --dry-run` under that policy: the same call succeeds without tags and fails `UnauthorizedOperation: ec2:CreateTags` with them.

`docs/adr-006-rollouts.md` — why upgrading a fleet is ONE durable decision resolved to a manifest digest rather than a per-host version, why compatibility is decided before anything stops, and why the host transaction's ORDER is its safety content. It also records the one duplicate this left standing: the Ansible `host` role and `billet host-upgrade` both implement the transaction ordering, and consolidating them means running the role's test suite against the Go command first — replacing a proven implementation with an unproven one to remove a duplicate is the wrong trade.

`docs/adr-007-codebuild-provider.md` — the second AWS backend, and why it does NOT use CodeBuild's own GitHub Actions runner integration. That feature is webhook-only (a "Runner project" plus a `WORKFLOW_JOB_QUEUED` webhook plus a `codebuild-<project>-${{ github.run_id }}-…` label, with CodeBuild fetching the registration token itself and overriding the buildspec), checked against the API reference rather than inferred — so billet starts an ordinary `NO_SOURCE` project with `StartBuild` and runs GitHub's runner from its own JIT config, exactly as the EC2 backend does inside an instance. It also records the two EXTERNAL ceilings a CodeBuild tier inherits (a 36-hour build maximum, and a queued build that fails after at most 8 hours), why `node.codebuild.accept_external_build_ceiling` has no default, why UNTRUSTED WORK IS REFUSED on every CodeBuild fleet — AWS documents reserved-capacity instances as surviving between builds and sharing cached data across projects in the account, by design, and macOS is reserved-only — and the seven things about that API which have to be MEASURED rather than read.

`docs/adr-008-state-backends.md` — SQLite and PostgreSQL as two backends behind one contract, and the measurements that decided the shape. **ONE QUERY SET SERVES BOTH ENGINES, and that was measured rather than hoped for**: with integer casts spelled `BIGINT`, sqlc's SQLite and PostgreSQL engines emit BYTE-IDENTICAL Go from the same query file — same structs, field names, field types, method signatures — differing only in `?N` against `$N`, and modernc.org/sqlite executes `$N` correctly (bound positionally, a repeated `$1` bound once, a `$2` appearing textually before `$1` resolved). So generation runs ONCE with the PostgreSQL engine, because a `$N` constant runs on both and a `?N` constant does not; the planned alternative was ~135 hand-written dialect-neutral types and about fifteen thousand lines of conversion. What it costs is that `sqlc diff` checks one catalogue, and `TestEveryGeneratedQueryPreparesAgainstTheMigratedSchema` covers the SQLite side more strongly than a catalogue would. What it constrains is PORTABILITY: `max(a, b)` is a scalar on SQLite and an aggregate on PostgreSQL (`GREATEST` is the trap facing the other way), so the answer to a statement that will not generate is the portable spelling, never a second query set. Driver measured against billet's own binary: 40.25MB → 45.49MB, +5.24MB and four modules for pgx; ADR-002's rejection of the AWS SDK does not transfer, because there the dependency could be replaced by six hundred lines pinned to AWS's own output and the PostgreSQL wire protocol cannot.

`docs/adr-009-controller-election.md` — the election behind a failover, the standby runtime, and shared deployment identity. The election IS the session advisory lock plus the epoch fence: a controller is dead when its SESSION is, decided by PostgreSQL, so there is no lease, no renewal clock and no failure detector, and the residual (a predecessor writing BEFORE a successor claims) is the ordinary fencing-token limit. It records why the claim rather than the directory flock authorises a migration on a shared ledger, why an operator command still migrates an unheld one and gives the exclusion straight back, why a standby's write refusal is structural rather than a rule its runtime remembers, why the layout is a config key rather than a flag or a default, and why shared identity is REPLICATION over the file layout rather than an authority that lives in a store. Eight alternatives are recorded as rejected with the reason each fails.

`docs/upgrades.md` is the operator's version of the same thing, and `docs/action-versioning.md` states the `@v0` tradeoff plainly rather than calling one form safe. `docs/codebuild.md` is the operator's version of ADR-007.

`docs/upstream-references.md` records what billet takes from other people's code and what it deliberately does not. Read it before reimplementing anything that touches the scale-set protocol. Two things from it that come up constantly:

- **`github.com/actions/scaleset` is the answer to most protocol questions**, and usually the only answer, because the API is not documented elsewhere.
- **billet is not actions-runner-controller without Kubernetes.** ARC does not track individual jobs; its whole scaling decision is `min(MinRunners+TotalAssignedJobs, MaxRunners)`, and Kubernetes absorbs scheduling, queueing and placement. billet has fixed hardware, a per-machine budget under a deployment ceiling, and placement constraints that need a lease bound to a specific host.

## Codex compatibility

This repo also supports OpenAI Codex, which reads the cross-tool standard paths. **Claude's files are canonical**; the standard paths are committed symlinks. Never create a real file at a symlink path, and never edit `AGENTS.md` — you would be editing the `CLAUDE.md` it points to.

- `AGENTS.md -> CLAUDE.md`
- `.agents/skills/<name> -> ../../.claude/skills/<name>` for every skill. **Add the symlink in the same PR that adds a skill**, and keep `SKILL.md` frontmatter strict YAML: quote any description containing `:`, because Codex rejects YAML that Claude tolerates.
- `.codex/config.toml` raises `project_doc_max_bytes`; keep it if you touch Codex config.

## Platform support

Linux (amd64, arm64) and macOS (arm64). A Windows port needs an equivalent of the `flock`-based state lock.
